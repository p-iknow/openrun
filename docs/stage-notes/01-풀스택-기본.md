# 1단계: 풀스택 기본

## 선택 이유

- **TypeScript 6.0:** 최신은 7.0이지만 `@nestjs/cli`가 `typescript ~6.0.2`에 의존한다.
- **타입 정보를 쓰는 린트:** `no-floating-promises`로 `tsc`와 일반 린트가 잡지 못하는 `await` 누락을 찾는다.
- **시각적 방향 A(부드러운):** 기존 예매 사이트를 조사해 정보 구조는 업계 관습을 따르고(`docs/research/ticketing-ui-benchmark.md`), 시각 표현은 프로토타입 두 개를 목록·상세, 데스크톱·모바일로 비교해 골랐다. 프로토타입은 `prototype/store-visual-direction` 브랜치에 남겼다(#18).
- **번호 페이지:** 업계는 무한 스크롤이나 더보기를 쓴다. 그래도 서버 렌더링, 주소(`?page=`)로 공유, 9단계의 깊은 오프셋 측정을 위해 번호 페이지를 유지한다(#18).
- **TDS 라이트 팔레트와 의미 토큰 두 단계:** 기본 팔레트는 `@theme` 밖의 CSS 변수로만 두어 `bg-blue-500` 같은 클래스가 생기지 않게 하고, 화면 코드는 의미 토큰(`primary`, `text-secondary` 등)만 쓴다. 색의 쓰임이 이름에 드러나고, 테마를 바꿀 때 토큰 값만 고치면 된다(#20).
- **`-subtle` 바탕에는 `-strong` 글자:** `primary`(blue500)는 blue50 위에서 대비가 약 3.3:1이라 작은 글자의 WCAG AA(4.5:1)에 못 미친다. Badge와 고른 칩이 이 규칙을 따른다(#20, #25).
- **Pretendard를 npm 패키지와 `next/font/local`로:** 버전이 lockfile에 묶이고 Storybook도 같은 파일을 쓴다. Next가 만든 대체 글꼴 크기 보정으로 레이아웃 흔들림을 막는다(#20, #21).
- **`store-ui`를 tsc로 파일별 빌드:** 번들러로 묶으면 파일별 `'use client'`가 사라진다. 스토어 Tailwind는 `@source`로 `dist`를 읽는다(#20).
- **Storybook 빌드를 `build`와 분리한 `build-storybook` 작업:** `^build`에 의존하는 스토어의 `dev`·`typecheck`·`test`가 Storybook 빌드를 기다리지 않게 했다(#21).
- **서버용 Pagination(`render`로 링크를 받는 compound):** 주소 규칙은 앱이 정하고 store-ui는 모양과 접근성 속성만 맡는다. `'use client'`가 없어 브라우저로 자바스크립트를 보내지 않는다. 이전·다음의 비활성은 필수 `disabled`로 받아, 빠뜨리면 타입 검사에서 걸린다(#23).
- **`export * as Drawer`:** `'use client'` 파일에서 만든 객체는 Server Component에서 속성을 꺼낼 수 없다. 부품을 이름으로 내보내고 서버에서 실행되는 `index.ts`가 namespace로 묶는다(#25).
- **입력 컴포넌트와 칩은 흰 바탕 테두리형:** 프로토타입의 회색 면이 실제 컴포넌트에서는 어둡게 보여, 입력 칸임이 테두리로 바로 드러나는 모양으로 바꿨다(#24, #25).

## 쓰지 않은 기술

- **Jest:** 스펙이 Vitest를 정했다.
- **Vitest의 SWC 플러그인:** Vite 8의 기본 변환(Oxc)이 tsconfig의 `emitDecoratorMetadata`를 읽어 데코레이터 메타데이터를 만든다. `import type`, `@Inject(TOKEN)`, enum까지 SWC와 결과가 같았다. 두 변환 모두 타입 정보가 없어 `import type`으로 받은 클래스와 enum에서는 `tsc`와 다른 값을 남기므로, SWC를 둬도 이 차이는 줄지 않는다(#14).
- **시각적 방향 B(단정한 잡지형)와 다크 방향:** B는 비교에서 고르지 않았고, 다크는 TDS 공개 팔레트에 다크 값이 없어 비교에서 뺐다. 다크 모드도 지원하지 않는다(#18).
- **`@toss/tds-colors` 패키지:** license 필드가 없어 설치하지 않고, hex 값과 출처 URL만 옮겨 적었다(#18).
- **CSS-in-JS:** Server Component에서 쓰려면 정적 CSS가 맞다. Tailwind 클래스와 토큰 CSS만 쓴다(#18).
- **번들러로 묶는 `store-ui` 빌드:** 위의 `'use client'` 문제 때문이다(#18).
- **DOM 테스트 환경(happy-dom, Testing Library):** 사실상 Base UI의 동작을 다시 테스트하게 된다. 동작이 있는 Pagination은 `react-dom/server`로 서버 렌더링 HTML을 확인하고, 나머지는 Storybook과 접근성 애드온으로 확인한다(#23, #24).
- **Pagination의 `baseUrl`·`queryName` props와 `getPageHref` 함수 prop:** 앞의 것은 앱의 라우팅 정책이 디자인 시스템에 들어오고, 뒤의 것은 Server Component에 함수 prop을 넘기지 않는다는 규칙을 깬다(#23).
- **처음부터 제어 컴포넌트로 만들기(`value`):** TextField, Select, ToggleGroup은 주소 값을 `defaultValue`로 채우는 비제어로만 둔다. 필요해지면 1.3에서 추가한다(#24, #25).
- **브라우저 기반 스토리 테스트와 시각적 회귀 테스트:** 2단계나 `/retro`에서 검토한다(#18).

## 회고

예상과 달랐던 점:

- Vitest의 SWC 플러그인이 DI에 필요하다고 생각했지만, 플러그인 없이도 생성자 주입이 동작했다. 조사해 보니 Vite 8이 이 기능을 기본으로 지원해서 플러그인을 뺐다.
- 루트 린트 설정이 Turborepo 입력에 없어 린트가 잘못 통과했다. 코드 리뷰에서 발견했다.
- `@ApiProperty`의 `type`을 빼고 tsx로 OpenAPI 명세를 만들면 타입이 빈 명세가 나올 줄 알았지만, 생성이 "순환 의존" 에러로 멈췄다.
- `'use client'`가 빠지면 빌드가 실패할 줄 알았지만, Base UI 컴포넌트를 감싸기만 하는 Button은 지시어 없이도 빌드가 통과했다. Base UI 파일에 이미 지시어가 있기 때문이다. 지시어가 빠져도 동작은 같고(함수 prop은 어느 쪽이든 Base UI 경계에서 거부된다), 훅을 추가하면 빌드가 잡는다. 그래서 자동 검사를 두지 않고, 지시어는 클라이언트용이라는 분류를 드러내는 관례로 둔다(#22).
- Tailwind 기본 테마를 지우자 `tailwind-merge`가 `text-caption`을 글자색으로 보고 `text-text`와 합칠 때 지웠다. `cn`에 토큰 이름을 알려 주고, 토큰을 추가하고 `cn`을 빠뜨리면 실패하는 테스트를 뒀다(#21).
- `'use client'` 파일에서 `Drawer` 객체를 만들어 내보내자 Server Component에서 `Drawer.Root`가 undefined가 됐다. 서버용인 Pagination에는 없던 문제다(#25).
- 포커스 테두리 색을 focus 변형에서만 정하자 `transition-colors` 때문에 0.15초간 검정에서 파랑으로 깜박였다. 평소 상태에 색을 두어 Button, Pagination까지 함께 고쳤다(#24).
- 프로토타입에서 고른 회색 면 입력과 칩이 실제 컴포넌트에서는 어둡게 보여 테두리형으로 바꿨다. 프로토타입은 목록과 상세 화면 위주라 입력 컴포넌트의 모양까지는 검증하지 못했다(#24, #25).
- 굵은 글자가 폭을 바꿔 칩 크기가 흔들렸다. 한글은 굵은 쪽이 오히려 좁은 경우도 있어(0.3px), 두 굵기를 같은 grid 칸에 겹쳐 넓은 쪽 폭을 쓰게 했다(#25).
- Pagination은 `baseUrl` props, `render` 생략 시 비활성, 필수 `disabled` 순으로 세 번 설계를 바꿨다. 디자인 시스템이 무엇을 모르게 할지(주소 규칙)를 먼저 정했으면 더 빨랐다(#23).

## 면접 대비

### `import type`으로 가져온 서비스는 왜 주입되지 않는가

`import type`은 컴파일 후 지워져서 `emitDecoratorMetadata`가 생성자 타입을 클래스 값으로 남기지 못한다. NestJS는 이 메타데이터로 주입 대상을 찾으므로 앱을 조립할 때 실패한다. `tsc`는 타입이 맞는지만 보기 때문에 통과한다. 그래서 앱을 실제로 조립하는 테스트가 필요하다.

### Turborepo 캐시는 어떻게 실패를 통과로 보여 주는가

입력이 캐시 해시를 정하므로, 입력에 없는 파일이 바뀌어도 해시는 그대로다. 그러면 작업을 실행하지 않고 지난 결과를 재생한다. 루트 린트 설정을 입력에 넣지 않았을 때 규칙을 추가해도 "0 errors"가 나온 이유다. 결과에 영향을 주는 것은 모두 입력에 넣어야 한다.

### 잠금 파일과 공개 대기 기간은 무엇을 막는가

잠금 파일은 설치되는 내용이 바뀌는 것을 막지만, 잠긴 버전 자체가 악성이면 막지 못한다. `minimumReleaseAge`는 새 버전을 고를 때 공개 직후 버전을 피할 뿐이고, 대기 기간이 지난 악성 버전은 막지 못한다. `minimumReleaseAgeExclude`는 이 대기를 건너뛰는 면제 목록이다. 잠긴 악성 버전은 잠금 파일을 안전한 버전으로 갱신해야 하고, 그 버전을 실행한 환경의 비밀값도 교체해야 한다.

### 시드가 비우고 다시 넣는 도중 실패하면 테이블은 어떻게 되는가

시드는 `TRUNCATE ... RESTART IDENTITY`와 `INSERT`를 한 트랜잭션으로 묶는다. 1.3부터는 `TRUNCATE performances, shows, venues`로 세 테이블을 한 문장에서 비우고, 공연장, 공연, 회차를 모두 같은 `db.transaction` 콜백 안에서 넣는다(#39). 공연 10개를 넣은 뒤 콜백에서 오류가 나면 Drizzle이 `ROLLBACK`을 보내 넣은 공연과 `TRUNCATE`가 함께 취소되고, 시드 전 데이터가 그대로 남는다. 도중에 연결이 끊기면 PostgreSQL 서버가 끝나지 않은 트랜잭션을 스스로 롤백한다. PostgreSQL의 `TRUNCATE`는 트랜잭션 안에서 롤백되고, `RESTART IDENTITY`로 되돌린 id 번호도 함께 롤백된다. 그래서 테이블은 시드 전 상태로 남는다. 로컬 DB에서 `BEGIN; TRUNCATE; ROLLBACK;`으로 확인했다. 트랜잭션이 없으면 `TRUNCATE`는 즉시 확정되고, 끊긴 `INSERT`는 문장 하나라서 통째로 취소되므로 빈 테이블이 남는다. 행 일부만 들어간 상태는 어느 쪽에서도 생기지 않는다. MySQL의 `TRUNCATE`는 암묵적으로 커밋되어 롤백되지 않으므로, 이 방식은 PostgreSQL이라서 안전하다.

### 테스트에서 앱을 닫지 않으면 무엇이 깨지는가

통합 테스트는 테스트마다 앱을 새로 조립하고, 그때마다 `DatabaseModule` 팩토리가 새 Pool을 만든다. `app.close()`를 빼면 `onApplicationShutdown`이 불리지 않아 Pool이 닫히지 않고 쌓인다. 테스트 2개를 돌리면 앱 연결 2개가 남는 것을 확인했다. 테스트가 PostgreSQL의 `max_connections`(기본 100)보다 많아지면 그 뒤 테스트는 `sorry, too many clients already`로 실패한다. `max_connections=5`인 컨테이너에서 6번째 앱부터 이 에러가 나는 것을 확인했다. 원인은 앞선 테스트에 있는데 실패는 뒤쪽 테스트에서 나므로, 하나만 돌리면 통과하고 순서에 따라 실패하는 테스트가 바뀌어 찾기 어렵다. 이 환경에서는 Vitest가 worker를 정리하고 컨테이너도 멈추므로 프로세스가 멈추지는 않았다. `onApplicationShutdown`은 Pool의 수명을 앱의 수명에 묶어 이 문제를 막는다.

### 스키마 파일을 하위 폴더로 옮기면 어떤 마이그레이션이 생기는가

`drizzle.config.ts`의 `schema: './src/db/schema'`는 폴더 한 단계만 읽는다. `shows.ts`를 `shows/table.ts`로 옮기면 drizzle-kit은 `shows` 테이블이 사라졌다고 보고, 다른 테이블 파일이 이미 있으면 경고 없이 `DROP TABLE "shows" CASCADE;`를 생성한다. `CASCADE`라서 참조하는 외래 키도 함께 지운다. 스키마 파일이 하나뿐이면 `No schema files found`로 실패하고, 같은 때 새 테이블이 생기면 이름 변경인지 묻는 대화형 질문이 나온다. 세 경우 모두 실험으로 확인했다. 막는 장치는 둘이다. PR에서 생성된 SQL을 읽는 것, 그리고 실제 마이그레이션을 적용하는 통합 테스트다. DROP 마이그레이션이 있는 상태에서 통합 테스트가 `relation "shows" does not exist`로 실패하는 것을 확인했다.

### OpenAPI 명세를 왜 tsx가 아니라 빌드한 `dist`에서 만드는가

`@nestjs/swagger`는 `@ApiProperty`에 `type`이 없으면 `design:type` 메타데이터로 속성 타입을 정한다. tsc는 `emitDecoratorMetadata`에 따라 `__metadata("design:type", String)`을 코드에 남기지만, tsx가 쓰는 esbuild는 타입을 분석하지 않아 이 줄을 만들지 않는다. `ShowDto.title`의 `type`을 빼고 실험하니 `dist`에서는 `"type": "string"`이 나왔고, tsx에서는 `A circular dependency has been detected (property key: "title")` 에러로 생성이 멈췄다. swagger가 `undefined`를 순환 import 때문에 아직 정의되지 않은 클래스로 보기 때문이다. 생성기가 파일을 쓰기 전에 멈추므로 `openapi.json`은 바뀌지 않는다. 틀린 명세가 조용히 생기지는 않지만, 서버에서는 문제없는 코드가 명세 생성에서만 엉뚱한 메시지로 실패한다. 그래서 서버와 같은 tsc 산출물에서 명세를 만든다.

### API 계약이 바뀌면 스토어의 타입 오류는 언제 보이는가

`@openrun/api-client`는 `exports`로 `dist`를 내보낸다. 그래서 `openapi.json`이 바뀌어도 `client:generate`와 api-client `build`가 다시 돌기 전에는 `dist`의 타입이 예전 그대로이고, 스토어를 연 에디터는 오류를 보여 주지 않는다. 커밋할 때는 pre-commit의 `pnpm typecheck`가 `client:generate`(입력인 `openapi.json`이 바뀌어 캐시 미스) → api-client `build`(스토어 `typecheck`의 `^build`) → 스토어 `typecheck` 순서로 돌아 오류를 드러내고 커밋을 막는다. `--no-verify`로 건너뛰면 다음 커밋의 pre-commit이나 직접 돌린 `pnpm typecheck`·`pnpm build`에서야 드러나고, 원인과 상관없는 커밋이 막힌다. 패키지를 소스가 아니라 `dist`로 내보내기로 한 결정의 대가다.

### `preview: true` 없이 OpenAPI 명세를 만들면 무엇이 실패하는가

Nest가 프로바이더를 실제로 만들면서 `DatabaseModule` 팩토리의 `readEnv()`가 `필수 환경 변수가 없습니다: DATABASE_URL`을 던지고, `pnpm openapi:generate`가 실패해 pre-commit이 커밋을 막는다. 셸에 `DATABASE_URL`을 설정해도 똑같이 실패하는 것을 확인했다. 셸 환경 변수는 보통 자식 프로세스로 그대로 넘어가지만, Turborepo 2는 기본이 strict 모드라 `turbo.json`에 선언한 환경 변수만 작업에 넘긴다. 선언한 값은 캐시 키에 들어가므로, 선언하지 않은 값이 결과를 바꿔 캐시 판단이 틀어지는 것을 막는 장치다. `openapi:generate`는 `env`를 선언하지 않았고 `--env-file`도 붙이지 않아 `.env`도 읽지 않는다. 반대로 접속할 수 없는 주소라도 `DATABASE_URL`이 있으면 생성은 성공했다. pg Pool은 첫 쿼리 때 연결하고, 명세 생성은 쿼리를 보내지 않기 때문이다. 그래도 가짜 `DATABASE_URL` 대신 `preview: true`를 쓴다. 부팅할 때 접속하는 프로바이더(Redis, `onModuleInit`의 쿼리)가 생겨도 preview 모드는 프로바이더를 만들지 않으므로 명세 생성이 깨지지 않는다.

### 빌드 때 정해지는 값과 요청 때 정해지는 값은 무엇이 다른가

스토어는 API 주소를 `NEXT_PUBLIC_API_URL`이 아니라 서버 변수 `API_INTERNAL_URL`로 둔다. Next.js는 `NEXT_PUBLIC_*` 값을 빌드할 때 자바스크립트 번들에 문자열로 박아 넣는다. 그래서 빌드에 그 값이 있어야 하고, 스테이징과 운영처럼 주소가 다른 환경마다 다시 빌드해야 하며, 값이 브라우저에 그대로 드러난다. 서버 변수는 서버가 `process.env`에서 읽으므로, 읽는 코드가 요청 때 실행되면 같은 빌드 결과물을 환경 변수만 바꿔 어디서나 실행할 수 있다. 이 주소는 서버끼리만 통하는 내부 주소이고 API를 부르는 곳도 서버 컴포넌트뿐이라, 브라우저에 공개할 이유도 없다. 요청 때 읽게 만드는 장치가 `await connection()`이다. 이 줄 뒤에서 `createServerApiClient()`가 변수를 읽으므로 페이지는 빌드 때 미리 렌더링되지 않고(`ƒ /`), API, DB, 환경 변수 없이도 `next build`가 통과하는 것을 깨끗한 클론에서 확인했다. 대가는 실패 시점이 늦어진다는 것이다. 값이 비어 있어도 빌드와 서버 시작은 성공하고, 누군가 페이지를 처음 열 때 `필수 환경 변수가 없습니다: API_INTERNAL_URL`을 던진다. `error.tsx`가 없어서 Next 기본 오류 화면(500)이 나온다. 개발 모드에서는 메시지가 오버레이에 보이지만, 운영 모드에서는 서버 컴포넌트 오류 메시지가 브라우저로 가지 않고 `digest`만 간다는 것이 Next.js 문서의 동작이다(직접 실험하지는 않았다). 설정 실수를 배포 직후에 잡으려면 서버 시작 때 환경 변수를 검사해야 하는데, 그 검사가 빌드 중에 실행되지 않도록 위치를 골라야 한다.

### Nest 기본 예외 필터는 5xx 메시지를 숨겨 주는가

일부만 숨긴다. 기본 필터(`BaseExceptionFilter`)는 `HttpException`이 아닌 예외(`throw new Error('db-internal:5432 refused')`)만 `{"statusCode":500,"message":"Internal server error"}`로 바꾼다. `HttpException`은 상태가 5xx여도 메시지를 그대로 내보낸다. 우리 필터 없이 앱을 띄워 확인하니 `new ServiceUnavailableException('redis-internal:6379 refused')`는 `{"message":"redis-internal:6379 refused","error":"Service Unavailable","statusCode":503}`로, 503짜리 `ProblemException`은 `{"statusCode":503,"message":"pg-internal:8443 timeout"}`으로 나갔다. 외부 서비스 장애를 503으로 알리려고 `HttpException`을 던지는 순간 내부 주소가 응답에 실린다. 그래서 `ProblemDetailsFilter`는 예외 종류와 상관없이 상태가 5xx면 `detail`을 고정 문구로 바꾸고, 원래 예외는 `Logger.error`로 서버 로그에만 남긴다(#38). 이 규칙은 처음 구현에서 `ProblemException` 분기만 빠져 있었는데, 코드 리뷰에서 잡아 503 회귀 테스트를 더했다. 필터를 `main.ts`의 `useGlobalFilters`로 옮기면 `main.ts`를 거치지 않는 통합 테스트 앱에는 기본 필터가 붙고, 이 테스트가 `pg-internal`이 응답에 있다며 실패한다. 운영 응답은 같아도 테스트가 다른 앱을 검증하게 되므로 `APP_FILTER`로 모듈에 등록한다.

### 응답에서 원인을 숨기면 운영 오류는 어떻게 추적하는가

스토어 서버 로그에서 출발해 API 서버 로그로 간다. 운영 모드의 Next는 서버 컴포넌트 오류 메시지를 브라우저로 보내지 않고 `digest`만 보내며, 원래 오류는 스토어 서버 로그에 남는다(Next.js `error.js` 문서의 동작, 운영 모드로 직접 실험하지는 않았다). 로그의 오류가 status 500, code `INTERNAL_SERVER_ERROR`인 `ApiError`면 API가 500을 돌려준 것이다. 메시지는 API가 숨긴 고정 문구라서 진짜 원인(DB 연결 실패 등)은 `ProblemDetailsFilter`가 남긴 API 서버 로그에만 있다. `TypeError: fetch failed`면 API에 연결하지 못한 것이고, 이때는 `unwrap`과 `transformErrorResponse`까지 가지 않는다. 그 밖의 오류는 스토어 쪽 문제다. 빈틈은 두 가지다. 첫째, 두 서버의 로그를 잇는 키가 없다. API 로그에는 예외만 남고 요청 경로나 요청 ID가 없어서 시각으로 맞춰 봐야 한다. 요청이 많아지면 요청 ID를 만들어 스토어가 헤더로 넘기고 두 서버가 함께 남겨야 한다. 둘째, `error.tsx`가 `digest`를 브라우저 콘솔에만 찍고 화면에는 보여 주지 않아서, 사용자가 신고할 때 식별자를 함께 알려 줄 수 없다. 원인을 응답에서 숨기는 결정은 로그로 추적하는 장치와 한 쌍이어야 한다.

### 오프셋 페이지에서 정렬 기준이 겹치면 무엇이 깨지는가

공연 목록은 `ORDER BY period.start, shows.id`로 정렬한다(#39). `shows.id`를 빼면 첫 회차 일시가 같은 공연끼리의 순서를 SQL이 정해 주지 않아, DB가 실행 계획에 따라 요청마다 다른 순서로 돌려줄 수 있다. 1페이지와 2페이지는 서로 다른 요청이므로, 20번째와 21번째의 일시가 같으면 1페이지에서 본 공연이 2페이지 첫 줄에 또 나오고 다른 공연은 어느 페이지에도 나오지 않을 수 있다. 시드는 날짜를 일 단위 오프셋으로 만들어 같은 첫 회차 일시가 실제로 생긴다. 겹치지 않는 `id`를 마지막 기준으로 붙이면 모든 행의 순서가 하나로 정해진다. 오프셋 페이지는 정렬이 완전히 고정돼야 성립한다. 커서 페이지도 "마지막으로 본 (일시, id) 다음"을 찾으므로 같은 조건이 필요하다.

### 목록 쿼리와 개수 쿼리 사이에 데이터가 바뀌면 응답은 어떻게 어긋나는가

공연 목록은 항목 쿼리와 개수 쿼리를 `Promise.all`로 함께 보낸다(#39). 두 쿼리는 연결 풀의 서로 다른 연결에서 트랜잭션 없이 실행되므로 서로 다른 시점의 데이터를 볼 수 있다. 사이에 공연이 하나 추가되면 `items`에는 없는 공연이 `totalCount`에는 세어지고, 경계(40개 → 41개)에서는 `totalPages`가 하나 늘어 빈 페이지가 생길 수 있다. 공연 목록은 돈이나 좌석을 판단하지 않는 표시용 값이고, 공연은 시드와 운영자 등록으로만 드물게 추가되며, 다음 요청에서 저절로 맞춰지므로 감수한다. 반드시 같은 시점이어야 하면 두 쿼리를 `REPEATABLE READ` 트랜잭션 하나로 묶어 같은 스냅숏을 보게 해야 한다. 그러면 연결 하나에서 차례로 실행해야 해서 동시에 보내는 이점이 사라진다. 개수를 `count(*) over()`로 항목 쿼리에 합치는 방법은 마지막 페이지를 넘는 요청에서 행이 없어 개수까지 사라지므로 쓰지 않았다.

### 운영 데이터가 있는 테이블에 NOT NULL 컬럼을 더하려면

1.3의 `0001` 마이그레이션은 `shows`에 `NOT NULL` 컬럼 `venue_id`를 더하기 전에 `TRUNCATE "shows" RESTART IDENTITY`를 손으로 넣었다(#39). 기본값 없는 `NOT NULL` 컬럼은 기존 행을 채울 값이 없어 PostgreSQL이 거부하고, 당시 행은 1.1의 임시 공연 2개뿐이었기 때문이다. 운영 DB에 그대로 적용하면 공연이 모두 지워진다. 다른 테이블(주문 등)이 외래 키로 공연을 참조하고 있으면 `TRUNCATE`가 거부되어 마이그레이션이 실패하고, `CASCADE`를 붙였다면 참조하는 데이터까지 지워진다. `RESTART IDENTITY`로 id가 다시 1부터 매겨져, 밖에 공유된 `/shows/1` 링크가 다른 공연을 가리키게 된다. 코드를 되돌려도 스키마와 데이터는 돌아오지 않아 백업으로 복원해야 한다. 운영 DB에서는 여러 단계로 나눈다. 비울 수 있는 컬럼으로 추가하고, 기존 행에 올바른 값을 채운 뒤, `NOT NULL`로 바꾼다. 무중단 배포라면 새 컬럼을 채우는 코드가 먼저 배포돼야 하므로 마이그레이션과 배포 순서도 함께 정해야 한다. 이는 4단계의 무중단 마이그레이션으로 이어진다. 1.3의 `0004`도 포스터 경로 `poster_path`를 더하며 같은 방식으로 비웠다(#42). 반대로 `TRUNCATE` 없이 공연이 있는 DB에 `ADD COLUMN ... NOT NULL`만 돌리면 `column "poster_path" contains null values`로 실패한다. PostgreSQL은 `ALTER TABLE`도 트랜잭션 안에서 되돌리므로, 실패한 마이그레이션은 컬럼도 만들지 않고 데이터도 건드리지 않는다. 데이터는 안전하지만 배포가 그 자리에서 멈춘다.

### 판매 상태를 왜 DB의 `now()`가 아니라 앱이 정한 시각으로 계산하는가

공연 판매 상태는 저장하지 않고 조회할 때마다 현재 시각으로 계산한다(#40). 이 시각을 SQL의 `now()`로 두지 않고, 앱이 `Clock`에서 받은 값을 파라미터로 넘긴다. 이유는 둘이다. 첫째, 테스트가 시각을 고정할 수 있어야 한다. 통합 테스트는 `overrideProvider(Clock)`으로 정한 시각을 돌려주는 Clock을 끼워, "판매 오픈 1ms 전은 판매 예정, 정각은 판매 중", "회차 시작 정각은 판매 종료" 같은 경계를 정확히 검증한다. `now()`는 PostgreSQL이 자기 시계로 계산하므로, Vitest의 가짜 시계(`vi.setSystemTime`)로 바꿀 수 있는 것은 테스트를 실행하는 Node 프로세스의 `new Date()`뿐이고 DB의 `now()`는 그대로다. 그러면 데이터를 실제 현재 시각 기준으로 매번 계산해 넣어야 하고, 넣고 조회하는 사이에도 시간이 흐르므로 1ms 단위의 경계 테스트는 만들 수 없다. 둘째, 시각의 기준이 하나여야 한다. 운영에서 앱 서버(NestJS)와 DB 서버(PostgreSQL)는 보통 다른 컴퓨터이고, 시간 동기화를 해도 시계가 조금씩 어긋날 수 있다. 판매 상태는 DB 시계로, 앞으로 만들 예매 가능 여부 검사는 앱 시계로 판단하면 경계 시각에 둘이 다른 답을 낸다. 판매 오픈 14:00:00 근처에서 앱 시계가 14:00:01, DB 시계가 13:59:59면 목록은 "판매 예정"인데 예매는 되는 식이다. 앱이 정한 시각 하나를 쿼리에 넘기면 두 판단이 같은 기준을 본다. 로컬에서는 앱과 DB가 같은 Mac에서 돌아 이 차이가 보이지 않는다. `Clock`은 추상 클래스라 타입이면서 실행 중에도 남는 값이어서, `@Inject(...)` 없이 생성자 타입만으로 주입 토큰이 된다.

### 캐시 버스팅: 내용이 바뀌는 포스터의 경로에 왜 해시를 넣는가

시드가 그리는 포스터에는 공연 기간이 찍히고, 회차는 시드를 돌린 날짜 기준으로 만들어지므로 같은 공연의 포스터도 날마다 내용이 바뀐다(#42). 경로를 `show-01.png`로 고정하면 내일 시드 뒤에도 카드에 어제 날짜의 포스터가 보인다. `next/image`의 최적화 서버(`/_next/image`)는 줄인 결과를 원본 주소, 폭, 품질, 출력 형식으로 만든 키로 디스크에 캐시하고(Next 16 기본 최소 4시간), 브라우저도 응답을 따로 캐시하기 때문이다. 기간이 지나도 첫 요청에는 옛 이미지를 먼저 돌려주고 뒤에서 다시 만든다(`X-Nextjs-Cache: STALE`). 캐시를 지우는 API도 없다. 그래서 주소 자체를 바꾸는 캐시 버스팅을 쓴다. 경로에 PNG 내용의 해시 8자리를 붙여(`show-01-3fa2b1c9.png`) 내용이 바뀌면 주소가 바뀌어 캐시에서 찾지 못하고 새로 받는다. 내용이 같으면 주소도 같아 캐시를 그대로 쓰므로, 바뀐 포스터만 다시 받는다. 빌드 결과물의 `main.4f2a1c.js`, Next의 정적 import 이미지와 같은 방법이다. 시드 시각이나 공연 id로 만들면 내용이 같아도 주소가 바뀌거나, 내용이 바뀌어도 주소가 그대로라 이 성질이 없다.

같은 최적화 서버는 SSRF 통로가 될 수 있다. `/_next/image?url=...`의 원본은 사용자 브라우저가 아니라 Next 서버가 받아 오고, `url`은 누구나 바꿀 수 있다. 허용 범위가 넓으면 `169.254.169.254`(클라우드 메타데이터)나 내부 관리 API처럼 서버만 닿는 곳에 요청을 보내게 할 수 있다. 응답이 이미지가 아니면 돌려주지 않아 내용 유출은 어렵지만, 오류 차이로 내부 서버와 포트를 알아내거나 GET으로 동작하는 내부 API를 실행시킬 수 있다. 그래서 `remotePatterns`는 `POSTER_BASE_URL`의 프로토콜, 호스트, 포트, `/posters/**` 경로 하나만 허용한다. 사설 IP 차단을 끄는 `dangerouslyAllowLocalIP`는 포스터 호스트가 `localhost`, `127.0.0.1`, `[::1]`일 때만 켠다. 개발에서도 `localhost:3001/posters/**`밖에 닿지 않아 같은 컴퓨터의 DB(5432)나 API(3000)로는 요청이 가지 않는다. `POSTER_BASE_URL`에서 `/posters`를 빼면 스토어의 모든 경로가 허용되지만 다른 포트는 여전히 막힌다.
