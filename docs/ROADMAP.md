# 오픈런(OpenRun) 로드맵

풀스택 전 과정을 학습하고 취업용 포트폴리오로 쓰기 위한 장기 프로젝트다. 마감을 두지 않으므로 일정이 아니라 **완료 기준**으로 진행을 관리한다.

- 용어: [`GLOSSARY.md`](../GLOSSARY.md)
- 구조 결정: [`docs/adr/`](./adr/)
- 구현 전 서비스 규칙: [`service-plan.md`](./service-plan.md)
- 이력서 문장과 측정값: [`resume-tracker.md`](./resume-tracker.md)
- 단계별 기록: [`stage-notes/`](./stage-notes/)
- 조사 자료: [`research/`](./research/)
- 티켓 작업 규칙: [`agents/ticket-workflow.md`](./agents/ticket-workflow.md)

## 진행 방식

### 작성과 리뷰
- 코드는 Claude가 작성하고, 사용자가 리뷰와 질문을 마친 뒤 직접 병합한다.
- 티켓 하나당 PR 하나로, 한 번에 리뷰할 수 있는 크기로 나눈다.
- diff는 GitHub PR에서 보고, 질문은 구현한 Claude 세션에서 한다.
- 백엔드와 인프라 PR에는 꼭 필요한 면접식 이해 확인 질문을 넣고, 세션에서 말로 답하며 빈틈을 함께 파고든다.
- 병합 기준은 질문에 답할 수 있고 스스로 납득한 것이다. 강제 장치는 두지 않는다.
- 세부 절차는 [`agents/ticket-workflow.md`](./agents/ticket-workflow.md)를 따른다.

### 계획
- 티켓은 지금 진행할 작업 묶음만 만든다. 세부 설계는 각 작업 묶음을 시작할 때 정한다.
- 문제를 먼저 재현하고 측정한 뒤 해결한다.
- 단계마다 선택 이유, 쓰지 않은 기술, 측정 결과를 `stage-notes/`에 짧게 기록한다.

### 측정
- 정확성 기준은 미리 고정한다. 동시 1만 요청에서 중복 예매는 0건이어야 한다.
- 성능 목표는 미리 정하지 않는다. 5단계의 기준선과 각 단계의 측정값을 근거로 정한다.
- 결과에는 측정 환경, 데이터 규모, 부하 생성 위치를 함께 적는다.
- 포트폴리오의 수치는 직접 측정한 값만 쓰고, 부하 테스트 결과임을 밝힌다.

### 공개와 비용
- 저장소는 처음부터 공개한다.
- 데모는 VPS에 계속 띄워 두고, 테스트 결제임을 화면에 표시한다.
- AWS는 실습할 때만 켜고 `terraform destroy`로 내린다. 예산 알림(월 5만 원)을 먼저 설정한다.
- 공연 데이터와 이미지는 가상으로 만들고, 화면은 기존 예매 사이트를 조사하고 벤치마킹해 실제 서비스에 가깝게 만든다.

## 스킬 사용 순서

**작업 묶음**은 아래 흐름을 한 번 도는 단위다. 1단계는 범위가 커서 세부 항목 11개를 각각 하나의 작업 묶음으로 삼고, 2단계부터는 단계 하나를 하나의 작업 묶음으로 삼는다. 범위가 너무 크면 단계를 시작할 때 더 나눈다.

### 처음 한 번
1. `/setup-matt-pocock-skills`: 공개 저장소 `openrun`의 GitHub Issues, 라벨, 문서 위치를 설정한다. 지침 파일은 `AGENTS.md`를 쓰고, `CLAUDE.md`는 만들지 않는다. `CLAUDE.md`가 있으면 Claude Code가 기본 설정에서 `AGENTS.md`를 읽지 않는다.

### A. 설계 세션
아래 과정은 한 세션에서 이어간다. 컨텍스트가 150k 토큰에 가까워지면 다음 과정으로 넘어갈 때 `/compact` 한다.

1. `/grill-with-docs docs/ROADMAP.md <작업 묶음>`: 범위와 설계를 정하고, 용어와 ADR을 기록한다.
2. 필요할 때만 질문에 답을 얻는다.
   - `/research`: 공식 문서로 확인해야 하는 사실
   - `/prototype`: 직접 보거나 돌려 봐야 판단할 수 있는 것
3. `/to-spec`: 인터뷰 내용을 스펙 이슈로 정리한다.
4. `/to-tickets`: 스펙을 차단 관계가 있는 티켓으로 나누고, 승인 후 이슈로 올린다.
5. `/clear`로 세션을 끝낸다.

### B. 티켓 구현
티켓 하나마다 반복한다. 브랜치, PR, 이해 확인 질문은 [`agents/ticket-workflow.md`](./agents/ticket-workflow.md)의 규칙으로 처리하므로 번호만 입력한다.

1. `/implement #<티켓 번호>`: 티켓 브랜치에서 `/tdd`로 구현하고 `/code-review`로 점검해 커밋한 뒤, `/pr` 양식으로 PR을 연다.
2. diff는 GitHub PR에서 보고, 질문은 **같은 세션에서** 한다. 구현 당시의 맥락이 남아 있어야 답이 정확하다.
   - `/wait-what`: 설명이 이해되지 않을 때
3. 사용자가 직접 병합한 뒤 `/clear` 한다.

한 세션에서 끝내지 못한 리뷰는 `/compact` 후 이어간다. `/implement-spec`은 쓰지 않는다. 서브에이전트가 통합 브랜치에 직접 병합하므로, 티켓마다 리뷰하고 직접 병합하는 규칙과 맞지 않는다.

### C. 작업 묶음 마무리
1. `stage-notes/`에 선택 이유, 쓰지 않은 기술, 측정 결과, 회고를 적는다. 근거는 스펙에 "마무리할 때 적는다"고 남긴 항목과 각 PR의 "왜 이렇게 했나", "쓰지 않은 대안"이다. 완료 기준: 작업 묶음의 PR이 모두 반영됐다.
2. `resume-tracker.md`에 측정값을 기록하고 문장을 채운다.
3. `/retro`: 다음 작업이 더 수월하도록 자동 검사, 코딩 표준, 지침의 개선점을 찾는다. `/setup-ts-deep-modules` 도입도 필요해지면 여기서 검토한다.
4. 필요할 때 `/improve-codebase-architecture`로 구조 개선점을 찾는다. 고른 항목은 A부터 진행한다.

### 수시로
- `/diagnosing-bugs`: 원인을 바로 찾기 어려운 버그, 간헐적인 실패, 성능 저하
- `/resolving-merge-conflicts`: 병합 충돌 해결
- `/handoff`: 다른 디렉터리나 도구로 작업을 옮길 때
- `/teach`: 코드를 넘어 개념 자체를 배우고 싶을 때. 학습 자료가 공개 저장소에 섞이지 않도록 `~/dev/openrun-study`에서 실행한다.

## 기술 구성

| 영역 | 선택 |
|---|---|
| 저장소 | 모노레포, pnpm workspace, Turborepo |
| 런타임 관리 | mise(Node, pnpm) |
| 린트와 포맷 | oxlint, Prettier |
| 스토어 | Next.js, TypeScript, TanStack Query |
| 어드민 | Vite, TanStack Router, TypeScript, TanStack Query (SPA) |
| 디자인 시스템 | `store-ui`, `admin-ui`, Base UI, Tailwind CSS, CSS 변수 토큰, Storybook |
| 백엔드 | NestJS, 모듈러 모놀리스, 워커는 별도 프로세스 |
| 데이터 | PostgreSQL, Drizzle, Redis, BullMQ |
| API | OpenAPI에서 타입과 클라이언트 생성 |
| 테스트 | Vitest, Testcontainers, Playwright, k6 |
| 인프라 | Docker, GitHub Actions, AWS(ECS, RDS, ALB), Terraform |
| 관측성 | Prometheus, Grafana, OpenTelemetry, Sentry |

- **API 호출 경로:** 브라우저는 `api.도메인`을 직접 호출하고, 서버 렌더링은 내부 주소로 호출한다.
- **렌더링:** 스토어의 공개된 조회 화면은 서버 렌더링, 좌석 선택과 결제는 클라이언트 렌더링으로 구성한다. 어드민은 SPA로 만들어 `admin.도메인`에 따로 배포한다. ([ADR 0005](./adr/0005-admin-as-spa.md)) 비즈니스 로직은 NestJS에 둔다.
- **디자인 시스템:** 스토어와 어드민의 디자인 시스템을 완전히 분리한다. ([ADR 0004](./adr/0004-separate-design-systems.md))
  - 도메인 용어를 넣지 않는다. 공연 카드와 좌석 배치도는 `apps/store`, 공연 등록 폼은 `apps/admin`에 둔다.
  - 판매 상태 배지처럼 양쪽에 필요한 것은 앱마다 따로 만들고, 값과 뜻은 용어집과 API 타입으로 일치시킨다.
  - 컴포넌트는 화면에서 필요해질 때만 추가한다.
  - Base UI가 맡지 않는 색 대비와 라벨은 Storybook 접근성 애드온으로 점검하고, 포커스 표시는 Storybook에서 직접 확인한다.
  - 시각적 회귀 테스트는 필요해지면 `/retro`에서 검토한다.
- **브랜치:** `main`에서 티켓별 브랜치를 따고 스쿼시 병합한다.
- **로컬 개발:** PostgreSQL, Redis, MinIO, 가짜 메일 서버만 Docker Compose로 실행하고, 앱은 로컬에서 직접 실행한다. 서비스는 필요해질 때 추가한다. 개발 기반에서 PostgreSQL과 가짜 메일 서버를 띄우고, MinIO는 어드민(1.7)에서, Redis는 처음 쓰는 단계에서 추가한다.
- **환경:** 처음에는 로컬과 운영만 두고, 4단계에서 스테이징을 추가한다.

```
openrun/
├── apps/
│   ├── store/        # 스토어, Next.js
│   ├── admin/        # 어드민, Vite + TanStack Router SPA
│   └── api/          # NestJS
├── packages/
│   ├── store-ui/     # 스토어 디자인 시스템
│   ├── admin-ui/     # 어드민 디자인 시스템
│   └── api-client/   # OpenAPI에서 생성한 타입과 클라이언트
├── infra/            # Docker Compose, 이후 Terraform
└── docs/
```

## 단계

각 단계의 "이력서 항목"은 [`resume-tracker.md`](./resume-tracker.md)의 항목 이름이다.

### 1. 풀스택 기본
- **완료 기준:** 로컬에서 다음이 모두 동작한다.
  - 이메일·소셜 가입과 약관 동의
  - 쿠폰과 포인트를 적용한 토스 테스트 결제, 티켓 확인, 주문 취소와 환불
  - 관람 후 리뷰 작성
  - FAQ와 공지사항 조회
  - 운영자의 공연·쿠폰·FAQ·공지사항 관리와 포스터 업로드
- **세부 순서:**
  1. **개발 기반:** 모노레포(`apps/store`, `apps/api`, `packages/api-client`), Docker Compose(PostgreSQL, 가짜 메일 서버), 린트와 포맷, 테스트, 빌드, 첫 마이그레이션, OpenAPI 클라이언트 생성, 코딩 표준. 새로 clone한 뒤 README 명령만 따라 해도 웹 페이지에 DB에서 읽은 값이 표시되고, 린트, 포맷, 타입 검사, 테스트, 빌드가 통과하면 완료다.
  2. **디자인 기반:** 스토어의 시각적 방향 선택, `store-ui` 토큰, 조회 화면에 필요한 컴포넌트, Storybook
  3. **조회:** 스키마(구역과 좌석 등급 포함), 시드, 공연 목록과 상세, 제목 검색, 장르·판매 상태 필터, 정렬, 오프셋 페이지
  4. **인증:** 이메일 회원가입과 인증, 로그인, 구글·카카오 로그인, 약관 동의와 재동의, 사용자·운영자 역할 구분
  5. **예매:** 좌석 선택, 환불 규정 동의, 주문, 가짜 결제, 티켓 발급
  6. **토스 테스트 결제:** 카드 결제 성공 경로
  7. **어드민:** `apps/admin`과 `admin-ui` 구축, 공연과 회차 등록, 구역별 좌석 등급 지정, 포스터 업로드, 주문·회원 조회
  8. **내 예매:** 예매 내역, 티켓 상세, 주문 취소와 환불, 내 정보 수정, 비밀번호 변경·재설정, 회원 탈퇴, 예매·취소 메일
  9. **리뷰:** 작성 자격 검사, 작성·수정·삭제, 평균 별점, 어드민 숨김
  10. **고객 지원:** FAQ, 공지사항, 어드민 관리
  11. **할인:** 쿠폰 발급과 사용, 포인트 원장, 회차 종료 후 적립 주기 작업, 어드민 쿠폰 관리
- **초기 규칙:** [`service-plan.md`](./service-plan.md)를 설계의 출발점으로 쓴다. 구현한 뒤에는 코드와 테스트가 기준이다.
- **제약:** 예매, 쿠폰, 포인트는 좌석 선점, 락, 유니크 제약 없이 구현한다. ([ADR 0001](./adr/0001-naive-booking-until-concurrency-stage.md))
- **시작 전 정할 것:** 인증 방식, 좌석 UI
- **학습 개념:** REST 설계, 오류 응답 규격, OpenAPI, 세션·JWT, OAuth 2.0, RBAC, IDOR 방어, 입력 검증, 토큰 기반 인증과 재설정, 동의 이력 관리, 개인정보 익명화, 원장 방식
- **이력서 항목:** 인증과 보안, API 설계와 테스트

### 2. 테스트
- **완료 기준:** 예매 성공, 매진, 권한 오류, 주문 취소, 쿠폰·포인트 금액 계산, 리뷰 작성 자격을 자동으로 검증한다.
- **범위:** 1단계부터 쌓인 Testcontainers 통합 테스트에서 빠진 시나리오를 채우고, Playwright E2E를 갖춘다.
- **학습 개념:** 단위·통합·E2E 테스트, Testcontainers
- **이력서 항목:** API 설계와 테스트

### 3. 직접 배포
- **완료 기준:** VPS에 Docker로 배포하고 내 도메인에 HTTPS로 접속한다.
- **범위:** 스토어, `admin.도메인`, `api.도메인`을 함께 배포한다. 포스터는 VPS의 MinIO에 저장한다. 실제 메일 서비스를 고르고, 운영 도메인용 소셜 로그인을 설정한다.
- **학습 개념:** 리버스 프록시, TLS, 비밀 정보 관리, 헬스 체크, Graceful Shutdown

### 4. CI/CD
- **완료 기준:** 병합 시 스테이징에 자동 배포하고, 검증 후 운영에 반영하며, 이전 버전으로 롤백할 수 있다.
- **제약:** 스테이징을 운영과 같은 VPS에 띄우면 부하 테스트는 그 서버에서 돌리지 않는다.
- **학습 개념:** 변경된 앱만 빌드하는 CI, 환경 분리, 무중단 마이그레이션

### 5. 관측성
- **완료 기준:** 느린 요청의 원인을 대시보드에서 찾고, 성능 기준선을 측정한다.
- **학습 개념:** 구조화 로그, 메트릭, 분산 트레이싱, SLO, k6 시나리오 설계, p95·p99
- **이력서 항목:** 운영과 장애 대응, 부하 테스트

### 6. 동시성과 좌석 선점
- **완료 기준:** 중복 예매를 재현한 뒤 선점과 자동 해제를 구현하고, 동시 1만 요청에도 중복 예매가 0건이다. 선착순 쿠폰 초과 발급과 포인트 이중 차감도 재현한 뒤 해결한다.
- **마무리:** ADR 0001을 대체됨으로 표시한다.
- **학습 개념:** 트랜잭션 격리 수준, 비관적·낙관적 락, 유니크 제약, 데드락, 분산 락, TTL, 경쟁 상태
- **이력서 항목:** 동시성과 트랜잭션, 좌석 선점, 부하 테스트

### 7. 비동기 처리
- **완료 기준:** 워커 장애에도 작업이 유실되지 않는다.
- **범위:** 메일 발송을 큐로 옮기고, 포인트 적립이 유실되지 않게 하며, 관심 공연과 판매 오픈 알림을 추가한다.
- **학습 개념:** 메시지 큐, at-least-once 전달, 재시도와 백오프, 실패 큐, 트랜잭셔널 아웃박스
- **이력서 항목:** 비동기 처리

### 8. 결제 정합성
- **완료 기준:** 가짜 토스 서버로 필수 시나리오 7개를 검증하고, 웹훅 중복·유실에도 주문 상태가 정확하다.
- **필수 시나리오:** 승인 요청 중복, 승인 응답 시간 초과, 결제 도중 좌석 선점 만료, 웹훅 중복 수신, 클라이언트의 금액 조작, 할인 금액 조작, 결제 실패 시 쿠폰과 포인트 복구
- **검토할 것:** 일괄 환불과 어드민 기능을 포함한 회차 취소 처리, 부분 취소와 취소 수수료 지원 여부, Playwright에서 토스 결제창을 다루는 방식
- **학습 개념:** 멱등성, 주문 상태 머신, 웹훅 검증, 타임아웃 처리, 보상 처리, 결제 대사
- **이력서 항목:** 결제 정합성

### 9. 쿼리와 캐시 성능

## 결제
- 토스페이먼츠 테스트 키(`test_`)만 쓰고 라이브 키는 쓰지 않는다. 연습할 때는 실제 카드 번호 대신 테스트용 값을 쓴다.
- `PaymentGateway` 인터페이스로 분리한다.
  - **토스 구현체:** 토스 API 또는 가짜 토스 서버를 호출한다.
  - **가짜 구현체:** 1단계부터 앱 안에서 결제를 대신한다.
  - **가짜 토스 서버:** 8단계에서 만드는 별도 HTTP 서버로, 타임아웃, 지연, 웹훅 재전송을 재현한다.
- 자동 테스트와 부하 테스트는 가짜만 쓰고, 외부 API에 대량 요청을 보내지 않는다.
- 웹훅은 결제 조회 API로 교차 확인하고 10초 안에 200으로 응답하며, 오래 걸리는 작업은 큐로 넘긴다.
- `TossPayments-Test-Code` 헤더로 오류를 재현하고, 가상계좌 입금 시뮬레이션으로 웹훅을 테스트한다.
- 1단계의 토스 연동과 8단계 시작 전에 토스페이먼츠 최신 공식 문서를 다시 확인한다.
