# 인증은 Better Auth를 본뜬 DB 세션으로 직접 구현한다

인증은 JWT가 아니라 DB에 저장하는 세션으로 하고, 라이브러리 없이 [Better Auth](../research/better-auth-session.md)의 설계를 본떠 직접 구현한다. 쿠키에는 HMAC으로 서명한 불투명 토큰을 담고, 만료는 7일, 마지막 갱신 뒤 1일이 지난 첫 요청에서 다시 연장한다. 탈퇴할 때 세션을 즉시 끊어야 하고 API 서버도 하나뿐이라 JWT의 무상태 장점을 살리기 어렵다. 또 세션 방식을 직접 만들어 봐야 라이브러리가 감춘 동작을 배울 수 있다.

## Better Auth와 다르게 정한 것

- **토큰은 SHA-256 해시로 저장한다.** Better Auth는 원문을 저장한다. 여러 DB 어댑터와 보조 저장소에서 토큰을 키로 쓰고, 토큰으로 세션을 고르는 API가 있기 때문으로 보인다. 우리에게는 그런 요구가 없고, 해시로 저장해도 조회는 한 번이라 DB와 비밀키가 함께 유출되는 경우까지 막는 쪽을 택했다.
- **쿠키 캐시(세션을 서명된 쿠키에 잠시 담아 DB 조회를 건너뛰는 기능)는 처음부터 켜지 않는다.** 세션 조회가 느리다는 측정 근거가 생기는 9단계에서, 켜기 전후를 측정하며 도입한다.
- **`AUTH_SECRET`이 32자보다 짧으면 부팅하지 않는다.** Better Auth는 경고만 한다. 짧은 키로 운영되면 서명을 추측할 수 있으므로 실수를 부팅에서 막는다.
- **로그인 상태 유지(`rememberMe`)는 로그인 요청의 필수 값이다.** Better Auth는 생략하면 켠다. 세션 유지 기간을 정하는 값이라 기본값을 API에 숨기지 않고, 스토어가 사용자가 고른 값을 늘 보내게 한다.
- **로그인 상태 유지 여부는 세션 행에 둔다.** Better Auth는 별도 쿠키(`dont_remember`)로 들고 다닌다.
- **로그인·가입 요청 속도 제한은 10단계에서 Redis와 함께 넣는다.** Better Auth는 운영 환경에서 기본으로 켠다.

## 고려한 대안

- **JWT 액세스 토큰과 회전하는 리프레시 토큰:** 즉시 끊으려면 결국 서버에 리프레시 토큰이나 차단 목록을 저장해야 해서, 세션보다 복잡해지기만 한다.
- **Better Auth를 그대로 쓰기:** 빠르지만 세션, 쿠키, OAuth 흐름이 감춰져 학습 목표와 맞지 않는다.

## 결과

- 스토어 서버 렌더링이 로그인 상태를 읽어야 하므로 사용자 세션 쿠키는 상위 도메인(`Domain=도메인`)에 굽고, API는 credentials를 허용하는 CORS를 둔다.
- CSRF 토큰은 쓰지 않는다. 변경 요청은 `Origin` 검사, `SameSite=Lax`, JSON 본문만 받기로 막는다.
