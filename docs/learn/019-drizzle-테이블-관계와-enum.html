019 Drizzle 테이블 관계와 enum

1.3에서 테이블이 공연장, 공연, 회차 셋으로 늘며 쓴 Drizzle 문법(외래 키, 인덱스, enum, 시간대가 있는 일시, 기본값)을 apps/api/src/db/schema/의 실제 코드로 설명한다. DB와 SQL을 잘 모르는 프론트엔드 개발자를 기준으로, 필요한 DB 개념을 자바스크립트에 빗대어 먼저 설명한다. pgTable, generatedAlwaysAsIdentity, db:generate 같은 Drizzle 기초는 004 문서에 있다.

먼저 알아 둘 DB 개념

이 문서의 나머지 절은 아래 개념을 안다고 보고 읽는다. 이미 아는 것은 건너뛰어도 된다. 비유는 이해를 돕기 위한 것이라 실제 DB 동작과 완전히 같지는 않다.

DB는 따로 도는 프로그램이다

PostgreSQL은 API 서버(Node)와 별개로 실행되는 프로그램이다. 이 저장소에서는 Docker 컨테이너 (pnpm infra:up)로 띄운다. API 서버는 네트워크로 PostgreSQL에 접속해 SQL이라는 문장을 보내고 결과를 받는다. 브라우저가 API 서버에 fetch를 보내는 관계와 비슷하다.

요청이 오가는 길
  1. 브라우저(스토어)
  2. HTTP로 API 서버(NestJS)
  3. SQL로 PostgreSQL

Drizzle은 TypeScript 코드를 SQL 문장으로 바꿔 보내 주는 도구다. 그래서 "DB 서버의 시각"과 "Node 서버의 시각"이 따로 있다. 두 프로그램이 서로 다른 컴퓨터에서 돌 수도 있기 때문이다. psql은 SQL을 직접 쳐서 PostgreSQL에 보내는 터미널 도구다.

테이블, 행, 컬럼

테이블은 모양이 같은 객체를 모은 배열이라고 생각하면 된다. 행(row)은 배열의 객체 하나, 컬럼(column)은 객체의 속성 하나다. 컬럼마다 타입이 정해져 있어서, 모든 행이 같은 속성과 타입을 갖는다. 

// shows 테이블을 자바스크립트로 그리면
const shows: { id: number; venue_id: number; title: string }[] = [
  { id: 1, venue_id: 1, title: '잃어버린 여름밤' }, // 행 하나
  { id: 2, venue_id: 1, title: '잃어버린 골목' },
];
// id, venue_id, title이 컬럼이다.

스키마 파일의 pgTable은 이 배열의 "타입 정의"에 해당한다. 다만 TypeScript 타입과 달리 DB가 실제로 지킨다. 타입이 맞지 않는 값을 넣으면 DB가 거부한다.

NULL과 NOT NULL

DB에서 "값이 없음"은 NULL이다. 자바스크립트의 null과 같다. 컬럼에 NOT NULL을 붙이면 그 컬럼은 비울 수 없다. TypeScript로 치면 title?: string이 아니라 title: string인 필수 속성이다.

기본 키

기본 키(primary key)는 행 하나를 가리키는 고유한 값이다. 이 저장소에서는 모든 테이블의 id가 기본 키다. 겹치거나 비어 있을 수 없다. 리스트를 렌더링할 때 React의 key로 쓰는 id와 같은 역할이다. 그 id가 정말 겹치지 않게 DB가 보장한다는 점이 다르다.

id 값은 DB가 1, 2, 3… 순서대로 매긴다. 번호를 기억하는 내부 장치를 시퀀스라고 하고, 은행의 번호표 기계와 비슷하다. 행을 지워도 번호표는 되돌아가지 않는다. RESTART IDENTITY는 번호표 기계를 1로 되돌리는 옵션이다.

외래 키: 다른 테이블의 id를 들고 있기

프론트엔드에서 서버 데이터를 정규화해 상태에 담을 때(예: Redux의 entities), 객체를 중첩하지 않고 id만 들고 있게 한다. 

// 중첩 대신 id로 가리킨다
const venues = { 1: { id: 1, name: '낙산 소극장' } };
const shows = { 1: { id: 1, title: '잃어버린 여름밤', venueId: 1 } };

const venue = venues[shows[1].venueId]; // 필요할 때 id로 찾아 붙인다

DB도 같은 방식이다. 공연 행에 공연장 정보를 통째로 넣지 않고 venue_id만 둔다. 공연장 이름이 바뀌어도 공연장 행 하나만 고치면 된다. 이렇게 다른 테이블의 기본 키를 가리키는 컬럼을 외래 키(foreign key)라고 한다.

자바스크립트에서는 venueId: 999처럼 없는 id를 넣어도 아무도 막지 않는다. 외래 키를 선언하면 DB가 "그 id를 가진 공연장이 실제로 있는가"를 검사해 막아 준다.

제약: DB가 하는 검증

NOT NULL, 기본 키, 외래 키처럼 DB가 값을 검사하는 규칙을 제약(constraint)이라고 한다. 폼 값을 zod 같은 라이브러리로 검증하는 것과 비슷한데, 검증이 DB 안에서 일어난다. 제약을 어기는 SQL은 실패하고 데이터는 바뀌지 않는다. API 코드에 버그가 있어도 깨진 데이터가 저장되지 않는 마지막 방어선이다.

JOIN: id로 두 배열 합치기

목록 화면에는 공연 제목과 공연장 이름이 함께 필요하다. 두 정보가 서로 다른 테이블에 있으므로, 공연의 venue_id로 공연장을 찾아 붙여야 한다. SQL에서 이것을 JOIN이라고 한다. 

// INNER JOIN을 자바스크립트로 쓰면
const rows = shows
  .map((show) => ({ show, venue: venues.find((v) => v.id === show.venue_id) }))
  .filter(({ venue }) => venue !== undefined) // INNER: 짝이 없는 행은 뺀다
  .map(({ show, venue }) => ({ title: show.title, venueName: venue.name }));

INNER JOIN은 짝이 있는 행만 남긴다. 이 저장소의 공연 목록은 회차와도 INNER JOIN을 하므로, 회차가 하나도 없는 공연은 목록에 나오지 않는다.

비슷하게 GROUP BY는 배열을 키별로 묶는 것(Object.groupBy)이고, min(), max()는 묶인 값에서 가장 작은 값과 큰 값을 고르는 것이다. 공연 기간(첫 회차와 마지막 회차)이 이 방식으로 계산된다.

인덱스: 찾아보기 목차

JOIN의 find처럼 조건에 맞는 행을 찾을 때, 아무 준비가 없으면 DB는 테이블을 처음부터 끝까지 읽는다. 배열에서 find를 하는 것과 같아서, 행이 많아지면 느려진다.

인덱스는 특정 컬럼 값으로 행을 빨리 찾게 미리 만들어 두는 자료 구조다. 책 뒤의 "찾아보기"나, 배열 대신 미리 만들어 둔 Map과 비슷하다. 

// 인덱스 없음: 매번 전부 훑는다
performances.filter((p) => p.show_id === 3);

// 인덱스 있음: 미리 만든 찾아보기로 바로 간다
const byShowId = Map.groupBy(performances, (p) => p.show_id); // 인덱스를 만드는 일
byShowId.get(3);

대가도 있다. 행을 넣거나 고칠 때마다 DB가 인덱스도 함께 고쳐야 하므로 쓰기가 조금 느려지고 저장 공간도 더 든다. 그래서 자주 찾는 컬럼에만 만든다. PostgreSQL의 기본 인덱스는 B-tree다. 값을 정렬해 나무 모양으로 저장해서, 정렬된 배열에서 이진 탐색을 하듯 빨리 찾는다.

DB는 쿼리를 받으면 인덱스를 쓸지, 테이블 전체를 읽을지를 스스로 정한다. 이 결정을 실행 계획이라고 하며, SQL 앞에 EXPLAIN을 붙이면 볼 수 있다.

SQL 문장의 두 종류

이 문서에 나오는 SQL은 두 종류다.

종류 문장 프론트엔드 비유
모양 바꾸기 CREATE TABLE(테이블 만들기), ALTER TABLE(컬럼이나 제약 더하기), CREATE INDEX, CREATE TYPE TypeScript 타입 정의를 고치는 것
데이터 다루기 SELECT(읽기), INSERT(넣기), UPDATE(고치기), DELETE(지우기), TRUNCATE(테이블 전체를 한 번에 비우기) 배열에 filter, push, 수정, 삭제를 하는 것

모양을 바꾸는 SQL을 파일로 쌓아 둔 것이 마이그레이션이다. DB 모양의 변경 이력이라, git 커밋을 순서대로 적용하듯 0000, 0001 순으로 DB에 적용한다. 자세한 흐름은 004 문서에 있다.

선택 읽기: SQL을 읽을 때 알아 둘 표기
  • 큰따옴표 "shows"는 테이블이나 컬럼의 이름이다. 작은따옴표 'musical'는 문자열 값이다. 자바스크립트와 달리 둘을 바꿔 쓸 수 없다.
  • "public"."venues": public은 PostgreSQL의 기본 이름공간 (스키마)이다. 폴더 안의 파일처럼 public 안에 venues 테이블이 있다는 뜻이다. 따로 정하지 않으면 모든 테이블이 public에 들어간다.
  • --로 시작하는 줄은 주석이다. 자바스크립트의 //와 같다.
  • 문장은 ;로 끝난다.

한눈에 보기

세 테이블은 외래 키로 이어진다. 공연은 공연장 하나에서 열리고, 회차는 공연 하나에 속한다(GLOSSARY.md). 화살표(→)는 "이 컬럼이 저 테이블의 id를 가리킨다"는 뜻이다.

  • venues (venues.ts) 공연장 id, name
    • shows (shows.ts) 공연 venue_id → venues.id, 장르(enum)
      • performances (shows.ts) 회차 show_id → shows.id, 회차 취소 여부

공연장 하나에 공연이 여러 개, 공연 하나에 회차가 여러 개 달린다. 이런 관계를 "일대다"라고 한다. 외래 키는 항상 "다" 쪽(공연, 회차)에 둔다. 공연장 행에 공연 id 목록을 넣지 않는 이유는, 한 칸에 값을 여러 개 넣으면 찾기도 고치기도 어렵기 때문이다.

파일은 모듈 단위로 나눴다(ADR 0003). 공연장은 venues 모듈, 공연과 회차는 shows 모듈이 소유하므로 performances도 shows.ts에 있다. 

// apps/api/src/db/schema/shows.ts
import { boolean, index, integer, pgEnum, pgTable, text, timestamp } from 'drizzle-orm/pg-core';
import { venues } from './venues.js';

export const GENRES = ['musical', 'play', 'concert', 'classical_dance', 'kids_family'] as const;
export type Genre = (typeof GENRES)[number];

export const genre = pgEnum('genre', GENRES);

export const shows = pgTable(
  'shows',
  {
    id: integer().primaryKey().generatedAlwaysAsIdentity(),
    venueId: integer('venue_id')
      .notNull()
      .references(() => venues.id),
    title: text().notNull(),
    genre: genre().notNull(),
    minAge: integer('min_age').notNull(),
    runningMinutes: integer('running_minutes').notNull(),
    description: text().notNull(),
    createdAt: timestamp('created_at', { withTimezone: true })
      .notNull()
      .defaultNow(),
  },
  (table) => [index().on(table.venueId)],
);

export const performances = pgTable(
  'performances',
  {
    id: integer().primaryKey().generatedAlwaysAsIdentity(),
    showId: integer('show_id')
      .notNull()
      .references(() => shows.id),
    startsAt: timestamp('starts_at', { withTimezone: true }).notNull(),
    salesOpenAt: timestamp('sales_open_at', { withTimezone: true }).notNull(),
    isCancelled: boolean('is_cancelled').notNull().default(false),
  },
  (table) => [index().on(table.showId)],
);

컬럼 빌더는 DB 타입 하나씩에 대응한다.

빌더 PostgreSQL 타입 TS 타입 담는 것
integer() integer number 정수. 약 ±21억까지
text() text string 길이 제한 없는 문자열
boolean() boolean boolean 참, 거짓
timestamp(...) timestamptz Date 일시(아래)
genre() genre(직접 만든 enum) Genre 장르 5개 중 하나(아래)

pgTable의 세 번째 인자 (table) => [...]는 004에 없던 것이다. 컬럼 하나에 붙일 수 없는 것(인덱스, 여러 컬럼에 걸친 제약)을 둔다. 두 번째 인자의 컬럼을 table로 받아 배열로 돌려준다.

컬럼 이름 직접 적기

컬럼 빌더의 첫 인자를 생략하면 객체 키가 그대로 DB 컬럼 이름이 된다(004 문서). title처럼 한 단어면 문제가 없지만, 두 단어부터는 다르다.

코드 만들어지는 컬럼
venueId: integer() "venueId". 대문자가 섞여 따옴표를 쳐야만 찾을 수 있는 이름
venueId: integer('venue_id') venue_id. PostgreSQL에서 흔히 쓰는 소문자와 밑줄(snake_case)

PostgreSQL은 SQL에 적힌 이름을 따옴표가 없으면 소문자로 바꿔 읽는다. SELECT venueId FROM shows라고 치면 venueid 컬럼을 찾다가 "그런 컬럼이 없다"는 오류가 난다. 대문자가 든 이름은 매번 "venueId"처럼 따옴표를 쳐야 한다. 그래서 DB 컬럼은 소문자와 밑줄로 짓는 것이 관례다.

코드에서는 shows.venueId, row.venueId처럼 camelCase로 쓰고, DB에는 venue_id로 저장한다. 둘을 잇는 것이 빌더의 첫 인자다. 자바스크립트 객체 키와 API 응답 키가 다를 때 매핑하는 것과 같은 일을 Drizzle이 해 준다.

선택 읽기: casing 옵션을 쓰지 않은 이유

drizzle(url, { casing: 'snake_case' })를 주면 키에서 snake_case 이름을 자동으로 만든다. 하지만 같은 설정을 drizzle-kit 설정(drizzle.config.ts)과 drizzle()을 부르는 모든 곳에 넣어야 한다.

  • src/db/database.module.ts: 앱
  • src/db/seed.ts: 시드
  • test/setup/postgres.ts: 테스트 DB 마이그레이션
  • test/shows.int.spec.ts: 테스트 데이터 준비

한 곳이라도 빠뜨리면 그곳만 "venueId"를 찾다가 실행 중에 실패한다. 컬럼마다 이름을 적는 쪽이 더 길지만, 이름이 스키마 한곳에서만 정해진다.

timestamptz

startsAt: timestamp('starts_at', { withTimezone: true }).notNull(),

withTimezone: true를 주면 컬럼 타입이 timestamp with time zone(줄여서 timestamptz)이 된다. 프론트엔드의 Date로 비유하면 이해가 쉽다.

자바스크립트 Date와 같은 방식

자바스크립트의 Date는 안에 "1970년 1월 1일 UTC부터 몇 밀리초 지났는가"라는 숫자 하나만 들고 있다. 시간대는 저장하지 않는다. 시간대는 toLocaleString('ko-KR', { timeZone: 'Asia/Seoul' })처럼 보여 줄 때 정한다. 같은 Date를 서울에서 보면 19:30, 런던에서 보면 10:30이지만 가리키는 순간은 하나다. 이런 값을 절대 시점이라고 한다.

timestamptz도 같다. 넣을 때 받은 시각을 UTC 기준 절대 시점으로 바꿔 저장하고, 시간대는 버린다. 이름에 "time zone"이 들어가지만 시간대를 저장하지는 않는다. 꺼낼 때는 DB 접속(세션)에 설정된 시간대로 바꿔 보여 준다.

타입 자바스크립트 비유 '2026-03-01 19:30+09'(서울 19:30)를 넣으면
timestamptz Date 객체(절대 시점) 2026-03-01 10:30 UTC라는 한 순간으로 저장
timestamp(시간대 없음) '2026-03-01T19:30'처럼 오프셋 없는 문자열 +09를 버리고 2026-03-01 19:30이라는 숫자만 저장

오프셋 없는 문자열은 읽는 쪽의 시간대에 따라 뜻이 달라진다. 자바스크립트에서도 new Date('2026-03-01T19:30')은 브라우저가 서울에 있으면 서울 19:30, 런던에 있으면 런던 19:30으로 읽힌다. 시간대 없는 timestamp도 그 숫자가 서울 시각인지 UTC인지 모른다.

회차 시작 일시는 "지금보다 지났는가"로 판매 상태를 계산하는 데 쓰인다(#40). 시점이 하나로 정해져야 서버가 어느 시간대에 있든 같은 결과가 나오므로 timestamptz를 쓴다. 화면에서는 스토어가 Asia/Seoul로 바꿔 보여 준다.

TS에서는 Date

timestamp의 기본 mode는 'date'라서 읽으면 Date 객체가 오고, 쓸 때도 Date를 넣는다. { withTimezone: true, mode: 'string' }을 주면 문자열로 주고받는다. 서비스가 응답을 만들 때 toISOString()을 부르는 것은 이 값이 Date이기 때문이다. JSON에는 Date를 그대로 담을 수 없어 ISO 문자열로 바꾼다.

기본값과 INSERT 타입

isCancelled: boolean('is_cancelled').notNull().default(false),
createdAt: timestamp('created_at', { withTimezone: true }).notNull().defaultNow(),

위 코드가 만드는 SQL은 컬럼 정의 한 줄씩이다.

"is_cancelled" boolean DEFAULT false NOT NULL
"created_at" timestamp with time zone DEFAULT now() NOT NULL

각 줄은 "컬럼 이름, 타입, 기본값, 제약" 순서다. DEFAULT는 행을 넣을 때(INSERT) 그 컬럼 값을 주지 않으면 DB가 대신 채울 값이다. 함수의 기본 매개변수(function f(x = false))와 비슷하다.

  • DEFAULT false: 값을 주지 않은 회차는 취소되지 않은 회차로 저장된다.
  • DEFAULT now(): now()는 PostgreSQL이 제공하는 "지금 시각" 함수다. Node 서버가 아니라 DB 서버의 시계를 읽는다. 공연을 넣은 순간이 등록 일시로 저장된다.

수식어는 SQL만 바꾸지 않고 TS 타입도 바꾼다. 아래 표가 Drizzle이 붙여 주는 타입이다.

수식어 읽을 때(SELECT) 타입 넣을 때(INSERT) 값
없음 string | null 선택. 빼면 NULL이 들어간다
.notNull() string 필수 빼면 컴파일 오류
.notNull().default(...) string 선택 빼면 DB가 기본값으로 채운다
.generatedAlwaysAsIdentity() number 넣을 수 없다. 번호는 DB만 매긴다

그래서 통합 테스트는 createdAt 없이 공연을 넣고, 시드는 과거 날짜를 흉내 내려고 createdAt을 직접 넣는다. 둘 다 같은 타입 검사를 통과한다.

#40에서 정한 "DB의 now()를 쓰지 않는다"는 판매 상태를 계산하는 쿼리 이야기다. 판매 상태는 테스트에서 "지금"을 원하는 시각으로 고정해야 하는데, DB 시계는 테스트가 바꿀 수 없다. 등록 일시처럼 "넣은 순간"을 기록하는 데는 DB 시각을 써도 된다.

외래 키

앞에서 본 외래 키를 Drizzle에서는 .references()로 선언한다. 

venueId: integer('venue_id')
  .notNull()
  .references(() => venues.id),

drizzle-kit이 만든 SQL은 이렇다.

ALTER TABLE "shows" ADD CONSTRAINT "shows_venue_id_venues_id_fk"
  FOREIGN KEY ("venue_id") REFERENCES "public"."venues"("id")
  ON DELETE no action ON UPDATE no action;

한 부분씩 읽으면 다음과 같다.

부분 뜻
ALTER TABLE "shows" shows 테이블의 모양을 바꾼다
ADD CONSTRAINT "shows_venue_id_venues_id_fk" 제약을 하나 더한다. 따옴표 안은 제약 이름이다. 오류 메시지에 이 이름이 나온다
FOREIGN KEY ("venue_id") 이 테이블의 venue_id 컬럼이 외래 키다
REFERENCES "public"."venues"("id") venues 테이블의 id 컬럼을 가리킨다
ON DELETE no action 가리켜지는 공연장을 지우려 하면 막는다(아래)
ON UPDATE no action 가리켜지는 공연장의 id를 바꾸려 하면 막는다. id는 바꾸지 않으므로 신경 쓸 일이 없다

외래 키가 있으면 DB가 두 가지를 막는다.

  • 없는 공연장 id로 공연을 넣는 것. venue_id: 999로 INSERT하면 999번 공연장이 없으므로 실패한다.
  • 공연이 남아 있는 공연장을 지우는 것. 지우면 그 공연의 venue_id가 없는 곳을 가리키게 된다.

.notNull()과 함께 쓰면 "공연은 반드시 실제로 있는 공연장 하나에 속한다"는 규칙을 DB가 지킨다. .notNull()이 없으면 venue_id를 비워 "공연장 없는 공연"을 만들 수 있다.

왜 화살표 함수인가

.references(venues.id)가 아니라 .references(() => venues.id)다. 함수로 감싸면 Drizzle은 함수를 저장만 해 두고, 실제 참조 정보가 필요할 때(마이그레이션 생성, 쿼리 실행) 부른다.

두 스키마 파일이 서로를 import하면(순환 import), 한쪽 파일이 읽히는 순간에 다른 쪽의 venues는 아직 정의되지 않았을 수 있다. 바로 venues.id를 읽으면 그때 터진다. 함수로 미뤄 두면 모든 파일을 읽은 뒤에 부르므로 안전하다. React의 lazy(() => import(...))가 함수를 받아 나중에 부르는 것과 같은 이유다. 지금은 shows.ts → venues.ts 한 방향뿐이지만 Drizzle은 항상 이 형태를 요구한다.

ON DELETE

가리켜지는 행(부모, 예: 공연)을 지우려 할 때, 그 행을 가리키는 행(자식, 예: 회차)을 어떻게 할지 정한다.

설정 공연을 지우면
no action(기본값, 지금 설정) 회차가 하나라도 남아 있으면 삭제가 실패한다
cascade 그 공연의 회차도 함께 지워진다
set null 회차의 show_id를 비운다(NOT NULL이면 쓸 수 없다) 
.references(() => shows.id, { onDelete: 'cascade' }) // 공연을 지우면 회차도 함께 지운다

지금은 공연이나 공연장을 지우는 기능이 없어 기본값으로 두었다. 나중에 회차에 주문이 붙으면, 실수로 회차가 줄줄이 지워지지 않게 막는 기본값이 오히려 안전하다.

외래 키 때문에 시드는 TRUNCATE performances, shows, venues RESTART IDENTITY처럼 세 테이블을 한 문장에서 비운다. TRUNCATE는 테이블의 모든 행을 한 번에 지우는 명령이다. shows만 비우면 그 행을 가리키는 performances가 남아 있어서 PostgreSQL이 거부한다. RESTART IDENTITY는 번호표를 1로 되돌려, 다시 넣은 행이 id 1부터 시작하게 한다.

외래 키 컬럼 인덱스

앞에서 본 인덱스를 회차의 show_id에 만들었다.

(table) => [index().on(table.showId)],
CREATE INDEX "performances_show_id_index" ON "performances" USING btree ("show_id");

SQL을 읽으면 "performances 테이블의 show_id 컬럼에, B-tree 방식으로, performances_show_id_index라는 이름의 인덱스를 만든다"이다.

PostgreSQL은 외래 키를 선언해도 그 컬럼에 인덱스를 자동으로 만들지 않는다. 가리켜지는 쪽(shows.id)은 기본 키라 인덱스가 저절로 생기지만, 가리키는 쪽(performances.show_id)에는 직접 만들어야 한다. MySQL은 자동으로 만들어 주므로 헷갈리기 쉽다.

이 인덱스는 "공연 3번의 회차를 모두 찾아라"처럼 show_id로 찾는 일을 빠르게 한다.

  • 목록에서 회차를 공연별로 묶어 공연 기간(첫 회차, 마지막 회차)을 구할 때
  • 공연 상세에서 "이 공연의 회차"를 찾을 때(#48)
  • 공연을 지울 때. ON DELETE no action을 지키려고 PostgreSQL이 "이 공연을 가리키는 회차가 남았는가"를 찾는다

index()에 이름을 주지 않아 drizzle-kit이 테이블_컬럼_index로 지었다. 이름을 정하려면 index('performances_show_id_idx')처럼 쓴다.

인덱스가 실제로 쓰이는지는 데이터가 적은 지금은 알 수 없다. 회차가 200개쯤이면 찾아보기를 펴는 것보다 전부 훑는 편이 빠를 때가 많아서, PostgreSQL이 인덱스를 쓰지 않는 실행 계획을 고른다. 데이터를 늘려 측정하는 일은 9단계에서 한다.

pgEnum과 as const

장르는 정해진 5개 값 중 하나만 들어갈 수 있다. TypeScript의 문자열 리터럴 유니언 ('musical' | 'play' | ...)과 같은 것을 DB에도 만드는 것이 enum 타입이다. 

export const GENRES = ['musical', 'play', 'concert', 'classical_dance', 'kids_family'] as const;
export type Genre = (typeof GENRES)[number];
export const genre = pgEnum('genre', GENRES);

// 테이블 안에서
genre: genre().notNull(),
  1. as const 배열 타입이 string[]이 아니라 읽기 전용 튜플 readonly ['musical', 'play', ...]가 된다. 값 하나하나가 리터럴 타입으로 남는다.
  2. (typeof GENRES)[number] "튜플의 아무 칸"의 타입이다. 결과는 'musical' | 'play' | 'concert' | 'classical_dance' | 'kids_family'다. 값 목록과 타입을 배열 하나에서 얻으므로 둘이 어긋나지 않는다.
  3. pgEnum('genre', GENRES) PostgreSQL에 genre라는 새 타입을 만든다. integer, text 같은 내장 타입 목록에 "장르 5개 중 하나"라는 타입을 하나 더하는 것이다. 테이블에 딸린 것이 아니라 DB에 따로 있는 타입이라 다른 테이블에서도 쓸 수 있다. 반환값 genre는 이 타입의 컬럼을 만드는 빌더 함수다.
  4. genre().notNull() enum 타입의 컬럼이다. 컬럼 이름이 키와 같아 인자를 생략했다. TS 타입이 위의 유니언이라 genre: 'opera'로 넣으면 컴파일 오류가 나고, 타입을 우회해 SQL을 직접 보내도 DB가 거부한다. 
CREATE TYPE "public"."genre" AS ENUM('musical', 'play', 'concert', 'classical_dance', 'kids_family');
ALTER TABLE "shows" ADD COLUMN "genre" "genre" NOT NULL;

첫 줄은 "genre라는 타입을 이 다섯 값 중 하나로 만든다", 둘째 줄은 "shows에 genre 타입의 genre 컬럼을 비울 수 없게 더한다"이다. 둘째 줄의 첫 "genre"는 컬럼 이름, 두 번째 "genre"는 타입 이름이다.

한 배열이 API 끝까지 간다

GENRES가 쓰이는 곳
  1. 스키마의 pgEnum
  2. DTO의 @ApiProperty({ enum: GENRES })
  3. openapi.json의 Genre
  4. 스토어의 생성 클라이언트 타입

스토어에서 components['schemas']['Genre'] 타입으로 받는 장르 값도 이 배열에서 왔다. 시드도 같은 배열을 돌며 장르를 붙인다. 스키마 파일은 다른 스키마 파일과 Drizzle만 import할 수 있으므로, 배열은 스키마 파일에 두고 DTO와 시드가 가져다 쓴다. 반대 방향(DTO에 두고 스키마가 import)은 규칙에 어긋난다.

enum을 바꾸는 비용

TypeScript 유니언은 코드만 고치면 바뀌지만, DB의 enum은 이미 저장된 행이 그 값을 쓰고 있어서 바꾸는 비용이 다르다.

바꾸는 것 비용
값 더하기 쉬움 ALTER TYPE "genre" ADD VALUE 'opera' 한 줄
값 빼기, 이름 바꾸기 어려움 PostgreSQL에 enum 값을 지우는 명령이 없다. 새 타입을 만들고, 컬럼을 새 타입으로 옮기고, 옛 타입을 지워야 한다. 그 값을 쓰던 행도 먼저 다른 값으로 바꿔야 한다

장르는 GLOSSARY에서 "고정된 분류"로 정했으므로 enum이 맞다. 운영자가 자주 추가하거나 이름을 바꿀 분류였다면, genres 테이블을 따로 만들고 공연이 외래 키로 가리키는 쪽이 맞다. 그러면 장르 추가가 마이그레이션이 아니라 행 하나를 넣는 일이 된다.

스키마에서 얻는 타입

테이블 정의에서 행 타입을 바로 꺼낼 수 있다. 위의 수식어 규칙이 그대로 반영된다. API 응답에서 타입을 만들어 주는 openapi-typescript와 비슷하게, DB 스키마에서 타입이 나온다. 

type ShowRow = typeof shows.$inferSelect; // 읽어 온 행
// {
//   id: number; venueId: number; title: string; genre: Genre;
//   minAge: number; runningMinutes: number; description: string; createdAt: Date;
// }

type NewShow = typeof shows.$inferInsert; // 넣을 값
// {
//   venueId: number; title: string; genre: Genre;
//   minAge: number; runningMinutes: number; description: string;
//   createdAt?: Date;          // DEFAULT now()라 선택
// }                            // id 없음: 번호는 DB만 매긴다

db.insert(shows).values({...})가 받는 값이 NewShow다. 이 프로젝트는 타입 이름을 따로 만들지 않고, insert와 select에서 추론되는 타입을 그대로 쓴다. 응답 타입은 DTO(ShowSummaryDto)가 따로 정한다. 그래서 DB 컬럼을 하나 더해도 API 응답이 저절로 바뀌지 않고, 스토어가 받는 모양은 DTO를 고칠 때만 바뀐다.

마이그레이션 손보기

스키마를 고치고 pnpm db:generate --name create_venues_and_performances를 실행하면 drizzle-kit이 drizzle/0001_create_venues_and_performances.sql을 만든다. 이번에는 생성된 SQL을 그대로 쓰지 못했다. 문제가 된 줄은 이것이다. 

ALTER TABLE "shows" ADD COLUMN "venue_id" integer NOT NULL;

"shows 테이블에 비울 수 없는 정수 컬럼 venue_id를 더한다"는 뜻이다. 테이블이 비어 있으면 문제가 없다. 그런데 개발 DB의 shows에는 1.1에서 넣은 임시 공연 2행이 있었다. 컬럼을 더하는 순간 그 두 행에도 venue_id 칸이 생기는데, 채울 값(기본값)이 없으니 비어 있게 된다. NOT NULL이라 비울 수 없으므로 PostgreSQL이 이 문장을 거부한다. 

// 자바스크립트로 비유하면
type Show = { id: number; title: string; venueId: number }; // venueId를 필수로 바꿨는데
const saved: Show[] = [{ id: 1, title: '레미제라블' }]; // 이미 저장된 객체에는 venueId가 없다 → 오류

그래서 생성된 파일 맨 앞에 한 줄을 직접 넣어, 컬럼을 더하기 전에 테이블을 비우게 했다.

-- 기존 shows 행은 임시 시드 2개뿐이다. NOT NULL 컬럼을 더하려고 비우며, 시드를 다시 넣으면 채워진다.
TRUNCATE "shows" RESTART IDENTITY;--> statement-breakpoint
  • --> statement-breakpoint는 drizzle의 구분자다. 마이그레이션을 실행할 때 이 표시로 파일을 문장 단위로 나눈다. 직접 넣는 줄에도 붙여야 한다.
  • 손으로 고쳐도 다음 generate에는 영향이 없다. drizzle-kit은 다음에 바뀐 점을 찾을 때 SQL 파일이 아니라 drizzle/meta/0001_snapshot.json과 비교한다. 이 스냅숏은 "마지막으로 본 스키마 모양"을 JSON으로 저장한 것이다. TRUNCATE는 데이터만 지우고 모양은 바꾸지 않으므로 스냅숏과 어긋나지 않는다.
  • 이미 적용된 마이그레이션은 고치지 않는다. drizzle은 어느 마이그레이션까지 적용했는지 DB 안의 기록 테이블에 남긴다. 적용한 뒤에 파일을 바꾸면, 이미 적용한 DB는 "적용 완료"로 보고 다시 실행하지 않는다. 이번 수정은 PR에서 처음 만든 파일이라 괜찮다.

이 TRUNCATE는 지워질 행이 임시 데이터뿐이라 쓸 수 있었다. 실제 사용자 데이터가 있는 운영 DB에 그대로 적용하면 공연이 모두 지워진다. 그런 경우에는 "기본값을 두고 컬럼 추가 → 기존 행에 올바른 값 채우기 → NOT NULL로 바꾸기"처럼 여러 단계로 나눠야 한다.

쓰지 않은 relations()

Drizzle에는 relations()로 관계를 선언하면 중첩 객체로 조회하는 기능(Relational Queries)이 있다. GraphQL처럼 "공연과 그 회차들"을 한 번에 중첩해서 받는 방식이다. 

// 이 프로젝트에서는 쓰지 않는다
db.query.shows.findMany({ with: { performances: true } });
// → [{ id: 1, title: '...', performances: [{ id: 1, ... }, ...] }, ...]

이름이 비슷하지만 .references()와는 다른 것이다.

.references() relations()
무엇인가 DB의 외래 키 제약 Drizzle 쿼리 편의 기능
누가 아는가 PostgreSQL Drizzle(TypeScript 코드)만
마이그레이션에 나오는가 나온다 나오지 않는다
이 프로젝트 쓴다 쓰지 않는다

대신 서비스에서 JOIN을 직접 적는다. 판매 상태처럼 SQL 안에서 회차를 묶고 세야 하는 쿼리가 많아, JOIN과 집계가 코드에 그대로 보이는 쪽이 맞다고 판단했다. 

this.db
  .select({ id: shows.id, venueName: venues.name, start: period.start, end: period.end })
  .from(shows)                                          // 공연 배열에서
  .innerJoin(venues, eq(venues.id, shows.venueId))      // venueId가 같은 공연장을 붙이고
  .innerJoin(period, eq(period.showId, shows.id));      // 공연별 첫·마지막 회차를 붙인다

relations()를 쓰려면 모든 테이블을 모은 객체를 drizzle()에 넘겨야 해서, 결국 중앙 집계 파일이 생긴다. 근거는 docs/research/drizzle-schema-organization.md의 Q3에 있다.

스스로 확인하기

질문에 먼저 답해 본 뒤, 눌러서 답을 확인한다.

1. 공연 행에 공연장 이름을 직접 넣지 않고 venue_id만 두는 이유는?

공연장 이름이 바뀌면 공연장 행 하나만 고치면 된다. 공연마다 이름을 복사해 두면 공연 수만큼 고쳐야 하고, 하나라도 빠뜨리면 같은 공연장이 다른 이름으로 보인다. 화면에 이름이 필요할 때는 JOIN으로 붙인다.

2. venueId: integer()로 이름 없이 썼다면 SQL로 공연장 id를 어떻게 조회해야 하는가?

컬럼 이름이 "venueId"가 되므로 SELECT "venueId" FROM shows처럼 따옴표를 쳐야 한다. 따옴표 없이 venueId로 쓰면 PostgreSQL이 venueid로 읽어 컬럼을 찾지 못한다.

3. 회차가 남아 있는 공연을 DELETE FROM shows WHERE id = 1로 지우면 어떻게 되는가?

performances.show_id의 외래 키가 ON DELETE no action이라 PostgreSQL이 삭제를 거부한다. 회차를 먼저 지우거나, 외래 키에 onDelete: 'cascade'를 줘야 한다.

4. 외래 키를 걸었는데 왜 index().on(table.showId)를 따로 썼는가?

PostgreSQL은 외래 키를 걸어도 가리키는 쪽 컬럼에 인덱스를 만들지 않는다. 회차를 공연별로 묶거나 찾는 쿼리, 공연을 지울 때의 참조 확인이 이 컬럼으로 찾으므로 직접 만든다.

5. 서울에서 19:30에 시작하는 회차를 timestamp(시간대 없음) 컬럼에 저장하면 무엇이 문제인가?

19:30이라는 숫자만 남아, 그것이 서울 시각인지 UTC인지 DB가 모른다. 오프셋 없는 '2026-03-01T19:30' 문자열을 new Date()로 읽을 때와 같은 문제다. 서버나 DB 접속의 시간대가 바뀌면 "이미 시작했는가" 계산이 9시간 어긋날 수 있다. timestamptz는 절대 시점으로 저장해 이 문제가 없다.

6. 장르 '오페라'를 더하려면 무엇을 바꿔야 하고, '연극'을 빼려면 왜 더 어려운가?

GENRES에 값을 더하고 db:generate를 돌리면 ALTER TYPE ... ADD VALUE 마이그레이션이 생긴다. DTO, OpenAPI, 생성 타입은 같은 배열에서 이어지므로 함께 바뀐다. 값을 빼는 것은 PostgreSQL에 enum 값을 지우는 명령이 없어 새 타입으로 옮겨야 하고, 그 값을 쓰던 공연도 먼저 정리해야 한다.

7. 시드에서 createdAt은 넣고 isCancelled는 빼도 타입 오류가 나지 않는 이유는?

둘 다 NOT NULL이지만 기본값(DEFAULT now(), DEFAULT false)이 있어서 INSERT 타입에서 선택 항목이다. 빼면 DB가 기본값으로 채운다.
