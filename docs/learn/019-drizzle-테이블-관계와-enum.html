019 Drizzle 테이블 관계와 enum

1.3에서 테이블이 공연장, 공연, 회차 셋으로 늘며 쓴 Drizzle 문법(외래 키, 인덱스, enum, 시간대가 있는 일시, 기본값)을 apps/api/src/db/schema/의 실제 코드로 설명한다. pgTable, generatedAlwaysAsIdentity, db:generate 같은 기초는 004 문서에 있다.

한눈에 보기

세 테이블은 외래 키로 이어진다. 공연은 공연장 하나에서 열리고, 회차는 공연 하나에 속한다(GLOSSARY.md).

  • venues (venues.ts) 공연장 id, name
    • shows (shows.ts) 공연 venue_id → venues.id, 장르(enum)
      • performances (shows.ts) 회차 show_id → shows.id, 회차 취소 여부

파일은 모듈 단위로 나눴다(ADR 0003). 공연장은 venues 모듈, 공연과 회차는 shows 모듈이 소유하므로 performances도 shows.ts에 있다. 

// apps/api/src/db/schema/shows.ts
import { boolean, index, integer, pgEnum, pgTable, text, timestamp } from 'drizzle-orm/pg-core';
import { venues } from './venues.js';

export const GENRES = ['musical', 'play', 'concert', 'classical_dance', 'kids_family'] as const;
export type Genre = (typeof GENRES)[number];

export const genre = pgEnum('genre', GENRES);

export const shows = pgTable(
  'shows',
  {
    id: integer().primaryKey().generatedAlwaysAsIdentity(),
    venueId: integer('venue_id')
      .notNull()
      .references(() => venues.id),
    title: text().notNull(),
    genre: genre().notNull(),
    minAge: integer('min_age').notNull(),
    runningMinutes: integer('running_minutes').notNull(),
    description: text().notNull(),
    createdAt: timestamp('created_at', { withTimezone: true })
      .notNull()
      .defaultNow(),
  },
  (table) => [index().on(table.venueId)],
);

export const performances = pgTable(
  'performances',
  {
    id: integer().primaryKey().generatedAlwaysAsIdentity(),
    showId: integer('show_id')
      .notNull()
      .references(() => shows.id),
    startsAt: timestamp('starts_at', { withTimezone: true }).notNull(),
    salesOpenAt: timestamp('sales_open_at', { withTimezone: true }).notNull(),
    isCancelled: boolean('is_cancelled').notNull().default(false),
  },
  (table) => [index().on(table.showId)],
);

pgTable의 세 번째 인자 (table) => [...]는 처음 나온다. 컬럼 하나에 붙일 수 없는 것(인덱스, 복합 기본 키, 여러 컬럼에 걸친 UNIQUE)을 둔다. 두 번째 인자의 컬럼을 table로 받아 배열로 돌려준다.

컬럼 이름 직접 적기

컬럼 빌더의 첫 인자를 생략하면 객체 키가 그대로 컬럼 이름이 된다(004 문서). title처럼 한 단어면 문제가 없지만, 두 단어부터는 다르다.

코드 만들어지는 컬럼
venueId: integer() "venueId". 따옴표가 있어야만 찾을 수 있는 대소문자 이름
venueId: integer('venue_id') venue_id. PostgreSQL 관례인 snake_case

PostgreSQL은 따옴표 없는 이름을 소문자로 바꿔 읽는다. 그래서 "venueId" 컬럼은 psql에서 SELECT venueId FROM shows로 찾을 수 없고, 매번 따옴표를 쳐야 한다.

코드에서는 shows.venueId, row.venueId처럼 camelCase로 쓰고, DB에는 venue_id로 저장한다. 둘을 잇는 것이 빌더의 첫 인자다.

선택 읽기: casing 옵션을 쓰지 않은 이유

drizzle(url, { casing: 'snake_case' })를 주면 키에서 snake_case 이름을 자동으로 만든다. 하지만 같은 설정을 drizzle-kit 설정(drizzle.config.ts)과 drizzle()을 부르는 모든 곳에 넣어야 한다.

  • src/db/database.module.ts: 앱
  • src/db/seed.ts: 시드
  • test/setup/postgres.ts: 테스트 DB 마이그레이션
  • test/shows.int.spec.ts: 테스트 데이터 준비

한 곳이라도 빠뜨리면 그곳만 "venueId"를 찾다가 실행 중에 실패한다. 컬럼마다 이름을 적는 쪽이 더 길지만, 이름이 스키마 한곳에서만 정해진다.

timestamptz

startsAt: timestamp('starts_at', { withTimezone: true }).notNull(),

withTimezone: true를 주면 컬럼 타입이 timestamp with time zone(줄여서 timestamptz)이 된다. 이름과 달리 시간대를 저장하지는 않는다.

타입 저장하는 것 '2026-03-01 19:30+09'를 넣으면
timestamptz 절대 시점(UTC로 바꿔 저장) 2026-03-01 10:30 UTC로 저장. 읽을 때 세션 시간대로 보여 준다
timestamp 벽시계 숫자 시간대를 버리고 2026-03-01 19:30만 저장. 서울 시각인지 UTC인지 모른다

회차 시작 일시는 "지금보다 지났는가"로 판매 상태를 계산하는 데 쓰인다(#40). 시점이 하나로 정해져야 서버 시간대와 상관없이 같은 결과가 나오므로 timestamptz를 쓴다. 화면에서는 스토어가 Asia/Seoul로 바꿔 보여 준다.

TS에서는 Date

timestamp의 기본 mode는 'date'라서 읽으면 Date 객체가 오고, 쓸 때도 Date를 넣는다. { withTimezone: true, mode: 'string' }을 주면 문자열로 주고받는다. 서비스가 응답을 만들 때 toISOString()을 부르는 것은 이 값이 Date이기 때문이다.

기본값과 INSERT 타입

isCancelled: boolean('is_cancelled').notNull().default(false),
createdAt: timestamp('created_at', { withTimezone: true }).notNull().defaultNow(),
"is_cancelled" boolean DEFAULT false NOT NULL
"created_at" timestamp with time zone DEFAULT now() NOT NULL

둘 다 SQL의 DEFAULT다. INSERT에서 값을 빼면 DB가 채운다. .defaultNow()는 DEFAULT now()이므로 Node 서버가 아니라 DB 서버의 시각이 들어간다.

수식어는 SQL만 바꾸지 않고 TS 타입도 바꾼다.

수식어 SELECT 결과 타입 INSERT 값 타입
없음 string | null 선택
.notNull() string 필수
.notNull().default(...) string 선택 빼면 DB가 채운다
.generatedAlwaysAsIdentity() number 넣을 수 없음(타입에서 빠진다)

그래서 통합 테스트는 createdAt 없이 공연을 넣고, 시드는 과거 날짜를 흉내 내려고 createdAt을 직접 넣는다. 둘 다 같은 타입 검사를 통과한다.

#40에서 정한 "DB의 now()를 쓰지 않는다"는 판매 상태를 계산하는 쿼리 이야기다. 등록 일시의 기본값처럼 "넣은 순간"을 기록하는 데는 DB 시각을 써도 된다. 테스트에서 시각을 고정해야 하는 것은 판매 상태 쪽이다.

외래 키

venueId: integer('venue_id')
  .notNull()
  .references(() => venues.id),
ALTER TABLE "shows" ADD CONSTRAINT "shows_venue_id_venues_id_fk"
  FOREIGN KEY ("venue_id") REFERENCES "public"."venues"("id")
  ON DELETE no action ON UPDATE no action;

외래 키가 있으면 DB가 두 가지를 막는다.

  • 없는 공연장 id로 공연을 넣는 것
  • 공연이 남아 있는 공연장을 지우는 것

.notNull()과 함께 쓰면 "공연은 반드시 실제로 있는 공연장 하나에 속한다"는 규칙을 DB가 지킨다. 앱 코드에 버그가 있어도 깨진 데이터가 들어가지 않는다.

왜 화살표 함수인가

.references(venues.id)가 아니라 .references(() => venues.id)다. 함수로 감싸면 Drizzle은 함수를 저장만 해 두고, 실제 참조 정보가 필요할 때(마이그레이션 생성, 쿼리 실행) 부른다.

두 스키마 파일이 서로를 import하면(순환 import), 한쪽 파일이 읽히는 순간에 다른 쪽의 venues는 아직 정의되지 않았을 수 있다. 바로 venues.id를 읽으면 그때 터진다. 함수로 미뤄 두면 모든 파일을 읽은 뒤에 부르므로 안전하다. 지금은 shows.ts → venues.ts 한 방향뿐이지만 Drizzle은 항상 이 형태를 요구한다.

ON DELETE

옵션을 주지 않으면 no action이다. 참조하는 행이 남아 있으면 삭제를 거부한다. 다른 동작이 필요하면 두 번째 인자로 준다. 

.references(() => shows.id, { onDelete: 'cascade' }) // 공연을 지우면 회차도 함께 지운다

지금은 공연이나 공연장을 지우는 기능이 없어 기본값으로 두었다. 나중에 회차에 주문이 붙으면, 회차를 함부로 지울 수 없게 막는 기본값이 오히려 안전하다.

외래 키 때문에 시드는 TRUNCATE performances, shows, venues RESTART IDENTITY처럼 세 테이블을 한 문장에서 비운다. shows만 비우면 그 행을 참조하는 performances가 있어서 PostgreSQL이 거부한다.

외래 키 컬럼 인덱스

(table) => [index().on(table.showId)],
CREATE INDEX "performances_show_id_index" ON "performances" USING btree ("show_id");

PostgreSQL은 외래 키 컬럼에 인덱스를 자동으로 만들지 않는다. 참조되는 쪽(shows.id)은 기본 키라 인덱스가 있지만, 참조하는 쪽(performances.show_id)에는 직접 만들어야 한다. MySQL은 자동으로 만들므로 헷갈리기 쉽다.

이 인덱스가 쓰이는 곳은 다음과 같다.

  • 목록에서 회차를 공연 단위로 묶어 공연 기간(첫 회차, 마지막 회차)을 구할 때
  • 공연 상세에서 "이 공연의 회차"를 찾을 때(#48)
  • 공연을 지울 때 PostgreSQL이 참조하는 회차가 남았는지 확인할 때

index()에 이름을 주지 않아 drizzle-kit이 테이블_컬럼_index로 지었다. 이름을 정하려면 index('performances_show_id_idx')처럼 쓴다. 방식을 주지 않으면 B-tree다.

인덱스가 실제로 쓰이는지는 데이터가 적은 지금은 알 수 없다. PostgreSQL은 행이 적으면 인덱스보다 테이블 전체를 읽는 쪽을 고른다. 실행 계획을 보고 측정하는 일은 9단계에서 한다.

pgEnum과 as const

export const GENRES = ['musical', 'play', 'concert', 'classical_dance', 'kids_family'] as const;
export type Genre = (typeof GENRES)[number];
export const genre = pgEnum('genre', GENRES);

// 테이블 안에서
genre: genre().notNull(),
  1. as const 배열 타입이 string[]이 아니라 읽기 전용 튜플 readonly ['musical', 'play', ...]가 된다. 값 하나하나가 리터럴 타입으로 남는다.
  2. (typeof GENRES)[number] "튜플의 아무 칸"의 타입이다. 결과는 'musical' | 'play' | 'concert' | 'classical_dance' | 'kids_family'다. 값 목록과 타입을 배열 하나에서 얻으므로 둘이 어긋나지 않는다.
  3. pgEnum('genre', GENRES) PostgreSQL의 enum 타입을 정의한다. 테이블 밖에 있는 독립된 DB 객체다. 반환값 genre는 이 타입의 컬럼을 만드는 빌더 함수다.
  4. genre().notNull() enum 타입의 컬럼이다. 컬럼 이름이 키와 같아 인자를 생략했다. TS 타입이 위의 유니언이라 genre: 'opera'로 넣으면 컴파일 오류가 나고, 타입을 우회해도 DB가 거부한다. 
CREATE TYPE "public"."genre" AS ENUM('musical', 'play', 'concert', 'classical_dance', 'kids_family');
ALTER TABLE "shows" ADD COLUMN "genre" "genre" NOT NULL;

한 배열이 API 끝까지 간다

GENRES가 쓰이는 곳
  1. 스키마의 pgEnum
  2. DTO의 @ApiProperty({ enum: GENRES })
  3. openapi.json의 Genre
  4. 생성 클라이언트 타입

시드도 같은 배열을 돌며 장르를 붙인다. 스키마 파일은 다른 스키마 파일과 Drizzle만 import할 수 있으므로, 배열은 스키마 파일에 두고 DTO와 시드가 가져다 쓴다. 반대 방향(DTO에 두고 스키마가 import)은 규칙에 어긋난다.

enum을 바꾸는 비용

바꾸는 것 비용
값 더하기 쉬움 ALTER TYPE "genre" ADD VALUE 'opera'
값 빼기, 이름 바꾸기 어려움 새 타입을 만들고, 컬럼을 옮기고, 옛 타입을 지워야 한다. 그 값을 쓰는 행도 먼저 정리해야 한다

장르는 GLOSSARY에서 "고정된 분류"로 정했으므로 enum이 맞다. 운영자가 자주 추가하거나 이름을 바꿀 분류였다면 별도 테이블(genres)과 외래 키가 맞다.

스키마에서 얻는 타입

테이블 객체에서 행 타입을 바로 꺼낼 수 있다. 위의 수식어 규칙이 그대로 반영된다. 

type ShowRow = typeof shows.$inferSelect;
// {
//   id: number; venueId: number; title: string; genre: Genre;
//   minAge: number; runningMinutes: number; description: string; createdAt: Date;
// }

type NewShow = typeof shows.$inferInsert;
// {
//   venueId: number; title: string; genre: Genre;
//   minAge: number; runningMinutes: number; description: string;
//   createdAt?: Date;          // DEFAULT now()라 선택
// }                            // id 없음: GENERATED ALWAYS라 넣을 수 없다

db.insert(shows).values({...})가 받는 값이 NewShow다. 이 프로젝트는 타입 이름을 따로 만들지 않고, insert와 select에서 추론되는 타입을 그대로 쓴다. 응답 타입은 DTO(ShowSummaryDto)가 따로 정하므로 DB 행 타입이 API로 새어 나가지 않는다.

마이그레이션 손보기

스키마를 고치고 pnpm db:generate --name create_venues_and_performances를 실행하면 drizzle-kit이 drizzle/0001_create_venues_and_performances.sql을 만든다. 이번에는 생성된 SQL을 그대로 쓰지 못했다. 

ALTER TABLE "shows" ADD COLUMN "venue_id" integer NOT NULL;

기본값 없는 NOT NULL 컬럼은 빈 테이블에만 더할 수 있다. 개발 DB의 shows에는 1.1의 임시 시드 2행이 있었으므로, 그 행들의 venue_id를 무엇으로 채울지 몰라 PostgreSQL이 거부한다. 그래서 생성된 파일 맨 앞에 한 줄을 직접 넣었다. 

-- 기존 shows 행은 임시 시드 2개뿐이다. NOT NULL 컬럼을 더하려고 비우며, 시드를 다시 넣으면 채워진다.
TRUNCATE "shows" RESTART IDENTITY;--> statement-breakpoint
  • --> statement-breakpoint는 drizzle의 구분자다. 마이그레이션을 실행할 때 이 표시로 파일을 문장 단위로 나눈다. 직접 넣는 줄에도 붙여야 한다.
  • 손으로 고쳐도 다음 generate에는 영향이 없다. drizzle-kit은 SQL 파일이 아니라 drizzle/meta/0001_snapshot.json(스키마 모양을 저장한 파일)과 비교한다. TRUNCATE는 스키마 모양을 바꾸지 않으므로 스냅숏과 어긋나지 않는다.
  • 이미 적용된 마이그레이션은 고치지 않는다. drizzle은 적용한 마이그레이션을 DB의 기록 테이블로 관리한다. 적용한 뒤에 파일을 바꾸면 이미 적용한 DB에는 반영되지 않는다. 이번 수정은 PR에서 처음 만든 파일이라 괜찮다.

이 TRUNCATE는 행이 임시 데이터뿐이라 쓸 수 있었다. 운영 데이터가 있었다면 "기본값을 두고 컬럼 추가 → 데이터 채우기 → NOT NULL로 바꾸기"처럼 여러 단계로 나눠야 한다. 운영 DB에 그대로 적용하면 공연이 모두 지워진다.

쓰지 않은 relations()

Drizzle에는 relations()로 관계를 선언하면 중첩 객체로 조회하는 기능(Relational Queries)이 있다. 

// 이 프로젝트에서는 쓰지 않는다
db.query.shows.findMany({ with: { performances: true } });
.references() relations()
무엇인가 DB의 외래 키 제약 Drizzle 쿼리 편의 기능
마이그레이션에 나오는가 나온다 나오지 않는다
이 프로젝트 쓴다 쓰지 않는다

대신 서비스에서 JOIN을 직접 적는다. 판매 상태처럼 SQL 안에서 회차를 묶고 세야 하는 쿼리가 많아, JOIN과 집계가 코드에 그대로 보이는 쪽이 맞다고 판단했다. 

this.db
  .select({ id: shows.id, venueName: venues.name, start: period.start, end: period.end })
  .from(shows)
  .innerJoin(venues, eq(venues.id, shows.venueId))
  .innerJoin(period, eq(period.showId, shows.id));

relations()를 쓰려면 모든 테이블을 모은 객체를 drizzle()에 넘겨야 해서, 결국 중앙 집계 파일이 생긴다. 근거는 docs/research/drizzle-schema-organization.md의 Q3에 있다.

스스로 확인하기

질문에 먼저 답해 본 뒤, 눌러서 답을 확인한다.

1. venueId: integer()로 이름 없이 썼다면 SQL로 공연장 id를 어떻게 조회해야 하는가?

컬럼 이름이 "venueId"가 되므로 SELECT "venueId" FROM shows처럼 따옴표를 쳐야 한다. 따옴표 없이 venueId로 쓰면 PostgreSQL이 venueid로 읽어 컬럼을 찾지 못한다.

2. 회차가 남아 있는 공연을 DELETE FROM shows WHERE id = 1로 지우면 어떻게 되는가?

performances.show_id의 외래 키가 ON DELETE no action이라 PostgreSQL이 삭제를 거부한다. 회차를 먼저 지우거나, 외래 키에 onDelete: 'cascade'를 줘야 한다.

3. 외래 키를 걸었는데 왜 index().on(table.showId)를 따로 썼는가?

PostgreSQL은 외래 키를 걸어도 참조하는 쪽 컬럼에 인덱스를 만들지 않는다. 회차를 공연별로 묶거나 찾는 쿼리, 공연을 지울 때의 참조 확인이 이 컬럼을 쓰므로 직접 만든다.

4. 서울에서 19:30에 시작하는 회차를 timestamp(시간대 없음) 컬럼에 저장하면 무엇이 문제인가?

19:30이라는 숫자만 남아, 그것이 서울 시각인지 UTC인지 DB가 모른다. 서버나 DB 세션의 시간대가 바뀌면 "이미 시작했는가" 계산이 9시간 어긋날 수 있다. timestamptz는 절대 시점으로 저장해 이 문제가 없다.

5. 장르 '오페라'를 더하려면 무엇을 바꿔야 하고, '연극'을 빼려면 왜 더 어려운가?

GENRES에 값을 더하고 db:generate를 돌리면 ALTER TYPE ... ADD VALUE 마이그레이션이 생긴다. DTO, OpenAPI, 생성 타입은 같은 배열에서 이어지므로 함께 바뀐다. 값을 빼는 것은 PostgreSQL이 enum 값 삭제를 지원하지 않아 새 타입으로 옮겨야 하고, 그 값을 쓰던 공연도 먼저 정리해야 한다.

6. 시드에서 createdAt은 넣고 isCancelled는 빼도 타입 오류가 나지 않는 이유는?

둘 다 NOT NULL이지만 기본값(DEFAULT now(), DEFAULT false)이 있어서 INSERT 타입에서 선택 항목이다. 빼면 DB가 기본값으로 채운다.
