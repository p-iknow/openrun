13 다대다 관계와 연결 테이블

양쪽 모두 "여러 개"인 관계(다대다)를 왜 외래 키 하나로 표현할 수 없는지, 연결 테이블이 그 문제를 어떻게 푸는지, 언제 만드는지를 본다. 예시는 학생과 수업으로 시작하고, 이 저장소의 회차 좌석(performance_seats)과 좌석 등급 지정(seat_grade_assignments)으로 이어 간다. 외래 키와 일대다 관계는 db-and-drizzle 01 문서에 있다.

출발점: 일대다는 외래 키 하나로 된다

공연장 하나에 공연이 여러 개 열리고, 공연 하나는 공연장 하나에서만 열린다. 이런 일대다 관계는 "다" 쪽 행에 상대의 id를 하나 적으면 된다.

shows (공연)
idtitlevenue_id
1뮤지컬 A7
2콘서트 B7

공연 행마다 공연장이 딱 하나라서 칸 하나(venue_id)에 들어간다.

양쪽 다 여러 개면 칸 하나로 안 된다

학생과 수업을 보자.

  • 학생 한 명은 수업을 여러 개 듣는다.
  • 수업 하나에는 학생이 여러 명 있다.

양쪽 모두 "여러 개"인 관계를 다대다라고 한다. 외래 키를 어느 쪽에 두어도 칸 하나로는 표현할 수 없다. 철수가 수학과 영어를 둘 다 들으면 학생 행의 course_id 칸에 무엇을 넣어야 할까?

칸에 목록을 넣으면 들어가기는 한다.

students (목록을 넣은 경우)
idnamecourse_ids
1철수[10, 11]
2영희[10]

하지만 이렇게 두면 문제가 생긴다.

하고 싶은 일목록 칸일 때
수학(10)을 듣는 학생 찾기모든 학생의 목록을 하나씩 열어 봐야 한다
없는 수업 id 막기목록 안의 값에는 외래 키를 걸 수 없다. 99가 들어가도 DB가 모른다
같은 수업 두 번 신청 막기목록 안의 중복은 유니크 제약으로 막을 수 없다
수강 취소목록을 꺼내 고치고 다시 저장해야 한다

해결: 관계 자체를 행으로 만든다

"철수가 수학을 듣는다"는 사실 하나를 행 하나로 적는 테이블을 따로 둔다. 이 테이블을 연결 테이블(join table, 교차 테이블)이라고 한다.

연결 행은 외래 키 두 개를 들고 각각 한쪽을 가리킨다. 그러면 다대다 관계가 일대다 두 개로 쪼개진다.

두 선 모두 까마귀 발(여러 개)이 연결 테이블 쪽에 있다. 학생 하나에 수강 행이 여러 개, 수업 하나에 수강 행이 여러 개다.

앞 절의 문제가 모두 풀린다.

하고 싶은 일연결 테이블일 때
수학(10)을 듣는 학생 찾기course_id = 10인 행을 찾는다. 인덱스도 쓸 수 있다
없는 수업 id 막기칸마다 값이 하나라 course_id에 외래 키를 건다
같은 수업 두 번 신청 막기(student_id, course_id)에 기본 키나 유니크 제약을 건다
수강 취소행 하나를 지운다

자바스크립트로 보면, 객체 안에 배열을 품는 대신 관계를 담은 배열을 따로 두는 것과 같다.

// 품기: 한쪽 객체 안에 목록
const student = { id: 1, name: '철수', courseIds: [10, 11] };

// 연결 테이블: 관계를 따로 나열
const enrollments = [
  { studentId: 1, courseId: 10 },
  { studentId: 1, courseId: 11 },
  { studentId: 2, courseId: 10 },
];
enrollments.filter((e) => e.courseId === 10); // 수학 듣는 학생
enrollments.filter((e) => e.studentId === 1); // 철수가 듣는 수업

학생 쪽에서 찾든 수업 쪽에서 찾든 같은 방법이다. 한쪽 객체에 목록을 품으면 반대쪽에서 찾기가 어려워지는데, 연결 테이블은 양쪽이 대칭이다.

관계에 붙은 정보도 연결 행에 둔다

"철수가 수학에서 받은 성적"은 어디에 둘까? 학생의 정보도 아니고 수업의 정보도 아니다. 철수와 수학의 관계에만 붙는 정보다. 그래서 연결 행에 둔다.

어떤 정보가 "A의 것도 B의 것도 아니고 A와 B의 조합에 붙는다"면, 그 정보는 연결 행에 둔다. 이 저장소의 연결 테이블은 모두 이런 정보를 가진다.

회차 좌석: 회차 × 좌석 → 판매 여부

  • 회차 하나는 좌석 여러 개를 판다(공연장의 모든 좌석).
  • 좌석 하나는 회차 여러 개에서 팔린다(그 공연장에서 열리는 모든 회차).

"팔렸나"는 좌석만의 정보가 아니다. A구역 1열 1번이 11-20 회차에서는 팔렸어도 11-21 회차에서는 비어 있을 수 있다. 이 회차의 이 좌석에 붙는 정보라서 연결 행에 둔다.

좌석 등급 지정: 공연 × 좌석 → 등급

  • 공연 하나는 좌석 여러 개에 등급을 정한다.
  • 좌석 하나는 공연 여러 개에서 등급을 받는다(같은 공연장에서 열리는 공연마다).

같은 A구역 1열 1번이 뮤지컬 A에서는 VIP석이고 콘서트 B에서는 스탠딩이다. 등급은 이 공연의 이 좌석에 붙는 정보라서 연결 행에 둔다.

등급을 seats에 두면 공연마다 다른 등급을 표현할 수 없고, shows에 두면 좌석 수만큼 칸이 필요하다. 기본 키 (show_id, seat_id)가 "공연마다 좌석 하나에 등급은 하나"를 지킨다. 등급이 다른 공연의 것이 되지 않게 막는 방법은 12 문서에 있다.

연결 테이블의 키 고르기

연결 테이블에는 "같은 조합이 두 번 들어가지 않게" 막는 장치가 거의 항상 필요하다. 같은 회차에 같은 좌석이 두 번 생기거나, 같은 공연의 같은 좌석에 등급이 두 번 붙으면 안 되기 때문이다. 막는 방법이 두 가지 있고, 이 저장소의 두 연결 테이블이 하나씩 쓴다.

회차 좌석 performance_seats좌석 등급 지정 seat_grade_assignments
기본 키id (따로 둔 번호)(show_id, seat_id) (조합 그대로)
조합 중복 막기UNIQUE (performance_id, seat_id)를 따로 건다기본 키가 막는다
생기는 인덱스2개 (id, 조합)1개 (조합)

중복을 막는 효과는 둘이 같다. 고르는 기준은 하나다. 다른 테이블이 이 행을 가리켜야 하는가?

예: 티켓이 회차 좌석을 가리킬 때

예매 기능이 생기면 회차 좌석을 가리키는 테이블이 여럿 생긴다. 용어집에 정해 둔 좌석 선점(결제 전까지 좌석을 한 사용자에게 묶어 두기), 주문(회차 좌석 최대 4석), 티켓(회차 좌석 하나당 하나)이 모두 "어느 회차 좌석인가"를 적어야 한다. 그중 티켓 테이블을 만든다고 생각해 보자. 회차 좌석의 기본 키 모양에 따라 티켓이 들고 있어야 하는 칸이 달라진다.

다른 테이블이 자주 가리킬 행이라면, 그 행을 부를 짧은 이름 하나(id)를 따로 두는 편이 가리키는 쪽 모두를 단순하게 만든다. 조합 중복은 UNIQUE로 따로 막는다.

아무도 가리키지 않으면 조합이 기본 키로 충분하다

좌석 등급 지정은 다른 테이블이 가리키지 않는 끝자리 테이블이다. 읽을 때도 "이 공연의 좌석들의 등급"처럼 늘 show_id로 찾는다. 여기에 id를 따로 두면 얻는 것 없이 비용만 는다.

  • 칸 하나와 그 칸의 인덱스가 더 생긴다. 공연 수 × 좌석 수만큼 행이 쌓이는 테이블이라 행마다 붙는 비용이 크다.
  • 중복을 막으려면 어차피 UNIQUE (show_id, seat_id)를 따로 걸어야 해서 인덱스가 둘이 된다.

조합을 기본 키로 쓰면 인덱스 하나가 중복 막기와 show_id로 찾기를 모두 맡는다. 앞 컬럼이 show_id라서 앞 컬럼 규칙대로 show_id만으로 찾을 때도 쓰인다. 

// 다른 테이블이 가리킬 행: id 기본 키 + 조합 유니크
(table) => [unique().on(table.performanceId, table.seatId)],

// 아무도 가리키지 않는 행: 조합 기본 키
(table) => [primaryKey({ columns: [table.showId, table.seatId] })],

회차 좌석에 id를 둔 이유는 스키마 주석(apps/api/src/db/schema/shows.ts의 performanceSeats)에 적혀 있다. 다만 회차 좌석을 가리키는 좌석 선점, 주문, 티켓 테이블은 예매 기능을 만들 때 생기므로 아직 없다. 지금 id는 남은 좌석 수를 셀 때(count(performance_seats.id))만 쓰인다.

언제 만드는지 판단하는 법

두 대상 A, B 사이에 관계가 있으면 두 질문을 한다.

A 하나에 B가 여러 개?B 하나에 A가 여러 개?관계만드는 것
예아니오일대다B에 a_id 외래 키 하나
아니오예다대일A에 b_id 외래 키 하나
예예다대다연결 테이블

이런 생각이 들면 연결 테이블이 필요하다는 신호다.

  • "이 칸에 id를 여러 개 넣고 싶다" (배열 컬럼, 쉼표로 이은 문자열)
  • "이 정보는 A의 것도 B의 것도 아니고 A와 B의 조합에 붙는다" (판매 여부, 등급, 성적)

실제 서비스에서 흔한 예는 이렇다.

관계연결 행에 붙는 정보
게시글 × 태그없음. 관계만 있다
사용자 × 찜한 공연찜한 시각
주문 × 상품수량, 주문할 때의 가격
회차 × 좌석판매 여부

PostgreSQL에는 배열 컬럼(integer[])이 있어서 목록을 칸 하나에 넣을 수는 있다. 하지만 배열 안의 값에는 외래 키를 걸 수 없으므로, 다른 테이블의 id를 담는 관계에는 연결 테이블을 쓴다.

  • 나. 공연과 출연 배우

답 보기

가: 좌석 하나는 구역 하나에만 있다. 일대다라서 seats.section_id 외래 키 하나로 된다.

나: 공연 하나에 배우가 여러 명이고, 배우 한 명은 공연 여러 개에 나온다. 다대다라서 연결 테이블이 필요하다. 배역 이름 같은 정보는 연결 행에 둔다.

다: 등급은 공연 하나에만 속한다(뮤지컬 A의 VIP석). 일대다라서 seat_grades.show_id 외래 키 하나로 된다.

회차 좌석 절의 is_sold를 옮긴다고 생각한다.

 export const seats = pgTable('seats', {
   id: integer().primaryKey().generatedAlwaysAsIdentity(),

 });
