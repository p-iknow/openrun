06 판매 상태 쿼리 읽기

1.3(#40)과 1.4(#41)에서 만든 판매 상태 계산(apps/api/src/shows/show-sales-status.ts)과, 그것을 공연 목록에 붙인 findPage()의 바뀐 부분을 따라간다. 같은 예시 데이터로 회차 한 줄이 공연 판매 상태 하나가 되기까지를 보고, 왜 그렇게 썼는지 설명한다. 공연 목록 쿼리의 나머지(공연 기간, 정렬, 페이지)는 db-and-drizzle 05 문서에 있다. 문법은 db-and-drizzle 03 문서, CASE·FILTER 같은 SQL 개념은 db-and-drizzle 01 문서에 있다.

이 문서의 "현재"는 2026-11-10 12:00(한국 시각)으로 정해 둔다. 판매 상태는 조회하는 시각에 따라 답이 바뀐다. 그래서 문서에 나오는 "현재", 코드의 now, 표의 판매 상태는 모두 이 시각을 기준으로 한다. 날짜는 모두 2026년이라 표에서는 연도를 빼고 11-10 12:00처럼 쓴다. 다른 시각으로 생각해 보는 문제는 스스로 확인하기에서 "현재 시각이 ~이면"으로 따로 적는다.

한눈에 보기

판매 상태는 테이블에 저장하지 않는다. 시간이 지나면 저절로 바뀌는 값이라, 저장하면 누군가 때맞춰 고쳐 줘야 한다. 그래서 조회할 때마다 "현재 시각"을 기준으로 쿼리 안에서 계산한다. 저장하는 것은 회차 취소 여부(is_cancelled)뿐이다. 회차 좌석이 팔렸는지는 판매 상태에 쓰지 않는다. 

// apps/api/src/shows/show-sales-status.ts (주석 줄임)
export const SHOW_SALES_STATUSES = ['on_sale', 'upcoming', 'ended'] as const;
export type ShowSalesStatus = (typeof SHOW_SALES_STATUSES)[number];

function priorityOf(status: ShowSalesStatus): SQL {
  return sql.raw(String(SHOW_SALES_STATUSES.indexOf(status)));
}
function literalOf(status: ShowSalesStatus): SQL {
  return sql.raw(`'${status}'`);
}

// ① 회차 하나의 판매 상태를 순번으로
function performancePriority({ now }: { now: Date }): SQL<number> {
  return sql<number>`case
    when ${performances.isCancelled} or ${performances.startsAt} <= ${now} then ${priorityOf('ended')}
    when ${now} < ${performances.salesOpenAt} then ${priorityOf('upcoming')}
    else ${priorityOf('on_sale')}
  end`;
}

export function showSalesStatusSubquery(db: Database, { now }: { now: Date }) {
  const priority = performancePriority({ now });
  const showPriority = sql`min(${priority})`;                         // ② 공연별 가장 작은 순번
  const toStatus = sql.join(                                          // ③ 순번 → 이름
    SHOW_SALES_STATUSES.map((status) => sql`when ${priorityOf(status)} then ${literalOf(status)}`),
    sql` `,
  );

  return db
    .select({
      showId: performances.showId,
      salesStatus: sql<ShowSalesStatus>`case ${showPriority} ${toStatus} end`.as('sales_status'),
      salesOpenAt: sql<Date | null>`case                              // ④ 판매 예정일 때만
        when ${showPriority} = ${priorityOf('upcoming')}
        then min(${performances.salesOpenAt}) filter (where ${priority} = ${priorityOf('upcoming')})
      end`
        .mapWith(performances.salesOpenAt)
        .as('sales_open_at'),
    })
    .from(performances)
    .groupBy(performances.showId)
    .as('show_sales_status');
}
회차 한 줄이 공연 판매 상태가 되기까지
  1. 회차마다 판매 상태를 순번(0~2)으로 계산한다
  2. 공연별로 묶어 가장 작은 순번을 고른다
  3. 순번을 상태 이름으로 바꾼다
  4. 판매 예정이면 판매 오픈 일시를 구한다
  5. 공연 목록에 JOIN하고 판매 종료는 뺀다

계산할 규칙

티켓(#40, #41)과 용어집이 정한 규칙이다. 코드는 이것을 SQL로 옮긴 것뿐이다.

  1. 회차의 판매 상태 위에서부터 먼저 맞는 것을 고른다. 판매 종료(취소됐거나 회차 시작 일시가 지남) → 판매 예정(판매 오픈 일시 전) → 판매 중. 회차 좌석이 팔렸는지는 보지 않는다. 다 팔린 회차도 판매 기간 안이면 판매 중이다.
  2. 공연 판매 상태 회차들의 판매 상태 중 우선순위가 가장 높은 것이다. 판매 중 > 판매 예정 > 판매 종료. 실제 예매 서비스(NOL 티켓, YES24 티켓, 멜론티켓)처럼 매진과 회차 취소는 공연 판매 상태로 두지 않는다.
  3. 목록 공연 판매 상태가 판매 종료인 공연은 목록과 전체 개수에서 뺀다. 판매 예정이면 판매 오픈 일시를 함께 준다.

1번은 회차 한 줄을 보는 규칙이고, 2번은 공연에 속한 여러 줄을 하나로 줄이는 규칙이다. SQL에서 한 줄을 보는 것은 CASE, 여러 줄을 하나로 줄이는 것은 집계 함수와 GROUP BY가 맡는다.

function performancePriority({ now }: { now: Date }): SQL<number> {
  return sql<number>`case
    when ${performances.isCancelled} or ${performances.startsAt} <= ${now} then ${priorityOf('ended')} -- 2
    when ${now} < ${performances.salesOpenAt} then ${priorityOf('upcoming')} -- 1

priority는 행도 숫자도 아니고 식(SQL로 쓴 계산식)이다. JS에서 performancePriority({ now })를 부르면 계산은 일어나지 않고 case when ... end라는 SQL 글자만 만들어진다. 엑셀에서 열 맨 위에 수식을 한 번 써 두면 행마다 값이 채워지듯, DB가 쿼리를 실행할 때 이 식을 회차 테이블의 행마다 계산해 행 하나에 순번 하나를 만든다. 이 순번들은 JS로 돌아오지 않고 min(${priority}) 안에서만 쓰인다.

CASE에는 회차 좌석을 보는 갈래가 없다. 회차 좌석이 모두 팔린 회차도 판매 기간 안이면 else로 판매 중이다. 예매가 취소되면 그 좌석은 바로 다시 판매 가능이 되므로, 공연이 시작하기 전까지는 다시 살 수 있기 때문이다. 실제 예매 서비스도 목록에서 매진을 공연 판매 상태로 보여 주지 않는다.

경계: 정각은 어느 쪽인가

비교 기호 하나가 "정각"이 어느 쪽에 속하는지 정한다. 통합 테스트는 이 경계를 1ms 전과 정각으로 확인한다.

조건 1ms 전 정각 뜻
starts_at <= now 판매 중 판매 종료 회차가 시작하는 순간 판매가 끝난다
now < sales_open_at 판매 예정 판매 중 판매 오픈 일시가 되는 순간 판매가 시작된다

<=를 <로 바꾸면, 시작 정각에 그 회차가 아직 판매 중으로 보인다. 공연이 이미 시작한 순간에도 예매 버튼이 열려 있는 셈이다. 실제로 바꿔 보면 테스트 "회차 시작 정각"이 실패한다.

상태를 숫자로 계산하는 이유

CASE가 'ended' 같은 이름이 아니라 숫자를 돌려주는 데는 이유가 있다. 공연 판매 상태는 "회차 상태 중 우선순위가 가장 높은 것"이다. 우선순위가 높을수록 작은 숫자를 주면, 이 정의가 곧 가장 작은 숫자 고르기, 즉 min()이 된다. 

export const SHOW_SALES_STATUSES = [
  'on_sale',   // 0 판매 중    ← 우선순위 가장 높음
  'upcoming',  // 1 판매 예정
  'ended',     // 2 판매 종료  ← 우선순위 가장 낮음
] as const;

배열의 순서가 우선순위이고, 각 상태의 순번은 배열 안의 위치(indexOf)다. 이름으로 계산하면 min('ended', 'on_sale')이 알파벳 순서로 'ended'를 골라 버린다. 우선순위와 알파벳 순서는 아무 상관이 없다.

상태를 하나 더할 때는 배열의 알맞은 자리에 한 줄만 넣으면 된다. 뒤쪽 순번이 하나씩 밀리고, 아래에서 볼 SQL의 숫자와 이름 매핑도 배열에서 다시 만들어진다.

공연 판매 상태로 모으기

지금까지는 회차 한 줄마다 순번을 구했다. 이제 같은 공연의 회차들을 한데 모아 순번 하나로 줄인다. 이 일은 쿼리 맨 아래의 .groupBy()와 select 안의 min()이 함께 한다. 

const priority = performancePriority({ now });  // 회차 한 줄의 순번 (앞 절의 CASE)
const showPriority = sql`min(${priority})`;      // 그 순번들 중 가장 작은 값
const toStatus = sql.join(/* ... */);            // 순번 → 이름 (아래 "순번을 이름으로 바꾸기")

return db
  .select({
    showId: performances.showId,
    salesStatus: sql`case ${showPriority} ${toStatus} end`.as('sales_status'),
    salesOpenAt: /* ... */,                      // 판매 예정일 때 판매 오픈 일시 (다음 절)
  })
  .from(performances)           // 회차 테이블의 모든 줄(회차 10개)에서
  .groupBy(performances.showId) // show_id가 같은 줄끼리 한 묶음으로 모은다
  .as('show_sales_status');     // → select는 묶음마다 한 줄씩 나온다

groupBy가 회차를 공연별로 묶는다

.groupBy(performances.showId)는 SQL의 GROUP BY "show_id"가 된다. 회차 10줄을 show_id가 같은 것끼리 묶어 묶음 4개를 만든다. 자바스크립트로는 Object.groupBy(rows, (r) => r.showId)와 같다. .groupBy()는 맨 아래에 적혀 있지만 DB는 select보다 먼저 실행한다(쓰는 순서와 실행 순서).

묶음 (show_id) 들어간 회차 회차마다 구한 순번
1 10, 11, 12 2, 0, 2
2 13, 14, 15 1, 1, 2
3 16, 17 2, 2
4 18, 19 0, 2

groupBy는 select 전체에 적용된다

groupBy는 min 하나가 아니라 이 서브쿼리의 select 전체에 적용된다. 결과는 묶음마다(공연마다) 한 줄, 모두 4줄이 나오고, 한 줄이니 컬럼마다 값도 하나여야 한다. 그런데 묶음 하나에는 회차가 여러 줄 들어 있다. 그래서 select의 컬럼은 묶음마다 값이 하나로 정해져야 한다(GROUP BY가 있으면 SELECT에 무엇을 쓸 수 있나).

컬럼 묶음마다 값 하나가 되는 방법
showId 묶는 기준이라 묶음 안의 회차가 모두 같은 값이다
salesStatus case min(회차 순번) ... end: min으로 값 하나를 만든 뒤 이름으로 바꾼다
salesOpenAt case when min(회차 순번) = 1 then min(sales_open_at) filter (...) end: 여기도 min으로 줄인다(판매 오픈 일시)

회차 순번(priority)을 select에 그대로 넣지 않고 꼭 min( )으로 감싼 이유도 이것이다. priority는 회차마다 값이 다른 식이라, 그대로 넣으면 공연 1 묶음에서 2, 0, 2 중 무엇을 줄지 정할 수 없어 PostgreSQL이 에러를 낸다. 

// 이렇게 쓰면 에러
.select({
  showId: performances.showId,
  startsAt: performances.startsAt, // 공연 1 묶음엔 회차가 3개인데, 어느 starts_at?
})
.groupBy(performances.showId)
// ERROR: column "performances.starts_at" must appear in the GROUP BY clause
//        or be used in an aggregate function

집계 함수는 여러 값 중 하나를 고르는 것이 아니라 여러 값을 하나로 줄이는 것이다. 이 쿼리의 min은 결과적으로 있는 순번 중 하나(공연 1이면 0)가 나오지만, count(*)를 쓰면 3(회차 수)처럼 어느 회차의 값도 아닌 새 값이 나온다.

min이 묶음마다 가장 작은 순번을 고른다

showPriority는 회차 순번 식(priority)을 min()으로 감싼 것이다. 테이블 전체가 아니라 묶음 안에서 가장 작은 순번을 고른다. 

function performancePriority({ now }) {
  return sql`case
    when ${performances.isCancelled} or ${performances.startsAt} <= ${now} then ${priorityOf('ended')}
    when ${now} < ${performances.salesOpenAt} then ${priorityOf('upcoming')}
    else ${priorityOf('on_sale')}
  end`;
}

const priority = performancePriority({ now }); // CASE 식
const showPriority = sql`min(${priority})`;

${priority} 자리에는 앞 절의 CASE 글자가 통째로 들어간다. DB가 받는 SQL은 이렇다. 읽기 쉽게 컬럼 이름의 따옴표와 테이블 이름을 빼고, 파라미터($1)는 값으로 바꿔 적고, 나머지 컬럼은 생략했다.

select show_id,
       min(        -- showPriority: sql`min(${priority})`의 min(
         case      -- ${priority} 자리에 들어간 CASE 식 시작
           when is_cancelled or starts_at <= '2026-11-10 12:00+09' then 2
           when '2026-11-10 12:00+09' < sales_open_at then 1
           else 0
         end       -- ${priority} 끝
       )           -- min( 의 닫는 괄호
from performances
group by show_id

DB가 하는 일을 JS로 쓰면 이렇다.

// group by show_id: 같은 공연의 회차끼리 묶는다
const groups = Object.groupBy(performances, (row) => row.showId);

for (const [showId, rows] of Object.entries(groups)) {
  // case ... end: 묶음 안의 행마다 순번을 계산한다   ← priority
  const priorities = rows.map((row) => {
    if (row.isCancelled || row.startsAt <= now) return 2;
    if (now < row.salesOpenAt) return 1;
    return 0;
  });
  // min(...): 그 순번들 중 가장 작은 값               ← showPriority
  const showPriority = Math.min(...priorities);
}

priority는 rows.map 안쪽 함수이고, min(${priority})는 Math.min(...rows.map(그 함수))다.

공연 회차 순번들 min 공연 판매 상태
1 달빛 정원 2, 0, 2 0 판매 중
2 겨울 기차 1, 1, 2 1 판매 예정
3 붉은 숲 2, 2 2 판매 종료
4 푸른 등대 0, 2 0 판매 중

붉은 숲은 끝난 회차와 취소된 회차만 남아 판매 종료다. 둘 다 더 팔 수 없는 회차라 공연도 더 팔 것이 없다. 푸른 등대는 남은 회차 18이 다 팔렸지만 판매 중이다. 판매 기간 안이라 취소표가 나오면 다시 살 수 있다.

salesStatus: sql<ShowSalesStatus>`case ${showPriority} ${toStatus} end`.as('sales_status'),

sql.join이 배열에서 when 0 then 'on_sale' when 1 then 'upcoming' ...을 만든다. 이것을 case ${showPriority} ... end에 넣으면 switch처럼 쓰는 CASE가 된다.

  when 0 then 'on_sale'
  when 1 then 'upcoming'

min(...)에는 이름(as)이 없다. select에 따로 나오지 않고 CASE의 재료로만 쓰이기 때문이다. 이름 "sales_status"는 min을 감싼 CASE 결과 전체에 붙고, 결과 컬럼에 min의 숫자는 없다. JS로는 toName(Math.min(...priorities))처럼 Math.min의 결과를 변수에 담지 않고 바로 넘기는 것과 같다.

이름으로 바꾸는 일을 JS가 아니라 SQL에서 하는 이유는 필터 때문이다. 결과 컬럼이 이름이면 바깥 쿼리가 ne(salesStatus.salesStatus, 'ended')처럼 이름으로 거를 수 있다. 다음 티켓의 판매 상태 필터도 inArray(salesStatus.salesStatus, ['on_sale', 'upcoming'])처럼 쓸 수 있다.

sql<ShowSalesStatus>는 결과 타입을 알려 주는 타입 약속이고, .as('sales_status')는 서브쿼리 밖에서 이 값을 부를 이름이다(.as()가 두 번 나오는 이유).

CASE가 겹쳐 있을 때 groupBy는 어떻게 동작하나

sales_status는 안쪽 CASE를 min이 감싸고, 그것을 다시 바깥 CASE가 감싼 세 겹이다. groupBy는 CASE가 겹친 모양을 신경 쓰지 않는다. 각 부분이 min 괄호 안에 있느냐, 밖에 있느냐만 본다(집계 괄호 안은 행마다, 밖은 묶음마다). 

case                                   -- 괄호 밖 → 묶음(공연)마다: 4번
  min(                                 -- ── 경계: 여러 행 → 값 하나
    case                               -- 괄호 안 → 행(회차)마다: 10번
      when is_cancelled or starts_at <= '2026-11-10 12:00+09' then 2
      when '2026-11-10 12:00+09' < sales_open_at then 1
      else 0
    end
  )
  when 0 then 'on_sale'
  when 1 then 'upcoming'
  when 2 then 'ended'
end as "sales_status"

DB는 이 순서로 계산한다.

  1. FROM 회차 10줄을 가져온다.
  2. GROUP BY show_id로 4묶음을 만든다.
  3. 괄호 안 묶음마다 그 묶음의 회차 하나하나에 안쪽 CASE를 계산한다. 공연 1이면 2, 0, 2.
  4. min 그 값들을 하나로 줄인다. 공연 1이면 0.
  5. 괄호 밖 바깥 CASE가 그 값 하나로 이름을 정한다. 공연 1이면 'on_sale'.

바깥 CASE에서 회차마다 다른 컬럼(starts_at 등)을 집계 없이 쓰면 공연 1의 어느 회차 값인지 정할 수 없어 에러가 난다. JS로는 rows.map 콜백 안에서만 row를 쓸 수 있고, 바깥에서는 Math.min 결과와 showId만 쓸 수 있는 것과 같다. 

for (const [showId, rows] of Object.entries(groups)) {
  // 콜백 안: row를 쓸 수 있다 (행마다)
  const m = Math.min(...rows.map((row) => 안쪽CASE(row)));

  // 밖: row가 없다. m과 showId만 (묶음마다)
  const status = 바깥CASE(m);
}

판매 오픈 일시

const priority = performancePriority({ now }); // 회차 한 줄의 순번 (행마다)
const showPriority = sql`min(${priority})`; // 공연의 가장 작은 순번 (묶음마다)

salesOpenAt: sql<Date | null>`case
  when ${showPriority} = ${priorityOf('upcoming')}
  then min(${performances.salesOpenAt})
       filter (where ${priority} = ${priorityOf('upcoming')})
end`
  .mapWith(performances.salesOpenAt)
  .as('sales_open_at'),

같은 회차 순번 식 priority가 두 번 쓰인다. 한 번은 min( )으로 감싸 공연 단위 판단에 (when), 한 번은 filter 안에서 회차 단위 조건에(then) 쓰인다. 안쪽부터 읽는다.

  1. min(sales_open_at) filter (where 회차 순번 = 1) 판매 예정 회차만 골라 가장 이른 판매 오픈 일시를 구한다(집계의 FILTER). 겨울 기차라면 회차 13(11-13), 14(11-12) 중 11-12 14:00이다. 회차 15는 판매 오픈이 11-11로 더 이르지만 취소돼 판매 종료(순번 2)이므로 고르지 않는다. min 괄호 안과 filter 조건은 회차마다 계산된다.
  2. case when 공연 순번 = 1 then ... end 공연이 판매 예정일 때만 1번 값을 쓰고, 아니면 else가 없으니 NULL이다. 이 CASE는 집계 괄호 밖이라 공연마다 한 번 계산되고, when과 then은 같은 공연의 회차들을 본다. 달빛 정원에 판매 예정 회차가 섞여 있어도, 공연은 판매 중이라 판매 오픈 일시를 보여 줄 이유가 없다.
  3. .mapWith(performances.salesOpenAt) 직접 쓴 조각이라 Drizzle이 결과를 Date로 바꿔 주지 않는다. timestamptz 컬럼과 같은 방법으로 바꾸라고 알려 준다(.mapWith). 그래서 서비스가 salesOpenAt?.toISOString()을 부를 수 있다.
공연 sales_status sales_open_at
1 on_sale NULL
2 upcoming 11-12 14:00
3 ended NULL
4 on_sale NULL

이 표가 서브쿼리 show_sales_status의 결과다. 공연당 한 줄이고, 회차가 없는 공연은 줄이 없다.

서브쿼리를 함수로 둔 이유

공연 기간 서브쿼리(period)는 findPage() 안에 바로 썼다. 판매 상태 서브쿼리는 showSalesStatusSubquery(db, { now })라는 함수로 따로 뺐다(서브쿼리를 돌려주는 함수).

  • 상세 API가 같은 계산을 써야 한다. 공연 상세 화면도 공연 판매 상태를 보여 준다. 목록과 상세가 판매 상태를 따로 계산하면 언젠가 둘이 다른 답을 낸다. 상세는 이 함수를 불러 JOIN하고 공연 id로 거르면 된다.
  • 필터, 개수, 페이지가 같은 기준이어야 한다. 판매 상태를 JS에서 계산하면, DB가 20개를 잘라 준 뒤에 거르게 되어 한 페이지가 20개보다 적어지고 전체 개수도 어긋난다. 쿼리 안에서 계산해야 where, count, limit이 모두 같은 값을 본다.
  • now를 인자로 받는다. 함수가 스스로 시각을 정하지 않으니, 부르는 쪽이 정한 시각 하나로 계산한다. 바로 다음 Clock 절과 이어진다.

현재 시각은 Clock에서

// apps/api/src/clock/clock.module.ts
export abstract class Clock {
  abstract now(): Date;
}
export class SystemClock extends Clock {
  now(): Date { return new Date(); }
}
// ClockModule이 Clock 자리에 SystemClock을 넣어 전역으로 내보낸다.

// ShowsService
constructor(@Inject(DATABASE) private readonly db: Database, private readonly clock: Clock) {}
showSalesStatusSubquery(this.db, { now: this.clock.now() });

SQL에는 DB가 현재 시각을 돌려주는 now() 함수가 있다. 그것을 쓰지 않고 앱이 정한 시각을 파라미터로 넘긴다.

  • 테스트가 시각을 고정할 수 있다. 통합 테스트는 overrideProvider(Clock)으로 원하는 시각을 돌려주는 가짜 Clock을 끼운다. 그래서 "판매 오픈 1ms 전", "회차 시작 정각" 같은 경계를 정확히 만들 수 있다. DB의 now()는 테스트가 바꿀 수 없어 실제 시각에 맞춰 데이터를 매번 만들어야 한다.
  • 시각의 기준이 하나다. 앱 서버와 DB 서버의 시계는 조금씩 다를 수 있다. 앱이 정한 시각 하나를 쓰면 판매 상태 계산과 뒤 단계의 예매 가능 여부 검사가 같은 기준을 본다.
  • 추상 클래스를 주입 토큰으로 쓴다. Clock은 타입이면서 실행 중에도 남는 값이라, DATABASE처럼 따로 @Inject(...)를 붙이지 않아도 생성자 타입만으로 주입된다(nest 02 문서).

now는 Date 그대로 sql 템플릿에 들어가 $1 같은 파라미터가 된다(다음 절). DB는 starts_at(timestamptz)과 비교하는 것을 보고 그 값을 timestamptz로 읽는다.

순번과 이름을 SQL에 넣기

회차 하나의 판매 상태의 CASE는 then 뒤에 순번(숫자)을 돌려준다. 이 숫자를 TS 코드에서 SQL로 넣는 방법이 두 가지 있고, 어느 쪽이냐에 따라 min의 결과가 달라질 수 있다. 같은 CASE를 두 방법으로 써 보고 실제로 만들어지는 SQL을 비교한다.

먼저: Drizzle이 DB에 보내는 것은 두 덩어리다

Drizzle은 쿼리를 문자열 하나로 보내지 않는다. 빈칸이 뚫린 SQL 글자와 빈칸에 채울 값 목록을 따로 보낸다. 빈칸 있는 신청서 양식과, 칸마다 적을 내용을 따로 건네는 것과 같다. 

// db.select().from(shows).where(eq(shows.id, 42)) 가 실제로 DB에 보내는 것
{
  sql: 'select ... from "shows" where "shows"."id" = $1', // 양식: $1이 빈칸
  params: [42],                                            // 빈칸에 채울 값
}
  • $1, $2…가 빈칸이고, 숫자는 params 배열의 몇 번째 값인지를 뜻한다. 이 빈칸을 파라미터라고 부른다.
  • 이렇게 나눠 보내는 이유는 사용자가 입력한 값이 SQL 글자에 섞여 명령처럼 실행되는 일(SQL 인젝션)을 막기 위해서다.

${...} 안에 무엇을 넣느냐에 따라 다르게 들어간다

sql`...` 템플릿은 ${...}마다 안에 든 것이 무엇인지 보고 SQL 글자에 다르게 넣는다.

${...}에 넣은 것 무엇인가 SQL 글자에 들어가는 것
performances.isCancelled, performances.startsAt 컬럼 정보(테이블 이름, 컬럼 이름, 타입). true/false 같은 값이 아니다 컬럼 이름 "is_cancelled", "starts_at" (실제로는 테이블 이름까지 붙은 "performances"."is_cancelled". 이 문서에서는 줄여 쓴다)
now, 2 JS 코드가 이미 가진 값 빈칸 $n. 값은 값 목록으로 따로 간다
sql.raw('2') SQL에 그대로 쓸 글자 2 그대로

컬럼이 빈칸이 되지 않는 이유는 JS가 그 값을 모르기 때문이다. 회차가 취소됐는지는 DB의 각 행에 저장돼 있고 행마다 다르다. 그래서 JS는 값을 보낼 수 없고 "각 행에서 이 컬럼을 읽어라"라고 이름만 적어 보낸다. 반대로 now와 2는 JS가 이미 가진 값이라 빈칸과 값 목록으로 보낸다. when "starts_at" <= $1에서 왼쪽은 DB가 행마다 읽는 컬럼이고, 오른쪽은 JS가 보낸 값이다.

방법 1. 숫자를 그냥 넣기: 빈칸이 된다

// 쓰지 않은 방법
sql`case
  when ${performances.isCancelled} or ${performances.startsAt} <= ${now} then ${2}
  when ${now} < ${performances.salesOpenAt} then ${1}
  else ${0}
end`
-- 빈칸에 값을 채워 쓴 모양. 주석의 $n이 빈칸으로 간 자리다
case
  when "is_cancelled" or "starts_at" <= '2026-11-10 12:00+09' then '2' -- $1, $2
  when '2026-11-10 12:00+09' < "sales_open_at" then '1'                 -- $3, $4
  else '0'                                                                 -- $5
end

${2}, ${1}도 값이라 빈칸이 됐다. SQL 글자에는 숫자가 하나도 없고, then 뒤가 모두 빈칸이다. 빈칸에 들어간 순번을 '2'처럼 따옴표로 적은 이유는 바로 아래에서 본다. DB가 이 값들을 글자로 읽기 때문이다.

빈칸의 타입은 누가 정하나

DB는 빈칸마다 "여기 들어올 값이 숫자인지, 글자인지, 시각인지"를 정해야 계산할 수 있다. 그런데 값 목록에는 타입이 적혀 있지 않다. 드라이버(pg)는 숫자 2도 글자 "2"로 바꿔서 보낸다. 그래서 DB는 값이 아니라 빈칸 주변의 SQL 글자를 보고 타입을 짐작한다.

빈칸 주변 DB가 정한 타입
$1, $3 시각 컬럼 starts_at, sales_open_at과 비교한다 시각(timestamptz). 단서가 있다
$2, $4, $5 then/else 뒤. 옆에 다른 빈칸밖에 없다 단서가 없어 글자(text)로 정한다

그래서 이 CASE는 숫자 2가 아니라 글자 '2'를 돌려준다. 바깥의 min은 글자를 사전 순서로 비교한다. 사전에서 '10'은 첫 글자 '1'이 '9'보다 앞이라 '9'보다 먼저 나온다. 

min('0', '2')   → '0'    -- 지금은 순번이 한 자리라 사전 순서와 숫자 순서가 같아 우연히 맞는다
min('10', '9')  → '10'   -- 순번이 10을 넘으면 틀린다

이 저장소의 로컬 PostgreSQL에 pg 드라이버로 직접 보내 확인했다. 빈칸으로 보낸 10과 9의 min은 글자 "10"이었고, SQL 글자로 쓴 10과 9의 min은 숫자 9였다.

방법 2. sql.raw로 넣기: SQL 글자가 된다

// 실제로 만들어지는 모양 (priorityOf가 sql.raw를 돌려준다)
sql`case
  when ${performances.isCancelled} or ${performances.startsAt} <= ${now} then ${sql.raw('2')}
  when ${now} < ${performances.salesOpenAt} then ${sql.raw('1')}
  else ${sql.raw('0')}
end`
-- 빈칸에 값을 채워 쓴 모양. 주석의 $n이 빈칸으로 간 자리다
case
  when "is_cancelled" or "starts_at" <= '2026-11-10 12:00+09' then 2 -- $1
  when '2026-11-10 12:00+09' < "sales_open_at" then 1               -- $2
  else 0
end

sql.raw는 값을 빈칸으로 만들지 않고 SQL 글자에 그대로 써 넣는다. 이제 SQL 글자에 then 2가 보이므로 DB는 짐작할 필요 없이 숫자(integer)로 정하고, min도 숫자로 비교한다. 실행할 때마다 바뀌는 now만 빈칸으로 남는다.

'2'를 직접 쓰지 않고 함수로 만든 이유

// priorityOf('ended') → sql.raw('2')
function priorityOf(status: ShowSalesStatus): SQL {
  return sql.raw(String(SHOW_SALES_STATUSES.indexOf(status)));
}
// literalOf('on_sale') → sql.raw("'on_sale'")
function literalOf(status: ShowSalesStatus): SQL {
  return sql.raw(`'${status}'`);
}

// 쓰는 곳
when ${performances.isCancelled} or ${performances.startsAt} <= ${now} then ${priorityOf('ended')}
  • 숫자를 배열에서 꺼낸다. priorityOf('ended')는 배열에서 'ended'의 위치(2)를 찾아 sql.raw('2')를 만든다. 상태를 배열에 끼워 넣으면 숫자가 저절로 밀리므로 CASE를 고칠 필요가 없다. 코드도 숫자 대신 상태 이름으로 읽힌다.
  • literalOf는 이름을 넣는다. 순번을 이름으로 바꾸는 단계(공연 판매 상태로 모으기)의 when 0 then 'on_sale'에서 'on_sale' 부분을 만든다. 이름은 원래 글자라 text가 되어도 문제가 없지만, 순번과 같은 방식으로 넣어 SQL을 읽을 때 값이 바로 보이게 했다.

sql.raw를 써도 안전한 이유

sql.raw에 들어간 글자는 그대로 SQL이 된다. 사용자 입력을 넣으면 SQL 인젝션이다.

두 함수의 인자 타입은 ShowSalesStatus라서 'on_sale', 'upcoming', 'ended' 세 값 말고는 컴파일이 되지 않는다. 그래서 sql.raw에 들어가는 것은 코드에 적힌 상수뿐이고, 사용자 입력이 닿을 길이 없다.
