05 공연 목록 쿼리 읽기

GET /shows의 서비스 함수 findPage()(apps/api/src/shows/shows.service.ts)를 한 줄씩 따라간다. 같은 예시 데이터로 쿼리의 각 단계가 표를 어떻게 바꾸는지 보고, 왜 그렇게 썼는지 설명한다. 문법은 db-and-drizzle 03 문서, JOIN·집계·서브쿼리 같은 개념은 db-and-drizzle 01 문서에 있다. 테이블 구조는 db-and-drizzle 04 문서를 본다.

한눈에 보기

findPage()는 공연 카드 목록 한 페이지와 전체 개수를 돌려준다. 카드에는 제목, 장르, 공연장 이름, 공연 기간(첫 회차 ~ 마지막 회차), 공연 판매 상태, 판매 예정이면 판매 오픈 일시가 들어간다. 공연 기간과 판매 상태는 테이블에 저장하지 않으므로 회차에서 계산해야 한다. 이 문서는 목록 쿼리의 구조를 따라가고, 판매 상태를 계산하는 서브쿼리 안쪽은 db-and-drizzle 06 문서에서 본다. 

// apps/api/src/shows/shows.service.ts
const PAGE = 1;
const PAGE_SIZE = 20;

async findPage(): Promise<ShowPageDto> {
  // ① 공연마다 첫 회차와 마지막 회차를 구하는 서브쿼리
  const periodSubquery = this.db
    .select({
      showId: performances.showId,
      start: min(performances.startsAt).as('start'),
      end: max(performances.startsAt).as('end'),
    })
    .from(performances)
    .groupBy(performances.showId)
    .as('period');
  // ② 공연마다 공연 판매 상태와 판매 오픈 일시를 구하는 서브쿼리 (06 문서)
  const salesStatusSubquery = buildShowSalesStatusSubquery({
    db: this.db,
    now: this.clock.now(),
  });
  // 판매 종료 공연은 목록에서 뺀다. 목록과 전체 개수가 같은 조건을 써야 페이지 수가 맞는다.
  const listCondition = ne(salesStatusSubquery.salesStatus, 'ended');

  const [rows, [total]] = await Promise.all([
    // ③ 목록 쿼리
    this.db
      .select({
        id: shows.id,
        title: shows.title,
        genre: shows.genre,
        venueName: venues.name,
        start: periodSubquery.start,
        end: periodSubquery.end,
        salesStatus: salesStatusSubquery.salesStatus,
        salesOpenAt: salesStatusSubquery.salesOpenAt,
      })
      .from(shows)
      .innerJoin(venues, eq(venues.id, shows.venueId))
      .innerJoin(periodSubquery, eq(periodSubquery.showId, shows.id))
      .innerJoin(salesStatusSubquery, eq(salesStatusSubquery.showId, shows.id))
      .where(listCondition)
      .orderBy(asc(periodSubquery.start), asc(shows.id))
      .limit(PAGE_SIZE)
      .offset((PAGE - 1) * PAGE_SIZE),
    // ④ 개수 쿼리
    this.db
      .select({ count: count() })
      .from(shows)
      .innerJoin(salesStatusSubquery, eq(salesStatusSubquery.showId, shows.id))
      .where(listCondition),
  ]);
  // ⑤ 응답으로 바꾸기
  ...
}
목록 쿼리가 표를 바꾸는 순서
  1. 회차를 공연당 한 줄로 줄인다 (periodSubquery, salesStatusSubquery)
  2. 공연에 공연장을 붙인다
  3. 공연에 periodSubquery와 salesStatusSubquery를 붙이고, 짝 없는 공연은 버린다
  4. 판매 종료 공연을 뺀다
  5. 첫 회차 순으로 줄 세운다
  6. 20개만 자른다

periodSubquery와 salesStatusSubquery는 따로 실행되지 않는다. ③과 ④ 안에 끼워 들어가므로 DB에 가는 SQL은 두 개다. ③의 SQL은 다음과 같다. 판매 상태 서브쿼리 안쪽은 (...)로 줄였다(전체는 db-and-drizzle 06 문서). 

select "shows"."id", "shows"."title", "shows"."genre", "venues"."name", "start", "end", "sales_status", "sales_open_at"
from "shows"
inner join "venues" on "venues"."id" = "shows"."venue_id"
inner join (
  select "show_id", min("starts_at") as "start", max("starts_at") as "end"
  from "performances" group by "performances"."show_id"
) "period" on "period"."show_id" = "shows"."id"
inner join (...) "show_sales_status" on "show_sales_status"."show_id" = "shows"."id"
where "sales_status" <> $7   -- $7은 'ended'
order by "start" asc, "shows"."id" asc
limit $8                         -- $8은 20

$1~$6은 판매 상태 서브쿼리 안에 들어가는 현재 시각이다. 값은 SQL 글자와 따로 빈칸으로 간다.

공연 기간 서브쿼리

const periodSubquery = this.db
  .select({
    showId: performances.showId,
    start: min(performances.startsAt).as('start'),
    end: max(performances.startsAt).as('end'),
  })
  .from(performances)
  .groupBy(performances.showId)
  .as('period');

groupBy(showId)가 같은 공연의 회차를 한 묶음으로 모으고, 묶음마다 min(가장 이른 값)과 max(가장 늦은 값)를 하나씩 뽑는다(집계 함수와 GROUP BY). 결과는 공연당 한 줄이다.

show_id start end
1 12-01 19:30 12-05 19:30
2 12-03 15:00 12-03 15:00

붉은 숲은 묶을 회차가 없으니 이 표에 줄이 없다. 이 사실이 뒤의 JOIN에서 중요해진다. 

// 자바스크립트로 비유하면
const period = Object.values(Object.groupBy(performances, (p) => p.showId)).map((group) => ({
  showId: group[0].showId,
  start: minOf(group.map((p) => p.startsAt)),
  end: maxOf(group.map((p) => p.startsAt)),
}));

차이는 이 계산이 앱이 아니라 DB 안에서 일어난다는 점이다. 회차를 전부 앱으로 가져오지 않아도 된다.

공연 기간을 shows에 컬럼으로 저장하지 않은 이유는 회차가 바뀔 때마다 같이 고쳐야 하기 때문이다. 회차를 더하거나 지우고 공연의 기간을 고치는 것을 잊으면 두 값이 어긋난다. 회차에서 매번 계산하면 어긋날 일이 없다(스펙 #36 "공연 기간은 저장하지 않는다").

end는 마지막 회차의 시작 일시

end는 max(startsAt)이므로 마지막 회차가 끝나는 시각이 아니라 시작하는 시각이다. 이름만 보면 헷갈리지만 의도한 값이다.

  • 카드에는 날짜만 나간다. 스토어의 select 함수가 2026.12.01 ~ 2026.12.05처럼 날짜만 보여 준다(apps/store/apps-src/_index/index-page.helper.ts). 필요한 것은 마지막 회차가 열리는 날이다.
  • 끝나는 시각은 날짜를 틀리게 만들 수 있다. 23:00에 시작하는 120분짜리 회차는 다음 날 01:00에 끝난다. 끝나는 시각을 쓰면 공연 기간이 하루 길어진다. 예매 사이트의 공연일은 시작한 날이다.
  • 뜻은 계약에 적어 두었다. DTO의 설명이 '마지막 회차의 시작 일시'이고 (apps/api/src/shows/show.dto.ts), 생성 타입의 주석으로 스토어까지 따라간다.

.as()가 두 번 나오는 이유

이 코드에는 .as()가 두 종류 있다. 문법은 db-and-drizzle 03 문서에 있다.

코드 붙는 곳 SQL 필요한 이유
.as('period') 쿼리 전체 ( ... ) "period" 쿼리를 실행하지 않고, 다른 쿼리 안에서 임시 테이블처럼 쓸 이름을 붙인다
.as('start'), .as('end') 계산한 값 min("starts_at") as "start" min(...)은 즉석에서 계산한 값이라 이름이 없다. 바깥 쿼리가 periodSubquery.start로 가리키려면 SQL 안에 이름이 있어야 한다

showId: performances.showId는 원래 이름(show_id)이 있는 컬럼이라 .as()가 필요 없다. 계산한 값에 .as()를 빼먹으면 Drizzle이 실행할 때 "서브쿼리의 SQL 필드에 alias가 없다"는 오류를 던진다.

세 번의 innerJoin과 where

.from(shows)
.innerJoin(venues, eq(venues.id, shows.venueId))
.innerJoin(periodSubquery, eq(periodSubquery.showId, shows.id))
.innerJoin(salesStatusSubquery, eq(salesStatusSubquery.showId, shows.id))
.where(listCondition)

JOIN은 공연 표의 줄마다 조건에 맞는 짝을 찾아 옆으로 이어 붙인다. 짝이 없을 때 어떻게 하느냐가 JOIN 종류의 차이다.

공연장 붙이기

shows.venue_id와 같은 id의 공연장을 붙여 venues.name을 꺼낸다. 공연은 venue_id가 NOT NULL이고 외래 키가 걸려 있어(db-and-drizzle 04 문서) 반드시 공연장이 있다. 그래서 이 JOIN으로 빠지는 공연은 없다.

periodSubquery 붙이기

공연 period에서 짝 찾기 결과
1 달빛 정원 show_id 1 있음 남는다
2 겨울 기차 show_id 2 있음 남는다
3 붉은 숲 show_id 3 없음 버려진다

salesStatusSubquery 붙이고 판매 종료 빼기

salesStatusSubquery도 회차를 공연별로 묶은 서브쿼리라 periodSubquery처럼 공연당 한 줄이고, 회차가 없는 붉은 숲은 줄이 없다. 그래서 이 JOIN으로 더 빠지는 공연은 없고, 남은 두 공연에 sales_status와 sales_open_at이 붙는다. 그다음 where(listCondition)가 sales_status가 'ended'인 줄을 뺀다. 예시의 두 공연은 판매 중이라 둘 다 남는다.

세 번의 JOIN을 마친 표는 아래처럼 넓다. 붙인 테이블과 서브쿼리의 컬럼이 모두 옆으로 이어지고, shows.id, venues.id, period.show_id처럼 같은 값이 여러 번 나온다. 실제로는 shows의 다른 컬럼(genre, description 등)도 모두 있지만 예시 데이터에 없는 컬럼은 뺐다.

shows.idshows.titleshows.venue_idvenues.idvenues.nameperiod.show_idperiodSubquery.startperiodSubquery.endshow_sales_status.show_idsales_statussales_open_at
1달빛 정원11낙산 소극장112-01 19:3012-05 19:301on_salenull
2겨울 기차22한강 아트홀212-03 15:0012-03 15:002on_salenull

where가 이 표에서 줄을 거르고, orderBy, limit, offset이 줄 순서를 정하고 자른다. 여기까지는 컬럼이 그대로다. 마지막으로 select가 필요한 컬럼만 골라 이름을 붙인 결과는 다음과 같다.

id title venueName start end salesStatus salesOpenAt
1 달빛 정원 낙산 소극장 12-01 19:30 12-05 19:30 on_sale null
2 겨울 기차 한강 아트홀 12-03 15:00 12-03 15:00 on_sale null

INNER JOIN을 고른 이유: 회차가 없는 공연은 공연 기간 칸에 쓸 날짜가 없다. 언제 하는지 모르는 공연은 목록에 띄우지 않기로 했으므로(findPage() 첫 줄 주석), 짝이 없으면 자동으로 버리는 INNER JOIN이 맞다.

periodSubquery만 LEFT JOIN으로 바꿔도 결과는 같다. salesStatusSubquery에도 붉은 숲의 줄이 없어서 그 INNER JOIN에서 빠지기 때문이다. 두 서브쿼리를 모두 LEFT JOIN으로 바꿔야 붉은 숲이 남고, 그때는 start, end, sales_status가 null이 된다. null <> 'ended'는 참이 아니므로(NULL) 이번에는 where가 붉은 숲을 뺀다.

min, max의 결과 타입은 Date | null이다(db-and-drizzle 03 문서). INNER JOIN 덕분에 실제로는 null이 오지 않지만 타입은 그걸 모른다. 그래서 응답으로 바꿀 때 toIso()가 null이면 오류를 던져 타입을 좁힌다.

회차를 바로 JOIN하지 않는 이유

periodSubquery를 만들지 않고 회차 표를 바로 JOIN하면 공연마다 짝이 되는 회차를 전부 붙인다. 달빛 정원은 짝이 둘이라 두 줄이 된다(일대다 JOIN은 행을 늘린다). 

// 이렇게 쓰면
this.db.select().from(shows).innerJoin(performances, eq(performances.showId, shows.id));
shows.id title performances.id starts_at
1 달빛 정원 10 12-01 19:30
1 달빛 정원 11 12-05 19:30
2 겨울 기차 12 12-03 15:00

공연은 2개인데 줄은 3개다. 실제로는 공연마다 회차가 수십 개라 훨씬 많이 불어난다. 그러면 두 가지가 깨진다.

  • 페이지가 틀어진다. limit(20)은 공연 20개가 아니라 줄 20개를 자른다. 공연마다 회차가 10개면 한 페이지에 공연이 2개만 나온다.
  • 개수가 틀어진다. 여기서 세면 공연 수가 아니라 회차 수가 나온다.

그래서 회차를 먼저 공연당 한 줄로 줄인 periodSubquery를 만들고, 그것을 붙였다. 공연 하나에 짝이 하나뿐이라 줄이 불어나지 않는다.

줄 수의 변화
  1. 회차 3줄
  2. 공연별로 묶어 periodSubquery 2줄
  3. 공연 3줄에 붙이면 결과 2줄 (붉은 숲은 빠짐)

정렬 기준을 두 개 둔 이유

.orderBy(asc(periodSubquery.start), asc(shows.id))

첫 회차가 이른 공연이 먼저 나온다. 문제는 첫 회차 일시가 같은 공연들이다. 이들끼리의 순서는 정해지지 않아서, DB는 요청마다 다른 순서로 돌려줄 수 있다.

순위 첫 회차 1페이지 요청 때 2페이지 요청 때
20번째 12-10 19:30 공연 A 공연 B
21번째 12-10 19:30 공연 B 공연 A

1페이지 끝에서 A를 봤는데 2페이지 첫 줄에 또 A가 나오고, B는 어디에도 나오지 않는다. 그래서 마지막 기준으로 절대 겹치지 않는 shows.id를 붙여 순서를 완전히 고정했다(orderBy).

limit과 offset으로 페이지 자르기

.limit(PAGE_SIZE)                 // 20개만
.offset((PAGE - 1) * PAGE_SIZE)   // 앞에서 이만큼 건너뛰고

limit은 최대 몇 줄을 가져올지, offset은 앞에서 몇 줄을 건너뛸지 정한다(LIMIT, OFFSET). 배열로 치면 sorted.slice(offset, offset + limit)이다.

페이지 offset limit 가져오는 줄
1 0 20 1~20번째
2 20 20 21~40번째
3 40 20 41~60번째
  • 지금은 항상 1페이지다. 첫 페이지 20개만 보여 주므로 PAGE = 1로 고정했다. 주소의 ?page=를 받는 일은 뒤 티켓에서 한다. 그때 PAGE만 요청 값으로 바꾸면 되도록 식으로 적어 두었다.
  • offset(0)은 SQL에 나오지 않는다. 0줄을 건너뛰는 것은 건너뛰지 않는 것과 같아서 Drizzle이 뺀다. 위 SQL에 offset이 없는 이유다.
  • 정렬이 먼저다. "21번째부터"는 순서가 고정돼 있어야 의미가 있다. 앞 절의 정렬 기준이 페이지 자르기의 전제다.

offset(10000)이면 DB는 1만 줄을 실제로 만들고 정렬한 뒤 버리고 나서 20줄을 준다. 뒤 페이지일수록 느려진다. "마지막으로 본 항목 다음부터" 가져오는 커서 방식이 대안이지만, 스펙이 번호 페이지를 원해서 오프셋 방식을 골랐다. 성능은 9단계에서 공연 1만 개로 측정한다.

개수 쿼리는 판매 상태만 JOIN한다

this.db
  .select({ count: count() })
  .from(shows)
  .innerJoin(salesStatusSubquery, eq(salesStatusSubquery.showId, shows.id))
  .where(listCondition)

totalCount는 화면 아래의 "전체 몇 개, 몇 페이지"를 계산하는 데 쓴다. 이 숫자는 목록에 실제로 나올 공연 수와 같아야 한다. 그래서 목록 쿼리에서 공연을 빼는 조건을 모두 같이 건다.

목록 쿼리의 단계 공연을 빼는가 개수 쿼리
innerJoin(venues) 빼지 않는다. 모든 공연에 공연장이 있다 뺐다
innerJoin(periodSubquery) 회차 없는 공연을 뺀다 뺐다. salesStatusSubquery가 같은 공연을 뺀다
innerJoin(salesStatusSubquery) 회차 없는 공연을 뺀다 넣었다
where(listCondition) 판매 종료 공연을 뺀다 넣었다
orderBy, limit, offset 순서와 페이지만 정한다 뺐다. 전체를 센다

where(listCondition)는 salesStatusSubquery의 컬럼을 보므로, 개수 쿼리도 salesStatusSubquery를 JOIN해야 한다. 이 JOIN이 회차 없는 공연도 함께 빼니 periodSubquery는 붙이지 않아도 개수가 같다. 예시에서는 달빛 정원, 겨울 기차 두 개를 세어 totalCount가 2다.

개수가 틀리면 페이지 수가 틀린다. 공연이 21개이고 그중 하나가 판매 종료라면 목록에 나올 공연은 20개라 한 페이지로 끝난다. 그런데 개수 쿼리에서 where(listCondition)를 빼고 21로 세면 totalPages가 2가 되고, 2페이지를 눌러 보면 빈 화면이 나온다. 그래서 조건을 listCondition 한 변수에 담아 두 쿼리가 함께 쓴다. 뒤 티켓에서 장르 필터나 제목 검색이 들어올 때도 같은 조건을 양쪽에 넣어야 한다.

응답으로 바꾸기

const [rows, [total]] = await Promise.all([목록쿼리, 개수쿼리]);

const totalCount = total?.count ?? 0;
return {
  items: rows.map(({ start, end, salesOpenAt, ...show }) => ({
    ...show,
    period: { start: toIso(start), end: toIso(end) },
    salesOpenAt: salesOpenAt?.toISOString() ?? null,
  })),
  page: PAGE,
  size: PAGE_SIZE,
  totalCount,
  totalPages: Math.ceil(totalCount / PAGE_SIZE),
};
  • Promise.all: 두 쿼리는 서로의 결과가 필요 없어서 동시에 보낸다(db-and-drizzle 03 문서). 두 개를 한꺼번에 fetch하는 것과 같다.
  • [total]: select의 결과는 항상 배열이라 개수도 [{ count: 2 }]로 온다. 첫 원소를 꺼낸다.
  • periodSubquery 객체로 묶기: DB 결과는 start, end가 펼쳐진 한 줄이다. 응답 모양(ShowSummaryDto)에 맞게 period: { start, end }로 묶고, Date를 ISO 문자열로 바꾼다.
  • salesOpenAt: 판매 예정이 아니면 null이라 ?.로 그대로 null을 넘기고, 값이 있으면 ISO 문자열로 바꾼다.
  • totalPages: 21개면 Math.ceil(21 / 20) = 2, 0개면 0이다.

스스로 확인하기

질문에 먼저 답해 본 뒤, 눌러서 답을 확인한다.

1. 회차가 없는 공연이 목록에서 빠지는 것은 코드의 어느 부분 때문인가?

.innerJoin(periodSubquery, ...)와 .innerJoin(salesStatusSubquery, ...) 둘 다다. 두 서브쿼리 모두 회차를 공연별로 묶어 만들어서 회차 없는 공연은 줄이 없고, INNER JOIN은 짝 없는 줄을 버린다. where(listCondition)는 판매 종료 공연을 빼는 조건이라 이 일과 상관없다.

2. 목록 쿼리의 .innerJoin(periodSubquery, ...)만 .leftJoin(periodSubquery, ...)로 바꾸면 무엇이 달라지는가?

결과는 같다. 회차 없는 공연은 salesStatusSubquery에도 줄이 없어서 .innerJoin(salesStatusSubquery, ...)에서 빠진다. 남는 공연은 모두 periodSubquery에 짝이 있으니 start, end도 null이 되지 않는다.

3. periodSubquery 없이 performances를 바로 JOIN하고 limit(20)을 걸면?

공연이 회차 수만큼 여러 줄로 불어나서, 20줄이 공연 20개가 아니게 된다. 같은 공연이 여러 번 나오고 한 페이지의 공연 수가 줄어든다.

4. min(performances.startsAt)에서 .as('start')를 지우면?

바깥 쿼리에서 periodSubquery.start를 가리킬 SQL 이름이 없어, Drizzle이 실행할 때 alias가 없다는 오류를 던진다.

5. orderBy에서 asc(shows.id)를 지우면 어떤 버그가 생길 수 있는가?

첫 회차 일시가 같은 공연들의 순서가 요청마다 달라질 수 있다. 페이지 경계에 걸치면 같은 공연이 두 페이지에 나오거나 어느 페이지에도 나오지 않는다.

6. 개수 쿼리에서 .where(listCondition)를 지우면?

판매 종료 공연까지 세어 totalCount가 실제 목록보다 커진다. totalPages가 늘어 빈 페이지가 생길 수 있다. 회차 없는 공연은 여전히 innerJoin(salesStatusSubquery, ...)에서 빠진다.

7. 23:00에 시작하는 120분 공연이 마지막 회차일 때, 공연 기간의 끝 날짜는?

시작한 날이다. end는 마지막 회차의 시작 일시(max(startsAt))라 끝나는 다음 날 01:00이 아니라 시작한 날의 날짜가 표시된다.
