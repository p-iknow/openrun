01 프론트엔드 개발자를 위한 DB 개념

다른 학습 문서가 안다고 보고 쓰는 DB와 SQL 개념을 자바스크립트에 빗대어 모았다. 처음부터 읽지 않고, 다른 문서에서 링크로 넘어와 필요한 절만 읽는 참고 문서다. 비유는 이해를 돕기 위한 것이라 실제 DB 동작과 완전히 같지는 않다. 새 개념이 필요해지면 이 문서에 절을 더한다.

DB는 따로 도는 프로그램이다

PostgreSQL은 API 서버(Node)와 별개로 실행되는 프로그램이다. 이 저장소에서는 Docker 컨테이너 (pnpm infra:up)로 띄운다. API 서버는 네트워크로 PostgreSQL에 접속해 SQL이라는 문장을 보내고 결과를 받는다. 브라우저가 API 서버에 fetch를 보내는 관계와 비슷하다.

요청이 오가는 길
  1. 브라우저(스토어)
  2. HTTP로 API 서버(NestJS)
  3. SQL로 PostgreSQL

Drizzle은 TypeScript 코드를 SQL 문장으로 바꿔 보내 주는 도구다. 그래서 "DB 서버의 시각"과 "Node 서버의 시각"이 따로 있다. 두 프로그램이 서로 다른 컴퓨터에서 돌 수도 있기 때문이다. psql은 SQL을 직접 쳐서 PostgreSQL에 보내는 터미널 도구다.

테이블, 행, 컬럼

테이블은 모양이 같은 객체를 모은 배열이라고 생각하면 된다. 행(row)은 배열의 객체 하나, 컬럼(column)은 객체의 속성 하나다. 컬럼마다 타입이 정해져 있어서, 모든 행이 같은 속성과 타입을 갖는다. 

// shows 테이블을 자바스크립트로 그리면
const shows: { id: number; venue_id: number; title: string }[] = [
  { id: 1, venue_id: 1, title: '잃어버린 여름밤' }, // 행 하나
  { id: 2, venue_id: 1, title: '잃어버린 골목' },
];
// id, venue_id, title이 컬럼이다.

스키마 파일의 pgTable은 이 배열의 "타입 정의"에 해당한다. 다만 TypeScript 타입과 달리 DB가 실제로 지킨다. 타입이 맞지 않는 값을 넣으면 DB가 거부한다.

NULL과 NOT NULL

DB에서 "값이 없음"은 NULL이다. 자바스크립트의 null과 같다. 컬럼에 NOT NULL을 붙이면 그 컬럼은 비울 수 없다. TypeScript로 치면 title?: string이 아니라 title: string인 필수 속성이다.

기본 키

기본 키(primary key)는 행 하나를 가리키는 고유한 값이다. 이 저장소에서는 모든 테이블의 id가 기본 키다. 겹치거나 비어 있을 수 없다. 리스트를 렌더링할 때 React의 key로 쓰는 id와 같은 역할이다. 그 id가 정말 겹치지 않게 DB가 보장한다는 점이 다르다.

id 값은 DB가 1, 2, 3… 순서대로 매긴다. 번호를 기억하는 내부 장치를 시퀀스라고 하고, 은행의 번호표 기계와 비슷하다. 행을 지워도 번호표는 되돌아가지 않는다. RESTART IDENTITY는 번호표 기계를 1로 되돌리는 옵션이다.

외래 키: 다른 테이블의 id를 들고 있기

프론트엔드에서 서버 데이터를 정규화해 상태에 담을 때(예: Redux의 entities), 객체를 중첩하지 않고 id만 들고 있게 한다. 

// 중첩 대신 id로 가리킨다
const venues = { 1: { id: 1, name: '낙산 소극장' } };
const shows = { 1: { id: 1, title: '잃어버린 여름밤', venueId: 1 } };

const venue = venues[shows[1].venueId]; // 필요할 때 id로 찾아 붙인다

DB도 같은 방식이다. 공연 행에 공연장 정보를 통째로 넣지 않고 venue_id만 둔다. 공연장 이름이 바뀌어도 공연장 행 하나만 고치면 된다. 이렇게 다른 테이블의 기본 키를 가리키는 컬럼을 외래 키(foreign key)라고 한다.

자바스크립트에서는 venueId: 999처럼 없는 id를 넣어도 아무도 막지 않는다. 외래 키를 선언하면 DB가 "그 id를 가진 공연장이 실제로 있는가"를 검사해 막아 준다.

일대다 관계

공연장 하나에 공연이 여러 개 달리고, 공연 하나에 회차가 여러 개 달린다. 이런 관계를 일대다라고 한다. 외래 키는 항상 "다" 쪽(공연, 회차)에 둔다. 

// 이렇게 하지 않는다: 공연장 행에 공연 id 목록을 넣기
{ id: 1, name: '낙산 소극장', show_ids: [1, 2, 5] }

// 이렇게 한다: 공연 행마다 자기 공연장 id를 들기
{ id: 1, title: '잃어버린 여름밤', venue_id: 1 }
{ id: 2, title: '잃어버린 골목', venue_id: 1 }

한 칸에 값을 여러 개 넣으면 "공연 5번은 어느 공연장인가"를 찾으려고 모든 공연장의 목록을 뒤져야 하고, 공연을 지울 때마다 목록도 고쳐야 한다. 공연마다 venue_id 하나만 두면 찾기도 고치기도 행 하나로 끝나고, 외래 키로 DB가 검사할 수도 있다. "공연장 1번의 공연 목록"은 venue_id = 1인 공연을 찾으면 된다.

제약: DB가 하는 검증

NOT NULL, 기본 키, 외래 키처럼 DB가 값을 검사하는 규칙을 제약(constraint)이라고 한다. 폼 값을 zod 같은 라이브러리로 검증하는 것과 비슷한데, 검증이 DB 안에서 일어난다. 제약을 어기는 SQL은 실패하고 데이터는 바뀌지 않는다. API 코드에 버그가 있어도 깨진 데이터가 저장되지 않는 마지막 방어선이다.

JOIN: id로 두 배열 합치기

목록 화면에는 공연 제목과 공연장 이름이 함께 필요하다. 두 정보가 서로 다른 테이블에 있으므로, 공연의 venue_id로 공연장을 찾아 붙여야 한다. SQL에서 이것을 JOIN이라고 한다. 

// INNER JOIN을 자바스크립트로 쓰면
const rows = shows
  .map((show) => ({ show, venue: venues.find((v) => v.id === show.venue_id) }))
  .filter(({ venue }) => venue !== undefined) // INNER: 짝이 없는 행은 뺀다
  .map(({ show, venue }) => ({ title: show.title, venueName: venue.name }));

INNER JOIN은 짝이 있는 행만 남긴다. 이 저장소의 공연 목록은 회차와도 INNER JOIN을 하므로, 회차가 하나도 없는 공연은 목록에 나오지 않는다.

비슷하게 GROUP BY는 배열을 키별로 묶는 것(Object.groupBy)이고, min(), max()는 묶인 값에서 가장 작은 값과 큰 값을 고르는 것이다. 공연 기간(첫 회차와 마지막 회차)이 이 방식으로 계산된다.

인덱스: 찾아보기 목차

JOIN의 find처럼 조건에 맞는 행을 찾을 때, 아무 준비가 없으면 DB는 테이블을 처음부터 끝까지 읽는다. 배열에서 find를 하는 것과 같아서, 행이 많아지면 느려진다.

인덱스는 특정 컬럼 값으로 행을 빨리 찾게 미리 만들어 두는 자료 구조다. 책 뒤의 "찾아보기"나, 배열 대신 미리 만들어 둔 Map과 비슷하다. 

// 인덱스 없음: 매번 전부 훑는다
performances.filter((p) => p.show_id === 3);

// 인덱스 있음: 미리 만든 찾아보기로 바로 간다
const byShowId = Map.groupBy(performances, (p) => p.show_id); // 인덱스를 만드는 일
byShowId.get(3);

대가도 있다. 행을 넣거나 고칠 때마다 DB가 인덱스도 함께 고쳐야 하므로 쓰기가 조금 느려지고 저장 공간도 더 든다. 그래서 자주 찾는 컬럼에만 만든다. PostgreSQL의 기본 인덱스는 B-tree다. 값을 정렬해 나무 모양으로 저장해서, 정렬된 배열에서 이진 탐색을 하듯 빨리 찾는다.

DB는 쿼리를 받으면 인덱스를 쓸지, 테이블 전체를 읽을지를 스스로 정한다. 이 결정을 실행 계획이라고 하며, SQL 앞에 EXPLAIN을 붙이면 볼 수 있다.

SQL 문장의 두 종류

이 문서에 나오는 SQL은 두 종류다.

종류 문장 프론트엔드 비유
모양 바꾸기 CREATE TABLE(테이블 만들기), ALTER TABLE(컬럼이나 제약 더하기), CREATE INDEX, CREATE TYPE TypeScript 타입 정의를 고치는 것
데이터 다루기 SELECT(읽기), INSERT(넣기), UPDATE(고치기), DELETE(지우기), TRUNCATE(테이블 전체를 한 번에 비우기) 배열에 filter, push, 수정, 삭제를 하는 것

모양을 바꾸는 SQL을 파일로 쌓아 둔 것이 마이그레이션이다. DB 모양의 변경 이력이라, git 커밋을 순서대로 적용하듯 0000, 0001 순으로 DB에 적용한다. 자세한 흐름은 db-and-drizzle 00 문서에 있다.

선택 읽기: SQL을 읽을 때 알아 둘 표기
  • 큰따옴표 "shows"는 테이블이나 컬럼의 이름이다. 작은따옴표 'musical'는 문자열 값이다. 자바스크립트와 달리 둘을 바꿔 쓸 수 없다.
  • "public"."venues": public은 PostgreSQL의 기본 이름공간 (스키마)이다. 폴더 안의 파일처럼 public 안에 venues 테이블이 있다는 뜻이다. 따로 정하지 않으면 모든 테이블이 public에 들어간다.
  • --로 시작하는 줄은 주석이다. 자바스크립트의 //와 같다.
  • 문장은 ;로 끝난다.

timestamptz: 절대 시점으로 저장하는 일시

PostgreSQL에는 일시 타입이 두 가지 있다. 자바스크립트의 Date와 문자열에 빗대면 차이가 쉽다.

자바스크립트의 Date는 안에 "1970년 1월 1일 UTC부터 몇 밀리초 지났는가"라는 숫자 하나만 들고 있다. 시간대는 저장하지 않고, toLocaleString('ko-KR', { timeZone: 'Asia/Seoul' })처럼 보여 줄 때 정한다. 같은 Date를 서울에서 보면 19:30, 런던에서 보면 10:30이지만 가리키는 순간은 하나다. 이런 값을 절대 시점이라고 한다.

타입 자바스크립트 비유 '2026-03-01 19:30+09'(서울 19:30)를 넣으면
timestamptz(timestamp with time zone) Date 객체(절대 시점) 2026-03-01 10:30 UTC라는 한 순간으로 저장한다
timestamp(timestamp without time zone) '2026-03-01T19:30'처럼 오프셋 없는 문자열 +09를 버리고 2026-03-01 19:30이라는 숫자만 저장한다

이름에 "time zone"이 들어가지만 timestamptz도 시간대를 저장하지 않는다. 넣을 때 받은 시간대로 UTC 순간을 계산해 저장하고, 꺼낼 때는 DB 접속(세션)에 설정된 시간대로 바꿔 보여 준다.

오프셋 없는 값은 읽는 쪽의 시간대에 따라 뜻이 달라진다. 자바스크립트에서도 new Date('2026-03-01T19:30')은 브라우저가 서울에 있으면 서울 19:30, 런던에 있으면 런던 19:30으로 읽힌다. 시간대 없는 timestamp도 그 숫자가 서울 시각인지 UTC인지 모른다. 그래서 "지금보다 지났는가" 같은 비교를 해야 하는 일시는 timestamptz로 저장한다.
