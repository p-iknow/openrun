01 프론트엔드 개발자를 위한 DB 개념

다른 학습 문서가 안다고 보고 쓰는 DB와 SQL 개념을 자바스크립트에 빗대어 모았다. 처음부터 읽지 않고, 다른 문서에서 링크로 넘어와 필요한 절만 읽는 참고 문서다. 비유는 이해를 돕기 위한 것이라 실제 DB 동작과 완전히 같지는 않다. 새 개념이 필요해지면 이 문서에 절을 더한다.

DB는 따로 도는 프로그램이다

PostgreSQL은 API 서버(Node)와 별개로 실행되는 프로그램이다. 이 저장소에서는 Docker 컨테이너 (pnpm infra:up)로 띄운다. API 서버는 네트워크로 PostgreSQL에 접속해 SQL이라는 문장을 보내고 결과를 받는다. 브라우저가 API 서버에 fetch를 보내는 관계와 비슷하다.

요청이 오가는 길
  1. 브라우저(스토어)
  2. HTTP로 API 서버(NestJS)
  3. SQL로 PostgreSQL

Drizzle은 TypeScript 코드를 SQL 문장으로 바꿔 보내 주는 도구다. 그래서 "DB 서버의 시각"과 "Node 서버의 시각"이 따로 있다. 두 프로그램이 서로 다른 컴퓨터에서 돌 수도 있기 때문이다. psql은 SQL을 직접 쳐서 PostgreSQL에 보내는 터미널 도구다.

테이블, 행, 컬럼

테이블은 모양이 같은 객체를 모은 배열이라고 생각하면 된다. 행(row)은 배열의 객체 하나, 컬럼(column)은 객체의 속성 하나다. 컬럼마다 타입이 정해져 있어서, 모든 행이 같은 속성과 타입을 갖는다. 

// shows 테이블을 자바스크립트로 그리면
const shows: { id: number; venue_id: number; title: string }[] = [
  { id: 1, venue_id: 1, title: '잃어버린 여름밤' }, // 행 하나
  { id: 2, venue_id: 1, title: '잃어버린 골목' },
];
// id, venue_id, title이 컬럼이다.

스키마 파일의 pgTable은 이 배열의 "타입 정의"에 해당한다. 다만 TypeScript 타입과 달리 DB가 실제로 지킨다. 타입이 맞지 않는 값을 넣으면 DB가 거부한다.

NULL과 NOT NULL

DB에서 "값이 없음"은 NULL이다. 자바스크립트의 null과 같다. 컬럼에 NOT NULL을 붙이면 그 컬럼은 비울 수 없다. TypeScript로 치면 title?: string이 아니라 title: string인 필수 속성이다.

기본 키

기본 키(primary key)는 행 하나를 가리키는 고유한 값이다. 이 저장소에서는 모든 테이블의 id가 기본 키다. 겹치거나 비어 있을 수 없다. 리스트를 렌더링할 때 React의 key로 쓰는 id와 같은 역할이다. 그 id가 정말 겹치지 않게 DB가 보장한다는 점이 다르다.

id 값은 DB가 1, 2, 3… 순서대로 매긴다. 번호를 기억하는 내부 장치를 시퀀스라고 하고, 은행의 번호표 기계와 비슷하다. 행을 지워도 번호표는 되돌아가지 않는다. RESTART IDENTITY는 번호표 기계를 1로 되돌리는 옵션이다.

외래 키: 다른 테이블의 id를 들고 있기

프론트엔드에서 서버 데이터를 정규화해 상태에 담을 때(예: Redux의 entities), 객체를 중첩하지 않고 id만 들고 있게 한다. 

// 중첩 대신 id로 가리킨다
const venues = { 1: { id: 1, name: '낙산 소극장' } };
const shows = { 1: { id: 1, title: '잃어버린 여름밤', venueId: 1 } };

const venue = venues[shows[1].venueId]; // 필요할 때 id로 찾아 붙인다

DB도 같은 방식이다. 공연 행에 공연장 정보를 통째로 넣지 않고 venue_id만 둔다. 공연장 이름이 바뀌어도 공연장 행 하나만 고치면 된다. 이렇게 다른 테이블의 기본 키를 가리키는 컬럼을 외래 키(foreign key)라고 한다.

자바스크립트에서는 venueId: 999처럼 없는 id를 넣어도 아무도 막지 않는다. 외래 키를 선언하면 DB가 "그 id를 가진 공연장이 실제로 있는가"를 검사해 막아 준다.

일대다 관계

공연장 하나에 공연이 여러 개 달리고, 공연 하나에 회차가 여러 개 달린다. 이런 관계를 일대다라고 한다. 외래 키는 항상 "다" 쪽(공연, 회차)에 둔다. 

// 이렇게 하지 않는다: 공연장 행에 공연 id 목록을 넣기
{ id: 1, name: '낙산 소극장', show_ids: [1, 2, 5] }

// 이렇게 한다: 공연 행마다 자기 공연장 id를 들기
{ id: 1, title: '잃어버린 여름밤', venue_id: 1 }
{ id: 2, title: '잃어버린 골목', venue_id: 1 }

한 칸에 값을 여러 개 넣으면 "공연 5번은 어느 공연장인가"를 찾으려고 모든 공연장의 목록을 뒤져야 하고, 공연을 지울 때마다 목록도 고쳐야 한다. 공연마다 venue_id 하나만 두면 찾기도 고치기도 행 하나로 끝나고, 외래 키로 DB가 검사할 수도 있다. "공연장 1번의 공연 목록"은 venue_id = 1인 공연을 찾으면 된다.

제약: DB가 하는 검증

NOT NULL, 기본 키, 외래 키처럼 DB가 값을 검사하는 규칙을 제약(constraint)이라고 한다. 폼 값을 zod 같은 라이브러리로 검증하는 것과 비슷한데, 검증이 DB 안에서 일어난다. 제약을 어기는 SQL은 실패하고 데이터는 바뀌지 않는다. API 코드에 버그가 있어도 깨진 데이터가 저장되지 않는 마지막 방어선이다.

JOIN: 두 테이블을 이어 붙이기

목록 화면에는 공연 제목과 공연장 이름이 함께 필요하다. 두 정보가 서로 다른 테이블에 있으므로, 공연의 venue_id로 공연장을 찾아 붙여야 한다. 이렇게 두 테이블의 행을 조건에 맞춰 이어 붙이는 것을 JOIN이라고 한다. 결과는 두 테이블의 컬럼을 옆으로 이어 붙인 새 표다. 

select shows.title, venues.name
from shows                                   -- 왼쪽 테이블
inner join venues                            -- 오른쪽 테이블
  on venues.id = shows.venue_id;             -- 짝을 찾는 조건

from에 쓴 테이블을 왼쪽, join 뒤에 쓴 테이블을 오른쪽이라고 부른다. on 뒤가 "어느 행끼리 짝인가"를 정하는 조건이다. JOIN 종류는 짝이 없는 행을 어떻게 하는가로 나뉜다.

INNER JOIN: 짝이 있는 행만

select shows.title, performances.starts_at
from shows inner join performances on performances.show_id = shows.id;
titlestarts_at
달빛 정원3월 1일
달빛 정원3월 2일
겨울 기차3월 5일

양쪽 모두에 짝이 있는 행만 남는다. 회차가 없는 "붉은 숲"은 결과에 없다. 그냥 join이라고만 쓰면 inner join이다. 

// 자바스크립트로 쓰면
shows.flatMap((show) =>
  performances
    .filter((p) => p.show_id === show.id) // 짝을 모두 찾는다
    .map((p) => ({ title: show.title, starts_at: p.starts_at })), // 짝이 없으면 빈 배열이라 사라진다
);

LEFT JOIN: 왼쪽 행은 모두 남기기

select shows.title, performances.starts_at
from shows left join performances on performances.show_id = shows.id;
titlestarts_at
달빛 정원3월 1일
달빛 정원3월 2일
겨울 기차3월 5일
붉은 숲NULL

왼쪽(shows) 행은 짝이 없어도 모두 남는다. 짝이 없는 행은 오른쪽 컬럼이 모두 NULL로 채워진다. LEFT OUTER JOIN이라고도 쓰며 같은 뜻이다. 

shows.flatMap((show) => {
  const matches = performances.filter((p) => p.show_id === show.id);
  return matches.length > 0
    ? matches.map((p) => ({ title: show.title, starts_at: p.starts_at }))
    : [{ title: show.title, starts_at: null }]; // 짝이 없어도 한 줄은 남긴다
});

"회차가 없어도 공연은 보여 줘야 한다"처럼 왼쪽을 빠짐없이 보여 줄 때 쓴다. 결과의 오른쪽 컬럼은 항상 NULL일 수 있다고 보고 다뤄야 한다.

RIGHT JOIN, FULL JOIN

종류남기는 행짝이 없을 때
RIGHT JOIN오른쪽 행 모두왼쪽 컬럼이 NULL
FULL JOIN양쪽 행 모두없는 쪽 컬럼이 NULL

RIGHT JOIN은 LEFT JOIN에서 양쪽을 바꾼 것이다. a right join b는 b left join a와 결과가 같아서, 보통은 읽기 쉬운 LEFT JOIN으로 바꿔 쓴다.

위 예시에 RIGHT JOIN을 해도 결과는 INNER JOIN과 같다. 회차는 외래 키 때문에 반드시 있는 공연을 가리키므로, 오른쪽(회차)에 짝 없는 행이 생길 수 없기 때문이다. 외래 키가 걸린 관계에서는 "짝 없는 행"이 외래 키가 없는 쪽(공연)에만 생긴다.

CROSS JOIN: 모든 조합

조건 없이 왼쪽 행 하나마다 오른쪽 행을 전부 붙인다. 3행과 3행이면 9행이 된다. 이중 for문으로 모든 쌍을 만드는 것과 같다. 예를 들어 "모든 회차 × 모든 좌석"으로 회차 좌석을 만들 때 쓸 수 있다.

일대다 JOIN은 행을 늘린다

INNER JOIN 결과에서 "달빛 정원"은 두 번 나왔다. 회차가 두 개라서다. 일대다 관계를 JOIN하면 "일" 쪽 행이 "다" 쪽 짝 수만큼 복사된다. 자바스크립트 비유가 find가 아니라 flatMap인 이유다.

그래서 공연 목록에 회차를 그대로 JOIN하면 공연이 회차 수만큼 겹쳐 나오고, 행 수를 세면 공연 수가 아니라 회차 수가 나온다. 이 저장소의 공연 목록은 회차를 먼저 공연별로 묶어 공연당 한 행으로 줄인 뒤(GROUP BY, 서브쿼리) JOIN한다. 그러면 공연 하나에 짝이 하나뿐이라 행이 늘지 않는다.

반대로 shows와 venues처럼 "다" 쪽(공연)에서 "일" 쪽(공연장)을 붙이면 짝이 많아야 하나라 행이 늘지 않는다.

LEFT JOIN에서 ON과 WHERE의 차이

"취소되지 않은 회차만 붙이되, 그런 회차가 없는 공연도 목록에 남기고 싶다"고 하자. 조건을 어디에 쓰느냐에 따라 결과가 다르다. 

-- ① ON에 쓰기: 짝을 고를 때 조건을 본다. 짝이 없는 공연도 NULL과 함께 남는다
from shows left join performances
  on performances.show_id = shows.id and performances.is_cancelled = false

-- ② WHERE에 쓰기: JOIN이 끝난 결과를 거른다
from shows left join performances on performances.show_id = shows.id
where performances.is_cancelled = false

②에서는 짝이 없는 공연의 is_cancelled가 NULL이다. NULL = false는 참이 아니므로 그 행이 걸러진다. 결국 LEFT JOIN을 쓴 의미가 사라지고 INNER JOIN과 같아진다. LEFT JOIN에서 오른쪽 테이블의 조건은 보통 ON에 쓴다. INNER JOIN에서는 어느 쪽에 써도 결과가 같다.

짝이 없는 행만 찾기

select shows.title
from shows left join performances on performances.show_id = shows.id
where performances.id is null;               -- → 붉은 숲

LEFT JOIN 뒤에 오른쪽의 기본 키가 NULL인 행만 남기면 "짝이 없는 왼쪽 행", 즉 회차가 없는 공연을 찾을 수 있다. NULL은 = null로 비교할 수 없고 is null로 검사한다. 같은 일을 where not exists (select 1 from performances where performances.show_id = shows.id)로도 쓸 수 있다.

Drizzle에서는 innerJoin, leftJoin, rightJoin, fullJoin, crossJoin 메서드로 쓴다(db-and-drizzle 03 문서).

인덱스: 찾아보기 목차

JOIN의 find처럼 조건에 맞는 행을 찾을 때, 아무 준비가 없으면 DB는 테이블을 처음부터 끝까지 읽는다. 배열에서 find를 하는 것과 같아서, 행이 많아지면 느려진다.

인덱스는 특정 컬럼 값으로 행을 빨리 찾게 미리 만들어 두는 자료 구조다. 책 뒤의 "찾아보기"나, 배열 대신 미리 만들어 둔 Map과 비슷하다. 

// 인덱스 없음: 매번 전부 훑는다
performances.filter((p) => p.show_id === 3);

// 인덱스 있음: 미리 만든 찾아보기로 바로 간다
const byShowId = Map.groupBy(performances, (p) => p.show_id); // 인덱스를 만드는 일
byShowId.get(3);

대가도 있다. 행을 넣거나 고칠 때마다 DB가 인덱스도 함께 고쳐야 하므로 쓰기가 조금 느려지고 저장 공간도 더 든다. 그래서 자주 찾는 컬럼에만 만든다. PostgreSQL의 기본 인덱스는 B-tree다. 값을 정렬해 나무 모양으로 저장해서, 정렬된 배열에서 이진 탐색을 하듯 빨리 찾는다.

DB는 쿼리를 받으면 인덱스를 쓸지, 테이블 전체를 읽을지를 스스로 정한다. 이 결정을 실행 계획이라고 하며, SQL 앞에 EXPLAIN을 붙이면 볼 수 있다.

SQL 문장의 두 종류

이 문서에 나오는 SQL은 두 종류다.

종류 문장 프론트엔드 비유
모양 바꾸기 CREATE TABLE(테이블 만들기), ALTER TABLE(컬럼이나 제약 더하기), CREATE INDEX, CREATE TYPE TypeScript 타입 정의를 고치는 것
데이터 다루기 SELECT(읽기), INSERT(넣기), UPDATE(고치기), DELETE(지우기), TRUNCATE(테이블 전체를 한 번에 비우기) 배열에 filter, push, 수정, 삭제를 하는 것

모양을 바꾸는 SQL을 파일로 쌓아 둔 것이 마이그레이션이다. DB 모양의 변경 이력이라, git 커밋을 순서대로 적용하듯 0000, 0001 순으로 DB에 적용한다. 자세한 흐름은 db-and-drizzle 00 문서에 있다.

선택 읽기: SQL을 읽을 때 알아 둘 표기
  • 큰따옴표 "shows"는 테이블이나 컬럼의 이름이다. 작은따옴표 'musical'는 문자열 값이다. 자바스크립트와 달리 둘을 바꿔 쓸 수 없다.
  • "public"."venues": public은 PostgreSQL의 기본 이름공간 (스키마)이다. 폴더 안의 파일처럼 public 안에 venues 테이블이 있다는 뜻이다. 따로 정하지 않으면 모든 테이블이 public에 들어간다.
  • --로 시작하는 줄은 주석이다. 자바스크립트의 //와 같다.
  • 문장은 ;로 끝난다.

timestamptz: 절대 시점으로 저장하는 일시

PostgreSQL에는 일시 타입이 두 가지 있다. 자바스크립트의 Date와 문자열에 빗대면 차이가 쉽다.

자바스크립트의 Date는 안에 "1970년 1월 1일 UTC부터 몇 밀리초 지났는가"라는 숫자 하나만 들고 있다. 시간대는 저장하지 않고, toLocaleString('ko-KR', { timeZone: 'Asia/Seoul' })처럼 보여 줄 때 정한다. 같은 Date를 서울에서 보면 19:30, 런던에서 보면 10:30이지만 가리키는 순간은 하나다. 이런 값을 절대 시점이라고 한다.

타입 자바스크립트 비유 '2026-03-01 19:30+09'(서울 19:30)를 넣으면
timestamptz(timestamp with time zone) Date 객체(절대 시점) 2026-03-01 10:30 UTC라는 한 순간으로 저장한다
timestamp(timestamp without time zone) '2026-03-01T19:30'처럼 오프셋 없는 문자열 +09를 버리고 2026-03-01 19:30이라는 숫자만 저장한다

이름에 "time zone"이 들어가지만 timestamptz도 시간대를 저장하지 않는다. 넣을 때 받은 시간대로 UTC 순간을 계산해 저장하고, 꺼낼 때는 DB 접속(세션)에 설정된 시간대로 바꿔 보여 준다.

오프셋 없는 값은 읽는 쪽의 시간대에 따라 뜻이 달라진다. 자바스크립트에서도 new Date('2026-03-01T19:30')은 브라우저가 서울에 있으면 서울 19:30, 런던에 있으면 런던 19:30으로 읽힌다. 시간대 없는 timestamp도 그 숫자가 서울 시각인지 UTC인지 모른다. 그래서 "지금보다 지났는가" 같은 비교를 해야 하는 일시는 timestamptz로 저장한다.

ORDER BY, LIMIT, OFFSET: 정렬하고 잘라 오기

SQL의 결과 순서는 ORDER BY를 쓰지 않으면 정해져 있지 않다. 같은 쿼리를 두 번 보내도 순서가 다를 수 있다. 화면에 순서대로 보여 주려면 항상 정렬 기준을 적는다. 

// SELECT ... ORDER BY first_starts_at ASC, id ASC LIMIT 20 OFFSET 40
rows
  .toSorted((a, b) => a.firstStartsAt - b.firstStartsAt || a.id - b.id) // ORDER BY
  .slice(40, 40 + 20); // OFFSET 40, LIMIT 20
  • ORDER BY a ASC, b ASC: a로 오름차순 정렬하고, 같으면 b로 정렬한다. DESC는 내림차순이다.
  • LIMIT 20: 최대 20개만 가져온다.
  • OFFSET 40: 앞의 40개를 건너뛴다. 3페이지(20개씩)는 OFFSET 40 LIMIT 20이다.

페이지로 나눌 때는 정렬 기준이 겹치지 않아야 한다. 첫 회차 일시가 같은 공연이 여러 개면 DB가 그 사이의 순서를 매번 다르게 줄 수 있어서, 1페이지 끝의 공연이 2페이지에 또 나오거나 아예 빠질 수 있다. 그래서 마지막 기준으로 겹치지 않는 id를 붙인다.

집계 함수와 GROUP BY

집계 함수는 여러 행을 값 하나로 줄인다. 배열의 reduce와 같다.

SQL 자바스크립트 비유
count(*) rows.length
min(starts_at), max(starts_at) Math.min(...rows.map((r) => r.startsAt))
sum(price) rows.reduce((s, r) => s + r.price, 0)

GROUP BY를 붙이면 행을 키별로 묶은 뒤 묶음마다 집계한다. Object.groupBy 뒤에 묶음마다 reduce를 하는 것과 같다. 

// SELECT show_id, min(starts_at), max(starts_at) FROM performances GROUP BY show_id
Object.entries(Object.groupBy(performances, (p) => p.show_id)).map(([showId, list]) => ({
  showId,
  start: Math.min(...list.map((p) => p.startsAt)),
  end: Math.max(...list.map((p) => p.startsAt)),
}));

GROUP BY가 있으면 SELECT에 무엇을 쓸 수 있나

GROUP BY는 집계 함수 하나가 아니라 SELECT 전체에 적용된다. 결과는 묶음마다 한 줄이 나오고, 한 줄이니 컬럼마다 값도 하나여야 한다. 그런데 묶음 안에는 행이 여러 개 들어 있다.

묶음 (show_id) 들어간 행의 starts_at 결과 한 줄에 무엇을 적나
1 3월 1일, 3월 2일 값이 둘이라 그대로는 하나를 적을 수 없다

그래서 SELECT에는 묶음마다 값이 하나로 정해지는 것만 쓸 수 있다.

  1. 묶는 키(show_id): 묶음 안의 행이 모두 같은 값이라 하나로 정해진다.
  2. 집계 함수로 감싼 것(min(starts_at), count(*)…), 또는 그것으로 만든 식: 여러 값을 값 하나로 줄인다.

묶음 안에서 행마다 값이 다른 컬럼을 그대로 쓰면 어느 행의 값을 줄지 정할 수 없어 PostgreSQL이 거절한다.

SELECT show_id, starts_at FROM performances GROUP BY show_id;
-- ERROR: column "performances.starts_at" must appear in the GROUP BY clause
--        or be used in an aggregate function

집계 함수는 여러 값 중 하나를 고르는 것이 아니라 여러 값을 하나로 줄이는 것이다. min, max는 결과적으로 있는 값 중 하나가 나오지만, count(*)는 2(행 수)처럼 어느 행의 값도 아닌 새 값을 만든다. 자바스크립트로는 Object.groupBy 뒤에 묶음마다 Math.min(...arr), arr.length, arr.reduce(...)처럼 배열을 값 하나로 만드는 연산이다.

min, max는 집계할 행이 하나도 없으면 NULL을 돌려준다. 빈 배열에서 최솟값이 없는 것과 같다. count(*)는 행이 없으면 0이다.

식이 겹쳐 있을 때: 집계 괄호 안은 행마다, 밖은 묶음마다

SELECT에는 집계 함수 안팎으로 식이 겹쳐 있을 수 있다(CASE 안에 집계, 집계 안에 CASE). 이때 각 부분이 언제 계산되는지는 겹친 모양이 아니라 집계 함수 괄호 안에 있느냐, 밖에 있느냐로 정해진다.

위치 계산 단위 쓸 수 있는 것
집계 함수 괄호 안 (FILTER 조건 포함) 묶음 안의 행마다 그 행의 모든 컬럼
집계 함수 괄호 밖 묶음마다 한 번 묶는 키와 집계 결과만 
SELECT show_id,
       case when count(*) >= 2 then '여러 회차' else '한 회차' end,  -- 괄호 밖: 묶음마다
       sum(case when starts_at < '2026-03-02' then 1 else 0 end)    -- 괄호 안: 행마다
FROM performances
GROUP BY show_id;
  • 두 번째 줄의 CASE는 count(*) 밖에 있다. 묶음마다 회차 수를 센 뒤 그 값 하나로 판단한다. 위 예시 데이터에서 공연 1은 회차가 2개라 '여러 회차', 공연 2는 1개라 '한 회차'다.
  • 세 번째 줄의 CASE는 sum( ) 안에 있다. 회차마다 1 또는 0을 만든 뒤 sum이 묶음마다 더한다. 공연 1은 3월 1일(1)과 3월 2일(0)이라 1, 공연 2는 3월 5일(0)이라 0이다.

괄호 밖에서 행마다 다른 컬럼을 집계 없이 쓰면 위의 규칙에 걸려 에러가 난다. 예를 들어 case when count(*) >= 2 then starts_at end는 starts_at이 괄호 밖이라, 묶음 안 어느 행의 값인지 정할 수 없다.

자바스크립트로는 map 콜백 안에서만 row를 쓸 수 있는 것과 같다.

const groups = Object.groupBy(performances, (p) => p.show_id);

for (const [showId, rows] of Object.entries(groups)) {
  // 콜백 안: row를 쓸 수 있다 (행마다)
  const early = rows
    .map((row) => (row.startsAt < '2026-03-02' ? 1 : 0))
    .reduce((a, b) => a + b, 0);

  // 밖: row가 없다. rows.length 같은 묶음 단위 값만 (묶음마다)
  const label = rows.length >= 2 ? '여러 회차' : '한 회차';
}

쓰는 순서와 실행 순서

SQL은 쓰는 순서와 DB가 실행하는 순서가 다르다. SELECT를 맨 앞에 쓰지만 DB는 행을 가져오고 거르고 묶은 뒤에 SELECT를 계산한다.

쓰는 순서 실행 순서 하는 일
1 SELECT 1 FROM / JOIN 테이블에서 행을 가져와 잇는다
2 FROM / JOIN 2 WHERE 행을 거른다
3 WHERE 3 GROUP BY 행을 키별로 묶는다
4 GROUP BY 4 SELECT 남은 행(또는 묶음)마다 결과 컬럼을 계산한다. 집계 함수도 여기서
5 ORDER BY 5 ORDER BY 결과를 정렬한다
6 LIMIT / OFFSET 6 LIMIT / OFFSET 일부만 자른다

그래서 GROUP BY를 맨 아래에 써도 SELECT 안의 min()이 계산될 때는 이미 묶음이 만들어져 있다. 쓰는 순서는 읽기 좋으라고 정한 문법일 뿐이다.

Drizzle 체인도 같다. db.select(...).from(...).groupBy(...)는 메서드를 부를 때마다 실행되지 않는다. 주문서에 칸을 하나씩 채울 뿐이고, 다 채운 뒤 SQL 문장 하나로 만들어 DB에 한꺼번에 보낸다. 메서드 순서는 SQL의 쓰는 순서를 따른 것이고, 실행 순서는 DB가 문장 전체를 받은 뒤 위 표대로 정한다. 자바스크립트로는 설정 객체의 키를 어떤 순서로 적든 받는 함수가 정해진 순서로 처리하는 것과 같다. 

// 키 순서와 상관없이 runQuery는 from → where → groupBy → select 순서로 처리한다
runQuery({ select: ['show_id', 'min(...)'], from: 'performances', groupBy: 'show_id' });

CASE: SQL 안의 if / else if

CASE는 조건에 따라 다른 값을 고르는 식이다. 문장이 아니라 값이 되므로 SELECT의 컬럼 자리, 집계 함수 안, WHERE 안 어디든 넣을 수 있다. 자바스크립트로는 즉시 실행하는 if / else if 함수, 또는 삼항 연산자를 이어 붙인 것과 같다. 아래 예시는 오늘이 2026-11-10이라고 보고 그 날짜를 직접 적었다. 실제 코드에서는 이 자리에 실행할 때의 시각이 들어간다. 

case
  when is_cancelled              then 2
  when starts_at <= '2026-11-10' then 3
  else 0
end
// 행 하나마다 이 함수를 부르는 것과 같다
((row) => {
  if (row.isCancelled) return 2;
  else if (row.startsAt <= '2026-11-10') return 3;
  else return 0;
})(row);
  • 위에서부터 먼저 맞는 것 하나만 고른다. 취소된 회차가 이미 시작했어도 첫 줄에서 2가 정해지고 아래 줄은 보지 않는다. 그래서 when의 순서가 곧 규칙의 우선순위다.
  • else가 없으면 NULL이다. 맞는 when이 없을 때 undefined를 돌려주는 함수와 같다.
  • 모든 결과는 같은 타입이어야 한다. 한 줄은 숫자, 다른 줄은 문자를 돌려줄 수 없다. DB가 결과 자리에 적힌 값들을 보고 CASE 전체의 타입을 정한다.

값 하나를 여러 후보와 비교할 때는 짧은 꼴도 있다. switch와 같다. 

case priority when 0 then 'on_sale' when 1 then 'upcoming' end
-- switch (priority) { case 0: return 'on_sale'; case 1: return 'upcoming'; }

집계의 FILTER: 집계에 넣을 행만 고르기

집계 함수는 묶음 안의 모든 행을 본다. 그중 일부 행만 집계하고 싶으면 집계 함수 뒤에 FILTER (WHERE 조건)을 붙인다. PostgreSQL이 지원하는 표준 SQL 문법이다. 

select show_id,
       min(sales_open_at),                                       -- 모든 회차 중 가장 이른 값
       min(sales_open_at) filter (where not is_cancelled)        -- 취소되지 않은 회차 중 가장 이른 값
from performances
group by show_id
// 묶음(list)마다
Math.min(...list.map((p) => p.salesOpenAt));
Math.min(...list.filter((p) => !p.isCancelled).map((p) => p.salesOpenAt));

WHERE와의 차이가 중요하다. WHERE는 묶기 전에 행을 버리므로 모든 집계에서 그 행이 사라진다. FILTER는 그 집계 하나에서만 행을 뺀다. 그래서 한 쿼리 안에서 "전체 중 최솟값"과 "조건에 맞는 것 중 최솟값"을 함께 구할 수 있다.

고른 행이 하나도 없으면 빈 배열의 최솟값처럼 NULL이 된다.

서브쿼리: 쿼리 결과를 테이블처럼 쓰기

SELECT의 결과도 행과 컬럼이 있는 표다. 그래서 쿼리 결과를 괄호로 감싸 이름을 붙이면 다른 쿼리에서 테이블처럼 JOIN할 수 있다. 이것을 서브쿼리라고 한다. 계산한 중간 결과를 변수에 담아 두고 다음 계산에 쓰는 것과 같다. 

select shows.title, period.start
from shows
inner join (
  select show_id, min(starts_at) as start      -- 공연별 첫 회차를 구한 표
  from performances
  group by show_id
) period on period.show_id = shows.id;          -- 그 표에 period라는 이름을 붙여 JOIN한다

as start는 계산한 값에 붙이는 이름(별칭)이다. min(starts_at) 같은 계산 결과에는 컬럼 이름이 없으므로, 바깥 쿼리에서 period.start로 부르려면 이름을 붙여야 한다.

파라미터: 값은 SQL과 따로 보낸다

Drizzle이 만든 SQL을 보면 값 자리에 $1, $2가 있고, 실제 값은 따로 보낸다. 

{ sql: 'insert into "venues" ("id", "name") values (default, $1)', params: ['낙산 소극장'] }

값을 SQL 문자열에 이어 붙이면, 값에 ' 같은 글자가 들어 있을 때 SQL 문장 자체가 바뀌어 버린다. 사용자가 검색어에 SQL 조각을 넣어 DB를 마음대로 조작하는 공격을 SQL 인젝션이라고 한다. React가 문자열을 innerHTML로 넣지 않고 글자로만 넣어 XSS를 막는 것과 같은 생각이다. 파라미터로 보내면 DB는 그 값을 항상 "값"으로만 다룬다.

트랜잭션: 모두 되거나 모두 안 되거나

여러 SQL을 하나로 묶어, 전부 성공하면 한꺼번에 반영하고 중간에 하나라도 실패하면 전부 없던 일로 되돌리는 것을 트랜잭션이라고 한다. 반영하는 것을 커밋(commit), 되돌리는 것을 롤백(rollback)이라고 한다.

시드가 "세 테이블을 비우고 공연장, 공연, 회차를 넣는" 일을 트랜잭션 하나로 묶은 것이 예다. 공연 10개를 넣다가 오류가 나면 비운 것까지 되돌아가므로, DB는 시드를 돌리기 전 상태 그대로 남는다. 묶지 않았다면 반쯤 지워지고 반쯤 채워진 상태가 남는다. 상태 관리에서 여러 값을 한 번에 바꿔 중간 상태가 화면에 보이지 않게 하는 것과 비슷하다.

트랜잭션이 끝나기 전에는 다른 접속에서 바뀐 내용이 보이지 않는다. 동시에 여러 요청이 같은 데이터를 바꿀 때의 문제(예: 같은 좌석을 두 사람이 사는 일)는 6단계에서 다룬다.
