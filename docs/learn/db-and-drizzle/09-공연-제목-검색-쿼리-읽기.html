09 공연 제목 검색 쿼리 읽기

GET /shows?q=정원이 제목에 "정원"이 들어간 공연만 돌려주는 과정을 따라간다. 중심은 findPage()(apps/api/src/shows/shows.service.ts)의 두 줄과 escapeLikePattern()이다. LIKE와 이스케이프 개념은 db-and-drizzle 01 문서, ilike와 and 문법은 db-and-drizzle 03 문서, 목록 쿼리 전체는 db-and-drizzle 05 문서에 있다.

한눈에 보기

검색어가 SQL이 되기까지
  1. 주소의 q=" 정원 "
  2. zod 스키마가 앞뒤 공백을 지우고 50자 이하인지 검사한다 → '정원'
  3. escapeLikePattern이 %, _, \ 앞에 \를 붙인다
  4. 앞뒤에 %를 붙여 "포함" 패턴을 만든다 → '%정원%'
  5. ilike 조건을 목록 쿼리와 개수 쿼리의 where에 함께 넣는다
// apps/api/src/shows/shows.service.ts
async findPage({ page, size, sort, q }: ShowListQuery): Promise<ShowPageDto> {
  ...
  // 목록과 전체 개수가 같은 조건을 써야 페이지 수가 맞는다. 판매 종료 공연은 목록에서 뺀다.
  const listCondition = and(
    ne(salesStatus.salesStatus, 'ended'),
    q ? ilike(shows.title, `%${escapeLikePattern(q)}%`) : undefined,
  );
  ...
  .where(listCondition) // 목록 쿼리
  ...
  .where(listCondition) // 개수 쿼리
}

// LIKE 패턴에서 특별한 뜻을 가진 %(여러 글자), _(한 글자), \(이스케이프 문자)를 글자 그대로 찾도록 앞에 \를 붙인다.
// PostgreSQL의 LIKE는 ESCAPE를 따로 적지 않으면 \를 이스케이프 문자로 쓴다.
function escapeLikePattern(value: string): string {
  return value.replace(/[\\%_]/g, '\\$&');
}

검색어가 있을 때만 붙는 조건

q ? ilike(...) : undefined는 검색어가 있으면 제목 조건을 만들고, 없으면 undefined를 넘긴다. and()는 undefined를 빼고 잇는다(db-and-drizzle 03 문서).

요청서비스가 받은 qwhere 절 (값을 채워 쓴 모습)
/shows?q=정원'정원'sales_status <> 'ended' and title ilike '%정원%'
/shows없음 (undefined)sales_status <> 'ended'
공백만 보냄 (/shows?q=%20%20)빈 글자 ('')sales_status <> 'ended'

<>는 SQL의 "같지 않다"로, 자바스크립트의 !==다. 첫 줄은 "판매 종료가 아니고 제목에 정원이 들어간 공연"이다. Drizzle의 ne(not equal)가 이 조건을 만든다(db-and-drizzle 03 문서).

읽기 쉽도록 값을 SQL 안에 채워 썼다. 실제로 DB에 가는 SQL에는 값 자리에 $7, $8 같은 번호가 있고, 값 'ended', '%정원%'는 따로 간다(파라미터). 번호가 7부터인 것은 앞의 판매 상태 서브쿼리가 $1~$6(현재 시각)을 먼저 쓰기 때문이다.

조건 검사를 q !== undefined가 아니라 q ?로 쓴 이유는 셋째 줄이다. 공백만 보낸 q는 스키마의 .trim()을 거쳐 빈 글자 ''가 된다. 빈 글자는 거짓으로 읽히므로 검색하지 않는다. 티켓의 "빈 검색어는 검색하지 않는다"가 이것이다.

조건을 변수 하나에 담아 두 쿼리에 넘기므로, 검색하면 목록과 전체 개수(totalCount)가 함께 줄어든다. 한쪽에만 넣으면 "공연 3개"라고 하면서 페이지 수는 검색 전 그대로인 화면이 된다.

이스케이프하지 않으면 생기는 일

Drizzle은 패턴을 손대지 않고 파라미터로 보낸다. 그래서 사용자가 입력한 %, _, \는 패턴의 특별한 글자로 읽힌다(이스케이프). 아래는 이스케이프 없이 `%${q}%`만 썼을 때 실제 PostgreSQL에서 나온 결과다.

찾고 싶은 것그대로 넣은 패턴DB가 읽는 뜻잘못 나오는 제목
100%%100%%100 포함1000 라이브
a_b%a_b%a, 아무 한 글자, b 포함axb 쇼
c\d%c\d%cd 포함cd 쇼만 나오고 c\d 쇼는 빠진다

SQL 인젝션과는 다른 문제다. 검색어는 파라미터로 가므로 SQL 문장은 바뀌지 않는다. 바뀌는 것은 패턴의 뜻이다. 결과가 틀릴 뿐 DB가 위험해지지는 않는다.

escapeLikePattern의 정규식

value.replace(/[\\%_]/g, '\\$&');

"\, %, _를 모두 찾아, 각각 앞에 \를 하나 붙여라"라는 뜻이다. 조각별로 보면 이렇다.

조각뜻
/ ... /정규식 리터럴
[ ... ]문자 클래스. 대괄호 안의 글자 중 하나와 맞는다
\\백슬래시 한 글자. 정규식에서도 \는 특별한 글자라 두 번 쓴다
%, _그 글자 그대로. 정규식에서는 특별한 뜻이 없다
g첫 번째만이 아니라 맞는 곳을 모두 바꾼다
'\\$&'바꿀 글자. '\\'는 백슬래시 한 글자, $&는 "방금 맞은 글자"다

$&는 replace의 두 번째 인자가 글자일 때 쓰는 특별한 표기다. 함수로 쓰면 이렇게 된다. 

value.replace(/[\\%_]/g, (matched) => '\\' + matched);

한 번에 바꾸는 이유

replace를 글자마다 세 번 부르면 순서에 따라 이미 붙인 \를 다시 이스케이프할 수 있다. 정규식 하나로 원래 글자를 한 번만 훑으면, 새로 붙인 \는 다시 보지 않는다. 스스로 확인하기 3번에서 순서를 틀린 경우를 따라간다.

백슬래시는 몇 개인가

이 코드가 헷갈리는 가장 큰 이유는 같은 \가 자리마다 다른 개수로 보이기 때문이다. 문자열이 여러 층을 지나는데, 층마다 \를 특별하게 다룬다.

층보이는 모습실제 글자
TS 소스의 정규식/[\\%_]/문자 클래스 \, %, _
TS 소스의 문자열'\\$&'\$& (세 글자)
테스트 코드의 'c\\d''c\\d'c\d (세 글자)
toSQL()을 JSON으로 찍은 params"%100\\%%"%100\%%. JSON도 \를 두 번 쓴다
DB가 받은 패턴%100\%%LIKE가 \%를 글자 %로 읽는다

코드에서 \\가 보이면 대부분 "실제로는 \ 하나"다. DB까지 가는 값에는 사용자가 입력한 글자 앞에 붙인 \ 하나만 더해진다.

입력에서 패턴까지

사용자 입력escapeLikePattern 뒤DB가 받는 패턴찾는 것
정원정원%정원%정원 포함
100%100\%%100\%%100% 포함
a_ba\_b%a\_b%a_b 포함
c\dc\\d%c\\d%c\d 포함

이 표의 "뒤"와 "패턴" 열은 실제 글자다. 앞 절처럼 코드로 옮기면 \가 두 배로 보인다.

인덱스를 두지 않은 이유

'%정원%'처럼 앞에 %가 붙은 패턴은 B-tree 인덱스를 쓰지 못해, DB가 공연을 모두 읽으며 맞춰 본다(앞에 %가 붙으면). 그래도 지금은 검색용 인덱스를 두지 않는다. 스펙(#36)이 검색 인덱스(pg_trgm 등)를 9단계로 미뤘다. 9단계에서 공연 1만 개 규모의 시드로 실행 계획을 보고, 인덱스를 넣기 전과 후를 측정한 뒤 정한다.

글자맞아야 하는 제목이스케이프가 없으면 함께 나오는 제목
%100% 라이브1000 라이브

DB를 흉내 내지 않고 실제 PostgreSQL로 확인하는 이유는, 패턴을 어떻게 읽는지가 DB의 규칙이기 때문이다. escapeLikePattern만 따로 테스트하면 "\를 붙였다"는 것만 확인할 뿐, DB가 그 \를 이스케이프로 읽는지는 확인하지 못한다.

스스로 확인하기

1. 정규식에서 \\를 빼면 어떤 테스트가 실패하고, 무엇이 나오는가?

테스트가 확인하는 것의 \ 경우를 생각한다.

-  return value.replace(/[\\%_]/g, '\\$&');
+  return value.replace(/[%_]/g, '\\$&');
답 보기

\ 글자를 그대로 찾는다가 실패한다. c\d가 그대로 가서 패턴이 %c\d%가 된다. DB는 \d를 "글자 d"로 읽어 cd 포함을 찾는다. 결과는 ['c\d 쇼']가 아니라 ['cd 쇼']다.

2. 공백만 있는 검색어(q=%20%20)로 요청하면 listCondition은 무엇이 되는가?

검색어가 있을 때만 붙는 조건. 스키마는 z.string().trim().max(50).optional()이다.

답 보기

스키마의 .trim()이 q를 ''로 바꾼다. ''는 거짓이라 undefined가 넘어가고, and()는 판매 종료 조건 하나만 돌려준다. 검색하지 않은 것과 같은 결과다.

3. 정규식 하나 대신 아래처럼 바꾸면 100%를 검색할 때 무엇을 찾게 되는가?

한 번에 바꾸는 이유. %를 먼저, \를 나중에 이스케이프한다.

-  return value.replace(/[\\%_]/g, '\\$&');
+  return value
+    .replace(/%/g, '\\%')
+    .replace(/_/g, '\\_')
+    .replace(/\\/g, '\\\\');
답 보기

100% → 100\% → 마지막 줄이 방금 붙인 \를 다시 이스케이프해 100\\%가 된다. 패턴 %100\\%%를 DB는 "글자 \" 다음에 와일드카드 %로 읽는다. 그래서 100\를 포함하는 제목을 찾는다. 100% 라이브는 나오지 않고, 100\x 쇼 같은 제목이 나온다. \를 맨 먼저 바꾸면 맞지만, 정규식 하나로 한 번에 바꾸면 순서를 신경 쓸 일이 없다.

4. 검색 조건을 목록 쿼리의 where에만 넣으면 화면에서 무엇이 틀리는가?

목록은 맞는 공연만 나오지만 개수 쿼리는 검색 전 전체를 센다. "공연 N개"와 전체 페이지 수가 검색 전 그대로라, 빈 페이지로 가는 페이지 링크가 생긴다.
