데코레이터와 메타데이터: Nest는 어떻게 코드를 읽는가

@Controller와 @Injectable()이 실제로 무엇을 하는지, 데코레이터 없이 쓰는 코드에서 출발해 해부한다. 기준 버전은 NestJS 12.4, TypeScript 6.0이다.

한눈에 보기

데코레이터는 클래스가 정의될 때 한 번 호출되는 평범한 함수이고, 메타데이터는 그 함수가 클래스에 붙여 두는 메모다.

빌드 타임: tsc
  1. @를 함수 호출로 변환
  2. 생성자 타입을 기록하는 코드 추가
  3. 타입 삭제
런타임: Node.js 프로세스 하나
  1. 파일 로드: 메모 쓰기
  2. 앱 조립: 메모 읽고 객체 생성, 주소 연결
  3. 요청 처리: 메서드 실행

Nest 코드의 흐름이 잘 안 보이는 이유도 여기에 있다. 메모를 남기는 곳과 그 메모로 실제 동작을 하는 곳이 떨어져 있다.

데코레이터 없이: 클래스에 메모 붙이기

목표는 "이 컨트롤러의 주소는 shows다"라는 메모를 클래스에 붙이는 것이다. 나중에 Nest가 읽어 가야 하기 때문이다. 이 절의 코드는 원리를 보이기 위해 타입을 생략한 JavaScript로 쓴다.

1단계: 직접 붙이기

JavaScript에서 클래스는 함수이고, 함수는 객체다. 그래서 객체처럼 속성을 붙일 수 있다. 

class ShowsController {}

console.log(typeof ShowsController); // 'function'

ShowsController.path = 'shows';      // 메모 붙이기

이 속성은 new로 만든 객체가 아니라 클래스 자체에 붙는다. 그래서 객체를 만들기 전에도 읽을 수 있다. 

ShowsController.path;       // 'shows'
new ShowsController().path; // undefined

2단계: 함수로 만들기

function setPath(target, path) {
  target.path = path;
}

setPath(ShowsController, 'shows');
setPath(ReviewsController, 'reviews');

3단계: 두 번에 나눠 호출하기

주소를 먼저 받고, 클래스를 나중에 받도록 바꾼다.

function Controller(path) {
  return function (target) { // 함수를 돌려준다
    target.path = path;
  };
}

const attach = Controller('shows'); // 주소만 넣어 함수를 받는다
attach(ShowsController);            // 받은 함수에 클래스를 넣는다

두 줄을 합치면 괄호가 두 쌍이 된다.

Controller('shows')(ShowsController);

결과는 setPath(ShowsController, 'shows')와 같다. 이렇게 나누는 이유는 다음 절의 @ 문법이 클래스 하나만 넣어서 호출하기 때문이다. 'shows'는 그 전에 미리 넣어 둬야 한다.

@ 문법으로 바꾸기

// 데코레이터 없이
class ShowsController {}
Controller('shows')(ShowsController);

// 데코레이터로
@Controller('shows')
class ShowsController {}

두 코드가 하는 일은 같다. @의 규칙은 하나뿐이다.

@ 뒤의 값은 함수여야 하고, 그 함수에 아래 클래스를 넣어 호출한다.

Nest의 데코레이터도 같은 모양이다. 실제 소스는 메타데이터 절에서 본다.

괄호가 있고 없는 차이

@ 뒤에 있는 것이 데코레이터 함수 자체인지, 데코레이터 함수를 만들어 주는 함수인지의 차이다.

쓴 코드 풀어 쓰면 함수 호출 횟수
@Sealed Sealed(Class) 1번
@Controller('shows') Controller('shows')(Class) 2번
@Injectable() Injectable()(Class) 2번 
// 괄호 없이 쓰는 함수: 클래스를 바로 받는다
function Sealed(target: Function) {
  console.log('Sealed got', target.name);
}

// 괄호를 붙여 쓰는 함수: 함수를 돌려주고, 그 함수가 클래스를 받는다
function Factory() {
  console.log('Factory called');
  return (target: Function) => console.log('inner got', target.name);
}

@Sealed
class A {}

@Factory()
class B {}
Sealed got A
Factory called
inner got B

인자가 없어도 괄호를 쓰는 이유는 옵션을 넘길 자리를 두기 위해서다. 예를 들어 @Injectable({ scope: Scope.REQUEST })처럼 쓸 수 있다. Nest의 데코레이터는 대부분 괄호를 붙이는 형태다.

@Injectable처럼 괄호를 빠뜨리면 Injectable(Class)가 되어 클래스가 옵션 자리에 들어간다. tsc가 TS1238 오류로 잡아 준다.

메서드 데코레이터

1단계: 데코레이터 없이 메모 붙이기

클래스에 쓴 메서드는 인스턴스가 아니라 클래스.prototype 객체에 저장된다. 메서드도 함수이므로 메모를 붙일 수 있다. 

class ShowsController {
  findPopular() { return []; }
}

ShowsController.prototype.findPopular.path = 'popular';

2단계: @가 넘겨주는 것

@Get('popular')를 메서드에 붙이면 결국 이런 호출이 일어난다. 실제로 누가 호출하는지는 뒤의 __decorate 절에서 본다. 

Get('popular')(ShowsController.prototype, 'findPopular', descriptor);

괄호 두 쌍은 클래스 때와 같다. 다른 점은 두 번째 괄호의 인자가 3개라는 것이다.

이름 뜻 예제의 값
target 메서드가 들어 있는 객체 ShowsController.prototype
key 메서드 이름 'findPopular'
descriptor 메서드의 정보가 담긴 객체 다음 단계에서 본다

3단계: descriptor의 정체

Nest나 데코레이터 전용 개념이 아니라, JavaScript 객체의 모든 속성이 갖는 설정 정보다. 직접 꺼내 볼 수 있다. 

Object.getOwnPropertyDescriptor(ShowsController.prototype, 'findPopular');
// {
//   value: [Function: findPopular],  ← 메서드 함수 자체
//   writable: true,
//   enumerable: false,
//   configurable: true,
// }

지금 필요한 것은 value뿐이다. 아래 둘은 같은 함수다.

descriptor.value === ShowsController.prototype.findPopular; // true

4단계: 직접 만들어 보기

function Get(path) {
  return (target, key, descriptor) => {
    descriptor.value.path = path; // findPopular 함수에 메모 붙이기
  };
}

1단계의 ShowsController.prototype.findPopular.path = 'popular'와 같은 일이다.

왜 descriptor를 넘겨주는가

메모만 붙일 때는 target[key]로도 같은 함수를 얻을 수 있어 꼭 필요하지 않다. descriptor가 필요한 경우는 메서드를 다른 함수로 바꿀 때다. value를 바꿔서 돌려주면 메서드가 교체된다. 

function Timed() {
  return (target, key, descriptor) => {
    const original = descriptor.value;

    descriptor.value = function (...args) {
      console.log(`${key} 시작`);
      const result = original.apply(this, args);
      console.log(`${key} 끝`);
      return result;
    };

    return descriptor; // 바꾼 설정을 돌려준다
  };
}

class ShowsService {
  @Timed()
  findAll() { console.log('본문 실행'); return []; }
}

new ShowsService().findAll();
findAll 시작
본문 실행
findAll 끝

이렇게 데코레이터는 메모를 남기는 일과 메서드를 감싸는 일을 모두 할 수 있다. @Get은 메모만 남기는 쪽이다.

메타데이터: 메모를 어디에 두는가

앞에서는 target.path = path로 단순화했지만, 실제 Nest는 reflect-metadata 라이브러리를 쓴다. 메모를 클래스 속성과 섞지 않고 별도 저장소(라이브러리 내부의 WeakMap)에 보관한다. 

Reflect.defineMetadata('path', 'shows', ShowsController); // 쓰기
Reflect.getMetadata('path', ShowsController);             // 읽기 → 'shows'

저장소에는 메모가 대상별로 이렇게 들어간다.

대상 (클래스 또는 함수) 메모 이름 값
ShowsController 'path' 'shows'
ShowsController.prototype.findPopular 'path' 'popular'
ShowsController.prototype.findPopular 'method' 0

Nest 데코레이터의 실제 소스

이제 Nest 소스를 읽을 수 있다. 앞에서 직접 만든 Controller, Get과 구조가 같고, target.path = path 줄이 Reflect.defineMetadata로 바뀌었을 뿐이다. 

// @nestjs/common/decorators/core/injectable.decorator.js
export function Injectable(options) {
  return (target) => {
    Reflect.defineMetadata(INJECTABLE_WATERMARK, true, target);
    Reflect.defineMetadata(SCOPE_OPTIONS_METADATA, options, target);
  };
}
// @nestjs/common/decorators/http/request-mapping.decorator.js (단순화)
const RequestMapping = (metadata) => {
  const path = /* @Get에 넘긴 주소 */;
  const requestMethod = /* GET, POST 등 */;

  return (target, key, descriptor) => {
    Reflect.defineMetadata('path', path, descriptor.value);
    Reflect.defineMetadata('method', requestMethod, descriptor.value);
    return descriptor;
  };
};
  • path, requestMethod: 바깥 함수에서 미리 받아 둔 값이다.
  • return descriptor: 받은 것을 그대로 돌려준다. 메서드를 바꾸지 않는다는 뜻이다.

실제 메모 꺼내 보기

아래 코드의 메모를 실제로 꺼내 보면 다음과 같다.

@Injectable()
class ShowsService {}

@Controller('shows')
class ShowsController {
  constructor(readonly shows: ShowsService) {}

  @Get('popular')
  findPopular() { return []; }
}

@Module({ controllers: [ShowsController], providers: [ShowsService] })
class ShowsModule {}
ShowsService
  { __injectable__: true, 'scope:options': undefined }
ShowsController
  { 'design:paramtypes': [ShowsService], __controller__: true, path: 'shows', ... }
ShowsController.prototype.findPopular
  { path: 'popular', method: 0 }
ShowsModule
  { controllers: [ShowsController], providers: [ShowsService] }

method: 0은 RequestMethod.GET이다.

컴파일러가 남기는 기록

Nest가 new BookingService(db, mailer)를 대신 실행하려면 무엇이 필요한지 알아야 한다. 그런데 컴파일하면 타입이 사라진다. 

class BookingService {
  constructor(db, mailer) {} // Database, Mailer라는 정보가 없다
}

사람이 직접 메모를 남길 수도 있다.

Reflect.defineMetadata('design:paramtypes', [Database, Mailer], BookingService);

하지만 생성자 타입을 두 번 적어야 하고, 고칠 때 깜빡할 수 있다. emitDecoratorMetadata를 켜면 컴파일러가 이 기록을 대신 넣어 준다. 

// 작성한 코드
@Injectable()
class BookingService {
  constructor(private readonly db: Database, private readonly mailer: Mailer) {}
}
// 컴파일 결과의 일부
BookingService = __decorate([
    Injectable(),                                         // 내가 쓴 데코레이터
    __metadata("design:paramtypes", [Database, Mailer])   // 컴파일러가 추가
], BookingService);

타입이 살아남은 것이 아니라, 타입 이름과 같은 이름의 클래스 값을 컴파일러가 배열로 적어 둔 것이다. __decorate가 이 코드를 어떻게 실행하는지는 다음 절에서 본다.

기록이 남는 조건

emitDecoratorMetadata가 켜져 있고, 클래스에 데코레이터가 하나라도 있어야 한다. 컴파일러는 그 데코레이터가 무슨 일을 하는지 보지 않는다. Nest와 무관한 빈 데코레이터를 붙여도 기록이 남고, 데코레이터가 없으면 남지 않는다. 그래서 @Controller가 붙은 컨트롤러에는 @Injectable()이 필요 없다.

메모 누가 적나 언제 생기나
__injectable__, path Nest 데코레이터 함수 데코레이터가 실행될 때
design:paramtypes 컴파일러가 넣은 코드 클래스에 데코레이터가 있을 때

타입이 어떻게 값으로 바뀌는가

작성한 생성자 타입 기록되는 값
Db (클래스) Db
string String
number Number
Pay (인터페이스) Object
Db | null Object

인터페이스는 런타임에 존재하지 않아 Object로 뭉개진다. 그래서 인터페이스를 타입으로 쓰면 Nest가 무엇을 주입할지 알 수 없다.

이 기록은 experimentalDecorators 방식의 데코레이터에서 동작한다. TypeScript의 표준 데코레이터는 방식이 달라, 이 문서의 내용이 그대로 적용되지 않는다. Nest는 experimentalDecorators를 쓴다.

__decorate 해부

이 절은 선택 읽기다. 처음에는 건너뛰어도 뒤의 절을 읽는 데 지장이 없다. 컴파일 결과가 어떻게 실행되는지 궁금할 때 돌아오면 된다.

컴파일러는 파일 맨 위에 도우미 함수 __decorate를 넣어 두고, 모든 데코레이터를 이 함수로 실행한다. 앞에서 "풀어 쓰면"이라고 단순화했던 호출을 실제로 하는 함수다.

클래스 데코레이터: 앞 절의 코드 풀어 쓰기

배열의 두 항목은 모두 "클래스를 받아 메모를 붙이는 함수"다. Injectable()이 그런 함수를 돌려준다는 것은 메타데이터 절의 소스에서 봤고, __metadata(...)도 같은 모양의 함수를 돌려준다. 

const decorators = [
  Injectable(),                                        // 함수 1: Nest의 메모를 붙인다
  __metadata('design:paramtypes', [Database, Mailer]), // 함수 2: 생성자 기록을 붙인다
];

__decorate는 이 배열을 뒤에서부터 돌며 클래스를 넣어 호출한다. 결과적으로 다음 코드와 같다.

// 함수 2가 먼저 실행된다
Reflect.defineMetadata('design:paramtypes', [Database, Mailer], BookingService);

// 그다음 함수 1이 실행된다
Reflect.defineMetadata('__injectable__', true, BookingService);
Reflect.defineMetadata('scope:options', undefined, BookingService);
코드 뜻
__decorate([...], BookingService) 배열의 함수를 뒤에서부터 호출하며 클래스를 넣는다
BookingService = ... 데코레이터가 다른 클래스를 돌려주면 그것으로 바꾼다. 여기서는 아무것도 돌려주지 않아 원래 클래스 그대로다

메서드 데코레이터: descriptor를 누가 넣어 주는가

컴파일러가 파일에 넣어 둔 도우미 함수 __decorate가 넣어 준다. 컴파일 결과에는 descriptor가 없고, 마지막 자리에 null이 있다. 

__decorate([
  Get('popular'),
  // 컴파일러가 넣은 __metadata(...)들
], ShowsController.prototype, 'findPopular', null);

실제 코드는 압축되어 있어, 메서드의 경우만 풀어 쓰면 다음과 같다.

function __decorate(decorators, target, key, desc) {
  // ① desc가 null이면 descriptor를 꺼낸다
  let descriptor = desc === null ? Object.getOwnPropertyDescriptor(target, key) : desc;

  // ② 데코레이터를 뒤에서부터 호출하며 넣어 주고, 돌려준 값을 이어받는다
  for (let i = decorators.length - 1; i >= 0; i--) {
    const result = decorators[i](target, key, descriptor);
    descriptor = result || descriptor;
  }

  // ③ 최종 descriptor를 메서드에 다시 적용한다
  Object.defineProperty(target, key, descriptor);
}

예제 값으로 따라가면 다음과 같다.

순서 실행되는 일 결과
1 파일 로드 중 ShowsController 클래스 정의 prototype에 findPopular가 생김
2 Get('popular') 호출 데코레이터 함수를 돌려받음
3 __decorate가 getOwnPropertyDescriptor 호출 descriptor 획득, value는 findPopular 함수
4 데코레이터 함수에 (prototype, 'findPopular', descriptor)를 넣어 호출 메서드 함수에 메모가 붙음
5 Object.defineProperty로 다시 적용 @Get은 그대로 돌려줬으므로 메서드는 그대로

풀어 쓴 코드에는 낯선 부분이 세 가지 있다.

① 왜 null을 넘기고 안에서 꺼내는가. __decorate는 모든 종류의 데코레이터가 함께 쓰는 함수다. 그래서 넘어온 인자로 경우를 구분한다. null은 "descriptor를 꺼내라"는 신호다.

대상 컴파일 결과 __decorate가 하는 일
클래스 K = __decorate([...], K) 클래스를 그대로 사용
메서드, getter __decorate([...], K.prototype, 'method', null) descriptor를 꺼냄
프로퍼티 __decorate([...], K.prototype, 'field', void 0) 꺼내지 않음

② 왜 result를 다시 할당하는가. 앞의 Timed처럼 데코레이터는 메서드를 바꿀 수 있다. 재할당이 있어야 그 값이 다음 데코레이터와 ③으로 이어진다. 메모만 붙이는 데코레이터는 아무것도 돌려주지 않으므로, ||로 기존 값을 유지한다.

데코레이터의 동작 돌려주는 값 result || descriptor의 결과
메모만 붙임 없음 기존 descriptor 유지
받은 것을 고쳐 돌려줌 같은 객체 같은 객체
새 객체를 돌려줌 새 객체 새 객체로 교체

새 descriptor를 돌려주는 데코레이터 A, B를 겹쳐 비교하면 차이가 보인다.

재할당 있음: A(B(body))
재할당 없음: body

③ 왜 defineProperty를 또 호출하는가. 꺼낸 descriptor는 복사본이라, 값을 고쳐도 메서드는 바뀌지 않는다. 다시 적용해야 반영된다. 

const d = Object.getOwnPropertyDescriptor(C.prototype, 'm');
d.value = () => 'replaced';

new C().m();                                // 'original'

Object.defineProperty(C.prototype, 'm', d);
new C().m();                                // 'replaced'

__decorate 전체는 복사본을 꺼내고, 데코레이터들이 차례로 고치게 한 뒤, 최종본을 다시 적용하는 과정이다.

reflect-metadata가 로드되어 있으면 __decorate는 내부에서 Reflect.decorate로 일을 넘긴다. Nest 앱이 이 경우에 해당하지만, descriptor를 꺼내 넣어 주는 흐름은 같다.

언제 실행되는가

컴파일은 앱이 실행되기 전 별도 과정이고, 나머지 셋은 모두 같은 Node.js 프로세스 안에서 일어나는 런타임이다. tsc도 Node.js로 돌아가지만 앱과는 별개의 프로그램이다.

타입은 컴파일 단계에만 존재한다. 런타임에는 컴파일러가 남긴 기록만 있다.

단계 구분 일어나는 일 해당 코드
컴파일 빌드 타임 @를 함수 호출로 바꾸고 기록 코드 추가, 타입 삭제 db: Database의 타입
파일 로드 런타임 클래스 정의와 함께 데코레이터 실행, 메모 저장 (1번) @Injectable(), Reflect.defineMetadata(...)
앱 조립 런타임 Nest가 메모를 읽어 객체 생성, 주소 연결. 기본 싱글턴은 1번 생성 Reflect.getMetadata(...), new ShowsService()
요청 처리 런타임 연결된 메서드 실행 (요청마다) findPopular()의 본문

명령으로 보면 둘이 나뉘어 있다.

pnpm build          # 빌드 타임: tsc가 .ts를 .js로 변환하고 끝난다
node dist/main.js   # 런타임: Node.js가 .js만 실행한다

런타임의 세 단계는 main.ts로 구분할 수 있다.

// 파일 로드: import를 따라 파일이 실행되고, 데코레이터도 이때 실행된다
import { NestFactory } from '@nestjs/core';
import { AppModule } from './app.module.js';

// 앱 조립: 메모를 읽어 객체를 만든다
const app = await NestFactory.create(AppModule);

// 앱 조립 마무리: 주소를 연결하고 포트를 연다
await app.listen(3000);

// 요청 처리: 이후 요청이 올 때마다 연결된 메서드가 실행된다

데코레이터 실행 순서

Tag는 Nest와 관계없이, 실행 순서를 보려고 직접 만든 데코레이터다. 메모는 남기지 않고 로그만 찍는다. 함수가 두 겹이므로 로그도 두 번 나온다. 

function Tag(label: string) {
  // 바깥 함수: @Tag('...')의 괄호가 호출될 때 실행된다
  console.log('factory', label);

  // 안쪽 함수: 데코레이터가 대상에 적용될 때 실행된다
  return function (target: any, key?: string) {
    // 클래스에 붙으면 target이 클래스, 메서드에 붙으면 target이 prototype이다
    const name = typeof target === 'function' ? target.name : target.constructor.name;
    console.log('apply', label, 'target=', name, 'key=', key);
  };
}

이 데코레이터를 메서드 하나와 클래스에 붙여 실행한다.

console.log('before class');

@Tag('class-A')
@Tag('class-B')
class Sample {
  @Tag('method')
  hello() { return 'hi'; }
}

console.log('after class');
before class
factory method
apply method target= Sample key= hello
factory class-A
factory class-B
apply class-B target= Sample key= undefined
apply class-A target= Sample key= undefined
after class
로그 뜻
factory method @Tag('method')의 괄호가 호출됨
apply method ... key= hello 안쪽 함수가 hello 메서드에 적용됨
factory class-A, factory class-B 클래스에 붙은 두 괄호가 위에서 아래로 호출됨
apply class-B, apply class-A 안쪽 함수가 아래에서 위로 클래스에 적용됨. 클래스에는 메서드 이름이 없어 key는 undefined
  • new도 요청도 필요 없다. 클래스가 정의될 때 실행되고, 다시 실행되지 않는다.
  • 메서드가 먼저, 클래스가 나중이다.

Nest가 메모를 읽는 과정

이 절의 파일 경로는 설치된 @nestjs/core 12.4.0 기준이다. 예제는 다음과 같다.

@Injectable()
class ShowsService {}

@Controller('shows')
class ShowsController {
  constructor(private readonly shows: ShowsService) {}

  @Get('popular')
  findPopular() { return []; }
}

@Module({ controllers: [ShowsController], providers: [ShowsService] })
class ShowsModule {}

소스에 나오는 이름

아래 소스의 변수는 Nest 내부 이름이다. 예제로 바꾸면 다음과 같다.

소스의 이름 뜻 예제의 값
metatype 등록된 클래스를 가리키는 Nest 내부 이름 ShowsController
prototype 그 클래스의 메서드가 들어 있는 객체 ShowsController.prototype
methodName 지금 살펴보는 메서드 이름 'findPopular'
prototypeCallback 그 메서드 함수 자체 ShowsController.prototype.findPopular
PATH_METADATA 메모 이름을 담은 상수 'path'
METHOD_METADATA 메모 이름을 담은 상수 'method'

세 번의 읽기

Nest는 앱 조립 중에 메모를 세 번 나눠 읽는다.

  1. 읽기 ①: 무엇이 있는지 모으기 (NestFactory.create) @Module의 메모를 읽어 클래스 목록을 만든다. 아직 객체는 만들지 않는다. imports에 모듈이 있으면 따라가서 반복한다. 
    // scanner.js
reflectMetadata(metadataKey, metatype) {
  return Reflect.getMetadata(metadataKey, metatype) || [];
}

    예제를 넣으면 이렇게 읽힌다.

    읽는 코드 값
    Reflect.getMetadata('imports', ShowsModule) 기록 없음, []로 처리
    Reflect.getMetadata('providers', ShowsModule) [ShowsService]
    Reflect.getMetadata('controllers', ShowsModule) [ShowsController]
  2. 읽기 ②: 객체 만들기 (NestFactory.create) 생성자 기록을 읽어 필요한 것을 먼저 만들고 new를 실행한다. 어딘가에서 평범한 new가 실행되는 것이다. 
    // injector/injector.js
reflectConstructorParams(type) {
  const paramtypes = [...(Reflect.getMetadata('design:paramtypes', type) || [])];
  // ...
}

// injector/injector.js의 instantiateClass
new metatype(...instances);

    예제를 넣으면 이 순서로 진행된다.

    순서 Nest가 하는 일 결과
    1 ShowsController의 design:paramtypes를 읽음 [ShowsService], 먼저 만들어야 함
    2 ShowsService의 design:paramtypes를 읽음 기록 없음, 필요한 것 없음
    3 new ShowsService() 실행 서비스 객체 생성
    4 new ShowsController(서비스 객체) 실행 컨트롤러 객체 생성
  3. 읽기 ③: 주소 연결하기 (app.listen → init) 클래스의 주소를 읽고, 프로토타입의 메서드를 하나씩 돌며 메서드의 주소도 읽는다. 
    // router/router-explorer.js의 extractRouterPath
const path = Reflect.getMetadata(PATH_METADATA, metatype);

// router/paths-explorer.js의 exploreMethodMetadata
const prototypeCallback = prototype[methodName];
const routePath = Reflect.getMetadata(PATH_METADATA, prototypeCallback);
if (isUndefined(routePath)) {
  return null; // 기록이 없으면 라우트가 아니다
}
const requestMethod = Reflect.getMetadata(METHOD_METADATA, prototypeCallback);

    읽은 값은 이렇게 쓰인다. instance[methodName]은 함께 모으는 메서드 함수다.

    변수 읽은 값 어떻게 쓰이나 결과
    path 'shows' 앞에 /를 붙여 컨트롤러 주소로 쓴다 '/shows'
    routePath 'popular' 앞에 /를 붙여 컨트롤러 주소 뒤에 잇는다 '/shows/popular'
    requestMethod 0 REQUEST_METHOD_MAP에서 Express 메서드 이름을 찾는다 'get'
    instance[methodName] findPopular 함수 요청이 오면 실행할 함수로 감싼다 handler

    마지막으로 이 값들을 합쳐 Express에 등록한다. 아래는 router/router-explorer.js의 applyCallbackToRouter를 예제 값으로 단순화한 코드다. 

    const fullPath = '/shows' + '/popular';

// 메서드를 실행하고 반환값을 응답으로 보내는 함수를 만든다
const handler = createCallbackProxy(controller, controller.findPopular);

// requestMethod가 0이므로 get을 고른다
router.get(fullPath, handler);

    결국 Express에서 app.get('/shows/popular', handler)를 직접 쓴 것과 같다. 요청이 오면 Express가 handler를 호출하고, handler가 findPopular()를 실행한 뒤 반환값을 응답으로 보낸다. 이 시점에 메모는 이미 쓰임을 다했다.

@Get이 파일 로드 때 메서드 함수에 붙인 메모를, Nest가 앱 조립 때 같은 함수에서 꺼낸다. 쓰는 곳과 읽는 곳이 여기서 만난다.

Hono라면 이 세 단계는 다음과 같이 직접 쓰는 코드에 해당한다.

const shows = new ShowsService();                   // 읽기 ①, ②에 해당
const controller = new ShowsController(shows);      // 읽기 ②에 해당
app.get('/shows/popular', (c) => c.json(controller.findPopular())); // 읽기 ③에 해당

망가뜨려 보기

어떤 메모가 빠졌는지에 따라 실패 시점이 달라진다. 첫 번째만 tsc가 잡는다.

실수 드러나는 단계 결과
@Injectable 괄호 누락 빌드 타임 TS1238 오류
providers 누락 앱 조립 앱이 켜지지 않고, 찾지 못한 클래스를 알려 줌
인터페이스를 생성자 타입으로 사용 앱 조립 앱이 켜지지 않고, 인자 위치만 알려 줌
@Controller 없는 클래스를 controllers에 등록 앱 조립 app.init()에서 예외 발생
@Injectable() 누락 요청 처리 앱은 켜지고, 의존성을 쓰는 순간 TypeError로 500 응답

원인은 앞에서 본 소스에 있다.

  • @Injectable() 누락이 조용한 이유: 기록이 없으면 || []로 빈 배열이 되어, Nest가 "필요한 것이 없는 클래스"로 보고 인자 없이 new를 실행한다.
  • providers 누락이 시끄러운 이유: 기록에 [Database]가 있는데 모듈에서 찾지 못한다.

@Injectable() 누락은 앱을 조립만 하는 테스트로 잡을 수 없다. 그 코드를 실제로 실행하는 테스트가 있어야 한다. 받는 것이 없는 서비스에도 항상 붙이면 나중에 생성자 인자를 추가할 때 깜빡할 일이 없다.

스스로 확인하기

질문에 먼저 답해 본 뒤, 눌러서 답을 확인한다.

1. @Controller('reviews')를 @ 없이 쓰면? 
class ReviewsController {}
Controller('reviews')(ReviewsController);
2. @Injectable()의 빈 괄호는 왜 필요한가?

Injectable은 호출해야 데코레이터 함수를 돌려주기 때문이다. 괄호를 빼면 클래스가 옵션 자리에 들어간다.

3. 아래 코드를 실행하면 hello는 몇 번 출력되고, 마지막 줄의 결과는 무엇인가? 
function Log(): ClassDecorator {
  return (target) => {
    console.log('hello');
    Reflect.defineMetadata('role', 'admin', target);
  };
}

@Log()
class A {}

new A();
new A();
console.log(Reflect.getMetadata('role', A));

hello는 클래스가 정의될 때 1번만 출력되고, 마지막 줄은 admin을 출력한다. new는 데코레이터를 다시 실행하지 않는다.

4. Nest와 관계없는 빈 데코레이터 @Log()만 붙인 클래스에도 design:paramtypes가 남는가?

남는다. emitDecoratorMetadata가 켜져 있으면 컴파일러는 데코레이터가 무슨 일을 하는지 보지 않고, 붙어 있는지만 본다.

5. @Controller('shows') 안의 @Get() 메서드 findAll과 데코레이터 없는 메서드 helper는 각각 라우트가 되는가?

findAll은 GET /shows로 등록된다. helper는 path 메모가 없어 건너뛴다. 라우트가 아닐 뿐 일반 메서드로 호출할 수 있다.

6. 생성자 인자가 있는 서비스에서 @Injectable()을 빼고 providers에만 등록하면 어떻게 되는가?

tsc와 앱 시작은 통과한다. 기록이 없어 인자 없이 new가 실행되므로 의존성이 undefined이고, 그것을 쓰는 코드가 실행될 때 TypeError가 나서 500으로 응답한다.

7. 인터페이스는 왜 생성자 주입의 기준으로 쓸 수 없는가?

인터페이스는 컴파일 후 사라지는 타입이라 design:paramtypes에 Object로 기록된다. Nest가 어떤 클래스를 찾아야 할지 알 수 없다.
