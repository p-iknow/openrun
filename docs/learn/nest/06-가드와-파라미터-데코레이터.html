06 가드와 파라미터 데코레이터

Nest의 가드가 무엇이고 요청 안에서 언제 실행되는지, 통과·거절을 어떻게 알리는지 정리한다. 그리고 가드가 확인한 값을 핸들러 인자로 받게 해 주는 createParamDecorator를 본다. 이 저장소의 로그인 가드는 auth 08 문서에서 다루고, 여기서는 일반 개념만 적는다. 내부 동작은 설치된 @nestjs/core·@nestjs/common 12.4 소스로 확인했다.

한눈에 보기

가드(Guard)는 "이 요청이 이 핸들러를 실행해도 되는가"를 정하는 문지기다. canActivate 메서드 하나를 가지고, 통과면 true를 돌려준다. 거절하려면 false를 돌려주거나 예외를 던진다. 거절되면 핸들러는 실행되지 않는다. 로그인 확인(인증)이나 역할 확인(인가)처럼 핸들러를 실행할지 말지를 가르는 검사를 둔다.

통과: 세션 쿠키가 있는 GET /me
  1. 가드: 세션 확인 → true
  2. 파이프
  3. 핸들러 실행
  4. 200
거절: 쿠키 없는 GET /me
  1. 가드: 세션 없음 → 예외
  2. 파이프·핸들러 건너뜀
  3. 예외 필터가 401 응답

프론트엔드로 비유하면 라우터의 보호 라우트(protected route)다. 로그인하지 않은 사용자가 /mypage에 들어오면 페이지 컴포넌트를 그리기 전에 로그인 화면으로 보낸다. 가드는 서버에서 같은 일을 한다. 페이지 컴포넌트가 핸들러다.

요청 안에서 가드의 자리

nest 05 문서에서 본 요청의 단계 중 가드는 미들웨어 다음, 인터셉터와 파이프 앞이다.

  1. 미들웨어 Express 단계. 쿠키 파싱, CORS, 로깅. 아직 어느 핸들러로 갈지 모른다.
  2. 가드 어느 컨트롤러의 어느 메서드인지 안다. 실행할지 말지를 정한다.
  3. 인터셉터 (앞부분) 핸들러 실행을 감싼다. 시간 재기, 응답 변환.
  4. 파이프 핸들러 인자를 하나씩 변환·검증한다.
  5. 핸들러 컨트롤러 메서드.
  6. 인터셉터 (뒷부분) 핸들러가 돌려준 값을 받아 바꿀 수 있다.
  1. 예외 필터 2~6 어디서든 예외가 나면 여기로 와서 오류 응답이 된다(nest 04 문서).

Nest가 요청 처리 함수를 만드는 router-execution-context.js를 보면 순서가 그대로 보인다. 가드 함수 fnCanActivate를 먼저 기다리고, 그다음 인터셉터가 핸들러(파이프를 거친 인자로 부르는)를 감싸 실행한다. 

// @nestjs/core 12.4: router/router-execution-context.js (줄임)
return async (req, res, next) => {
  const args = this.contextUtils.createNullArray(argsLength);
  fnCanActivate && (await fnCanActivate([req, res, next]));   // 1. 가드
  this.responseController.setStatus(res, httpStatusCode);
  // ...
  const resultOrDeferred = this.interceptorsConsumer.intercept( // 2. 인터셉터가
    interceptors, [req, res, next], instance, callback,
    handler(args, req, res, next, ...),                          // 3. 파이프 → 핸들러를 감싼다
    contextType,
  );
  // ...
};

왜 로그인 확인을 미들웨어가 아니라 가드에 두나

미들웨어로도 쿠키를 읽고 401을 보낼 수 있다. 하지만 미들웨어는 "이 요청이 어느 핸들러로 가는지" 모르므로, 로그인이 필요한 경로를 URL 패턴으로 따로 관리해야 한다. 가드는 핸들러에 데코레이터로 붙으므로, 컨트롤러 코드만 봐도 "이 API는 로그인이 필요하다"가 보인다. 핸들러 정보(getHandler())로 메타데이터를 읽어 핸들러마다 다르게 판단할 수도 있다.

canActivate: true, false, 예외

// @nestjs/common: 가드가 지켜야 하는 모양
interface CanActivate {
  canActivate(context: ExecutionContext): boolean | Promise<boolean> | Observable<boolean>;
}

돌려줄 수 있는 것은 불리언, 불리언의 Promise, 불리언의 Observable이다. DB를 봐야 하는 가드는 async로 쓰고 Promise를 돌려준다. 결과에 따라 일어나는 일은 셋 중 하나다.

가드가 한 일 핸들러 응답
true를 돌려줌 다음 가드로, 마지막이면 실행 핸들러가 정함
false를 돌려줌 실행 안 함 403 ForbiddenException('Forbidden resource')
예외를 던짐 실행 안 함 그 예외를 예외 필터가 응답으로 바꿈 (401, 403, 무엇이든)

false가 403이 되는 곳은 Nest 코드에 그대로 있다.

// @nestjs/core 12.4: router/router-execution-context.js
createGuardsFn(guards, instance, callback, contextType) {
  const canActivateFn = async (args) => {
    const canActivate = await this.guardsConsumer.tryActivate(guards, args, instance, callback, contextType);
    if (!canActivate) {
      throw new ForbiddenException(FORBIDDEN_MESSAGE); // 'Forbidden resource'
    }
  };
  return guards.length ? canActivateFn : null;
}

"로그인하지 않았다"를 false로 알리면 403이 된다. HTTP에서 401(Unauthorized)은 "누군지 모르겠다, 인증하라", 403(Forbidden)은 "누군지 알지만 허락하지 않는다"이다. 로그인 가드가 401을 내려면 false 대신 401 예외를 직접 던져야 한다. 원하는 오류 코드와 본문을 정할 수 있다는 것도 예외를 던지는 쪽의 장점이다.

가드가 여러 개면 붙인 순서대로 하나씩 실행하고, 하나라도 false면 거기서 멈춘다(GuardsConsumer.tryActivate). 예외를 던지면 당연히 그 자리에서 멈춘다. 뒤 가드는 앞 가드가 통과했다는 것을 믿고 써도 된다.

ExecutionContext

canActivate가 받는 ExecutionContext는 "지금 처리 중인 호출"에 대한 정보다. 예외 필터가 받는 ArgumentsHost를 넓힌 것이라, 같은 방법으로 요청과 응답을 꺼내고 거기에 "어느 핸들러인지"가 더해진다.

메서드 돌려주는 것 쓰는 곳
switchToHttp() HTTP용 도우미. .getRequest(), .getResponse() 쿠키 읽기, 요청에 값 붙이기, 응답에 쿠키 굽기
getHandler() 실행하려는 메서드 함수 (예: MeController.prototype.findMe) 메서드에 붙은 메타데이터 읽기 (예: @Roles('admin'))
getClass() 컨트롤러 클래스 (예: MeController) 클래스에 붙은 메타데이터 읽기
getType() 'http', 'ws', 'rpc' 같은 가드를 HTTP와 웹소켓에서 함께 쓸 때 나누기 
async canActivate(context: ExecutionContext): Promise<boolean> {
  const http = context.switchToHttp();
  const request = http.getRequest<Request>();   // Express의 req
  const response = http.getResponse<Response>(); // Express의 res
  // ...
}

getRequest<Request>()의 타입 인자는 타입스크립트에게 알려 주는 것일 뿐 실행 중에 검사하지 않는다. 실제로 오는 것은 Express의 req 객체다.

가드를 붙이는 세 곳과 순서

// 1. 메서드 하나에만
@Controller('orders')
export class OrdersController {
  @Get(':id')
  @UseGuards(LoginGuard)
  findOne() {}
}

// 2. 컨트롤러의 모든 메서드에
@Controller('me')
@UseGuards(LoginGuard)
export class MeController {}

// 3. 앱 전체에 (둘 중 하나)
app.useGlobalGuards(new LoginGuard());                 // main.ts. 인스턴스를 직접 만든다
@Module({ providers: [{ provide: APP_GUARD, useClass: LoginGuard }] }) // 모듈에서. Nest가 만든다

한 핸들러에 여러 곳의 가드가 걸리면 전역 → 컨트롤러 → 메서드 순서로 실행한다. Nest가 가드 목록을 만드는 ContextCreator.createContext가 이 순서로 이어 붙인다. 

// @nestjs/core 12.4: helpers/context-creator.js
return [
  ...this.createConcreteContext(globalMetadata || [], contextId, inquirerId),
  ...this.createConcreteContext(classMetadata, contextId, inquirerId),
  ...this.createConcreteContext(methodMetadata, contextId, inquirerId),
];

클래스를 넘기나, 인스턴스를 넘기나

@UseGuards(LoginGuard)처럼 클래스를 넘기면 Nest가 인스턴스를 만들고 생성자 인자를 주입한다. @UseGuards(new LoginGuard())처럼 인스턴스를 넘기면 그대로 쓰므로 주입이 없다. 전역 가드도 같다. useGlobalGuards(new ...)는 모듈 바깥에서 직접 만든 인스턴스라 주입을 받을 수 없고, APP_GUARD는 Nest가 만들므로 주입을 받는다. 예외 필터의 APP_FILTER와 같은 이야기다(nest 04 문서).

가드 안에서 의존성 주입

가드는 @Injectable()을 붙인 클래스라서 서비스처럼 생성자로 다른 프로바이더를 받을 수 있다 (nest 02 문서). 세션을 확인하려면 세션 저장소가 필요하니 주입받는다. 

@Injectable()
export class LoginGuard implements CanActivate {
  constructor(private readonly sessions: SessionService) {}

  async canActivate(context: ExecutionContext): Promise<boolean> {
    const request = context.switchToHttp().getRequest<Request>();
    const session = await this.sessions.find(request);
    if (!session) {
      throw new UnauthorizedException();
    }
    return true;
  }
}

가드는 "쓰는 쪽 모듈"에서 만들어진다

@UseGuards(LoginGuard)로 붙인 가드는 providers에 적지 않아도 된다. Nest가 앱을 훑을 때 컨트롤러에 붙은 가드를 찾아 그 컨트롤러가 속한 모듈의 주입 대상으로 등록한다(scanner.js의 reflectDynamicMetadata). 요청 때는 그 모듈에서 인스턴스를 꺼낸다(guards-context-creator.js의 getInstanceByMetatype).

그래서 가드의 생성자가 받는 프로바이더는 가드를 붙인 컨트롤러의 모듈에서 보여야 한다. 그 모듈의 providers에 있거나, 가져온(imports) 모듈이 exports한 것이어야 한다. 아니면 앱이 켜질 때 "Nest can't resolve dependencies of the LoginGuard" 오류가 난다.

createParamDecorator

핸들러 인자에 붙이는 @Body(), @Query(), @Req()는 모두 "요청에서 무엇을 꺼내 이 인자에 넣을지"를 정하는 파라미터 데코레이터다. createParamDecorator로 같은 것을 직접 만들 수 있다. 

import { createParamDecorator, type ExecutionContext } from '@nestjs/common';

// 요청 헤더 하나를 꺼내는 데코레이터
export const Header = createParamDecorator(
  (name: string, context: ExecutionContext): string | undefined => {
    const request = context.switchToHttp().getRequest<Request>();
    return request.get(name);
  },
);

// 쓰는 쪽
@Get()
find(@Header('user-agent') userAgent: string | undefined) {}
  1. 팩토리 함수를 넘긴다 (data, context) => 값. data는 데코레이터를 쓸 때 괄호 안에 넣은 값('user-agent'), context는 가드가 받는 것과 같은 ExecutionContext다.
  2. 데코레이터를 붙이는 시점에는 메타데이터만 남긴다 "이 메서드의 몇 번째 인자는 이 팩토리로 채운다"를 기록할 뿐이다(nest 01 문서).
  3. 요청마다 팩토리를 불러 인자를 채운다 핸들러를 부르기 직전, 가드를 통과한 뒤다. 그래서 팩토리는 가드가 요청에 붙여 둔 값을 읽을 수 있다.

직접 만든 데코레이터의 인자도 파이프를 거친다. 이때 파이프가 받는 metadata.type은 'custom'이다 (nest 05 문서).

가드가 확인한 값을 핸들러로 넘기기

가드는 세션을 찾아 통과시키지만, 핸들러도 "누가 요청했는지" 알아야 한다. 핸들러에서 다시 세션을 찾으면 같은 일을 두 번 한다. 그래서 흔히 쓰는 짝이 있다. 가드가 요청 객체에 값을 붙이고, 파라미터 데코레이터가 그 값을 꺼낸다.

  1. 요청 객체
  2. 가드
  3. 파라미터 데코레이터
  4. 핸들러
  1. canActivate(context)
  2. 세션 확인
  3. request.user = 세션 값을 붙임
  4. 팩토리(data, context)
  5. request.user 꺼내기
  6. 인자로 넣어 호출
// 가드: 확인하고 붙인다
async canActivate(context: ExecutionContext): Promise<boolean> {
  const request = context.switchToHttp().getRequest();
  const user = await this.sessions.find(request);
  if (!user) throw new UnauthorizedException();
  request.user = user;
  return true;
}

// 데코레이터: 꺼낸다
export const CurrentUser = createParamDecorator(
  (_: unknown, context: ExecutionContext) => context.switchToHttp().getRequest().user,
);

// 핸들러: 받기만 한다
@Get('me')
@UseGuards(LoginGuard)
findMe(@CurrentUser() user: User) {}

Passport(@nestjs/passport)가 쓰는 방식도 같다. 인증에 성공하면 req.user에 사용자를 붙인다. 다만 user처럼 흔한 문자열 키는 다른 라이브러리와 부딪힐 수 있다. 이 저장소가 문자열 대신 Symbol을 키로 쓴 이유는 auth 08 문서에 있다.

헷갈리기 쉬운 점

  • false는 403이다. 401을 원하면 예외를 던진다.
  • 가드는 파이프보다 먼저다. 가드 안에서 request.body를 읽으면 아직 검증·변환되지 않은 값이다. 가드는 본문 내용이 아니라 "누가 보냈나"를 보는 곳이다.
  • 인스턴스로 넘긴 가드는 주입을 받지 못한다. @UseGuards(new LoginGuard())의 생성자 인자는 비어 있다.
  • 파라미터 데코레이터는 가드를 대신하지 않는다. @CurrentUser()만 붙이고 가드를 빼면 핸들러는 그대로 실행되고 값만 undefined가 된다. 막는 것은 가드의 일이다.

스스로 확인하기

1. 이 가드로 로그인하지 않은 요청을 막으면 응답 상태 코드는 무엇일까?

canActivate 절의 표를 본다.

async canActivate(context: ExecutionContext): Promise<boolean> {
  const session = await this.sessions.find(context.switchToHttp().getRequest());
  return session !== null;
}
답 보기

403. false를 돌려주면 Nest가 ForbiddenException('Forbidden resource')를 던진다. "로그인이 필요하다"는 뜻의 401을 내려면 UnauthorizedException 같은 401 예외를 직접 던져야 한다.

2. 실행 순서를 적어 보자.

가드를 붙이는 세 곳과 순서 절. APP_GUARD로 RateLimitGuard를 전역에 등록했다.

@Controller('orders')
@UseGuards(LoginGuard)
export class OrdersController {
  @Post()
  @UseGuards(TermsConsentGuard)
  create(@Body({ schema: orderSchema }) body: OrderBody) {}
}
답 보기

RateLimitGuard(전역) → LoginGuard(컨트롤러) → TermsConsentGuard(메서드) → 본문 검증 파이프 → create. 앞 가드가 거절하면 뒤는 실행되지 않으므로, TermsConsentGuard는 로그인한 요청만 받는다고 믿어도 된다.

3. 앱이 켜지지 않는다. 무엇을 고쳐야 할까?

가드 안에서 의존성 주입 절. LoginGuard는 생성자로 SessionService를 받는다. SessionService는 AuthModule의 providers에만 있다. OrdersModule의 컨트롤러에 @UseGuards(LoginGuard)를 붙이자 "Nest can't resolve dependencies of the LoginGuard" 오류가 난다.

답 보기

가드는 OrdersModule에서 만들어지므로 SessionService가 OrdersModule에서 보여야 한다. AuthModule이 exports: [SessionService]로 내보내고, OrdersModule이 imports: [AuthModule]로 가져오면 된다.

4. 가드를 빼먹으면 어떻게 될까?

가드가 확인한 값을 핸들러로 넘기기 절의 예시에서 @UseGuards(LoginGuard)를 지웠다.

답 보기

로그인하지 않은 요청도 핸들러까지 들어오고, @CurrentUser()는 undefined를 넣는다. 핸들러가 user.id를 읽다가 500 오류가 나거나, 더 나쁘면 사용자 없이 일을 진행한다. 데코레이터가 값이 없을 때 예외를 던지게 만들면 이런 실수를 바로 알아챌 수 있다. 이 저장소의 CurrentSession이 그렇게 한다.
