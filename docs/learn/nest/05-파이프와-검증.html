05 파이프와 검증

Nest의 파이프가 무엇이고 어떤 문제를 풀려고 나왔는지, 요청 안에서 언제 어떤 순서로 실행되는지 정리한다. 그다음 GET /shows의 쿼리를 검증하는 StandardSchemaValidationPipe와 zod 스키마를 한 줄씩 따라간다. Nest 내부 동작은 설치된 @nestjs/core·@nestjs/common 12.4 소스로, 검증 결과는 저장소의 스키마를 직접 실행해 확인했다.

한눈에 보기

파이프(Pipe)는 Nest가 컨트롤러 메서드(핸들러)를 부르기 직전에, 핸들러에 넘길 인자 하나하나를 받아 바꾸거나(변환) 검사하는(검증) 함수다. 값을 돌려주면 그 값이 핸들러에 들어가고, 예외를 던지면 핸들러는 불리지 않는다. 요청 값을 검사하는 파이프를 검증 파이프라고 부른다.

올바른 요청: GET /shows?page=2
  1. 쿼리 { page: '2' }
  2. 파이프: 숫자로 바꾸고 검사
  3. 핸들러가 { page: 2, size: 20 }을 받음
잘못된 요청: GET /shows?page=abc
  1. 쿼리 { page: 'abc' }
  2. 파이프: 검사 실패 → 예외
  3. 핸들러는 불리지 않음, 예외 필터가 400 응답

프론트엔드로 비유하면 react-hook-form에 zod 스키마를 넘겨 두는 것과 같다. 폼의 onSubmit은 검사를 통과한 값만 받고, 검사 실패는 폼 라이브러리가 따로 처리한다. Nest에서는 핸들러가 onSubmit, 파이프가 폼 라이브러리의 검증 단계, 예외 필터가 오류 표시를 맡는다.

파이프가 없으면

HTTP 요청의 쿼리 문자열은 전부 글자로 온다. ?page=2의 2도 숫자 2가 아니라 글자 '2'다. 파이프가 없다면 GET /shows?page=abc&size=500을 받는 핸들러는 이렇게 생겨야 한다. 

@Get()
findPage(@Query() query: Record<string, string | undefined>) {
  // 1. 글자를 숫자로 바꾸고, 빠졌으면 기본값을 넣는다.
  const page = query.page === undefined ? 1 : Number(query.page);
  const size = query.size === undefined ? 20 : Number(query.size);

  // 2. 범위를 검사하고, 틀리면 ADR 0007 형식으로 400을 던진다.
  const errors = [];
  if (!Number.isSafeInteger(page) || page < 1) {
    errors.push({ field: 'page', detail: '1 이상의 정수여야 합니다.' });
  }
  if (!Number.isSafeInteger(size) || size < 1 || size > 100) {
    errors.push({ field: 'size', detail: '1 이상 100 이하의 정수여야 합니다.' });
  }
  if (errors.length > 0) {
    throw new ProblemException({ status: 400, code: 'VALIDATION_FAILED', detail: '요청 값이 올바르지 않습니다.', errors });
  }

  // 3. 이제야 하려던 일을 한다.
  return this.showsService.findPage({ page, size });
}

이 코드에는 문제가 세 가지 있다.

  1. 모든 핸들러가 같은 코드를 반복한다 엔드포인트가 열 개면 "글자를 숫자로, 범위 검사, 400 던지기"를 열 번 쓴다. 공연 상세(GET /shows/:id)도, 뒤 티켓의 장르·판매 상태 필터도 같은 일을 한다.
  2. 오류 응답 모양이 제각각이 된다 누구는 errors를 빼먹고, 누구는 code를 다르게 쓴다. 스토어는 모든 오류가 같은 형식으로 온다고 믿고 transformErrorResponse 하나로 처리하므로, 한 곳만 어긋나도 깨진다.
  3. 핸들러가 업무보다 입력 청소에 바쁘다 핸들러가 실제로 하는 일은 마지막 한 줄인데, 읽는 사람은 그 앞의 검사 코드를 모두 지나야 한다.

파이프는 이 입력 청소를 핸들러 바깥의 한곳으로 뺀다. 지금 저장소의 핸들러는 한 줄이고, query.page는 이미 1 이상의 정수(number)다. 

// apps/api/src/shows/shows.controller.ts
@Get()
@ApiOkResponse({ type: ShowPageDto })
findPage(
  @Query({ schema: showListQuerySchema }) query: ShowListQuery,
): Promise<ShowPageDto> {
  return this.showsService.findPage(query);
}

파이프의 생김새

파이프는 transform 메서드 하나짜리 객체다. 두 번째 인자 metadata의 타입 ArgumentMetadata부터 보면, 파이프가 "지금 어떤 인자를 다루는지" 알 수 있는 정보가 이것뿐이다. 아래는 설치된 @nestjs/common 12.4의 선언이고, 주석의 값은 GET /shows?page=abc에서 이 저장소의 핸들러 findPage(@Query({ schema: showListQuerySchema }) query: ShowListQuery)가 받는 값이다. 

// @nestjs/common: interfaces/features/paramtype.interface.d.ts
type Paramtype = 'body' | 'query' | 'param' | 'custom';

// @nestjs/common: interfaces/features/pipe-transform.interface.d.ts
interface ArgumentMetadata<Metatype = any> {
  // 값이 요청의 어디서 왔나. @Body → 'body', @Query → 'query', @Param → 'param',
  // createParamDecorator로 만든 직접 만든 데코레이터 → 'custom'
  readonly type: Paramtype;                        // 예: 'query'

  // 매개변수에 적은 TypeScript 타입이 실행 중에도 남는 것(클래스, String, Number 등)이면 그 생성자.
  // ShowListQuery는 type 별칭이라 컴파일하면 사라지고 Object로 남는다.
  readonly metatype?: Type<Metatype> | undefined;  // 예: Object

  // 데코레이터에 넘긴 이름. @Query('page')면 'page', @Query()처럼 전체를 받으면 undefined
  readonly data?: string | undefined;              // 예: undefined

  // @Query({ schema })처럼 데코레이터에 붙인 Standard Schema(zod 등)
  readonly schema?: StandardSchemaV1;              // 예: showListQuerySchema
}

// @nestjs/common: 파이프가 지켜야 하는 모양
interface PipeTransform {
  transform(value: unknown, metadata: ArgumentMetadata): unknown;
  //        └ 예: { page: 'abc' }   └ 예: 위의 네 값
}

같은 요청이라도 매개변수를 어떻게 적느냐에 따라 metadata가 달라진다.

핸들러의 매개변수 value metadata
@Query({ schema: showListQuerySchema }) query: ShowListQuery { page: 'abc' } { type: 'query', metatype: Object, data: undefined, schema: showListQuerySchema }
@Query('page') page: string 'abc' (그 키의 값만) { type: 'query', metatype: String, data: 'page', schema: undefined }
@Param('id') id: number (/shows/7) '7' (주소 조각도 글자) { type: 'param', metatype: Number, data: 'id', schema: undefined }
@Body() body: CreateOrderDto (클래스) 요청 본문 객체 { type: 'body', metatype: CreateOrderDto, data: undefined, schema: undefined }

세 번째 줄처럼 타입을 number로 적어도 value는 글자 '7'이다. 타입은 파이프에게 metatype: Number라는 힌트를 줄 뿐, 값을 바꾸는 것은 파이프(ParseIntPipe 등)의 일이다. 아래 표는 첫 번째 줄, 곧 이 저장소의 경우를 하나씩 풀어 쓴 것이다.

받는 것·돌려주는 것 뜻 GET /shows?page=abc일 때
value 이 인자에 들어갈 원래 값 { page: 'abc' }
metadata.type 값이 어디서 왔나: 'query', 'body', 'param' 등 'query'
metadata.data @Query('page')처럼 이름을 줬을 때 그 이름 undefined (쿼리 전체를 받음)
metadata.metatype 매개변수의 TypeScript 타입이 클래스면 그 클래스 Object (아래 설명)
metadata.schema @Query({ schema })로 붙인 스키마 showListQuerySchema
돌려주는 값 핸들러에 실제로 들어갈 값. 바꿔 돌려주면 변환 (예외를 던지므로 없음)
던지는 예외 핸들러를 부르지 않고 예외 필터로 보낸다. 이것이 검증 ProblemException

metatype이 Object인 이유: ShowListQuery는 type 별칭이라 컴파일하면 사라진다. 컴파일러가 남기는 타입 기록(nest 01 문서)에는 클래스만 남고, 클래스가 아니면 Object로 적힌다. 그래서 파이프가 타입만 보고는 무엇을 검사할지 알 수 없고, 스키마를 데코레이터에 직접 넘긴다.

직접 만들어 보기

검증 파이프가 하는 일을 손으로 만들면 이렇다. 이 저장소에는 없는 연습용 코드다. 쿼리 값 하나를 받아 1 이상의 정수로 바꾸고, 아니면 400을 던진다. 

import { HttpStatus, type ArgumentMetadata, type PipeTransform } from '@nestjs/common';
import { ProblemException } from '../problem-details/problem.exception.js';

export class ParsePositiveIntPipe implements PipeTransform<unknown, number> {
  transform(value: unknown, metadata: ArgumentMetadata): number {
    const number = Number(value);
    if (typeof value !== 'string' || !Number.isSafeInteger(number) || number < 1) {
      throw new ProblemException({
        status: HttpStatus.BAD_REQUEST,
        code: 'VALIDATION_FAILED',
        detail: '요청 값이 올바르지 않습니다.',
        errors: [{ field: metadata.data ?? 'value', detail: '1 이상의 정수여야 합니다.' }],
      });
    }
    return number; // 글자 '2'가 숫자 2로 바뀌어 핸들러에 들어간다.
  }
}

// 쓰는 쪽
@Get(':id')
findOne(@Param('id', ParsePositiveIntPipe) id: number) {
  // 여기서 id는 항상 1 이상의 정수다.
}

@Param('id', ParsePositiveIntPipe)의 두 번째 인자가 이 인자에만 붙는 파이프다. Nest가 metadata.data에 'id'를 넣어 주므로 오류에 필드 이름을 실을 수 있다. Nest에는 이런 파이프가 몇 개 들어 있다(ParseIntPipe, ParseUUIDPipe, ParseEnumPipe 등).

값 하나짜리라면 이걸로 충분하다. 하지만 쿼리에 page, size, genre, sort가 함께 오면 인자마다 파이프를 붙여야 하고, 여러 필드의 오류를 한 응답에 모으지도 못한다. 그래서 객체 전체를 규칙 묶음(스키마)으로 한 번에 검사하는 검증 파이프를 쓴다(3부).

핸들러 앞의 네 단계

요청 하나는 핸들러에 닿기 전에 정해진 순서로 여러 단계를 지난다. 파이프는 핸들러 바로 앞이다.

  • HTTP 요청 Express가 받아 req.query를 객체로 만든다
    • 1. 미들웨어 Express 단계. 로깅, CORS 등. 아직 어느 핸들러인지 모른다
    • 2. 가드(Guard) "들여보내도 되나?" 인증·권한. 1.4 인증에서 쓴다
    • 3. 인터셉터 앞부분 시간 재기, 응답 감싸기 등. 핸들러 실행 전체를 감싼다
    • 4. 파이프 이 문서 인자마다 변환·검증
    • 5. 핸들러 컨트롤러 메서드. showsService.findPage(query)
    • 6. 인터셉터 뒷부분 핸들러가 돌려준 값을 받아 다룬다
    • 어디서든 예외 예외 필터 → 오류 응답 (nest 04 문서)

Nest 소스(@nestjs/core/router/router-execution-context.js)에서 순서가 그대로 보인다. 가드를 먼저 기다리고, 파이프와 핸들러 호출을 묶은 함수(handler)를 인터셉터에 넘긴다. 

// 핸들러를 부르기 직전에 파이프를 기다린다.
const handler = (args, req, res, next, ...) => async () => {
  const pendingPipes = fnApplyPipes && fnApplyPipes(args, req, res, next);
  pendingPipes && (await pendingPipes);       // 파이프에서 예외가 나면 여기서 멈춘다
  const result = callback.apply(instance, args); // 핸들러 호출
  ...
};

return async (req, res, next) => {
  fnCanActivate && (await fnCanActivate([req, res, next])); // 가드
  ...
  // 인터셉터가 handler(파이프 + 핸들러)를 감싸 실행한다.
  const resultOrDeferred = this.interceptorsConsumer.intercept(interceptors, ..., handler(args, req, res, next, ...));
};

가드가 파이프보다 앞이다. 로그인하지 않은 사용자의 요청은 입력 검사까지 가지도 않고 가드에서 막힌다. 반대로 파이프에서 막힌 요청도 핸들러와 서비스, DB 쿼리를 하나도 실행하지 않는다.

파이프를 붙이는 네 곳과 순서

붙이는 곳 쓰는 법 적용 범위
전역 { provide: APP_PIPE, ... } 또는 app.useGlobalPipes() 모든 핸들러의 모든 인자
컨트롤러 클래스에 @UsePipes(...) 그 컨트롤러의 핸들러
메서드 메서드에 @UsePipes(...) 그 핸들러
인자 @Query('page', ParseIntPipe), @Query({ pipes: [...] }) 그 인자 하나

여러 곳에 붙어 있으면 전역 → 컨트롤러 → 메서드 → 인자 순서로 하나씩 실행되고, 앞 파이프가 돌려준 값이 다음 파이프의 value가 된다. Nest 소스(pipes/pipes-consumer.js)는 단순한 반복문이다. 

async applyPipes(value, { metatype, type, data, schema }, transforms) {
  let result = isThenable(value) ? await value : value;
  for (const pipe of transforms) {
    result = await pipe.transform(result, { metatype, type, data, schema });
  }
  return result;
}

transforms는 "전역·컨트롤러·메서드 파이프"에 "그 인자의 파이프"를 이어 붙인 배열이다 (pipes.concat(paramPipes)). 이 저장소는 전역에 검증 파이프 하나만 둔다.

파이프를 거치지 않는 인자

모든 인자가 파이프를 지나지는 않는다. Nest는 요청에서 꺼낸 값인 인자만 파이프에 넘긴다.

파이프를 거친다 거치지 않는다
@Body, @Query, @Param, @RawBody, @UploadedFile(s), @Cookies 등 @Req, @Res, @Next, @Headers 등 요청·응답 객체 자체

Express의 req 객체를 검증하거나 바꿀 일은 없기 때문이다. 소스의 isPipeable(type)이 이 목록을 정한다.

검증 파이프 두 가지

Nest 12에는 객체 전체를 검사하는 검증 파이프가 두 개 들어 있다. 같은 쿼리 규칙을 두 방식으로 적어 보면 차이가 보인다.

ValidationPipe: 클래스와 데코레이터

class-validator로 규칙을 클래스 속성의 데코레이터에 적는다. 숫자로 바꾸기는 class-transformer의 @Type이 맡는다. 이 PR의 첫 구현이 이 방식이었다. 

export class ShowListQueryDto {
  @ApiPropertyOptional({ type: 'integer', minimum: 1, default: 1 }) // OpenAPI 문서용
  @Type(() => Number)                                                 // 글자 → 숫자
  @IsInt({ message: '1 이상의 정수여야 합니다.' })                    // 검증용
  @Min(1, { message: '1 이상의 정수여야 합니다.' })                    // 검증용
  page: number = 1;                                                   // 기본값
}

@Get()
findPage(@Query() query: ShowListQueryDto) {} // 파이프는 metatype(클래스)을 보고 검사한다

minimum: 1(문서)과 @Min(1)(검증)이 같은 규칙을 두 번 말한다. 하나만 고치면 문서와 실제 동작이 어긋나는데, 아무것도 이를 알려 주지 않는다.

StandardSchemaValidationPipe: 스키마

zod처럼 Standard Schema 규격을 따르는 스키마로 검사한다. 스키마 하나에서 검증, OpenAPI 문서, TypeScript 타입이 모두 나온다. 지금 저장소가 쓰는 방식이다. 

export const showListQuerySchema = z.object({
  page: z.coerce.number(PAGE_MESSAGE).int(PAGE_MESSAGE).min(1, PAGE_MESSAGE).default(1),
});
export type ShowListQuery = z.infer<typeof showListQuerySchema>; // { page: number }

@Get()
findPage(@Query({ schema: showListQuerySchema }) query: ShowListQuery) {} // 파이프는 metadata.schema를 보고 검사한다
ValidationPipe StandardSchemaValidationPipe
규칙을 적는 곳 클래스 속성의 데코레이터 스키마 객체
파이프가 보는 것 metadata.metatype (클래스) metadata.schema
글자 → 숫자 @Type(() => Number) z.coerce.number()
기본값 속성 초기값 page = 1 .default(1)
모르는 값 버리기 whitelist: true 옵션 z.object가 기본으로 버림
OpenAPI 문서 @ApiProperty에 한 번 더 적음 @nestjs/swagger가 스키마에서 만듦
핸들러 타입 클래스 자체 z.infer<typeof schema>
필요한 패키지 class-validator, class-transformer zod (Nest·swagger 쪽은 기본 제공)
선택 읽기: 스키마에서 OpenAPI 문서가 나오는 과정

Standard Schema 규격은 스키마가 ~standard라는 속성을 갖게 한다. zod 4는 여기에 검사 함수 validate와 JSON Schema 변환 함수 jsonSchema를 넣어 둔다. 

Object.keys(showListQuerySchema['~standard']);
// ['validate', 'vendor', 'version', 'jsonSchema']

showListQuerySchema['~standard'].jsonSchema.input({ target: 'openapi-3.0' });
// { type: 'object', properties: {
//     page: { default: 1, type: 'integer', minimum: 1, maximum: 9007199254740991, description: '...' },
//     size: { default: 20, type: 'integer', minimum: 1, maximum: 100, description: '...' } } }

@nestjs/swagger 12의 StandardSchemaOpenApiConverter가 문서를 만들 때 이 함수를 불러 객체의 속성을 쿼리 파라미터 하나하나로 펼친다. input을 쓰는 이유는 요청 쪽 모양(기본값이 있으니 생략 가능)을 문서로 보여 주기 위해서다. 그래서 apps/api/openapi.json에 page, size가 각각 "in": "query"로 나온다.

showListQuerySchema 읽기

// apps/api/src/shows/show-list-query.ts
export const showListQuerySchema = z.object({
  page: z.coerce
    .number(PAGE_MESSAGE)   // ① 글자를 Number()로 바꾼다. NaN이면 이 문구로 실패
    .int(PAGE_MESSAGE)      // ② 정수인가 (zod 4의 int()는 Number.MAX_SAFE_INTEGER까지만)
    .min(1, PAGE_MESSAGE)   // ③ 1 이상인가
    .default(1)             // ④ 값이 없으면(undefined) ①~③을 건너뛰고 1
    .meta({ description: '페이지 번호(1부터). ...' }), // ⑤ OpenAPI 설명
  size: z.coerce
    .number(SIZE_MESSAGE)
    .int(SIZE_MESSAGE)
    .min(1, SIZE_MESSAGE)
    .max(MAX_PAGE_SIZE, SIZE_MESSAGE) // 100 이하인가
    .default(DEFAULT_PAGE_SIZE)
    .meta({ description: '페이지 크기' }),
});
  • z.coerce: 검사 전에 Number(value)로 바꾼다. 쿼리 문자열은 늘 글자라 이것이 없으면 '2'도 "숫자가 아니다"로 실패한다.
  • .default()의 위치: 맨 뒤에 있지만 실행은 가장 먼저 판단한다. 값이 undefined면 앞의 변환과 검사를 거치지 않고 기본값을 쓴다. Number(undefined)는 NaN이라, 기본값이 없었다면 쿼리를 생략한 요청이 실패했을 것이다.
  • 필드마다 문구 하나: 어느 규칙에 걸려도 같은 문구가 나오게 했다. 스토어나 사용자는 "몇 번째 규칙에 걸렸나"가 아니라 "이 값은 이래야 한다"를 알면 된다.
  • z.object: 스키마에 없는 키(?foo=bar)는 결과에서 빠진다. 오류는 아니다.

잘못된 요청 하나 따라가기

GET /shows?page=abc&size=500이 들어왔을 때 일어나는 일을 순서대로 본다.

  1. Express가 쿼리를 객체로 만든다 값은 모두 글자다: { page: 'abc', size: '500' }.
  2. Nest가 이 핸들러의 인자 정보를 꺼낸다 @Query({ schema: showListQuerySchema })가 앱이 뜰 때 저장해 둔 정보로 metadata를 만든다: { type: 'query', data: undefined, metatype: Object, schema: showListQuerySchema }. 데코레이터가 정보를 저장하고 Nest가 읽는 과정은 nest 01 문서에 있다.
  3. 가드와 인터셉터를 지난다 지금 저장소에는 둘 다 없다.
  4. 전역 파이프의 transform이 불린다 AppModule에 APP_PIPE로 등록한 StandardSchemaValidationPipe다. 
// @nestjs/common/pipes/standard-schema-validation.pipe.js
async transform(value, metadata) {
  const schema = metadata.schema;
  if (!schema || !this.toValidate(metadata)) {
    return value;                                   // 스키마가 없는 인자는 그대로 통과
  }
  this.stripProtoKeys(value);                       // __proto__ 같은 위험한 키 제거
  const result = await this.validate(value, schema, this.validateOptions); // schema['~standard'].validate
  if (result.issues) {
    throw this.exceptionFactory(result.issues);     // 실패 → 우리가 넣은 함수로 예외를 만든다
  }
  return this.isTransformEnabled ? result.value : value; // 성공 → 변환된 값
}
  1. zod가 필드마다 검사한다 page: Number('abc')는 NaN → 숫자가 아니라 실패. size: 500 → 정수 통과 → 1 이상 통과 → 100 이하 실패. 결과는 { issues: [{ path: ['page'], message: '1 이상의 정수여야 합니다.' }, { path: ['size'], message: '1 이상 100 이하의 정수여야 합니다.' }] }.
  2. exceptionFactory가 ProblemException을 만든다 path를 'page' 같은 필드 이름으로 바꿔 errors에 담는다(아래 절).
  3. 핸들러는 불리지 않는다 showsService.findPage도, DB 쿼리도 실행되지 않는다.
  4. 예외 필터가 응답을 쓴다 ProblemDetailsFilter가 ProblemException을 받아 application/problem+json으로 보낸다(nest 04 문서).

올바른 요청 ?page=2라면 5단계에서 검사가 통과하고 result.value가 { page: 2, size: 20 }이다. 이 값이 핸들러의 query로 들어가므로, 서비스는 (page - 1) * size를 바로 계산한다.

값마다 무엇이 나오나

저장소의 showListQuerySchema에 쿼리 객체를 넣어 직접 실행한 결과다.

쿼리 결과 왜
(없음) 통과 { page: 1, size: 20 } 둘 다 기본값
?page=2 통과 { page: 2, size: 20 } 글자 '2'가 숫자 2로
?page=2&foo=x 통과 { page: 2, size: 20 } foo는 버려진다
?page=1e1 통과 { page: 10, size: 20 } Number('1e1')은 10. 값으로는 정수다
?page=%202 (앞에 공백) 통과 { page: 2, size: 20 } Number(' 2')는 2
?page=abc 400 page NaN
?page= (빈 값) 400 page 빈 값은 undefined가 아니라 ''이고, Number('')는 0
?page=0, ?page=1.5 400 page 1 미만, 정수 아님
?page=1&page=2 400 page 같은 키가 두 번이면 배열 ['1', '2']가 오고, Number(['1','2'])는 NaN
?page=1e30 400 page Number.MAX_SAFE_INTEGER를 넘는다
?size=500 400 size 100 초과

1e1과 ' 2'가 통과하는 것은 일부러 둔 결정이다. 값으로는 정수라 "정수가 아닌 page는 400"이라는 규칙에 맞고, 스토어가 API를 부르기 전에 ^[1-9]\d*$로 주소를 먼저 정리하므로 실제로 이런 값이 API에 오지 않는다.

exceptionFactory: 필드별 오류

exceptionFactory는 zod의 오류 목록(issues)을 우리 API의 오류 형식 (ProblemException)으로 바꾸는 번역기다. 직접 부르는 곳은 없고, 검사가 실패했을 때만 파이프가 부른다. 검사가 통과하면 아예 불리지 않는다.

왜 바꿔 끼우나

파이프의 기본 동작은 Nest의 BadRequestException을 던지는 것이다. 그 응답에는 ADR 0007의 code와 필드별 errors가 없다. 스토어는 모든 오류가 같은 Problem Details 형식으로 온다고 믿으므로, 예외를 만드는 함수를 바꿔 끼워 형식을 맞춘다.

누가 언제 부르나

  • GET /shows?page=abc&size=500 Nest가 쿼리를 { page: 'abc', size: '500' }로 만든다
    • pipe.transform(value, metadata) 전역 파이프. metadata.schema는 showListQuerySchema
      • schema['~standard'].validate(value) zod가 검사. 실패하면 { issues: [...] }
      • exceptionFactory(issues) 이 절 ProblemException을 만들어 돌려준다
      • throw 파이프가 돌려받은 예외를 던진다. 핸들러는 불리지 않는다
    • ProblemDetailsFilter 그 예외로 400 응답을 쓴다 (nest 04 문서)

코드

// apps/api/src/problem-details/validation.pipe.ts
export function createValidationPipe(): StandardSchemaValidationPipe {
  return new StandardSchemaValidationPipe({
    exceptionFactory: (issues) => {
      // 한 필드가 여러 규칙에 걸릴 수 있어 필드마다 처음 걸린 것 하나만 남긴다.
      const errors = new Map<string, FieldErrorDto>();           // ① 필드 이름 → 오류 하나
      for (const issue of issues) {
        const field = (issue.path ?? [])                          // ② 위치 배열. 예: ['page'], ['genre', 1]
          .map((segment) =>
            typeof segment === 'object' ? String(segment.key) : String(segment), // ③ 한 칸을 글자로
          )
          .join('.');                                             // ④ 점으로 잇기. 예: 'page', 'genre.1'
        if (!errors.has(field)) {                                 // ⑤ 이 필드가 처음이면
          errors.set(field, { field, detail: issue.message });    // ⑥ 저장
        }
      }
      return new ProblemException({                               // ⑦ 우리 형식의 예외
        status: HttpStatus.BAD_REQUEST,
        code: 'VALIDATION_FAILED',
        detail: '요청 값이 올바르지 않습니다.',
        errors: [...errors.values()],                             // ⑧ Map에 넣은 순서대로 배열로
      });
    },
  });
}

들어오는 값: issues

issues는 zod가 만든 배열이다. 항목마다 여러 속성이 있지만 이 함수는 두 개만 쓴다(전체 모양은 zod 00 문서).

속성 뜻 예
path 틀린 값의 위치. 속성 이름과 배열 순번을 바깥부터 차례로 담은 배열 ['page'], ['genre', 1]
message 스키마에 적은 문구 '1 이상의 정수여야 합니다.'

아래 세 예시는 저장소의 createValidationPipe()에 값을 넣어 실제로 실행한 결과다. 예시 2와 3은 지금 GET /shows에 없는 필드라, 뒤 티켓에서 붙을 검색어와 장르를 가정한 스키마로 돌렸다.

예시 1: 두 필드가 틀림

요청 GET /shows?page=abc&size=500. 들어오는 issues:

[
  { path: ['page'], message: '1 이상의 정수여야 합니다.' },
  { path: ['size'], message: '1 이상 100 이하의 정수여야 합니다.' },
]

두 필드가 서로 달라 둘 다 errors에 들어가고, 넣은 순서대로 배열이 되어 이 예외가 만들어진다:

new ProblemException({
  status: 400,
  code: 'VALIDATION_FAILED',
  detail: '요청 값이 올바르지 않습니다.',
  errors: [
    { field: 'page', detail: '1 이상의 정수여야 합니다.' },
    { field: 'size', detail: '1 이상 100 이하의 정수여야 합니다.' },
  ],
})

이 예외가 ProblemDetailsFilter를 거쳐 따라가기 절의 마지막 응답이 된다. errors 배열이 응답의 errors로 그대로 나간다.

예시 2: 한 필드가 규칙 두 개에 걸림 → Map이 하는 일

검색어 스키마 z.object({ q: z.string().max(3, '3자 이하').regex(/^[a-z]*$/, '소문자만') })에 { q: 'ABCDE' }를 넣었다. 다섯 글자이고 대문자라 두 규칙에 모두 걸린다. 

[
  { path: ['q'], message: '3자 이하' },
  { path: ['q'], message: '소문자만' },   // 같은 필드가 한 번 더
]

두 번째 issue는 errors.has('q')가 true라 건너뛴다. 결과: errors: [{ field: 'q', detail: '3자 이하' }].

Map을 쓴 이유가 이것이다. 키가 필드 이름이라 같은 필드는 처음 것만 남고, 응답의 errors가 "필드마다 하나"라는 약속을 지킨다. 그냥 배열에 push했다면 q가 두 번 들어가, 스토어가 필드 이름으로 오류를 찾을 때 어느 것을 보여 줄지 정해야 한다. 지금 GET /shows의 숫자 필드는 int()에서 멈춰 오류가 늘 하나지만(zod 00 문서), 파이프는 앞으로 붙을 모든 스키마에 쓰인다.

예시 3: 배열 안의 값 → join이 하는 일

장르 스키마 z.object({ genre: z.array(z.enum(['musical', 'play'], '모르는 장르')) })에 ?genre=musical&genre=x, 곧 { genre: ['musical', 'x'] }를 넣었다. 

[{ path: ['genre', 1], message: '모르는 장르' }]   // genre 배열의 1번째(0부터 셈) 값

path의 칸마다 String()을 씌우면 ['genre', '1'], 점으로 이으면 'genre.1'이다. 결과: errors: [{ field: 'genre.1', detail: '모르는 장르' }]. path가 배열인 이유는 위치가 여러 단계일 수 있어서다(객체 안의 배열 안의 값 등). 응답에서는 사람이 읽기 쉽게 점으로 이어 붙인다.

typeof segment === 'object'는 왜 있나

Standard Schema 규격에서는 path의 한 칸이 'page'나 1 같은 값일 수도 있고, { key: 'page' } 같은 객체일 수도 있다. 이 파이프는 zod만이 아니라 그 규격을 따르는 모든 검증 라이브러리를 받으므로, 객체로 오면 .key를 꺼낸다. 

String('page')            // 'page'
String(1)                 // '1'
String({ key: 'page' })   // '[object Object]'  ← .key를 꺼내지 않으면 이렇게 된다

zod는 위 실행 결과처럼 항상 값으로 주므로, 지금은 언제나 String(segment) 쪽으로 간다.

통과하면

GET /shows?page=2면 zod가 issues 없이 { value: { page: 2, size: 20 } }를 돌려주므로 exceptionFactory는 불리지 않는다. 파이프가 그 값을 돌려주고, 핸들러의 query로 들어간다.

왜 APP_PIPE인가

// apps/api/src/app.module.ts
providers: [
  { provide: APP_FILTER, useClass: ProblemDetailsFilter },
  { provide: APP_PIPE, useFactory: createValidationPipe },
],

main.ts에서 app.useGlobalPipes(createValidationPipe())로 붙여도 운영 앱은 똑같이 동작한다. 하지만 통합 테스트는 main.ts를 거치지 않고 AppModule로 앱을 따로 조립한다. main.ts에 붙이면 테스트 앱에는 파이프가 없어 ?page=abc가 검사 없이 핸들러까지 가고, 테스트는 운영과 다른 앱을 검증하게 된다. 예외 필터를 APP_FILTER로 등록한 것과 같은 이유다(nest 04 문서).

useClass가 아니라 useFactory인 이유: 파이프에 exceptionFactory 옵션을 넘겨 만들어야 하는데, useClass는 생성자 인자를 줄 수 없다. 팩토리 함수가 옵션을 넣어 new한 인스턴스를 돌려준다.

헷갈리기 쉬운 점

스키마를 안 붙이면 검사하지 않는다. 전역 파이프여도 metadata.schema가 없는 인자는 return value로 그냥 통과한다. @Query()만 쓰면 page는 글자 'abc' 그대로 핸들러에 들어오고, 타입 검사도 이를 잡지 못한다.

타입 주석은 검사가 아니다. query: ShowListQuery라고 적어도 실행 중에는 아무 일도 일어나지 않는다. 핸들러가 받는 값이 정말 그 모양이 되는 것은 파이프가 스키마로 바꿔 넣었기 때문이다.

transform을 끄면 검사만 하고 원래 값을 넘긴다. new StandardSchemaValidationPipe({ transform: false })면 마지막 줄이 value를 돌려준다. 검사는 통과해도 page는 글자이고, 기본값과 모르는 키 버리기도 적용되지 않는다.

파이프는 응답을 쓰지 않는다. 예외를 던질 뿐이고, 응답 모양은 예외 필터가 정한다. 그래서 검증 실패든 404든 500이든 모두 ProblemDetailsFilter 한곳에서 Problem Details로 나간다.

metadata.schema가 없으니 전역 파이프가 값을 그대로 넘긴다. 핸들러는 { page: 'abc' }를 받고, size도 기본값이 없어 undefined다. 서비스의 .limit(size)와 (page - 1) * size가 undefined와 NaN을 만나 DB 쿼리가 실패하거나 엉뚱하게 동작하고, 400이 아니라 500이 나갈 수 있다. 타입 검사는 ShowListQuery를 믿으므로 아무 경고도 하지 않는다.

2. 아래처럼 가드가 붙은 엔드포인트에 로그인하지 않고 ?page=abc를 보내면 401과 400 중 무엇이 오는가?

핸들러 앞의 네 단계의 순서를 묻는다. AuthGuard는 로그인하지 않았으면 401 예외를 던진다고 하자.

401이다. 가드가 파이프보다 먼저 실행되어 거기서 예외가 나므로, 파이프는 불리지 않는다. 그래서 로그인하지 않은 사람은 쿼리를 어떻게 보내도 입력 오류 정보를 얻지 못한다.

-    .default(1)
답 보기

400이 온다. page가 없으면 값은 undefined이고, z.coerce가 Number(undefined)로 NaN을 만들어 숫자 검사에서 실패한다. 스토어는 fetchShows가 언제나 page와 size를 보내므로 영향이 없지만, 쿼리 없이 부르는 다른 클라이언트(어드민, curl, 앞으로의 앱)는 모두 오류를 받는다. OpenAPI 문서의 default: 1도 사라진다. 기본값은 "생략할 수 있다"는 계약의 일부다.

4. 전역 파이프를 main.ts로 옮기면 어떤 테스트가 깨지는가?

왜 APP_PIPE인가를 묻는다.

// apps/api/src/app.module.ts
-    { provide: APP_PIPE, useFactory: createValidationPipe },
// apps/api/src/main.ts
+app.useGlobalPipes(createValidationPipe());
답 보기

shows.int.spec.ts의 "잘못된 쿼리 값은 필드별 오류를 담은 400 Problem Details로 응답한다"가 깨진다. 테스트 앱은 main.ts를 거치지 않아 파이프가 없으므로 ?page=abc가 핸들러까지 가서 400이 아닌 응답이 나온다. 같은 이유로 페이지 자르기 테스트도 page, size가 글자로 들어와 결과가 달라질 수 있다.

5. exceptionFactory에 아래 issues가 들어오면 응답의 errors는 무엇인가?

exceptionFactory 절의 ④⑤⑧을 묻는다.

[
  { path: ['size'], message: 'A' },
  { path: ['page'], message: 'B' },
  { path: ['size'], message: 'C' },
  { path: ['genre', 0], message: 'D' },
]
답 보기

[{ field: 'size', detail: 'A' }, { field: 'page', detail: 'B' }, { field: 'genre.0', detail: 'D' }]. 세 번째 issue는 size가 이미 있어 건너뛴다. Map은 처음 넣은 순서를 기억하므로 size, page, genre.0 순서로 나온다. ['genre', 0]은 'genre.0'이 된다.
