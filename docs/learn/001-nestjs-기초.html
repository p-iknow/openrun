NestJS 기초: 초기화된 파일 읽기

apps/api에 초기화된 파일을 읽는 데 필요한 개념을 정리한다. 기준 버전은 NestJS 12.4다.

한눈에 보기

조립 시점: 앱이 켜질 때
  1. main.ts
  2. AppModule
  3. ShowsModule
  4. ShowsController
  5. GET /shows 연결
  6. 3000번 포트 열기
요청 시점: 요청이 들어올 때
  1. GET /shows
  2. findAll() 실행
  3. [] 반환
  4. 200 + JSON 응답

기억할 내용은 두 가지다.

  • Nest는 AppModule에서 시작해 imports를 따라가며 앱을 조립한다.
  • 일은 조립 시점과 요청 시점으로 나뉜다. 문제가 어느 시점에 드러나는지 구분하면 원인을 찾기 쉽다.

Nest가 대신 해 주는 일

Nest 없이 Express로 같은 API를 만들면 대략 다음과 같다.

const app = express();                    // 앱 만들기
const controller = new ShowsController(); // 객체 만들기
app.get('/shows', (req, res) => {         // 주소와 함수 연결하기
  res.json(controller.findAll());         // 응답 보내기
});
app.listen(3000);                         // 요청 받기 시작

Nest에서는 이 일을 직접 쓰지 않고 데코레이터로 알려 준다. 그래서 코드 어디에도 new ShowsController()가 없다.

코드 Nest에 알려 주는 내용
@Module({ controllers: [ShowsController] }) 이 컨트롤러를 앱에 포함해 줘
@Controller('shows') + @Get() GET /shows를 이 메서드에 연결해 줘
NestFactory.create(AppModule) 이 모듈부터 따라가며 앱을 만들어 줘

데코레이터는 @로 시작하며, 클래스나 메서드에 정보를 붙인다. Nest는 시작할 때 이 정보를 읽어 앱을 조립한다.

앱이 동작하는 순서

조립 시점: 앱이 켜질 때

  1. 코드 실행 pnpm dev가 nest start --watch를 실행한다. Nest CLI가 tsc로 코드를 컴파일하고 main.ts의 결과물을 실행한다. --watch 때문에 파일을 고치면 이 과정이 다시 실행된다.
  2. main.ts: 조립 시작 
    const app = await NestFactory.create(AppModule);
    AppModule을 시작점으로 앱 조립을 시작한다.
  3. app.module.ts: 다음 모듈 찾기 
    @Module({
  imports: [ShowsModule],
})
export class AppModule {}
    imports를 보고 ShowsModule도 앱에 포함한다. 클래스 본문이 비어 있어도 정상이다. 필요한 내용은 데코레이터에 들어 있다.
  4. shows.module.ts: 컨트롤러 찾기 
    @Module({
  controllers: [ShowsController],
})
export class ShowsModule {}
    ShowsController를 찾아 인스턴스를 만든다. 생성자에서 요구하는 것이 없어 바로 만들 수 있다.
  5. main.ts: 주소 연결 후 요청 받기 
    await app.listen(3000);
    listen()은 초기화가 안 됐으면 init()을 먼저 실행한다. 이때 Nest가 데코레이터를 읽어 GET /shows와 findAll()을 연결한다. 그다음 3000번 포트를 열고 요청을 기다린다.

요청 시점: GET /shows가 들어올 때

  1. 요청 수신 Express가 요청을 받고, 조립 때 연결해 둔 findAll()을 호출한다. Nest는 기본 HTTP 서버로 Express를 쓴다. 그래서 @nestjs/platform-express를 직접 import하지 않아도 된다.
  2. shows.controller.ts: 메서드 실행 
    @Controller('shows')
export class ShowsController {
  @Get()
  findAll() {
    return [];
  }
}
    메서드는 빈 배열만 반환하고, HTTP 응답을 직접 다루지 않는다.
  3. 응답 전송 Nest가 반환값을 JSON으로 바꿔 상태 코드 200과 함께 보낸다. 그래서 클라이언트는 []를 받는다.

컨트롤러: 주소와 메서드 연결

@Controller의 경로와 @Get의 경로가 합쳐져 주소가 된다.

컨트롤러 메서드 주소
@Controller('shows') @Get() GET /shows
@Controller('shows') @Get('popular') GET /shows/popular

상태 코드의 기본값은 200이고, POST만 201이다.

모듈: 기능을 묶는 단위

@Module에는 네 가지 항목을 쓸 수 있다.

항목 의미 현재 사용
imports 가져올 다른 모듈 AppModule
controllers 이 모듈의 HTTP 진입점 ShowsModule
providers 이 모듈 안에서 주입할 수 있는 객체 없음
exports 다른 모듈에 공개할 프로바이더 없음

파일이 있어도 모듈에 등록하지 않으면 Nest는 그 존재를 모른다.

프로바이더와 DI: 아직 코드에 없지만 곧 필요한 개념

컨트롤러는 요청을 받고, 실제 일은 보통 서비스에 맡긴다. 이때 서비스 객체를 직접 만들지 않고 생성자에 필요하다고 적기만 한다. 이렇게 필요한 객체를 밖에서 넣어 주는 방식이 DI(의존성 주입)이고, Nest가 만들어 넣어 주는 객체가 프로바이더다. 

@Injectable()
export class ShowsService {
  findAll() {
    return [];
  }
}

@Controller('shows')
export class ShowsController {
  constructor(private readonly shows: ShowsService) {}
}

@Module({
  controllers: [ShowsController],
  providers: [ShowsService], // Nest가 만들어서 필요한 곳에 넣어 줌
})
export class ShowsModule {}

다른 모듈의 프로바이더 쓰기

프로바이더는 기본적으로 등록한 모듈 안에서만 보인다. 다른 모듈에서 쓰려면 두 가지가 모두 필요하다.

  • 제공하는 쪽: exports에 넣어 공개한다.
  • 사용하는 쪽: 그 모듈을 imports에 넣는다.
@Module({
  providers: [ShowsService],
  exports: [ShowsService], // 공개
})
export class ShowsModule {}

@Module({
  imports: [ShowsModule], // 가져오기
  controllers: [ReviewsController],
})
export class ReviewsModule {}

ReviewsModule의 providers에 ShowsService를 넣어 해결하면 안 된다. 오류는 사라지지만 모듈마다 인스턴스가 따로 생겨서, 서비스가 상태를 가지면 값이 서로 달라질 수 있다.

import type으로 가져오면 주입되지 않는다

import type { ShowsService }는 컴파일 후 지워져서 런타임에 클래스 정보가 남지 않는다. 그러면 Nest가 무엇을 주입할지 알 수 없다. tsc는 타입만 보기 때문에 이 문제를 잡지 못한다. 자세한 내용은 docs/stage-notes/01-풀스택-기본.md에 있다.

어떤 문제가 언제 드러나는가

상황 실패 시점 결과
모듈을 imports에서 뺌 요청 시점 앱은 켜지고 404 응답
컨트롤러를 controllers에서 뺌 요청 시점 앱은 켜지고 404 응답
서비스를 providers에 넣지 않음 조립 시점 앱이 켜지지 않음
서비스를 exports에 넣지 않음 조립 시점 앱이 켜지지 않음

디버깅은 다음 순서로 시작한다.

  • 앱이 안 켜지면: 조립 단계를 본다. 생성자에서 요구하는 프로바이더의 providers, exports, imports를 확인한다.
  • 앱은 켜졌는데 404가 나면: imports와 controllers에 등록이 빠졌는지, 주소가 맞는지 확인한다.

조립에 실패하면 다음과 같은 오류가 난다. ?는 찾지 못한 생성자 인자의 위치를 뜻한다. 

Nest can't resolve dependencies of the ReviewsController (?).
Please make sure that the argument ShowsService at index [0]
is available in the ReviewsModule module.

테스트: test/shows.int.spec.ts

테스트도 같은 흐름을 따른다. 다만 listen(3000)을 호출하지 않는다.

Test.createTestingModule({ imports: [AppModule] }).compile(); // 모듈 그래프 조립
moduleRef.createNestApplication();                            // 앱 인스턴스 생성
app.init();                                                   // 주소 연결, 포트는 열지 않음
request(app.getHttpServer()).get('/shows');                   // HTTP 요청
  • 포트: app.getHttpServer()는 아직 포트를 열지 않은 서버 객체를 돌려준다. supertest가 이 서버를 임시 포트로 직접 열어 요청을 보낸다.
  • 검증 범위: 컨트롤러 메서드만 호출하지 않고 앱 전체를 조립한다. 그래서 라우팅과 모듈 연결까지 검증한다.
  • 정리: 테스트마다 app.close()로 앱을 닫는다.
  • DB: 프로바이더를 가짜로 바꾸지 않고, Testcontainers로 띄운 실제 PostgreSQL에 연결한다. 그래서 pnpm test가 아니라 pnpm test:integration으로 실행한다. 연결 구조는 004 문서에 있다.

Nest가 아니라 ESM 때문에 낯선 부분

이 프로젝트는 "type": "module"과 module: nodenext를 쓴다.

  • .js 확장자: .ts 파일을 import해도 경로에는 .js를 쓴다.
  • 최상위 await: bootstrap() 함수로 감싸지 않아도 await를 쓸 수 있다.

설정 파일

파일 역할
nest-cli.json 소스 위치를 src로 정하고, 빌드 전에 dist를 비운다. 빌더를 지정하지 않아 기본값인 tsc를 쓴다.
tsconfig.json 공통 TypeScript 설정이다. pnpm typecheck가 쓰며, test까지 검사한다.
tsconfig.build.json Nest CLI가 우선 쓰는 빌드 설정이다. src만 빌드해서 결과물이 dist/main.js에 생긴다.
vitest.config.ts 테스트 설정이다. 코드를 Vite 기본 변환기(Oxc)로 변환한다.
  • 컴파일러가 둘이다: 빌드는 tsc, 테스트는 Vite의 Oxc를 쓴다. Oxc는 파일 하나씩 변환해 타입 정보가 없으므로, import type으로 받은 클래스와 enum의 메타데이터가 tsc와 다르게 나온다.
  • experimentalDecorators: Nest가 쓰는 데코레이터 문법을 켠다.
  • emitDecoratorMetadata: 생성자 인자 타입을 런타임에 남긴다. DI가 이 정보를 쓴다.
  • reflect-metadata: 데코레이터 정보를 저장하는 라이브러리다. @nestjs/core와 @nestjs/common이 내부에서 import해서 직접 불러오지 않아도 된다.

지금은 건너뛰어도 되는 것

파이프, 가드, 인터셉터, 예외 필터, 미들웨어는 현재 코드에 없다. 입력 검증이나 인증을 구현할 때 배워도 된다. rxjs도 현재 코드에서 직접 쓰지 않는다.

스스로 확인하기

질문에 먼저 답해 본 뒤, 눌러서 답을 확인한다.

1. @Controller('shows')에 @Get('popular')를 추가하면 주소는 무엇인가?

GET /shows/popular다.

2. ShowsModule을 AppModule의 imports에서 빼면 어떻게 되는가?

앱은 켜지고, GET /shows는 404가 된다.

3. 테스트가 listen()을 호출하지 않는데 HTTP 요청이 되는 이유는 무엇인가?

supertest가 서버를 임시 포트로 직접 열기 때문이다.

4. 생성자에서 요구하는 ShowsService가 providers에 없으면 어떻게 되는가?

조립 시점에 실패해 앱이 켜지지 않는다. 테스트에서는 compile()에서 실패한다.

5. ShowsModule을 import했는데 ShowsService를 주입하지 못하면 무엇을 봐야 하는가?

ShowsModule의 exports에 ShowsService가 있는지 본다.
