의존성 주입(DI): 무엇을 해결하고 무엇을 내주는가

  • nestjs

DI가 없을 때의 문제에서 출발해, 손으로 DI를 해 보고, 그 조립을 Nest에 맡기면 무엇을 얻고 무엇을 내주는지 살펴본다. 기준 버전은 NestJS 12.4, TypeScript 6.0이다. 데코레이터와 메타데이터는 002 문서에서 다뤘다.

한눈에 보기

DI(의존성 주입)는 객체를 쓰는 일과 객체를 만들고 연결하는 일을 나누는 방식이다. 필요한 객체를 안에서 new로 만들지 않고 밖에서 받는다.

DI 없이: 서비스가 다 한다
  1. 서비스 안에서 new Database()
  2. 만드는 방법까지 서비스가 앎
  3. 밖에서 바꿔 끼울 수 없음
DI: 만드는 곳과 쓰는 곳이 나뉜다
  1. 바깥에서 new Database()
  2. 생성자로 전달
  3. 서비스는 쓰기만 함

이 문서에서 가장 먼저 구분할 것은 세 가지 말이다.

말 뜻 예
DI 필요한 것을 밖에서 받는 설계 방식. 프레임워크가 필요 없다. new SeatHoldService(db, mailer)
조립 객체를 순서대로 만들어 서로 연결하는 일. 누군가는 해야 한다. 앱 시작 파일에서 new로 객체를 만들고 넘기는 코드
DI 컨테이너 조립을 대신 해 주는 코드. Nest에 들어 있다. @Module의 providers

그래서 문서도 두 부분으로 나뉜다.

부분 질문 절
1부 DI를 왜 쓰는가 DI 없는 코드의 문제 → 손으로 하는 DI → db.ts와 비교 → 숨은 의존성 → 주입할 값과 인자로 넘길 값
2부 조립까지 Nest에 맡기면 무엇을 얻고 내주는가 조립을 Nest에 맡기기 → Hono와 비교 → 비용 1~3과 해법 → 언제 쓰는가

1부는 프레임워크 없이 진행한다. DI 자체는 Nest 없이도 쓸 수 있기 때문이다.

DI 없는 코드의 문제

좌석 선점 기능으로 시작한다. 좌석 선점은 결제 전까지 회차 좌석을 한 사용자에게 임시로 묶어 두는 일이다. 예제에 쓸 부품 두 개를 먼저 정의한다. 데이터베이스와 메일 발송은 설명을 위해 단순하게 줄였다. 

// database.ts
export class Database {
  constructor(readonly url: string) {
    // 실제로는 여기서 url로 연결 풀을 만든다
  }

  async query(sql: string, params: unknown[]): Promise<void> {
    // sql을 실제 데이터베이스에서 실행한다
  }
}

// mailer.ts
export class Mailer {
  async send(to: string, text: string): Promise<void> {
    // 실제 메일을 보낸다
  }
}

서비스가 필요한 객체를 직접 만들면 이렇게 된다.

export class SeatHoldService {
  private db = new Database(process.env.DATABASE_URL!);
  private mailer = new Mailer();

  async hold(performanceSeatId: string, userId: string) {
    await this.db.query(
      'UPDATE performance_seats SET held_by = $1 WHERE id = $2',
      [userId, performanceSeatId],
    );
    await this.mailer.send(userId, `${performanceSeatId} 좌석을 선점했습니다`);
  }
}

짧고 읽기 쉽다. 문제는 코드가 자라면서 네 가지로 나타난다.

문제 1: 테스트가 실제 데이터베이스와 메일을 건드린다

const service = new SeatHoldService(); // 실제 Database와 Mailer가 만들어진다
await service.hold('A-1', 'user-1');   // 실제 UPDATE, 실제 메일 발송

db는 서비스 안에서 만들어지므로, 클래스 밖에서는 다른 객체를 넣을 방법이 없다. 테스트마다 실제 데이터베이스가 필요하고, 실제 메일을 막을 길도 따로 찾아야 한다.

문제 2: 만드는 방법이 여러 곳에 흩어진다

OrderService, ShowsService도 데이터베이스가 필요하면 같은 줄을 반복한다. 

private db = new Database(process.env.DATABASE_URL!); // 서비스마다 반복

나중에 Database 생성자에 연결 수 제한 인자를 추가하면 이 줄을 모두 고쳐야 한다. 쓰는 곳이 만드는 방법까지 알기 때문이다.

문제 3: 공유해야 할 객체가 공유되지 않는다

데이터베이스 연결은 만드는 데 시간이 걸려서, 미리 몇 개 열어 두고 돌려 쓴다. 이 묶음이 연결 풀이다. PostgreSQL의 동시 연결 한도(max_connections)는 기본 100개이고, Node.js 드라이버 pg의 풀은 기본 최대 10개까지 연다.

new Database()마다 풀이 하나씩 생긴다면, 서비스 10개가 각자 하나씩 만들 때 연결 수는 이렇게 달라진다.

서버 수 풀 하나를 공유 서비스마다 풀 PostgreSQL 한도 100과 비교
1대 최대 10개 최대 100개 서비스마다 풀이면 한도에 닿음
4대 최대 40개 최대 400개 서비스마다 풀이면 한도의 4배

풀은 필요할 때 연결을 늘리기 때문에 평소에는 드러나지 않는다. 트래픽이 몰리는 티켓 오픈 순간에 연결을 더 열지 못해 실패한다. 게다가 한 서비스의 풀에 빈 연결이 남아 있어도 다른 서비스가 빌려 쓸 수 없다.

문제 4: 무엇이 필요한지 밖에서 보이지 않는다

const service = new SeatHoldService();

이 줄만 보면 아무것도 필요 없는 객체 같다. 실제로는 데이터베이스, 환경 변수, 메일 서버가 필요하다. 이렇게 사용하는 쪽에서 보이지 않는 의존 관계를 숨은 의존성이라 한다. 안을 읽어야만 알 수 있다.

손으로 하는 DI

프레임워크 없이, 위 코드를 조금씩 바꿔 본다.

1단계: 생성자로 받기

필드에서 new를 지우고 값을 생성자로 받는다.

export class SeatHoldService {
  private readonly db: Database;
  private readonly mailer: Mailer;

  constructor(db: Database, mailer: Mailer) {
    this.db = db;
    this.mailer = mailer;
  }

  // hold()는 그대로
}

TypeScript에는 이 패턴을 줄여 쓰는 문법이 있다. 생성자 인자에 private readonly를 붙이면 필드 선언과 대입을 대신 해 준다. 위 코드와 아래 코드는 같다. 

export class SeatHoldService {
  constructor(
    private readonly db: Database,
    private readonly mailer: Mailer,
  ) {}

  // hold()는 그대로
}

이것이 DI의 전부다. 서비스는 이제 Database를 어떻게 만드는지 모른다.

2단계: 한곳에서 조립하기

new가 사라진 것은 아니다. 앱이 시작되는 파일로 옮겨 왔다. 이렇게 객체를 모아서 연결하는 한곳을 컴포지션 루트(composition root)라고 부른다. 

// main.ts
const db = new Database(process.env.DATABASE_URL!);
const mailer = new Mailer();
const seatHolds = new SeatHoldService(db, mailer);
const orders = new OrderService(db); // 같은 db를 함께 쓴다

3단계: 테스트에서 가짜 넣기

생성자로 받으므로 테스트에서는 가짜를 넣으면 된다. 아래 as unknown as Database는 "모양이 완전히 같지 않아도 이 타입으로 취급하라"는 단언이다. 테스트에 필요한 메서드만 만들기 위해 쓴다. 

const calls: unknown[][] = [];
const fakeDb = {
  query: async (_sql: string, params: unknown[]) => {
    calls.push(params); // 실행 대신 인자만 기록한다
  },
} as unknown as Database;
const fakeMailer = { send: async () => {} } as unknown as Mailer;

const service = new SeatHoldService(fakeDb, fakeMailer);
await service.hold('A-1', 'user-1');

console.log(calls); // [ [ 'user-1', 'A-1' ] ]

네 문제가 어떻게 되었나

문제 지금
테스트 가짜를 생성자로 넣는다. 파일을 통째로 가짜로 바꾸는 도구가 필요 없다.
흩어진 생성 방법 new Database가 main.ts 한 줄에 모인다.
공유 같은 db를 여러 서비스에 넘긴다.
숨은 의존성 생성자를 보면 필요한 것이 나온다.

여기까지 Nest도 데코레이터도 쓰지 않았다. DI와 DI 컨테이너는 다르다. Hono나 Express에서도 이렇게 DI를 쓸 수 있다.

db.ts로도 되지 않나

파일에서 객체를 하나 만들어 내보내는 db.ts 방식으로도 연결 풀 공유와 테스트는 된다. 테스트에서는 vi.mock으로 파일을 통째로 가짜로 바꾸면 된다. 그래서 생성자 DI의 이득은 "불가능을 가능하게 함"이 아니라 의존 관계가 드러나고 교체가 쉬워짐이다. 그 이득은 코드와 사람이 늘수록 커진다.

선택 읽기: db.ts 방식과 생성자 DI 비교

JavaScript를 쓰다 보면 자연스럽게 나오는 반론이다. 파일에서 객체를 하나 만들어 내보내면 어떨까? ES 모듈은 한 번만 실행되므로 이 객체는 앱 전체에서 하나다. 

// db.ts
export const db = new Database(process.env.DATABASE_URL!);

// seat-hold.service.ts
import { db } from './db.js';
import { mailer } from './mailer.js';

export async function hold(performanceSeatId: string, userId: string) {
  await db.query(/* ... */);
  await mailer.send(/* ... */);
}

테스트도 가능하다. vi.mock은 파일을 통째로 가짜로 바꿔 준다.

vi.mock('./db.js', () => ({ db: { query: vi.fn() } }));

즉 "DI가 없으면 테스트할 수 없다"는 JavaScript에서는 과장이다. 비교하면 차이는 생각보다 좁다.

항목 db.ts 방식 생성자 DI
연결 풀 공유 해결 해결
생성 방법 모으기 해결 해결
테스트 교체 단위 파일 단위. 테스트 파일 전체에 적용 객체 단위. 테스트마다 다른 가짜를 넣기 쉬움
의존성이 보이는 곳 파일 위쪽 import 생성자 시그니처
의존성을 빠뜨렸을 때 테스트에서 실제 객체가 그대로 실행될 수 있음 직접 new를 쓰면 컴파일 오류
생성·종료 순서 파일을 불러오는 순서에 묶임. 종료는 직접 구현 조립 코드나 컨테이너에서 정함
트랜잭션 인자 전달 또는 AsyncLocalStorage 같음

다음 절이 그중 가장 큰 이득인 숨은 의존성을 자세히 본다.

숨은 의존성

앞 절의 결론은 "생성자 DI의 남는 이득은 의존 관계가 드러나는 것"이었다. 처음에 본 문제 4, 무엇이 필요한지 밖에서 보이지 않는 문제가 바로 이것이다. 이 절에서는 세 가지를 본다.

  1. 의존 관계가 드러나면 실제로 무엇이 달라지는가
  2. 드러난다고 해도 어디까지 보이는가
  3. 그렇다면 무엇을 생성자로 받아야 하는가

메일 기능을 추가한 날

처음에는 hold가 데이터베이스만 썼고, 테스트도 그때 썼다. 나중에 메일 발송을 추가했다. 테스트는 고치지 않았다. 두 방식에서 각각 무슨 일이 생기는지 본다. 아래 결과는 실제로 실행해 확인했다.

db.ts 방식: 테스트가 통과하고 실제 메일이 나간다

// seat-hold.service.ts: 메일 발송을 추가한 뒤
import { db } from './db.js';
import { mailer } from './mailer.js'; // 새로 추가

export async function hold(performanceSeatId: string, userId: string) {
  await db.query(/* ... */);
  await mailer.send(userId, `${performanceSeatId} 좌석을 선점했습니다`); // 새로 추가
}

// seat-hold.service.spec.ts: 메일 추가 전에 쓴 그대로
vi.mock('./db.js', () => ({ db: { query: vi.fn() } })); // db만 가짜로 바꾼다

it('좌석을 선점한다', async () => {
  await hold('A-1', 'user-1'); // 통과한다. 그런데 실제 mailer.send가 실행된다
});

테스트 파일은 mailer의 존재를 모른다. ./mailer.js는 가짜로 바꾸지 않았으니 진짜가 그대로 쓰인다. 아무 경고도 없다.

생성자 DI 방식: 컴파일러가 멈춰 세운다

// seat-hold.service.ts: 메일 발송을 추가한 뒤
export class SeatHoldService {
  constructor(
    private readonly db: Database,
    private readonly mailer: Mailer, // 새로 추가
  ) {}

  // hold()에서 this.mailer.send(...)를 호출한다
}

// seat-hold.service.spec.ts: 메일 추가 전에 쓴 그대로
it('좌석을 선점한다', async () => {
  const service = new SeatHoldService(fakeDb); // 컴파일 오류
  await service.hold('A-1', 'user-1');
});
error TS2554: Expected 2 arguments, but got 1.

생성자에 인자가 하나 늘었으니, 인자를 하나만 넘기는 기존 테스트는 컴파일되지 않는다. 테스트를 고치려면 Mailer에 무엇을 넣을지 정해야 하고, 그때 가짜를 넣게 된다.

같은 변경인데 한쪽은 실제 메일이 나가고, 한쪽은 컴파일러가 막는다. 의존 관계가 숨어 있느냐 드러나 있느냐의 차이다.

생성자는 설계 신호도 된다. 생성자 인자가 여덟 개라면 그 서비스가 너무 많은 일을 한다는 뜻일 수 있다. 내부의 import로 흩어져 있으면 이 신호를 놓치기 쉽다.

이 이득의 한계

  • import도 힌트는 된다. 파일 맨 위를 보면 어느 정도 알 수 있다. 다만 그것을 실제로 쓰는지, 무엇을 교체해야 하는지까지는 말해 주지 않는다.
  • 직접 의존성만 보인다. 생성자에 OrderService가 있으면, 그 안에 무엇이 있는지는 또 들어가 봐야 한다.
  • 컴파일 오류는 직접 new할 때만 난다. Nest 테스트 모듈로 조립하면 등록된 실제 객체가 조용히 주입된다. 비용 1에서 다시 본다.
  • DI를 써도 전역은 숨을 수 있다. 아래 코드가 그렇다.

DI를 썼는데도 남은 숨은 의존성

logger는 다른 파일이 내보내는 객체이고, HOLD_MINUTES는 선점 유지 시간을 정하는 환경 변수라고 하자. 

import { logger } from './logger.js';

export class SeatHoldService {
  constructor(private readonly db: Database) {}

  async hold(performanceSeatId: string, userId: string) {
    const minutes = Number(process.env.HOLD_MINUTES);
    const expiresAt = new Date(Date.now() + minutes * 60_000);

    logger.info(`선점: ${performanceSeatId}`);
    await this.db.query(/* expiresAt을 저장 */);
  }
}

생성자에는 db만 있지만, 실제로는 process.env, 현재 시각, logger에도 의존한다. 그렇다고 전부 주입할 필요는 없다. 판단 기준은 세 가지다.

  • 테스트에서 실제로 실행되면 곤란한가?
  • 결과를 좌우하는데 다른 방법으로 제어하기 어려운가?
  • 환경에 따라 다른 구현이 필요한가?
대상 판단 이유
process.env 설정 객체로 주입 값이 없으면 Number(undefined)가 NaN이 되어 요청 처리 중에야 드러난다. 설정 객체에 모으면 앱 시작 때 검증할 수 있다.
new Date 먼저 fake timer vi.setSystemTime으로 제어할 수 있다. 시간 계산이 핵심인 도메인이 되면 그때 Clock을 주입한다.
logger 대개 주입하지 않음 실행되어도 곤란하지 않고 결과도 바꾸지 않는다. 로그 내용 자체가 요구 사항일 때만 다시 생각한다.
Mailer 주입 테스트에서 실제로 나가면 곤란하고, 환경마다 구현이 달라질 수 있다.

주입할 값, 인자로 넘길 값

앞 절에서는 무엇을 생성자로 받을지 봤다. 이 절은 그 반대로, 생성자로 받으면 안 되는 값을 본다. 기준은 그 값을 언제까지 쓰느냐다.

DI는 만능 전달 수단이 아니다. 앱이 켜져 있는 동안 계속 쓰는 객체에 맞고, 작업 한 번에만 쓰는 값에는 맞지 않는다. 이 구분을 놓치면 뒤의 비용 2에서 보듯 요청끼리 값이 섞인다.

값 수명 전달 방법
Database, Mailer, 설정 객체 앱이 켜져 있는 동안 생성자 주입
사용자 ID, 회차 좌석 ID 요청 하나를 처리하는 동안 메서드 인자
트랜잭션 작업 하나를 처리하는 동안 메서드 인자 또는 AsyncLocalStorage

트랜잭션이 대표적인 예다

좌석 선점과 주문 생성을 함께 성공시키거나 함께 되돌리려면 두 쿼리가 같은 연결 위에서 실행되어야 한다. 풀에서 각자 연결을 꺼내면 같은 트랜잭션이 아니다. 아래 transaction은 설명용 메서드다. 연결 하나를 잡아 그 연결에 묶인 tx를 콜백에 넘기고, 콜백이 끝나면 커밋하고 오류가 나면 되돌린다. 

export class CheckoutService {
  constructor(
    private readonly db: Database,        // 앱 전체에 하나 → 주입
    private readonly seatHolds: SeatHoldService,
    private readonly orders: OrderService,
  ) {}

  async checkout(performanceSeatId: string, userId: string) {
    await this.db.transaction(async (tx) => {
      await this.seatHolds.hold(tx, performanceSeatId, userId); // 작업 하나 → 인자
      await this.orders.create(tx, performanceSeatId, userId);
    });
  }
}

인자를 계속 넘기기 번거로우면 AsyncLocalStorage로 비동기 흐름 전체에서 꺼내 쓸 수 있다. 다만 이때는 tx가 함수 시그니처에서 사라지므로 또 하나의 숨은 의존성이 된다.

조립을 Nest에 맡기기

여기까지는 프레임워크 없이 DI를 봤다. 이제 문서의 두 번째 질문으로 넘어간다. 손으로 쓰던 조립 코드를 Nest에 맡기면 어떻게 되는가?

Nest의 providers, useFactory, exports, @Inject는 새로운 개념이 아니다. 앞에서 손으로 쓴 new 조립 코드를 Nest 방식으로 옮겨 적는 방법이다. 대신 new가 내 코드에서 사라지면서 생기는 비용이 있고, 그것은 뒤의 비용 절에서 본다.

먼저 왜 맡기고 싶어지는지부터 본다. 손으로 하는 조립은 명확하지만, 클래스가 늘면 이런 일이 생긴다.

const db = new Database(process.env.DATABASE_URL!);
const mailer = new Mailer();
const seatHolds = new SeatHoldService(db, mailer);
const orders = new OrderService(db);
const checkout = new CheckoutService(db, seatHolds, orders);
// ... 클래스가 늘어날 때마다 이어진다
  • 필요한 것이 먼저 만들어지도록 순서를 직접 맞춰야 한다.
  • 생성자 인자가 바뀌면 조립 코드도 같이 고쳐야 한다.

그런데 "누가 무엇을 필요로 하는가"는 이미 생성자에 적혀 있다. Nest는 그 기록을 읽어 이 코드를 대신 실행한다. 위 코드를 한 줄씩 Nest로 옮겨 보자. 뒤로 갈수록 경우가 어려워진다.

단계 손으로 쓸 때 Nest에서
1. 클래스만 필요한 객체 new SeatHoldService(mailer) providers + 생성자
2. 문자열이 필요한 객체 new Database(url) useFactory
3. 여러 곳에서 함께 쓰는 객체 같은 db 변수를 전달 exports + imports
4. 인터페이스로 받는 객체 new SeatHoldService(clock) @Inject(토큰)
5. 앱을 끌 때 정리 순서를 정해 직접 호출 onModuleDestroy

1단계: 클래스만 필요한 객체

데이터베이스는 다음 단계에서 붙이고, 우선 Mailer만 받는 서비스로 시작한다. 손으로는 이렇게 쓴다. 

const mailer = new Mailer();
const seatHolds = new SeatHoldService(mailer);

Nest에서는 new를 지우고, 만들 클래스를 providers에 적는다.

@Injectable()
export class Mailer {}

@Injectable()
export class SeatHoldService {
  constructor(private readonly mailer: Mailer) {}
}

@Module({
  providers: [SeatHoldService, Mailer],
})
export class SeatHoldModule {}

앱이 시작되면 Nest가 SeatHoldService의 생성자 기록에서 Mailer가 필요하다는 것을 읽고, Mailer를 먼저 만들어 넘긴다. @Injectable()은 이 기록이 남게 하는 표시다. 이렇게 providers에 적어 Nest가 만들어 주는 객체를 프로바이더라 부른다. Nest가 기록을 읽는 자세한 과정은 002의 "세 번의 읽기"에 있다.

providers: [Mailer]는 사실 아래를 줄인 것이다.

providers: [{ provide: Mailer, useClass: Mailer }]

provide는 찾을 때 쓰는 이름표이고, useClass는 그 이름표로 만들 클래스다. 생성자에 Mailer가 적혀 있으면 Nest는 Mailer라는 이름표로 객체를 찾는다. 이름표와 내용물이 나뉘어 있어서 2단계와 4단계가 가능하다.

2단계: 문자열이 필요한 객체

이번에는 Database를 옮긴다.

const db = new Database(process.env.DATABASE_URL!);

providers: [Database]로는 안 된다. 인자가 URL 문자열인데, 문자열은 Nest가 찾을 수 있는 프로바이더가 아니기 때문이다. 이때는 만드는 코드를 함수로 직접 등록한다. useFactory가 그 함수이고, inject에 적은 프로바이더가 함수의 인자로 들어온다. 

@Injectable()
export class AppConfig {
  readonly databaseUrl = process.env.DATABASE_URL!;
}

@Module({
  providers: [
    AppConfig,
    {
      provide: Database, // 이름표
      inject: [AppConfig],
      useFactory: (config: AppConfig) => new Database(config.databaseUrl),
    },
  ],
})
export class DatabaseModule {}

손으로 쓴 new Database(...)가 함수 안으로 그대로 들어갔다. Database를 쓰는 서비스는 생성자에 Database만 적으면 되고, 어떻게 만들어지는지는 몰라도 된다.

3단계: 여러 곳에서 함께 쓰는 객체

손으로 조립할 때는 같은 변수를 넘겨서 연결 풀을 공유했다.

const seatHolds = new SeatHoldService(db, mailer);
const orders = new OrderService(db); // 같은 db

Nest의 프로바이더는 기본적으로 앱에 하나만 만들어져 공유된다. 다만 등록한 모듈 안에서만 보이므로, 다른 모듈에서 쓰려면 주는 쪽의 exports와 받는 쪽의 imports가 모두 필요하다. 2단계의 DatabaseModule에 exports를 추가한다. 

@Module({
  providers: [AppConfig, /* 2단계의 Database 등록 */],
  exports: [Database], // 다른 모듈에 공개
})
export class DatabaseModule {}

@Module({
  imports: [DatabaseModule], // Database를 받아 온다
  providers: [SeatHoldService, Mailer],
  exports: [SeatHoldService], // Mailer는 공개하지 않아 이 모듈 안에만 남는다
})
export class SeatHoldModule {}

@Module({
  imports: [DatabaseModule], // 같은 Database 객체를 받는다
  providers: [OrderService],
})
export class OrderModule {}

이 공개 범위는 손 조립이나 db.ts에는 없던 것으로, Nest를 쓰면 새로 생기는 경계다. 자세한 사용법은 001 문서에 있다.

exports 대신 두 모듈의 providers에 각각 적으면 오류 없이 객체가 두 개 만들어지고, 연결 풀도 두 개가 된다.

4단계: 인터페이스로 받는 객체

손으로 조립할 때는 인터페이스로 받아도 문제가 없다. 넘기는 값을 컴파일러가 확인해 주기 때문이다. 

interface Clock {
  now(): number;
}

class SeatHoldService {
  constructor(private readonly clock: Clock) {}
}

new SeatHoldService({ now: () => Date.now() });

Nest에서는 생성자에 적힌 타입을 이름표로 쓰는데, 인터페이스는 컴파일 후 사라져 Object로 기록된다. 찾을 이름표가 없는 셈이다. 그래서 런타임에도 남는 값으로 이름표를 만들고, @Inject로 직접 적어 준다. 

const CLOCK = Symbol('CLOCK'); // 런타임에 남는 이름표

@Injectable()
export class SeatHoldService {
  constructor(
    @Inject(CLOCK)
    private readonly clock: Clock,
  ) {}
}

@Module({
  providers: [
    SeatHoldService,
    { provide: CLOCK, useValue: { now: () => Date.now() } },
  ],
})
export class SeatHoldModule {}

5단계: 앱을 끌 때 정리

앱을 끌 때는 연결 풀을 닫아야 한다. 서비스가 아직 쿼리를 쓰는 중에 닫으면 안 되므로 순서가 중요하다. 손으로 조립하면 이 순서도 직접 맞춰야 한다. Nest에서는 클래스에 onModuleDestroy 메서드를 만들어 두면 앱이 닫힐 때 호출해 준다. 

export class Database implements OnModuleDestroy {
  async onModuleDestroy() {
    // 연결 풀을 닫는다
  }
}

SeatHoldService가 Database에 의존하고 둘 다 이 메서드를 구현했을 때의 실행 결과다. providers 순서를 바꾸거나 두 모듈로 나눠도 결과는 같았다.

시점 첫 번째 두 번째
앱 시작: 생성자 Database SeatHoldService
app.close(): onModuleDestroy SeatHoldService Database

필요한 것을 먼저 만들고, 닫을 때는 반대로 닫는다. 이 동작은 app.close()를 호출할 때의 결과다. 프로세스 종료 신호에도 반응하게 하려면 app.enableShutdownHooks()를 호출한다.

다섯 단계를 거치면서 조립 코드의 new가 모두 내 코드에서 사라졌다. 조립은 이제 Nest가 한다. 다음 절에서는 Hono와 나란히 놓고 그 결과 무엇이 안 보이게 됐는지 본다.

Hono와 나란히 보기

같은 기능을 Hono와 Nest로 쓴다. Hono 쪽도 DI를 쓰고 있다는 점에 주목하자. 두 코드의 차이는 DI가 아니라 조립과 연결을 누가 하느냐다. 

// Hono: 조립과 연결이 눈앞에 있다
const db = new Database(process.env.DATABASE_URL!);
const mailer = new Mailer();
const seatHolds = new SeatHoldService(db, mailer);

const app = new Hono();

app.post('/seat-holds', async (c) => {
  const body = await c.req.json();
  await seatHolds.hold(body.performanceSeatId, body.userId);
  return c.json({ ok: true });
});
// Nest: 표시만 하고, 조립과 연결은 프레임워크가 한다
@Controller('seat-holds')
export class SeatHoldController {
  constructor(private readonly seatHolds: SeatHoldService) {}

  @Post()
  async create(@Body() body: { performanceSeatId: string; userId: string }) {
    await this.seatHolds.hold(body.performanceSeatId, body.userId);
    return { ok: true };
  }
}

Hono에서는 내 코드가 프레임워크를 호출한다. Nest에서는 프레임워크가 내 코드를 호출한다. 이것을 제어의 역전이라 한다. Nest 코드가 잘 안 보인다고 느끼는 이유는 이 때문이다.

일 Hono, Express Nest
객체 생성 new를 직접 호출 providers와 생성자를 보고 Nest가 호출
주소 연결 app.post(...) 호출 @Post()를 읽어 Nest가 호출
응답 c.json(...) 호출 메서드 반환값을 Nest가 응답으로 보냄
처리 단계 app.use를 쓴 순서대로 Nest가 정한 단계 순서대로
코드 시작 지점 파일 맨 위에서 따라 읽음 요청이 오면 메서드가 불림
구조 직접 설계. 사람마다 다를 수 있음 모듈 구조가 정해져 있음

안 보일 때 어디를 보나

Nest에서 코드 흐름을 찾을 때는 "어디서 호출하나" 대신 아래 질문으로 바꿔 찾는다.

질문 볼 곳
이 클래스는 무엇이 필요한가? 생성자
이 모듈에 어떤 객체가 있나? @Module의 providers
왜 다른 모듈에서 못 찾나? 주는 쪽 exports, 받는 쪽 imports
이 객체는 어떻게 만들어지나? providers 안의 useFactory, useClass
이 주소를 어느 메서드가 처리하나? @Controller + @Post 등의 주소

비용 1: 실패 시점, 간접성, 테스트

여기부터는 조립을 Nest에 맡기면서 내주는 것을 본다. 비용마다 먼저 무엇을 내주는지 보고, 이어서 그 비용을 줄이는 해법을 본다.

비용: 컴파일러가 잡던 실수가 런타임으로 간다

손으로 조립하면 new 호출을 컴파일러가 검사한다. Nest가 조립하면 그 호출이 코드에 없으므로 컴파일러가 검사할 대상이 없다. 표의 결과는 모두 이 저장소의 버전으로 실행해 확인했다.

실수 손으로 조립 Nest
필요한 객체를 주지 않음 컴파일 TS2554 앱 시작 providers 누락. UnknownDependenciesException
다른 모듈의 객체를 공개하지 않음 해당 없음 앱 시작 exports 누락. 메시지는 providers 누락과 같음
인터페이스 타입으로 받음 문제없음. 컴파일러가 구조로 검사 앱 시작 클래스 이름 없이 인자 위치만 알려 줌
@Injectable() 누락 필요 없음 요청 처리 앱은 켜지고 의존성이 undefined. 사용할 때 500
같은 클래스를 두 모듈의 providers에 등록 new가 두 번 보임 오류 없음. 객체가 두 개 생김. 풀이면 풀도 두 개

@Injectable() 누락이 조용한 이유는 002 문서에 있다.

해법: 앱 조립 테스트와 습관으로 다시 앞당긴다

컴파일러 대신 테스트가 잡게 한다. 앱 전체를 조립해 보는 테스트 하나면 "앱 시작" 실패를 배포 전에 잡는다. 이 저장소의 apps/api/test/shows.int.spec.ts가 이미 이렇게 AppModule을 조립한다. 실제 DB가 필요해 pre-commit이 아니라 pnpm test:integration에서 실행되므로, PR을 열기 전에 직접 돌려야 한다. 

const moduleRef = await Test.createTestingModule({
  imports: [AppModule], // 앱 전체를 조립한다
}).compile(); // 조립에 실패하면 여기서 예외가 난다

이 테스트가 무엇을 잡는지 실제로 확인한 결과와, 잡지 못하는 것의 해법이다.

실수 앱 조립 테스트 해법
providers 누락 잡음 조립 테스트를 유지한다
exports 누락 잡음 조립 테스트를 유지한다
인터페이스 타입으로 받음 잡음 토큰과 @Inject를 쓴다
@Injectable() 누락 통과함 받는 것이 없어도 항상 붙인다. 그 코드를 실제로 실행하는 테스트를 둔다
두 모듈에 같은 클래스 등록 통과함 공유할 객체는 한 모듈에 등록하고 exports로 공개한다

비용: "누가 넣어 줬는지"를 코드에서 따라가기 어렵다

new SeatHoldService(db, mailer)는 IDE에서 호출한 곳을 찾을 수 있다. Nest에는 그 호출이 내 코드에 없다. 생성자의 Database가 실제로 어떤 객체인지 알려면 providers를 찾아 읽어야 한다. useFactory나 overrideProvider를 쓰면 타입이 같아도 실제 내용물이 다를 수 있다.

프레임워크 지식이 전제가 되는 것도 비용이다. @Injectable(), imports, exports, 스코프를 알아야 코드 동작을 정확히 읽을 수 있다.

해법: 찾는 순서와 두는 곳을 정해 둔다

  • 찾는 순서를 정한다. 호출한 곳 대신 생성자 → 모듈의 providers → imports, exports 순서로 찾는다. "안 보일 때 어디를 보나" 표가 그 순서다.
  • 만드는 코드는 모듈 파일 한곳에 둔다. useFactory를 그 객체를 공개하는 모듈에만 두면 "어떻게 만들어지나"를 찾을 곳이 하나가 된다.

비용: 테스트 모듈에서는 실제 객체가 조용히 주입된다

Nest에서는 테스트도 모듈을 조립해서 쓸 수 있다. 등록된 프로바이더 중 일부만 가짜로 바꾸는 것이 overrideProvider다. 

const moduleRef = await Test.createTestingModule({
  imports: [SeatHoldModule],
})
  .overrideProvider(Database)
  .useValue(fakeDb)
  .compile();

const service = moduleRef.get(SeatHoldService);
await service.hold('A-1', 'user-1');

위 테스트는 Database만 바꿨다. SeatHoldService에 Mailer가 있다면 실제 Mailer가 주입되고 실제 send가 실행된다. 실행해 보면 오류 없이 통과한다. 숨은 의존성 절에서 생성자 DI가 막아 주던 문제가, 조립을 Nest에 맡기면 다시 생기는 것이다.

해법: 확인할 것에 따라 테스트 방법을 고른다

방법 쓰는 때 새 의존성을 추가하면
직접 new SeatHoldService(fakeDb, fakeMailer) 서비스의 로직만 볼 때 컴파일 오류로 알려 줌
Test.createTestingModule + overrideProvider 모듈 등록, 주소, 요청 처리까지 함께 볼 때 실제 객체가 조용히 주입됨
  • 로직은 직접 new로 테스트한다. 무엇이 들어가는지 코드에 그대로 보이고, 새 의존성이 생기면 컴파일 오류로 알 수 있다.
  • 모듈 테스트에서는 외부로 나가는 프로바이더를 모두 바꾼다. 메일, 결제처럼 실제로 실행되면 곤란한 것은 빠짐없이 overrideProvider했는지 확인한다.

비용 2: 싱글턴의 필드

비용: 싱글턴의 필드는 모든 요청이 함께 쓴다

Nest는 프로바이더를 앱 시작 때 한 번 만들어 모든 요청에 같은 객체를 쓴다. 연결 풀이 공유되는 이유이기도 하고, 아래 문제의 원인이기도 하다.

아래 wait는 쿼리가 오래 걸리는 상황을 흉내 내는 함수다. 넘긴 시간(ms)이 지나야 끝난다. 

const wait = (ms: number) => new Promise((resolve) => setTimeout(resolve, ms));

@Injectable()
export class SeatHoldService {
  private userId?: string; // 요청 값을 필드에 저장했다

  async hold(userId: string, ms: number) {
    this.userId = userId;
    await wait(ms); // 쿼리를 기다리는 동안 이 함수는 멈춘다
    return this.userId;
  }
}

await에서 무슨 일이 일어나는가

Node.js는 한 번에 코드 한 줄만 실행한다. 대신 await를 만나면 그 함수를 잠시 멈추고, 기다리는 동안 다른 일을 처리한다. 쿼리 결과를 기다리며 놀지 않기 위해서다.

코드 일어나는 일
this.userId = userId; 바로 실행된다.
await wait(ms); hold가 멈춘다. Node.js는 그동안 다른 요청을 처리한다.
return this.userId; 기다림이 끝나면 여기부터 이어서 실행된다.

멈춘 사이에 처리되는 다른 요청이 같은 SeatHoldService의 hold를 부르면 어떻게 될까? 객체가 하나뿐이니 this.userId도 하나이고, 두 요청이 그 한 칸을 같이 쓰게 된다.

실제로 실행한 결과

A 사용자와 B 사용자의 요청이 거의 동시에 들어왔다고 하자. A는 쿼리에 50ms, B는 5ms가 걸린다고 가정한다. 서버 없이 이 상황을 재현하는 코드다. 

@Module({
  providers: [SeatHoldService],
})
class SeatHoldModule {}

// 서버 없이 Nest 컨테이너만 띄운다
const app = await NestFactory.createApplicationContext(SeatHoldModule);

// Nest가 만든 SeatHoldService 객체를 꺼낸다
const service = app.get(SeatHoldService);

// 같은 객체의 hold를 두 번, 동시에 실행한다
const results = await Promise.all([
  service.hold('A', 50), // A 사용자의 요청
  service.hold('B', 5),  // B 사용자의 요청
]);

console.log(results); // [ 'B', 'B' ]
  • app.get(SeatHoldService): 몇 번을 불러도 같은 객체를 돌려준다. 실제 앱에서 모든 요청의 컨트롤러가 받는 것도 이 객체 하나다.
  • Promise.all([...]): 배열 안의 두 호출을 기다리지 않고 연달아 시작한 뒤, 둘 다 끝나면 결과를 순서대로 배열로 돌려준다. 요청 두 개가 거의 동시에 들어온 상황이다.

결과의 첫 번째 값은 A 요청이 돌려받은 값이다. A를 넣었는데 B가 나왔다. 실행 순서를 시간순으로 펼치면 다음과 같다.

시각 실행되는 코드 실행 후 this.userId
0ms A가 this.userId = 'A' 실행 A
0ms A가 await에서 멈춤. Node.js는 다음 요청을 처리 A
0ms B가 끼어듦: this.userId = 'B' 실행 B
0ms B도 await에서 멈춤 B
5ms B가 이어서 실행되어 B를 돌려받음. 정상 B
50ms A가 이어서 실행되어 this.userId를 읽음. A를 넣었는데 B를 돌려받음 B

A가 적어 둔 값을 B가 지운 것이다. 실제 코드였다면 A 사용자가 고른 좌석이 B 사용자에게 묶일 수 있다.

같은 두 호출을 하나씩 차례로 실행하면 문제가 없다.

const first = await service.hold('A', 50);  // A가 끝날 때까지 기다린다
const second = await service.hold('B', 5);  // 그다음에 B를 시작한다

console.log(first, second); // A B

A가 멈춘 동안 시작된 다른 호출이 없어서 덮어쓸 기회가 없다. 요청을 하나씩 보내는 테스트로는 이 문제를 찾을 수 없는 이유다.

해법 1: 필드 대신 인자로 넘긴다

메서드 인자는 호출할 때마다 따로 생긴다. A의 호출과 B의 호출이 각자 자기 userId를 가지므로, 다른 요청이 바꿀 수 없다.

앞의 코드에서 필드 userId를 지우고, 인자를 그대로 쓰도록 바꿨다. 나머지 실행 코드는 앞과 같다. 

@Injectable()
export class SeatHoldService {
  // private userId 필드가 없다

  async hold(userId: string, ms: number) {
    await wait(ms);
    return userId; // 필드가 아니라 이번 호출의 인자를 돌려준다
  }
}

@Module({
  providers: [SeatHoldService],
})
class SeatHoldModule {}

const app = await NestFactory.createApplicationContext(SeatHoldModule);
const service = app.get(SeatHoldService); // 객체는 여전히 하나다

const results = await Promise.all([
  service.hold('A', 50), // A 사용자의 요청
  service.hold('B', 5),  // B 사용자의 요청
]);

console.log(results); // [ 'A', 'B' ]

시간순으로 펼치면 B가 끼어들어도 A의 값이 그대로 남는다.

시각 실행되는 코드 A 호출의 userId B 호출의 userId
0ms A가 await에서 멈춤 A 아직 없음
0ms B가 끼어들어 await에서 멈춤 A B
5ms B가 이어서 실행되어 B를 돌려받음 A B
50ms A가 이어서 실행되어 A를 돌려받음 A 끝남

객체는 하나지만 userId는 호출마다 따로 있어서, 앞의 표와 달리 두 요청이 같은 칸을 쓰지 않는다.

이 문제는 동시 요청이 await 사이에 끼어들 때만 나타난다. 싱글턴의 필드에는 요청마다 달라지는 값을 넣지 않는다. 위의 해법 1처럼 인자로 넘긴다.

해법 2: 요청마다 객체를 새로 만든다 (Scope.REQUEST)

값이 섞인 원인은 객체가 하나뿐인데 그 필드에 요청마다 다른 값을 넣은 것이었다. 해법 1은 필드를 쓰지 않는 방법이고, 해법 2는 반대로 요청마다 객체를 따로 만드는 방법이다. 객체가 요청별로 있으니 필드에 넣어도 섞이지 않는다.

@Injectable({ scope: Scope.REQUEST })를 붙인 클래스는 앱 시작 때 만들지 않고, 요청이 올 때마다 새로 만든다. 아래 RequestInfo는 요청 헤더 x-user-id에서 사용자를 읽어 담는다. REQUEST는 지금 처리 중인 요청 객체를 받는 토큰이다. 

import { REQUEST } from '@nestjs/core';
import type { Request } from 'express'; // Nest가 기본으로 쓰는 Express의 요청 타입

@Injectable({ scope: Scope.REQUEST })
export class RequestInfo {
  readonly userId: string;

  constructor(
    @Inject(REQUEST)
    request: Request,
  ) {
    this.userId = request.headers['x-user-id'] as string;
  }
}

@Injectable()
export class Database {}

@Injectable()
export class SeatHoldService {
  constructor(
    private readonly info: RequestInfo,
    private readonly db: Database,
  ) {}

  async hold(ms: number) {
    await wait(ms);
    return this.info.userId; // 필드를 읽지만, 이 객체는 이번 요청 전용이다
  }
}

@Controller('seat-holds')
export class SeatHoldController {
  constructor(private readonly seatHolds: SeatHoldService) {}

  @Post()
  create(@Query('ms') ms: string) {
    return this.seatHolds.hold(Number(ms));
  }
}

앞과 같은 조건으로, 이번에는 실제 HTTP 요청 두 개를 동시에 보낸다.

await app.listen(0); // 비어 있는 포트로 서버를 띄운다
const url = await app.getUrl(); // 띄운 서버의 주소. 예: http://127.0.0.1:53021

const responses = await Promise.all([
  fetch(`${url}/seat-holds?ms=50`, { method: 'POST', headers: { 'x-user-id': 'A' } }),
  fetch(`${url}/seat-holds?ms=5`, { method: 'POST', headers: { 'x-user-id': 'B' } }),
]);

console.log(await Promise.all(responses.map((r) => r.text()))); // [ 'A', 'B' ]

섞이지 않았다. 대신 표시는 RequestInfo에만 붙였는데, 다른 클래스까지 영향을 받는다.

해법 2의 비용: 위쪽 클래스까지 요청마다 만들어진다

예제의 의존 관계는 이렇다.

SeatHoldController → SeatHoldService → RequestInfo (요청 스코프)
                                     → Database

SeatHoldService가 싱글턴으로 남는다고 해 보자. 생성자는 한 번만 실행되니 그때 받은 RequestInfo 하나를 계속 들고 있게 되고, B 요청에도 A 요청의 사용자를 쓴다. 앞에서 본 값이 섞이는 문제가 다시 생긴다. 그래서 Nest는 요청 스코프를 받는 클래스도 요청마다 만들고, 그 클래스를 받는 클래스도 요청마다 만든다. 의존 관계를 따라 위로 퍼진다.

각 생성자가 몇 번 실행됐는지 세어 본 결과다.

시점 RequestInfo SeatHoldService SeatHoldController Database
앱 시작 직후 0 0 0 1
요청 2번 처리 후 2 2 2 1
  • 앱 시작 직후: 요청 스코프가 된 세 클래스는 아직 만들어지지 않았다. 싱글턴인 Database만 하나 있다.
  • 요청 2번 후: 세 클래스는 요청마다 하나씩 만들어졌다. Database는 RequestInfo를 받지 않으므로 여전히 하나다.
비용 내용
요청마다 객체 생성 싱글턴이면 요청마다 0개인데, 이 예제는 3개를 만든다. 의존 관계가 깊을수록 늘어난다.
영향이 코드에 안 보임 아래쪽 한 클래스에 표시를 붙였을 뿐인데 위쪽 클래스의 동작이 바뀐다. 위쪽 코드에는 흔적이 없다.
꺼내는 방법이 달라짐 app.get(SeatHoldService)가 "scoped provider"라며 실패하고 resolve()를 쓰라고 안내한다. 요청마다 다른 객체라 "그 객체 하나"를 꺼낼 수 없기 때문이다.

그래서 해법 1(인자로 넘기기)을 먼저 쓴다. 객체는 계속 하나이고 전파도 일어나지 않는다. 요청 스코프는 인자로 넘기기 어려운 경우에만 쓴다.

비용 3: 순환 의존

SeatHoldService가 OrderService를 필요로 하고, OrderService도 SeatHoldService를 필요로 한다면 어떻게 될까? 손으로 조립하면 문제가 바로 보인다. 

const orders = new OrderService(seatHolds); // seatHolds가 아직 없다
const seatHolds = new SeatHoldService(orders);

Nest에 맡기면 이 문제가 코드 한 줄로 드러나지 않고, 두 파일에 나뉘어 숨는다. 이것이 비용이다. 이 앱처럼 ES 모듈을 쓰면 Nest가 조립하기도 전에, 파일을 불러오는 단계에서 실패한다. 

// a.ts
import { B } from './b.js';

@Injectable()
export class A {
  constructor(public b: B) {}
}

// b.ts
import { A } from './a.js';

@Injectable()
export class B {
  constructor(public a: A) {}
}
__metadata("design:paramtypes", [A])
                                 ^
ReferenceError: Cannot access 'A' before initialization

왜 이런 오류가 나는지 순서대로 보면 다음과 같다.

  1. a.ts를 불러오기 시작 첫 줄의 import 때문에 b.ts를 먼저 실행한다. 클래스 A는 아직 정의되지 않았다.
  2. b.ts가 클래스 B를 정의 @Injectable()이 붙어 있으므로 컴파일러가 넣은 생성자 타입 기록 코드가 실행되는데, 거기에 A가 값으로 들어 있다.
  3. 아직 없는 A를 읽어 실패 이 오류는 Nest의 UnknownDependenciesException이 아니라 JavaScript 오류다. 그래서 메시지에 Nest의 안내가 없다.

해법 1: forwardRef로 우회한다

Nest의 해법은 forwardRef다. 클래스를 바로 읽지 않고 나중에 읽도록 함수로 감싼다. 그런데 실패 원인은 생성자 타입 기록 쪽이라 그것만으로는 부족하다. tsc로 빌드해 node로 실행한 결과다.

시도 기록되는 값 결과
그대로 public a: A [A] 파일 로드 때 ReferenceError
@Inject(forwardRef(() => A)) public a: A [A] 파일 로드 때 ReferenceError
@Inject(forwardRef(() => A)) public a: Ref<A> [Object] 양쪽 모두 적용 시 앱 시작, 서로 같은 객체 주입

Ref는 export type Ref<T> = T;로 직접 정의한 타입 별칭이다. 타입으로는 A와 같지만, 컴파일러가 클래스로 기록하지 않아서 Object가 남는다. 파일을 불러올 때 A를 읽지 않으므로 오류가 사라지고, 실제 주입은 forwardRef가 맡는다.

동작은 하지만 타입 별칭이라는 요령이 필요하고, 순환 자체는 그대로 남는다.

해법 2: 의존 방향을 끊는다

해법 1보다 의존 방향을 끊는 쪽을 먼저 시도한다. 순환은 두 클래스의 책임이 섞였다는 신호인 경우가 많다. 둘이 같이 쓰는 부분을 세 번째 서비스로 빼면 화살표가 한 방향이 된다.

후: 위에서 아래로만 필요로 함

생성자 DI 드러나는 의존 관계, 쉬운 교체, 설계 신호 조립 코드를 어딘가에 써야 함 조립을 한곳에 모으거나 컨테이너에 맡김
DI 컨테이너 조립 코드 제거, 공유 자동화, 수명 주기, 모듈 경계 늦어진 실패 시점, 간접성, 테스트에서 조용히 주입되는 실제 객체 앱 조립 테스트, @Injectable() 습관, 찾는 순서 정하기, 외부 프로바이더 모두 교체
기본 싱글턴 연결 풀 공유, 객체 생성 비용 감소 필드에 요청 값을 두면 요청끼리 값이 섞임 인자로 넘기기. 꼭 필요할 때만 요청 스코프
컨테이너의 자동 연결 순서를 몰라도 조립됨 순환 의존이 두 파일에 숨음 세 번째 서비스로 의존 방향 끊기

"DI가 없으면 큰일 난다"가 아니다. 규모가 커질수록 의존 관계가 드러나고 교체하기 쉬운 쪽이 유리하고, 대신 간접성을 비용으로 낸다.

이 프로젝트에서는

지금 apps/api에는 GET /shows가 빈 배열을 돌려주는 컨트롤러뿐이다. 서비스도, 데이터베이스도 없다. 이 크기에서는 Hono가 더 단순해 보이는 것이 당연하다. 비용만 보이고 이득은 아직 드러나지 않을 때다.

이득이 드러날 곳은 ADR 0003이 정한 모듈러 모놀리스다. 코드베이스 하나를 공연, 주문, 결제 모듈로 나눌 때 exports는 "다른 모듈이 쓸 수 있는 것"을 코드로 정한다. 트랜잭션과 락, 결제 정합성을 다룰 때 외부 결제나 메일을 테스트에서 바꿔 끼우는 일도 잦아진다.

코드를 쓸 때 기억할 규칙은 다섯 가지다.

  • 필요한 것은 생성자로 받고, 받는 것이 없어도 @Injectable()을 붙인다.
  • 연결 풀처럼 공유할 객체는 모듈 하나에 등록하고 exports로 공개한다.
  • 요청 값과 트랜잭션은 인자로 넘기고, 싱글턴의 필드에 담지 않는다.
  • 외부로 나가는 것은 주입한다. 시간은 fake timer로 먼저 해결하고, 로거는 대개 주입하지 않는다.
  • 순환 의존이 보이면 forwardRef보다 의존 방향부터 다시 본다.

스스로 확인하기

질문에 먼저 답해 본 뒤, 눌러서 답을 확인한다.

1. DI를 쓰려면 DI 컨테이너가 꼭 필요한가?

아니다. 생성자로 받고 main.ts에서 직접 new로 조립해도 DI다. 컨테이너는 그 조립을 대신 해 줄 뿐이다.

2. 서비스마다 연결 풀이 생기는 문제를 해결하려면 DI가 꼭 필요한가?

아니다. 핵심은 "한곳에서 만들어 공유"이므로 db.ts로도 해결된다. 이 문제만으로는 DI를 고를 이유가 되지 않는다.

3. 아래 서비스의 숨은 의존성 세 가지는 무엇이고, 어떤 것을 주입해야 하는가? 
class CouponService {
  constructor(private readonly db: Database) {}

  async issue(userId: string) {
    const limit = Number(process.env.COUPON_LIMIT);
    const issuedAt = new Date();
    logger.info(`쿠폰 발급: ${userId}`);
    await this.db.query(/* limit, issuedAt 사용 */);
  }
}

process.env, new Date, logger다. 환경 변수는 시작 때 검증되도록 설정 객체로 주입하는 것이 좋다. 시각은 fake timer로 먼저 해결하고, 로거는 보통 주입하지 않는다.

4. 아래 등록에서 useFactory가 필요한 이유는 무엇인가? 
{
  provide: Database,
  inject: [AppConfig],
  useFactory: (config: AppConfig) => new Database(config.databaseUrl),
}

Database의 생성자 인자는 문자열이다. Nest는 생성자 타입 기록으로 등록된 프로바이더를 찾는데, String은 등록된 프로바이더가 아니다. 그래서 만드는 방법을 함수로 직접 등록한다.

5. 같은 Database를 두 모듈의 providers에 적으면 어떻게 되는가?

오류 없이 객체가 두 개 생기고, 풀도 그만큼 늘어난다. 공유하려면 한 모듈에 등록해 exports하고 다른 모듈이 imports해야 한다.

6. 싱글턴 서비스의 필드에 userId를 저장하면 왜 혼자 테스트할 때는 문제가 없는가?

요청이 하나면 덮어쓰는 다른 요청이 없기 때문이다. 동시 요청이 await 사이에 끼어들 때만 값이 바뀌므로, 트래픽이 생긴 뒤에야 드러난다.

7. Scope.REQUEST를 맨 아래 프로바이더 하나에만 지정했다. 그 위의 싱글턴 컨트롤러는 어떻게 되는가?

그것에 의존하는 서비스와 컨트롤러도 요청 스코프가 되어 요청마다 만들어진다. 의존 관계가 없는 프로바이더는 그대로 싱글턴이다.

8. ES 모듈에서 forwardRef를 썼는데도 Cannot access 'A' before initialization이 나는 이유는 무엇인가?

forwardRef는 주입 대상을 나중에 읽게 할 뿐이고, 생성자 타입 기록 design:paramtypes에는 여전히 A가 남아 파일 로드 때 읽히기 때문이다. 타입 별칭으로 기록을 Object로 만들거나, 의존 방향을 끊어야 한다.

9. Nest의 overrideProvider(Database) 테스트를 통과했다. 이 서비스가 실제 메일을 보내지 않았다고 단정할 수 있는가?

없다. Mailer를 따로 바꾸지 않았다면 실제 객체가 조용히 주입된다. 직접 new로 만들 때와 달리 컴파일 오류도 나지 않는다.
