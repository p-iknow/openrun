Server Component 단계와 SSR 단계

Next는 페이지 하나를 만들 때 서버에서 일을 두 번에 나눠 한다. 먼저 Server Component만 실행해 화면의 설계도를 만들고(Server Component 단계), 그 설계도로 첫 화면 HTML을 만든다(SSR 단계). 그 뒤 브라우저가 HTML에 이벤트를 연결한다(하이드레이션). 스토어 앱에 임시 페이지를 만들어 단계마다 나오는 결과물을 직접 꺼내 보고, 링크로 이동할 때는 무엇이 달라지는지까지 정리한다.

헷갈리는 두 문장

Server Component를 공부하다 보면 서로 반대처럼 보이는 두 문장을 만난다.

  1. "서버는 'use client' 파일을 실행하지 않는다" 014 문서에서 본 대로, 서버는 'use client' 파일 대신 이름표 붙은 가짜를 받는다. 그래서 Drawer.Root가 undefined가 됐다.
  2. "Client Component도 서버에서 한 번 실행된다" 페이지 소스를 보면 Client Component인 Button도 <button class="…">으로 완성돼 있다. 누군가 서버에서 Button 코드를 실행했다는 뜻이다.

둘 다 맞다. 두 문장이 말하는 "서버"가 서로 다른 단계다. 1번은 Server Component 단계, 2번은 SSR 단계 이야기다. 이 문서는 이 두 단계를 구분하는 것이 목표다.

건물 짓기로 비유하면 이렇다.

  1. 건축가 (1단계) 직접 지을 수 있는 부분(Badge)은 완성하고, 전문 업체가 맡을 부분(Button)에는 "OO업체가 이 사양으로 설치"라는 쪽지만 붙인 설계도를 만든다.
  2. 모델하우스 (2단계) 손님이 바로 볼 수 있게 쪽지 자리까지 실제로 만들어 보여 준다. 다만 아직 전기가 안 들어와서 눌러도 반응이 없다.
  3. 입주 (3단계) 전문 업체(브라우저로 온 JS)가 와서 전기를 연결한다. 이제 버튼이 작동한다.

실험한 페이지

스토어 앱에 임시 페이지를 만들었다. 서버용 Badge(지시어 없음)와 클라이언트용 Button('use client')을 나란히 둔 Server Component다. 실험이 끝난 뒤 지웠다. 

// apps/store/app/probe-stages/page.tsx (임시)
import { Badge, Button } from '@openrun/store-ui';

export default function ProbeStages() {
  return (
    <main>
      <Badge tone="primary">서버용 배지</Badge>
      <Button variant="secondary">클라이언트 버튼</Button>
    </main>
  );
}

이 페이지는 요청마다 바뀔 내용이 없어 next build가 미리 만들어 둔다. 그래서 두 단계의 결과물이 파일로 남는다.

  • apps/store/.next/server/app/
    • probe-stages.rsc 1단계 설계도 (RSC payload)
    • probe-stages.html 2단계 첫 화면 HTML

1단계: Server Component 단계

하는 일: Server Component만 실행해 화면의 설계도를 만든다. 'use client' 컴포넌트는 실행하지 않고 그 자리에 이름표만 둔다.

probe-stages.rsc에서 이 페이지에 해당하는 부분만 뽑았다(줄바꿈과 들여쓰기는 읽기 쉽게 넣었다).

a:I[86223,["/_next/static/chunks/2qj-s9lpzec8-.js","/_next/static/chunks/16f11qb2p8waj.js"],"Button"]
…
["$","main",null,{"children":[
  ["$","span",null,{"className":"inline-flex h-[24px] items-center rounded-badge px-sm text-caption font-semibold bg-primary-subtle text-primary-strong","children":"서버용 배지"}],
  ["$","$La",null,{"variant":"secondary","children":"클라이언트 버튼"}]
]}]
컴포넌트 설계도에 남은 것 뜻
Badge (지시어 없음) ["$","span",null,{className, children:"서버용 배지"}] 실행 끝 Badge 함수가 이미 실행돼 <span>이라는 결과만 남았다. Badge 코드는 설계도 어디에도 없다
Button ('use client') ["$","$La",null,{variant, children}] 실행 안 함 결과 대신 자리표시자 $La와 props만 남았다. $La는 맨 위 a: 줄의 이름표를 가리킨다

설계도는 HTML이 아니라 React 전용 형식이다. 응답 형식도 text/x-component다. 브라우저는 이것만으로 화면을 바로 그릴 수 없고, React가 읽어서 그려야 한다.

설계도 읽는 법

설계도의 줄은 두 종류만 알면 읽을 수 있다.

  1. 요소: ["$", 종류, key, props] JSX 하나가 배열 하나다. ["$","span",null,{…}]는 <span …>이다. 종류 자리에 "span" 같은 HTML 태그 이름이 오면 그대로 그리고, "$La"처럼 $L로 시작하면 "a 줄의 클라이언트 컴포넌트를 불러와 그려라"는 뜻이다.
  2. 이름표: a:I[모듈 번호, [JS 파일들], export 이름] a:I[86223,[…],"Button"]은 "86223번 모듈(button.js)의 Button export, 코드는 이 JS 파일들에 있다"는 뜻이다. 014 문서의 manifest에 적혀 있던 그 번호와 파일들이다.

그러니까 ["$","$La",null,{"variant":"secondary",…}]를 풀어 읽으면 "여기에 button.js의 Button을 variant: 'secondary'로 그려라"가 된다. 014 문서에서 말한 이름표가 실제 결과물에서는 이렇게 생겼다.

2단계: SSR 단계

하는 일: 1단계 설계도를 받아 브라우저가 바로 그릴 수 있는 HTML로 바꾼다. 이름표 자리를 채우려고 진짜 Button 코드를 서버에서 실행한다. SSR은 Server-Side Rendering(서버에서 HTML 만들기)의 줄임말이다.

probe-stages.html에서 같은 부분을 뽑았다.

<main>
  <span class="inline-flex h-[24px] … bg-primary-subtle text-primary-strong">서버용 배지</span>
  <button type="button" tabindex="0" class="group relative inline-flex h-[52px] …">
    <span class="group-data-loading:opacity-0">클라이언트 버튼</span>
  </button>
</main>
  • Badge: 설계도에 있던 <span>을 그대로 HTML로 옮겼다.
  • Button: 설계도에는 이름표뿐이었는데 여기서는 <button class="…">으로 완성돼 있다. cva로 클래스를 계산하고 Base UI Button이 type, tabindex를 붙인 결과다. SSR 단계가 Button 코드를 실제로 실행했다는 증거다.

왜 HTML을 따로 만드나

설계도만 보내도 React가 브라우저에서 그릴 수는 있다. 그래도 첫 로딩 때 HTML을 만드는 까닭은 이렇다.

  • 빨리 보인다: 브라우저는 HTML을 받자마자 그린다. 설계도로 그리려면 React와 컴포넌트 JS를 다 받고 실행할 때까지 빈 화면을 봐야 한다.
  • JS 없이도 내용이 있다: 검색 엔진이나 링크 미리보기처럼 JS를 실행하지 않는 쪽도 내용을 읽을 수 있다.

3단계: 브라우저의 하이드레이션

HTML만으로는 버튼이 보이기만 하고 동작하지 않는다. 이벤트를 연결하는 일은 브라우저가 한다.

  1. HTML 그리기 브라우저가 HTML을 받아 바로 화면에 그린다. 이때 버튼은 모양만 있다.
  2. JS와 설계도 받기 HTML 안에 함께 실려 온 설계도를 읽고, 이름표에 적힌 JS 파일(Button 코드)을 받는다. Badge 코드는 받지 않는다. 설계도에 Badge는 이미 <span> 결과로만 있기 때문이다.
  3. 연결하기 React가 Button을 한 번 더 실행해 결과가 이미 그려진 HTML과 같은지 맞춰 보고, 같으면 그 <button>에 클릭 같은 이벤트를 붙인다. 이것을 하이드레이션(hydration, 물 주기)이라 부른다. 마른 HTML에 JS라는 물을 줘서 살아 움직이게 한다는 뜻이다.

연결하기에서 서버 결과와 브라우저 결과가 다르면 하이드레이션 오류가 난다. 예를 들어 Client Component가 렌더링 중에 Date.now()나 Math.random()을 쓰면 2단계(서버)와 3단계(브라우저)의 값이 달라진다.

링크로 이동할 때는 2단계가 없다

첫 로딩 뒤 next/link로 다른 페이지에 갈 때는 HTML을 다시 받지 않는다. 브라우저에 이미 React가 있으니 설계도만 받아 화면을 바꾸면 되기 때문이다. 임시 페이지 두 개로 확인했다. 

// probe-a: Badge, Button, 그리고 B로 가는 링크
<Link href="/probe-b">B로 이동</Link>

// probe-b: 다른 Badge와 Button

next build 뒤 next start로 띄우고 브라우저에서 /probe-a를 열었다.

  1. 처음 열기 네트워크에 /probe-a 문서 요청 하나가 HTML로 왔다. 1·2단계를 다 거친 결과다.
  2. 미리 받기 (prefetch) 링크가 화면에 보이자마자 클릭하기 전에 /probe-b?_rsc=… 요청이 나갔다. Next가 이동할 페이지의 설계도를 미리 받아 둔 것이다.
  3. 클릭 링크를 누르자 주소가 /probe-b로 바뀌고 내용이 B로 바뀌었다. 새 네트워크 요청은 없었다. 미리 받은 설계도로 그렸다. 클릭 전에 window에 넣어 둔 값도 그대로 남아 있었다. 페이지를 새로 불러오지 않았다는 뜻이다.

같은 주소 /probe-b를 두 방식으로 요청해 응답을 비교했다.

# 주소창으로 열 때와 같은 요청
curl -s -D - http://127.0.0.1:3100/probe-b

# 링크로 이동할 때 Next가 보내는 요청 (RSC 헤더, _rsc 주소로 리다이렉트된다)
curl -s -L -D - -H "RSC: 1" http://127.0.0.1:3100/probe-b
요청 Content-Type Button 자리 거친 단계
주소창 (일반 요청) text/html <button type="button" class="…"> 완성된 HTML 1단계 + 2단계
링크 이동 (RSC: 1) text/x-component a:I[86223,[…],"Button"] 이름표와 $La. <button은 0개 1단계만

2단계(SSR)는 첫 화면을 빨리 보여 주기 위한 단계라서 처음 열 때만 한다. 1단계(Server Component)는 처음 열 때든 링크로 이동할 때든 늘 한다. 서버에서 데이터를 읽어 화면을 정하는 일이 이 단계이기 때문이다.

언제 하나: 빌드 때와 요청 때

"빌드된 뒤 요청이 오면 그때 SSR을 하나?"는 페이지마다 다르다. 1·2단계가 하는 일은 같고, 언제 하느냐만 다르다.

페이지 종류 (next build 표시) 1·2단계를 하는 때 요청이 오면 예
○ Static 정적 빌드 때 한 번 미리 만든 .html(첫 로딩)이나 .rsc(링크 이동)를 그대로 보낸다. SSR을 다시 하지 않는다 이 문서의 실험 페이지, _not-found
ƒ Dynamic 동적 요청마다 그때 1단계(설계도)를 하고, 첫 로딩이면 2단계(HTML)까지 한다 스토어 홈 (await connection()으로 요청 때 렌더링)

빌드 결과물 폴더(apps/store/.next/server/app/)를 보면 차이가 그대로 보인다.

  • .next/server/app/
    • _not-found.{html,rsc} ○ 빌드 때 만든 결과물이 파일로 있다
    • probe-stages.{html,rsc} ○ 실험 페이지도 같다
    • page.js ƒ 스토어 홈. 결과물 파일은 없고, 요청 때 실행할 코드만 있다
  • 스토어 홈은 요청 때마다 API에서 최신 공연 목록을 읽어야 해서 동적이다. 그래서 빌드에 API와 DB가 필요 없다.
  • 정적 페이지는 SSR을 빌드 때 미리 해 둔 것이다. 요청이 오면 서버는 파일을 보내기만 하므로 빠르다.
  • 어떤 조건에서 정적·동적이 갈리는지, 정적 결과물을 다시 만드는 방법(재검증) 같은 내용은 006 Next.js 렌더링 시점과 캐시에서 다룬다.

1단계와 2단계는 "무엇을 만드나"의 구분이고, 정적·동적은 "언제 만드나"의 구분이다. 정적 페이지는 둘 다 빌드 때, 동적 페이지는 둘 다 요청 때 한다. 링크 이동이면 어느 쪽이든 2단계 없이 설계도만 보낸다.

두 문장 다시 보기

문장 어느 단계 이야기인가 이 문서의 증거
"서버는 'use client' 파일을 실행하지 않는다" 1단계 Server Component 설계도에 Button은 이름표와 props뿐이다
"Client Component도 서버에서 한 번 실행된다" 2단계 SSR HTML에 <button class="…">이 완성돼 있다

Drawer.Root가 undefined였던 문제는 1단계에서 터졌다. 1단계가 설계도를 만들려면 Drawer.Root가 이름표여야 하는데, 서버 손에는 Drawer 이름표 하나뿐이고 그 안에 Root가 없었다. 자세한 내용은 014 문서의 "객체로 묶으면 속이 비는 이유"에 있다.

자주 하는 오해

오해 실제
Server Component와 SSR은 같은 말이다 다른 단계다. Server Component는 1단계에서 설계도를 만드는 컴포넌트이고, SSR은 2단계에서 HTML을 만드는 일이다. Server Component 없이 SSR만 하던 예전 방식(pages 폴더의 getServerSideProps)도 있었다.
'use client'면 브라우저에서만 실행된다 처음 열 때는 2단계(SSR)에서 서버에서도 실행된다. 그래서 Client Component도 렌더링 중에 window, localStorage 같은 브라우저 전용 값을 바로 읽으면 SSR에서 오류가 난다. 이런 값은 useEffect 안이나 이벤트 핸들러에서 읽는다.
Server Component 코드도 브라우저로 간다 가지 않는다. 1단계 결과(<span> 같은)만 설계도에 실려 간다. 실험 페이지의 Badge 코드는 설계도에도 브라우저 JS에도 없다.
링크로 이동할 때마다 서버가 HTML을 새로 만든다 설계도만 받는다(text/x-component). 링크가 화면에 보이면 미리 받아 두기도 한다.

우리 프로젝트에서는

  • 스토어 홈(apps/store/app/page.tsx)은 Server Component다. 1단계에서 API로 공연 목록을 읽어 설계도를 만들고, 처음 열 때는 2단계에서 HTML이 된다.
  • store-ui의 Badge, Skeleton, Pagination은 지시어가 없어서 Server Component에서 쓰면 1단계에서 실행이 끝난다. 브라우저로 코드가 가지 않는다.
  • Button, TextField, Select, ToggleGroup, Drawer는 'use client'라서 1단계에서는 이름표만 남고, 2단계에서 HTML이 되고, 3단계에서 하이드레이션된다.
  • 클라이언트용 컴포넌트에 Server Component가 함수 props를 넘기지 않는 규칙은 1단계 설계도에 함수를 적을 수 없기 때문이다.

스스로 확인하기

1. Server Component 단계와 SSR 단계는 각각 무엇을 만드나?

Server Component 단계는 Server Component만 실행해 설계도(RSC payload, text/x-component)를 만든다. SSR 단계는 그 설계도를 받아 Client Component까지 실행해 첫 화면 HTML(text/html)을 만든다.

2. 실험 페이지의 설계도에서 Badge와 Button은 각각 어떤 모습이었나?

Badge는 이미 실행이 끝나 ["$","span",…,"서버용 배지"]라는 결과로 있었다. Button은 실행되지 않고 ["$","$La",…] 자리표시자와 props만 있었고, $La는 a:I[86223,[…],"Button"] 이름표를 가리켰다.

3. "Client Component도 서버에서 실행된다"는 말은 어느 단계 이야기이고, 증거는 무엇인가?

SSR 단계 이야기다. HTML 결과물에 Button이 <button class="…">으로 완성돼 있었다.

4. 링크로 다른 페이지로 갈 때 서버는 무엇을 보내나?

HTML이 아니라 설계도(text/x-component)만 보낸다. SSR 단계를 거치지 않는다. 실험에서는 링크가 보이자마자 /probe-b?_rsc=… 로 미리 받아 두었고, 클릭할 때는 새 요청 없이 그 설계도로 그렸다.

5. Client Component의 렌더링 코드에서 window를 바로 읽으면 왜 오류가 나나?

처음 열 때 SSR 단계에서 그 코드가 서버에서 실행되는데, 서버에는 window가 없기 때문이다. useEffect 안이나 이벤트 핸들러에서 읽으면 브라우저에서만 실행된다.

6. 빌드된 뒤 요청이 오면 매번 SSR을 하나?

페이지마다 다르다. 정적(○) 페이지는 빌드 때 1·2단계를 한 번 해서 .html과 .rsc 파일로 저장해 두고, 요청이 오면 그 파일을 보낸다. 동적(ƒ) 페이지는 요청마다 1단계를 하고, 첫 로딩이면 2단계까지 한다. 스토어 홈은 동적이라 빌드 결과물에 page.js만 있다.

7. Drawer.Root가 undefined였던 문제는 어느 단계에서 생겼나?

Server Component 단계다. 이 단계는 'use client' 파일을 이름표로만 받는데, 'use client' 파일 안에서 만든 Drawer 객체는 이름표 하나로 바뀌어 Root 속성이 없었다.
