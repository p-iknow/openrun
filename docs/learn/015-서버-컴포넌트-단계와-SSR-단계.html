Server Component 단계와 SSR 단계

Next 앱에서 컴포넌트가 화면이 되기까지는 네 가지 일이 있다. 빌드할 때 코드를 준비하고(코드 준비), 서버에서 Server Component만 실행해 화면의 설계도를 만들고(1단계, Server Component 단계), 그 설계도로 첫 화면 HTML을 만든 뒤(2단계, SSR 단계), 브라우저가 HTML에 이벤트를 연결한다(3단계, 하이드레이션). 스토어 앱에 임시 페이지를 만들어 단계마다 나오는 결과물을 직접 꺼내 보고, 링크로 이동할 때와 정적·동적 페이지에서 무엇이 달라지는지, Drawer.Root 문제가 실제로 어느 때 생기는지까지 정리한다.

헷갈리는 두 문장

Server Component를 공부하다 보면 서로 반대처럼 보이는 두 문장을 만난다.

  1. "서버는 'use client' 파일을 실행하지 않는다" 014 문서에서 본 대로, 서버는 'use client' 파일 대신 이름표 붙은 가짜를 받는다. 그래서 Drawer.Root가 undefined가 됐다.
  2. "Client Component도 서버에서 한 번 실행된다" 페이지 소스를 보면 Client Component인 Button도 <button class="…">으로 완성돼 있다. 누군가 서버에서 Button 코드를 실행했다는 뜻이다.

둘 다 맞다. 두 문장이 말하는 "서버"가 서로 다른 단계다. 1번은 1단계(설계도 만들기, Server Component 단계), 2번은 2단계(HTML 만들기, SSR 단계) 이야기다. 그리고 1번에서 "이름표 붙은 가짜"를 만들어 두는 일은 그보다 앞서 빌드할 때(코드 준비) 일어난다. 이 문서는 이 단계들을 구분하는 것이 목표다.

건물 짓기로 비유하면 이렇다.

  1. 자재 준비 (코드 준비) 공사 전에 자재를 나눈다. 현장에서 쓸 것(서버용 코드)과 전문 업체에 보낼 것(브라우저용 JS)으로 나누고, 업체에 맡길 부분은 현장 자재 목록에 "OO업체 담당"이라는 쪽지로만 적어 둔다.
  2. 건축가 (1단계) 현장 자재로 직접 지을 수 있는 부분(Badge)은 완성하고, 쪽지로만 있는 부분(Button)에는 "OO업체가 이 사양으로 설치"라는 쪽지를 붙인 설계도를 만든다.
  3. 모델하우스 (2단계) 손님이 바로 볼 수 있게 쪽지 자리까지 실제로 만들어 보여 준다. 다만 아직 전기가 안 들어와서 눌러도 반응이 없다.
  4. 입주 (3단계) 전문 업체(브라우저로 온 JS)가 와서 전기를 연결한다. 이제 버튼이 작동한다.

먼저: 빌드 때 코드 준비

1단계와 2단계는 이미 준비된 코드를 실행하는 일이다. 그 코드는 next build가 미리 만들어 둔다. 이 준비 과정에서 컴포넌트는 하나도 실행되지 않지만, 이후 단계의 규칙이 여기서 정해진다.

  1. 변환 TS와 JSX를 JS로 바꾼다.
  2. 서버용 코드 만들기 1단계에서 실행할 서버용 코드(page.js와 그 묶음)를 만든다. 이때 import를 따라가다 'use client' 파일을 만나면, 그 파일의 내용을 넣지 않고 export 이름마다 이름표 붙은 가짜(registerClientReference(…))로 바꿔 끼운다. 014 문서에서 꺼내 본 대역 코드가 이것이다.
  3. 브라우저용 JS 만들기 'use client' 파일의 진짜 코드는 브라우저로 보낼 JS 파일(/_next/static/chunks/…)에 넣는다. 2단계(SSR)에서 쓸 서버 쪽 사본도 따로 만든다.
  4. 표 만들기 이름표(파일 경로)와 진짜 코드가 든 JS 파일을 잇는 표(client reference manifest)를 만든다.
  5. 정적 페이지만: 미리 실행 요청마다 달라질 게 없는 정적 페이지는 이어서 1단계와 2단계를 실행해 .rsc와 .html로 저장한다(아래).

"서버는 'use client' 파일을 실행하지 않는다"의 정확한 뜻은 이렇다. 빌드 때 서버용 코드에서 그 파일이 이름표로 바뀌어 버렸기 때문에, 1단계가 실행할 진짜 코드가 애초에 서버용 코드 안에 없다. 1단계는 바꿔 끼워진 가짜를 그대로 쓸 뿐이다.

실험한 페이지

스토어 앱에 임시 페이지를 만들었다. 서버용 Badge(지시어 없음)와 클라이언트용 Button('use client')을 나란히 둔 Server Component다. 실험이 끝난 뒤 지웠다. 

// apps/store/app/probe-stages/page.tsx (임시)
import { Badge, Button } from '@openrun/store-ui';

export default function ProbeStages() {
  return (

이 페이지는 요청마다 바뀔 내용이 없어 next build가 미리 만들어 둔다. 그래서 두 단계의 결과물이 파일로 남는다.

  • apps/store/.next/server/app/
    • probe-stages.rsc 1단계 설계도 (RSC payload)
    • probe-stages.html 2단계 첫 화면 HTML

1단계: 설계도 만들기 (Server Component 단계)

하는 일: 빌드 때 준비한 서버용 코드로 Server Component만 실행해 화면의 설계도를 만든다. 'use client' 컴포넌트는 서버용 코드에 이름표로만 들어 있으니, 실행하지 않고 그 자리에 이름표를 둔다.

probe-stages.rsc에서 이 페이지에 해당하는 부분만 뽑았다. 실제 파일은 한 줄에 붙어 있는데, 읽기 쉽게 줄바꿈과 들여쓰기, 띄어쓰기를 넣고 긴 클래스 이름은 …로 줄였다.

컴포넌트 설계도에 남은 것 뜻
Badge (지시어 없음) ["$","span",null,{className, children:"서버용 배지"}] 실행 끝 Badge 함수가 이미 실행돼 <span>이라는 결과만 남았다. Badge 코드는 설계도 어디에도 없다
Button ('use client') ["$","$La",null,{variant, children}] 실행 안 함 결과 대신 자리표시자 $La와 props만 남았다. $La는 맨 위 a: 줄의 이름표를 가리킨다

설계도는 HTML이 아니라 React 전용 형식이다. 응답 형식도 text/x-component다. 브라우저는 이것만으로 화면을 바로 그릴 수 없고, React가 읽어서 그려야 한다.

설계도 읽는 법

이 문서에서 "설계도"라고 부르는 것의 정식 이름은 RSC payload다. 형식, 실려 오는 곳, 스트리밍은 아래 "RSC payload 자세히"에서 따로 다룬다. 여기서는 원본 코드와 한 줄씩 맞춰 보며 읽는 법을 익힌다.

원본 코드와 나란히 놓기

실험 페이지의 JSX 세 줄이 설계도에서 각각 이렇게 바뀌었다.

원본 코드 (page.tsx) 설계도 (.rsc) 무슨 일이 있었나
<main>…</main> ["$","main",null,{"children":[…]}] 그대로 HTML 태그라서 이름 "main"이 그대로 적혔다. 안의 두 줄은 children 배열에 들어간다
<Badge tone="primary">서버용 배지</Badge> ["$","span",null,{"className":"inline-flex … bg-primary-subtle text-primary-strong","children":"서버용 배지"}] 실행됨 Badge라는 이름이 사라지고 Badge가 그린 <span>만 남았다. tone="primary"도 사라지고 그 결과인 클래스 (bg-primary-subtle …)로 바뀌었다
<Button variant="secondary">클라이언트 버튼</Button> ["$","$La",null,{"variant":"secondary","children":"클라이언트 버튼"}] 실행 안 됨 <button>으로 바뀌지 않았다. 이름 자리에 "$La"가 들어가고, props(variant, 글자)는 쓴 그대로 남았다

Badge 줄과 Button 줄을 비교하면 핵심이 보인다. Server Component인 Badge는 결과(span, 클래스)가 적히고, Client Component인 Button은 주문서(누구를, 어떤 props로)가 적힌다.

배열 한 칸씩 읽기

설계도의 ["$", …] 배열은 JSX 태그 하나를 네 칸에 나눠 적은 것이다. Button 줄로 칸을 맞춰 보면 이렇다.

칸 설계도의 값 원본 JSX에서는
1. 표시 "$" "이 배열은 요소 하나다"라는 표시. 늘 "$"다
2. 무엇을 그리나 "$La" 태그 이름 Button 자리
3. key null key를 주지 않아서 비어 있다
4. props {"variant":"secondary","children":"클라이언트 버튼"} variant="secondary"와 태그 사이의 글자. 글자는 children이라는 이름으로 들어간다

"$La"는 무엇을 가리키나

2번 칸의 "$La"는 $L + a로 나눠 읽는다. "a번 줄에 적힌 컴포넌트를 불러와 여기에 그려라"라는 뜻이다. 설계도 위쪽에 a번 줄이 있다(실제로는 한 줄인데 읽기 쉽게 나눴다). 

a:I[
  86223,
  [
    "/_next/static/chunks/2qj-s9lpzec8-.js",
    "/_next/static/chunks/16f11qb2p8waj.js"
  ],
  "Button"

조각 뜻 원본에서는
a: 이 줄의 번호. "$La"가 이 번호로 찾아온다 없음 (설계도 안에서만 쓰는 번호)
I[…] Client Component 이름표라는 표시 (Import의 I) 파일 첫 줄의 'use client'
86223 모듈 번호. manifest에서 이 번호가 button.js다 import { Button } from '@openrun/store-ui'가 가리키는 파일
["…2qj….js","…16f1….js"] 진짜 Button 코드가 든 브라우저 JS 파일들 빌드가 만든 파일 (원본에는 없음)
"Button" 그 파일에서 꺼낼 export 이름 import { Button }의 Button

이 이름표는 014 문서에서 본 서버용 가짜 (registerClientReference(…, "button.js", "Button"))가 설계도에 적힌 모습이다. manifest에 적혀 있던 번호와 JS 파일도 그대로다.

합쳐 읽으면: 원본 JSX로 되돌리기

설계도의 Button 줄을 한 번에 이해하기 어렵다면, 값을 하나씩 바꿔 넣어 원본 JSX로 되돌려 보면 된다. 수학에서 x에 값을 대입하는 것과 같다. 

① 설계도에 적힌 줄
   ["$", "$La",   null, {"variant":"secondary", "children":"클라이언트 버튼"}]

② "$La"를 a번 줄로 바꾼다          ← a:I[86223, […], "Button"] = button.js의 Button
   ["$", Button,  null, {"variant":"secondary", "children":"클라이언트 버튼"}]

③ 배열 네 칸을 JSX 모양으로 옮긴다  ← [표시, 무엇을, key, props]
   <Button variant="secondary">클라이언트 버튼</Button>

③이 page.tsx에 쓴 원본과 글자 하나까지 같다. 서버가 Button을 실행하지 않고, "이 컴포넌트를 이 props로 그려 달라"는 주문을 원본 그대로 브라우저와 2단계(SSR)로 넘겼다는 뜻이다.

같은 방법을 Badge 줄에 해 보면 차이가 분명해진다.

① 설계도에 적힌 줄
   ["$", "span", null, {
     "className": "inline-flex … bg-primary-subtle text-primary-strong",
     "children": "서버용 배지"
   }]

② 바꿔 넣을 것이 없다 ($L이 없다)

③ JSX 모양으로 옮긴다
   <span className="inline-flex … bg-primary-subtle text-primary-strong">
     서버용 배지
   </span>

원본은 <Badge tone="primary">서버용 배지</Badge>였는데, 되돌린 결과는 <span …>이다. 원본으로 돌아가지 않는다. 서버가 Badge를 이미 실행해서 결과로 바꿔 버렸기 때문이다.

원본 설계도를 JSX로 되돌린 것 뜻
Badge <Badge tone="primary"> <span className="…"> 다름 서버가 실행해 결과를 적었다
Button <Button variant="secondary"> <Button variant="secondary"> 같음 서버가 실행하지 않고 주문만 넘겼다

2단계: HTML 만들기 (SSR 단계)

하는 일: 1단계 설계도를 받아 브라우저가 바로 그릴 수 있는 HTML로 바꾼다. 이름표 자리를 채우려고 진짜 Button 코드를 서버에서 실행한다. SSR은 Server-Side Rendering(서버에서 HTML 만들기)의 줄임말이다.

probe-stages.html에서 같은 부분을 뽑았다.

<main>
  <span class="inline-flex h-[24px] … bg-primary-subtle text-primary-strong">
    서버용 배지
  </span>
  <button
    type="button"
    tabindex="0"
    class="group relative inline-flex h-[52px] …"
  >
    <span class="group-data-loading:opacity-0">클라이언트 버튼</span>
  </button>
</main>
  • Badge: 설계도에 있던 <span>을 그대로 HTML로 옮겼다.
  • Button: 설계도에는 이름표뿐이었는데 여기서는 <button class="…">으로 완성돼 있다. cva로 클래스를 계산하고 Base UI Button이 type, tabindex를 붙인 결과다. SSR 단계가 Button 코드를 실제로 실행했다는 증거다.

왜 HTML을 따로 만드나

설계도만 보내도 React가 브라우저에서 그릴 수는 있다. 그래도 첫 로딩 때 HTML을 만드는 까닭은 이렇다.

  • 빨리 보인다: 브라우저는 HTML을 받자마자 그린다. 설계도로 그리려면 React와 컴포넌트 JS를 다 받고 실행할 때까지 빈 화면을 봐야 한다.
  • JS 없이도 내용이 있다: 검색 엔진이나 링크 미리보기처럼 JS를 실행하지 않는 쪽도 내용을 읽을 수 있다.

3단계: 브라우저의 하이드레이션

HTML만으로는 버튼이 보이기만 하고 동작하지 않는다. 이벤트를 연결하는 일은 브라우저가 한다.

  1. HTML 그리기 브라우저가 HTML을 받아 바로 화면에 그린다. 이때 버튼은 모양만 있다.
  2. JS와 설계도 받기 HTML 안에 함께 실려 온 설계도(<script>self.__next_f.push(…)</script>, 아래)를 읽고, 이름표에 적힌 JS 파일(Button 코드)을 받는다. Badge 코드는 받지 않는다. 설계도에 Badge는 이미 <span> 결과로만 있기 때문이다.
  3. 연결하기 React가 Button을 한 번 더 실행해 결과가 이미 그려진 HTML과 같은지 맞춰 보고, 같으면 그 <button>에 클릭 같은 이벤트를 붙인다. 이것을 하이드레이션(hydration, 물 주기)이라 부른다. 마른 HTML에 JS라는 물을 줘서 살아 움직이게 한다는 뜻이다.

연결하기에서 서버 결과와 브라우저 결과가 다르면 하이드레이션 오류가 난다. 예를 들어 Client Component가 렌더링 중에 Date.now()나 Math.random()을 쓰면 2단계(서버)와 3단계(브라우저)의 값이 달라진다.

링크로 이동할 때는 2단계가 없다

첫 로딩 뒤 next/link로 다른 페이지에 갈 때는 HTML을 다시 받지 않는다. 브라우저에 이미 React가 있으니 설계도만 받아 화면을 바꾸면 되기 때문이다. 임시 페이지 두 개로 확인했다. 

// probe-a: Badge, Button, 그리고 B로 가는 링크
<Link href="/probe-b">B로 이동</Link>

// probe-b: 다른 Badge와 Button

next build 뒤 next start로 띄우고 브라우저에서 /probe-a를 열었다.

  1. 처음 열기 네트워크에 /probe-a 문서 요청 하나가 HTML로 왔다. 1·2단계를 다 거친 결과다.
  2. 미리 받기 (prefetch) 링크가 화면에 보이자마자 클릭하기 전에 /probe-b?_rsc=… 요청이 나갔다. Next가 이동할 페이지의 설계도를 미리 받아 둔 것이다.
  3. 클릭 링크를 누르자 주소가 /probe-b로 바뀌고 내용이 B로 바뀌었다. 새 네트워크 요청은 없었다. 미리 받은 설계도로 그렸다. 클릭 전에 window에 넣어 둔 값도 그대로 남아 있었다. 페이지를 새로 불러오지 않았다는 뜻이다.

같은 주소 /probe-b를 두 방식으로 요청해 응답을 비교했다.

# 주소창으로 열 때와 같은 요청
curl -s -D - http://127.0.0.1:3100/probe-b

# 링크로 이동할 때 Next가 보내는 요청 (RSC 헤더, _rsc 주소로 리다이렉트된다)
curl -s -L -D - -H "RSC: 1" http://127.0.0.1:3100/probe-b
요청 Content-Type Button 자리 거친 단계
주소창 (일반 요청) text/html <button type="button" class="…"> 완성된 HTML 1단계 + 2단계
링크 이동 (RSC: 1) text/x-component a:I[86223,[…],"Button"] 이름표와 $La. <button은 0개 1단계만

2단계(SSR)는 첫 화면을 빨리 보여 주기 위한 단계라서 처음 열 때만 한다. 1단계(Server Component)는 처음 열 때든 링크로 이동할 때든 늘 한다. 서버에서 데이터를 읽어 화면을 정하는 일이 이 단계이기 때문이다.

RSC payload 자세히

지금까지 "설계도"라고 부른 것이 RSC payload다. RSC는 React Server Components, payload는 "실어 보내는 내용물"이라는 뜻이다.

RSC payload는 1단계(Server Component 단계)가 만든 컴포넌트 트리를, 브라우저로 보낼 수 있게 글자로 적은 것이다. 2단계(SSR)는 이것을 받아 HTML로 바꾸고, 브라우저의 React는 이것을 읽어 하이드레이션하거나 화면을 바꾼다.

무엇이 들어 있나

들어 있는 것 실험 페이지에서 본 모습 설계도 비유
실행이 끝난 Server Component의 결과 ["$","span",null,{"className":"…","children":"서버용 배지"}] 이미 완성된 부분
Client Component를 가리키는 이름표 a:I[86223,[…JS 파일들],"Button"] "OO업체 담당" 쪽지
그 자리에 넘길 props ["$","$La",null,{"variant":"secondary",…}] 쪽지에 적힌 설치 사양
미리 받아 둘 자원 :HL["/_next/static/chunks/…css","style"], 글꼴 파일 미리 주문할 자재 목록

Server Component의 코드는 들어 있지 않다. 실행 결과만 들어 있다. Client Component의 코드도 들어 있지 않다. 코드가 든 JS 파일의 위치만 이름표에 적혀 있다.

형식: 줄마다 번호가 붙는다

RSC payload는 한 덩어리 JSON이 아니라 번호:값 꼴의 줄이 이어진 것이다.

1:"$Sreact.fragment"
2:"/_next/static/chunks/2qj-s9lpzec8-.js"
a:I[86223,["$2","$9"],"Button"]
:HL["/_next/static/chunks/1hq86fhdfh4j3.css","style"]
0:{…페이지 트리…}

자주 보이는 표시는 이렇다.

표시 뜻 예
["$", 종류, key, props] 요소 하나. JSX 하나에 해당한다 ["$","main",null,{"children":[…]}]
I[…] Client Component 이름표 (모듈 번호, JS 파일들, export 이름) a:I[86223,[…],"Button"]
"$L번호" "번호 줄을 여기 넣어라". 이름표 줄일 수도 있고, 아직 도착하지 않은 줄일 수도 있다 "$La", "$L15"
"$S…" React가 쓰는 특별한 기호 "$Sreact.fragment", "$Sreact.suspense"
"$번호" 다른 줄의 값을 가져다 쓴다 (같은 글자를 반복하지 않으려고) ["$2","$9"]는 2번, 9번 줄의 JS 파일 주소
:HL[…] 미리 받아 둘 자원 힌트. 브라우저가 CSS와 글꼴을 일찍 받기 시작하게 한다 :HL["/…css","style"]

이 형식은 React 내부 규칙이라 버전에 따라 바뀔 수 있다. 공부하거나 디버깅할 때 읽는 용도이고, 앱 코드에서 직접 읽거나 만들면 안 된다.

어디에 실려 오나

같은 RSC payload가 상황에 따라 세 곳에 나타난다.

곳 언제 모습
.next/server/app/*.rsc 파일 정적 페이지를 빌드할 때 1단계 결과를 그대로 저장한 파일
HTML 안의 <script> 페이지 열기 요청 self.__next_f.push([1,"1:…\n2:…"])
?_rsc=… 응답 링크 이동 요청, 미리 받기 Content-Type text/x-component. 줄들 그대로

빌드된 _not-found.html을 열어 보면 <script>self.__next_f.push([1,"1:\"$Sreact.fragment\"\n2:…"])</script> 같은 태그가 4개 있다. 안에 든 1:, 2:, 3:I[…] 줄이 같은 페이지의 _not-found.rsc 내용과 같다. 그래서 페이지를 열 때 브라우저가 받는 것은 두 가지다.

  • HTML: 브라우저가 바로 그리는 용도 (2단계 결과)
  • HTML 안에 실린 RSC payload: 하이드레이션 때 React가 읽는 용도 (1단계 결과)

HTML만으로는 어느 <button>이 어떤 Client Component인지, props가 무엇이었는지 알 수 없다. React는 payload의 이름표와 props를 보고 Button JS를 받아, 이미 그려진 HTML과 맞춰 이벤트를 붙인다.

스트리밍: 준비된 줄부터 보낸다

줄 단위 형식이라 다 만들 때까지 기다리지 않고 준비된 줄부터 보낼 수 있다. 느린 Server Component를 <Suspense>로 감싼 동적 페이지로 확인했다(실험 뒤 지웠다). 

async function Slow() {
  await new Promise((resolve) => setTimeout(resolve, 2000)); // 느린 데이터 읽기 흉내
  return <Badge tone="success">2초 뒤 도착</Badge>;
}

export default async function ProbeStream() {
  await connection();
  return (
    <main>
      <Badge tone="primary">바로 보이는 배지</Badge>
      <Button variant="secondary">클라이언트 버튼</Button>
      <Suspense fallback={<p>불러오는 중…</p>}>
        <Slow />
      </Suspense>
    </main>
  );
}

응답이 조각으로 도착하는 시각을 쟀다.

요청 0.0초에 온 조각 2.0초에 온 조각
링크 이동 (text/x-component) 4,288바이트. 바로 보이는 배지, 버튼 이름표, "불러오는 중…" 185바이트. "2초 뒤 도착" 한 줄
페이지 열기 (text/html) 바로 보이는 배지, 버튼 HTML, "불러오는 중…" "2초 뒤 도착"의 payload 줄과 HTML 조각

먼저 온 조각에서 Suspense 부분은 이렇게 생겼다(읽기 쉽게 줄바꿈과 띄어쓰기를 넣었다).

b:"$Sreact.suspense"
…
["$", "$b", null, {
  "fallback": ["$", "p", null, { "children": "불러오는 중…" }],
  "children": "$L15"
}]
  1. 먼저 보내기 $b는 Suspense다. fallback("불러오는 중…")은 바로 적고, children에는 아직 없는 15번 줄을 가리키는 "$L15"만 적어 보낸다.
  2. 나중에 채우기 2초 뒤 15:["$","span",null,{…,"children":"2초 뒤 도착"}] 한 줄이 따로 온다. React는 15번 줄이 도착하면 "불러오는 중…" 자리를 이 내용으로 바꾼다.
  3. HTML도 같은 방식 페이지 열기 요청에서도 2초 뒤 조각에 self.__next_f.push([1,"16:[…2초 뒤 도착…]"])와 함께 <div hidden id="S:0">에 담긴 HTML 조각이 왔다. 숨겨서 보낸 HTML을 "불러오는 중…" 자리에 끼워 넣는 방식이다.

덕분에 느린 데이터 하나 때문에 화면 전체가 기다리지 않는다. 빠른 부분은 0초에 보이고, 느린 부분만 나중에 채워진다.

담을 수 있는 것과 없는 것

RSC payload는 글자라서 글자로 적을 수 있는 값만 담긴다.

Client Component에 넘기는 props payload에
문자열, 숫자, 불리언, null, 배열, 일반 객체, JSX 요소 담긴다
함수 (onClick={() => …}) 못 담는다 오류가 난다

Client Component에 넘긴 props는 payload에 글자 그대로 실린다. 실험에서도 "variant":"secondary"가 그대로 보였다. 브라우저 개발자 도구에서 누구나 볼 수 있으니, 비밀번호나 내부용 필드가 든 객체를 통째로 넘기지 말고 화면에 필요한 값만 골라 넘긴다. 반대로 Server Component 안에서만 쓰고 화면에 그리지 않은 값은 payload에 실리지 않는다.

언제 하나: 빌드 때와 요청 때

단계마다 하는 일은 같고, 언제 하느냐가 페이지 종류와 요청 종류에 따라 다르다. 요청은 두 종류다.

  • 페이지 열기 요청: 주소창에 입력하거나 새로고침할 때. 브라우저에 아직 아무것도 없으니 HTML이 필요하다.
  • 링크 이동 요청: 이미 열린 페이지에서 <Link>를 눌러 옮길 때. 브라우저에 React가 있으니 설계도면 된다.
페이지 종류 (next build 표시) 빌드 때 페이지 열기 요청이 오면 링크 이동 요청이 오면
○ Static 정적
예: 이 문서의 실험 페이지, _not-found 		코드 준비 + 1단계 + 2단계. 결과를 .rsc, .html로 저장 저장해 둔 .html을 보낸다 저장해 둔 .rsc를 보낸다
ƒ Dynamic 동적
예: 스토어 홈 (await connection()) 		코드 준비만 1단계 + 2단계를 해서 HTML을 보낸다 1단계만 해서 설계도를 보낸다

빌드 결과물 폴더(apps/store/.next/server/app/)를 보면 차이가 그대로 보인다.

  • .next/server/app/
    • _not-found.{html,rsc} ○ 빌드 때 1·2단계까지 끝낸 결과물이 파일로 있다
    • probe-stages.{html,rsc} ○ 실험 페이지도 같다
    • page.js ƒ 스토어 홈. 코드 준비만 했다. 결과물 파일은 없고 요청 때 실행할 코드만 있다
  • 스토어 홈은 요청 때마다 API에서 최신 공연 목록을 읽어야 해서 동적이다. 빌드 때 1단계를 해 버리면 빌드 시점의 목록으로 굳는다. 덕분에 빌드에 API와 DB가 필요 없다.
  • 정적 페이지는 1·2단계를 빌드 때 미리 해 둔 것이다. 요청이 오면 서버는 파일을 보내기만 하므로 빠르다.
  • 어떤 조건에서 정적·동적이 갈리는지, 정적 결과물을 다시 만드는 방법(재검증) 같은 내용은 006 Next.js 렌더링 시점과 캐시에서 다룬다.

1단계와 2단계는 "무엇을 만드나"의 구분이고, 정적·동적은 "언제 만드나"의 구분이다. 코드 준비는 어느 페이지든 빌드 때 한다.

문제는 빌드 때 생기고, 터지는 때는 다르다

Drawer.Root가 undefined였던 문제를 단계로 나눠 보면, 원인이 생기는 때와 오류가 드러나는 때가 다르다.

  1. 원인이 생기는 때: 빌드의 코드 준비 'use client' 파일 안에서 만든 Drawer 객체가 서버용 코드에서 이름표 하나(가짜 함수)로 바뀐다. 객체를 만드는 코드는 서버용 코드에 들어가지 않는다. 이 순간 서버 쪽 Drawer.Root는 이미 undefined로 정해진다.
  2. 오류가 드러나는 때: 1단계를 실행할 때 설계도를 만들려고 <Drawer.Root>를 렌더링하는 순간 "Element type is invalid … got: undefined"가 난다. 그런데 1단계를 언제 하느냐는 페이지 종류에 따라 다르다(위).

그래서 같은 코드라도 페이지가 정적이냐 동적이냐에 따라 오류를 만나는 때가 달라진다. 임시 페이지로 확인했다. 

// 'use client' 파일 (임시)
export const ProbeObj = { Root: ObjRoot };

// app/probe-dyn/page.tsx (임시, 동적 페이지)
export default async function ProbeDyn() {
  await connection(); // 요청 때 렌더링하는 동적 페이지로 만든다
  return <ProbeObj.Root>x</ProbeObj.Root>;
}

동적 페이지에서는 이 실수가 빌드를 통과해 배포까지 갈 수 있다. 원인은 빌드 때 이미 생겼지만, 빌드는 동적 페이지를 실행해 보지 않으니 잡지 못한다. 그래서 compound 컴포넌트를 묶는 위치처럼 빌드가 잡아 주지 않는 규칙은 처음부터 맞게 만들어 두고(export * as Drawer), 정적 페이지나 테스트로 한 번 렌더링해 확인하는 편이 안전하다.

자주 하는 오해

오해 실제
Server Component와 SSR은 같은 말이다 다른 단계다. Server Component는 1단계에서 설계도를 만드는 컴포넌트이고, SSR은 2단계에서 HTML을 만드는 일이다. Server Component 없이 SSR만 하던 예전 방식(pages 폴더의 getServerSideProps)도 있었다.
'use client'면 브라우저에서만 실행된다 처음 열 때는 2단계(SSR)에서 서버에서도 실행된다. 그래서 Client Component도 렌더링 중에 window, localStorage 같은 브라우저 전용 값을 바로 읽으면 SSR에서 오류가 난다. 이런 값은 useEffect 안이나 이벤트 핸들러에서 읽는다.
Server Component 코드도 브라우저로 간다 가지 않는다. 1단계 결과(<span> 같은)만 설계도에 실려 간다. 실험 페이지의 Badge 코드는 설계도에도 브라우저 JS에도 없다.
링크로 이동할 때마다 서버가 HTML을 새로 만든다 설계도만 받는다(text/x-component). 링크가 화면에 보이면 미리 받아 두기도 한다.

우리 프로젝트에서는

  • 스토어 홈(apps/store/app/page.tsx)은 Server Component다. 1단계에서 API로 공연 목록을 읽어 설계도를 만들고, 처음 열 때는 2단계에서 HTML이 된다.
  • store-ui의 Badge, Skeleton, Pagination은 지시어가 없어서 Server Component에서 쓰면 1단계에서 실행이 끝난다. 브라우저로 코드가 가지 않는다.
  • Button, TextField, Select, ToggleGroup, Drawer는 'use client'라서 1단계에서는 이름표만 남고, 2단계에서 HTML이 되고, 3단계에서 하이드레이션된다.
  • 클라이언트용 컴포넌트에 Server Component가 함수 props를 넘기지 않는 규칙은 1단계 설계도에 함수를 적을 수 없기 때문이다.

스스로 확인하기

1. Server Component 단계와 SSR 단계는 각각 무엇을 만드나?

Server Component 단계는 Server Component만 실행해 설계도(RSC payload, text/x-component)를 만든다. SSR 단계는 그 설계도를 받아 Client Component까지 실행해 첫 화면 HTML(text/html)을 만든다.

2. 실험 페이지의 설계도에서 Badge와 Button은 각각 어떤 모습이었나?

Badge는 이미 실행이 끝나 ["$","span",…,"서버용 배지"]라는 결과로 있었다. Button은 실행되지 않고 ["$","$La",…] 자리표시자와 props만 있었고, $La는 a:I[86223,[…],"Button"] 이름표를 가리켰다.

3. "Client Component도 서버에서 실행된다"는 말은 어느 단계 이야기이고, 증거는 무엇인가?

SSR 단계 이야기다. HTML 결과물에 Button이 <button class="…">으로 완성돼 있었다.

4. 링크로 다른 페이지로 갈 때 서버는 무엇을 보내나?

HTML이 아니라 설계도(text/x-component)만 보낸다. SSR 단계를 거치지 않는다. 실험에서는 링크가 보이자마자 /probe-b?_rsc=… 로 미리 받아 두었고, 클릭할 때는 새 요청 없이 그 설계도로 그렸다.

5. Client Component의 렌더링 코드에서 window를 바로 읽으면 왜 오류가 나나?

처음 열 때 SSR 단계에서 그 코드가 서버에서 실행되는데, 서버에는 window가 없기 때문이다. useEffect 안이나 이벤트 핸들러에서 읽으면 브라우저에서만 실행된다.

6. 빌드된 뒤 요청이 오면 매번 SSR을 하나?

페이지마다 다르다. 정적(○) 페이지는 빌드 때 1·2단계를 한 번 해서 .html과 .rsc 파일로 저장해 두고, 요청이 오면 그 파일을 보낸다. 동적(ƒ) 페이지는 요청마다 1단계를 하고, 첫 로딩이면 2단계까지 한다. 스토어 홈은 동적이라 빌드 결과물에 page.js만 있다.

7. 빌드 때 코드 준비에서는 'use client' 파일을 어떻게 다루나?

서버용 코드에는 그 파일의 내용을 넣지 않고 export 이름마다 이름표 붙은 가짜(registerClientReference)로 바꿔 끼운다. 진짜 코드는 브라우저용 JS에 넣고, 둘을 잇는 manifest를 만든다. 컴포넌트는 하나도 실행하지 않는다.

8. Drawer.Root가 undefined였던 문제는 어느 때 생기고, 어느 때 드러나나?

원인은 빌드의 코드 준비에서 생긴다. 'use client' 파일 안에서 만든 Drawer 객체가 서버용 코드에서 이름표 하나로 바뀌어 Root 속성이 없어진다. 오류는 1단계에서 <Drawer.Root>를 렌더링할 때 드러난다. 정적 페이지면 빌드 중에 실패하고, 동적 페이지면 빌드는 통과하고 요청 때 500이 난다.

9. RSC payload에는 무엇이 들어 있고, 무엇이 들어 있지 않나?

실행이 끝난 Server Component의 결과(요소), Client Component의 이름표와 그 props, 미리 받을 자원 힌트가 들어 있다. Server Component의 코드와 Client Component의 코드는 들어 있지 않다. Client Component 코드는 이름표에 적힌 JS 파일에 따로 있다.

10. 페이지를 처음 열 때 RSC payload는 어디에 있나? 왜 HTML과 함께 오나?

HTML 안의 <script>self.__next_f.push(…)</script>에 실려 온다. HTML만으로는 어느 요소가 어떤 Client Component이고 props가 무엇인지 알 수 없어서, 하이드레이션 때 React가 이 payload를 읽는다.

11. <Suspense>로 감싼 느린 Server Component는 payload에서 어떻게 보내지나?

먼저 보내는 조각에 fallback과 함께 아직 없는 줄을 가리키는 "$L15" 같은 표시만 적는다. 데이터가 준비되면 15번 줄만 따로 보내고, React가 fallback 자리를 그 내용으로 바꾼다. 실험에서는 0초에 4,288바이트, 2초 뒤에 185바이트가 왔다.
