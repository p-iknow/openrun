라이브러리 빌드와 'use client' 경계

"store-ui의 dist를 번들러로 한 파일에 묶으면 Button의 'use client'는 어떻게 되고, Badge는 어떤 영향을 받는가?"라는 질문에서 시작한다. 지시어가 무엇을 표시하는지, 지금 빌드가 경계를 어떻게 지키는지, Base UI·MUI·Radix는 실제로 어떻게 빌드하고 왜 그렇게 하는지, 번들러(tsdown, Rolldown)를 쓰면 무엇이 달라지는지, npm에 배포할 때 무엇을 챙기는지 차례로 정리한다.

한눈에 보기

같은 소스를 어떻게 빌드하느냐에 따라 결과가 세 갈래로 나뉜다.

빌드 방식 Button Badge
파일 단위 출력 (지금의 tsc, tsdown unbundle) 정상 클라이언트 경계 정상 서버에서만 렌더
한 파일로 묶기 (기본 설정) 깨짐 지시어가 사라져 서버 모듈로 취급 영향 없음
한 파일로 묶고 맨 위에 'use client' (banner) 동작함 손해 클라이언트 번들에 들어감

흔히 떠올리는 답은 "묶으면 서버 컴포넌트의 이점(클라이언트 번들에 안 들어감)이 사라진다"이다. 이건 세 번째 줄에만 해당한다. 기본 설정으로 묶으면 그보다 먼저 지시어가 사라져서 Button이 깨진다.

'use client'가 표시하는 것

'use client'는 "이 컴포넌트는 클라이언트용"이라는 딱지가 아니다. "이 파일에서 서버 코드가 클라이언트 코드로 넘어간다"는 입구 표시다. 세 가지 성질을 기억하면 된다.

  1. 파일 단위다 지시어는 파일 맨 위, import보다 앞에 둔다(주석은 앞에 와도 된다). 함수 하나나 컴포넌트 하나에만 붙일 수 없다. 그래서 파일이 합쳐지면 표시할 자리가 없어진다. 이 문서 전체가 이 성질에서 나온다.
  2. 입구만 표시하면 된다 클라이언트 파일이 import하는 파일은 따로 표시하지 않아도 이미 클라이언트에서 실행된다. 서버 코드가 직접 import하는 파일 중 훅, 상태, 이벤트 핸들러, 브라우저 API를 쓰는 파일에만 표시하면 된다.
  3. 서버에서는 클라이언트 참조로 바뀐다 Server Component가 'use client' 파일에서 import한 값은 실제 함수가 아니라 "클라이언트의 이 컴포넌트를 여기에 그려라"라는 자리표시자다. 서버는 그 컴포넌트를 실행하지 않고, props만 직렬화해 브라우저로 보낸다.

지시어가 없는 컴포넌트는 "서버 전용"이 아니라 공용이다.

누가 import하나 지시어 없는 Badge 'use client'인 Button
Server Component 서버에서 렌더. 코드가 브라우저로 가지 않는다 클라이언트 참조. 코드가 브라우저로 가서 하이드레이션된다
Client Component 클라이언트에서 렌더. 코드가 브라우저로 간다 클라이언트에서 렌더

지금 store-ui는 어떻게 빌드하나

packages/store-ui/package.json의 빌드 스크립트는 번들러가 아니라 TypeScript 컴파일러다.

"build": "tsc -p tsconfig.build.json"

tsc는 파일 하나를 받아 파일 하나를 내놓는다. TS와 JSX를 JS로 바꾸고 .d.ts를 만들 뿐 파일을 합치지 않는다. 그래서 src와 dist가 1:1로 대응하고, 각 파일 맨 위의 지시어도 그대로 남는다.

  • dist/
    • index.js export { Button } from './button.js' 같은 re-export만 있다. 지시어 없음
    • badge.js 공용 지시어 없음
    • skeleton.js 공용 지시어 없음
    • cn.js 공용 지시어 없음
    • button.js 입구 첫 줄이 'use client';

스토어 홈(apps/store/app/page.tsx)은 Server Component이고, import { Badge, Button } from '@openrun/store-ui'로 둘을 함께 가져온다. Next는 이 import를 이렇게 처리한다.

  1. 진입점 찾기 package.json의 exports가 dist/index.js를 가리킨다.
  2. re-export 따라가기 Next의 번들러가 index.js를 따라 badge.js와 button.js를 각각 별도 모듈로 읽는다.
  3. 파일마다 판단하기 button.js는 지시어가 있으니 클라이언트 경계로 처리하고 클라이언트 번들에 넣는다. badge.js는 지시어가 없으니 서버에서 렌더하고 클라이언트 번들에서 뺀다.

라이브러리는 일부러 묶지 않고 파일 구조를 그대로 내보낸다. 묶는 일은 최종 소비자인 Next에 맡긴다. Next의 번들러는 서버·클라이언트 경계를 이해하므로 파일마다 지시어를 보고 정확히 나눌 수 있다.

번들러로 하나로 묶는다는 것

번들러(Rollup, Rolldown, esbuild, tsup, tsdown, Vite 라이브러리 모드 등)는 진입점에서 import를 따라가며 만나는 모듈을 한 파일에 이어 붙인다. 이름이 겹치지 않게 바꾸고, 모듈 사이의 import와 export 문은 대부분 지운다.

tsc (지금)
  1. src 파일 5개
  2. dist 파일 5개
  3. 지시어는 파일마다 남음
번들러 (기본 설정)
  1. src 파일 5개
  2. dist/index.js 하나
  3. 지시어를 둘 자리가 애매함

Button 코드와 Badge 코드가 같은 파일에 들어가면 'use client'를 어디에 둬야 할지가 문제다. 파일 맨 위에 두면 파일 전체가 클라이언트가 되고, 안 두면 Button도 클라이언트가 아니게 된다. 중간에 둘 방법은 없다. 지시어는 파일 단위이기 때문이다.

묶으면 생기는 두 가지 일

1) 기본 동작: 지시어가 사라진다

Rollup, Rolldown, esbuild는 모듈을 합칠 때 모듈 맨 위의 지시어를 버리고 경고만 남긴다. 결과는 이렇다.

  • Button이 든 파일에 'use client'가 없으니 Next는 이 파일을 공용 모듈로 보고 서버에서 실행한다.
  • Base UI의 Button은 내부에서 훅과 context를 쓴다. 서버에는 훅이 없으므로 Server Component에서 <Button>을 렌더하면 빌드나 렌더 단계에서 에러가 난다.
  • Badge는 원래 지시어가 없었으니 아무 영향이 없다. 이 경우 망가지는 쪽은 Button이다.

2) 우회책: 파일 전체에 'use client'를 붙인다

번들러의 banner 옵션으로 결과 파일 맨 위에 'use client'를 넣으면 Button은 다시 동작한다. 대신 같은 파일에 든 Badge도 함께 클라이언트 경계 안으로 들어간다.

  • Server Component에서만 써도 Badge 코드가 브라우저로 가고 하이드레이션 대상이 된다.
  • Badge에 넘기는 props도 직렬화할 수 있어야 한다는 제약이 생긴다.
  • 나중에 Badge를 async 컴포넌트로 만들거나 서버 전용 API를 쓰고 싶어도 쓸 수 없다.

"묶으면 서버 컴포넌트의 이점이 사라진다"는 2)의 결과다. 기본 설정에서는 1)이 먼저 일어나 Button이 깨진다. 둘 다 원인은 같다. 지시어는 파일 단위인데, 파일을 합쳐 버렸기 때문이다.

tsdown으로 직접 확인하기

tsdown은 Rolldown(Rust로 만든 Rollup 호환 번들러) 위에서 동작하는 라이브러리 빌드 도구다. store-ui의 src를 임시 폴더에 복사하고 tsdown 0.23.7로 두 가지 방식으로 빌드했다. 

# 기본: 한 파일로 묶는다
npx tsdown src/index.ts --format esm --no-dts

# unbundle: 파일 구조를 그대로 둔다
npx tsdown src/index.ts --format esm --no-dts --unbundle
모드 출력 파일 'use client'
기본 (bundle) index.mjs 하나 0개 사라짐
--unbundle index, badge, button, cn, skeleton 각각 button.mjs 첫 줄에만 지금 tsc와 같음

기본 모드로 빌드하면 Rolldown이 이런 경고를 띄운다. 지시어를 지켜 주지 않는다는 뜻이다.

src/button.tsx (1:0) [MODULE_LEVEL_DIRECTIVE] The semantics of the module level directive
"use client" in "src/button.tsx" may not be preserved when bundling.

Rolldown 문서도 같은 규칙을 적어 둔다. 맨 위 지시어는 번들링할 때 사라질 수 있고, 진입 모듈이거나 preserveModules(tsdown의 unbundle)일 때만 출력에 남는다.

실험하다 함정을 하나 더 발견했다. @base-ui/react가 package.json의 dependencies에 없으면 tsdown은 Base UI 코드까지 번들 안에 넣는다. 그러면 Base UI 내부 파일 (Button.mjs, useButton.mjs 등)의 'use client'도 같은 경고와 함께 사라진다. 의존성은 반드시 dependencies나 peerDependencies에 적어 번들 밖에 남긴다.

번들러를 쓰면서 경계 지키기

CSS 처리, ESM과 CJS 동시 출력, 경로 별칭 해석처럼 tsc로는 어려운 일이 생기면 번들러가 필요해진다. 그때 경계를 지키는 방법은 넷이다.

  1. 모듈 구조 보존 tsdown은 unbundle: true, Rollup과 Vite는 output.preserveModules: true로 파일을 합치지 않는다. Rollup은 이것만으로는 지시어를 지우므로 rollup-preserve-directives 같은 플러그인을 함께 쓴다. bunchee처럼 지시어를 직접 지원하는 도구도 있다.
  2. 진입 파일에 지시어 두기 번들러는 다른 모듈의 맨 위 지시어는 버리지만 진입 모듈의 지시어는 남긴다. 그래서 진입 파일 (src/index.ts) 첫 줄에 'use client'를 두면 묶은 결과 파일 첫 줄에도 남는다. 진입점 전체가 클라이언트가 되므로, 패키지 하나에 클라이언트 컴포넌트 하나만 담을 때 맞는 방법이다. Radix가 이렇게 한다(아래).
  3. 진입점 분리 + banner @pkg/client와 @pkg/server처럼 진입점을 나누고, 클라이언트 진입점의 결과 파일에만 output.banner: "'use client';"를 붙인다. Rolldown 문서가 권하는 우회책이다. 쓰는 쪽이 경로를 구분해 import해야 하는 불편이 있다.
  4. 빌드 결과 검사 도구를 바꾸거나 버전을 올리면 경계가 소리 없이 깨질 수 있다. 어떤 방법을 쓰든 dist를 직접 읽어 확인하는 테스트를 두는 게 실질적인 보장이다.
선택 읽기: dist 검사 테스트 예시

빌드 뒤에 실행해, 입구 파일에만 지시어가 있는지 확인한다.

import { readFileSync } from 'node:fs';
import { expect, it } from 'vitest';

const firstLine = (file: string) => readFileSync(`dist/${file}`, 'utf8').split('\n')[0];

it('클라이언트 입구 파일만 use client로 시작한다', () => {
  expect(firstLine('button.js')).toBe("'use client';");
  expect(firstLine('badge.js')).not.toContain('use client');
  expect(firstLine('index.js')).not.toContain('use client');
});

"서버 컴포넌트를 보장한다"는 말

앞에서 봤듯 Badge는 서버 전용이 아니라 공용이다. 클라이언트 번들에 절대 들어가면 안 되는 컴포넌트라면 파일에 import 'server-only';를 넣는다. 클라이언트 쪽에서 import하는 순간 빌드 에러가 난다. 다만 그러면 클라이언트 컴포넌트 안에서는 그 컴포넌트를 쓸 수 없다. 디자인 시스템의 Badge처럼 어디서나 쓰여야 하는 컴포넌트에는 맞지 않으므로, 대신 훅이나 브라우저 API를 쓰지 않는다는 규칙을 리뷰와 린트로 지킨다.

다른 라이브러리는 어떻게 하나

Base UI, MUI, Radix의 배포 파일을 열어 보고, GitHub 저장소의 빌드 스크립트까지 따라가 확인했다. 셋 다 unbundle은 쓰지 않는다. 방식은 두 갈래로 나뉜다.

라이브러리 빌드 도구 출력 경계를 지키는 방법
Base UI 1.9.0 번들러 없음 Babel 파일 단위 클라이언트 파일마다 지시어. 파일마다 변환하므로 그대로 남는다
MUI Material 9.5.0 번들러 없음 Babel 파일 단위 같음
Radix (react-dialog 1.3.1) 번들러 esbuild 패키지마다 dist/index.mjs 한 파일 컴포넌트마다 패키지를 나누고, 진입 파일에 지시어
지금 store-ui 번들러 없음 tsc 파일 단위 Base UI, MUI와 같음

Base UI와 MUI: Babel로 파일마다 변환

두 저장소(mui/base-ui, mui/material-ui)의 패키지 빌드 스크립트는 MUI 공용 빌드 도구 code-infra build다. 이 도구(mui/mui-public의 packages/code-infra)가 실제로 실행하는 명령은 Babel CLI다. 

# packages/code-infra/src/utils/babel.mjs (요약)
babel --config-file ... ${sourceDir} --out-dir ${outDir} --out-file-extension ...

디렉터리를 받아 파일마다 변환해 --out-dir에 그대로 내놓는다. 번들러가 아니다. 코드에 bundle이라는 옵션이 나오지만 값이 esm/cjs라서 묶기가 아니라 출력 형식을 고르는 이름이다. 배포된 Base UI Button을 보면 이렇게 생겼다.

  • @base-ui/react/button/
    • index.mjs 배럴. 지시어 없음
    • Button.mjs 입구 첫 줄이 'use client';
    • ButtonDataAttributes.mjs 상수만 있어 지시어 없음
    • *.js, *.d.ts, *.d.mts CJS와 타입도 파일 단위로 함께 배포
  • 파일 단위로 출력하고, 클라이언트 코드가 든 파일마다 지시어를 둔다. 패키지 전체에서 use client가 든 파일이 869개다. package.json에는 "sideEffects": false가 있다.
  • 내부 훅 파일(useButton.mjs, useStableCallback.mjs 등)에도 지시어가 있다. 사용자가 서브패스로 어느 파일이든 서버에서 바로 import할 수 있으니, 입구가 될 수 있는 파일을 모두 표시한 것이다.
  • MUI도 같다. Button/Button.mjs 첫 줄에 'use client'가 있고, Button/buttonClasses.mjs와 배럴 index.mjs에는 없다. 지시어가 든 파일이 444개다.
  • CJS 파일(Button.js)은 @babel/runtime 헬퍼를 require한다. 번들러가 넣는 런타임 코드는 없다.

Radix: 번들러로 묶고, 진입 파일에 지시어

Radix는 @radix-ui/react-dialog, @radix-ui/react-slot처럼 컴포넌트마다 npm 패키지가 따로 있다. 패키지 빌드 스크립트 radix-build의 실체는 radix-ui/primitives 저장소의 internal/builder/builder.js이고, esbuild로 묶는다. 

// internal/builder/builder.js (요약)
const esbuildConfig = {
  entryPoints: ['src/index.ts'],
  packages: 'external', // 의존성은 묶지 않는다
  bundle: true,
  format: 'cjs', // ESM은 같은 설정에 format: 'esm', .mjs로 한 번 더
  keepNames: true,
};

이 파일에는 banner도 use client도 없다. 지시어는 진입 파일에 있고, 컴포넌트 본체인 dialog.tsx에는 없다. 

// packages/react/dialog/src/index.ts
'use client';
export { createDialogScope, ... } from './dialog';
  • 번들러는 진입 모듈의 지시어를 남기므로, 결과물 dist/index.mjs 첫 줄에 "use client";가 있다. 그 아래는 esbuild가 넣은 __defProp, __name 헬퍼로 시작한다.
  • 패키지 하나에 컴포넌트 하나라서 진입점 전체가 클라이언트여도 잃는 게 없다. 경계 단위가 파일이 아니라 패키지인 셈이다.
  • 클라이언트일 필요가 없는 react-slot은 진입점에 지시어가 없다.

store-ui는 공용 Badge와 클라이언트 Button을 한 패키지에 담는다. Radix 방식을 따르려면 패키지를 나눠야 하므로, Base UI와 MUI처럼 파일 단위로 빌드하는 쪽이 맞다.

왜 Base UI와 MUI는 번들러를 쓰지 않나

"번들러로 묶고 압축하면 더 작아지고 좋은 것 아닌가?"라는 의문이 들 수 있다. 답은 압축은 사용하는 쪽이 어차피 다시 한다는 것이다. 라이브러리가 미리 하면 최종 크기는 거의 같고, 잃는 것만 생긴다.

npm 패키지 크기와 사용자가 받는 크기는 다르다

개발자 컴퓨터와 빌드 서버
  1. 라이브러리 배포본 (압축 안 됨, 파일 수백 개)
  2. 앱의 번들러 (Next 등)
사용자 브라우저
  1. 쓰는 코드만, 압축된 JS
  • node_modules의 파일은 개발자 컴퓨터와 빌드 서버에만 있다. 브라우저로 그대로 가지 않는다.
  • 브라우저로 가는 건 앱 번들러의 출력이다. 앱이 실제로 import한 코드만 골라 묶고, 압축하고, 페이지별로 나눈다.
  • 라이브러리가 미리 압축해도 앱 번들러가 다시 압축하므로 최종 크기는 거의 같다.

사용처에서 빌드된다. 단, 변환은 라이브러리 몫

"사용처에서 빌드된다"는 맞다. 다만 묶기와 변환(transpile)은 하는 쪽이 다르다.

일 누가 하나
TS 타입 지우기, JSX를 jsx() 호출로 바꾸기 라이브러리 Babel, tsc
ESM과 CJS 두 형식 준비, .d.ts 생성 라이브러리
필요한 파일만 고르기, 묶기, 압축, 페이지별 분할 앱 Next, Vite 등
  • 앱 번들러는 기본적으로 node_modules 안의 TS나 JSX를 변환해 주지 않는다. 그래서 라이브러리는 바로 실행할 수 있는 평범한 JS까지는 만들어 배포한다.
  • Next의 transpilePackages를 켜면 TS 소스를 받아 변환할 수도 있다. 하지만 공개 라이브러리는 모든 사용자가 그 설정을 하리라 기대할 수 없으니 변환해서 배포한다.
  • store-ui도 같다. tsc가 TS와 JSX를 JS로 바꿔 dist에 두고, 묶고 압축하는 일은 apps/store의 Next가 한다.

미리 묶거나 압축하면 잃는 것

  1. tree-shaking이 둔해진다 Button만 import할 때 파일이 나뉘어 있으면 번들러는 Button.mjs와 그 파일이 import하는 파일만 가져온다. 한 파일로 묶여 있으면 그 안에서 안 쓰는 코드를 골라내야 하는데, 부수 효과가 있어 보이는 코드는 지우지 못하고 남긴다.
  2. 서버·클라이언트 경계를 나눌 수 없다 이 문서의 출발점이다. 파일 단위라야 컴포넌트마다 'use client'를 따로 둘 수 있다.
  3. 서브패스 import가 어렵다 @base-ui/react/button처럼 컴포넌트 하나만 가리키는 경로를 주려면 그 파일이 따로 있어야 한다.
  4. 디버깅이 어렵다 압축하면 함수 이름이 a, b로 바뀐다. 압축하지 않으면 에러 스택을 읽을 수 있고, 사용자가 node_modules의 코드를 열어 그대로 읽을 수 있다. 배포된 Base UI 코드에는 JSDoc 주석까지 남아 있다.
  5. 의존성이 중복될 수 있다 의존성을 실수로 함께 묶으면 앱에 같은 라이브러리가 두 벌 들어간다. React나 context처럼 하나여야 하는 것이 둘이 되면 버그가 난다. tsdown 실험에서 Base UI가 번들 안으로 들어온 것이 이 경우다.

번들하지 않는 쪽의 단점

  • 파일 수가 많다: 설치 용량과 파일 수가 늘어난다. 개발자 컴퓨터 사정이고, 사용자가 받는 크기와는 상관없다.
  • 배럴 import가 개발 서버에서 느릴 수 있다: import { Button } from '@mui/material'처럼 배럴에서 가져오면, tree-shaking을 하지 않는 개발 모드에서는 배럴이 가리키는 모듈 수백 개를 읽는다. Next는 optimizePackageImports로 배럴 import를 개별 파일 import로 바꿔 준다. store-ui는 파일이 몇 개뿐이라 해당하지 않는다.

라이브러리는 실행할 수 있는 JS로 변환만 하고 파일 구조를 그대로 넘긴다. 묶기와 압축은 실제로 무엇을 쓰는지 아는 앱이 한다. 최적화를 포기한 게 아니라 더 잘할 수 있는 쪽에 맡긴 것이다.

파일마다 지시어만 두면 될까

아니다. 파일마다 지시어를 두는 건 필요조건이다. 아래 다섯 가지가 함께 맞아야 경계가 의도대로 동작한다.

  1. 빌드 뒤에도 살아 있어야 한다 소스에 써도 빌드가 파일을 합치면 사라진다. 파일 단위 출력과 의존성 외부화가 먼저다.
  2. 필요한 파일에만 둔다 훅, 상태, 이벤트 핸들러, 브라우저 API를 쓰는 입구 파일(Button)에만 둔다. Badge, Skeleton, cn에 두면 공용이던 것이 클라이언트로 넘어간다. 배럴(index.ts)에는 절대 두지 않는다. 배럴에 두면 거기서 re-export하는 모든 것이 클라이언트가 된다.
  3. 파일 맨 위에 둔다 import보다 앞이어야 한다. 주석은 앞에 와도 된다. 지금 button.tsx는 첫 줄에 있다.
  4. 클라이언트 파일에서는 컴포넌트만 export한다 Server Component가 받는 것은 클라이언트 참조라서, JSX로 렌더하는 건 되지만 함수로 호출할 수는 없다. button.tsx가 buttonVariants를 export하고 서버에서 호출하면 깨진다. 이런 값을 공개하려면 지시어 없는 별도 파일로 분리한다. 지금 index.ts는 Button과 타입만 내보내므로 괜찮다.
  5. 경계를 넘는 props는 직렬화할 수 있어야 한다 Server Component에서 <Button onClick={...}>처럼 함수를 넘기면 에러가 난다. 지시어로 해결되는 문제가 아니라 쓰는 쪽이 지킬 규칙이다. 스토어 홈은 함수 대신 <form action="/">와 type="submit"으로 새로고침을 만들었다.

1~4는 라이브러리가 지키고, 5는 라이브러리를 쓰는 앱이 지킨다. 지금 store-ui는 1~4를 모두 만족한다.

npm에 배포할 때

배포해도 원칙은 같다. npm 패키지는 소비자 앱에서 다시 번들링되므로 라이브러리가 미리 압축하거나 합칠 이유가 별로 없다. 지금 tsc 빌드를 그대로 쓰고, 내부용이던 package.json만 고치면 된다. 

{
  "name": "@openrun/store-ui",
  "version": "0.1.0",
  // "private": true 를 지운다
  "type": "module",
  "files": ["dist"],                  // npm에 올라갈 파일만
  "sideEffects": ["**/*.css"],        // CSS 말고는 tree-shaking을 허용
  "exports": {
    ".": { "types": "./dist/index.d.ts", "default": "./dist/index.js" },
    "./tokens.css": "./dist/tokens.css"   // 지금은 ./src/tokens.css
  },
  "peerDependencies": { "react": "^19.3.1" }  // React는 소비자 것을 쓴다
}
  • tokens.css 경로: 지금은 src를 가리킨다. files에 dist만 넣으면 배포본에서 이 파일이 빠지므로, 빌드할 때 dist로 복사하거나 files에 추가한다.
  • Tailwind 클래스: 컴포넌트가 클래스 이름을 문자열로 들고 있어서, 소비자 앱이 dist를 스캔해야 CSS가 생성된다. 스토어의 globals.css는 이미 @source '../node_modules/@openrun/store-ui/dist';로 하고 있다. 배포하면 README에 이 줄을 안내하거나, 미리 빌드한 CSS를 함께 배포한다.
  1. 올라갈 파일 확인 npm pack --dry-run으로 목록을 본다.
  2. 지시어 확인 dist/button.js 첫 줄에 'use client'가 있고, badge.js와 index.js에는 없는지 본다.
  3. 실제 앱에서 확인 npm pack으로 만든 tarball을 Next 앱에 설치하고, Server Component에서 Badge와 Button을 함께 렌더한다. Badge 코드가 클라이언트 청크에 없는지까지 보면 확실하다.

우리 프로젝트에서는

  • store-ui는 tsc로 파일 단위 빌드를 한다. tsdown unbundle과 같은 결과라서, 번들러가 필요한 일(CSS 번들, CJS 출력 등)이 생기기 전까지 바꿀 이유가 없다.
  • 클라이언트 입구는 button.tsx 하나이고, 지시어는 첫 줄에 있다. Badge와 Skeleton은 지시어 없는 공용 컴포넌트로 둔다.
  • 스토어 홈은 Server Component에서 Badge와 Button을 직접 렌더한다. Button에는 함수 prop 없이 type="submit"만 넘긴다.
  • Base UI, MUI와 같은 이유로 묶거나 압축하지 않는다. 변환만 tsc가 하고, 묶기와 압축은 스토어의 Next가 한다.
  • 번들러로 바꾸게 되면 unbundle: true를 켜고, dist 검사 테스트를 함께 둔다.

스스로 확인하기

1. dist를 번들러 기본 설정으로 한 파일에 묶으면 Button과 Badge는 각각 어떻게 되나?

번들러가 모듈 맨 위의 'use client'를 버린다. Button이 든 파일이 공용 모듈로 취급되어 서버에서 실행되고, Base UI의 훅 때문에 Server Component에서 렌더할 때 에러가 난다. Badge는 원래 지시어가 없었으므로 영향이 없다.

2. 그 문제를 banner로 파일 전체에 'use client'를 붙여 해결하면 무엇을 잃나?

Badge도 클라이언트 경계 안으로 들어간다. 서버에서만 써도 Badge 코드가 브라우저로 가고, props는 직렬화할 수 있어야 하며, async 컴포넌트나 서버 전용 API를 쓸 수 없게 된다.

3. index.ts에 'use client'를 붙이면 왜 안 되나?

배럴이 클라이언트 입구가 되어, 거기서 re-export하는 Badge, Skeleton, cn까지 모두 클라이언트 참조가 된다. 서버에서 cn()을 호출하면 실제 함수가 아니라서 깨진다.

4. button.tsx가 buttonVariants를 export하고, Server Component에서 그걸 호출해 클래스를 만들면?

서버가 받은 buttonVariants는 클라이언트 참조라서 호출할 수 없다. 지시어 없는 별도 파일 (예: button-variants.ts)로 옮기고, button.tsx와 서버 코드가 둘 다 그 파일을 import하게 한다.

5. tsdown unbundle을 켰는데도 Base UI의 'use client' 경고가 쏟아진다면 무엇을 의심하나?

@base-ui/react가 dependencies나 peerDependencies에 없어서 번들 안으로 들어간 것이다. 의존성으로 선언해 번들 밖에 남기면 Base UI의 파일과 지시어가 그대로 유지된다.

6. Radix는 esbuild로 한 파일에 묶는데 어떻게 'use client'가 결과 파일에 남나?

지시어를 컴포넌트 파일이 아니라 진입 파일 src/index.ts 첫 줄에 둔다. 번들러는 다른 모듈의 맨 위 지시어는 버리지만 진입 모듈의 지시어는 남기므로 dist/index.mjs 첫 줄에 그대로 나온다. 패키지 하나에 컴포넌트 하나라서 진입점 전체가 클라이언트가 돼도 손해가 없다.

7. 라이브러리가 미리 압축해 배포하면 사용자가 받는 JS가 작아지나?

거의 그렇지 않다. 사용자가 받는 건 앱 번들러의 출력이고, 앱 번들러가 쓰는 코드만 골라 다시 압축한다. 미리 압축하면 최종 크기는 비슷한데 디버깅이 어려워지고, 한 파일로 묶었다면 tree-shaking과 경계 나누기까지 불리해진다.

8. 그럼 라이브러리가 TS 소스를 그대로 배포하면 안 되나?

앱 번들러는 기본적으로 node_modules의 TS와 JSX를 변환하지 않는다. Next의 transpilePackages 같은 설정이 있어야 하는데, 공개 라이브러리는 모든 사용자가 그렇게 하리라 기대할 수 없다. 그래서 변환까지는 라이브러리가 하고, 묶기와 압축만 앱에 맡긴다.
