useRender로 요소 바꿔 끼우기

Pagination을 만들며 쓴 Base UI의 useRender를 다룬다. 쓰는 쪽이 건넨 요소(<a>나 Next.js의 Link)에 디자인 시스템의 모양과 접근성 속성을 얹는 방법, 속성이 겹칠 때의 규칙, 이름이 훅인데도 Server Component에서 도는 이유를 설명한다. 기준 버전은 @base-ui/react 1.9.0이다.

어떤 문제를 푸는가

Pagination에는 두 쪽의 바람이 부딪힌다.

누가 정하고 싶은 것
store-ui 디자인 시스템 원형 40px, 현재 페이지는 파란색, aria-current와 이름 붙이기
apps/store 쓰는 쪽 <a>를 쓸지 Next.js의 Link를 쓸지, 주소를 어떻게 만들지

store-ui가 <a>를 직접 그리면 쓰는 쪽은 Link로 바꿀 수 없다. 반대로 쓰는 쪽이 다 그리면 모양과 접근성 속성을 매번 손으로 붙여야 하고, 빠뜨리기 쉽다.

useRender는 이 둘을 합친다. 쓰는 쪽이 "이 요소로 그려 줘"라고 요소를 건네면, 디자인 시스템이 그 요소에 자기 속성을 정해진 규칙으로 얹어서 돌려준다.

비유하면 쓰는 쪽은 빈 컵(<Link href="/shows?page=3" />)을 건네고, 디자인 시스템은 그 컵에 색과 라벨(클래스, aria-current, 번호)을 붙여 돌려준다. 컵의 종류는 쓰는 쪽이, 꾸미기는 디자인 시스템이 맡는다.

한눈에 보기

쓰는 쪽이 건네는 것 (render)
  1. 요소 종류: Link
  2. 속성: href="/shows?page=3"
store-ui가 얹는 것 (props, state)
  1. className, aria-label="3페이지"
  2. aria-current="page", 글자 3
  3. state: { active: true } → data-active

useRender가 두 쪽을 합쳐 Link 하나를 돌려주고, 그 Link가 최종적으로 <a>를 그린다.

우리 코드에서

packages/store-ui/src/pagination.tsx의 Pagination.Link다.

function PaginationLink({ render, page, active = false }: PaginationLinkProps) {
  const element = useRender({
    render,                  // ① 쓰는 쪽이 건넨 요소 (빈 컵)
    defaultTagName: 'a',     // ② render가 없을 때 쓸 기본 태그
    state: { active },       // ③ 상태 → data-* 속성으로 바뀐다
    props: {                 // ④ store-ui가 얹을 속성
      'aria-label': `${page}페이지`,
      'aria-current': active ? 'page' : undefined,
      className: itemClass,
      children: page,
    },
  });
  return <li>{element}</li>;  // ⑤ 완성된 요소를 받아 그대로 그린다
}

쓰는 쪽은 이렇게 부른다.

<Pagination.Link page={3} active render={<Link href="/shows?page=3" />} />
  1. render 쓰는 쪽이 건넨 React 요소다. 아직 그려지지 않은 "설계도"라서 Server Component에서 넘겨도 직렬화된다. 함수가 아니라 요소이기 때문이다.
  2. defaultTagName render가 없을 때 그릴 태그다. Pagination은 render를 필수로 받으므로 실제로는 쓰이지 않지만, 기본값(div)이 엉뚱하게 나오지 않도록 a로 둔다.
  3. state 컴포넌트의 상태다. useRender가 data-* 속성으로 바꿔 붙인다(아래).
  4. props store-ui가 요소에 얹을 속성이다. children도 여기에 넣으면 요소의 내용이 된다.
  5. 반환값 속성이 합쳐진 React 요소 하나다. 그대로 JSX 안에 넣어 그린다.

넣은 것과 나온 것

들어간 것 어디서 왔나
Link 컴포넌트, href="/shows?page=3" 쓰는 쪽 render
aria-label="3페이지", aria-current="page", className, 글자 3 store-ui props
active: true store-ui state

react-dom/server로 그려 보면 이렇게 나온다(클래스는 줄였다).

<a href="/shows?page=3" data-active="" aria-label="3페이지" aria-current="page" class="inline-flex size-[40px] …">3</a>

쓰는 쪽이 고른 Link와 href가 그대로 남고, 그 위에 store-ui의 속성이 얹혔다.

같은 속성이 겹치면

쓰는 쪽 요소에도 className이나 aria-label이 있을 수 있다. 겹칠 때의 규칙은 useRender의 props 설명과 Base UI의 mergeProps 문서에 적혀 있다.

속성 합치는 방식 예
className 이어 붙임 store-ui "rounded-full …" + 쓰는 쪽 "mt-sm" → 둘 다 남는다
style 합침 같은 CSS 속성은 쓰는 쪽 값이 남는다
이벤트(onClick 등) 둘 다 실행 store-ui 핸들러와 쓰는 쪽 핸들러가 모두 불린다
그 밖의 속성 쓰는 쪽이 이김 쓰는 쪽이 aria-label="3페이지로 이동"을 주면 그 값이 남는다

그래서 Pagination 테스트의 "render로 넘긴 요소에 aria-label을 주면 기본 이름을 덮어쓴다"는 따로 코드를 쓰지 않아도 통과한다. 이 규칙이 그대로 적용된 결과다. 

<Pagination.Link page={3} render={<a href="/shows?page=3" aria-label="3페이지로 이동" />} />
// → <a href="/shows?page=3" aria-label="3페이지로 이동" …>3</a>

store-ui는 기본값을 주고, 쓰는 쪽은 필요할 때 덮어쓴다. 단, 클래스는 덮어쓰지 않고 더해지므로 쓰는 쪽이 store-ui의 모양을 실수로 지우지 않는다.

state와 data 속성

state: { active: true }를 넘기면 useRender가 data-active=""를 붙인다. 값이 false면 속성을 아예 붙이지 않는다. 이전·다음은 state: { disabled }로 data-disabled를 붙인다.

state 붙는 속성
{ active: true } data-active=""
{ active: false } (없음)
{ disabled: true } data-disabled=""

이 속성으로 Tailwind 클래스를 고른다.

'data-active:bg-primary data-active:text-on-primary data-active:hover:bg-primary-hover',
'data-disabled:cursor-not-allowed data-disabled:text-text-tertiary',

상태마다 클래스를 cn으로 고르는 분기가 없어지고, 클래스 목록 하나로 모든 상태를 표현한다. Base UI의 Button도 상태를 data-*로 드러내므로 우리 Button의 data-disabled: 클래스와 쓰는 법이 같다(design-system 03 문서). 쓰는 쪽도 render 요소의 className에서 같은 속성으로 상태별 스타일을 덧댈 수 있다.

비활성 이전·다음은 왜 다르게 하나

const element = useRender({
  render: disabled ? <a role="link" aria-disabled="true" /> : render,
  defaultTagName: 'a',
  state: { disabled },
  props: { 'aria-label': label, className: itemClass, children: <svg … /> },
});

비활성일 때는 쓰는 쪽이 건넨 요소를 쓰지 않고, store-ui가 만든 href 없는 <a>를 대신 넣는다. Next.js의 Link는 href가 꼭 있어야 해서, 건네받은 Link에서 href만 뺄 수 없기 때문이다. 컵을 꾸미는 대신 "못 쓰는 컵"으로 바꿔 끼우는 셈이다.

  • href가 없으니 누를 수 없고 Tab 순서에서도 빠진다.
  • role="link"와 aria-disabled="true"로 스크린 리더에 "비활성 링크"라고 알린다.

이름이 use…인데 서버에서 도는 이유

React에서 use로 시작하는 함수는 훅이고, 보통 훅은 Server Component에서 쓸 수 없다. 그런데 useRender가 하는 일은 대부분 속성 합치기라서 순수한 계산이다. 훅이 필요한 일은 하나뿐인데, ref 합치기(쓰는 쪽 ref와 내부 ref를 한 요소에 함께 연결하기)다.

Base UI 소스에서 그 부분은 이렇게 되어 있다.

// node_modules/@base-ui/react/internals/useRenderElement.mjs (1.9.0)
// This also skips the `useMergedRefs` call on the server, which is fine because
// refs are not used on the server side.
if (typeof document !== 'undefined') {     // 브라우저일 때만
  outProps.ref = useMergedRefs(outProps.ref, getReactElementRef(renderProp), ref);
}
  1. 서버에는 document가 없다 그래서 ref를 합치는 훅을 건너뛰고, 순수한 속성 합치기만 한다.
  2. 서버에는 ref가 필요 없다 ref는 브라우저의 실제 DOM 요소를 가리키는 것이라, 서버에서 HTML을 만들 때는 쓰이지 않는다.
  3. 'use client'가 없다 use-render 모듈에는 지시어가 없어서 import해도 클라이언트 경계가 생기지 않는다(경계가 무엇인지는 design-system 04 문서).

그래서 Pagination은 'use client' 없이 서버용으로 남는다. 스토어에 임시 정적 라우트를 만들고 Next.js의 Link를 넘긴 Pagination을 next build로 미리 렌더링해, HTML이 제대로 나오는 것을 확인했다.

이 동작은 Base UI 내부 구현에 기댄다. 문서에 "Server Component에서 쓸 수 있다"고 약속된 것이 아니라, 소스가 지금 그렇게 되어 있는 것이다. 그래서 두 가지로 지킨다. package.json에서 Base UI를 1.9.0으로 정확히 고정했고, 올릴 때 이 동작이 바뀌면 react-dom/server로 그리는 Pagination 테스트가 바로 깨진다.

직접 만들면

useRender 없이 React의 cloneElement로도 비슷하게 만들 수 있다. 하지만 합치는 규칙을 우리가 직접 관리해야 한다.

선택 읽기: cloneElement로 흉내 내기 
import { cloneElement, type ReactElement } from 'react';

function renderWith(render: ReactElement<Record<string, unknown>>, ours: Record<string, unknown>, state: { active: boolean }) {
  const theirs = render.props;
  return cloneElement(render, {
    ...ours,
    ...theirs,                                                      // 그 밖의 속성은 쓰는 쪽이 이김
    className: cn(ours.className as string, theirs.className as string), // 클래스는 이어 붙임
    ...(state.active && { 'data-active': '' }),                    // state → data 속성
    // 이벤트 핸들러 둘 다 부르기, style 합치기, ref 합치기는 아직 없다
  });
}

이벤트 합치기, style 합치기, ref 합치기까지 넣으면 훨씬 길어지고, Base UI 컴포넌트(Button 등)와 합치는 방식이 미묘하게 어긋날 수 있다.

같은 규칙을 Base UI와 공유하려고 useRender를 골랐다. 우리 Button의 바탕인 Base UI Button을 비롯한 Base UI 컴포넌트가 모두 같은 render 규칙을 쓰므로, 나중에 store-ui 컴포넌트에 render를 열어 줄 때도 방식이 하나로 맞는다.

쓸 때 지킬 규칙

  • 훅 규칙을 따른다. 컴포넌트 맨 위에서 조건 없이 한 번 부른다. if (disabled) useRender(...)처럼 조건 안에서 부르지 않는다. 그래서 비활성 이전·다음도 useRender는 늘 부르고, 넘기는 render 값만 바꾼다.
  • render에는 요소를 넘긴다. useRender는 함수((props, state) => …)도 받지만, 함수는 Server Component에서 넘길 수 없다. Pagination의 render 타입은 ReactElement로 좁혀 두었다.
  • 클래스는 문자열 그대로 둔다. Tailwind가 dist에서 클래스 이름을 찾아 CSS를 만들기 때문에, 조각을 이어 붙여 만든 이름(`data-${x}:…`)은 쓰지 않는다.

우리 프로젝트에서는

부품 render store-ui가 얹는 것
Pagination.Link 필수. 쓰는 쪽 링크 클래스, aria-label="N페이지", aria-current, data-active, 번호
Pagination.Previous / Next 필수. disabled면 쓰지 않음 클래스, aria-label, data-disabled, 화살표 아이콘

Base UI 문서의 예시는 컴포넌트가 나머지 props를 모두 받아 mergeProps로 합친다. 우리 Pagination.Link는 page, active, render만 받고, 그 밖의 속성(href, 추가 클래스 등)은 모두 render 요소에 적게 했다. 속성을 넣는 곳이 한 군데라 헷갈리지 않는다.

스스로 확인하기

1. 쓰는 쪽이 render 요소에 className="mt-sm"을 주면 store-ui의 원형 모양은 사라지나?

사라지지 않는다. className은 덮어쓰지 않고 이어 붙이므로 store-ui의 클래스와 mt-sm이 함께 남는다.

2. 쓰는 쪽이 render 요소에 aria-current="false"를 주면 어떻게 되나?

className, style, 이벤트가 아닌 속성은 쓰는 쪽이 이기므로 aria-current="false"가 남는다. 기본값을 덮어쓸 수 있다는 건 잘못 덮어쓸 수도 있다는 뜻이다.

3. 비활성 다음 링크에서 쓰는 쪽 요소의 href만 지우지 않고 요소를 통째로 바꾸는 이유는?

Next.js의 Link는 href가 꼭 필요해서 href 없이 그릴 수 없다. 쓰는 쪽이 어떤 컴포넌트를 넘길지 store-ui는 모르므로, 비활성일 때는 store-ui가 아는 <a>로 바꾼다.

4. Base UI를 올렸더니 useRender가 서버에서도 ref 훅을 부르게 바뀌었다. 무엇이 먼저 알려 주나?

react-dom/server로 그리는 Pagination 테스트가 먼저 깨진다. 스토어에서는 Pagination을 쓰는 Server Component의 렌더링이 실패할 수 있다. Server Component에서는 ref 훅을 쓸 수 없기 때문이다.

5. state에 { active: false }를 넘기면 HTML에 data-active="false"가 붙나?

붙지 않는다. false면 속성 자체를 빼서, data-active: 클래스가 적용되지 않는다.
