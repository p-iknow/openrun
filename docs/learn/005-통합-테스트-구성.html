통합 테스트 구성: Testcontainers, Vitest, Turborepo

  • testing

GET /shows를 진짜 PostgreSQL로 검증하는 통합 테스트가 어떻게 짜여 있는지 본다. 대상 파일은 apps/api의 vitest.config.ts, vitest.integration.config.ts, test/setup/postgres.ts, test/shows.int.spec.ts와 루트의 turbo.json이다. 기준 버전은 Vitest 5.1, Testcontainers 12.2, Turborepo 2.11이다. DB 연결 구조는 004 문서에서 다뤘다.

한눈에 보기

이 저장소의 API 테스트는 두 종류로 나뉜다.

명령 대상 DB 언제
pnpm test test/**/*.spec.ts 중 *.int.spec.ts를 뺀 것 필요 없음 커밋마다 pre-commit
pnpm test:integration test/**/*.int.spec.ts Testcontainers가 띄운 진짜 PostgreSQL PR 전 직접 실행

통합 테스트는 Docker로 DB를 띄우느라 몇 초가 걸린다. 그래서 커밋마다 돌리지 않고 따로 뺐다. 지금 API에는 단위 테스트가 없어서 pnpm test는 "테스트 없음"으로 통과한다.

pnpm test:integration을 실행하면 이 순서로 진행된다.

  1. globalSetup: 전체에서 딱 한 번 Docker로 PostgreSQL 컨테이너를 띄우고, 실제 마이그레이션(drizzle/*.sql)을 적용하고, 접속 주소를 테스트 쪽에 넘긴다.
  2. 테스트 파일: 테스트마다 반복 테이블 비우기 → 앱 조립 → 요청 → 응답 검증 → 앱 닫기.
  3. 정리: 전체에서 딱 한 번 globalSetup이 돌려준 함수가 컨테이너를 멈춘다.

Vitest 설정 파일 두 개

단위용: vitest.config.ts

test: {
  include: ['test/**/*.spec.ts'],
  // DB가 필요한 테스트는 vitest.integration.config.ts로 test:integration에서만 실행한다.
  exclude: [...configDefaults.exclude, 'test/**/*.int.spec.ts'],
  passWithNoTests: true,
},
  • *.int.spec.ts도 *.spec.ts 패턴에 걸리므로 exclude로 명시적으로 뺀다.
  • exclude를 직접 적으면 Vitest 기본값(node_modules 제외 등)을 덮어쓴다. 그래서 configDefaults.exclude를 펼쳐 기본값을 살려 두었다.
  • Vitest는 테스트 파일이 0개면 기본으로 실패한다. 지금은 0개가 정상 상태라 passWithNoTests를 켰다.

통합용: vitest.integration.config.ts

test: {
  include: ['test/**/*.int.spec.ts'],
  globalSetup: ['test/setup/postgres.ts'],
  hookTimeout: 120_000,
},
  • globalSetup은 테스트 파일들보다 먼저, 전체에서 한 번만 실행할 파일이다.
  • hookTimeout을 120초로 늘렸다. 처음 실행할 때는 postgres:18-alpine 이미지를 내려받느라 기본 10초로는 부족하다.

DB를 띄우고 마이그레이션 적용

test/setup/postgres.ts의 본문이다.

export default async function setup(project: TestProject) {
  const container = await new PostgreSqlContainer('postgres:18-alpine').start();
  const databaseUrl = container.getConnectionUri();

  const db = drizzle(databaseUrl);
  await migrate(db, { migrationsFolder: 'drizzle' });
  await db.$client.end();

  project.provide('databaseUrl', databaseUrl);

  return async () => {
    await container.stop();
  };
}

Testcontainers가 하는 일

코드에서 Docker에 "이 이미지로 컨테이너 하나 띄워 줘"라고 요청하는 라이브러리다. docker run을 코드로 하는 셈이다.

  • 포트는 비어 있는 아무 포트에 연결한다. 그래서 로컬 Compose의 PostgreSQL(5432)이 떠 있어도 충돌하지 않는다.
  • getConnectionUri()는 그렇게 정해진 포트와 계정이 담긴 postgres://... 주소를 돌려준다.

migrate(): 진짜 마이그레이션 적용

  • drizzle-orm의 함수다. drizzle/meta/_journal.json에 적힌 순서대로 drizzle/*.sql을 실행한다.
  • 로컬의 pnpm db:migrate(drizzle-kit CLI)와 같은 SQL 파일을 쓴다. 그래서 테스트가 통과하면 "이 마이그레이션이 빈 DB에 실제로 적용된다"까지 확인한 셈이다.
  • 끝나면 $client.end()로 연결을 닫는다. 마이그레이션용 연결이라 더 쓸 일이 없다.

스키마를 바꾸고 pnpm db:generate를 빼먹으면, 테스트 DB에는 새 컬럼이 없어 테스트가 깨진다. 이 테스트는 마이그레이션 누락을 잡는 장치이기도 하다.

provide와 inject: 주소를 테스트 파일에 넘기기

globalSetup과 테스트 파일은 다른 실행 환경에서 돈다. 테스트 파일은 별도 worker에서 실행되므로, setup에서 변수를 export해도 공유되지 않는다. 그래서 Vitest가 제공하는 통로를 쓴다.

globalSetup (메인 프로세스)
  1. 컨테이너 주소를 얻음
  2. project.provide('databaseUrl', 값)
테스트 파일 (worker)
  1. inject('databaseUrl')
  2. 같은 주소를 받음

파일 맨 위의 선언은 이 통로에 타입을 붙인다.

declare module 'vitest' {
  export interface ProvidedContext {
    databaseUrl: string;
  }
}

덕분에 inject('databaseUrl')이 string으로 추론되고, 키 이름에 오타를 내면 컴파일 오류가 난다.

정리 함수

globalSetup이 함수를 돌려주면, Vitest는 모든 테스트가 끝난 뒤 그 함수를 실행한다. 여기서 컨테이너를 멈춘다.

연결이 두 개다

test/shows.int.spec.ts의 준비와 정리 부분이다. 주석이 각 줄이 하는 일이다. 

describe('GET /shows', () => {
  // 테스트 코드가 쓸 DB 연결. globalSetup이 넘긴 컨테이너 주소로 만든다.
  // describe 본문은 파일을 읽을 때 바로 실행되므로, 아래 훅들보다 먼저 만들어진다.
  const db = drizzle(inject('databaseUrl'));

  // 테스트마다 새로 만들 앱을 담아 둘 변수. 훅과 테스트가 같이 쓰려고 바깥에 둔다.
  // <App>은 supertest가 받을 HTTP 서버 타입이다.
  let app: INestApplication<App>;

  // process.env.DATABASE_URL을 컨테이너 주소로 바꿔 둔다.
  // 앱이 readEnv()로 이 값을 읽어 컨테이너 DB에 붙는다.
  beforeAll(() => {
    vi.stubEnv('DATABASE_URL', inject('databaseUrl'));
  });

  afterAll(async () => {
    vi.unstubAllEnvs();      // 바꿔 둔 환경 변수를 원래 값으로 되돌린다
    await db.$client.end();  // 테스트 코드의 연결(Pool)을 닫는다
  });

  beforeEach(async () => {
    // shows를 비우고 id 번호를 1로 되돌린다. 모든 테스트가 빈 테이블에서 시작한다.
    await db.execute('TRUNCATE shows RESTART IDENTITY');

    // AppModule 전체로 모듈 그래프를 조립하고 프로바이더를 만든다.
    // 이때 DatabaseModule의 팩토리가 실행되어 앱의 DB 연결이 생긴다.
    const moduleRef = await Test.createTestingModule({
      imports: [AppModule],
    }).compile();

    app = moduleRef.createNestApplication(); // 조립된 모듈로 Nest 앱(Express 서버 포함)을 만든다
    await app.init();                        // 라우트를 연결한다. 포트는 열지 않는다
  });

  // 앱을 닫는다. 종료 훅(onApplicationShutdown)이 불려 앱의 DB 연결이 닫힌다.
  afterEach(async () => {
    await app.close();
  });

  // 테스트 두 개
});

테스트가 두 개일 때 실제 실행 순서는 이렇다.

  1. 파일을 읽을 때 describe 본문이 실행되어 테스트용 db가 만들어진다.
  2. beforeAll DATABASE_URL을 컨테이너 주소로 바꾼다.
  3. 테스트 1: beforeEach → 테스트 → afterEach 테이블 비우기, 앱 조립, 요청과 검증, 앱 닫기.
  4. 테스트 2: beforeEach → 테스트 → afterEach 같은 과정을 처음부터 다시 한다. 앱도 새로 만든다.
  5. afterAll 환경 변수를 되돌리고 테스트용 db의 연결을 닫는다.
연결 누가 쓰나 용도
테스트 파일의 db 테스트 코드 테이블 비우기, 테스트 데이터 넣기
앱의 DATABASE (DatabaseModule이 만듦) 실제 앱 코드 GET /shows 처리

둘 다 같은 컨테이너 DB를 보지만, 각자 자기 Pool을 가진 별개의 연결이다. 테스트가 db로 넣은 데이터를 앱이 자기 연결로 읽어 오는지 확인하는 구조다. 그래서 정리도 따로 한다. 테스트의 연결은 afterAll의 db.$client.end()가, 앱의 연결은 afterEach의 app.close()가 닫는다.

compile()은 무엇인가

TypeScript 컴파일과는 관계가 없다. "적어 둔 모듈 설정대로 실제 객체들을 만들어라"라는 뜻이다. 앱 조립은 두 단계로 나뉜다. 

const moduleRef = await Test.createTestingModule({ imports: [AppModule] }) // ① 설계도
  .compile(); // ② 실제로 만들기
  1. Test.createTestingModule(...): 설계도만 적는다 "AppModule로 앱을 만든다"는 설계도(TestingModuleBuilder)를 돌려준다. 아직 서비스도 DB 연결도 만들어지지 않았다. 그래서 이 사이에 .overrideProvider(DATABASE).useValue(가짜)처럼 일부를 갈아 끼울 수 있다.
  2. .compile(): 설계도대로 만든다 모듈을 훑어 무엇이 등록됐는지 파악하고, 필요한 것부터 순서대로 객체를 만든다. 결과로 moduleRef를 돌려준다.

이 저장소에서는 compile() 중에 이런 일이 일어난다.

compile()
  1. AppModule → DatabaseModule, ShowsModule 훑기
  2. DATABASE 팩토리 → readEnv() → drizzle(url)
  3. ShowsService 생성 (db 주입)
  4. ShowsController 생성

앱의 DB 연결이 바로 이때 생긴다. 만들어진 moduleRef로는 moduleRef.get(ShowsService)처럼 객체를 꺼내거나, 테스트 코드에서 compile() 다음 줄처럼 createNestApplication()으로 HTTP 앱을 만든다. 팩토리 중에는 비동기도 있을 수 있어서 모두 만들어질 때까지 await로 기다린다.

선택 읽기: compile()의 실제 코드

@nestjs/testing의 testing-module.builder.js를 줄인 것이다.

async compile(options = {}) {
  // ...
  await scanner.scan(this.module, { overrides: this.getModuleOverloads() }); // 모듈 훑기
  this.applyOverloadsMap();                         // overrideProvider로 바꾼 것 반영
  await this.createInstancesOfDependencies(/* */);  // 의존 순서대로 객체 생성
  // ...
  return testingModule;                             // 결과(moduleRef)
}

실제 앱(main.ts)과 비교

// main.ts: 훑기 + 객체 생성 + 앱 만들기를 한 번에
NestFactory.create(AppModule);

// 테스트: 단계를 나눈다
// ① 설계도
const builder = Test.createTestingModule({ imports: [AppModule] });
// ② 훑기 + 객체 생성
const moduleRef = await builder.compile();
// ③ 앱 만들기
const app = moduleRef.createNestApplication();

나눈 이유는 ①과 ② 사이에서 설계를 바꿀 수 있게 하기 위해서다.

객체를 만드는 시점이 같으므로 실패하는 곳도 대응한다. DATABASE_URL이 없으면 앱에서는 NestFactory.create가, 테스트에서는 compile()이 실패한다. vi.stubEnv를 beforeAll에서 먼저 하는 것도 compile()보다 먼저 값이 있어야 하기 때문이다.

앱을 테스트 DB에 붙이기

테스트에서 앱은 로컬 DB가 아니라 Testcontainers가 띄운 컨테이너 DB에 붙어야 한다. 그래서 beforeAll에서 vi.stubEnv로 앱이 읽는 환경 변수를 컨테이너 주소로 바꿔 둔다. 

vi.stubEnv('DATABASE_URL', inject('databaseUrl'));

그 뒤로는 앱이 평소와 똑같이 움직인다.

  1. compile() 중 DatabaseModule 팩토리 실행 readEnv()가 process.env.DATABASE_URL을 읽는다. 지금은 컨테이너 주소다.
  2. drizzle(url) 그 주소로 앱의 DB 연결을 만든다.

즉 운영에서 앱이 DB를 찾아가는 경로(readEnv() → 팩토리 → drizzle(url))를 테스트도 그대로 지나간다. 이 경로에 실수가 있으면 테스트가 잡는다. 예를 들어 readEnv()에서 변수 이름을 잘못 바꾸면, 테스트가 넣은 DATABASE_URL을 앱이 찾지 못해 compile()에서 실패한다.

afterAll의 vi.unstubAllEnvs()는 바꿔 둔 값을 원래대로 되돌린다. 테스트가 끝나면 손댄 것을 원래 상태로 돌려 두는 정리다.

선택 읽기: overrideProvider를 쓰지 않은 이유

Nest 테스트에서 DB를 바꿔 끼울 때 흔히 쓰는 방법은 overrideProvider다. NestJS 공식 테스트 문서가 이 방법을 보여 주고, 공식 @nestjs/drizzle 문서도 테스트에서 DB 토큰 자리에 가짜 객체를 넣는 방법을 보여 준다. 이 저장소의 001 문서도 처음에는 "DB를 붙이면 overrideProvider()로 바꿀 수 있다"고 안내했다. 그래서 "왜 그 방법을 쓰지 않았나"에 답해 둔다. 

await Test.createTestingModule({ imports: [AppModule] })
  .overrideProvider(DATABASE)
  .useValue(drizzle(inject('databaseUrl')))
  .compile();

이렇게 하면 DATABASE 자리에 미리 만든 객체가 바로 들어가서, readEnv()와 팩토리가 아예 실행되지 않는다. DATABASE_URL을 비운 채 이렇게 조립해도 성공하는 것을 실행해 확인했다. 테스트는 통과하지만, 위에서 말한 경로의 실수는 잡지 못하고 실제로 앱을 띄울 때에야 드러난다. 그래서 환경 변수를 바꾸는 방법을 골랐다.

overrideProvider가 맞는 경우도 있다. 실제 DB 없이 가짜 객체를 넣어 서비스 로직만 볼 때다. 이 저장소는 HTTP 경계에서 진짜 DB로 테스트하기로 했으므로 해당하지 않는다.

테스트끼리 섞이지 않게

TRUNCATE shows RESTART IDENTITY

  • 각 테스트는 빈 테이블에서 시작해야 한다. 앞 테스트가 넣은 데이터가 남아 있으면 "빈 목록" 테스트가 깨진다.
  • TRUNCATE만으로는 번호가 이어진다. RESTART IDENTITY는 id 번호도 1로 되돌린다. 그래서 테스트 순서나 개수와 상관없이 검증에 { id: 1, ... }처럼 고정된 값을 쓸 수 있다.

id가 매번 1부터 시작하므로 기대값을 { id: 1, title: '레미제라블' }처럼 그대로 적을 수 있다. 번호를 모르면 "DB에서 다시 조회한 값과 응답이 같은가"처럼 써야 하는데, 그러면 앱이 쓰는 쿼리와 같은 방식으로 기대값을 만들게 되어 쿼리가 틀려도 테스트가 통과할 수 있다.

테스트마다 앱을 새로 만든다

  • beforeEach에서 AppModule 전체를 조립한다. 컨트롤러만 따로 부르지 않으므로 모듈 연결, DI, 라우팅, DB 연결이 모두 검증된다.
  • afterEach의 app.close()가 DatabaseModule.onApplicationShutdown을 불러 앱의 Pool을 닫는다. 이게 없으면 테스트마다 Pool이 하나씩 쌓이고, 끝나도 프로세스가 종료되지 않을 수 있다.

테스트 두 개

it('공연이 없으면 빈 목록을 돌려준다', async () => {
  const response = await request(app.getHttpServer()).get('/shows');

  expect(response.status).toBe(200);
  expect(response.body).toEqual([]);
});

it('저장된 공연의 id와 title을 돌려준다', async () => {
  await db.insert(shows).values([{ title: '레미제라블' }, { title: '오페라의 유령' }]);

  const response = await request(app.getHttpServer()).get('/shows');

  expect(response.status).toBe(200);
  expect(response.body).toEqual([
    { id: 1, title: '레미제라블' },
    { id: 2, title: '오페라의 유령' },
  ]);
});
  • 준비는 DB에 직접, 검증은 HTTP 응답으로만 한다. 검증까지 DB 조회로 하면 내부 구현에 묶인다. 밖에서 보이는 결과인 응답만 본다.
  • 준비를 직접 insert로 하는 이유: 공연을 만드는 API가 아직 없다. CODING_STANDARDS.md에서 테스트 데이터 준비를 쓰기 규칙의 예외로 적은 것이 이 부분이다.
  • toEqual은 정확히 일치해야 통과한다. 응답에 다른 필드가 섞이거나 순서가 바뀌면 실패한다. 순서는 ShowsService의 orderBy(asc(shows.id))가 보장한다.

Turborepo 설정

"test": {
  "dependsOn": ["^build"],
  "env": ["DATABASE_URL"]
},
"dev": {
  "cache": false,
  "persistent": true,
  "env": ["DATABASE_URL"]
},
"test:integration": {
  "dependsOn": ["^build"],
  "env": ["DATABASE_URL"],
  "passThroughEnv": ["DOCKER_HOST", "TESTCONTAINERS_*"]
}
설정 작업에 전달 캐시 키에 포함 쓰는 곳
env 예 예. 값이 바뀌면 다시 실행 DATABASE_URL
passThroughEnv 예 아니오 DOCKER_HOST, TESTCONTAINERS_*
선언 안 함 아니오 아니오 그 외 모든 변수

Turborepo 2는 선언하지 않은 환경 변수를 작업에 아예 전달하지 않는다. 그래서 작업이 쓰는 변수는 두 칸 중 하나에 적어야 한다.

DOCKER_HOST, TESTCONTAINERS_*: 전달만 한다

Testcontainers가 Docker를 찾고 동작 방식을 정할 때 읽는 변수다. DOCKER_HOST는 Colima나 OrbStack처럼 Docker 소켓 위치가 기본과 다른 환경에서 쓰고, TESTCONTAINERS_로 시작하는 변수는 Testcontainers 자체 설정이다. 선언하지 않으면 그런 환경에서 통합 테스트가 Docker를 찾지 못한다. 값이 바뀌어도 테스트 결과는 같으므로 캐시 키에는 넣지 않았다.

DATABASE_URL: 지금은 읽는 테스트가 없다

test와 test:integration에 DATABASE_URL을 선언했지만, 지금 이 값을 실제로 읽는 테스트는 없다. 단위 테스트는 0개이고, 통합 테스트는 컨테이너 주소를 vi.stubEnv로 직접 넣는다. 티켓의 수용 기준 "환경 변수가 Turborepo에 선언되어 있어, 값이 바뀌면 캐시가 무효화된다"를 맞추고, 이 값을 읽는 테스트가 생겼을 때 오래된 캐시를 통과로 착각하지 않게 미리 선언해 두었다. dev에 선언한 것은 캐시 때문이 아니라, 셸에서 준 값이 앱까지 전달되게 하려는 것이다.

test:integration 결과도 캐시된다. 코드가 그대로면 두 번째 실행은 테스트를 실제로 돌리지 않고 지난 결과를 다시 보여 준다(cache hit). 강제로 다시 돌리려면 pnpm test:integration --force를 쓴다.

로컬 개발 DB와의 관계

항목 로컬 개발 (compose.yaml) 통합 테스트 (Testcontainers)
띄우는 방법 pnpm infra:up으로 직접 테스트가 자동으로
포트 5432 고정 빈 포트 아무거나
데이터 볼륨에 남음 테스트가 끝나면 컨테이너째 사라짐
마이그레이션 pnpm db:migrate (drizzle-kit) migrate() (drizzle-orm)
접속 주소 apps/api/.env provide / inject로 전달

두 환경은 완전히 분리되어 있다. 통합 테스트가 로컬 DB의 데이터를 지우는 일은 없다.

앞으로 조심할 점

지금은 통합 테스트 파일이 하나라 문제가 없다. 하지만 Vitest는 테스트 파일들을 병렬로 돌리고, 모든 파일이 컨테이너 DB 하나를 같이 쓴다.

1.3에서 orders.int.spec.ts 같은 파일이 생기면, 한 파일의 TRUNCATE가 다른 파일이 넣어 둔 데이터를 지울 수 있다. 실패가 실행할 때마다 달라지는 불안정한 테스트가 된다.

두 번째 통합 테스트 파일을 추가하는 티켓에서 아래 중 하나를 고른다.

방법 장점 단점
통합 설정에 fileParallelism: false 한 줄로 끝난다 파일이 늘수록 느려진다
파일마다 별도 데이터베이스(또는 스키마) 병렬로 빠르게 돈다 setup이 복잡해진다

스스로 확인하기

질문에 먼저 답해 본 뒤, 눌러서 답을 확인한다.

1. test/setup/postgres.ts에서 export const databaseUrl로 주소를 내보내고 테스트에서 import하면 왜 안 되는가?

globalSetup은 메인 프로세스에서, 테스트 파일은 별도 worker에서 실행된다. 테스트에서 import하면 파일이 worker에서 새로 실행될 뿐, setup이 만든 값을 받지 못한다. 그래서 provide와 inject를 쓴다.

2. beforeEach에서 RESTART IDENTITY를 빼면 어떤 테스트가 어떻게 깨지는가?

지금은 깨지지 않는다(실행해 확인했다). 첫 테스트가 아무것도 넣지 않아 번호가 소비되지 않고, 컨테이너도 실행마다 새로 만들어지기 때문이다. 하지만 TRUNCATE는 테이블만 비우고 번호는 이어 간다. insert하는 테스트가 앞에 하나 더 생기면 두 번째 테스트의 id가 3, 4가 되어 toEqual이 실패한다. 지금 통과하는 것은 우연이고, RESTART IDENTITY가 그 우연에 기대지 않게 해 준다.

3. 스키마에 venue 컬럼을 추가하고 db:generate를 잊은 채 test:integration을 돌리면 어떻게 되는가?

테스트 DB는 drizzle/*.sql로 만들어지므로 venue 컬럼이 없다. 앱이 그 컬럼을 조회하는 순간 PostgreSQL 오류가 나서 테스트가 실패한다. 마이그레이션 누락을 PR 전에 잡는다.

4. 코드를 바꾸지 않고 pnpm test:integration을 두 번 돌렸더니 두 번째가 1초도 안 걸렸다. 테스트가 정말 돌았는가?

아니다. Turborepo가 입력이 같다고 보고 지난 결과를 다시 보여 준 것이다(cache hit). 실제로 돌리려면 --force를 붙인다.

5. 로컬에서 pnpm infra:up으로 PostgreSQL을 띄워 둔 채 통합 테스트를 돌려도 되는가?

된다. Testcontainers는 별도 컨테이너를 빈 포트에 띄우므로 5432와 충돌하지 않는다. 로컬 DB의 데이터도 건드리지 않는다.
