01 필터 칩: 제어 컴포넌트와 useOptimistic

공연 목록의 장르와 판매 상태 칩(apps/store/src/shows/show-filter-chips.tsx)이 왜 제어 컴포넌트이고, 왜 useOptimistic과 startTransition을 쓰는지를 하나씩 빼 보면서 설명한다. 실험 결과는 개발 서버의 페이지 응답을 일부러 2초 늦춰 브라우저에서 직접 잰 값이다(Next 16.4.5, React 19.3.1). useOptimistic 자체의 원리, 특징, 다른 사용 사례는 react-next 11 문서에 있고, 이 문서는 필터 칩에 쓴 이유와 방법에 집중한다.

한눈에 보기

칩은 주소의 값을 그대로 보여 주는 제어 컴포넌트다. 그래서 초기화 링크나 뒤로 가기를 따라가고, 키보드 포커스도 잃지 않는다. 대신 주소가 바뀌기 전(서버 응답 전)에는 눌러도 켜지지 않는다. 이 공백을 useOptimistic으로 메운다. 고른 값을 임시로 먼저 보여 주고, 화면 이동이 끝나면 주소의 값으로 돌아간다.

방법 누르면 바로 켜짐 초기화·뒤로 가기를 따라감 포커스 유지
A. 비제어(defaultValue)OXO
A + keyOOX
B. 제어(value={query.genre})XOO
B + useOptimistic 지금 코드OOO
 
const [genre, setOptimisticGenre] = useOptimistic<string[]>(query.genre);

<ToggleGroup
  label="장르"
  items={GENRE_ITEMS}
  value={genre}
  onValueChange={(value) => {
    startTransition(() => {
      setOptimisticGenre(value);                          // ① 고른 값을 먼저 보여 준다
      router.replace(getGenreChangeHref({ query, value })); // ② 주소를 바꿔 진짜 값을 받아 온다
    });
  }}
/>

칩을 누르면 일어나는 일

필터 값은 주소(/?genre=musical&genre=play)에만 있다. 그래서 새로고침이나 공유를 해도, 상세에서 돌아와도 필터가 남는다. 주소를 읽고 만드는 함수는 store-logic 00 문서에 있다.

  1. 칩을 누른다 onValueChange가 새 선택(['musical', 'play'])을 받는다.
  2. 주소를 바꾼다 router.replace('/?genre=musical&genre=play'). 방문 기록을 쌓지 않으려고 push 대신 replace를 쓴다.
  3. 서버가 다시 그린다 서버의 page.tsx가 새 주소로 API를 불러 목록을 만든다. 여기서 시간이 걸린다.
  4. 새 query가 내려온다 칩 컴포넌트가 새 query(query.genre = ['musical', 'play'])를 props로 받는다.

이 문서의 질문은 하나다. 칩이 "지금 무엇이 켜져 있는지"를 어디에 기억할까?

방법 A: 칩이 스스로 기억한다

<ToggleGroup defaultValue={query.genre} onValueChange={...} />

defaultValue를 주면 칩(ToggleGroup)은 처음 그릴 때 그 값을 자기 안에 복사해 둔다. 그다음부터는 누를 때마다 자기가 들고 있는 값을 바꾼다. 이런 컴포넌트를 비제어 컴포넌트라고 한다. 누르면 바로 켜지므로 반응은 빠르다.

문제는 칩을 누르지 않고 주소가 바뀔 때다. defaultValue는 처음 한 번만 읽기 때문이다.

  1. "뮤지컬"을 누른다 칩의 기억: [뮤지컬], 주소: ?genre=musical
  2. "조건 초기화" 링크를 누른다 주소: /(장르 없음). 목록은 전체 공연으로 바뀐다.
  3. 칩은 그대로다 칩은 주소가 바뀐 것을 모르니 [뮤지컬]이 켜진 채로 남는다.

뒤로 가기도 같다. 화면의 칩과 실제 목록이 서로 다른 말을 한다.

A를 key로 고치면: 포커스가 사라진다

비제어 컴포넌트가 주소를 따라가게 하는 흔한 방법은 주소가 바뀔 때 컴포넌트를 새로 만드는 것이다.

<ToggleGroup key={query.genre.join()} defaultValue={query.genre} />

React는 key가 바뀌면 이전 컴포넌트를 버리고 새로 만든다(리마운트). 새로 만들 때 defaultValue를 다시 읽으니 초기화와 뒤로 가기는 해결된다. 정렬 Select가 이 방법을 쓴다(react-next 09 문서).

그런데 칩을 직접 눌러도 주소가 바뀌므로 칩 줄을 새로 만든다. 키보드로 쓰는 사람에게 문제가 생긴다.

  1. Tab으로 "연극"까지 가서 Space로 누른다 포커스가 "연극" 버튼에 있다.
  2. 주소가 바뀌어 key가 바뀐다 React가 칩 줄을 버리고 새 버튼들을 만든다.
  3. 포커스가 튄다 포커스를 갖고 있던 버튼이 문서에서 사라졌으니 포커스가 페이지 맨 앞(body)으로 간다.
  4. 처음부터 다시 "콘서트"도 고르려면 Tab을 처음부터 다시 눌러야 한다.

정렬 Select는 하나를 고르면 끝나므로 이 문제가 작다. 칩은 여러 개를 이어서 고르는 경우가 많아 그냥 둘 수 없다.

방법 B: 받은 값만 보여 준다

<ToggleGroup value={query.genre} onValueChange={...} />

value를 주면 칩은 아무것도 기억하지 않고 받은 값을 그대로 보여 준다. 이런 컴포넌트를 제어 컴포넌트라고 한다. 칩의 값을 정하는 것은 칩이 아니라 부모가 넘긴 query.genre, 곧 주소다.

  • 초기화와 뒤로 가기: 주소가 바뀌면 query.genre가 바뀌고 칩도 바뀐다. 해결.
  • 포커스: 칩 줄을 새로 만들지 않고 aria-pressed 같은 속성만 바꾼다. 누른 버튼이 그대로 있으니 포커스도 남는다. 해결.

대신 새 문제가 생긴다. 칩은 주소의 값만 보여 주므로, 주소가 바뀌기 전에는 눌러도 켜지지 않는다. 서버 응답을 2초 늦추고 "연극"을 누른 뒤 0.3초 뒤에 "콘서트"를 누른 기록이다. 

    0ms  "연극" 클릭     연극=꺼짐  콘서트=꺼짐  주소=/
  302ms  "콘서트" 클릭   연극=꺼짐  콘서트=꺼짐  주소=/
 2376ms  화면 바뀜       연극=꺼짐  콘서트=켜짐  주소=?genre=concert
  • 반응이 없다: 2초 넘게 눌렀는지 알 수 없다.
  • 앞의 클릭이 사라진다: "콘서트"를 누를 때 ToggleGroup은 화면에 보이는 값(아직 [])에 콘서트를 더해 ['concert']를 넘긴다. "연극"은 주소에 반영되기 전이라 빠진다.

응답 전까지 고른 값을 먼저 보여 준다

useOptimistic은 "진짜 값이 올 때까지 잠깐 보여 줄 값"을 두는 훅이다. 진짜 값을 인자로 받고, 보여 줄 값과 임시 값을 넣는 함수를 돌려준다. 

const [genre, setOptimisticGenre] = useOptimistic(query.genre);
// genre: 평소에는 query.genre 그대로. 임시 값을 넣으면 화면 이동이 끝날 때까지 그 값

칩에는 query.genre 대신 genre를 넘긴다. 같은 실험을 지금 코드로 한 기록이다.

    0ms  "연극" 클릭     연극=꺼짐  콘서트=꺼짐  주소=/
    5ms  화면 바뀜       연극=켜짐  콘서트=꺼짐  주소=/              ← 임시 값
  302ms  "콘서트" 클릭
  305ms  화면 바뀜       연극=켜짐  콘서트=켜짐  주소=/              ← 임시 값
 2337ms  주소 바뀜       연극=켜짐  콘서트=켜짐  주소=?genre=play&genre=concert
  • 바로 켜진다: 5ms 만에 켜졌다.
  • 앞의 클릭이 남는다: "콘서트"를 누를 때 ToggleGroup이 보는 값이 임시 값 ['play']라서 ['play', 'concert']를 넘긴다.
  • 진짜 값이 오면 바꿔 끼운다: 2.3초에 주소가 바뀌고 query.genre가 임시 값과 같아져 화면은 그대로다.

첫 번째 router.replace(?genre=play)의 화면은 그려지지 않았다. 두 번째 이동이 앞의 이동을 대신했기 때문이다. 서버에 간 요청이 하나 더 있었을 뿐, 화면에는 마지막 선택만 나온다.

임시 값은 언제 사라지나

임시 값이 너무 빨리 사라지면 칩이 다시 꺼지고, 너무 오래 남으면 주소와 어긋난다. React가 정한 규칙은 이렇다.

setOptimistic을 부르면 임시 값은 바로 화면에 그려진다. 그리고 그 순간의 transition 차선에 "여기가 끝나면 임시 값을 버린다"는 표시를 남긴다. 그 차선의 화면이 다 그려지면(커밋되면) 임시 값을 버리고 인자로 받은 진짜 값을 보여 준다.

transition은 "급하지 않은 화면 갱신"을 뜻한다. startTransition(() => { ... }) 안에서 일어난 갱신이 transition이 되고, React는 이런 갱신을 차선(lane)이라는 번호표로 묶어 함께 처리한다. 같은 차선의 갱신은 함께 그려지고 함께 끝난다.

여기서 중요한 사실이 둘 있다.

  1. router.replace는 스스로 startTransition을 연다 Next의 화면 이동은 안에서 startTransition으로 라우터 상태를 바꾼다. 새 페이지가 서버에서 올 때까지 이 차선의 그리기는 기다린다(끝나지 않는다).
  2. 한 이벤트 안의 transition은 같은 차선을 쓴다 클릭 하나를 처리하는 동안 연 transition은 몇 개든 같은 차선 번호를 받는다. 그래서 setOptimisticGenre가 남긴 표시와 router.replace의 화면 이동이 같은 차선에 묶인다.

두 사실을 합치면, 임시 값을 버리는 시점이 "새 페이지가 서버에서 와서 그려지는 시점"과 정확히 같아진다. 그 사이에 옛 값이 끼어들 틈이 없다.

선택 읽기: React와 Next 소스에서 확인하기

react-dom-client.development.js(19.3.1)를 줄여 옮겼다. 임시 값은 즉시 그리는 차선(2)에 넣고, 되돌릴 차선은 지금 이벤트의 transition 차선으로 정한다.

function dispatchOptimisticSetState(fiber, throwIfDuringRender, queue, action) {
  null === ReactSharedInternals.T && 0 === currentEntangledLane &&
    console.error('An optimistic state update occurred outside a transition or action. ...');
  action = {
    lane: 2,                              // 바로 그린다
    revertLane: requestTransitionLane(),  // 이 차선이 끝나면 되돌린다
    action, ...
  };
  ...
}

function requestTransitionLane() {
  if (0 === currentEventTransitionLane) {
    // 이 이벤트에서 처음 요청하면 새 차선을 하나 고른다
    currentEventTransitionLane = ...;
  }
  return currentEventTransitionLane;    // 같은 이벤트 안에서는 늘 같은 차선
}

next/dist/client/components/sequential-router-queue.js(16.4.5)의 화면 이동도 startTransition 안에서 라우터 상태를 바꾼다.

  navigate(href, 'replace', ...);
}
function navigate(...) {
  ...
  startTransition(() => { /* 라우터 상태를 바꾼다 */ });
}

네 가지로 바꿔 실험하기

코드를 네 가지로 바꿔 "연극"을 한 번 누르고, 칩의 aria-pressed가 바뀌는 순간을 모두 기록했다. 서버 응답은 2초 늦췄다.

코드 기록 결과
지금 코드 같은 startTransition 안에 둘 다 5ms 켜짐 → 2.0초 주소 바뀜(계속 켜짐) 깜빡임 없음
startTransition은 setOptimisticGenre만 감싸고, router.replace는 바로 다음 줄 3ms 켜짐 → 2.0초 주소 바뀜(계속 켜짐) 깜빡임 없음. 같은 이벤트라 같은 차선이다
startTransition 없이 두 줄만 11ms 켜짐 → 2.1초 주소 바뀜(계속 켜짐) 동작은 같지만 React가 콘솔에 오류를 찍는다
router.replace를 setTimeout(..., 0)으로 다음 차례에 8ms 켜짐 → 14ms 꺼짐 → 2.1초 다시 켜짐 깜빡임. 다른 이벤트라 다른 차선이다

마지막 줄이 규칙을 잘 보여 준다. router.replace가 다른 이벤트에서 열리면 다른 차선을 받는다. 그러면 임시 값을 버릴 차선에는 임시 값 하나만 들어 있어 6ms 만에 끝나고, 칩은 아직 옛 값인 query.genre로 돌아가 꺼진다. 새 페이지가 온 2.1초에 다시 켜진다. 

// 세 번째 줄의 코드. 콘솔에 아래 오류가 찍힌다
setOptimisticGenre(value);
router.replace(getGenreChangeHref({ query, value }));
An optimistic state update occurred outside a transition or action. To fix, move the update to an action, or wrap with startTransition.

그래도 같은 startTransition에 넣는 이유

실험으로 보면 둘째, 셋째 줄도 지금은 깜빡이지 않는다. 그래도 지금 코드처럼 쓰는 이유가 있다.

  • setOptimistic은 transition 안에서 부르라고 정해져 있다. 셋째 줄처럼 밖에서 부르면 React가 오류를 찍는다. 지금 동작하는 것은 React가 경고만 하고 넘어가 주기 때문이다.
  • "화면 이동이 끝날 때까지"라는 관계가 코드에 드러난다. 둘째 줄은 "한 이벤트 안의 transition은 같은 차선"이라는 React 내부 규칙에 기대어 우연히 맞는다. 나중에 누가 router.replace 앞에 await나 setTimeout을 넣으면 넷째 줄처럼 깜빡인다. 같은 startTransition 안에 두면 "이 임시 값은 이 화면 이동과 한 묶음"이라는 뜻을 코드만 보고 알 수 있다.
  • React 문서의 예도 이 모양이다. 임시 값을 넣는 일과 실제 작업을 같은 transition(action) 안에 둔다.

덤으로 얻는 것

useState로 화면용 복사본을 두면 "언제 복사본을 버리고 주소 값으로 돌아갈지"를 직접 짜야 한다. 초기화 링크나 뒤로 가기로 주소가 바뀔 때 복사본을 맞추는 useEffect가 필요하고, 그 코드가 다시 비제어 컴포넌트의 문제를 만든다. useOptimistic은 transition이 끝나면 언제나 진짜 값으로 돌아가므로 이런 코드가 없다.

  • 초기화 링크, 뒤로 가기: 임시 값을 넣은 적이 없으니 처음부터 주소 값(query.genre)이 보인다.
  • 칩 클릭: 화면 이동이 끝날 때까지만 고른 값이 보이고, 그 뒤로는 다시 주소 값이 보인다.

헷갈리기 쉬운 점

  • 임시 값은 상태가 아니다. useOptimistic은 값을 저장해 두지 않는다. 진짜 값 위에 잠깐 덮어 보여 주는 것이고, 덮개는 transition이 끝나면 걷힌다.
  • 제어 컴포넌트는 "누르면 바로 켜짐"을 공짜로 주지 않는다. value를 주는 순간 칩은 부모가 바꿔 줄 때만 바뀐다. 부모의 값이 서버에서 온다면 그 사이를 메울 방법(여기서는 useOptimistic)이 필요하다.
  • key는 값을 다시 채우는 도구이지 동기화 도구가 아니다. 주소가 바뀔 때마다 컴포넌트를 새로 만드는 것이라 포커스, 열림 상태, 입력 중인 글자 같은 것이 모두 사라진다.
  • router.replace를 쓴 이유와 useOptimistic을 쓴 이유는 다르다. replace는 방문 기록을 쌓지 않으려고, useOptimistic은 응답 전 공백을 메우려고 쓴다. push를 써도 이 문서의 내용은 그대로다.

확인 문제

1. 칩을 이렇게 바꾸면 "조건 초기화" 링크를 눌렀을 때 칩은 어떻게 되는가?

방법 A 절. "뮤지컬"이 켜진 상태에서 초기화 링크를 누른다고 생각한다.

 <ToggleGroup
-  value={genre}
+  defaultValue={query.genre}
   onValueChange={...}
 />
답 보기

목록은 전체 공연으로 바뀌지만 "뮤지컬" 칩은 켜진 채로 남는다. defaultValue는 처음 그릴 때만 읽고, 그 뒤로는 칩이 자기 안의 값을 보여 준다. 초기화 링크는 칩을 누르지 않고 주소만 바꾸므로 칩이 알 방법이 없다.

2. router.replace를 아래처럼 setTimeout으로 미루면 칩은 어떻게 보이는가?

임시 값은 언제 사라지나와 실험 표의 넷째 줄. 서버 응답은 2초 걸린다.

 onValueChange={(value) => {
   startTransition(() => {
     setOptimisticGenre(value);
-    router.replace(getGenreChangeHref({ query, value }));
   });
+  setTimeout(() => router.replace(getGenreChangeHref({ query, value })), 0);
 }}
답 보기

켜졌다가 바로 꺼지고, 2초 뒤에 다시 켜진다. setTimeout 안의 router.replace는 다른 이벤트라 다른 차선을 받는다. 임시 값을 버릴 차선에는 임시 값 하나만 있어 곧바로 끝나고, 칩은 아직 옛 값인 query.genre로 돌아간다. 실험에서는 8ms에 켜지고 14ms에 꺼졌다.

3. useOptimistic 없이 value={query.genre}만 두고 "연극"과 "콘서트"를 빠르게 누르면 주소는 어떻게 되는가?

방법 B 절. 두 클릭 사이는 0.3초, 서버 응답은 2초 걸린다.

답 보기

?genre=concert가 된다. "콘서트"를 누를 때 칩에 보이는 값은 아직 []라서 ToggleGroup이 ['concert']를 넘긴다. "연극"은 주소에 반영되기 전이라 사라진다. useOptimistic이 있으면 보이는 값이 임시 값 ['play']라서 ?genre=play&genre=concert가 된다.
