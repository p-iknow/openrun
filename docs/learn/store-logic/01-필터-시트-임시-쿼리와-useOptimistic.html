01 필터 시트: 임시 쿼리, 제어 컴포넌트, useOptimistic

공연 목록의 필터 줄(apps/store/src/shows/show-filter-bar.tsx)과 필터 시트(apps/store/src/shows/show-filter-sheet.tsx)가 왜 고른 값을 주소와 따로 둔 임시 쿼리에 두는지, 왜 시트의 칩이 제어 컴포넌트인지, 적용한 뒤에 왜 useOptimistic과 startTransition을 쓰는지 하나씩 빼 보면서 설명한다. useOptimistic 자체의 원리, 특징, 다른 사용 사례는 react-next 11 문서에 있고, 이 문서는 필터 시트에 쓴 이유와 방법에 집중한다.

한눈에 보기

시트에서 고른 값은 임시 쿼리(draft)에만 두고, "적용"을 누를 때 한 번에 주소에 넣는다. 시트의 칩은 draft를 그대로 보여 주는 제어 컴포넌트다. 그래서 "초기화"처럼 바깥에서 값을 바꿔도 칩이 따라가고, 키보드 포커스도 잃지 않는다. 적용한 뒤 서버가 새 목록을 그릴 때까지는 칩 이름과 필터 점에 useOptimistic으로 적용한 값을 먼저 보인다.

값 어디에 두나 누가 보나
query주소(서버가 정리해 props로 내려 준다)목록. 필터 줄에서는 shownQuery의 바탕
shownQuery필터 줄의 useOptimistic(query)필터 줄의 칩 이름과 필터 점, 시트를 열 때의 처음 값
draft필터 시트의 useState시트 안의 칩. 적용하면 시트가 필터 줄에 돌려준다
 
// 필터 줄(ShowFilterBar)
const [shownQuery, setShownQuery] = useOptimistic(query);

// 필터 시트(ShowFilterSheet)
const [draft, setDraft] = useState(initialQuery);
<ToggleGroup
  label="장르"
  items={GENRE_ITEMS}
  value={draft.genre}
  onValueChange={(value) => {
    setDraft(getGenreChangeQuery({ query: draft, value }));
  }}
/>
// 필터 줄: 시트가 "적용"으로 돌려준 쿼리를 주소에 넣는다
if (next === null) return;
startTransition(() => {
  setShownQuery(next);
  router.replace(getFilterApplyHref(next));
});

필터 줄과 시트가 하는 일

목록 화면(apps/store/app/page.tsx)은 화면 폭과 관계없이 필터 줄 하나(ShowFilterBar)를 둔다. NOL 티켓 모바일 검색 결과처럼 왼쪽에 [장르 ▾][판매 상태 ▾] 칩을 두고(넘치면 가로 스크롤), 오른쪽에 [필터]와 [정렬] 버튼을 고정한다. 칩과 필터 버튼은 같은 필터 시트를 열고, 칩으로 열면 그 칩의 부분으로 스크롤한다. 좁은 화면에서는 아래에서 올라오는 시트(store-ui Drawer)로, 넓은 화면(sm, 640px 이상)에서는 가운데 뜨는 창(store-ui Dialog)으로 연다(picker-sheet.tsx). 어느 쪽으로 열지는 여는 순간 openPickerSheet가 matchMedia로 정하므로, 그릴 때 화면 폭을 읽지 않는다. 정렬은 따로 정렬 시트(show-sort-sheet.tsx)를 연다.

시트는 openPickerSheet로 연다. 이 함수는 창 종류를 정한 뒤 overlay-kit의 overlay.openAsync로 시트를 그리고 Promise를 돌려준다. 시트가 controller.close(값)을 부르면 Promise가 그 값으로 끝난다. 필터 시트는 "적용"이면 고친 쿼리를, 그 밖의 방법으로 닫으면 null을 돌려준다. 필터 줄은 그 결과를 받아 주소를 바꾼다. 그래서 열림 상태와 고르는 중인 값은 시트가 갖고, 필터 줄은 여는 일과 결과를 적용하는 일만 한다.

필터 값은 주소(/?genre=musical&genre=play)에 남는다. 그래서 새로고침이나 공유를 해도, 상세에서 돌아와도 필터가 그대로다. 주소를 읽고 만드는 함수는 store-logic 00 문서에 있다.

  1. 칩이나 필터 버튼을 누른다 openFilterSheet가 새 필터 시트를 연다. 시트의 draft는 지금 보이는 쿼리(shownQuery)로 시작한다.
  2. 시트에서 고른다 칩을 누를 때마다 draft만 바뀐다. 주소와 목록은 그대로다.
  3. 적용을 누른다 시트가 controller.close(draft)로 닫히고, 필터 줄이 받은 쿼리로 router.replace한다. 방문 기록을 쌓지 않으려고 push 대신 replace를 쓴다.
  4. 서버가 다시 그린다 서버의 page.tsx가 새 주소로 API를 불러 목록을 만든다. 여기서 시간이 걸린다.
  5. 새 query가 내려온다 ShowFilterBar가 새 query를 props로 받는다.

필터 줄의 칩 이름은 고른 값이다. 고른 장르가 없으면 "장르", 있으면 getGenreChipLabel이 "뮤지컬,연극"처럼 쉼표로 잇는다. 필터가 하나라도 걸려 있으면 필터 버튼에 점을 단다.

고른 값은 임시 쿼리에 둔다

칩을 누를 때마다 주소를 바꿀 수도 있다. 그러면 시트에 가린 목록이 칩마다 서버에서 다시 그려진다. 사용자는 시트에 가려 목록을 보지 못하는데, 요청만 칩 수만큼 간다. 그래서 시트 안에서는 draft만 바꾸고, "적용"으로 한 번에 주소에 넣는다. NOL 티켓 모바일 필터 시트도 이렇게 동작한다.

draft는 장르와 판매 상태를 나누지 않고 쿼리 전체(ShowListQuery) 하나로 둔다. 다음 값은 getGenreChangeQuery, getStatusChangeQuery(show-list-query.ts)가 draft에서 만든다. 이 함수들은 주소의 genre, status를 정리할 때와 같은 규칙으로 모르는 값을 버리고 선택지 순서로 맞춘다. 주소가 아니라 쿼리를 돌려주므로 draft에 그대로 넣고, 적용하면 필터 줄이 getFilterApplyHref로 주소를 만든다.

draft는 브라우저 안의 상태라 칩을 누르면 바로 켜진다. 서버를 기다리지 않으니 시트 안에서는 useOptimistic이 필요 없다.

남은 질문은 이것이다. 시트의 칩이 "지금 무엇이 켜져 있는지"를 어디에 기억할까?

방법 A: 칩이 스스로 기억한다

<ToggleGroup
  defaultValue={draft.genre}
  onValueChange={(value) => setDraft(getGenreChangeQuery({ query: draft, value }))}
/>

defaultValue를 주면 칩(ToggleGroup)은 처음 그릴 때 그 값을 자기 안에 복사해 둔다. 그다음부터는 누를 때마다 자기가 들고 있는 값을 바꾼다. 이런 컴포넌트를 비제어 컴포넌트라고 한다. onValueChange로 draft에도 적어 두면 적용할 값은 맞는다.

문제는 칩을 누르지 않고 draft가 바뀔 때다. defaultValue는 처음 한 번만 읽기 때문이다.

  1. 시트에서 "뮤지컬"을 누른다 칩의 기억: [뮤지컬], draft.genre: ['musical']
  2. "초기화"를 누른다 draft.genre: []
  3. 칩은 그대로다 칩은 draft가 바뀐 것을 모르니 [뮤지컬]이 켜진 채로 남는다.

화면의 칩과 적용될 값이 서로 다른 말을 한다. 이대로 적용하면 켜진 칩과 달리 장르 필터가 없는 목록이 나온다.

시트를 여는 것만 보면 비제어로도 된다. 시트는 열 때마다 새로 그려지므로 defaultValue도 열 때마다 처음 값을 다시 읽는다. 문제는 시트가 열려 있는 동안 바깥에서 값을 바꾸는 "초기화"다.

A를 key로 고치면: 포커스가 사라진다

비제어 컴포넌트가 바깥 값을 따라가게 하는 흔한 방법은 값이 바뀔 때 컴포넌트를 새로 만드는 것이다.

<ToggleGroup key={draft.genre.join()} defaultValue={draft.genre} />

React는 key가 바뀌면 이전 컴포넌트를 버리고 새로 만든다(리마운트). 새로 만들 때 defaultValue를 다시 읽으니 초기화는 해결된다. 검색 폼이 주소의 검색어를 key로 두는 것도 이 방법이다(react-next 09 문서).

그런데 칩을 직접 눌러도 draft.genre가 바뀌므로 칩 묶음을 새로 만든다. 키보드로 쓰는 사람에게 문제가 생긴다.

  1. Tab으로 "연극"까지 가서 Space로 누른다 포커스가 "연극" 버튼에 있다.
  2. draft.genre가 바뀌어 key가 바뀐다 React가 칩 묶음을 버리고 새 버튼들을 만든다.
  3. 포커스를 잃는다 포커스를 갖고 있던 버튼이 문서에서 사라졌다.
  4. 처음부터 다시 "콘서트"도 고르려면 다시 Tab으로 찾아가야 한다.

검색 폼은 제출해야 검색어가 바뀌므로 입력하는 도중에 새로 만들 일이 없다. 칩은 여러 개를 이어서 고르는 경우가 많아 누를 때마다 새로 만들면 그냥 둘 수 없다.

방법 B: 임시 쿼리를 그대로 보여 준다

<ToggleGroup value={draft.genre} onValueChange={...} />

value를 주면 칩은 아무것도 기억하지 않고 받은 값을 그대로 보여 준다. 이런 컴포넌트를 제어 컴포넌트라고 한다. 칩의 값을 정하는 것은 칩이 아니라 부모가 넘긴 draft.genre다. 값이 있는 곳이 하나뿐이라 화면과 적용될 값이 어긋날 틈이 없다.

  • 초기화: setDraft({ ...draft, genre: [], status: [] })로 draft를 비우면 칩도 꺼진다. 해결.
  • 포커스: 칩 묶음을 새로 만들지 않고 aria-pressed 같은 속성만 바꾼다. 누른 버튼이 그대로 있으니 포커스도 남는다. 해결.

store-ui ToggleGroup의 value 설명(packages/store-ui/src/toggle-group.tsx)도 이 경우를 든다. 시트의 임시 값처럼 바깥에서 값을 바꿔야 할 때 제어로 쓰고, 칩을 새로 만들지 않아 누른 칩의 포커스가 남는다.

닫으면 버리고, 열 때마다 새로 시작한다

async function openFilterSheet(section: FilterSection) {
  const next = await openPickerSheet<ShowListQuery>((controller) => (
    <ShowFilterSheet
      controller={controller}
      initialQuery={shownQuery}
      section={section}
    />
  ));
  if (next === null) return;
  applyQuery({ next, href: getFilterApplyHref(next) });
}

// 창이 돌려준 결과를 먼저 보이고 주소를 바꾼다. 같은 transition이라 새 목록이 올 때까지 보인 값이 남는다.
function applyQuery({ next, href }: { next: ShowListQuery; href: string }) {
  startTransition(() => {
    setShownQuery(next);
    router.replace(href);
  });
}

시트는 열 때마다 새로 그려지고, 닫히는 움직임이 끝나면(onCloseComplete에 넘긴 unmount) 트리에서 빠진다. 그래서 draft는 열 때 받은 initialQuery로 늘 새로 시작한다. 적용하지 않고 닫으면(바깥 누르기, Esc 등) 시트가 controller.close(null)을 부르고, 고르던 draft는 시트와 함께 사라진다. 다시 열 때 채울 코드가 따로 없다.

initialQuery에는 query가 아니라 shownQuery를 넘긴다. 적용한 직후 서버가 답하기 전에 다시 열어도, 아직 옛 값인 query가 아니라 방금 적용한 값으로 시트가 열린다.

"초기화"는 시트 안의 장르와 판매 상태 선택만 지우고 시트를 닫지 않는다. 검색어와 정렬은 시트에서 고르는 값이 아니므로 그대로 둔다. 주소는 적용할 때 바뀐다.

응답 전까지 적용한 값을 먼저 보여 준다

적용을 누르면 시트는 바로 닫히지만, 새 query는 서버가 새 목록을 그린 뒤에야 내려온다. 필터 줄이 query를 그대로 보여 주면 그동안 칩 이름은 옛 값("장르")이고 필터 점도 없다. 방금 고른 것이 반영되지 않은 것처럼 보인다.

useOptimistic은 "진짜 값이 올 때까지 잠깐 보여 줄 값"을 두는 훅이다. 진짜 값을 인자로 받고, 보여 줄 값과 임시 값을 넣는 함수를 돌려준다. 

const [shownQuery, setShownQuery] = useOptimistic(query);
// shownQuery: 평소에는 query 그대로. 임시 값을 넣으면 화면 이동이 끝날 때까지 그 값

필터 줄은 query 대신 shownQuery로 칩 이름, 칩의 고른 모양, 필터 점을 정한다.

const hasFilter = shownQuery.genre.length > 0 || shownQuery.status.length > 0;
<FilterBarButton
  selected={shownQuery.genre.length > 0}
  onClick={() => {
    void openFilterSheet('genre');
  }}
>
  <span className="max-w-[160px] truncate">
    {getGenreChipLabel(shownQuery.genre)}
  </span>
  <ChevronDownIcon />
</FilterBarButton>
  • 바로 바뀐다: 적용을 누르자마자 칩 이름이 "뮤지컬,연극"이 되고 필터 점이 붙는다.
  • 진짜 값이 오면 바꿔 끼운다: 새 query가 내려올 때 화면 이동이 끝나고 임시 값이 걷힌다. 그때 query는 임시 값과 같은 조건이라 화면은 그대로다.

임시 값에는 시트가 돌려준 쿼리(next, 시트의 draft)를 그대로 넣는다. 그 page는 3처럼 남아 있을 수 있지만, 필터 줄은 장르와 판매 상태만 보므로 상관없다. 주소는 getFilterApplyHref가 page를 빼서 만든다.

임시 값은 언제 사라지나

임시 값이 너무 빨리 사라지면 칩 이름이 옛 값으로 돌아갔다가 다시 바뀌고, 너무 오래 남으면 주소와 어긋난다. React가 정한 규칙은 이렇다.

setOptimistic을 부르면 임시 값은 바로 화면에 그려진다. 그리고 그 순간의 transition 차선에 "여기가 끝나면 임시 값을 버린다"는 표시를 남긴다. 그 차선의 화면이 다 그려지면(커밋되면) 임시 값을 버리고 인자로 받은 진짜 값을 보여 준다.

transition은 "급하지 않은 화면 갱신"을 뜻한다. startTransition(() => { ... }) 안에서 일어난 갱신이 transition이 되고, React는 이런 갱신을 차선(lane)이라는 번호표로 묶어 함께 처리한다. 같은 차선의 갱신은 함께 그려지고 함께 끝난다.

여기서 중요한 사실이 둘 있다.

  1. router.replace는 스스로 startTransition을 연다 Next의 화면 이동은 안에서 startTransition으로 라우터 상태를 바꾼다. 새 페이지가 서버에서 올 때까지 이 차선의 그리기는 기다린다(끝나지 않는다).
  2. 이어서 실행되는 transition은 같은 차선을 쓴다 React는 지금 처리하는 차례에서 처음 고른 transition 차선을 기억해 두고, 그 차례에 연 transition에 몇 번이든 같은 번호를 준다. 필터 줄은 시트가 돌려준 결과를 받은 뒤 한 startTransition 안에서 두 줄을 이어서 부르므로, setShownQuery가 남긴 표시와 router.replace의 화면 이동이 같은 차선에 묶인다.

두 사실을 합치면, 임시 값을 버리는 시점이 "새 페이지가 서버에서 와서 그려지는 시점"과 정확히 같아진다. 그 사이에 옛 값이 끼어들 틈이 없다.

같은 startTransition에 넣는 이유

setShownQuery와 router.replace를 같은 startTransition 안에서 부르는 이유는 이렇다.

  • setOptimistic은 transition 안에서 부르라고 정해져 있다. 밖에서 부르면 React가 콘솔에 An optimistic state update occurred outside a transition or action. 오류를 찍는다.
  • "화면 이동이 끝날 때까지"라는 관계가 코드에 드러난다. 같은 startTransition 안에 두면 "이 임시 값은 이 화면 이동과 한 묶음"이라는 뜻을 코드만 보고 알 수 있다. 임시 값은 자기를 넣은 transition이 끝날 때 걷히므로, 화면 이동을 같은 transition에 넣어야 새 목록이 올 때까지 남는다.
  • React 문서의 예도 이 모양이다. 임시 값을 넣는 일과 실제 작업을 같은 transition(action) 안에 둔다.

덤으로 얻는 것

useState로 화면용 복사본을 두면 "언제 복사본을 버리고 주소 값으로 돌아갈지"를 직접 짜야 한다. 결과가 없을 때의 "조건 초기화" 링크나 뒤로 가기로 주소가 바뀔 때 복사본을 맞추는 useEffect가 필요하다. useOptimistic은 transition이 끝나면 언제나 진짜 값으로 돌아가므로 이런 코드가 없다.

  • 조건 초기화 링크, 뒤로 가기: 임시 값을 넣은 적이 없으니 처음부터 주소 값(query)이 보인다.
  • 적용: 화면 이동이 끝날 때까지만 적용한 값이 보이고, 그 뒤로는 다시 주소 값이 보인다.

draft는 반대로 useState가 맞다. 시트가 열려 있는 동안 사용자가 고친 값을 오래 들고 있어야 하고, 주소가 따라오지 않기 때문이다. 시트가 열릴 때마다 새로 그려지므로 언제 처음 값으로 돌아갈지 따로 정할 필요도 없다.

헷갈리기 쉬운 점

  • draft와 shownQuery는 하는 일이 다르다. draft는 아직 적용하지 않은 선택이고 시트 안의 칩만 본다. shownQuery는 적용한 선택이고 필터 줄만 본다. 시트에서 칩을 눌러도 필터 줄의 칩 이름은 바뀌지 않는다.
  • 임시 값은 상태가 아니다. useOptimistic은 값을 저장해 두지 않는다. 진짜 값 위에 잠깐 덮어 보여 주는 것이고, 덮개는 transition이 끝나면 걷힌다.
  • key는 값을 다시 채우는 도구이지 동기화 도구가 아니다. 값이 바뀔 때마다 컴포넌트를 새로 만드는 것이라 포커스, 열림 상태, 입력 중인 글자 같은 것이 모두 사라진다.
  • router.replace를 쓴 이유와 useOptimistic을 쓴 이유는 다르다. replace는 필터를 여러 번 바꿔도 뒤로 가기 한 번에 목록에 오기 전 화면으로 가려고, useOptimistic은 응답 전 공백을 메우려고 쓴다. push를 써도 2부의 내용은 그대로다.
