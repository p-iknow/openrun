00 공연 목록 쿼리: 정리하고 주소 만들기

공연 목록 주소(/?q=정원&sort=newest&page=2)의 쿼리를 읽고, 고치고, 다시 주소로 만드는 함수들을 실제 값을 넣어 정리한다. 모두 apps/store/src/shows/show-list-query.ts에 있다.

전체 흐름

목록의 상태(검색어, 정렬, 페이지)는 주소에만 있다. 그래서 하는 일은 두 방향뿐이다. 주소를 읽어 쿼리 객체로 만들고, 쿼리 객체로 주소를 만든다. 쿼리 객체는 API를 부를 때도 쓴다.

주소 → 쿼리 (읽기)
  1. 서버 page.tsx: normalizeShowListQuery
  2. 클라이언트 HeaderSearch: getShowListQueryFromSearch
쿼리 → 주소 (만들기, 모두 getShowListHref를 거침)
  1. 페이지 번호와 조건 초기화 링크
  2. 정렬 시트: getSortChangeHref
  3. 필터 시트 적용: getFilterApplyHref
  4. 검색 제출: getSearchSubmitHref
  5. 마지막 페이지 보정: getLastPageRedirectHref

주소를 만드는 길이 getShowListHref 하나라서, 어디서 만든 주소든 기본값을 빼는 규칙과 q, sort, page 순서가 같다. 같은 화면이 늘 같은 주소 하나로 나타난다.

아래 예시의 결과는 모두 실제로 함수를 실행해 얻었다. 주소는 읽기 쉽게 한글 그대로 적었다. 실제 주소에서는 q=%EC%A0%95%EC%9B%90처럼 인코딩된다.

쿼리의 모양

읽기 함수는 어떤 주소가 들어와도 늘 이 모양의 객체를 돌려준다. 이 객체에는 잘못된 값이 없다.

/** 정렬 선택지. API 계약이 바뀌면 `satisfies`가 타입 검사에서 알린다. */
export const SHOW_SORTS = [
  'start_date',
  'newest',
] as const satisfies readonly ApiShowSort[];
export type ShowSort = (typeof SHOW_SORTS)[number];

const DEFAULT_PAGE = 1;
const DEFAULT_SORT: ShowSort = 'start_date';

export interface ShowListQuery {
  /** 1부터 센다. */
  page: number;
  /** 공연 제목 검색어. 앞뒤 공백을 지운 값이고, 검색하지 않으면 `null`이다. */
  q: string | null;
  sort: ShowSort;
}

기본값은 { page: 1, q: null, sort: 'start_date' }이고, 이 값은 주소에 적지 않는다. 그래서 기본 상태의 주소는 /다.

값 하나하나를 고치는 규칙

Next의 searchParams에서 값 하나는 세 모양으로 온다. 없으면 undefined, 한 번 있으면 글자, ?page=2&page=3처럼 여러 번 있으면 배열이다. 세 함수 parsePage, parseTitleQuery, parseSort가 이것을 하나의 올바른 값으로 고친다. 잘못된 값은 오류로 만들지 않고 기본값으로 바꾼다. 

// 1 이상이고 JS가 정확히 다루는 정수만 받는다. "02"처럼 같은 수를 다르게 쓴 값도 잘못된 값으로 본다.
function parsePage(value: string | string[] | undefined): number {
  if (typeof value !== 'string' || !/^[1-9]\d*$/.test(value)) {
    return DEFAULT_PAGE;
  }
  const page = Number(value);
  return Number.isSafeInteger(page) ? page : DEFAULT_PAGE;
}

// API와 같이 앞뒤 공백을 지운 뒤 길이를 잰다. 빈 값과 너무 긴 값은 검색하지 않는다.
// 검색 칸이 maxLength로 길이를 막으므로, 너무 긴 값은 주소를 직접 고쳤을 때만 들어온다.
function parseTitleQuery(value: string | string[] | undefined): string | null {
  if (typeof value !== 'string') {
    return null;
  }
  const q = value.trim();
  return q === '' || q.length > SHOW_TITLE_QUERY_MAX_LENGTH ? null : q;
}

function parseSort(value: string | string[] | undefined): ShowSort {
  return (typeof value === 'string' && findShowSort(value)) || DEFAULT_SORT;
}

function findShowSort(value: string): ShowSort | undefined {
  return SHOW_SORTS.find((sort) => sort === value);
}
값 들어온 값 결과 이유
page '2' 2
없음, '0', 'abc', '02' 1 1 이상의 정수만 받는다. '02'는 2와 같은 수지만 다르게 쓴 값이라 버린다. 받아 주면 같은 화면에 주소가 두 개 생긴다
['2', '3'] 1 여러 번 들어오면 어느 쪽인지 정할 수 없어 버린다
q ' 정원 ' '정원' API와 같이 앞뒤 공백을 지운다
없음, '', ' ' null 공백을 지워 비면 검색하지 않는다
51자 null API가 50자를 넘으면 400으로 응답하므로 미리 버린다. 검색 칸은 maxLength=50이라 주소를 손으로 고칠 때만 들어온다
['정원', '햄릿'] null 여러 번 들어오면 버린다

없음, 'popular' 'start_date' 선택지(SHOW_SORTS)에 없는 값은 기본값으로 바꾼다

normalizeShowListQuery: 서버에서 읽고 고치기

app/page.tsx가 요청마다 부른다. 값 하나하나를 위 규칙으로 고쳐 쿼리를 만든 뒤, 그 쿼리로 getShowListHref를 불러 주소를 다시 만든다. 다시 만든 주소가 들어온 주소와 글자까지 같으면 redirectTo는 null이고, 다르면 다시 만든 주소를 담는다. 

/**
 * Next의 `searchParams`를 목록 쿼리로 정리한다. 모르는 쿼리와 잘못된 값은 버리거나 기본값으로 고친다.
 * 정리한 주소가 원래 주소와 다르면 `redirectTo`에 정리된 주소를 담는다.
 */
export function normalizeShowListQuery(searchParams: SearchParams): {
  query: ShowListQuery;
  redirectTo: string | null;
} {
  const query = {
    page: parsePage(searchParams.page),
    q: parseTitleQuery(searchParams.q),
    sort: parseSort(searchParams.sort),
  };
  const href = getShowListHref(query);
  return {
    query,
    redirectTo: href === toHref(toSearch(searchParams)) ? null : href,
  };
}

function toSearch(searchParams: SearchParams): URLSearchParams {
  const search = new URLSearchParams();
  for (const [key, value] of Object.entries(searchParams)) {
    for (const item of [value ?? []].flat()) {
      search.append(key, item);
    }
  }
  return search;
}
들어온 주소 query redirectTo
/?q=정원&sort=newest&page=2 { page: 2, q: '정원', sort: 'newest' } null: 이미 정리된 주소
/ { page: 1, q: null, sort: 'start_date' } null
/?q= 정원 { page: 1, q: '정원', sort: 'start_date' } /?q=정원: 공백 정리
/?sort=start_date&page=1 기본값 /: 기본값은 주소에서 뺀다
/?sort=newest&q=정원 { page: 1, q: '정원', sort: 'newest' } /?q=정원&sort=newest: 순서를 q, sort, page로 맞춘다
/?q=정원&utm=abc { page: 1, q: '정원', sort: 'start_date' } /?q=정원: 모르는 키는 버린다
/?page=abc 기본값 /

page.tsx는 redirectTo가 있으면 API를 부르기 전에 redirect한다. 그래서 API는 늘 정리된 값만 받고, 사용자는 오류 화면 대신 정리된 목록을 본다. redirect가 흐름을 어떻게 끊는지는 react-next 07 문서에 있다.

주소를 글자 그대로 비교하므로 순서만 달라도 리다이렉트한다. 이 덕분에 같은 화면은 늘 같은 주소 하나로 남는다. 대신 주소를 만드는 쪽이 getShowListHref를 거치지 않고 손으로 주소를 쓰면, 누를 때마다 리다이렉트를 한 번 더 거친다.

getShowListQueryFromSearch: 클라이언트에서 읽기

헤더의 HeaderSearch는 레이아웃에 있어 searchParams를 받지 못하므로 useSearchParams()로 주소를 읽는다(react-next 08 문서). 그 값은 URLSearchParams라서, Next의 searchParams와 같은 모양(한 번이면 글자, 여러 번이면 배열)으로 바꾼 뒤 normalizeShowListQuery에 넘긴다. 규칙을 두 번 쓰지 않고 한 함수를 함께 쓰기 위해서다. 클라이언트에서는 리다이렉트하지 않으므로 query만 쓴다. 

/**
 * 클라이언트에서 읽은 주소의 쿼리 문자열(`useSearchParams`)을 목록 쿼리로 정리한다.
 * Next의 `searchParams`와 같은 모양(한 번이면 글자, 여러 번이면 배열)으로 바꿔 같은 규칙을 쓴다.
 */
export function getShowListQueryFromSearch(
  search: URLSearchParams,
): ShowListQuery {
  const searchParams: SearchParams = {};
  for (const key of new Set(search.keys())) {
    const values = search.getAll(key);
    searchParams[key] = values.length === 1 ? values[0] : values;
  }
  return normalizeShowListQuery(searchParams).query;
}
입력: 주소의 쿼리 중간: searchParams 모양 결과: query
q=정원&sort=newest { q: '정원', sort: 'newest' } { page: 1, q: '정원', sort: 'newest' }
q=정원&q=햄릿&sort=newest { q: ['정원', '햄릿'], sort: 'newest' } { page: 1, q: null, sort: 'newest' }

둘째 줄은 주소에 q가 두 번 붙은 경우다. URL 규칙상 같은 이름을 여러 번 넣을 수 있어서, 주소를 손으로 고치거나 밖에서 잘못 만든 링크로 들어오면 이런 주소가 생긴다. 우리 화면은 늘 getShowListHref로 주소를 만들어 q를 한 번만 넣으므로 스스로 만들지는 않는다. 정원과 햄릿 중 무엇을 찾으려던 건지 알 수 없으므로, q의 규칙에 따라 배열이면 검색어가 없는 것(null)으로 본다.

URLSearchParams.get('q')로 첫 값만 읽지 않고 배열로 바꾸는 이유도 여기 있다. 헤더가 첫 값 정원을 쓰고 서버는 버리면, 같은 주소를 두 곳이 다르게 읽는다.

HeaderSearch는 목록 화면(/)이 아니면 빈 URLSearchParams를 넘긴다. 그래서 다른 화면에서는 쿼리가 기본값 { page: 1, q: null, sort: 'start_date' }이 되고, 검색은 정렬 없이 새로 시작한다.

getShowListHref: 모든 주소 만들기의 바탕

기본값과 같은 값은 빼고, 남은 값을 q → sort → page 순서로 붙인다.

/**
 * 목록 쿼리로 주소를 만든다. 기본값은 주소에서 빼고, 순서는 q, sort, page로 고정한다.
 * 페이지 링크는 현재 쿼리에서 `page`만 바꿔 넘긴다.
 */
export function getShowListHref(query: ShowListQuery): string {
  return toHref(getShowListSearchParams(query));
}

function getShowListSearchParams(query: ShowListQuery): URLSearchParams {
  const search = new URLSearchParams();
  if (query.q !== null) {
    search.set('q', query.q);
  }
  if (query.sort !== DEFAULT_SORT) {
    search.set('sort', query.sort);
  }
  if (query.page !== DEFAULT_PAGE) {
    search.set('page', String(query.page));
  }
  return search;
}

function toHref(search: URLSearchParams): string {
  const query = search.toString();
  return query === '' ? LIST_PATH : `${LIST_PATH}?${query}`;
}
query 주소
{ page: 1, q: null, sort: 'start_date' } /
{ page: 3, q: null, sort: 'start_date' } /?page=3
{ page: 1, q: '정원', sort: 'newest' } /?q=정원&sort=newest
{ page: 2, q: '정원', sort: 'newest' } /?q=정원&sort=newest&page=2

다른 곳은 지금 쿼리를 펼친 뒤 바꿀 값만 덮어써서 이 함수에 넘긴다. 지금 쿼리가 { page: 2, q: '정원', sort: 'newest' }일 때:

쓰는 곳 넘기는 값 주소
페이지 번호 3 (ShowListPagination) { ...query, page: 3 } /?q=정원&sort=newest&page=3
페이지 번호 1 { ...query, page: 1 } /?q=정원&sort=newest

getSortChangeHref: 정렬 시트

정렬 시트(ShowSortSheet)에서 선택지를 누르면 시트가 고른 정렬을 돌려주고, 필터 줄(ShowFilterBar)이 이 함수로 주소를 만들어 router.replace한다. 다른 조건은 두고 정렬을 바꾸고 page를 1로 돌린다. 정렬이 바뀌면 3페이지의 내용이 전혀 다른 공연이 되므로 1페이지부터 보여 준다. 시트는 선택지(SHOW_SORTS)로만 버튼을 그리므로 sort는 늘 ShowSort이고, 잘못된 값을 걸러 낼 일이 없다. 지금 쿼리가 page 3, 검색어 '정원', 정렬 'newest'일 때: 

/** 정렬 시트에서 고른 정렬로 옮겨 갈 주소를 만든다. 다른 조건은 두고 page는 빼서 1페이지로 돌아간다. */
export function getSortChangeHref({
  query,
  sort,
}: {
  query: ShowListQuery;
  sort: ShowSort;
}): string {
  return getShowListHref({ ...query, sort, page: DEFAULT_PAGE });
}
고른 정렬 결과
'start_date' /?q=정원: 기본 정렬이라 sort가 빠지고, page도 1이라 빠진다
'newest' /?q=정원&sort=newest: 정렬은 같고 page만 빠진다

getFilterApplyHref: 필터 시트 적용

필터 시트에서 "적용"을 누르면 시트가 고친 임시 쿼리(draft)를 돌려주고, 필터 줄이 이 함수로 주소를 만든다. 정렬과 같이 page를 빼서 1페이지로 간다. 임시 쿼리를 어떻게 고치고 언제 적용하는지는 store-logic 01 문서에 있다. 

/**
 * 필터 시트에서 "적용"을 눌렀을 때 옮겨 갈 주소를 만든다. 시트에서 고친 임시 쿼리를 받는다.
 * 임시 쿼리는 `getGenreChangeQuery`, `getStatusChangeQuery`로 고치지만, 칩을 바꾸지 않고 적용하면 주소의 page가 남아 있으므로 여기서 뺀다.
 */
export function getFilterApplyHref(draft: ShowListQuery): string {
  return getShowListHref({ ...draft, page: DEFAULT_PAGE });
}

단위 테스트는 page 3, 검색어 '정원', 장르 ['musical', 'concert'], 판매 상태 ['on_sale'], 정렬 'newest'인 임시 쿼리가 /?q=정원&genre=musical&genre=concert&status=on_sale&sort=newest가 되는지 본다.

getSearchSubmitHref: 검색 제출

검색 폼을 제출하면 ShowListSearchForm이 이 함수로 주소를 만들어 router.push한다. 정렬은 두고, 입력한 글자를 q의 규칙(parseTitleQuery)으로 정리하고, page를 1로 돌린다. 제출 흐름은 react-next 09 문서에 있다. 

/**
 * 제목 검색 폼을 제출할 때 옮겨 갈 주소를 만든다. 정렬은 두고 page는 빼서 결과의 1페이지로 간다.
 * 검색어는 주소의 q와 같은 규칙으로 정리한다. 앞뒤 공백을 지우고, 비었으면 검색어를 뺀다.
 */
export function getSearchSubmitHref({
  query,
  value,
}: {
  query: ShowListQuery;
  /** 검색 칸에 입력한 글자 */
  value: string;
}): string {
  return getShowListHref({
    ...query,
    q: parseTitleQuery(value),
    page: DEFAULT_PAGE,
  });
}
지금 쿼리 입력한 글자 결과
{ page: 3, q: '정원', sort: 'newest' } ' 햄릿 ' /?q=햄릿&sort=newest
같음 ' ' /?sort=newest: 검색어가 빠진다
다른 화면이라 기본값 '햄릿' /?q=햄릿

이동하기 전에 이미 정리했으므로, 도착한 page.tsx의 normalizeShowListQuery는 redirectTo: null을 돌려준다. 정리용 리다이렉트를 한 번 덜 거친다.

getLastPageRedirectHref: 응답을 받은 뒤 마지막 페이지로

주소의 page가 올바른 정수여도 공연이 그만큼 많지 않을 수 있다. 몇 페이지까지 있는지는 API 응답의 totalPages를 받아야 안다. 그래서 이 함수는 API를 부른 뒤에 쓴다. 요청한 page가 마지막 페이지보다 크면 다른 쿼리는 두고 마지막 페이지 주소를 돌려주고, 아니면 null을 돌려준다. 공연이 없어 totalPages가 0이면 1페이지를 마지막 페이지로 본다. 

/**
 * API는 마지막 페이지를 넘는 요청에 빈 항목으로 응답한다. 그때 다른 쿼리는 그대로 두고 마지막 페이지 주소를 돌려준다.
 * 공연이 없으면(전체 페이지 수 0) 1페이지를 마지막 페이지로 본다.
 */
export function getLastPageRedirectHref({
  query,
  totalPages,
}: {
  query: ShowListQuery;
  /** API 응답의 전체 페이지 수 */
  totalPages: number;
}): string | null {
  const lastPage = Math.max(DEFAULT_PAGE, totalPages);
  return query.page > lastPage
    ? getShowListHref({ ...query, page: lastPage })
    : null;
}

page: 5 3 /?q=정원&page=3
page: 2 3 null
page: 1 0 null: 그대로 빈 상태를 보여 준다
page: 2 0 /?q=정원: 1페이지로

API로 넘기기

fetchShows는 쿼리를 API의 쿼리 파라미터로 옮긴다. 주소와 달리 기본값도 그대로 보내고, 주소에 없는 페이지 크기(20, SHOW_PAGE_SIZE)를 더한다. q가 null이면 undefined로 바꿔 아예 보내지 않는다. 

export async function fetchShows({
  client,
  query,
}: {
  client: ApiClient;
  query: ShowListQuery;
}): Promise<ShowPage> {
  return unwrap(
    await client.GET('/shows', {
      params: {
        query: {
          page: query.page,
          size: SHOW_PAGE_SIZE,
          q: query.q ?? undefined,
          sort: query.sort,
        },
      },
    }),
  );
}
query API 요청
{ page: 1, q: null, sort: 'start_date' } GET /shows?page=1&size=20&sort=start_date
{ page: 2, q: '정원', sort: 'newest' } GET /shows?page=2&size=20&q=정원&sort=newest

한 번에 따라가 보기

  1. 지저분한 주소로 들어온다 /?sort=newest&q= 정원 &page=02
  2. 정리하고 리다이렉트한다 normalizeShowListQuery가 { page: 1, q: '정원', sort: 'newest' }로 고친다. page는 '02'라 1이 된다. 다시 만든 주소 /?q=정원&sort=newest가 들어온 주소와 달라 그 주소로 redirect한다.
  3. 정리된 주소로 다시 들어온다 이번에는 redirectTo가 null이다. fetchShows가 GET /shows?page=1&size=20&q=정원&sort=newest를 부르고, getLastPageRedirectHref는 page가 1이라 null이다.
  4. 헤더도 같은 쿼리를 읽는다 getShowListQueryFromSearch가 같은 쿼리를 얻어 검색 칸에 정원을 채운다.
  5. 새로 검색한다 햄릿을 검색하면 getSearchSubmitHref가 /?q=햄릿&sort=newest를 만든다. 이미 정리된 주소라 리다이렉트 없이 목록이 그려진다.

확인 문제

1. 이 주소로 들어오면 redirectTo는 무엇인가?

normalizeShowListQuery의 규칙. 들어온 주소는 /?page=2&q=정원&sort=start_date다.

답 보기

/?q=정원&page=2. 쿼리는 { page: 2, q: '정원', sort: 'start_date' }로 값은 모두 올바르지만, 기본값인 sort=start_date는 빠지고 순서가 q, page로 바뀌어 들어온 주소와 다르다.

2. 정렬을 바꿀 때 page를 그대로 두면 무엇이 어색한가?

getSortChangeHref를 이렇게 바꾼다고 생각한다.

-  return getShowListHref({ ...query, sort, page: DEFAULT_PAGE });
+  return getShowListHref({ ...query, sort });
답 보기

3페이지를 보다가 "최근 등록 순"을 고르면, 새 순서의 3페이지(41~60번째)가 나온다. 사용자는 새 순서의 맨 앞을 보려고 정렬을 바꿨으므로 1~20번째를 건너뛴 셈이 된다.

3. 결과가 없는 검색에서 Math.max를 빼면 무슨 일이 생기는가?

getLastPageRedirectHref를 이렇게 바꾸고, 결과가 없는 검색 /?q=없는제목(page 1, totalPages 0)으로 들어온다고 생각한다. 

-  const lastPage = Math.max(DEFAULT_PAGE, totalPages);
+  const lastPage = totalPages;
답 보기

리다이렉트가 끝없이 돈다. page 1이 마지막 페이지 0보다 크므로 /?q=없는제목&page=0으로 보낸다. 그 주소로 들어오면 normalizeShowListQuery가 '0'을 잘못된 값으로 보고 page 1인 /?q=없는제목으로 다시 보낸다. 처음 주소로 돌아왔으니 같은 일이 되풀이되고, 브라우저는 결국 "리디렉션한 횟수가 너무 많습니다" 오류를 보여 준다. 0을 1로 올려 두면 page 1에서 멈추고 빈 상태가 나온다.
