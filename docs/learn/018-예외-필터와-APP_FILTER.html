예외 필터와 APP_FILTER: 모든 오류를 Problem Details로 보내기

apps/api/src/problem-details/problem-details.filter.ts가 무엇을 하는지, AppModule의 { provide: APP_FILTER, useClass: ProblemDetailsFilter }가 무슨 뜻인지 NestJS를 처음 보는 사람 기준으로 정리한다. Nest 내부 동작은 설치된 @nestjs/core 12.4 소스로 확인했다.

한눈에 보기

예외 필터는 "던져진 예외를 HTTP 응답으로 바꾸는 담당자"다. Nest에는 기본 담당자가 있고, 우리는 ADR 0007의 Problem Details 형식으로 응답하는 담당자 ProblemDetailsFilter를 만들어 바꿔 끼웠다. APP_FILTER는 그 담당자를 앱 전체에 끼우는 Nest의 이름표다.

질문 짧은 답
필터는 언제 실행되나 컨트롤러나 서비스, Nest 내부에서 예외가 던져져 응답을 만들 수 없을 때.
필터가 하는 일 예외를 보고 status, code, detail을 정해 application/problem+json으로 응답한다.
5xx는 왜 다르게 다루나 메시지에 내부 정보가 섞일 수 있어 고정 문구로 바꾸고, 원래 예외는 서버 로그에 남긴다.
APP_FILTER는 뭔가 "이 provider를 전역 예외 필터로 써라"는 뜻의 Nest 예약 이름표.
왜 main.ts가 아니라 모듈에 등록하나 통합 테스트는 main.ts를 거치지 않고 AppModule로 앱을 만든다. 모듈에 적어야 테스트에도 붙는다.

오류가 나면 누가 응답을 만드나

요청이 정상으로 처리되면 컨트롤러 메서드의 반환값이 그대로 JSON 응답이 된다. 컨트롤러와 서비스의 관계는 001 문서에 있다.

정상 흐름
  1. GET /shows
  2. ShowsController.findAll()
  3. ShowsService.findAll() → DB
  4. 반환값을 JSON으로 응답
도중에 throw
  1. GET /shows
  2. ShowsService가 throw new Error('DB 연결 실패')
  3. 예외 필터가 예외를 받음
  4. 필터가 오류 응답을 만듦

중간에 누군가 throw하면 컨트롤러는 반환값을 만들지 못한다. Nest는 이 예외를 잡아 예외 필터에게 넘기고, 필터가 상태 코드와 본문을 정해 응답한다. 우리 코드에 try/catch를 하나도 쓰지 않아도 오류 응답이 나가는 이유다.

없는 경로도 같은 길을 탄다. 요청이 어떤 컨트롤러에도 맞지 않으면 Nest가 내부에서 NotFoundException을 던지고(@nestjs/core의 routes-resolver.js, registerNotFoundHandler), 그 예외도 같은 필터로 간다. 

// @nestjs/core/router/routes-resolver.js (요약)
const callback = (req, res) => {
  throw new NotFoundException(`Cannot ${method} ${url}`);
};

Nest 기본 필터의 응답

필터를 따로 만들지 않아도 Nest에는 기본 필터(BaseExceptionFilter)가 있어서 오류 응답은 나간다. 모양이 Nest 고유의 형식일 뿐이다. 

// 없는 경로
{ "statusCode": 404, "message": "Cannot GET /nope", "error": "Not Found" }

// 예상하지 못한 오류 (new Error 등)
{ "statusCode": 500, "message": "Internal server error" }

ADR 0007은 모든 오류를 RFC 9457 Problem Details(type, title, status, detail)에 앱 오류 코드 code를 더한 형식으로 보내기로 정했다. 그래서 기본 담당자를 우리 담당자로 바꿔야 한다. 

{
  "type": "about:blank",
  "title": "Not Found",
  "status": 404,
  "detail": "Cannot GET /nope",
  "code": "NOT_FOUND"
}
선택 읽기: 우리 필터와 기본 필터는 어떻게 나뉘어 실행되나

Nest가 예외를 받으면 ExceptionsHandler가 먼저 등록된 필터(우리 필터)를 찾아 본다. 맞는 필터가 있으면 그것만 실행하고, 없으면 기본 필터로 넘긴다. 

// @nestjs/core/exceptions/exceptions-handler.js (요약)
next(exception, ctx) {
  if (this.invokeCustomFilters(exception, ctx)) {
    return;                    // 우리 필터가 처리했으면 끝
  }
  super.catch(exception, ctx); // 아니면 BaseExceptionFilter
}

우리 필터는 @Catch()로 모든 예외를 맡으므로, 기본 필터까지 가는 경우가 없다.

HttpException이란

필터 코드를 읽기 전에 알아야 할 Nest 클래스가 하나 있다. HttpException은 Nest가 "HTTP 상태 코드를 가진 예외"로 미리 만들어 둔 클래스다. 자주 쓰는 상태마다 상속한 클래스가 있다.

  • Error JS 기본 예외. 상태 코드가 없다.
    • HttpException getStatus()로 상태 코드를 꺼낼 수 있다.
      • NotFoundException Nest 404. 없는 경로에서 Nest가 던진다.
      • BadRequestException Nest 400. Nest의 기본 ValidationPipe가 던진다.
      • ProblemException 우리 앱 오류 코드(code)와 필드별 오류(errors)를 더 가진다.

반대로 throw new Error(...)나 DB 드라이버가 던지는 오류는 HttpException이 아니다. Nest 입장에서는 "상태 코드를 모르는 예외"다. 필터는 이 차이로 응답을 나눈다. 

// apps/api/src/problem-details/problem.exception.ts
export class ProblemException extends HttpException {
  readonly code: string;
  readonly errors?: FieldErrorDto[];

  constructor(options: { status: number; code: string; detail: string; errors?: FieldErrorDto[] }) {
    super(options.detail, options.status); // 메시지와 상태 코드는 HttpException이 들고 있는다
    this.code = options.code;
    this.errors = options.errors;
  }
}

ProblemException이 HttpException을 상속하므로 getStatus()와 message를 그대로 쓸 수 있고, 거기에 code와 errors만 더했다.

@Catch()와 catch 메서드

// apps/api/src/problem-details/problem-details.filter.ts
@Catch()
export class ProblemDetailsFilter implements ExceptionFilter {
  private readonly logger = new Logger(ProblemDetailsFilter.name);

  catch(exception: unknown, host: ArgumentsHost) {
    const problem = toProblem(exception);
    if (problem.status >= 500) {
      this.logger.error(exception);
    }

    host
      .switchToHttp()
      .getResponse<Response>()
      .status(problem.status)
      .type('application/problem+json')
      .json(problem);
  }
}
  1. @Catch() "이 클래스는 예외 필터이고, 이런 예외를 맡는다"는 표시다. @Catch(HttpException)처럼 쓰면 그 종류만 맡고, 괄호를 비우면 모든 예외를 맡는다. 우리 목표가 "어디서 난 오류든"이라 비워 뒀다. 데코레이터가 클래스에 표시를 붙이는 원리는 002 문서에 있다.
  2. implements ExceptionFilter TypeScript 약속이다. catch(exception, host) 메서드를 꼭 구현하겠다는 뜻이고, Nest는 예외가 날 때마다 이 메서드를 부른다.
  3. exception: unknown 던져진 값 그 자체다. JS에서는 문자열이나 숫자도 던질 수 있어서 타입을 unknown으로 두고, 아래에서 instanceof로 좁힌다.
  4. host.switchToHttp().getResponse() host는 지금 처리 중인 요청의 정보 묶음이다. Nest는 HTTP 말고 WebSocket이나 마이크로서비스도 지원해서, "HTTP 요청으로 보겠다"고 switchToHttp()를 먼저 부른다. getResponse()가 돌려주는 것은 Express의 res다. Express를 써 봤다면 res.status(404).type(...).json({...})와 같은 코드다. 이 줄에서 실제로 무슨 일이 일어나는지는 다음 절에서 소스로 따라간다.
  5. .type('application/problem+json') RFC 9457이 정한 Content-Type이다. Express의 res.json()은 Content-Type이 비어 있을 때만 application/json을 넣으므로, 먼저 정해 두면 그대로 나간다.

host에서 응답이 나가기까지

host는 Express의 [req, res, next]를 담은 상자다. switchToHttp().getResponse()는 그 상자의 두 번째 칸 res를 꺼낸다. 그 뒤의 .status().type().json()은 Express의 res 메서드를 이어 부른 것이고, 응답이 실제로 나가는 순간은 마지막 .json() 안이다.

아래 코드는 설치된 @nestjs/core 12.4와 express 5.3 소스에서 필요한 부분만 줄인 것이다.

0. host는 어디서 오나

Nest는 Express 라우트 핸들러를 감싸 두고, 예외가 나면 그 자리에서 host를 만들어 필터로 넘긴다. 

// @nestjs/core/router/router-proxy.js
return async (req, res, next) => {          // Express가 넘겨준 req, res, next
  try {
    await targetCallback(req, res, next);   // 컨트롤러 실행
  } catch (e) {
    const host = new ExecutionContextHost([req, res, next]); // 상자를 만든다
    exceptionsHandler.next(e, host);        // → 결국 우리 필터의 catch(e, host)
    return res;
  }
};

host는 특별한 객체가 아니라, Express가 원래 주던 req, res, next를 배열로 담아 둔 것이다.

1. switchToHttp(): 칸에 이름을 붙인다

// @nestjs/core/helpers/execution-context-host.js
switchToHttp() {
  return Object.assign(this, {
    getRequest: () => this.getArgByIndex(0),  // args[0] = req
    getResponse: () => this.getArgByIndex(1), // args[1] = res
    getNext: () => this.getArgByIndex(2),     // args[2] = next
  });
}

새 객체를 만들지도, 통신을 하지도 않는다. 같은 상자에 "0번 칸은 request, 1번 칸은 response"라는 이름 붙은 꺼내기 함수를 달아 줄 뿐이다. 이 단계가 따로 있는 이유는 Nest가 HTTP 말고 WebSocket이나 마이크로서비스도 같은 상자로 다루고, 종류마다 칸의 뜻이 다르기 때문이다.

메서드 0번 칸 1번 칸
switchToHttp() request response
switchToWs() client(소켓) data
switchToRpc() data context

2. getResponse<Response>(): Express의 res를 꺼낸다

args[1], 즉 Express의 res 객체 그 자체를 돌려준다. <Response>는 TypeScript에게 "이건 Express의 Response 타입"이라고 알려 주는 표시일 뿐, 실행할 때는 아무 일도 하지 않는다. 여기서부터는 Nest가 아니라 Express 코드다.

3. .status(): 상태 코드를 적어 둔다

// express/lib/response.js
res.status = function status(code) {
  // 정수가 아니거나 100~999 밖이면 TypeError, RangeError를 던진다
  this.statusCode = code; // Node 응답 객체에 상태 코드만 적어 둔다
  return this;            // res를 그대로 돌려준다
};

아직 아무것도 보내지 않는다. "보낼 때 이 상태 코드로 보내라"고 적어 둘 뿐이다. return this 덕분에 다음 메서드를 이어 부를 수 있다(메서드 체이닝).

4. .type(): Content-Type 헤더를 적어 둔다

res.type = function contentType(type) {
  var ct = type.indexOf('/') === -1
    ? (mime.contentType(type) || 'application/octet-stream') // 'html' 같은 줄임말이면 찾아서 바꾼다
    : type;                                                  // '/'가 있으면 그대로 쓴다
  return this.set('Content-Type', ct);
};

우리 값에는 /가 있으므로 Content-Type: application/problem+json 헤더를 그대로 적어 둔다. 여기서도 아직 보내지 않는다.

5. .json(): 여기서 응답이 나간다

res.json = function json(obj) {
  var body = stringify(obj, replacer, spaces, escape); // ① 객체 → JSON 문자열
  if (!this.get('Content-Type')) {                     // ② 비어 있을 때만
    this.set('Content-Type', 'application/json');
  }
  return this.send(body);                              // ③ send로 넘긴다
};
  1. JSON 문자열로 바꾼다 problem 객체를 문자열로 만든다. 값이 undefined인 키는 이때 빠진다.
  2. Content-Type이 없을 때만 채운다 그래서 4번 .type()을 .json()보다 먼저 불러야 한다. 순서를 바꾸면 .json()이 먼저 application/json을 넣고 응답까지 보내 버린다.
  3. send로 넘긴다 실제 전송은 send가 한다. 
res.send = function send(body) {
  // 문자열이면 Content-Type에 charset을 붙인다
  //   → 'application/problem+json; charset=utf-8'
  // 본문 길이를 재서 Content-Length 헤더를 붙인다
  // 본문으로 ETag 헤더를 만든다
  // ...
  this.end(chunk, encoding); // 상태 줄 + 헤더 + 본문을 실제로 소켓에 쓴다
  return this;
};

end()가 불리는 순간 지금까지 적어 둔 상태 코드, 헤더, 본문이 한꺼번에 클라이언트로 나간다. curl -i로 본 응답의 각 줄이 어디서 왔는지 맞춰 보면 이렇다.

응답의 줄 만든 곳
HTTP/1.1 404 Not Found 3. .status()가 적어 둔 값
Content-Type: application/problem+json; charset=utf-8 4. .type() + send가 붙인 charset
Content-Length: 102 send
ETag: W/"66-..." send
{"type":"about:blank",...,"code":"NOT_FOUND"} 5. .json()의 stringify

전체를 시간 순서로

  1. 요청 도착 Express가 요청을 받아 Nest가 감싼 핸들러에 req, res, next를 넘긴다.
  2. 예외 컨트롤러나 서비스에서 예외가 난다.
  3. 상자 만들기 Nest가 new ExecutionContextHost([req, res, next])를 만들어 우리 필터의 catch(exception, host)를 부른다.
  4. 내용 정하기 toProblem(exception)이 보낼 내용을 정한다.
  5. res 꺼내기 switchToHttp().getResponse()가 상자에서 res를 꺼낸다.
  6. 적어 두기 .status(404)와 .type('application/problem+json')이 상태 코드와 헤더를 적어 둔다.
  7. 보내기 .json(problem)이 JSON으로 바꾸고, send가 길이와 ETag를 붙인 뒤 end()로 보낸다.

toProblem: 세 가지 결정

응답의 내용은 toProblem 함수가 정한다. 예외를 보고 세 가지를 결정한다.

function toProblem(exception: unknown): ProblemDetailsDto {
  // ① 상태 코드
  const status =
    exception instanceof HttpException ? exception.getStatus() : HttpStatus.INTERNAL_SERVER_ERROR;
  // ② 앱 오류 코드
  const code =
    exception instanceof ProblemException ? exception.code : (HttpStatus[status] ?? 'HTTP_ERROR');
  // ③ 사람이 읽는 설명
  const detail =
    exception instanceof HttpException && status < 500
      ? exception.message
      : '서버에서 요청을 처리하지 못했습니다.';
  const errors = exception instanceof ProblemException ? exception.errors : undefined;

  return {
    type: 'about:blank',
    title: STATUS_CODES[status] ?? 'Error',
    status,
    detail,
    code,
    ...(errors && { errors }),
  };
}
결정 규칙 이유
① status HttpException이면 그 상태 코드, 아니면 500 상태를 모르는 예외는 서버가 예상하지 못한 실패다.
② code ProblemException이면 직접 준 코드, 아니면 상태 이름(NOT_FOUND 등) Nest가 던진 예외에는 앱 오류 코드가 없다. HttpStatus[404]는 'NOT_FOUND'다.
③ detail 4xx HttpException이면 그 메시지, 5xx나 모르는 예외면 고정 문구 5xx 메시지에는 DB 주소 같은 내부 정보가 섞일 수 있다(아래).

나머지 필드는 정해진 규칙대로 채운다.

  • type: 'about:blank': RFC 9457에서 "상태 코드 말고 따로 설명할 오류 종류가 없다"는 뜻의 기본값이다. 우리는 오류 종류를 code로 나누므로 종류별 URI를 만들지 않았다.
  • title: RFC 9457은 type이 about:blank이면 title을 HTTP 상태 문구로 두라고 한다. Node가 가진 표(STATUS_CODES[404] → 'Not Found')에서 가져온다.
  • errors: 검증 오류처럼 ProblemException이 필드별 오류를 들고 있을 때만 붙인다.

5xx는 왜 숨기고 로그에 남기나

4xx는 "요청이 잘못됐다"는 뜻이라 메시지를 보여 줘야 클라이언트가 고칠 수 있다. 5xx는 "서버가 처리하지 못했다"는 뜻이고, 메시지는 대개 서버 내부 사정이다. 

connection to db-internal:5432 refused
relation "shows" does not exist
pg-internal:8443 timeout

이런 문장이 응답에 실리면 DB 주소, 테이블 이름, 내부 서비스 구성이 밖으로 드러난다. 클라이언트가 이 문장으로 할 수 있는 일도 없다. 그래서 5xx는 앱 예외(ProblemException)라도 detail을 고정 문구로 바꾸고, code만 싣는다.

응답에서 숨기면 원인을 찾을 곳이 없어진다. 그래서 catch는 5xx일 때 this.logger.error(exception)로 원래 예외를 서버 로그에 남긴다. 기본 필터도 모르는 예외를 로그에 남기므로, 필터를 바꾸면서 이 동작을 잃지 않게 직접 넣었다.

필터를 붙이는 세 범위

필터 클래스를 만들기만 하면 아무 일도 일어나지 않는다. Nest에게 "이 필터를 써라"고 알려야 한다. 붙이는 방법은 세 가지다. 

// (가) 컨트롤러나 메서드 하나에만
@UseFilters(ProblemDetailsFilter)
@Controller('shows')
export class ShowsController {}

// (나) 앱 전체: main.ts에서
const app = await NestFactory.create(AppModule);
app.useGlobalFilters(new ProblemDetailsFilter());

// (다) 앱 전체: 모듈에서 ← 우리가 쓴 방법
@Module({
  providers: [{ provide: APP_FILTER, useClass: ProblemDetailsFilter }],
})
export class AppModule {}
방법 적용 범위 적는 곳 필터를 만드는 쪽
(가) @UseFilters 그 컨트롤러나 메서드 컨트롤러 파일 Nest
(나) useGlobalFilters 전역 main.ts 우리가 new
(다) APP_FILTER 전역 모듈의 providers Nest

모든 경로에 적용해야 하니 (가)는 맞지 않는다. (나)와 (다)는 둘 다 전역이고, 적는 곳이 다르다. 이 차이가 테스트에서 결과를 가른다.

여러 범위에 필터가 있으면 요청에 더 가까운 쪽(메서드 → 컨트롤러 → 전역)이 먼저 예외를 맡는다. 우리는 전역 필터 하나만 둔다.

APP_FILTER 문법 풀기

// apps/api/src/app.module.ts
@Module({
  imports: [DatabaseModule, ShowsModule],
  providers: [{ provide: APP_FILTER, useClass: ProblemDetailsFilter }],
})
export class AppModule {}

providers는 "앱이 시작할 때 Nest가 만들어 둘 물건 목록"이다. ShowsModule의 providers: [ShowsService]도 같은 목록이다. 보통은 클래스 이름만 적지만, 객체로 적으면 이름표와 실제 물건을 따로 정할 수 있다. 이 문법은 003 문서에서 DATABASE 토큰으로 이미 봤다.

  1. provide: APP_FILTER 이 물건의 이름표다. APP_FILTER는 Nest가 미리 정해 둔 특별한 이름표(실제 값은 문자열 'APP_FILTER')이고, Nest는 이 이름표가 붙은 물건을 전역 예외 필터로 쓴다.
  2. useClass: ProblemDetailsFilter 그 이름표의 실제 물건은 이 클래스로 만들라는 뜻이다. Nest가 new를 대신 해 준다.

합치면 "전역 예외 필터 자리에 ProblemDetailsFilter를 끼워라"를 모듈 설정으로 적은 것이다. 같은 방식의 이름표로 APP_PIPE(전역 파이프), APP_GUARD(전역 가드), APP_INTERCEPTOR(전역 인터셉터)가 있다.

Nest 안에서 일어나는 일

Nest가 앱을 조립할 때 모듈의 providers를 훑는다. 이 일을 하는 코드가 @nestjs/core의 scanner.js다. 이름표가 APP_FILTER인 provider를 만나면 전역 필터 목록에 더한다. 

// @nestjs/core/scanner.js (요약)
getApplyProvidersMap() {
  return {
    [APP_INTERCEPTOR]: (interceptor) => this.applicationConfig.addGlobalInterceptor(interceptor),
    [APP_PIPE]: (pipe) => this.applicationConfig.addGlobalPipe(pipe),
    [APP_GUARD]: (guard) => this.applicationConfig.addGlobalGuard(guard),
    [APP_FILTER]: (filter) => this.applicationConfig.addGlobalFilter(filter),
  };
}
  1. 훑기 AppModule의 providers에서 provide: APP_FILTER를 발견한다.
  2. 만들기 다른 provider처럼 ProblemDetailsFilter 인스턴스를 하나 만든다.
  3. 등록 addGlobalFilter로 전역 필터 목록에 넣는다. (나)의 app.useGlobalFilters도 결국 같은 목록에 넣는다.
  4. 사용 어느 경로에서든 예외가 나면 이 목록의 필터가 맡는다. 없는 경로의 404 처리도 같은 목록을 쓴다.

Nest가 직접 만들기 때문에, 나중에 필터가 다른 provider(예: 설정 값을 읽는 서비스)를 생성자로 받아야 할 때도 그대로 주입할 수 있다. (나)처럼 new로 만들면 주입을 받을 수 없다.

왜 main.ts가 아니라 모듈인가

main.ts는 서버를 실제로 켤 때만 실행되는 파일이다.

// apps/api/src/main.ts
const app = await NestFactory.create(AppModule, { abortOnError: false });
await app.listen(3000);

통합 테스트는 main.ts를 거치지 않고 AppModule로 앱을 직접 조립한다. 테스트 구성은 005 문서에 있다. 

// apps/api/test/problem-details.int.spec.ts (요약)
const moduleRef = await Test.createTestingModule({ imports: [AppModule] }).compile();
app = moduleRef.createNestApplication();
await app.init();
main.ts 실행 AppModule 읽음 (나) useGlobalFilters (다) APP_FILTER
운영 서버 (pnpm start) 예 예 붙음 붙음
통합 테스트 아니오 예 안 붙음 붙음

필터를 main.ts에 붙이면 테스트 앱은 Nest 기본 형식으로 응답한다. 테스트는 실패하고, 운영과 테스트가 서로 다른 앱이 된다. AppModule에 붙이면 두 곳이 같은 필터를 쓴다. app.module.ts의 주석이 이 이유를 적어 둔 것이다.

스스로 확인하기

1. @Catch(HttpException)으로 바꾸면 서비스가 throw new Error()를 던질 때 응답은 어떻게 되나?

Error는 HttpException이 아니므로 우리 필터가 맡지 않는다. Nest 기본 필터로 넘어가 { "statusCode": 500, "message": "Internal server error" }가 application/json으로 나간다. 500 통합 테스트가 실패한다.

2. 필터 등록을 APP_FILTER에서 main.ts의 useGlobalFilters로 옮기면 무엇이 깨지나? 운영 응답은 달라지나?

통합 테스트가 깨진다. 테스트 앱은 main.ts를 실행하지 않아 필터가 없으므로 Content-Type 검사와 본문 검사가 모두 실패한다. 운영 서버는 main.ts를 거치므로 응답이 같다. 테스트가 운영과 다른 앱을 검증하게 되는 것이 문제다.

3. 서비스가 new ProblemException({ status: 503, code: 'PAYMENT_GATEWAY_DOWN', detail: 'pg-internal:8443 timeout' })을 던지면 응답에 무엇이 실리나?

status 503, code PAYMENT_GATEWAY_DOWN, detail은 고정 문구다. 5xx라서 앱 예외라도 설명을 숨긴다. 원래 메시지 pg-internal:8443 timeout은 서버 로그에만 남는다.

4. 없는 경로 404는 컨트롤러를 거치지 않는데 어떻게 우리 필터가 처리하나?

Nest가 어떤 경로에도 맞지 않는 요청을 위해 별도 핸들러를 등록하고, 그 핸들러가 NotFoundException을 던진다. 이 핸들러도 전역 필터 목록을 쓰므로 우리 필터가 처리한다.

5. catch에서 .json(problem)을 먼저 부르고 .type('application/problem+json')을 나중에 부르면 응답은 어떻게 되나?

.json()이 Content-Type이 비어 있는 것을 보고 application/json을 넣은 뒤 send와 end()로 응답을 이미 보낸다. 그 뒤의 .type()은 이미 나간 응답의 헤더를 바꾸려 하므로 반영되지 않고, Node가 ERR_HTTP_HEADERS_SENT 오류를 던진다. 클라이언트는 application/json; charset=utf-8을 받으므로 Content-Type 검사 테스트가 실패한다.

6. 운영에서 500이 났다는 신고를 받았다. 응답에는 고정 문구뿐인데 원인은 어디서 찾나?

API 서버 로그를 본다. 필터가 5xx일 때 this.logger.error(exception)로 원래 예외와 스택을 남긴다. 응답에 원인을 싣지 않는 대신 로그에 남기는 것이 이 설계의 짝이다.
