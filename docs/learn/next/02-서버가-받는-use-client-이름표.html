서버가 받는 'use client' 파일: 이름표 붙은 가짜

Server Component가 'use client' 파일을 import하면 서버는 그 파일의 코드를 받지 않는다. 대신 export 이름마다 "어느 파일의 어느 export"라는 이름표가 붙은 가짜 함수를 받는다. 스토어 빌드 결과물에서 이 가짜를 직접 꺼내 보고, 그 때문에 Drawer.Root가 undefined가 됐던 이유와 export * as Drawer로 풀리는 이유를 정리한다.

출발점: Drawer.Root가 undefined

Drawer를 compound 컴포넌트로 바꾸면서 'use client' 파일 안에서 부품을 객체로 묶어 내보냈다. 

// drawer.tsx
'use client';
function Root() { /* … */ }
function Trigger() { /* … */ }
export const Drawer = { Root, Trigger };

Server Component인 스토어 페이지에서 이것을 렌더링하자 빌드가 실패했다.

Error: Element type is invalid: expected a string (for built-in components)
or a class/function (for composite components) but got: undefined.

Client Component에서는 멀쩡히 동작하는 코드다. 서버에서만 Drawer.Root가 undefined가 된다. 그 까닭은 서버가 drawer.tsx를 어떤 모습으로 받는지 보면 알 수 있다.

서버는 'use client' 파일을 가짜로 바꾼다

store-ui의 button.js는 'use client' 파일이고, Server Component인 스토어 홈이 import한다. 원래 내용은 이렇다. 

// packages/store-ui/dist/button.js (원래 코드, 줄임)
'use client';
export const buttonVariants = cva([/* 클래스 목록 */], {
  variants: { /* … */ },
});
export function Button({
  variant,
  type,
  disabled,
  loading,
  onClick,
  children,
}) {
  return (
    <BaseButton className={buttonVariants({ variant })} …>
      {children}
    </BaseButton>
  );
}

그런데 next build가 만든 서버용 결과물(.next/server/chunks/ssr/…js)에서 button.js 자리에 들어 있는 코드는 이것이다. 압축된 코드를 읽기 쉽게 풀어 썼다. 

// 서버용 결과물에 들어 있는 button.js의 대역
export const Button = registerClientReference(
  function () {
    throw Error(
      'Attempted to call Button() from the server ' +
        'but Button is on the client. ' +
        "It's not possible to invoke a client function from the server, " +
        'it can only be rendered as a Component ' +
        'or passed to props of a Client Component.',
    );
  },
  '[project]/packages/store-ui/dist/button.js', // 어느 파일의
  'Button', // 어느 export인지
);

export const buttonVariants = registerClientReference(
  function () {
    throw Error('Attempted to call buttonVariants() from the server …');
  },
  '[project]/packages/store-ui/dist/button.js',
  'buttonVariants',
);

원래 코드와 비교하면 세 가지가 다르다.

  1. 원래 코드가 하나도 없다 cva도, Base UI도, JSX도 없다. Server Component를 실행하는 쪽은 button.js를 실행하지 않는다.
  2. export 이름마다 가짜 함수가 하나씩 있다 Button과 buttonVariants 자리에 각각 가짜 함수가 들어 있다. 가짜를 실수로 호출하면 바로 오류를 던진다.
  3. 가짜마다 이름표가 붙어 있다 registerClientReference가 가짜 함수에 "파일 경로"와 "export 이름" 두 가지를 적어 붙인다. 이름표에 적힌 정보는 이 둘뿐이다.

이 바꿔 끼우기는 페이지를 렌더링할 때가 아니라 next build가 서버용 코드를 만들 때 일어난다. 빌드 때 무엇을 준비하고 그 뒤 단계들이 언제 실행되는지는 next 03 문서의 "먼저: 빌드 때 코드 준비"에 정리했다.

"'use client' 파일은 서버에 참조만 넘긴다"는 말의 뜻이 이것이다. 서버가 받는 것은 export 이름마다 하나씩 만든, 이름표 붙은 가짜 함수이고, 그 export가 원래 무엇이었는지(함수인지 객체인지, 안에 뭐가 들었는지)는 모른다.

이름표는 택배 송장에 비유할 수 있다. 서버는 상자(코드)를 받지 않고 "button.js 상자의 Button 칸"이라고 적힌 송장만 받는다. 상자는 브라우저로 바로 배송된다.

진짜 코드는 어디 있나

이름표에는 파일 경로만 있고, 그 파일이 브라우저의 어느 JS 파일에 들어갔는지는 따로 적힌 표가 안다. 같은 빌드의 .next/server/app/page_client-reference-manifest.js에 이런 항목이 있다. 

"[project]/packages/store-ui/dist/button.js": {
  "id": 86223,
  "name": "*",
  "chunks": [
    "/_next/static/chunks/2qj-s9lpzec8-.js",
    "/_next/static/chunks/16f11qb2p8waj.js"
  ],
  "async": false
}
무엇 어디에 들어 있는 것
이름표 붙은 가짜 서버 .next/server/chunks/… 파일 경로 + export 이름
표 (client reference manifest) 서버 page_client-reference-manifest.js 파일 경로 → 브라우저 JS 파일 목록
진짜 Button 코드 브라우저 /_next/static/chunks/…js cva, Base UI, JSX 전부

이름표로 그리는 흐름

서버가 가짜만 가지고 있는데 <Button>이 화면에 나오는 까닭은, 서버가 그리지 않고 브라우저에 "그려 달라"고 전달하기 때문이다. 스토어 홈의 이 코드로 따라가 본다. 

// apps/store/app/page.tsx (Server Component)
<Button type="submit" variant="secondary">새로고침</Button>
서버
  1. Button이 이름표 붙은 가짜임을 알아봄
  2. 실행하지 않고 이름표와 props를 적음
브라우저
  1. 표를 보고 button.js 코드를 받음
  2. Button export를 꺼내 props로 그림
  1. 알아보기 React가 <Button>을 렌더링하려다 Button에 이름표가 붙은 것을 본다. 일반 컴포넌트라면 함수를 호출해 결과를 얻겠지만, 이름표가 있으면 호출하지 않는다.
  2. 적기 결과물(RSC payload)에 "여기에 button.js의 Button을 이 props로 그려라"라고 적는다. props는 { type: 'submit', variant: 'secondary', children: '새로고침' }이다.
  3. 받기 브라우저가 결과물을 읽다가 그 표시를 만나면, 표에서 button.js가 든 JS 파일을 찾아 받는다.
  4. 그리기 받은 모듈에서 이름표에 적힌 export 이름 Button을 꺼내, 적혀 온 props로 그린다. 이때 이벤트가 붙는다 (하이드레이션).

"Client Component도 서버에서 한 번 실행된다"는 말과 헷갈리기 쉽다. 둘 다 맞다. Next는 서버에서 두 단계를 거친다. 먼저 Server Component 단계가 컴포넌트 트리를 그리는데, 이 단계는 이 문서의 가짜(이름표)만 받고 Client Component를 실행하지 않는다. 그다음 HTML을 만드는 단계(SSR)가 그 결과를 받아, 이름표를 보고 진짜 Button 코드를 실행해 첫 화면 HTML을 만든다. 이 문서에서 "서버는 실행하지 않는다"고 할 때의 서버는 앞의 Server Component 단계다.

이름표라서 생기는 규칙

Server Component에서 클라이언트용 컴포넌트를 쓸 때 지켜야 하는 규칙들은 모두 "서버 손에는 이름표만 있다"에서 나온다.

서버에서 하려는 일 결과 이유
<Button>으로 렌더링 됨 이름표를 적어 브라우저에 넘기면 된다
buttonVariants({ variant })처럼 호출 오류 가짜 함수라서 호출하면 "Attempted to call … from the server" 오류를 던진다
<Button onClick={() => …}>처럼 함수 props 넘기기 오류 props를 글자로 적어 브라우저에 보내야 하는데, 함수는 글자로 적을 수 없다
Drawer.Root처럼 export의 속성 꺼내기 undefined 이름표 붙은 가짜에는 원래 객체의 속성이 없다 (다음 절)

buttonVariants 호출이 안 되는 이유는 design-system 03 문서의 "파일마다 지시어만 두면 될까"에서도 다뤘다. 그때 "클라이언트 참조라서 호출할 수 없다"고 적은 것이 이 가짜 함수다.

객체로 묶으면 속이 비는 이유

처음 문제로 돌아간다. 'use client' 파일 안에서 객체를 만들어 내보냈다.

'use client';
function Root() { /* … */ }
function Trigger() { /* … */ }
export const Drawer = { Root, Trigger };

서버는 이 파일도 실행하지 않는다. export 이름은 Drawer 하나이므로, 같은 방식대로 가짜도 하나만 만든다. 

// 서버가 받는 것
export const Drawer = registerClientReference(
  function () {
    throw …;
  },
  'drawer.js',
  'Drawer',
);
  1. 서버 손의 Drawer { Root, Trigger } 객체가 아니라 "drawer.js의 Drawer" 이름표가 붙은 가짜 함수다.
  2. Drawer.Root 꺼내기 가짜 함수에는 Root라는 속성이 없다. 객체를 만드는 코드({ Root, Trigger })는 서버에서 실행된 적이 없기 때문이다. 그래서 undefined다.
  3. 렌더링 React가 <undefined>를 그리려다 "Element type is invalid … got: undefined"로 실패한다.

컴포넌트에 정적 속성으로 붙여도(Root.Trigger = Trigger) 같다. 서버는 그 대입문도 실행하지 않으므로 가짜 Root에 Trigger가 생기지 않는다.

직접 확인하기

정말 그런지 임시 파일로 확인했다. 'use client' 파일 하나에서 세 가지 방식으로 내보내고, Server Component 페이지가 받은 값을 그리지 않고 그대로 들여다봤다. 

// __probe-obj.tsx (임시)
'use client';
function ObjRoot() { /* … */ }
function ObjPart() { /* … */ }
export const ProbeObj = { Root: ObjRoot, Part: ObjPart }; // ① 객체로 묶기

function StaticRoot() { /* … */ }
StaticRoot.Part = ObjPart;
export const ProbeStatic = StaticRoot; // ② 정적 속성으로 붙이기

export { ObjRoot as ProbeNamedRoot }; // ③ 이름 단위로 내보내기 (비교용)
// app/probe-obj/page.tsx (임시, Server Component)
import { ProbeNamedRoot, ProbeObj, ProbeStatic } from '@openrun/store-ui';

function describe(name: string, value: any) {
  return {
    name,
    typeof: typeof value,
    $$typeof: String(value.$$typeof),
    $$id: String(value.$$id),
    Root: typeof value.Root,
    Part: typeof value.Part,
    ownKeys: Object.getOwnPropertyNames(value).join(','),
  };
}

export default function ProbePage() {
  const rows = [
    describe('ProbeObj', ProbeObj),
    describe('ProbeStatic', ProbeStatic),
    describe('ProbeNamedRoot', ProbeNamedRoot),
  ];
  return <pre>{JSON.stringify(rows, null, 2)}</pre>;
}

next build가 만든 페이지 HTML에 찍힌 결과는 이렇다.

서버가 받은 값 typeof $$id (이름표) .Root / .Part
① ProbeObj function 객체가 아님 …/__probe-obj.js#ProbeObj undefined / undefined
② ProbeStatic function …/__probe-obj.js#ProbeStatic undefined / undefined
③ ProbeNamedRoot function …/__probe-obj.js#ProbeNamedRoot undefined / undefined
  • 셋 다 $$typeof가 Symbol(react.client.reference)다. React가 "이건 이름표"라고 알아보는 표시다.
  • 셋 다 자기 속성이 length,name,prototype,$$typeof,$$id,$$async뿐이다. 함수의 기본 속성과 이름표 정보만 있고, Root나 Part는 없다.
  • ①은 원래 객체였는데도 서버에서는 함수다. 서버는 export가 원래 무엇이었는지 모르고, 모든 export를 똑같이 이름표 붙은 가짜 함수로 바꾸기 때문이다.

같은 빌드의 서버용 결과물에서 이 파일의 대역 코드도 꺼냈다(줄바꿈만 넣었다).

let c = registerClientReference(
    function () {
      throw Error("Attempted to call ProbeNamedRoot() from the server …");
    },
    "[project]/packages/store-ui/dist/__probe-obj.js",
    "ProbeNamedRoot",
  ),
  d = registerClientReference(
    function () {
      throw Error("Attempted to call ProbeObj() from the server …");
    },
    "[project]/packages/store-ui/dist/__probe-obj.js",
    "ProbeObj",
  ),
  e = registerClientReference(
    function () {
      throw Error("Attempted to call ProbeStatic() from the server …");
    },
    "[project]/packages/store-ui/dist/__probe-obj.js",
    "ProbeStatic",
  );

객체(①)와 정적 속성(②)도 함수 export(③)와 똑같은 가짜로 바뀐다. 대역 코드 어디에도 { Root, Part }나 StaticRoot.Part = …가 없다. 서버가 아는 것은 export 이름 세 개뿐이다.

서버 쪽 파일에서 묶으면 되는 이유

해결은 묶는 일을 서버가 실행하는 파일로 옮기는 것이다. 'use client' 파일은 부품을 이름 단위로 내보내고, 지시어가 없는 진입점이 묶는다. 

// drawer.tsx — 'use client', 부품을 이름 단위로 내보낸다
'use client';
export function Root() { /* … */ }
export function Trigger() { /* … */ }

// index.ts — 지시어 없음. 서버가 실제로 실행한다
export * as Drawer from './drawer.js';
  1. index.ts 실행 지시어가 없으니 서버가 index.ts를 실제로 실행하고, 그 과정에서 drawer.js를 import한다.
  2. drawer.js는 가짜로 바뀜 'use client' 파일이라 가짜로 바뀐다. 다만 export가 Root, Trigger처럼 이름 단위이니 가짜도 이름마다 따로 생긴다. Root에는 "drawer.js의 Root", Trigger에는 "drawer.js의 Trigger" 이름표가 붙는다.
  3. 서버에서 객체를 만듦 export * as Drawer는 서버 쪽에서 그 가짜들을 담은 진짜 객체 { Root: 가짜, Trigger: 가짜 }를 만든다.
  4. Drawer.Root 꺼내기 진짜 객체이니 Drawer.Root로 Root 이름표 붙은 가짜를 꺼낼 수 있다. 그 뒤는 이름표로 그리는 흐름과 같다.
묶는 방법 객체를 만드는 곳 서버 손의 Drawer Drawer.Root
'use client' 파일 안에서 { Root, Trigger } 서버가 실행하지 않는 파일 이름표 1개 (Drawer) undefined
'use client' 파일 안에서 Root.Trigger = Trigger 서버가 실행하지 않는 파일 이름표 1개 (Root) undefined
지시어 없는 파일에서 export * as Drawer 서버가 실행하는 파일 진짜 객체 { Root: 이름표, … } 이름표

차이는 객체를 어디서 만드느냐다. 서버가 꺼낼 수 있는 단위는 export 이름 하나하나의 이름표뿐이므로, 이름표들을 객체로 묶는 일은 서버가 실행하는 파일이 해야 한다.

우리 프로젝트에서는

  • packages/store-ui/src/drawer.tsx는 'use client' 파일이고, 부품을 Root, Trigger, Popup처럼 이름 단위로 내보낸다. 파일 안에서 Drawer 객체를 만들지 않는다.
  • packages/store-ui/src/index.ts가 export * as Drawer from './drawer.js'로 묶는다. Base UI도 같은 방식이다(@base-ui/react/drawer/index.mjs).
  • Pagination은 'use client'가 없는 서버용 파일이라 그 안에서 Pagination 객체를 만들어도 된다. 서버가 그 파일을 실제로 실행하기 때문이다.
  • Server Component에서 클라이언트용 컴포넌트에 함수 props를 넘기지 않는 규칙(스토어 홈의 새로고침 버튼은 <form action="/">와 type="submit"을 쓴다)도 같은 이유에서 나온다.

스스로 확인하기

1. Server Component가 'use client' 파일을 import하면 서버가 받는 것은 정확히 무엇인가?

export 이름마다 하나씩 만든 가짜 함수다. 가짜에는 파일 경로와 export 이름이 적힌 이름표가 붙어 있고, 원래 코드는 들어 있지 않다. 호출하면 "Attempted to call … from the server" 오류를 던진다.

2. 서버가 가짜만 가지고 있는데 <Button>이 화면에 나오는 이유는?

React가 이름표를 보고 Button을 호출하지 않는다. 대신 "button.js의 Button을 이 props로 그려라"라고 결과물에 적는다. 브라우저가 manifest에서 button.js가 든 JS 파일을 찾아 받고, Button export를 꺼내 그 props로 그린다.

3. 'use client' 파일 안에서 export const Drawer = { Root, Trigger }로 묶으면 서버에서 Drawer.Root가 왜 undefined인가?

서버가 받는 Drawer는 "drawer.js의 Drawer" 이름표 붙은 가짜 함수 하나다. 객체를 만드는 코드는 서버에서 실행되지 않았으므로 가짜에는 Root 속성이 없다.

4. index.ts의 export * as Drawer는 왜 되는가?

index.ts에는 지시어가 없어 서버가 실제로 실행한다. drawer.js의 Root, Trigger가 각각 이름표 붙은 가짜로 바뀌고, export * as가 서버 쪽에서 그 가짜들을 담은 진짜 객체를 만든다. 그래서 Drawer.Root로 Root 이름표를 꺼낼 수 있다.

5. Server Component에서 <Button onClick={...}>이 안 되는 이유를 이름표로 설명하면?

서버는 Button을 실행하지 않고 이름표와 props를 글자로 적어 브라우저에 보낸다. 함수는 글자로 적을 수 없으므로 props에 함수가 있으면 보낼 방법이 없어 오류가 난다.

6. Pagination은 지시어 없는 파일 안에서 Pagination 객체를 만드는데 왜 괜찮은가?

지시어가 없으니 서버가 그 파일을 실제로 실행한다. 객체도 서버에서 진짜로 만들어지고, 그 안의 부품도 서버에서 그리는 진짜 컴포넌트라 Pagination.Root를 문제없이 꺼낼 수 있다.
