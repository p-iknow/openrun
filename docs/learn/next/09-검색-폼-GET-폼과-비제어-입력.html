09 검색 폼: GET 폼, 숨은 입력 칸, 비제어 입력과 key

헤더의 제목 검색 폼(apps/store/src/shows/show-list-search-form.tsx)이 제출될 때 무슨 일이 일어나는지, 왜 눈에 보이지 않는 입력 칸을 두는지, 왜 key로 폼을 새로 만드는지를 본다. 내용은 Next 16.4.5의 문서와, 이 저장소의 스토어 개발 서버에서 실제로 검색하고 뒤로 가며 확인한 결과를 기준으로 했다. 폼이 Suspense로 감싸인 이유는 next 08 문서에 있다.

한눈에 보기

// apps/store/src/shows/show-list-search-form.tsx
export function ShowListSearchForm({ query }: { query: ShowListQuery }) {
  const hiddenFields = getSearchFormHiddenFields(query); // 예: [['sort', 'newest']]

  return (
    <Form action="/" role="search">                      {/* ① GET 폼 */}
      <SearchField name="q" defaultValue={query.q ?? ''} ... />  {/* ② 비제어 입력 */}
      {hiddenFields.map(([name, value]) => (
        <input key={`${name}=${value}`} type="hidden" name={name} value={value} />  {/* ③ 숨은 입력 칸 */}
      ))}
    </Form>
  );
}

// apps/store/src/shows/header-search.tsx
return <ShowListSearchForm key={query.q ?? ''} query={query} />;  {/* ④ key */}
무엇푸는 문제
①GET 폼입력 칸의 값을 주소(/?q=정원)로 바꾼다. API는 그 주소를 그리는 서버가 부른다
②비제어 입력입력하는 동안 React가 글자를 관리하지 않는다. 처음 값만 defaultValue로 채운다
③숨은 입력 칸제출하면 쿼리 문자열이 통째로 바뀌는데, 지금 정렬이 사라지지 않게 함께 보낸다
④key뒤로 가기 등으로 주소의 검색어가 바뀌면 폼을 새로 만들어 검색 칸을 다시 채운다

검색 폼은 API를 부르지 않는다

검색 폼이 하는 일은 주소를 바꾸는 것뿐이다. 브라우저가 API를 직접 부르지 않는다. API는 바뀐 주소로 화면을 그리는 서버가 부른다.

  1. 제출 Enter나 돋보기 버튼을 누르면 주소가 /?q=정원으로 바뀐다. 폼이 하는 일은 여기까지다.
  2. 서버에서 그리기 Next가 서버에 새 주소의 화면을 요청한다. app/page.tsx가 searchParams에서 q를 읽는다.
  3. API 호출 page.tsx의 fetchShows가 서버에서 API GET /shows?q=정원을 부른다.
  4. 화면 갱신 결과 목록이 브라우저로 와서 페이지 부분만 바뀐다.

페이지 번호 링크와 같은 구조다. 링크는 /?page=2로, 검색 폼은 /?q=정원으로 주소를 바꾸고, 목록 화면은 "주소에 적힌 조건으로 API를 불러 그린다"는 일 하나만 한다. 그래서 검색 결과 주소를 공유하거나 새로고침해도 같은 결과가 나온다.

GET 폼: 입력 칸이 쿼리 문자열이 된다

HTML <form>에는 원래 이런 기능이 있다. method가 GET(기본값)이면, 제출할 때 브라우저가 폼 안에서 name이 있는 입력 칸을 모두 모아 쿼리 문자열을 만들고 action 주소로 이동한다. 자바스크립트가 필요 없다. 

<form action="/">
  <input name="q" value="정원" />
  <input name="sort" value="newest" />
</form>
<!-- 제출하면 → /?q=정원&sort=newest 로 이동 -->
// 브라우저가 하는 일을 자바스크립트로 쓰면
const query = new URLSearchParams(new FormData(form)).toString(); // 'q=정원&sort=newest'
location.href = `${form.action}?${query}`;

제출은 Enter나 type="submit" 버튼(돋보기)을 누를 때만 일어난다. 그래서 글자를 입력하는 동안에는 주소도 목록도 바뀌지 않는다.

새 주소의 쿼리 문자열은 폼에 있는 값만으로 만든다. 지금 주소에 있던 다른 값은 폼에 없으면 사라진다. 이것이 숨은 입력 칸이 필요한 이유다.

next/form이 더하는 것

next/form의 <Form>은 action에 문자열을 주면 위의 GET 폼과 똑같이 쿼리 문자열을 만든다. 다른 점은 이동 방법이다.

HTML <form>next/form의 <Form>
제출하면페이지 전체를 새로 불러온다링크를 누를 때처럼 새로고침 없이 화면을 옮긴다(클라이언트 내비게이션)
헤더 같은 공유 화면새로 그린다그대로 둔다
미리 불러오기없다폼이 화면에 보이면 이동할 화면의 공유 부분(레이아웃, loading.tsx)을 미리 불러 둔다
JS가 아직 실행되지 않았으면—보통 HTML 폼처럼 동작한다(점진적 향상)

개발 서버에서 검색해 보면 주소가 /?q=햄릿&sort=newest로 바뀌지만, 브라우저의 페이지 로드 기록은 처음 연 주소 그대로다. 페이지를 새로 불러오지 않고 화면만 옮겼다는 뜻이다.

숨은 입력 칸으로 정렬을 지킨다

정렬을 "최근 등록 순"으로 바꾼 상태(/?sort=newest)에서 "햄릿"을 검색한다고 하자. 폼에 검색 칸 하나만 있으면 새 주소는 그 칸의 값만으로 만들어진다.

지금 주소"햄릿" 검색 후 주소결과
숨은 입력 칸 없음/?sort=newest/?q=햄릿정렬이 기본값(공연 시작일 순)으로 풀린다
숨은 입력 칸 있음/?sort=newest/?q=햄릿&sort=newest정렬이 유지된다

그래서 지금 정렬을 type="hidden" 입력 칸에 담는다. 화면에는 보이지 않지만 name이 있으니 제출할 때 쿼리 문자열에 들어간다. 

<input type="hidden" name="sort" value="newest" />

어떤 숨은 입력 칸을 둘지는 getSearchFormHiddenFields(query)가 정한다(show-list-query.ts).

쿼리숨은 입력 칸이유
sort넣는다. 기본 정렬이면 넣지 않는다사용자가 고른 정렬을 지킨다. 기본값은 주소에서 빼는 규칙과 맞춘다
page넣지 않는다3페이지를 보다가 새로 검색하면 결과의 1페이지부터 봐야 한다. 빠지면 1페이지다
q넣지 않는다사용자가 검색 칸에 쓴 값이 곧 q다

비제어 입력: defaultValue는 처음에만 쓰인다

React에서 입력 칸을 다루는 방법은 두 가지다.

제어 입력비제어 입력
코드<input value={text} onChange={...} /><input defaultValue="정원" />
칸의 글자를 누가 관리하나React의 state브라우저(DOM)
prop을 바꾸면칸의 글자가 바로 바뀐다칸이 이미 있으면 아무 일도 없다

defaultValue는 "칸을 처음 만들 때 써 넣을 글자"다. 칸이 만들어진 뒤로는 사용자가 지우고 쓰는 글자를 브라우저가 관리하고, React는 신경 쓰지 않는다.

종이 신청서로 생각하면 쉽다. defaultValue는 신청서에 미리 인쇄된 글자다. 사용자는 그 위에 연필로 고쳐 쓴다. 나중에 "인쇄할 글자를 바꿔"라고 해도, 이미 손에 든 종이의 글자는 바뀌지 않는다. 새로 인쇄하는 종이부터 적용된다.

헤더의 검색 칸은 화면을 옮겨도 남아 있다

검색 칸은 레이아웃의 헤더에 있다. Next는 같은 레이아웃 아래에서 화면을 옮길 때 레이아웃을 새로 만들지 않고 페이지 부분만 바꾼다. 그래서 검색 칸은 처음 만든 그 칸이 계속 남는다. 같은 종이를 계속 들고 있는 셈이다.

주소가 바뀌면 HeaderSearch는 useSearchParams()로 새 검색어를 읽어 defaultValue로 넘긴다. 하지만 칸이 이미 있으니 무시된다. key를 빼고 개발 서버에서 실제로 해 보면 이렇게 된다.

순서주소목록검색 칸
① 열기/?q=정원정원 결과정원
② 칸을 고쳐 "햄릿"으로 검색/?q=햄릿햄릿 결과햄릿 (사용자가 쓴 글자)
③ 뒤로 가기/?q=정원정원 결과햄릿 ← 바뀌지 않는다

목록은 정원 결과인데 검색 칸에는 햄릿이 남아, 화면이 서로 맞지 않는다. 목록 아래의 "조건 초기화" 링크도 같다. 주소에서 q가 빠져도 검색 칸에는 예전 검색어가 남는다.

key를 바꿔 폼을 새로 만든다

<ShowListSearchForm key={query.q ?? ''} query={query} />

React는 key를 "이 컴포넌트가 누구인지"를 나타내는 이름표로 본다. 리스트를 그릴 때 항목마다 주는 그 key와 같은 것이다. 같은 자리에 그리는 컴포넌트의 이름표가 바뀌면 React는 "다른 것이 왔다"고 보고, 예전 폼을 DOM에서 지우고 새 폼을 처음부터 만든다. 새로 만드니 defaultValue가 다시 적용된다. 손에 든 종이를 버리고 새로 인쇄한 종이를 받는 것이다.

순서주소keyReact가 하는 일검색 칸
② "햄릿" 검색/?q=햄릿"햄릿"이름표가 바뀜 → 새로 만듦햄릿
③ 뒤로 가기/?q=정원"정원"이름표가 바뀜 → 새로 만듦정원

개발 서버에서 검색 칸 DOM 요소를 붙잡아 두고 비교해 보면, ②와 ③에서 모두 이전과 다른 요소로 바뀌어 있다. 폼을 새로 만들었다는 뜻이다.

key는 검색어만으로 정한다. 정렬은 검색 칸에 보이는 값이 아니고, 숨은 입력 칸은 value를 그대로 받는 제어 입력이라 정렬이 바뀌면 알아서 따라간다. 검색어가 같으면 폼을 다시 만들 이유가 없다.

제어 입력으로 하면

검색 칸을 제어 입력으로 만들어도 같은 문제를 풀 수 있다. 다만 코드가 늘어난다.

// 제어 입력이면: 칸의 글자를 state로 들고, 주소가 바뀌면 state도 맞춰야 한다
const [text, setText] = useState(query.q ?? '');
useEffect(() => setText(query.q ?? ''), [query.q]); // 뒤로 가기 대응
<input name="q" value={text} onChange={(event) => setText(event.target.value)} />
  • 검색 칸의 값은 제출할 때만 필요하다. 입력하는 동안 React가 글자를 알아야 할 일이 없다.
  • 주소가 바뀌었을 때 state를 맞추는 useEffect가 필요하고, 한 번은 예전 글자로 그렸다가 다시 그리게 된다.
  • 티켓은 store-ui 컴포넌트를 defaultValue로 채우는 비제어로 쓰라고 정했다.

그래서 브라우저에 맡기는 비제어 입력으로 두고, 주소의 검색어가 바뀌는 순간에만 key로 새로 만든다.

정렬 Select는 이 폼과 다르게 고르는 즉시 router.push로 주소를 바꾼다(show-sort-select.tsx). 검색어는 끝까지 입력한 뒤 제출해야 하지만, 정렬은 고르는 순간이 곧 결정이기 때문이다. 이때도 getSortChangeHref가 검색어는 두고 page만 뺀다.

주소에서 q가 빠져 목록은 전체 공연으로 돌아가지만, 검색 칸에는 방금 검색한 글자가 그대로 남는다. 헤더는 새로 만들어지지 않고, 비제어 입력은 바뀐 defaultValue(빈 글자)를 무시하기 때문이다.

4. 검색 결과 주소를 친구에게 보내면 친구도 같은 결과를 보는가? 검색 폼이 API를 직접 불렀다면 어땠을까?

같은 결과를 본다. 검색 조건이 모두 주소에 있고, 서버가 그 주소로 API를 불러 그리기 때문이다. 폼이 API를 직접 불러 결과만 화면에 바꿔 넣었다면 주소는 그대로라, 친구는 검색 전 목록을 보고 새로고침하면 검색 결과도 사라진다.
