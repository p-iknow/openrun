08 useSearchParams와 Suspense 경계

헤더의 제목 검색 칸은 모든 화면이 함께 쓰는 레이아웃에 있고, useSearchParams()로 주소의 검색어를 읽는다. 이 컴포넌트를 <Suspense>로 감싸지 않으면 빌드가 실패한다. 이 문서는 왜 그런지, Suspense가 정확히 무엇을 하는지를 본다. 내용은 Next 16.4.5의 문서와, 이 저장소의 스토어를 빌드하고 띄워 받은 HTML을 기준으로 했다.

한눈에 보기

레이아웃은 404처럼 빌드 때 미리 그리는 화면에도 쓰인다. 미리 그릴 때는 요청이 없으니 주소의 쿼리를 알 수 없다. 그래서 useSearchParams()를 쓰는 부분은 그런 화면에서 서버가 그리지 않고 브라우저가 그리게 미룬다. <Suspense>는 미룰 범위를 정하고, 미리 그린 HTML에서 그 자리를 채울 fallback을 받는다.

화면언제 그리나헤더 검색 칸을 그리는 곳
공연 목록 /동적 요청이 올 때마다서버. 처음 HTML부터 검색어가 채워져 있다
404정적 빌드할 때 한 번브라우저. 미리 그린 HTML에는 fallback(빈 검색 칸)이 있다

레이아웃은 주소의 쿼리를 받지 못한다

페이지(page.tsx)는 searchParams prop으로 주소의 쿼리를 받는다. 레이아웃(layout.tsx)은 받지 못한다. 레이아웃은 여러 페이지가 함께 쓰고, 같은 레이아웃 아래에서 링크로 이동하면 레이아웃은 다시 그리지 않고 페이지만 바꾼다. 레이아웃이 쿼리를 받으면 이동한 뒤에도 예전 쿼리를 들고 있게 되므로 Next가 아예 주지 않는다.

그래서 Next 문서는 레이아웃에서 쿼리가 필요하면 클라이언트 컴포넌트에서 useSearchParams()를 쓰라고 한다. 클라이언트 컴포넌트는 주소가 바뀔 때마다 브라우저에서 새 값으로 다시 그려진다. 헤더의 HeaderSearch가 이렇게 만들어졌다. 

// apps/store/src/shows/header-search.tsx
'use client';

export function HeaderSearch() {
  const pathname = usePathname();
  const searchParams = useSearchParams(); // 주소의 ?q=정원&sort=newest
  const query = getShowListQueryFromSearch(
    pathname === LIST_PATH ? searchParams : new URLSearchParams(),
  );
  return <ShowListSearchForm key={query.q ?? ''} query={query} />;
}

정적 화면과 동적 화면

Next는 화면마다 언제 그릴지를 정한다(next 00 문서). 빌드 결과의 경로 목록에 표시가 붙는다. 

Route (app)
┌ ƒ /
└ ○ /_not-found

○  (Static)   prerendered as static content
ƒ  (Dynamic)  server-rendered on demand
표시뜻비유이 저장소의 예
○ 정적 빌드할 때 한 번 그려 HTML 파일로 저장해 두고, 요청이 오면 그 파일을 보낸다 미리 인쇄해 둔 전단지 404 화면(/_not-found)
ƒ 동적 요청이 올 때마다 서버에서 그린다 주문을 받고 나서 인쇄 공연 목록 /. await connection()과 searchParams를 쓰기 때문이다

두 화면 모두 같은 루트 레이아웃(app/layout.tsx) 안에 그려진다. 그래서 헤더의 검색 칸은 정적 화면에도, 동적 화면에도 들어간다.

미리 그릴 때 주소를 모른다

'use client'가 붙은 클라이언트 컴포넌트도 처음 HTML은 서버에서 그린다(next 03 문서의 SSR 단계). 정적 화면이면 그 "서버에서 그리기"가 빌드 때 일어난다.

빌드 때 404 화면을 그리다가 HeaderSearch의 useSearchParams()를 만나면 Next는 막힌다. 이 HTML은 나중에 /없는-주소?q=정원으로 오는 사람에게도, /없는-주소로 오는 사람에게도 똑같이 보내질 파일이다. 전단지를 인쇄하는 시점에는 누가 어떤 주소로 올지 모르니, 검색어 자리에 무엇을 인쇄해야 할지 정할 수 없다.

모르는 부분은 브라우저가 그린다

Next는 이럴 때 그 부분을 미리 그리지 않는다. 미리 그린 HTML에는 빈자리를 남겨 두고, 페이지가 브라우저에서 열린 뒤 브라우저가 실제 주소를 읽어 그 자리를 그린다. 이것을 클라이언트 렌더링으로 넘긴다(client-side rendering bailout)고 한다.

  1. 빌드 404 화면을 그리다 useSearchParams()를 만난다. 그 부분은 그리지 않고 표시만 남긴 채 HTML로 저장한다.
  2. 요청 누군가 없는 주소로 오면 저장해 둔 HTML을 그대로 보낸다. 빈자리에는 fallback이 보인다.
  3. 브라우저 JS가 실행되면 React가 HeaderSearch를 처음부터 그린다. 이제는 window.location이 있으니 주소의 쿼리를 읽을 수 있다.

동적 화면에서는 이 일이 없다. 요청이 온 뒤에 그리므로 서버도 주소를 안다. Next 문서도 동적 화면에서는 useSearchParams()가 처음 서버 렌더링 때부터 값을 돌려준다고 적고 있다.

Suspense가 정하는 범위

브라우저로 넘기는 범위는 useSearchParams()를 쓴 컴포넌트부터 가장 가까운 바깥 <Suspense>까지다. Suspense를 어디에 두느냐에 따라 미리 그리는 양이 달라진다.

  • <html>, <body>미리 그린다
    • <header> 로고미리 그린다
    • <Suspense> 경계 여기서 멈추고 fallback을 HTML에 넣는다
      • <HeaderSearch> 브라우저가 그린다
    • 404 본문미리 그린다

Suspense가 없으면 멈출 경계가 없다. 그러면 화면 전체를 미리 그리지 못하고 통째로 브라우저에 맡겨야 한다. 정적 화면을 만든 의미가 없어지므로, Next는 이것을 실수로 보고 빌드를 멈춘다. 이 저장소에서 Suspense를 빼고 빌드하면 실제로 이렇게 나온다. 

⨯ useSearchParams() should be wrapped in a suspense boundary at page "/404".
Error occurred prerendering page "/_not-found".
Export encountered an error on /_not-found/page: /_not-found, exiting the build.

Suspense는 컴포넌트를 클라이언트 컴포넌트로 바꾸는 장치가 아니다. HeaderSearch는 이미 'use client'다. Suspense는 "미리 그리다 막히면 여기까지만 비우고, 그 자리에 이것(fallback)을 넣어라"라는 경계 표시다.

fallback에 무엇을 둘까

// apps/store/app/layout.tsx
<Suspense fallback={<ShowListSearchForm query={normalizeShowListQuery({}).query} />}>
  <HeaderSearch />
</Suspense>

fallback은 미리 그린 HTML에서 브라우저가 진짜 컴포넌트를 그리기 전까지 보이는 화면이다. 여기서는 normalizeShowListQuery({}), 즉 "쿼리가 하나도 없는 주소"로 그린 검색 폼을 둔다. 검색어는 비어 있고 정렬은 기본값이다.

  • 생김새가 같다. 진짜 검색 칸과 크기, 모양이 똑같아서 바뀌는 순간 헤더가 덜컥거리지 않는다. "불러오는 중…" 같은 글자를 두면 높이가 달라져 아래 내용이 밀린다.
  • 정적 화면에서는 결과도 같다. HeaderSearch는 공연 목록(/)이 아니면 주소를 무시하고 빈 쿼리로 그린다. 지금 정적 화면은 404뿐이라, 브라우저가 그려도 fallback과 같은 빈 칸이 나온다.
  • JS가 늦어도 쓸 수 있다. fallback도 action="/"가 있는 진짜 GET 폼이라, JS가 실행되기 전에 검색해도 공연 목록으로 간다.

빌드 결과물로 확인하기

404: fallback이 든 HTML

빌드하면 404 화면이 .next/server/app/_not-found.html 파일로 저장된다. 그 안에서 검색 칸 부분을 찾으면 이렇다(클래스는 줄였다). 

<!--$!--><template data-dgst=""></template>
<form role="search" action="/">
  ...
  <input type="search" placeholder="공연 제목으로 찾기" maxLength="50" name="q" value=""/>
  ...
</form>

<!--$!-->는 React가 Suspense 경계에 남기는 표시다. 느낌표가 붙으면 "서버에서 이 경계 안을 그리지 못했으니 브라우저에서 처음부터 그려라"라는 뜻이다. 그 뒤에 이어지는 폼이 fallback이고, 검색 칸의 value는 비어 있다. 같은 파일에서 다른 Suspense 경계는 느낌표 없는 <!--$-->로, 서버가 끝까지 그린 경계다.

공연 목록: 검색어가 채워진 HTML

/?q=정원을 요청해 서버가 보낸 HTML을 보면, 검색 칸에 처음부터 검색어가 들어 있다.

<input type="search" placeholder="공연 제목으로 찾기" maxLength="50" name="q" value="정원"/>

동적 화면이라 서버가 요청을 받은 뒤 그리므로 useSearchParams()가 값을 돌려준다. fallback은 쓰이지 않는다.

자주 하는 오해

오해실제
'use client'면 서버에서 그리지 않는다 클라이언트 컴포넌트도 처음 HTML은 서버에서 그린다. 브라우저에서 도 실행될 뿐이다
Suspense로 감싸면 늘 브라우저에서 그린다 미리 그리다 막히는 정적 화면에서만 브라우저로 넘긴다. 동적 화면에서는 서버가 그대로 그린다
Suspense는 데이터를 기다릴 때만 쓴다 여기서는 기다릴 데이터가 없다. "미리 그리지 못하는 부분의 범위"를 정하려고 쓴다
빌드 오류만 막으면 되니 레이아웃 전체를 감싸도 된다 감싼 범위 전체가 정적 화면에서 브라우저 몫이 된다. useSearchParams()를 쓰는 컴포넌트만 좁게 감싼다

우리 프로젝트에서는

파일하는 일
apps/store/app/layout.tsx헤더에 <Suspense fallback={빈 검색 폼}><HeaderSearch /></Suspense>를 둔다
apps/store/src/shows/header-search.tsxuseSearchParams(), usePathname()으로 주소를 읽어 검색 폼을 채운다. 공연 목록이 아니면 빈 쿼리로 그린다
apps/store/src/shows/show-list-search-form.tsx검색 폼 자체. fallback과 HeaderSearch가 함께 쓴다

나중에 공연 상세처럼 정적으로 그릴 수 있는 화면이 늘어나도, 그 화면들의 헤더 검색 칸은 같은 방식으로 fallback이 먼저 보이고 브라우저에서 바뀐다. 목록 밖에서는 빈 칸이 맞으므로 사용자 눈에는 차이가 없다.

스스로 확인하기

1. 아래처럼 Suspense를 빼면 무엇이 일어나는가? 개발 서버(next dev)와 빌드(next build)에서 각각 생각해 본다.

Suspense가 정하는 범위. 개발 서버는 화면을 미리 그리지 않고 요청마다 그린다.

-<Suspense fallback={...}>
   <HeaderSearch />
-</Suspense>
답 보기

개발 서버에서는 요청마다 그리므로 주소를 알고, 화면이 그대로 나온다. 문제는 빌드 때 드러난다. 404 화면을 미리 그리다 useSearchParams()를 만나고, 멈출 경계가 없어 useSearchParams() should be wrapped in a suspense boundary로 빌드가 실패한다. 개발 중에 괜찮았다고 안심하면 안 되는 이유다.

2. fallback을 아래처럼 바꾸면 404 화면에서 무엇이 달라지는가?

fallback에 무엇을 둘까.

-<Suspense fallback={<ShowListSearchForm query={normalizeShowListQuery({}).query} />}>
+<Suspense fallback={<p>불러오는 중…</p>}>
답 보기

404 HTML에는 검색 칸 대신 "불러오는 중…"이 들어간다. JS가 실행될 때까지 검색할 수 없고, 글자와 검색 칸의 높이가 달라 바뀌는 순간 헤더가 덜컥거린다. 공연 목록 /은 동적 화면이라 fallback을 쓰지 않으므로 달라지지 않는다.

3. 레이아웃이 searchParams를 받을 수 있다면 어떤 버그가 생길 수 있는가?

같은 레이아웃 아래에서 링크로 이동하면 레이아웃은 다시 그리지 않는다. 그러면 /?q=정원에서 /?q=햄릿으로 이동해도 레이아웃은 처음 받은 정원을 들고 있어, 헤더 검색 칸에 예전 검색어가 남는다. 그래서 Next는 레이아웃에 주지 않고, 주소가 바뀔 때마다 다시 그려지는 useSearchParams()를 쓰게 한다.
