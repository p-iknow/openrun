06 next/image가 해결하는 문제와 동작 방식

next/image는 <img> 태그를 대신 그려 주는 컴포넌트와, 이미지를 줄이고 바꿔 주는 서버 기능(/_next/image) 두 부분으로 되어 있다. 먼저 일반 <img>로는 어떤 문제가 생기는지 보고, 컴포넌트가 어떤 HTML을 만들고, 브라우저가 그중 어떤 파일을 고르고, 서버가 그 파일을 어떻게 만들어 캐시하는지 차례로 본다. 내용은 Next 16.4.5의 문서와 소스 코드를 기준으로 했고, 예시는 공연 카드의 포스터(apps/store/src/shows/show-card.tsx)다.

해결하려는 문제

포스터를 일반 <img>로 그리면 이렇게 된다.

<img src="http://localhost:3001/posters/show-01-3fa2b1c9.png" alt="" />

코드는 짧지만, 휴대폰으로 공연 목록을 여는 순간 다섯 가지 문제가 한꺼번에 생긴다.

1. 화면보다 훨씬 큰 파일을 받는다

포스터 원본은 600×800 PNG로 약 70KB다. 모바일 카드에서는 96px 폭으로 그려지는데도 브라우저는 원본 전체를 받는다. 같은 포스터를 폭 256의 WebP로 줄이면 약 5KB다. 한 페이지에 카드가 20장이면 원본은 약 1.4MB, 줄인 파일은 약 100KB다. 느린 모바일 회선에서는 이 차이가 그대로 기다리는 시간과 데이터 요금이 된다.

파일 크기 (시드 포스터 한 장을 실제로 변환해 잰 값)
원본 PNG 600×800 71KB
WebP 폭 640 (원본이 600이라 600으로) 12KB
WebP 폭 384 7.7KB
WebP 폭 256 4.9KB

2. 오래된 이미지 형식을 쓴다

PNG와 JPEG는 오래된 형식이다. 요즘 브라우저는 같은 화질을 더 작게 담는 WebP와 AVIF를 읽는다. 하지만 업로드되는 원본은 대부분 PNG나 JPEG이고, 모든 브라우저가 새 형식을 읽는다고 장담할 수도 없다.

3. 이미지가 도착하면 화면이 밀린다

브라우저는 이미지를 받기 전까지 그 크기를 모른다. 그래서 처음에는 높이 0으로 그렸다가, 이미지가 오면 그만큼 아래 내용을 밀어 낸다. 공연 제목을 누르려던 손가락 아래로 다른 카드가 미끄러져 들어온다. 이 흔들림을 CLS(Cumulative Layout Shift)라고 하고, 구글이 페이지 품질을 재는 핵심 지표(Core Web Vitals) 중 하나다.

4. 보이지도 않는 이미지까지 처음에 받는다

스크롤해야 보이는 아래쪽 카드 이미지도 페이지를 열자마자 함께 받는다. 그 사이 첫 화면에 꼭 필요한 글꼴, 스크립트, 위쪽 이미지가 회선을 나눠 써서 느려진다.

5. 직접 고치려면 일이 많다

위 문제는 HTML 기능만으로도 고칠 수 있다. 다만 직접 하면 이만큼 써야 하고, 이미지마다 반복해야 한다.

<picture>
  <source type="image/webp"
          srcset="show-01-256.webp 256w, show-01-384.webp 384w, show-01-640.webp 640w"
          sizes="(min-width: 1024px) 280px, (min-width: 640px) 33vw, 96px" />
  <img src="show-01-640.png"
       srcset="show-01-256.png 256w, show-01-384.png 384w, show-01-640.png 640w"
       sizes="(min-width: 1024px) 280px, (min-width: 640px) 33vw, 96px"
       width="600" height="800" loading="lazy" decoding="async" alt="" />
</picture>

그리고 이 HTML이 가리키는 파일 여섯 개를 누군가 미리 만들어 둬야 한다. 포스터가 새로 올라올 때마다 여러 폭, 여러 형식으로 변환하는 작업을 따로 돌리고, 폭 목록을 바꾸면 기존 이미지를 전부 다시 만들어야 한다.

next/image가 하는 일

next/image는 다섯 문제를 이렇게 나눠 맡는다. 개발자는 <Image> 한 줄만 쓴다.

문제 next/image의 방법 맡는 쪽 자세히
1. 큰 파일 여러 폭의 후보를 srcset으로 자동으로 적고, 브라우저가 화면에 맞는 것을 고른다. 그 폭의 파일은 서버가 요청 때 줄여 만든다 컴포넌트 서버 srcset 규칙, 고르는 방법
2. 옛 형식 브라우저가 보낸 Accept 헤더를 보고 WebP를 읽을 수 있으면 WebP로 바꿔 준다. 못 읽으면 원본 형식 그대로 준다 서버 최적화 서버
3. 화면 밀림 width·height, fill, 정적 import 중 하나를 쓰지 않으면 오류를 낸다. 이미지가 오기 전에 자리가 정해진다 컴포넌트 크기 정하기
4. 안 보이는 이미지 loading="lazy"가 기본값이라 화면 가까이 올 때 받는다. 중요한 이미지만 preload로 앞당긴다 컴포넌트 언제 받나
5. 손이 많이 감 파일을 미리 만들지 않는다. 처음 요청이 올 때 만들어 디스크에 캐시하고, 다음부터는 캐시에서 준다. 폭 목록을 바꿔도 다시 만들 것이 없다 서버 캐시

핵심은 일을 둘로 나눈 것이다. 컴포넌트는 HTML 표준 기능(srcset, sizes, loading, width·height)을 빠짐없이 채운 <img>를 만든다. 서버는 그 HTML이 요청하는 파일을 그때그때 만들어 준다. 브라우저 입장에서는 평범한 <img> 하나라서 자바스크립트 없이도 동작한다.

대가도 있다. 처음 요청은 서버가 이미지를 줄이느라 느리고, 서버의 CPU와 디스크를 쓴다. 누구나 부를 수 있는 공개 API가 하나 생기므로 남용을 막는 설정이 필요하다(보안). 캐시를 지우는 방법이 없어서 이미지 내용이 바뀌면 주소를 바꿔야 한다(캐시 버스팅).

위의 세 단계가 아래 절의 순서다. 컴포넌트가 만드는 HTML, 브라우저의 선택, 최적화 서버와 캐시를 차례로 본다.

컴포넌트가 만드는 HTML

카드의 포스터 코드는 이렇다.

const POSTER_SIZES = '(min-width: 1024px) 280px, (min-width: 640px) 33vw, 96px';

<Image src={card.posterUrl} alt="" fill sizes={POSTER_SIZES} className="object-cover" />

서버 컴포넌트가 실행되면 HTML에는 대략 이런 태그가 들어간다(주소는 줄였다).

<img
  alt=""
  loading="lazy"
  decoding="async"
  data-nimg="fill"
  class="object-cover"
  style="position:absolute;height:100%;width:100%;left:0;top:0;right:0;bottom:0;color:transparent"
  sizes="(min-width: 1024px) 280px, (min-width: 640px) 33vw, 96px"
  srcset="/_next/image?url=http%3A%2F%2Flocalhost%3A3001%2Fposters%2Fshow-01-3fa2b1c9.png&w=256&q=75 256w,
          /_next/image?url=...&w=384&q=75 384w,
          /_next/image?url=...&w=640&q=75 640w,
          ...
          /_next/image?url=...&w=3840&q=75 3840w"
  src="/_next/image?url=...&w=3840&q=75"
/>
속성 뜻
srcset 같은 이미지의 여러 폭 후보. 256w는 "이 파일은 폭이 256px"이라는 뜻이다. 각 후보의 주소가 원본이 아니라 /_next/image다.
sizes 화면 폭마다 이 이미지가 그려질 폭. 브라우저가 CSS를 읽기 전에 후보를 고르려고 쓴다
src srcset을 모르는 옛 브라우저용. 가장 큰 후보를 넣는다
loading="lazy" 기본값. 화면 가까이 올 때까지 요청을 미룬다
decoding="async" 이미지를 푸는 작업이 글자 그리기를 막지 않게 한다
style fill이라서 부모를 꽉 채우는 absolute 배치가 붙는다

이 모든 것이 서버에서 HTML로 만들어진다. 브라우저에서 따로 실행되는 자바스크립트 없이 일반 <img> 기능(srcset, sizes, loading)만으로 동작한다.

srcset을 만드는 규칙

후보 폭은 설정의 두 목록을 합쳐서 고른다. 아래는 Next 16의 기본값이다.

deviceSizes: [640, 750, 828, 1080, 1200, 1920, 2048, 3840] // 화면 폭 기준
imageSizes:  [32, 48, 64, 96, 128, 256, 384]                // 화면보다 작은 이미지 기준
// 둘을 합쳐 정렬한 것이 전체 후보: 32, 48, ..., 384, 640, ..., 3840

어떤 후보를 srcset에 넣을지는 props에 따라 다르다(get-img-props.js의 getWidths).

props srcset 어울리는 경우
width={200}, sizes 없음 1x, 2x 두 개(200 이상, 400 이상인 가장 작은 후보) 아이콘, 아바타처럼 크기가 고정된 이미지
fill, sizes 없음 deviceSizes만, sizes="100vw"로 간주 화면 폭을 꽉 채우는 배경 이미지
sizes 있음 전체 후보에서 너무 작은 것만 뺀 목록 카드 그리드처럼 화면에 따라 폭이 바뀌는 이미지

sizes가 있을 때 "너무 작은 것"은 이렇게 정한다. sizes 문자열에서 vw 값을 찾아 가장 작은 비율을 구하고, deviceSizes의 가장 작은 값(640)에 곱한다. 그보다 작은 후보는 뺀다. 

// 우리 sizes에서 vw 값은 33vw 하나 → 640 × 0.33 = 211.2
// 211.2 이상인 후보만 남는다
srcset 폭 = [256, 384, 640, 750, 828, 1080, 1200, 1920, 2048, 3840]

96px, 280px처럼 px로 적은 값은 이 계산에 쓰이지 않는다. 그래서 모바일에서 96px로 그려지는 포스터인데도 96, 128 후보는 빠지고 가장 작은 후보가 256이다. 큰 손해는 아니지만, sizes가 srcset 후보까지 바꾼다는 점은 알아 둔다.

브라우저가 파일을 고르는 방법

  1. 그려질 폭 계산 sizes를 앞에서부터 읽어 처음 맞는 조건의 값을 쓴다. 화면 폭 390px이면 앞의 두 조건이 맞지 않아 96px이다.
  2. 화면 배율 곱하기 휴대폰은 화면 배율(DPR)이 보통 2~3이라 CSS 1px에 실제 픽셀이 2~3개다. 96px × 3 = 288px만큼의 픽셀이 필요하다.
  3. 그 이상인 후보 고르기 288 이상인 가장 작은 후보 384w를 고른다. 정확한 선택은 브라우저마다 조금씩 다르다. 캐시에 이미 더 큰 파일이 있으면 그것을 쓰기도 한다.
화면 sizes 결과 필요한 픽셀(DPR 2 기준) 받는 파일
모바일 390px 96px 192 w=256
태블릿 768px (3열) 33vw ≈ 253px 507 w=640
데스크톱 1440px (4열) 280px 560 w=640

브라우저는 CSS를 받기 전에, HTML을 읽는 순간 이미지 요청을 시작할 수 있다. 그 시점에는 그리드가 몇 열인지 모르므로 sizes로 미리 알려 줘야 한다. sizes를 빼면 이미지가 화면 폭만큼(100vw) 크다고 보고 모바일에서도 1080px 같은 큰 파일을 받는다. 그래서 그리드 열 수를 바꾸면 sizes도 함께 고친다.

크기 정하기: width·height, fill, 정적 import

이미지가 오기 전에 자리를 정해 두지 않으면, 이미지가 도착할 때 아래 내용이 밀린다(CLS). next/image는 세 방법 중 하나를 꼭 쓰게 한다.

방법 자리를 정하는 쪽 언제
width, height <img width height> 속성. 브라우저가 이 비율로 자리를 잡는다. 실제 그려지는 크기는 CSS가 정한다 원본 크기를 알 때
fill 부모 요소. 이미지는 absolute로 부모를 채우므로 부모에 position과 크기가 있어야 한다 원본 크기를 모르거나, 틀에 맞춰 잘라야 할 때. 포스터가 이 경우다
정적 import (import hero from './hero.png') 빌드가 파일을 읽어 width, height를 자동으로 채운다 저장소 안에 있는 고정 이미지

정적 import는 빌드가 파일 내용으로 만든 해시를 주소에 넣고(/_next/static/media/hero.4f2a1c.png), 1년짜리 immutable 캐시 헤더로 내보낸다. 아래 캐시 버스팅을 Next가 대신 해 주는 셈이다. 포스터는 시드가 실행 중에 만드는 파일이라 이 방법을 쓸 수 없다. 틀을 잡는 Tailwind 조합은 style 00 문서에 있다.

언제 받나: loading, preload, placeholder

prop 기본값 하는 일
loading "lazy" 화면에서 일정 거리 안으로 들어올 때 요청한다. 스크롤 아래의 카드 이미지는 처음에 받지 않는다. "eager"는 바로 받는다
preload false <head>에 <link rel="preload">를 넣어 HTML 본문을 읽기 전부터 받는다. 화면에서 가장 큰 요소(LCP)인 첫 화면 대표 이미지에만 쓴다. Next 16에서 priority를 대신한다
fetchPriority 없음 "high"면 브라우저가 다른 요청보다 먼저 받는다. 문서는 대부분 preload보다 loading="eager"나 이것을 권한다
placeholder "empty" 로드 전에 보일 그림. "blur"는 blurDataURL(아주 작은 흐린 이미지)을 깔아 둔다. 정적 import면 빌드가 자동으로 만든다

공연 목록은 카드가 많아 어느 하나가 대표 이미지라고 하기 어렵다. 그래서 모두 기본값(lazy)으로 두고, placeholder 대신 틀의 배경색을 자리 표시자로 쓴다.

최적화 서버 /_next/image

srcset의 주소는 모두 /_next/image?url=…&w=…&q=…다. 이 주소를 받은 Next 서버가 하는 일은 다음과 같다(next/dist/server/image-optimizer.js).

  1. 요청 검사 url이 허용 목록(/로 시작하면 localPatterns, 아니면 remotePatterns)에 맞는지, w가 deviceSizes·imageSizes에 있는 값인지, q가 qualities(기본 [75])에 있는지 본다. 하나라도 어긋나면 400이다.
  2. 출력 형식 정하기 브라우저가 보낸 Accept 헤더에 image/webp가 있으면 WebP로 만든다(기본 formats: ['image/webp']). 없으면 원본 형식 그대로 둔다.
  3. 캐시 찾기 원본 주소, 폭, 품질, 출력 형식으로 키를 만들어 .next/cache/images에서 찾는다. 있으면 바로 응답한다.
  4. 원본 받기 상대 주소(/posters/a.png)는 네트워크를 거치지 않고 서버 안에서 그 경로를 처리해 받는다. 절대 주소는 HTTP로 받아 오며, 이때 호스트가 사설 IP로 풀리면 거절하고 리다이렉트는 3번까지 따라간다.
  5. 줄이고 바꾸기 받은 내용이 실제 이미지인지 확인하고, sharp로 폭 w에 맞게 줄이고(원본보다 크게 키우지는 않는다) 품질 q의 WebP로 바꾼다. SVG는 기본으로 거절하고(dangerouslyAllowSVG), 움직이는 GIF·PNG·WebP는 줄이지 않고 원본을 돌려준다.
  6. 저장하고 응답 결과를 디스크 캐시에 쓰고 응답한다. Vary: Accept(형식마다 따로 캐시), Content-Disposition: attachment(주소를 직접 열면 내려받게 해 악성 파일이 페이지처럼 열리지 않게 함), X-Nextjs-Cache: MISS 헤더가 붙는다.
선택 읽기: 우리 포스터 하나가 받는 응답

포스터 원본은 600×800 PNG다. 데스크톱에서 w=640을 요청하면 원본보다 크게 키우지 않으므로 폭 600의 WebP가 온다. 모바일의 w=256은 256×341 WebP다. 화면에 따라 받는 크기가 몇 배씩 차이 난다. 

HTTP/1.1 200 OK
Content-Type: image/webp
Cache-Control: public, max-age=14400, must-revalidate
Vary: Accept
Content-Disposition: attachment; filename="show-01-3fa2b1c9.webp"
X-Nextjs-Cache: MISS

개발 서버(next dev)에서는 max-age=0이라 브라우저가 매번 다시 확인한다.

캐시와 캐시 버스팅

최적화 결과는 두 곳에 캐시된다.

  • Next 서버의 디스크(.next/cache/images): 유효 기간은 minimumCacheTTL(기본 4시간)과 원본 응답의 Cache-Control max-age 중 큰 값이다. 디스크 용량이 넘치면 오래 안 쓴 것부터 지운다.
  • 브라우저: 응답의 Cache-Control을 따라 따로 캐시한다.
X-Nextjs-Cache 상황 응답
MISS 처음 요청 원본을 받아 만든 새 결과
HIT 기간 안에 다시 요청 디스크에 있던 결과
STALE 기간이 지난 뒤 요청 일단 옛 결과를 주고, 뒤에서 원본을 다시 받아 새로 만든다. 다음 요청부터 새 결과

캐시의 키는 주소다. 원본 파일의 내용이 바뀌어도 주소가 같으면 서버도 브라우저도 바뀐 걸 모른다. 그리고 문서에 적힌 대로 이 캐시를 지우는 API가 없다. 남은 방법은 src를 바꾸거나 캐시 폴더를 직접 지우는 것뿐이다.

캐시 버스팅(cache busting): 내용이 바뀌면 주소도 바뀌게 만들어 캐시를 피하는 방법이다. 가장 흔한 형태는 파일 이름에 내용의 해시를 넣는 것이다. 내용이 바뀌면 새 주소라 새로 받고, 내용이 같으면 같은 주소라 캐시를 그대로 쓴다. 빌드 결과물의 main.4f2a1c.js, Next의 정적 import 이미지가 모두 이 방법이다.

시드가 그리는 포스터에는 공연 기간이 찍혀서 시드를 돌린 날마다 내용이 바뀐다. 그래서 시드는 포스터 경로에 PNG 내용의 해시 8자리를 붙인다(show-01-3fa2b1c9.png). 경로가 show-01.png로 고정이면 다음 날 시드 뒤에도 카드에 어제 날짜의 포스터가 보인다.

보안: 허용 목록과 SSRF

/_next/image는 누구나 주소를 바꿔 부를 수 있는 공개 API다. 설정의 허용 목록은 대부분 이 API가 남용되지 않게 막는 장치다.

설정 막는 것
remotePatterns 아무 외부 이미지나 우리 서버 자원으로 줄여 주는 것. 프로토콜, 호스트, 포트, 경로까지 맞아야 한다. 컴포넌트의 src가 여기에 없으면 렌더링 때 바로 오류가 난다
localPatterns 상대 주소 중 의도하지 않은 경로를 줄이는 것
w는 크기 목록, qualities w=1부터 w=3840까지, 품질 1~100을 모두 요청해 변형을 수천 개 만들게 하는 공격(CPU와 디스크 소모). 그래서 Next 16부터 qualities가 필수다
dangerouslyAllowLocalIP (기본 false) SSRF. 아래 설명
dangerouslyAllowSVG (기본 false) 스크립트가 든 SVG가 우리 도메인에서 열리는 것

SSRF(Server-Side Request Forgery)는 서버를 시켜 서버만 닿을 수 있는 곳에 요청하게 만드는 공격이다. 최적화 서버는 내부망 안에서 원본을 받아 오므로, 허용 범위가 넓으면 이런 요청이 가능해진다. 

/_next/image?url=http://169.254.169.254/latest/meta-data/&w=64&q=75   ← 클라우드 서버 정보
/_next/image?url=http://10.0.0.5:8080/admin/purge&w=64&q=75          ← 내부 관리 API

응답이 이미지가 아니면 돌려주지 않아 내용을 그대로 빼내기는 어렵다. 하지만 오류의 차이로 내부에 무엇이 있는지 알아내거나, GET으로 동작하는 내부 API를 실행시킬 수 있다. Next 16은 호스트가 사설 IP(10.x, 127.x, 169.254.x 등)로 풀리면 거절한다. 리다이렉트는 remotePatterns를 다시 검사하지 않지만, 따라간 주소도 사설 IP 검사는 다시 받는다. dangerouslyAllowLocalIP는 이 마지막 방어선을 끄는 옵션이다.

최적화를 끄거나 맡기기

  • unoptimized: /_next/image를 거치지 않고 원본 주소를 그대로 쓴다. srcset도 만들지 않는다. 1KB 미만 이미지, SVG, 움직이는 GIF처럼 줄여도 이득이 없을 때 쓴다.
  • loader / loaderFile: srcset의 주소를 만드는 함수를 바꾼다. Cloudinary, imgix, CloudFront 같은 이미지 CDN이 줄이기를 맡고, Next 서버는 이미지 일을 하지 않는다. 트래픽이 많은 서비스는 보통 이쪽을 쓴다.

우리 프로젝트에서는

  • API가 포스터의 완전한 URL(POSTER_BASE_URL + 포스터 경로)을 주므로 src가 절대 주소다. 그래서 최적화 서버가 원본을 HTTP로 받고, 개발에서는 그 호스트가 localhost라 사설 IP 차단에 걸린다. apps/store/next.config.ts는 POSTER_BASE_URL의 호스트가 localhost, 127.0.0.1, [::1]일 때만 dangerouslyAllowLocalIP를 켜고, remotePatterns는 그 주소의 /posters/** 하나만 허용한다.
  • POSTER_BASE_URL이 없으면 remotePatterns가 빈 목록이다. 빌드는 통과하지만 카드를 그릴 때 "hostname is not configured" 오류가 난다. 값을 바꾸면 스토어 서버를 다시 켜야 한다.
  • 포스터 경로에 내용 해시를 넣어 캐시 버스팅을 한다(#42).
  • sizes는 ShowCardList의 열 수(모바일 1열 가로형, sm 3열, lg 4열)와 맞춘다.

스스로 확인하기

1. sizes를 지우면 모바일 카드는 어떤 파일을 받나?

srcset을 만드는 규칙, 브라우저가 고르는 방법. 화면 390px, DPR 3.

-<Image src={card.posterUrl} alt="" fill sizes={POSTER_SIZES} className="object-cover" />
+<Image src={card.posterUrl} alt="" fill className="object-cover" />
답 보기

fill에 sizes가 없으면 srcset은 deviceSizes(640~3840)만 쓰고 sizes="100vw"가 붙는다. 브라우저는 이미지가 390px이라고 보고 390 × 3 = 1170 이상인 w=1200을 고른다. 96px 칸에 그릴 이미지를 폭 600짜리 원본 크기로 받는다(원본보다 키우지는 않으므로). 필요한 것보다 몇 배 큰 파일이다.

2. 포스터 경로에 해시가 없을 때, 운영 서버에서 시드 다음 날 첫 방문자와 두 번째 방문자는 무엇을 보나?

캐시와 캐시 버스팅. 어제 만든 캐시는 4시간이 지나 기간이 끝났고, 두 방문자의 브라우저 캐시는 비어 있다.

답 보기

첫 방문자는 어제 포스터를 본다. 기간이 지난 캐시는 STALE로 옛 결과를 먼저 주고 뒤에서 다시 만들기 때문이다. 두 번째 방문자는 새로 만든 오늘 포스터를 본다. 기간이 아직 안 지났다면 둘 다 어제 포스터를 본다. 같은 주소인 한 언제 바뀔지 알 수 없다는 것이 문제다.

3. 공격자가 /_next/image?url=…&w=1000&q=75 를 보내면 어떻게 되나?

1000은 deviceSizes에도 imageSizes에도 없어서 400으로 거절된다. 폭을 마음대로 받으면 같은 이미지로 변형을 끝없이 만들게 해 CPU와 디스크를 쓰게 할 수 있기 때문이다.

4. src를 절대 주소 대신 /posters/show-01-3fa2b1c9.png 처럼 상대 주소로 주면 dangerouslyAllowLocalIP가 필요할까?

필요 없다. 상대 주소는 최적화 서버가 네트워크로 받지 않고 서버 안에서 그 경로를 처리해 받으므로 사설 IP 검사를 거치지 않는다. 대신 localPatterns로 허용 경로를 정한다. 우리는 스펙이 완전한 URL을 요구하고 나중에 포스터가 다른 호스트로 옮겨 가므로 절대 주소를 쓴다.
