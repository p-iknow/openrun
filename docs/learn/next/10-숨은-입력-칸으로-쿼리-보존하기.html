10 숨은 입력 칸으로 쿼리 보존하기

검색 결과 화면에서 정렬을 바꿔 둔 뒤 다시 검색하면 정렬이 풀리는 문제가 있다. GET 폼은 제출할 때 주소의 쿼리 문자열을 폼 값으로 통째로 바꾸기 때문이다. 이 문서는 <input type="hidden">으로 지금 쿼리를 지키는 방법과, 이 방법의 장점과 약점, 대안을 본다. GET 폼의 동작은 Chrome에서 작은 시험 페이지로 직접 확인했다.

한눈에 보기

GET 폼은 제출할 때 폼 안의 입력 칸만으로 새 주소의 쿼리 문자열을 만든다. 그래서 지금 주소에 있던 다른 쿼리(예: 정렬)는 사라진다. 지키고 싶은 쿼리를 화면에 보이지 않는 입력 칸(type="hidden")에 담아 두면, 제출할 때 함께 실려 간다. 

<!-- 지금 주소: /?sort=newest -->
<form action="/">
  <input name="q" placeholder="공연 제목으로 찾기" />
  <input type="hidden" name="sort" value="newest" />  <!-- 지금 정렬을 함께 보낸다 -->
</form>
<!-- "햄릿"을 쓰고 제출하면 → /?q=햄릿&sort=newest -->

GET 폼이 주소를 만드는 규칙

<form>의 method를 정하지 않으면 GET이다. GET 폼을 제출하면 브라우저가 다음 순서로 이동한다. 자바스크립트는 필요 없다.

  1. 값 모으기 폼 안에서 name이 있는 입력 칸의 이름과 값을 차례로 모은다.
  2. 쿼리 문자열 만들기 모은 값을 q=햄릿&sort=newest처럼 잇는다. 한글과 공백은 주소에 쓸 수 있게 바꾼다(인코딩).
  3. 이동 action 주소 뒤에 ?와 쿼리 문자열을 붙여 그 주소로 간다.
// 브라우저가 하는 일을 자바스크립트로 쓰면
const values = new FormData(form); // ① name 있는 입력 칸의 값을 모은다
const query = new URLSearchParams(values).toString(); // ② 'q=%ED%96%84%EB%A6%BF&sort=newest'
location.href = `${form.action}?${query}`; // ③ action 주소로 이동한다

제출은 입력 칸에서 Enter를 누르거나, 폼 안의 type="submit" 버튼을 누를 때 일어난다. 글자를 입력하는 동안에는 일어나지 않는다.

문제: 지금 쿼리가 사라진다

위 규칙의 ②를 다시 보자. 쿼리 문자열은 폼에 있는 값만으로 새로 만든다. 지금 주소의 쿼리를 이어 붙이지 않는다. 그래서 폼에 검색 칸 하나만 있으면 이런 일이 생긴다.

순서사용자가 한 일주소
①정렬을 "최근 등록 순"으로 바꾼다/?sort=newest
②검색 칸에 "햄릿"을 쓰고 Enter/?q=햄릿 ← sort가 사라졌다

사용자는 정렬을 바꾼 적이 없는데 목록이 기본 정렬로 돌아간다. 검색 결과 화면에서 필터(장르, 날짜)를 고른 뒤 검색해도 필터가 모두 풀린다.

action에 쿼리를 붙이면 안 되나

가장 먼저 떠오르는 방법은 action 주소에 지금 쿼리를 붙여 두는 것이다. 하지만 GET 폼에서는 통하지 않는다.

<form action="/?sort=newest">
  <input name="q" />
</form>
<!-- "정원"을 쓰고 제출하면 → /?q=정원  (sort=newest는 버려진다) -->

GET 폼은 action 주소의 쿼리 부분을 폼 값으로 만든 쿼리로 바꿔 끼운다. 덧붙이지 않는다. HTML 표준이 정한 동작이고, Chrome에서 시험해 봐도 sort가 사라진다. 그래서 지키고 싶은 값은 action이 아니라 폼 안의 입력 칸으로 넣어야 한다.

해결: 숨은 입력 칸

<input type="hidden">은 화면에 보이지 않고, 사용자가 고칠 수도 없는 입력 칸이다. 하지만 name이 있으면 다른 입력 칸과 똑같이 제출된다. "사용자가 쓰지는 않지만 함께 보내야 하는 값"을 폼에 싣는 표준 수단이다. 

<!-- 지금 주소: /?sort=newest -->
<form action="/">
  <input name="q" />
  <input type="hidden" name="sort" value="newest" />
</form>
지금 주소"햄릿" 검색 후 주소정렬
숨은 칸 없음/?sort=newest/?q=햄릿풀린다
숨은 칸 있음/?sort=newest/?q=햄릿&sort=newest유지된다

비유하면, 우편으로 신청서를 보낼 때 사용자가 쓴 칸만 보내지는데, 담당자가 "이 신청서는 최근 등록 순으로 처리"라는 메모를 봉투 안에 미리 넣어 두는 것과 같다. 사용자 눈에는 메모가 보이지 않지만 신청서와 함께 도착한다.

어떤 값을 숨은 칸에 넣나

지금 주소의 쿼리를 하나씩 보며 "새 검색에서도 이어져야 하나"를 정한다. 공연 목록(/?q=정원&sort=newest&page=3)이면 이렇다.

쿼리숨은 칸이유
sort넣는다사용자가 고른 정렬은 새 검색에서도 이어져야 한다
page넣지 않는다새 검색 결과는 1페이지부터 봐야 한다. 3페이지를 이어 가면 결과가 적을 때 빈 페이지가 된다
q넣지 않는다사용자가 검색 칸에 쓴 값이 새 q다. 숨은 칸에도 넣으면 q가 두 번 실려 간다

기본값은 넣지 않는 것이 좋다. 정렬이 기본값(공연 시작일 순)이면 주소에서 sort를 빼는 규칙인데, 숨은 칸에 sort=start_date를 넣으면 검색할 때마다 주소에 기본값이 붙는다.

React와 Next에서 쓰기

숨은 칸 목록은 지금 쿼리에서 계산한다. 주소를 만드는 함수와 같은 규칙에서 뽑으면, 나중에 쿼리(예: 장르)가 늘어도 숨은 칸에 자동으로 들어간다. 

import Form from 'next/form';

// 지금 쿼리에서 q와 page를 뺀 나머지(기본값 제외)를 [이름, 값] 목록으로 만든다.
function getHiddenFields(query: ShowListQuery): [string, string][] {
  return [...getShowListSearchParams({ ...query, q: null, page: 1 })];
}

export function SearchForm({ query }: { query: ShowListQuery }) {
  return (
    <Form action="/" role="search">
      <input name="q" defaultValue={query.q ?? ''} />
      {getHiddenFields(query).map(([name, value]) => (
        <input key={`${name}=${value}`} type="hidden" name={name} value={value} />
      ))}
    </Form>
  );
}
  • next/form: action이 문자열이면 위 GET 폼 규칙대로 쿼리 문자열을 만들되, 페이지 전체를 새로 불러오지 않고 링크처럼 화면을 옮긴다. JS가 실행되기 전에는 보통 HTML 폼으로 동작한다. 숨은 칸 규칙도 그대로 적용된다.
  • 숨은 칸의 value: 숨은 칸은 사용자가 고칠 수 없으니 value를 그대로 줘도 된다(onChange가 필요 없다). 정렬이 바뀌어 다시 그리면 값도 따라 바뀐다.

알아 둘 규칙

Chrome에서 시험 페이지로 확인한 GET 폼의 규칙이다. 숨은 칸을 쓸 때 헷갈리기 쉬운 것들이다.

규칙예결과
action의 쿼리는 버려진다action="/?sort=newest"/?q=정원
빈 칸도 보내진다검색 칸을 비우고 제출/?q=&sort=newest. 받는 쪽이 빈 q를 "검색 안 함"으로 처리해야 한다
name이 없으면 보내지 않는다<input value="x" />쿼리에 없다
disabled면 보내지 않는다<input name="sort" disabled />쿼리에 없다. 보내기 싫은 숨은 칸은 아예 그리지 않는다
누른 버튼의 name과 value도 보낸다<button name="sort" value="newest">/?q=햄릿&sort=newest

숨은 칸은 "화면에 안 보일" 뿐 비밀이 아니다. 개발자 도구에서 보이고, 제출하면 주소에 그대로 나온다. 사용자가 고쳐서 보낼 수도 있으므로, 받는 쪽은 숨은 칸의 값도 다른 쿼리처럼 검사해야 한다(이 저장소는 normalizeShowListQuery가 모르는 정렬값을 버린다).

장점과 약점

장점

  • HTML 표준만으로 동작한다. 브라우저가 주소를 만들므로 JS가 아직 받아지지 않았거나 꺼져 있어도, 정렬을 지킨 채 검색할 수 있다.
  • 오래되고 흔한 방법이다. 검색 결과 화면에서 정렬이나 필터를 유지한 채 다시 검색하는 폼은 오래전부터 이렇게 만들어 왔다.
  • 값이 어긋나지 않게 만들 수 있다. 숨은 칸을 주소 규칙에서 뽑으면 따로 관리할 값이 없다.

약점

  • 동작이 코드에 드러나지 않는다. "제출하면 쿼리가 통째로 바뀐다"를 모르면, 코드만 보고는 숨은 칸이 왜 있는지 알 수 없다. 읽는 사람이 HTML 폼 규칙을 알아야 한다.
  • 같은 일을 두 방식으로 하게 된다. 정렬 Select처럼 고르는 즉시 이동하는 컨트롤은 함수로 주소를 만들어 이동한다. 검색만 폼에 값을 실어 보내면, "지금 쿼리에서 하나만 바꿔 이동한다"는 같은 일을 두 방식으로 하게 된다.
  • 화면에 없는 값이 DOM에 있다. 상태의 원본은 주소인데 그 복사본이 폼 안에도 생긴다.

대안: 함수로 주소를 만들어 이동하기

JS로 제출을 가로채, 지금 쿼리와 검색어로 새 주소를 함수로 만들고 router.push로 이동하는 방법이다. 숨은 칸이 필요 없다. 

<form
  role="search"
  onSubmit={(event) => {
    event.preventDefault(); // 브라우저의 기본 제출(GET 폼 이동)을 막는다
    const q = String(new FormData(event.currentTarget).get('q') ?? '');
    router.push(getSearchSubmitHref({ query, value: q })); // 정렬은 두고 q를 바꾸고 page는 뺀다
  }}
>
  <input name="q" defaultValue={query.q ?? ''} />
</form>
숨은 입력 칸 (GET 폼)함수 + router.push
지금 쿼리를 지키는 곳폼 안의 숨은 칸주소를 만드는 함수. 단위 테스트로 확인
코드만 보고 이해하기HTML 폼 규칙을 알아야 한다함수 이름과 인자로 의도가 드러난다
JS 없이 검색된다. 정렬도 지킨다JS가 실행되기 전에는 우리 함수가 돌지 않는다
다른 컨트롤과의 일관성정렬 Select와 방식이 다르다정렬 Select와 같다

어느 쪽이 옳다기보다 무엇을 더 중요하게 보느냐의 문제다. JS 없이 동작하는 것이 중요하면 숨은 칸이, 코드를 읽기 쉽고 컨트롤마다 방식이 같은 것이 중요하면 함수 방식이 맞다.

스스로 확인하기

1. 지금 주소가 /?sort=newest&page=3일 때, 아래 폼으로 "햄릿"을 검색하면 새 주소는 무엇인가?

action에 쿼리를 붙이면 안 되나.

<form action="/?sort=newest">
  <input name="q" />
</form>
답 보기

/?q=햄릿이다. GET 폼은 action의 쿼리를 폼 값으로 만든 쿼리로 바꿔 끼우므로 sort=newest도 사라진다.

2. 숨은 칸에 page도 넣으면 어떤 문제가 생기는가?

어떤 값을 숨은 칸에 넣나. 지금 주소는 /?sort=newest&page=3이다.

   <input type="hidden" name="sort" value="newest" />
+  <input type="hidden" name="page" value="3" />
답 보기

새 검색 결과의 3페이지로 간다. 결과가 한 페이지뿐이면 빈 페이지가 되고(이 저장소는 마지막 페이지로 리다이렉트한다), 사용자는 결과의 처음 부분을 놓친다. 새 검색은 1페이지부터 보여야 하므로 page는 넣지 않는다.

3. 숨은 칸의 정렬값을 사용자가 개발자 도구로 sort=hack으로 바꿔 제출하면 어떻게 되는가?

주소가 /?q=…&sort=hack이 된다. 숨은 칸은 비밀도 잠금도 아니기 때문이다. 받는 쪽인 normalizeShowListQuery가 모르는 정렬값을 버리고 기본 정렬 주소로 리다이렉트하므로 문제는 생기지 않는다. 숨은 칸의 값도 사용자 입력처럼 검사해야 하는 이유다.
