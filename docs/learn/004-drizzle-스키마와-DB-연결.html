Drizzle 스키마와 DB 연결: shows.ts와 DatabaseModule

  • drizzle
  • nestjs

Drizzle을 처음 쓰는 사람 기준으로, 이 저장소의 두 파일을 읽는다. 테이블을 정의하는 apps/api/src/db/schema/shows.ts와, 그 테이블을 쿼리할 연결을 앱에 등록하는 apps/api/src/db/database.module.ts다. 기준 버전은 drizzle-orm 0.45.4, drizzle-kit 0.31.11, pg 8.23, NestJS 12.4다. 프로바이더, useFactory, 토큰은 003 문서에서 다뤘다.

한눈에 보기

Drizzle은 TypeScript용 ORM이다. SQL을 감추기보다 SQL 모양을 거의 그대로 TypeScript로 옮겨 놓았다. 그래서 SQL을 알면 코드를 읽기 쉽다. 테이블 정의 하나에서 마이그레이션 SQL과 쿼리 타입이 함께 나온다.

개발 중: 스키마 → 마이그레이션 (drizzle-kit)
  1. shows.ts 수정
  2. pnpm db:generate
  3. drizzle/*.sql 생성
  4. pnpm db:migrate로 DB에 적용
앱 실행 중: 스키마 → 쿼리 (drizzle-orm)
  1. DatabaseModule이 연결 등록
  2. ShowsService가 db 주입받음
  3. db.select().from(shows)
  4. 타입이 붙은 결과
파일 하는 일 누가 실행하나
db/schema/shows.ts shows 테이블의 모양을 정의 drizzle-kit(개발 도구)과 앱 코드 둘 다
db/database.module.ts 앱 전체가 함께 쓸 DB 연결을 Nest에 등록 Nest(앱 부팅과 종료 때)

shows.ts 한 줄씩

SQL의 CREATE TABLE을 직접 쓰는 대신 TypeScript 객체로 테이블을 표현한다.

import { integer, pgTable, text } from 'drizzle-orm/pg-core';

export const shows = pgTable('shows', {
  id: integer().primaryKey().generatedAlwaysAsIdentity(),
  title: text().notNull(),
});

from 'drizzle-orm/pg-core'

PostgreSQL용 도구를 가져온다. MySQL은 mysql-core, SQLite는 sqlite-core를 쓴다. DB마다 지원하는 타입이 달라서 나뉘어 있다.

pgTable('shows', { ... })

  • 첫 인자 'shows'는 DB의 실제 테이블 이름이다.
  • 두 번째 인자의 각 키가 컬럼이 된다.
  • 컬럼 이름을 따로 주지 않으면 키 이름(id, title)이 그대로 DB 컬럼 이름이 된다. integer('show_id')처럼 쓰면 DB 컬럼 이름만 따로 정할 수 있다.

id: integer().primaryKey().generatedAlwaysAsIdentity()

메서드를 이어 붙여 컬럼 성질을 하나씩 더한다.

  1. integer() 정수 타입이다.
  2. .primaryKey() 기본 키다. 값이 겹칠 수 없고 비어 있을 수 없다.
  3. .generatedAlwaysAsIdentity() 번호를 DB가 1, 2, 3… 자동으로 매긴다. 예전 serial의 표준 SQL 버전이다.

ALWAYS는 "항상 DB가 정한다"는 뜻이다. insert에서 id를 직접 넣으면 DB가 거부한다. 그래서 시드(src/db/seed.ts)는 "id 1, 2로 고정해 덮어쓰기" 대신 "비우고 번호를 1부터 다시 시작(TRUNCATE ... RESTART IDENTITY)"을 쓴다. 직접 넣는 것을 허용하려면 generatedByDefaultAsIdentity()를 쓴다.

title: text().notNull()

길이 제한 없는 문자열이고, 비울 수 없다(NOT NULL).

이 코드가 만드는 SQL

pnpm db:generate를 실행하면 drizzle-kit이 이 파일을 읽어 apps/api/drizzle/0000_create_shows.sql을 만든다. 

CREATE TABLE "shows" (
  "id" integer PRIMARY KEY GENERATED ALWAYS AS IDENTITY (...),
  "title" text NOT NULL
);

TypeScript 한 줄이 SQL 한 줄과 거의 1:1로 대응한다.

스키마가 쓰이는 두 곳

1. 마이그레이션을 만들 때 (drizzle-kit, 개발 도구)

  1. 스키마 수정 예를 들어 venue: text()를 추가한다.
  2. pnpm db:generate 지난번 상태(drizzle/meta/*.json)와 지금 스키마를 비교한다.
  3. 차이만큼 새 SQL 파일 생성 ALTER TABLE "shows" ADD COLUMN "venue" text;가 담긴 0001_...sql이 생긴다.

generate는 파일을 만들기만 하고 DB는 건드리지 않는다. DB에 적용하는 일은 pnpm db:migrate가 따로 한다. 생성과 적용이 나뉘어 있으므로, 적용하기 전에 PR에서 SQL을 읽고 확인할 수 있다.

2. 앱에서 쿼리할 때 (drizzle-orm, 런타임)

shows.service.ts는 같은 shows 객체를 쿼리 재료로 쓴다.

this.db
  .select({ id: shows.id, title: shows.title })
  .from(shows)
  .orderBy(asc(shows.id));
// → SELECT "id", "title" FROM "shows" ORDER BY "id" ASC

이때 TypeScript가 타입을 알아서 붙여 준다.

상황 결과
위 쿼리의 결과 { id: number; title: string }[]로 자동 추론
shows.titel처럼 오타 컴파일 오류
insert에서 title을 빠뜨림 컴파일 오류. notNull이므로
insert에 id를 넣음 컴파일 오류. ALWAYS identity라 insert 타입에서 빠짐

테이블 정의 하나에서 마이그레이션과 쿼리 타입이 같이 나오므로, 스키마와 코드가 어긋나기 어렵다.

스키마 파일 규칙

이 저장소의 CODING_STANDARDS.md와 drizzle.config.ts가 정한 규칙이다.

  • 스키마 파일은 다른 스키마 파일과 Drizzle만 import한다. drizzle-kit은 Nest 앱 밖에서 이 파일을 실제로 실행한다. 여기서 서비스나 설정 코드를 import하면 그 코드도 함께 실행된다.
  • 폴더를 평평하게 유지한다. drizzle.config.ts의 schema: './src/db/schema'는 폴더 한 단계만 읽는다.
  • 테이블 이름은 복수형이다. 앞으로 생길 order, user는 단수형이 PostgreSQL 예약어다.

파일을 schema/shows/table.ts처럼 하위 폴더로 옮기면 drizzle-kit 눈에는 shows 테이블이 사라진 것으로 보인다. 그래서 경고 없이 DROP TABLE "shows"가 담긴 마이그레이션이 생성된다. 생성된 SQL을 PR에서 꼭 읽어야 하는 이유다. 근거는 docs/research/drizzle-schema-organization.md에 있다.

pg와 Drizzle, 두 층

여기부터는 database.module.ts를 본다. 이 파일은 앱 전체가 함께 쓸 DB 연결 하나를 만들어 Nest에 등록한다. 서비스는 연결을 직접 만들지 않고 "DB를 달라"고 요청만 한다. 

export const DATABASE = Symbol('DATABASE');
// drizzle()이 안에서 만든 pg Pool은 $client로 꺼낼 수 있다.
export type Database = NodePgDatabase & { $client: Pool };

@Global()
@Module({
  providers: [
    {
      provide: DATABASE,
      useFactory: (): Database => drizzle(readEnv().databaseUrl),
    },
  ],
  exports: [DATABASE],
})
export class DatabaseModule implements OnApplicationShutdown {
  constructor(@Inject(DATABASE) private readonly db: Database) {}

  async onApplicationShutdown() {
    await this.db.$client.end();
  }
}

먼저 알아 둘 것이 있다. Drizzle은 PostgreSQL과 직접 통신하지 않는다. 실제 통신은 pg라는 드라이버가 하고, Drizzle은 그 위에 얹힌다.

층 하는 일
ShowsService db.select()...로 쿼리를 쓴다
Drizzle (db) TypeScript 쿼리를 SQL 문자열로 바꾸고, 결과에 타입을 붙인다
pg Pool (db.$client) SQL을 실제로 PostgreSQL에 보내고 결과를 받아 온다
PostgreSQL 실행한다

Pool이 뭔가

DB 연결을 맺는 일은 비싸다(네트워크 왕복과 인증). 요청마다 맺고 끊으면 느리므로, 연결 몇 개를 열어 두고 돌려 쓰는 묶음을 둔다. 이것이 Pool이다. 서비스마다 Pool을 만들면 안 되는 이유는 003의 문제 3에 있다.

drizzle(url): Pool까지 한 번에 만든다

drizzle()에 주소 문자열을 주면, Drizzle이 안에서 new Pool({ connectionString: url })을 대신 호출하고 그 Pool 위에 db 객체를 만들어 돌려준다. 우리 코드에는 new Pool이 없다.

  • 안에서 만든 Pool은 db.$client로 꺼낼 수 있다. 앱을 끌 때 이걸로 Pool을 닫는다.
  • Database 타입은 NodePgDatabase(쿼리 기능)에 $client: Pool을 붙인 것이다. 이렇게 적어야 db.$client.end()가 타입 검사를 통과한다.
선택 읽기: drizzle 안에서 Pool을 만드는 코드

node_modules/drizzle-orm/node-postgres/driver.js(0.45.4)의 해당 부분을 줄인 것이다. 

function drizzle(...params) {
  if (typeof params[0] === "string") {     // 첫 인자가 주소 문자열이면
    const instance = new pg.Pool({         // 여기서 Pool을 만든다
      connectionString: params[0]
    });
    return construct(instance, params[1]);
  }
  // ...
}

function construct(client, config = {}) {
  // ...
  db.$client = client;                     // 만든 Pool을 db.$client에 붙여 둔다
  return db;
}

Pool 옵션(최대 연결 수 등)이 필요해지면 drizzle({ connection: { connectionString, max } })처럼 객체로 넘긴다. 그러면 new pg.Pool(connection)으로 그대로 전달된다.

프로바이더 등록

프로바이더는 "이 이름표로 요청하면 이 값을 준다"는 등록이다.

{
  provide: DATABASE,
  useFactory: (): Database => drizzle(readEnv().databaseUrl),
}

왜 useFactory로 만드는 함수를 직접 주나

Nest가 객체를 스스로 만드는 방법은 하나뿐이다. 클래스에 new를 호출하면서, 생성자 인자 자리에 등록된 다른 프로바이더를 넣는 것이다.

대상 만드는 코드 Nest가 혼자 만들 수 있나
ShowsService new ShowsService(db) 있다 인자 db가 등록된 프로바이더다. providers: [ShowsService]면 된다.
Drizzle db drizzle(url) 없다 클래스가 아니라 함수 호출이고, 인자도 주소 문자열이다. Nest는 new만 할 줄 알고, 문자열은 등록된 프로바이더가 아니다.

그래서 "이렇게 만들어라"는 함수를 useFactory로 직접 준다. Nest는 이 함수를 한 번 실행해서 나온 값을 DATABASE라는 이름표로 등록한다. 003의 2단계에서 new Database(url)을 등록한 것과 같은 상황이다.

이름표: Symbol('DATABASE')

클래스로 등록하는 ShowsService는 클래스 자체가 이름표다. db는 함수가 돌려준 값이라 이름표를 따로 만들어야 한다. Symbol은 세상에 하나뿐인 값이라 다른 이름표와 겹칠 수 없다. 문자열 'DATABASE'도 동작하지만 다른 라이브러리와 겹칠 위험이 있다. 받는 쪽의 @Inject(DATABASE)만 봐도 "앱의 DB를 받는다"가 읽힌다는 장점도 있다.

부팅 중에 환경 변수를 검사한다

  • 팩토리 안의 readEnv()가 DATABASE_URL을 확인하고, 없으면 에러를 던진다.
  • Nest는 부팅 중(NestFactory.create)에 팩토리를 실행한다. 그래서 "필수 환경 변수가 없으면 부팅이 바로 실패한다"가 성립한다.

main.ts는 NestFactory.create(AppModule, { abortOnError: false })로 부른다. 기본값 true이면 부팅 오류에서 Nest가 process.abort()를 호출해 프로세스를 강제로 멈춘다. false이면 오류를 던지므로 필수 환경 변수가 없습니다: DATABASE_URL 메시지와 함께 exit 1로 끝난다.

부팅이 성공했다고 DB에 붙는 것은 아니다

readEnv()는 DATABASE_URL 값이 있는지만 본다. 그 주소로 DB에 접속되는지는 보지 않는다. drizzle(url)이 안에서 만드는 Pool도 주소를 기억만 하고 접속하지 않는다. Pool은 첫 쿼리가 올 때 연결을 연다. 그래서 부팅 과정에는 DB와 통신하는 순간이 한 번도 없다.

상황 언제 실패하나
DATABASE_URL이 없다 부팅 exit 1
값은 있는데 DB가 꺼져 있거나, 주소나 비밀번호가 틀렸다 첫 요청 부팅은 성공하고, GET /shows에서 ECONNREFUSED 등으로 500. 아무것도 떠 있지 않은 포트를 주소로 줘서 실행해 확인했다.

"부팅 성공"은 "DB에 붙을 수 있다"를 뜻하지 않는다. DATABASE_URL의 비밀번호에 오타가 있어도 앱은 멀쩡히 뜨고, 첫 요청이 들어와서야 500으로 드러난다. 앱이 이상하면 부팅 로그만 믿지 말고 DB 접속 정보부터 확인한다.

선택 읽기: 부팅 때 DB 접속까지 확인하려면

팩토리에서 쿼리를 한 번 실행하면 된다. 접속이 안 되면 부팅이 실패한다.

useFactory: async (): Promise<Database> => {
  const db = drizzle(readEnv().databaseUrl);
  await db.execute('select 1'); // 접속 실패 시 여기서 throw → 부팅 실패
  return db;
},

대가가 있다. 배포 환경에서는 DB가 앱보다 늦게 뜨는 일이 흔한데, 그때마다 앱이 부팅에 실패한다. 그래서 운영에서는 부팅을 막기보다, DB 접속 여부를 알려 주는 헬스 체크 엔드포인트를 따로 두는 방식을 많이 쓴다.

지금 코드는 이 확인을 하지 않는다. 어느 방식을 쓸지는 배포 단계에서 정한다.

exports와 @Global()

database.module.ts에서 이 절이 다루는 두 줄이다.

@Global() // ← 모든 모듈에서 쓸 수 있게 한다
@Module({
  providers: [
    { provide: DATABASE, useFactory: (): Database => drizzle(readEnv().databaseUrl) },
  ],
  exports: [DATABASE], // ← 모듈 밖에 공개한다
})
export class DatabaseModule implements OnApplicationShutdown { /* ... */ }
설정 효과
exports: [DATABASE] 다른 모듈이 DATABASE를 받아 쓸 수 있게 공개한다.
@Global() 원래는 다른 모듈의 프로바이더를 쓰려면 그 모듈을 imports에 적어야 한다. Global이면 AppModule에 한 번만 등록해도 모든 모듈에서 쓸 수 있다. 거의 모든 모듈이 쓰는 DB 같은 것에 흔히 쓴다.

그래서 ShowsModule은 imports 없이 이렇게 받아 쓴다.

@Injectable()
export class ShowsService {
  constructor(@Inject(DATABASE) private readonly db: Database) {}
}

클래스가 아니라 이름표로 등록했으므로, 받을 때도 @Inject(DATABASE)로 이름표를 적어 줘야 한다. 생성자 타입 Database만으로는 Symbol 이름표를 찾을 수 없기 때문이다.

꼭 Symbol과 @Inject여야 하나

아니다. 다만 drizzle(url)이 돌려준 값을 넣으려면 어떤 형태로든 이름표가 필요하고, 그 이름표가 클래스가 아니면 받는 쪽에서 @Inject로 적어야 한다.

@Inject 없이 받으면 Nest는 생성자 인자의 타입 기록(design:paramtypes)을 이름표로 쓴다. 이 기록에는 런타임에 남는 클래스만 제대로 남는다. Database는 NodePgDatabase & { $client: Pool }이라는 교차 타입이라 Object로 기록되고(실행해 확인했다), Nest는 무엇을 넣을지 모른다.

선택 읽기: @Inject 없이 받는 방법들
방법 받는 쪽 단점
이 저장소 Symbol + @Inject @Inject(DATABASE) db: Database 받을 때마다 @Inject를 적어야 한다
Drizzle 클래스를 이름표로 db: NodePgDatabase 타입을 NodePgDatabase 그대로 적어야 해서 $client 타입이 빠진다. Drizzle 내부 클래스 이름에 코드가 묶인다
추상 클래스 + 인터페이스 병합 db: Database 아래처럼 같은 이름을 클래스와 인터페이스로 겹쳐 선언한다. 동작은 하지만(실행해 확인했다) 처음 보는 사람에게는 수수께끼 같은 코드다
감싸는 서비스 databaseService: DatabaseService 쿼리마다 this.databaseService.db.select()...처럼 한 단계를 더 거친다

세 번째 방법의 모양이다. 클래스는 런타임 이름표가 되고, 인터페이스는 타입을 채운다.

export abstract class Database {}
export interface Database extends NodePgDatabase {
  $client: Pool;
}

// 등록: { provide: Database, useFactory: (): Database => drizzle(url) }
// 받기: constructor(private readonly db: Database) {}

NestJS 공식 @nestjs/drizzle도 받을 때 @InjectDrizzle() 데코레이터를 쓴다. 그 안의 이름표는 getDrizzleToken()이 돌려주는 토큰이다. "토큰으로 등록하고, 받을 때 데코레이터로 토큰을 적는다"는 지금 코드와 같은 구조다.

그래서 Symbol + @Inject를 쓴다. Nest가 클래스가 아닌 값을 주입하는 표준 방법이고, 공식 패키지와 구조도 같다. 받는 곳이 늘어 @Inject(DATABASE)가 길게 느껴지면 export const InjectDatabase = () => Inject(DATABASE);로 줄여 @InjectDatabase()로 쓸 수 있다. 지금은 쓰는 곳이 ShowsService 하나라 필요 없다.

앱을 끌 때

export class DatabaseModule implements OnApplicationShutdown {
  constructor(@Inject(DATABASE) private readonly db: Database) {}

  async onApplicationShutdown() {
    await this.db.$client.end();
  }
}
  • 모듈 클래스도 프로바이더를 주입받을 수 있다. 여기서는 자기가 등록한 db를 받아 둔다.
  • onApplicationShutdown은 app.close()가 호출되면 Nest가 불러 주는 생명주기 훅이다.
  • db.$client.end()는 Drizzle이 안에서 만든 Pool의 연결을 모두 닫는다.

이 훅이 없으면 열린 연결이 Node 프로세스를 붙잡는다. 그러면 테스트가 끝나도 프로세스가 종료되지 않거나, 테스트마다 연결이 쌓인다. 통합 테스트는 테스트마다 앱을 만들고 닫는데, 그래도 깔끔하게 끝나는 것은 이 훅 덕분이다.

onModuleDestroy가 아니라 onApplicationShutdown인 이유

003의 5단계는 onModuleDestroy로 풀을 닫았다. 둘 다 app.close()에서 불리지만 시점이 다르다. NestJS 12.4 소스의 순서는 이렇다.

  1. onModuleDestroy 모든 프로바이더의 정리 훅
  2. beforeApplicationShutdown 종료 직전 훅
  3. HTTP 서버 닫기 더 이상 요청을 받지 않는다
  4. onApplicationShutdown 마지막 훅. 여기서 풀을 닫는다

풀은 다른 코드가 모두 정리되고 HTTP 서버까지 닫힌 뒤에 닫는 것이 안전하다. 다른 모듈의 onModuleDestroy가 마지막으로 DB에 무언가를 쓰더라도 풀이 아직 열려 있기 때문이다. NestJS 공식 샘플도 같은 훅에서 Pool을 닫는다.

이 훅은 app.close()를 부를 때만 실행된다. Ctrl+C 같은 종료 신호에도 실행하려면 app.enableShutdownHooks()를 호출해야 한다. 지금 main.ts에는 없다. 프로세스가 종료되면 OS가 연결을 끊으므로 로컬 개발에는 문제가 없지만, 배포 단계에서 다시 볼 부분이다.

전체 흐름

부팅: NestFactory.create(AppModule)
  1. DATABASE 팩토리 → readEnv()
  2. DATABASE_URL 없으면 실패, exit 1
  3. drizzle(url) → 안에서 Pool 생성
  4. ShowsService에 db 주입
요청과 종료
  1. GET /shows → db.select()...
  2. Pool이 연결을 빌려 SQL 실행 후 반납
  3. app.close() → HTTP 서버 닫기
  4. onApplicationShutdown → db.$client.end()

스스로 확인하기

질문에 먼저 답해 본 뒤, 눌러서 답을 확인한다.

1. pnpm db:generate를 실행하면 DB의 테이블이 바뀌는가?

아니다. generate는 스키마와 지난번 스냅샷을 비교해 SQL 파일만 만든다. DB에 적용하는 것은 pnpm db:migrate다. 둘이 나뉘어 있어서 적용 전에 SQL을 리뷰할 수 있다.

2. shows 테이블에 { id: 10, title: '...' }로 insert하면 어떻게 되는가?

TypeScript에서는 id가 insert 타입에 없어 컴파일 오류가 난다. SQL로 직접 넣어도 GENERATED ALWAYS 컬럼이라 PostgreSQL이 거부한다.

3. PostgreSQL이 꺼진 상태에서 pnpm start를 하면 언제 실패하는가?

부팅은 성공한다. drizzle(url)이 만드는 Pool은 접속 정보만 기억하고 실제 연결은 첫 쿼리 때 열기 때문이다. GET /shows 요청에서 처음 실패한다. 반면 DATABASE_URL이 아예 없으면 부팅에서 실패한다.

4. ShowsService가 생성자에 @Inject(DATABASE) 없이 private readonly db: Database만 적으면 어떻게 되는가?

부팅 때 의존성을 해결하지 못했다는 오류가 난다(실행해 확인했다). Nest는 @Inject가 없으면 생성자 타입 기록을 이름표로 쓰는데, 프로바이더는 DATABASE라는 Symbol로 등록했으므로 타입으로는 찾을 수 없다. 토큰으로 등록한 프로바이더는 받을 때도 토큰을 적어야 한다.

5. 우리 코드에는 new Pool이 없는데, 앱을 끌 때 무엇을 어떻게 닫는가?

drizzle(url)이 안에서 만든 pg Pool을 닫는다. 그 Pool은 db.$client로 꺼낼 수 있고, onApplicationShutdown에서 db.$client.end()를 부른다. Database 타입에 $client: Pool을 붙여 둔 것은 이 호출이 타입 검사를 통과하게 하려는 것이다.
