05 세션 토큰: 만들기, 서명, 저장

로그인하면 서버는 무작위 토큰을 하나 만들어, 브라우저에는 서명을 붙여 쿠키로 주고 DB에는 해시만 저장한다. apps/api/src/auth/session-token.ts의 네 함수와 서명 키를 읽는 readAuthSecret을 따라가며, 같은 토큰이 어디에 어떤 모습으로 있는지, 서명과 해시가 각각 무엇을 막는지 정리한다.

한눈에 보기

세션 토큰은 "이 브라우저는 세션 몇 번의 주인이다"를 증명하는 무작위 문자열이다. 아무 뜻도 담지 않은 불투명한(opaque) 값이라, 토큰만 봐서는 누구의 세션인지 알 수 없다. 서버가 DB에서 찾아봐야 안다. JWT처럼 토큰 안에 사용자 정보를 담는 방식과의 차이는 01 문서의 세션과 JWT 절에 있다.

함수 입력 → 출력 쓰는 곳
createSessionToken 없음 → 무작위 32글자 로그인할 때 한 번
signSessionToken 토큰, 키 → 토큰.서명 쿠키를 내릴 때(발급, 연장)
readSignedSessionToken 쿠키 값, 키 → 토큰 또는 null 요청의 쿠키를 읽을 때마다
hashSessionToken 토큰 → SHA-256 hex 64글자 DB에 쓰거나 DB에서 찾을 때마다

이 네 함수는 DB도, 요청도, Nest도 모르는 순수 함수다. 언제 부르는지는 SessionManager가 정한다(06 문서).

원문, 쿠키 값, DB 값

토큰 하나가 세 군데에서 서로 다른 모습으로 존재한다(값은 예시).

브라우저 쿠키: 토큰.서명
  1. Xk3p…(32글자)…Q9aZ
  2. .
  3. 5/y8Fvgm…(44글자)…teC9U=
DB sessions.token_hash: SHA-256 hex
  1. 9f86d081…(64글자)…0f00a08
모습 있는 곳 모양 원문을 알 수 있나
원문 서버 메모리(요청을 처리하는 동안), 쿠키 값의 앞부분 영숫자 32글자 원문 그 자체
쿠키 값 브라우저 쿠키 openrun.session_token 원문.서명, 서명은 HMAC-SHA256 base64 44글자 있다. 앞부분이 원문이다
DB 값 sessions.token_hash SHA-256 hex 64글자 없다. 해시는 되돌릴 수 없다

원문을 아는 곳은 브라우저뿐이다. 서버는 원문을 받아서 계산에 쓰고 버린다. DB와 로그 어디에도 원문은 남지 않는다. 그래서 쿠키는 HttpOnly로 자바스크립트에서 숨기고(07 문서), DB에는 되돌릴 수 없는 해시만 둔다.

발급할 때와 읽을 때

로그인 요청에서 토큰이 만들어지고, 다음 요청에서 다시 읽히는 순서다.

  1. 브라우저
  2. API 서버
  3. DB
  1. 발급: POST /auth/sign-in이 비밀번호 확인을 통과한 뒤
  2. createSessionToken() 원문 32글자
  3. hashSessionToken(원문) SHA-256 hex
  4. INSERT sessions (token_hash, …)
  5. signSessionToken(원문, AUTH_SECRET) 원문.서명
  6. Set-Cookie: openrun.session_token=원문.서명
  7. 읽기: 다음 요청부터 매번
  8. Cookie: openrun.session_token=원문.서명
  9. readSignedSessionToken(쿠키 값, AUTH_SECRET) 서명이 틀리면 여기서 null, DB에 가지 않는다
  10. hashSessionToken(원문)
  11. SELECT … WHERE token_hash = ?
  12. 세션 행

읽을 때 서버는 쿠키에서 원문을 꺼내 다시 해시해서 DB에서 찾는다. 같은 입력에 늘 같은 해시가 나오므로 DB 조회는 저장할 때와 같은 한 번이다. 원문을 저장하는 방식과 비교해 늘어나는 비용은 SHA-256 계산 한 번(수 마이크로초)뿐이다.

createSessionToken: 추측할 수 없는 32글자

import {
  createHash,
  createHmac,
  randomInt,
  timingSafeEqual,
} from 'node:crypto';

const TOKEN_ALPHABET =
  'ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789';
// 영숫자 62종에서 32자를 뽑아 약 190비트다(Better Auth와 같음).
const TOKEN_LENGTH = 32;

/** 세션 토큰을 새로 만든다. randomInt는 모듈로 편향 없이 고르게 뽑는다. */
export function createSessionToken(): string {
  return Array.from(
    { length: TOKEN_LENGTH },
    () => TOKEN_ALPHABET[randomInt(TOKEN_ALPHABET.length)],
  ).join('');
}

62글자짜리 알파벳(대문자 26 + 소문자 26 + 숫자 10)에서 한 글자씩 32번 뽑아 잇는다.

약 190비트: 얼마나 추측하기 어려운가

글자 하나가 62가지이므로 32글자 토큰은 6232가지다. 이것을 2의 거듭제곱으로 바꾼 것이 엔트로피(비트)다. 

log2(62) × 32 ≈ 5.954 × 32 ≈ 190.5비트
62^32 ≈ 2^190 ≈ 1.6 × 10^57가지

1초에 1조(1012)번 추측해도 전체의 절반을 훑는 데 1037년이 넘게 걸린다. 그래서 세션 토큰은 무작위로 맞혀 보는 공격을 걱정하지 않아도 된다. 난수와 엔트로피의 일반 개념은 01 문서의 난수 절에 있다.

randomInt를 쓰는 이유: 모듈로 편향

Math.random()은 예측할 수 있는 의사 난수라 보안 값에 쓰면 안 된다. 그렇다면 암호용 난수 바이트를 뽑아 나머지 연산으로 글자를 고르면 어떨까? 

// 이렇게 하면 안 된다
const byte = randomBytes(1)[0]; // 0~255, 256가지
const char = TOKEN_ALPHABET[byte % 62];

256은 62로 나누어떨어지지 않는다(256 = 62 × 4 + 8). 0~247은 각 글자에 정확히 4번씩 대응하지만, 남는 248~255의 8개는 0~7번 글자(A~H)에 한 번씩 더 붙는다.

글자 대응하는 바이트 수 뽑힐 확률
A~H (8글자) 5 5/256 ≈ 1.95%
나머지 54글자 4 4/256 ≈ 1.56%

이렇게 특정 값이 더 자주 나오는 것을 모듈로 편향이라고 한다. 편향이 있으면 실제 엔트로피가 계산보다 줄어든다. crypto.randomInt(62)는 범위에 맞지 않는 난수가 나오면 버리고 다시 뽑는 방식(거부 샘플링)으로 0~61을 정확히 같은 확률로 돌려준다. 그래서 글자마다 확률이 1/62로 같고, 190비트 계산이 그대로 성립한다.

Better Auth와 같다. 영숫자 62종 32글자, 약 190비트라는 토큰 모양을 그대로 가져왔다.

signSessionToken: 토큰.서명

/** 쿠키에 담을 `토큰.서명` 값을 만든다. 서명은 HMAC-SHA256의 base64다. */
export function signSessionToken({
  token,
  secret,
}: {
  token: string;
  secret: string;
}): string {
  return `${token}.${getSignature({ token, secret })}`;
}
function getSignature({
  token,
  secret,
}: {
  token: string;
  secret: string;
}): string {
  return createHmac('sha256', secret).update(token).digest('base64');
}

서명은 토큰을 AUTH_SECRET을 키로 HMAC-SHA256에 넣은 값이다. HMAC은 "키를 아는 사람만 만들 수 있는 지문"이다(01 문서의 HMAC). 32바이트 결과를 base64로 바꾸면 44글자가 된다(끝에 패딩 = 하나). 

원문:   Xk3p…Q9aZ                                   (32글자)
서명:   HMAC-SHA256(AUTH_SECRET, 원문) → base64      (44글자)
쿠키:   Xk3p…Q9aZ.5/y8FvgmrZZIXqzu/gOg2VRhbfq+H1I71ju3YhteC9U=

base64에는 +, /, =가 들어가는데, 이 글자들은 쿠키 값에 그대로 넣기 곤란하다. Express의 response.cookie는 값을 encodeURIComponent로 바꿔 내리므로 실제 Set-Cookie에는 %2B, %2F, %3D로 나간다. 요청에서 읽을 때 쓰는 cookie 패키지의 parseCookie가 다시 원래 글자로 되돌리므로, readSignedSessionToken은 인코딩을 신경 쓰지 않는다.

readSignedSessionToken: 서명 확인

요청의 쿠키 값에서 토큰을 꺼내되, 서명이 맞을 때만 꺼낸다.

/** 쿠키 값의 서명이 맞으면 토큰을, 아니면 null을 돌려준다. 서명이 틀린 쿠키는 DB를 조회하기 전에 거른다. */
export function readSignedSessionToken({
  value,
  secret,
}: {
  value: string;
  secret: string;
}): string | null {
  const separator = value.lastIndexOf('.');
  if (separator <= 0) {
    return null;
  }
  const token = value.slice(0, separator);
  const signature = Buffer.from(value.slice(separator + 1));
  const expected = Buffer.from(getSignature({ token, secret }));
  if (
    signature.length !== expected.length ||
    !timingSafeEqual(signature, expected)
  ) {
    return null;
  }
  return token;
}
  1. 마지막 .에서 나눈다 토큰 알파벳(영숫자)에도, base64 알파벳(영숫자와 + / =)에도 .은 없다. 그래서 정상 쿠키에는 .이 정확히 하나 있고 그 자리가 경계다. separator <= 0은 .이 없거나(-1) 맨 앞에 있어 토큰이 빈 문자열인 경우(0)다. 둘 다 서명을 볼 것도 없이 null이다.
  2. 앞부분으로 서명을 다시 계산한다 서버만 아는 AUTH_SECRET으로 앞부분(토큰)의 HMAC을 다시 만든다. 이것이 "이 토큰이라면 서명은 이래야 한다"는 정답이다.
  3. 길이를 먼저, 그다음 timingSafeEqual timingSafeEqual은 길이가 다른 버퍼를 받으면 예외를 던지므로, 쿠키 뒷부분을 잘라 보낸 요청이 500이 되지 않도록 길이부터 본다. 길이가 같으면 끝까지 같은 시간에 비교해, 서명을 한 바이트씩 맞혀 가는 타이밍 공격을 막는다(01 문서의 타이밍 공격). 04 문서의 비밀번호 비교와 같은 모양이다.
  4. 맞으면 토큰, 틀리면 null 틀린 서명을 오류로 다루지 않는다. 호출하는 SessionManager.readToken은 null을 "쿠키 없음"과 똑같이 다뤄, DB를 조회하지 않고 로그인하지 않은 요청으로 처리한다. 
// 서명이 맞는 쿠키의 토큰만 돌려준다. 서명이 틀리면 DB를 조회하지 않고 없는 것으로 다룬다.
private readToken(request: Request): string | null {
  const value = parseCookie(request.get('cookie') ?? '')[
    this.options.cookie.name
  ];
  if (!value) {
    return null;
  }
  return readSignedSessionToken({ value, secret: this.options.secret });
}
선택 읽기: 이 동작을 지키는 테스트

apps/api/test/auth.int.spec.ts의 '서명이 틀린 쿠키는 로그인하지 않은 것으로 다룬다'는 진짜 토큰에 엉뚱한 서명을 붙여 보낸다. 토큰은 DB에 있는 진짜 세션의 것이지만, 서명이 틀렸으므로 현재 세션 조회는 401이 아니라 200과 null(로그인하지 않음)이다.

hashSessionToken: DB에는 해시만

/** DB에 저장하고 조회할 때 쓰는 토큰의 SHA-256 해시(hex)다. DB가 유출돼도 원문을 알 수 없다. */
export function hashSessionToken(token: string): string {
  return createHash('sha256').update(token).digest('hex');
}

토큰을 SHA-256에 넣어 64글자 hex로 만든다. 세션을 만들 때 이 값을 sessions.token_hash에 넣고, 찾을 때도 쿠키의 토큰을 이 함수에 넣은 값으로 WHERE token_hash = ?를 건다(칸에는 UNIQUE 제약과 그에 따른 인덱스가 있다. 03 문서).

비밀번호는 scrypt인데 토큰은 왜 SHA-256인가

비밀번호 (04 문서) 세션 토큰
누가 만드나 사람. 짧고 흔한 값이 많다 서버. 190비트 무작위
DB를 훔친 공격자의 대입 흔한 비밀번호 목록으로 대입하면 맞힐 수 있다 → 일부러 느린 scrypt 2190가지라 아무리 빨라도 못 맞힌다 → 빠른 해시로 충분
솔트 있다. 같은 비밀번호도 저장 값이 다르다 없다. 토큰만으로 해시를 다시 만들어 조회해야 한다
얼마나 자주 계산하나 로그인할 때 한 번 요청마다. 60ms짜리 scrypt를 매번 돌릴 수 없다

솔트가 없다는 점이 핵심이다. 비밀번호는 이메일로 행을 먼저 찾은 뒤 그 행의 솔트로 비교하지만, 세션은 쿠키의 토큰 하나가 유일한 단서라 "토큰 → 해시"가 늘 같은 값이어야 DB에서 찾을 수 있다. 토큰 자체가 충분히 무작위라 솔트가 할 일도 없다.

AUTH_SECRET: 32자 미만이면 부팅하지 않는다

// HMAC 키로 쓰기에 짧으면 추측할 수 있으므로 길이를 확인한다. Better Auth도 32자보다 짧으면 경고한다.
const MIN_AUTH_SECRET_LENGTH = 32;

/** 세션 쿠키 서명(HMAC-SHA256)의 키. 32자 이상의 난수 문자열이다. */
export function readAuthSecret(
  source: NodeJS.ProcessEnv = process.env,
): string {
  const value = getOrThrow({ source, name: 'AUTH_SECRET' });
  if (value.length < MIN_AUTH_SECRET_LENGTH) {
    throw new Error(
      `AUTH_SECRET은 ${MIN_AUTH_SECRET_LENGTH}자 이상이어야 합니다.`,
    );
  }
  return value;
}

AUTH_SECRET은 서명의 키다. 사용자 세션 SessionManager를 만드는 팩토리가 부팅할 때 이 함수를 부르므로, 값이 없거나 32자보다 짧으면 API 서버가 아예 뜨지 않는다.

짧은 키가 위험한 이유

공격자도 회원가입하고 로그인하면 자기 쿠키 토큰.서명 한 쌍을 얻는다. 토큰과 서명을 둘 다 알므로, 서버에 요청하지 않고 자기 컴퓨터에서 키 후보를 하나씩 넣어 HMAC을 계산해 서명이 맞는 키를 찾을 수 있다(오프라인 대입). 키가 짧거나 사람이 지은 단어면 금방 찾는다. 키를 알아내면 서명 검사가 아무것도 걸러 내지 못한다. 32자 이상의 무작위 문자열이면 이런 대입이 불가능해진다.

운영 값은 apps/api/.env.example의 안내대로 openssl rand -base64 32로 만든다. 32바이트 난수를 base64로 바꾼 44글자다.

Better Auth와 다르다. Better Auth는 키가 32자보다 짧으면 경고만 하고 그대로 뜬다. 이 저장소는 부팅을 막는다. 경고는 운영 로그에 묻혀 지나치기 쉽고, 짧은 키로 운영되는 실수는 서버를 띄우는 순간에 잡는 편이 싸다(ADR 0009).

서명이 막는 것, 해시가 막는 것

서명과 해시는 서로 다른 위험을 맡는다. 상황별로 공격자가 무엇을 가졌을 때 남의 세션을 쓸 수 있는지 보자.

공격자가 가진 것 이 저장소 (서명 + 해시 저장) 막는 장치

  • 서명은 문 앞의 경비다. 키 없이 지어낸 쿠키를 DB까지 가기 전에 돌려보낸다. 아무 값이나 대량으로 보내는 요청이 DB 부하로 이어지지 않는다.
  • 해시 저장은 금고 안의 내용물을 쓸모없게 만드는 장치다. 금고(DB)가 털려도, 심지어 경비의 열쇠(키)까지 함께 털려도 세션을 쓸 수 없다.

마지막 줄처럼 쿠키 값 자체를 빼앗기면 어떤 장치도 막지 못한다. 쿠키는 그 자체로 "로그인된 상태"이기 때문이다. 그래서 쿠키가 새어 나가지 않게 하는 쿠키 속성과, 빼앗겨도 피해 기간을 줄이는 만료가 함께 필요하다.

Better Auth와 다른 점

Better Auth는 DB에 토큰 원문을 저장한다. 이 저장소는 SHA-256 해시를 저장한다(ADR 0009).

Better Auth는 여러 DB 어댑터와 보조 저장소에서 토큰을 키로 쓰고, 세션 목록 API가 클라이언트에 토큰을 돌려주며 그 토큰으로 세션을 골라 끊는 API(revoke-session)가 있다. 원문이 있어야 하는 요구가 있는 셈이다. 이 저장소에는 그런 요구가 없고, 해시로 저장해도 조회는 그대로 한 번이다. 그래서 위 표의 "DB 유출"과 "서버 전체 유출" 경우까지 막는 쪽을 택했다.

나중에 "다른 기기의 세션 목록 보기, 골라서 끊기"가 필요해지면 토큰 대신 세션 id로 고르면 된다. 세션 행에는 ip_address, user_agent가 함께 저장되어 있어 목록을 보여 줄 재료도 있다.
