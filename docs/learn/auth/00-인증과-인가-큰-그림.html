00 인증과 인가 큰 그림

이 폴더의 문서들이 어떤 순서로 이어지는지 먼저 본다. 인증과 인가가 무엇인지, 1단계 인증에서 무엇을 만들었고 무엇이 남았는지, 로그인한 요청 하나가 어떤 파일을 지나가는지를 한 장에 모았다. 세부 동작은 뒤 문서에서 하나씩 파고든다.

인증과 인가

둘 다 "인증"처럼 들려 헷갈리지만 묻는 질문이 다르다. 공연장 입구에 빗대면 이렇다.

인증 (authentication) 인가 (authorization)
묻는 것 너는 누구인가? 너는 이것을 해도 되는가?
공연장 비유 입구에서 신분증을 보고 손목 띠를 채워 준다 손목 띠 색을 보고 VIP석 구역에 들여보낼지 정한다
이 저장소에서 이메일과 비밀번호를 확인하고 세션 쿠키를 내린다. 이후 요청은 쿠키로 "몇 번 사용자"인지 안다 그 사용자가 이 API를, 이 데이터를 쓸 수 있는지 판단한다
실패 응답 401 Unauthorized (이름과 달리 "인증 안 됨"이다) 403 Forbidden, 또는 존재를 숨기려고 404

인가는 늘 인증 다음이다. 누구인지 모르면 무엇을 해도 되는지 판단할 수 없다. 그래서 이 폴더도 인증부터 다룬다.

지금 만든 인가: "로그인했는가"

지금 코드에 있는 인가는 하나뿐이다. /me에 붙은 로그인 가드(UserSessionGuard)가 "로그인한 사용자만 들어온다"를 검사한다. 가장 거친 인가지만, 인가 판단이 컨트롤러에 들어가기 전에 한곳에서 일어나는 구조가 여기서 시작된다. 이 가드는 08 문서에서 본다.

앞으로 더할 인가

  • 운영자 경로 분리: /admin/*은 운영자 세션만, 나머지는 사용자 세션만 읽는다(ADR 0010). 사용자에게 역할 컬럼을 두지 않으니, 사용자가 운영자 API를 부를 길이 구조적으로 없다.
  • IDOR 방어: 주문, 티켓처럼 주인이 있는 데이터는 "로그인했는가"로 부족하다. 로그인한 사람이 /orders/123의 주인인지도 확인해야 한다. 남의 id를 넣어 남의 데이터를 읽는 공격을 IDOR(Insecure Direct Object Reference)라 한다. 주문과 티켓이 생기는 예매(1.5)부터 다룬다.

요청 하나가 지나가는 길

인증의 핵심은 두 장면이다. 로그인할 때 서버가 "출입증"(세션 쿠키)을 만들어 주고, 그 뒤 요청마다 브라우저가 출입증을 내밀면 서버가 DB에서 확인한다. 자세한 단계는 02 문서에서 한 줄씩 따라간다.

  1. 브라우저
  2. API 서버
  3. DB
  1. 장면 1: 로그인
  2. POST /auth/sign-in 이메일, 비밀번호, 로그인 상태 유지
  3. 계정의 비밀번호 해시 읽기
  4. 비밀번호 확인 scrypt로 다시 계산해 비교
  5. 새 세션 토큰 만들기
  6. 세션 행 저장 토큰은 SHA-256 해시만
  7. 200 + Set-Cookie 토큰.HMAC서명
  8. 장면 2: 로그인이 필요한 요청
  9. GET /me Cookie 헤더에 세션 쿠키가 실려 간다

브라우저 자바스크립트는 세션 쿠키를 읽지도 만지지도 않는다. 쿠키는 HttpOnly라 스크립트에 보이지 않고, 브라우저가 요청마다 알아서 실어 보낸다. 프론트엔드가 할 일은 credentials를 켜서 쿠키가 실려 가게 하는 것뿐이다.

파일 지도

인증 코드는 두 폴더로 나뉜다. auth/는 "세션이란 무엇인가"를 정하는 공용 로직이고, 특정 테이블을 모른다. users/는 사용자에게 그 로직을 연결한다. 운영자 로그인(#82)이 붙으면 운영자 모듈이 users/와 같은 모양으로 auth/를 가져다 쓴다.

  • apps/api/src
    • auth/ 공용 사용자·운영자가 함께 쓴다
      • password.ts scrypt 해시와 확인 (04)
      • session-token.ts 토큰 만들기, HMAC 서명, SHA-256 해시 (05)
      • session-manager.ts 세션 발급·확인·연장·폐기, 쿠키 쓰기 (06, 07)
      • session-guard.ts 로그인 가드 팩토리와 @CurrentSession() (08)
      • authentication-required.ts 401 AUTHENTICATION_REQUIRED 오류 (09)
    • users/ 사용자 공용 로직을 사용자에 연결한다
      • user-session.ts 사용자 세션 정책(7일/1일), 쿠키 이름, UserSessionGuard
      • user-session-store.ts sessions 테이블을 읽고 쓰는 SessionStore 구현
      • users.service.ts 비밀번호 확인, 세션 응답에 담을 사용자 읽기
      • auth.controller.ts /auth/sign-in, /auth/sign-out, /auth/session
      • me.controller.ts GET /me. 로그인 가드가 붙는다
      • sign-in-body.ts 로그인 요청 본문의 zod 스키마
      • session.dto.ts 세션 응답 모양
      • invalid-credentials.ts 401 INVALID_CREDENTIALS 오류
    • db/schema/users.ts users, accounts, sessions 테이블 (03)
    • config/env.ts AUTH_SECRET, COOKIE_DOMAIN, Secure 쿠키 여부

두 폴더를 잇는 이음매는 SessionStore 인터페이스다. auth/의 SessionManager는 "세션 행을 만들고, 해시로 찾고, 만료를 늘리고, 지운다"는 네 동작만 요구하고, users/의 UserSessionStore가 그것을 sessions 테이블로 구현해 넘긴다.

주요 결정

세션 방식은 라이브러리 Better Auth의 설계를 본떠 직접 만들었다. 라이브러리가 감추는 동작을 배우기 위해서다. 결정과 이유는 ADR에 있다.

결정 이유 근거
JWT가 아니라 DB에 저장하는 세션 탈퇴하거나 로그아웃하면 즉시 끊어야 하고, API 서버가 하나라 JWT의 무상태 장점이 작다 ADR 0009
쿠키에 HMAC으로 서명한 불투명 토큰 위조한 쿠키는 DB를 조회하기 전에 거른다 ADR 0009
DB에는 토큰의 SHA-256 해시만 저장 DB가 유출돼도 그 값으로 로그인할 수 없다 ADR 0009 (Better Auth와 다름)
7일 만료, 마지막 연장 뒤 1일 지난 첫 요청에서 연장 쓰는 동안은 로그인이 이어지고, 요청마다 DB에 쓰지는 않는다 ADR 0009
CSRF 토큰 없이 Origin 검사, SameSite=Lax, JSON 본문 세 겹으로 막으면 토큰을 주고받는 복잡함 없이 충분하다 ADR 0009 (#72에서 구현)
운영자는 별도 테이블, 별도 세션과 쿠키 역할 검사를 빠뜨려 운영자 권한이 생길 길을 구조적으로 없앤다. 운영자에게만 30분 유휴 만료 ADR 0010

Better Auth와 다르게 정한 것이 몇 가지 있다. 토큰을 해시로 저장하기, 쿠키 캐시를 처음부터 켜지 않기, AUTH_SECRET이 32자보다 짧으면 부팅하지 않기, rememberMe를 필수 값으로 받기, 로그인 상태 유지 여부를 쿠키가 아니라 세션 행에 두기, 요청 속도 제한은 10단계로 미루기. 각 문서에서 해당 코드를 볼 때 다시 짚는다.

소셜 로그인이 붙으면

소셜 로그인은 "누구인가"를 확인하는 방법만 바뀐다. 비밀번호 대신 구글이나 카카오가 "이 사람은 우리 쪽 몇 번 계정이다"라고 알려 준다. 확인이 끝난 뒤 세션을 만들고 쿠키를 내리는 부분은 지금 코드를 그대로 쓴다.

이메일 로그인 (지금)
  1. 이메일·비밀번호 받기
  2. accounts(provider=credential)의 비밀번호 해시와 비교
  3. 사용자 id 얻음
  4. SessionManager.issue
  5. 세션 쿠키
소셜 로그인 (1.4b)
  1. 구글·카카오로 보냈다가 콜백으로 돌아옴
  2. 제공자에게 그 사람의 계정 id 받기
  3. accounts(provider=google, providerAccountId)로 사용자 찾기·만들기
  4. SessionManager.issue
  5. 세션 쿠키
그대로인 것 더해지는 것
sessions 테이블, SessionManager의 발급·확인·연장·폐기, 세션 쿠키, 로그인 가드, /auth/session과 /me account_provider enum에 google, kakao. 사용자 한 명에 accounts 행이 여러 개 생긴다. 제공자로 보내고 돌아오는 두 경로(시작, 콜백). 위조 요청을 막는 state와 PKCE 값을 잠시 보관할 곳

accounts를 처음부터 사용자 테이블과 나눠 둔 이유가 이것이다. 비밀번호를 users에 두지 않았기 때문에, 비밀번호 없이 카카오로만 가입한 사용자도 같은 모양이 된다. 구조는 03 문서에서 본다.

읽는 순서

큰 흐름에서 세부 로직으로 내려간다. 모르는 개념(쿠키 속성, 해시, HMAC 등)이 나오면 01 웹 인증 개념의 해당 절로 넘어갔다 돌아오면 된다.

  1. 02 로그인 요청 한 번 따라가기 로그인부터 /me까지 한 요청씩 따라가며 각 단계가 어느 파일인지 잇는다.
  2. 03 사용자·계정·세션 테이블 세 테이블의 관계, 소셜 계정을 받을 수 있게 나눈 구조.
  3. 04 비밀번호 해시와 확인 scrypt, 솔트, 상수 시간 비교, 없는 이메일에도 해시를 계산하는 이유.
  4. 05 세션 토큰: 만들기, 서명, 저장 190비트 난수 토큰, 쿠키의 HMAC 서명, DB의 SHA-256 해시.
  5. 06 SessionManager: 발급, 확인, 연장, 폐기 세션의 일생과 연장 계산, 겹치는 요청.
  6. 07 세션 쿠키 설정 쿠키 속성 하나하나를 왜 그렇게 정했는지.
  7. 08 로그인 가드와 CurrentSession 가드가 컨트롤러 앞에서 세션을 확인하고 넘기는 방식.
  8. 09 인증 API 응답 설계 네 API의 응답과 오류 코드를 그렇게 정한 이유.

Nest의 가드 자체가 처음이면 08 전에 nest 06 가드와 파라미터 데코레이터를 먼저 읽는다.

3. 카카오로만 가입한 사용자에게는 비밀번호가 없다. 비밀번호 해시를 users 테이블에 두었다면 무엇이 불편했을까?

소셜 로그인이 붙으면 절.

답 보기

비밀번호 칸이 NULL인 사용자와 아닌 사용자가 섞이고, 카카오 계정 id와 구글 계정 id를 담을 칸을 제공자마다 users에 더해야 한다. 한 사람이 이메일과 카카오를 함께 쓰는 경우도 표현하기 어렵다. accounts로 나누면 로그인 수단이 하나 늘 때 행이 하나 늘 뿐이다.

답 보기

가드는 "세션 쿠키가 가리키는 세션이 살아 있는가"만 본다. 그 세션을 비밀번호로 확인하고 만들었는지, 카카오로 확인하고 만들었는지는 모른다. 두 로그인 모두 마지막에 같은 SessionManager.issue로 같은 모양의 세션을 만들기 때문이다.
