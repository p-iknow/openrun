08 로그인 가드와 CurrentSession

로그인이 필요한 API에 붙이는 UserSessionGuard와, 가드가 확인한 세션을 핸들러 인자로 받는 @CurrentSession()을 읽는다. 가드 하나를 사용자와 운영자가 함께 쓰도록 만든 구조, 주입 토큰, 모듈 경계를 차례로 본다. 가드와 파라미터 데코레이터의 일반 개념은 nest 06 문서에 있다.

GET /me가 가드를 지나는 길

GET /me는 로그인 가드가 붙은 첫 API다. 세션 쿠키를 실은 요청과 쿠키 없는 요청이 각각 어떻게 흐르는지 보자.

  1. 브라우저
  2. SessionGuard
  3. SessionManager
  4. MeController
  1. 세션 쿠키가 있을 때
  2. GET /me Cookie: openrun.session_token=토큰.서명
  3. authenticate({ request, response })
  4. 쿠키 → 서명 확인 → DB 조회 06 문서의 판단 순서
  5. { sessionId, subjectId }
  6. request[AUTHENTICATED_SESSION] = 세션 true를 돌려줌
  7. @CurrentSession()이 세션을 꺼내 findMe(session) 호출
  8. 200 { id, email, name, emailVerified }
  9. 쿠키가 없을 때
  10. GET /me
  11. authenticate({ request, response })
  12. null
  13. 401 AUTHENTICATION_REQUIRED MeController는 실행되지 않음

가드는 "세션이 있나"만 정하고, 세션을 찾는 방법은 모두 SessionManager에 맡긴다 (06 문서). 가드가 하는 일은 결과를 보고 막거나, 결과를 요청에 붙여 핸들러에 넘기는 것뿐이다.

파일 지도

공용 부품은 auth/에, 사용자 세션에만 해당하는 설정은 users/에 있다. 운영자 세션(#82)이 생기면 운영자 모듈이 users/와 같은 자리에 자기 설정을 둔다.

  • apps/api/src/
    • auth/ 공용 사용자·운영자가 함께 쓰는 것
      • session-guard.ts createSessionGuard, CurrentSession
      • authentication-required.ts 401 AUTHENTICATION_REQUIRED 예외
      • session-manager.ts 세션 규칙 (06 문서)
    • users/ 사용자 사용자 세션의 설정과 API
      • user-session.ts 정책, 쿠키 이름, 주입 토큰, UserSessionGuard, 프로바이더
      • users.module.ts 프로바이더 등록과 내보내기
      • me.controller.ts 가드를 붙인 첫 API GET /me

SessionGuard.canActivate

canActivate는 우리가 지은 이름이 아니라 Nest의 CanActivate 인터페이스가 정한 이름이다. Nest는 가드마다 이 메서드를 불러 "이 요청으로 핸들러를 실행해도 되는가"를 묻는다(nest 06 문서). 

// apps/api/src/auth/session-guard.ts
    async canActivate(context: ExecutionContext): Promise<boolean> {
      // 1. 요청과 응답을 꺼내 세션을 확인한다
      const http = context.switchToHttp();
      const request = http.getRequest<RequestWithSession>();
      const session = await this.sessionManager.authenticate({
        request,
        response: http.getResponse<Response>(),
      });
      // 2. 세션이 없으면 401 예외를 던진다
      if (!session) {
        throw createAuthenticationRequiredException();
      }
      // 3. 세션을 요청에 붙이고 통과시킨다
      request[AUTHENTICATED_SESSION] = session;
      return true;
    }
  1. 요청과 응답을 꺼내 세션을 확인한다 switchToHttp()로 Express의 req, res를 얻는다. 응답도 넘기는 이유는 authenticate가 만료된 쿠키를 지우거나 연장한 쿠키를 다시 구워야 하기 때문이다. 가드 단계에서 붙인 Set-Cookie는 나중에 핸들러가 보내는 응답에 그대로 실린다.
  2. 세션이 없으면 401 예외를 던진다 false를 돌려주지 않는다. 이유는 아래에 있다.
  3. 세션을 요청에 붙이고 통과시킨다 핸들러가 세션을 다시 찾지 않도록, 찾은 결과를 요청 객체의 Symbol 키에 둔다(다음 절).

요청에 붙이는 키를 Symbol로

// apps/api/src/auth/session-guard.ts
// 가드가 확인한 세션을 컨트롤러에 넘기는 자리다.
const AUTHENTICATED_SESSION = Symbol('AUTHENTICATED_SESSION');

type RequestWithSession = Request & {
  [AUTHENTICATED_SESSION]?: AuthenticatedSession;
};

가드는 찾은 세션을 request[AUTHENTICATED_SESSION]에 둔다. request.session이나 request.user 같은 문자열 키를 쓰지 않은 이유는 셋이다.

  1. 다른 라이브러리와 부딪히지 않는다 req.session은 express-session이, req.user는 Passport가 쓰는 이름이다. 나중에 그런 미들웨어가 들어와도 덮어쓰거나 덮어써지지 않는다.
  2. 이 파일 밖에서는 읽고 쓸 수 없다 AUTHENTICATED_SESSION은 export하지 않았다. 세션을 붙이는 곳은 가드, 꺼내는 곳은 CurrentSession뿐이고 둘 다 이 파일에 있다. 다른 코드가 실수로 request.session = ...을 써서 로그인한 것처럼 만드는 길이 없다.
  3. 타입이 정확하다 RequestWithSession이 Express의 Request에 이 키 하나만 더한다. 전역 Express.Request 타입을 넓히지 않으므로, 가드를 거치지 않은 곳에서 request에 세션이 있는 것처럼 보이지 않는다.

CurrentSession

// apps/api/src/auth/session-guard.ts
/** 로그인 가드가 확인한 세션. 가드를 붙인 핸들러에서만 쓴다. */
export const CurrentSession = createParamDecorator(
  (_: unknown, context: ExecutionContext): AuthenticatedSession => {
    const session = context.switchToHttp().getRequest<RequestWithSession>()[
      AUTHENTICATED_SESSION
    ];
    if (!session) {
      throw new Error(
        '로그인 가드를 붙이지 않은 핸들러에서 세션을 읽었습니다.',
      );
    }
    return session;
  },
);
// apps/api/src/users/me.controller.ts
// 내 정보. 로그인 가드가 붙는 첫 API이고, 1.8에서 넓힌다.
@Controller('me')
@UseGuards(UserSessionGuard)
export class MeController {
  constructor(private readonly usersService: UsersService) {}

  @Get()
  @ApiOkResponse({ type: SessionUserDto })
  findMe(
    @CurrentSession() session: AuthenticatedSession,
  ): Promise<SessionUserDto> {
    return this.usersService.findSessionUser(session.subjectId);
  }
}

@CurrentSession()은 가드가 붙여 둔 세션을 꺼내 인자로 넣는다. 값이 없으면 401이 아니라 일반 Error를 던져 500이 된다. 왜일까?

  • 가드를 붙인 핸들러라면 가드가 세션 없는 요청을 이미 401로 막았으므로, 여기서 세션이 없을 수 없다.
  • 그런데도 없다면 개발자가 @UseGuards를 빼먹은 것이다. 사용자 잘못이 아니라 코드의 버그다. 401로 응답하면 "로그인이 필요한 API인데 가드만 빠진" 상태가 겉으로는 정상처럼 보인다. 500으로 크게 실패해야 개발 중에 바로 알아챈다.
  • undefined를 그대로 넘기지 않는 것도 같은 이유다. 핸들러가 session.subjectId를 읽다 엉뚱한 곳에서 터지는 것보다, 원인이 적힌 메시지로 바로 실패하는 편이 낫다.

AuthenticatedSession에는 sessionId와 subjectId만 있다. 사용자 정보(이메일, 이름)는 필요한 핸들러가 subjectId로 직접 조회한다. 가드가 매번 사용자까지 읽으면 사용자 정보가 필요 없는 API도 쿼리를 한 번 더 하게 된다.

false가 아니라 401 예외

// apps/api/src/auth/authentication-required.ts
import { HttpStatus } from '@nestjs/common';
import { ProblemException } from '../problem-details/problem.exception.js';

// 로그인이 필요한데 세션이 없거나 만료됐다. 스토어는 code를 보고 로그인 화면으로 보낸다.
export function createAuthenticationRequiredException(): ProblemException {
  return new ProblemException({
    status: HttpStatus.UNAUTHORIZED,
    code: 'AUTHENTICATION_REQUIRED',
    detail: '로그인이 필요합니다.',
  });
}

가드가 false를 돌려주면 Nest는 403 Forbidden resource로 응답한다 (nest 06 문서). 로그인하지 않은 요청에는 403이 맞지 않는다.

상태 코드 뜻 이 저장소에서
401 Unauthorized 누군지 모른다. 인증하고 다시 오라 세션이 없거나 만료됨: AUTHENTICATION_REQUIRED
403 Forbidden 누군지 알지만 이 일은 허락하지 않는다 앞으로: Origin 검사 실패(#72) 등

예외를 직접 던지면 상태 코드뿐 아니라 본문도 정할 수 있다. 오류 응답은 ADR 0007의 Problem Details 형식이고, 스토어는 code가 AUTHENTICATION_REQUIRED인 것을 보고 로그인 화면으로 보낸다. 실제 응답은 이렇다. 

  const AUTHENTICATION_REQUIRED = {
    type: 'about:blank',
    title: 'Unauthorized',
    status: 401,
    detail: '로그인이 필요합니다.',
    code: 'AUTHENTICATION_REQUIRED',
  };

응답 설계 전체는 09 문서에서 다룬다.

왜 가드를 함수로 만드나

canActivate는 this.sessionManager로 세션을 확인했다. 여기부터는 이 매니저가 어디서 어떻게 가드에 들어오는지 본다. 

// apps/api/src/auth/session-guard.ts
/**
 * 주입 토큰이 가리키는 SessionManager로 세션을 확인하는 로그인 가드를 만든다.
 * 사용자 세션과 운영자 세션은 SessionManager(세션 테이블과 쿠키)만 바꿔 같은 가드를 쓴다.
 * 세션이 없거나 만료됐으면 401 AUTHENTICATION_REQUIRED다.
 */
export function createSessionGuard(
  sessionManagerToken: symbol,
): Type<CanActivate> {
  @Injectable()
  class SessionGuard implements CanActivate {
    constructor(
      @Inject(sessionManagerToken)
      private readonly sessionManager: SessionManager,
    ) {}

    async canActivate(context: ExecutionContext): Promise<boolean> {
      const http = context.switchToHttp();
      const request = http.getRequest<RequestWithSession>();
      const session = await this.sessionManager.authenticate({
        request,
        response: http.getResponse<Response>(),
      });
      if (!session) {
        throw createAuthenticationRequiredException();
      }
      request[AUTHENTICATED_SESSION] = session;
      return true;
    }
  }
  return SessionGuard;
}

createSessionGuard는 가드 인스턴스가 아니라 가드 클래스를 만들어 돌려준다. 사용자 쪽에서는 이렇게 한 번 부른다. 

// apps/api/src/users/user-session.ts
/** 사용자 세션의 SessionManager 주입 토큰. */
export const USER_SESSION_MANAGER = Symbol('USER_SESSION_MANAGER');

/** 사용자 로그인이 필요한 핸들러에 붙이는 가드. */
export const UserSessionGuard = createSessionGuard(USER_SESSION_MANAGER);

사용자 가드와 운영자 가드의 차이는 "어느 SessionManager를 쓰나" 하나뿐이다. 그런데 가드가 무엇을 주입받을지는 생성자의 @Inject(토큰)에 적고, 이 데코레이터 인자는 클래스를 정의하는 순간 정해진다. 클래스 하나로는 토큰을 하나밖에 적을 수 없다. 그래서 토큰을 함수 인자로 받아, 그 토큰을 쓰는 클래스를 함수 안에서 정의한다.

방법 모양 문제
가드 클래스를 둘 쓴다 UserSessionGuard, OperatorSessionGuard를 각각 작성 canActivate 본문이 똑같이 두 벌이 된다
가드 하나가 메타데이터를 읽는다 @SessionKind('operator')를 읽어 매니저를 고름 두 매니저를 모두 주입받아야 하고, 메타데이터를 빼먹으면 엉뚱한 세션을 본다
함수가 클래스를 만든다 (지금) createSessionGuard(토큰) 본문은 한 벌, 가드마다 필요한 매니저 하나만 주입받는다

함수를 부를 때마다 다른 클래스가 나온다. Nest는 가드를 클래스로 구별하므로 사용자 가드와 운영자 가드는 서로 다른 주입 대상이 된다. 그래서 user-session.ts에서 한 번만 불러 상수 UserSessionGuard에 담아 두고 모든 컨트롤러가 그 상수를 쓴다. 컨트롤러마다 createSessionGuard(...)를 새로 부르면 동작은 하지만 같은 가드가 여러 벌 생긴다.

운영자 로그인(#82)을 만들면 createSessionGuard(OPERATOR_SESSION_MANAGER)처럼 토큰만 바꿔 한 줄로 운영자 가드를 만들 수 있다. 아직 구현 전이다.

주입 토큰과 FactoryProvider

Nest에서 보통 프로바이더는 클래스 자체가 주입 토큰(DI 컨테이너에서 인스턴스를 찾는 열쇠. 쿠키의 세션 토큰과는 다른 것이다)이다. 모듈에 클래스를 등록하고, 받는 쪽 생성자에 타입만 적으면 Nest가 만들어 넣어 준다(nest 02 문서). 

// 보통의 방식: UsersService
@Injectable()
export class UsersService {
  // ...
}

@Module({ providers: [UsersService] })
export class UsersModule {}

export class AuthController {
  // 타입 UsersService가 곧 토큰이다. Nest가 등록된 UsersService를 찾아 넣는다
  constructor(private readonly usersService: UsersService) {}
}

SessionManager를 같은 방식으로 등록하면 두 군데서 막힌다.

// SessionManager도 그렇게 하면
@Module({ providers: [SessionManager] })

@Injectable()
export class SessionManager {
  // 1. Nest가 options를 자동으로 주입할 수 없다
  constructor(private readonly options: SessionManagerOptions) {}
}

export class AuthController {
  constructor(
    // 2. 사용자용인지 운영자용인지 고를 수 없다
    private readonly sessionManager: SessionManager,
  ) {}
}
  1. Nest가 options를 자동으로 주입할 수 없다 SessionManagerOptions는 다른 프로바이더가 아니라 정책, 쿠키 이름, 비밀키를 담은 객체다. 게다가 인터페이스라 실행할 때는 타입이 지워져 Nest에게는 Object로만 보인다. 앱이 켜질 때 "SessionManager의 의존성을 풀 수 없다"는 오류로 멈춘다.
  2. 사용자용인지 운영자용인지 고를 수 없다 사용자 세션과 운영자 세션은 같은 SessionManager 클래스를 옵션만 달리해 두 개 만든다. 토큰이 클래스 하나뿐이면 하나만 등록할 수 있고, 받는 쪽도 어느 것을 원하는지 말할 방법이 없다.

그래서 인스턴스마다 Symbol로 주입 토큰을 따로 만들고, 인스턴스를 만드는 함수를 직접 준다. 받는 쪽은 @Inject(USER_SESSION_MANAGER)로 어느 매니저인지 이름표를 적는다. 

// apps/api/src/users/user-session.ts
/** 사용자 세션의 SessionManager 주입 토큰. */
export const USER_SESSION_MANAGER = Symbol('USER_SESSION_MANAGER');
// ...
export const userSessionManagerProvider: FactoryProvider<SessionManager> = {
  provide: USER_SESSION_MANAGER,
  inject: [UserSessionStore, Clock],
  useFactory: (store: UserSessionStore, clock: Clock) => {
    const useSecureCookies = shouldUseSecureCookies();
    return new SessionManager({
      store,
      clock,
      secret: readAuthSecret(),
      cookie: {
        name: useSecureCookies ? `${SECURE_COOKIE_PREFIX}${COOKIE_NAME}` : COOKIE_NAME,
        domain: readCookieDomain(),
        secure: useSecureCookies,
      },
      getPolicy: ({ rememberMe }) =>
        rememberMe ? REMEMBERED_POLICY : NOT_REMEMBERED_POLICY,
    });
  },
};
// apps/api/src/users/auth.controller.ts
export class AuthController {
  constructor(
    private readonly usersService: UsersService,
    @Inject(USER_SESSION_MANAGER)
    private readonly sessionManager: SessionManager,
  ) {}
}
속성 뜻
provide: USER_SESSION_MANAGER 이 값을 찾을 때 쓰는 이름표
inject: [UserSessionStore, Clock] Nest가 먼저 만들어 useFactory의 인자로 넘겨 줄 프로바이더
useFactory 인스턴스를 만드는 함수. 앱이 켜질 때 한 번 불린다. 환경 변수도 이때 읽으므로 AUTH_SECRET이 없거나 짧으면 앱이 켜지지 않는다

토큰을 문자열 'USER_SESSION_MANAGER'가 아니라 Symbol로 만든 이유는 겹치지 않기 때문이다. 문자열은 다른 곳에서 같은 글자를 쓰면 같은 토큰이 된다. Symbol('...')은 만들 때마다 유일한 값이라, 이 상수를 가져다 쓰는 곳만 같은 토큰을 가리킨다. 괄호 안 글자는 디버깅할 때 보이는 설명일 뿐이다.

왜 USER_SESSION_MANAGER를 내보내나

// apps/api/src/users/users.module.ts
@Module({
  controllers: [AuthController, MeController],
  providers: [UsersService, UserSessionStore, userSessionManagerProvider],
  // 다른 모듈이 UserSessionGuard를 붙이려면 사용자 세션의 SessionManager가 필요하다.
  exports: [USER_SESSION_MANAGER],
})
export class UsersModule {}

가드 클래스는 UserSessionGuard 하나이고, 어느 컨트롤러든 @UseGuards(UserSessionGuard)로 붙이기만 한다. 다만 가드는 어느 모듈의 providers에도 적혀 있지 않으므로, Nest가 가드 인스턴스를 그 컨트롤러가 속한 모듈 기준으로 생성하고 생성자 인자도 그 모듈에서 찾는다 (nest 06 문서). 가드는 생성자에서 USER_SESSION_MANAGER를 주입받으므로, 가드를 붙인 컨트롤러의 모듈에서 이 토큰이 보여야 한다.

지금: MeController는 UsersModule 안에 있다
  1. Nest가 가드를 UsersModule 기준으로 생성
  2. USER_SESSION_MANAGER가 UsersModule의 providers에 있음
  3. 주입 성공
앞으로: 예매 모듈의 컨트롤러에 가드를 붙이면
  1. Nest가 가드를 예매 모듈 기준으로 생성
  2. 예매 모듈이 UsersModule을 imports
  3. UsersModule이 exports한 USER_SESSION_MANAGER가 보임
  4. 주입 성공

exports가 없으면 다른 모듈에서 UserSessionGuard를 붙이는 순간 앱이 켜지지 않는다. UserSessionStore나 UsersService는 내보내지 않는다. 다른 모듈은 세션 테이블을 직접 만질 일이 없고, 가드만 쓸 수 있으면 된다.

가드를 모듈마다 따로 생성한다면 가드도 여럿이 될 텐데, 그래도 괜찮을까? 이렇게 하면 가드 인스턴스는 UsersModule과 예매 모듈에 하나씩, 둘이 된다(nest 06 문서). 그래도 둘이 주입받는 SessionManager는 UsersModule이 만든 같은 객체다. 가드는 필드에 상태를 두지 않고 매니저에게 맡기며, 요청당 한 번만 확인하게 하는 WeakMap도 매니저 안에 있으므로 어느 모듈의 가드든 동작이 같다.

인증 가드와 인가

지금 가드는 "로그인했는가"만 본다. 이것이 인증(authentication, 누구인가)이다. 인가(authorization, 이 사람이 이 일을 해도 되는가)는 아직 거의 없다. 1단계에서 인가가 들어올 자리는 이렇다.

검사 질문 어디서 상태
로그인 가드 로그인한 사용자인가 UserSessionGuard 구현됨
운영자 가드 운영자 세션이 있는가. 사용자 세션으로는 /admin/*에 못 들어온다 같은 createSessionGuard에 운영자 토큰 #82 예정
내 것인가 (IDOR 방어) 이 주문이 요청한 사람의 것인가 서비스의 쿼리: WHERE user_id = subjectId 예매 단계

마지막 줄이 중요하다. GET /orders/42에 로그인 가드만 붙이면, 로그인한 누구나 42번 주문을 볼 수 있다. URL의 id만 바꿔 남의 데이터를 보는 이런 취약점을 IDOR(Insecure Direct Object Reference)라고 한다. 가드는 어느 주문인지 모르므로 막을 수 없고, 주문을 읽는 서비스가 @CurrentSession()으로 받은 subjectId를 조건에 넣어야 한다. 남의 주문이면 "없음"(404)으로 응답해 존재 여부도 알려 주지 않는 것이 흔한 방식이다.

정리: 가드는 "들어와도 되는 사람인가"를, 서비스는 "이 데이터를 만져도 되는 사람인가"를 본다. 앞의 것은 요청마다 같은 검사라 가드로 모으고, 뒤의 것은 데이터마다 달라 쿼리에 녹인다.

스스로 확인하기

1. 이렇게 바꾸면 쿠키 없는 GET /me의 응답은 어떻게 달라질까?

false가 아니라 401 예외 절. 가드를 바꾼다.

       if (!session) {
-        throw createAuthenticationRequiredException();
+        return false;
       }

401 AUTHENTICATION_REQUIRED 대신 403이 된다. Nest가 ForbiddenException('Forbidden resource')를 던지기 때문이다. 스토어는 AUTHENTICATION_REQUIRED를 보고 로그인 화면으로 보내므로, 이 변경으로 로그인 화면 이동이 깨진다.

2. 예매 모듈의 컨트롤러에 가드를 붙였더니 앱이 켜지지 않는다. 왜일까?

왜 USER_SESSION_MANAGER를 내보내나 절. 누군가 UsersModule을 이렇게 바꿨다. 예매 모듈은 UsersModule을 가져온다.

   providers: [UsersService, UserSessionStore, userSessionManagerProvider],
-  // 다른 모듈이 UserSessionGuard를 붙이려면 사용자 세션의 SessionManager가 필요하다.
-  exports: [USER_SESSION_MANAGER],
 })
답 보기

가드는 예매 모듈에서 만들어지고, 생성자가 USER_SESSION_MANAGER를 주입받아야 한다. UsersModule이 이 토큰을 내보내지 않으면 예매 모듈에서는 보이지 않아 "Nest can't resolve dependencies of the SessionGuard" 오류가 난다. MeController는 UsersModule 안에 있어서 이 변경과 상관없이 동작한다.

3. 가드를 빼먹으면 어떻게 될까?

CurrentSession 절. MeController에서 @UseGuards(UserSessionGuard)를 지우고, 로그인한 사용자가 쿠키를 실어 GET /me를 부른다.

로그인한 사용자여도 500이다. 세션을 찾아 요청에 붙이는 것은 가드의 일이라, 가드가 없으면 쿠키가 있어도 request[AUTHENTICATED_SESSION]이 비어 있다. CurrentSession이 "로그인 가드를 붙이지 않은 핸들러에서 세션을 읽었습니다."를 던진다. 개발 중에 바로 드러나므로 가드 누락이 운영까지 가지 않는다.

4. 이 API에는 무엇이 빠졌을까?

인증 가드와 인가 절. 앞으로 만들 주문 상세 API를 이렇게 짰다고 하자.

@Get(':id')
@UseGuards(UserSessionGuard)
findOne(@Param('id') id: number) {
  return this.ordersService.findById(id); // SELECT ... FROM orders WHERE id = ?
}
답 보기

인가가 빠졌다. 로그인한 누구나 id만 바꿔 남의 주문을 볼 수 있다(IDOR). @CurrentSession() session을 받아 WHERE id = ? AND user_id = session.subjectId로 조회하고, 없으면 404로 응답해야 한다.
