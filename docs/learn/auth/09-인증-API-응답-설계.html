09 인증 API 응답 설계

인증 API 네 개(POST /auth/sign-in, POST /auth/sign-out, GET /auth/session, GET /me)가 어떤 상태 코드와 본문으로 응답하는지, 왜 그렇게 정했는지 본다. "로그인하지 않았으면 401"이 늘 정답은 아니라는 것, 같은 401이라도 오류 코드로 뜻을 나누는 방법이 이 문서의 중심이다. 요청이 서버 안을 지나가는 순서는 02 문서에 있다.

API 네 개 한눈에 보기

API하는 일로그인 가드성공실패
POST /auth/sign-in로그인없음200 + SessionDto + 쿠키400 VALIDATION_FAILED, 401 INVALID_CREDENTIALS
POST /auth/sign-out로그아웃없음204 + 쿠키 지우기없음(늘 204)
GET /auth/session지금 누가 로그인해 있나없음200 + SessionDto 또는 null없음(로그인하지 않아도 200)
GET /me내 정보UserSessionGuard200 + SessionUserDto401 AUTHENTICATION_REQUIRED

로그인 가드가 붙은 곳은 /me 하나다. 나머지 셋은 로그인하지 않은 사람도 부를 수 있어야 하는 API라서 가드가 없다. 로그인 API에 "로그인해야 들어올 수 있다"는 가드를 붙일 수는 없고, 로그아웃과 현재 세션 조회는 로그인하지 않은 상태에서도 뜻 있는 답이 있다.

POST /auth/sign-in

성공: 200과 세션

HTTP/1.1 200 OK
Set-Cookie: openrun.session_token=<토큰>.<서명>; Max-Age=604800; Path=/; Expires=…; HttpOnly; SameSite=Lax
Content-Type: application/json; charset=utf-8

{"user": {"id": 1, "email": "kim@example.com", "name": "김오픈", "emailVerified": true}}
  • 201이 아니라 200이다. Nest는 POST에 201(Created)을 기본으로 붙인다. 세션 행이 새로 생기기는 하지만 클라이언트가 그 자원을 주소로 다시 가리킬 일이 없고, 응답이 돌려주는 것은 "로그인한 지금의 세션"이라 @HttpCode(HttpStatus.OK)로 200을 준다.
  • 본문은 GET /auth/session과 같은 SessionDto다. 로그인 화면은 응답을 받자마자 재동의 화면을 띄울지 같은 다음 화면을 정해야 한다(#79, 예정). 같은 모양을 주면 로그인 직후와 새로 고침 뒤를 같은 코드로 처리할 수 있다.
  • 쿠키는 헤더로만 간다. 토큰은 본문에 없다. HttpOnly 쿠키라 자바스크립트가 토큰을 만질 일이 없다 (07 문서).

rememberMe는 필수 값이다

본문에서 rememberMe를 빠뜨리면 기본값으로 채우지 않고 400으로 거절한다.

Better Auth와 다른 점: Better Auth는 rememberMe를 생략하면 켠 것으로 본다. 이 저장소는 세션을 7일 둘지 1일 둘지 정하는 값을 API의 기본값에 숨기지 않고, 스토어가 사용자가 고른 값을 늘 보내게 했다(ADR 0009). 기본값이 있으면 스토어가 체크박스 값을 빠뜨리는 실수를 해도 조용히 7일 세션이 생긴다.

"가입하지 않은 이메일입니다"와 "비밀번호가 틀렸습니다"를 나눠 주면 사용자에게는 친절하지만, 공격자는 이메일 목록을 넣어 보며 어떤 이메일이 우리 서비스에 가입했는지 알아낼 수 있다(계정 존재 여부 노출). 그래서 두 경우는 상태, 본문, 응답 시간까지 같게 만든다. 응답 시간을 같게 하는 방법은 04 문서에 있다.

가입(#74)에서는 "이미 가입된 이메일"을 알려 주기로 했다(스펙 #70 사용자 스토리 12). 가입 쪽에서 존재 여부가 드러나는 만큼 로그인 쪽을 막는 효과는 줄어들지만, 로그인은 비밀번호를 대입하는 공격의 입구라 로그인 응답에서 "이 이메일은 있다"를 확인해 주지 않는 일은 여전히 뜻이 있다. 요청 속도 제한은 10단계에서 Redis와 함께 넣는다(ADR 0009).

로그아웃은 세션 행을 지우고, 이미 지난 만료 일시로 같은 이름의 쿠키를 다시 내려 브라우저가 쿠키를 버리게 한다. 돌려줄 내용이 없으므로 204(No Content)다.

사용자가 로그아웃 버튼을 누르는 이유는 "이 브라우저에서 로그인돼 있지 않은 상태"가 되는 것이다. 이미 그 상태라면 목적은 이루어졌으니 오류가 아니다. 여기서 401을 주면 스토어는 로그아웃 버튼 하나에 "이미 로그아웃됐을 때"라는 오류 처리를 따로 짜야 한다. 같은 요청을 여러 번 보내도 결과가 같은 성질을 멱등성이라고 한다. 로그아웃이 멱등이면 네트워크가 끊겨 다시 보내도 안전하다.

로그인하지 않았으면 401이 아니라 200과 null

이 API가 묻는 것은 "지금 로그인한 사람은 누구인가"다. "아무도 없다"는 오류가 아니라 정상적인 답이다. 401은 "이 요청은 로그인해야 들어올 수 있는데 하지 않았다"는 뜻인데, 이 API는 로그인하지 않은 사람도 들어올 수 있다.

로그인하지 않으면 401로그인하지 않으면 200 null (선택)
스토어 코드방문자마다 오류 처리 갈래를 탄다. 진짜 오류(서버 장애)와 구분하는 코드가 필요하다data === null 하나로 갈린다
브라우저 콘솔과 모니터링방문자가 페이지를 열 때마다 401이 빨갛게 찍힌다조용하다
공통 오류 처리"401이면 로그인 화면으로" 규칙에 걸려 둘러보기만 하려던 방문자가 로그인 화면으로 끌려갈 수 있다걸리지 않는다

Better Auth의 getSession도 같은 방식으로 로그인하지 않았으면 null을 돌려준다. 반대로 /me처럼 로그인해야 뜻이 있는 API는 401을 준다(아래).

null을 직접 JSON으로 쓰는 이유

  // 헤더를 그릴 때마다 부르므로, 로그인하지 않았으면 오류가 아니라 null로 응답한다.
  // Nest는 핸들러가 null을 돌려주면 빈 본문을 보내므로, JSON null을 직접 쓴다.
  @Get('session')
  @ApiOkResponse({
    description: '현재 세션. 로그인하지 않았으면 null이다.',
    schema: { nullable: true, allOf: [{ $ref: getSchemaPath(SessionDto) }] },
  })
  async getSession(
    @Req() request: Request,
    @Res() response: Response,
  ): Promise<void> {
    const session = await this.sessionManager.authenticate({
      request,
      response,
    });
    const body: SessionDto | null = session && {
      user: await this.usersService.findSessionUser(session.subjectId),
    };
    response.json(body);
  }

다른 핸들러처럼 return body로 끝내면 로그인했을 때는 잘 되지만, null일 때 문제가 생긴다. Nest의 Express 어댑터는 핸들러가 돌려준 값이 null이나 undefined면 본문 없이 응답을 끝낸다.

쓴 코드응답 본문클라이언트의 response.json()
return null(비어 있음, 0바이트)JSON을 읽다가 오류
response.json(null)null (4바이트)null

그래서 @Res()를 passthrough 없이 받아 응답을 직접 보낸다. passthrough가 없으면 Nest는 응답을 보내지 않고 기다리므로, 이 핸들러는 반드시 response.json으로 끝내야 한다. 로그인한 경우도 같은 줄로 보내므로 두 갈래가 한 줄로 모인다.

이 API에도 authenticate가 쓰이므로, 세션을 연장할 때가 된 요청이면 연장한 쿠키가, 만료된 쿠키를 들고 온 요청이면 쿠키를 지우는 Set-Cookie가 함께 나간다. 헤더가 자주 부르는 API라 연장이 자연스럽게 일어나는 곳이기도 하다 (06 문서).

401 두 가지와 403

상태 코드는 HTTP가 정한 큰 분류이고, 앱 오류 코드(code)는 그 안에서 클라이언트가 무엇을 해야 하는지 나누는 이름이다. 인증 API의 401은 둘이다.

code언제스토어가 할 일
INVALID_CREDENTIALS로그인하려고 낸 이메일·비밀번호가 맞지 않다로그인 화면에 그대로 머물며 안내 문구를 보인다
AUTHENTICATION_REQUIRED로그인이 필요한 API인데 세션이 없거나 만료됐다로그인 화면으로 보내고, 로그인한 뒤 원래 화면으로 돌아온다

상태 코드만 보고 "401이면 로그인 화면으로"라고 처리하면, 로그인 화면에서 비밀번호를 틀렸을 때 로그인 화면으로 다시 이동하는 어색한 일이 생긴다. code로 나누면 두 경우를 정확히 다르게 처리할 수 있다.

401은 인증, 403은 인가다. 401(Unauthorized)은 이름과 달리 "누구인지 모른다"(인증 실패)는 뜻이고, 403(Forbidden)은 "누구인지는 아는데 이 일은 할 수 없다"(인가 실패)는 뜻이다. 1.4a에서는 필수 약관에 다시 동의하지 않은 사용자가 /me를 부르면 403 TERMS_CONSENT_REQUIRED로 막는 재동의 가드가 들어온다(#79, 예정). 인증과 인가의 차이는 00 문서에 있다.

오류 객체는 상태와 코드, 문구를 한곳에 두는 작은 함수로 만든다. 같은 오류를 여러 곳에서 던져도 응답이 늘 같다.

// apps/api/src/auth/authentication-required.ts
// 로그인이 필요한데 세션이 없거나 만료됐다. 스토어는 code를 보고 로그인 화면으로 보낸다.
export function createAuthenticationRequiredException(): ProblemException {
  return new ProblemException({
    status: HttpStatus.UNAUTHORIZED,
    code: 'AUTHENTICATION_REQUIRED',
    detail: '로그인이 필요합니다.',
  });
}

AUTHENTICATION_REQUIRED는 사용자와 운영자가 함께 쓰는 가드 팩토리(08 문서)가 던지므로 공용 폴더(auth/)에, INVALID_CREDENTIALS는 사용자 로그인에서만 쓰므로 users/에 있다.

오류 본문: Problem Details

위의 오류 응답은 모두 같은 모양이다. API의 모든 오류는 RFC 9457 Problem Details 형식(application/problem+json)으로 보낸다 (ADR 0007). 인증 오류도 따로 형식을 만들지 않고 이 틀에 code만 바꿔 싣는다.

필드예뜻
typeabout:blank오류 종류를 설명하는 문서 주소. 따로 없으므로 표준의 기본값
titleUnauthorized상태 코드의 이름
status401HTTP 상태 코드
detail로그인이 필요합니다.사람이 읽는 설명
codeAUTHENTICATION_REQUIRED앱이 더한 오류 코드. 클라이언트는 이 값으로 갈린다
errors[{ field, detail }]검증 오류일 때만. 필드별 오류

컨트롤러와 가드는 ProblemException을 던지기만 하고, 이 본문을 만드는 일은 전역 예외 필터가 맡는다. 필터가 예외를 본문으로 바꾸는 과정은 nest 04 문서에 있다.

SessionDto의 모양

// apps/api/src/users/session.dto.ts

  @ApiProperty({ type: String, description: '이름' })

export class SessionDto {
  @ApiProperty({ type: SessionUserDto, description: '로그인한 사용자' })

}

emailVerified가 들어간 이유

이메일 가입은 가입 화면 안에서 이메일을 인증해야 끝나므로(#76, #74), 이메일 가입자는 항상 true다. 미인증 안내나 가입 뒤 인증 메일 다시 보내기 같은 화면은 없다. 그래도 스펙 #70은 세션 응답에 이메일 인증 여부를 두기로 했다. 1.4b 소셜 가입에서는 제공자가 인증해 주지 않은 이메일이 들어올 수 있어, 그때 스토어가 로그인 직후 요청을 더 하지 않고 이 값으로 화면을 정할 수 있다.

DB에는 email_verified_at(일시)이 있지만 응답에는 참/거짓만 내보낸다. 클라이언트에게 필요한 것은 "했는가"이고, 언제 했는지는 내부 기록이다(03 문서). 

// apps/api/src/users/users.service.ts
      emailVerified: user.emailVerifiedAt !== null,

사용자를 user로 한 번 감싼 이유

본문을 사용자 객체 그대로({ id, email, … })가 아니라 { user: { … } }로 한 겹 감쌌다. SessionDto는 "로그인 직후 무엇을 보여 줄지 정하는 값"을 모으는 자리이고, 사용자는 그중 하나다. 스펙은 재동의가 필요한 약관과 시행 예정 개정판 목록도 이 응답에 담기로 했다(#79, #81, 예정). 감싸 두면 그런 값을 user 옆에 더해도 기존 코드가 깨지지 않고, 사용자의 칸과 세션의 칸이 섞이지 않는다.

지금
  1. { user }
재동의(#79) 이후 예정
  1. { user, 재동의할 약관, 시행 예정 개정판 }

email은 DB에서 NULL을 허용하지만(탈퇴) 응답에서는 string이다. 탈퇴할 때 세션도 함께 지우므로 세션이 있는 사용자는 늘 이메일이 있다. findSessionUser는 이 전제가 깨지면 500으로 드러나도록 오류를 던진다.

OpenAPI 명세

컨트롤러의 @ApiOkResponse와 DTO의 @ApiProperty, 본문의 zod 스키마에서 apps/api/openapi.json이 만들어지고, 스토어는 이 명세로 만든 타입과 클라이언트로 API를 부른다(react-next 01 문서). GET /auth/session의 응답은 이렇게 적힌다(parameters와 tags는 뺐다). 

"/auth/session": {
  "get": {
    "operationId": "AuthController_getSession",
    "responses": {
      "200": {
        "description": "현재 세션. 로그인하지 않았으면 null이다.",
        "content": {
          "application/json": {
            "schema": {
              "nullable": true,
              "allOf": [
                { "$ref": "#/components/schemas/SessionDto" }
              ]
            }
          }
        }
      },
      "default": {
        "description": "오류(Problem Details)",
        "content": {
          "application/problem+json": {
            "schema": { "$ref": "#/components/schemas/ProblemDetailsDto" }
          }
        }
      }
    }
  }
}

"$ref"만 쓰면 옆에 nullable을 붙일 수 없어서(OpenAPI 3.0에서 $ref 옆의 다른 키는 무시된다) allOf로 한 번 감싸고 nullable: true를 붙였다. 이 명세로 만든 타입에서 이 응답은 SessionDto | null이 되어, 스토어 코드가 null 처리를 빠뜨리면 타입 검사에서 걸린다.

/auth/sign-in의 요청 본문은 signInBodySchema(zod)의 .meta() 설명이 그대로 명세에 들어가고, 세 값이 모두 required로 적힌다. 명세의 default 응답은 모든 API에 붙는 Problem Details 오류다.

스토어가 이 응답들로 헤더와 로그인 화면을 그리는 방법은 #73에서 다룬다(예정).
