04 비밀번호 해시와 확인

비밀번호를 DB에 어떤 모양으로 저장하고, 로그인할 때 어떻게 맞는지 확인하는지 정리한다. apps/api/src/auth/password.ts의 두 함수와, 로그인에서 그 함수를 부르는 UsersService.verifyCredentials를 한 줄씩 따라간다. 숫자(메모리, 걸리는 시간, 문자열 길이)는 이 저장소의 Node에서 직접 실행해 확인했다.

한눈에 보기

비밀번호는 원문도, 되돌릴 수 있는 암호문도 저장하지 않는다. 무작위 솔트와 비밀번호를 scrypt에 넣어 나온 키만 솔트:키 형식으로 저장한다. 확인할 때는 저장된 솔트로 입력한 비밀번호를 다시 한 번 같은 방식으로 계산해, 나온 키가 저장된 키와 같은지 본다.

저장할 때: hashPassword
  1. 비밀번호 pw1234!
  2. 무작위 솔트 16바이트
  3. NFKC 정규화
  4. scrypt → 키 64바이트
  5. 솔트:키 문자열
  6. accounts.password_hash에 저장
확인할 때: verifyPassword
  1. 저장된 솔트:키
  2. :로 나누기
  3. 입력한 비밀번호 + 저장된 솔트로 scrypt
  4. 새 키와 저장된 키 비교
  5. 같으면 true

해시, 솔트, 키 유도 함수(KDF)라는 개념 자체는 01 문서의 해시, 솔트, 키 유도 함수 절에 있다. 이 문서는 이 저장소의 코드가 그 개념을 어떻게 쓰는지만 다룬다. 비유하면 비밀번호 확인은 자물쇠를 열어 보는 일이 아니라, 같은 재료(비밀번호 + 솔트)로 같은 반죽을 다시 빚어 보고 모양이 똑같은지 대조하는 일이다. 반죽에서 재료를 되돌려 뽑아낼 방법은 없다.

hashPassword: 솔트:키 만들기

비밀번호를 저장할 문자열로 바꾸는 함수다. 지금은 테스트와 시드가 쓰고, 회원가입 API(#74)가 생기면 가입할 때도 쓴다. 

/** 비밀번호를 `솔트:키`(hex) 형식의 scrypt 해시로 만든다. */
export async function hashPassword(password: string): Promise<string> {
  const salt = randomBytes(SALT_BYTES).toString('hex');
  const key = await deriveKey({ password, salt });
  return `${salt}:${key.toString('hex')}`;
}
  1. 솔트를 뽑는다 randomBytes(16)은 운영체제의 암호용 난수로 16바이트(128비트)를 뽑는다. toString('hex')로 바이트 하나를 두 글자로 바꾸므로 솔트는 32글자 문자열이 된다. 같은 비밀번호라도 사용자마다 솔트가 달라서, 저장된 값이 모두 다르다.
  2. scrypt로 키를 유도한다 deriveKey가 비밀번호를 NFKC로 정규화한 뒤 솔트와 함께 scrypt에 넣어 64바이트 키를 만든다. 일부러 느리고 메모리를 많이 쓰게 만든 계산이라 한 번에 약 60ms가 걸린다(아래).
  3. 솔트와 키를 콜론으로 잇는다 확인할 때 같은 솔트가 다시 필요하므로 솔트를 키 옆에 함께 저장한다. 솔트는 비밀이 아니다. 비밀은 비밀번호뿐이고, 솔트는 "같은 비밀번호라도 결과가 달라지게" 하는 역할만 한다.

deriveKey는 Node의 콜백 방식 scrypt를 Promise로 감싼 것이다.

function deriveKey({
  password,
  salt,
}: {
  password: string;
  salt: string;
}): Promise<Buffer> {
  return new Promise((resolve, reject) => {
    // 같은 글자를 다른 코드 포인트로 입력해도(예: 조합형 한글) 같은 비밀번호로 보도록 정규화한다(Better Auth와 같음).
    scrypt(
      password.normalize('NFKC'),
      salt,
      KEY_LENGTH,
      SCRYPT_OPTIONS,
      (error, key) => (error ? reject(error) : resolve(key)),
    );
  });
}

scryptSync가 아니라 비동기 scrypt를 쓴다. 60ms짜리 계산을 동기로 돌리면 그동안 Node의 이벤트 루프가 멈춰 다른 모든 요청이 기다린다. 비동기 버전은 계산을 libuv 스레드 풀로 보내고 이벤트 루프는 다른 요청을 계속 처리한다. 프론트엔드에서 무거운 계산을 Web Worker로 보내 메인 스레드를 막지 않는 것과 같다.

저장된 값의 모양

accounts.password_hash 칸에 들어가는 값은 이렇게 생겼다(값은 예시).

3f9a0c1e5b7d2a4c6e8f0a1b2c3d4e5f:9c2e…(128글자)…41ab
부분 바이트 hex 글자 수 정하는 상수
솔트 16 32 SALT_BYTES = 16
구분자 : - 1 -
키 64 128 KEY_LENGTH = 64
합계 - 161 -

hex는 0-9a-f만 쓰므로 솔트와 키 안에는 :가 나올 수 없다. 그래서 split(':')로 안전하게 나눌 수 있다. 어느 알고리즘과 파라미터로 만든 값인지는 문자열에 적혀 있지 않다. 파라미터는 코드의 SCRYPT_OPTIONS가 정하므로, 나중에 파라미터를 바꾸면 이미 저장된 해시는 확인되지 않는다는 점을 기억해 둔다.

이 칸이 users가 아니라 accounts에 있는 이유(소셜 로그인만 쓰는 사용자도 같은 모양으로 담기 위해)는 03 문서에 있다.

scrypt 파라미터와 메모리

// Better Auth와 같은 scrypt 파라미터다. 해시 하나에 약 128 × N × r = 32MiB를 쓴다.
const SCRYPT_OPTIONS = {
  N: 16384,
  r: 16,
  p: 1,
  // Node의 기본 메모리 한도(32MiB)에 딱 걸려 오류가 나므로 두 배로 넉넉히 준다.
  maxmem: 128 * 16384 * 16 * 2,
} satisfies ScryptOptions;
const KEY_LENGTH = 64;
const SALT_BYTES = 16;
파라미터 값 뜻
N 16384 (214) 비용. 내부에서 큰 표를 만들고 무작위 순서로 다시 읽는 횟수와 표 크기를 정한다. 두 배로 올리면 시간과 메모리가 두 배다
r 16 블록 크기. 표의 한 칸이 128 × r바이트다. 메모리 사용량에 곱해진다
p 1 병렬도. 같은 계산을 몇 번 따로 돌릴지다. 1이면 한 번

메모리: 128 × N × r = 32MiB

scrypt가 쓰는 메모리는 대략 128 × N × r바이트다.

128 × 16384 × 16 = 33,554,432바이트 = 32MiB

비밀번호 하나를 확인하는 데 32MiB를 잡아먹는다는 뜻이다. 서버 입장에서는 로그인 한 번에 잠깐 쓰는 양이지만, DB를 훔친 공격자가 비밀번호 수십억 개를 GPU로 대입해 보려면 시도마다 32MiB가 필요하다. GPU는 계산 장치는 많아도 장치마다 쓸 수 있는 메모리가 적어서, 메모리를 많이 요구하는 계산은 병렬로 많이 돌리기 어렵다. scrypt가 "메모리를 먹는(memory-hard)" 함수로 설계된 이유다.

maxmem을 두 배로 준 이유

Node의 scrypt에는 메모리 한도 maxmem이 있고 기본값이 32MiB다. 필요한 양이 딱 32MiB라 한도와 같은데, 실제로는 한도를 넘었다고 실패한다. 이 저장소의 Node에서 maxmem 없이 실행하면 이렇게 된다. 

Invalid scrypt params: error:030000AC:digital envelope routines::memory limit exceeded

계산에 필요한 메모리가 128 × N × r보다 조금 더 크기 때문이다. 그래서 한도를 두 배(64MiB)로 넉넉히 준다. maxmem은 "이만큼 쓰라"가 아니라 "이보다 많이 쓰면 거부하라"는 안전장치라서, 올려도 실제 사용량은 늘지 않는다.

얼마나 걸리나

이 저장소 개발 환경(Apple Silicon 노트북)에서 같은 파라미터로 재 보니 한 번에 약 59ms였다. 로그인 한 번에 사용자가 느끼지 못할 만큼이지만, 공격자가 초당 시도할 수 있는 횟수는 코어 하나당 약 17번으로 줄어든다. 운영 서버에서는 CPU에 따라 달라진다.

Better Auth와 같다. N, r, p, 키 길이, 솔트 길이, 솔트:키 hex 형식, NFKC 정규화를 모두 Better Auth에서 그대로 가져왔다. 나중에 Better Auth로 옮기거나 비교할 때 해시를 그대로 쓸 수 있다.

NFKC 정규화

유니코드에서는 눈에 같아 보이는 글자를 여러 코드 포인트 조합으로 쓸 수 있다. 한글 한이 대표적이다.

입력 방식 코드 포인트 JS 문자열
완성형 (대부분의 키보드) U+D55C 한 개 '한'
조합형 (macOS 파일 이름, 일부 입력기) U+1112 ᄒ + U+1161 ᅡ + U+11AB ᆫ 세 개 '한' 
'한' === '한'; // false: 바이트가 다르다
'한'.normalize('NFKC') === '한'.normalize('NFKC'); // true: 둘 다 U+D55C가 된다

해시는 바이트가 하나만 달라도 완전히 다른 값이 나온다. 정규화하지 않으면 휴대폰에서 가입한 비밀번호 한글1234를 다른 기기에서 똑같이 쳐도 로그인되지 않을 수 있다. 그래서 deriveKey는 scrypt에 넣기 전에 늘 password.normalize('NFKC')를 거친다. 저장할 때와 확인할 때 같은 함수를 지나므로 둘이 어긋나지 않는다.

NFKC의 K(호환)는 모양이 비슷한 호환 문자도 기본 문자로 바꾼다. 예를 들어 전각 Ａ는 A로, ①은 1로 바뀐다(직접 실행해 확인). 비밀번호의 가짓수는 아주 조금 줄지만, 같은 글자를 쳤는데 로그인이 안 되는 문제를 막는 쪽을 택한 것이다.

verifyPassword: 다시 만들어 비교하기

/** 비밀번호가 해시와 맞는지 상수 시간으로 비교한다. */
export async function verifyPassword({
  password,
  hash,
}: {
  password: string;
  hash: string;
}): Promise<boolean> {
  const [salt, keyHex] = hash.split(':');
  if (!salt || !keyHex) {
    return false;
  }
  const expected = Buffer.from(keyHex, 'hex');
  const actual = await deriveKey({ password, salt });
  return expected.length === actual.length && timingSafeEqual(expected, actual);
}
  1. 솔트와 키를 나눈다 '솔트:키'.split(':')의 앞 두 조각을 꺼낸다.
  2. 모양이 깨졌으면 바로 false DB 값이 비었거나 :가 없거나 한쪽이 빈 문자열이면(':abc', 'abc:') 확인할 재료가 없으므로 예외를 던지지 않고 "맞지 않음"으로 끝낸다. 로그인 쪽에서는 틀린 비밀번호와 똑같이 401이 된다.
  3. 저장된 키를 바이트로 되돌린다 Buffer.from(keyHex, 'hex')는 hex 두 글자를 1바이트로 바꾼다. 정상이면 64바이트다.
  4. 입력한 비밀번호로 키를 다시 만든다 저장할 때와 같은 솔트, 같은 파라미터, 같은 정규화를 거치므로 비밀번호가 같으면 바이트까지 똑같은 64바이트가 나온다.
  5. 두 키를 비교한다 길이가 같은지 먼저 보고, 같을 때만 timingSafeEqual로 내용을 비교한다. 순서가 중요한 이유는 다음 절에 있다.

길이를 먼저, 그다음 timingSafeEqual

return expected.length === actual.length && timingSafeEqual(expected, actual);

왜 === 가 아니라 timingSafeEqual인가

보통의 비교는 앞에서부터 한 바이트씩 보다가 다른 바이트를 만나면 바로 멈춘다. 그러면 앞부분이 많이 맞을수록 비교가 조금 더 오래 걸리고, 공격자가 그 시간 차이를 재서 값을 한 조각씩 맞혀 갈 여지가 생긴다(01 문서의 타이밍 공격). timingSafeEqual은 다른 바이트를 만나도 끝까지 비교해, 어디서 달라지든 같은 시간이 걸린다.

왜 길이를 먼저 보나

timingSafeEqual은 두 버퍼의 길이가 다르면 비교하지 않고 예외를 던진다. 

timingSafeEqual(Buffer.from('ab'), Buffer.from('abc'));
// RangeError [ERR_CRYPTO_TIMING_SAFE_EQUAL_LENGTH]

새로 만든 키(actual)는 늘 64바이트지만, 저장된 키(expected)는 DB 값이 깨졌다면 다를 수 있다. 예를 들어 hex가 아닌 글자가 섞이면 Buffer.from은 그 앞까지만 읽는다(Buffer.from('12zz', 'hex')는 1바이트). 길이 검사를 && 앞에 두면 이런 경우 예외 대신 false가 나와, 로그인 요청이 500이 아니라 401로 끝난다. 길이는 비밀이 아니므로(정상이면 늘 64) 길이를 먼저 비교해 시간이 달라져도 드러나는 정보가 없다.

verifyCredentials의 세 갈래

로그인 API(POST /auth/sign-in)는 이메일과 비밀번호를 UsersService.verifyCredentials에 넘긴다. 맞으면 사용자 id를 돌려주고, 아니면 401을 던진다. 요청 전체 흐름은 02 문서에 있고, 여기서는 이 함수 안만 본다. 

async verifyCredentials({
  email,
  password,
}: {
  email: string;
  password: string;
}): Promise<number> {
  const [account] = await this.db
    .select({ userId: accounts.userId, passwordHash: accounts.passwordHash })
    .from(accounts)
    .innerJoin(users, eq(users.id, accounts.userId))
    .where(and(eq(users.email, email), eq(accounts.provider, 'credential')));

  if (!account?.passwordHash) {
    // 비밀번호 해시는 수십 ms가 걸린다. 없는 이메일에서도 한 번 계산해 응답 시간으로 가입 여부를 알 수 없게 한다(Better Auth와 같음).
    await hashPassword(password);
    throw createInvalidCredentialsException();
  }
  const matches = await verifyPassword({
    password,
    hash: account.passwordHash,
  });
  if (!matches) {
    throw createInvalidCredentialsException();
  }
  return account.userId;
}

먼저 이메일이 같은 사용자의 이메일 로그인 계정(provider = 'credential')을 찾는다. 소셜 로그인(1.4b)이 생기면 한 사용자에게 구글, 카카오 계정 행도 붙지만, 비밀번호가 있는 행은 credential 하나뿐이다. 찾은 결과에 따라 세 갈래로 나뉜다.

  1. AuthController
  2. verifyCredentials
  3. DB
  1. 이메일, 비밀번호
  2. SELECT … WHERE email = ? AND provider = 'credential'
  3. 갈래 A: 계정이 없다 (가입하지 않은 이메일, 또는 소셜 계정만 있다)
  4. 빈 결과
  5. hashPassword(입력한 비밀번호) 결과는 버린다. 약 60ms
  6. 401 INVALID_CREDENTIALS
  7. 갈래 B: 계정은 있는데 비밀번호가 틀렸다
  8. userId, passwordHash
  9. verifyPassword → false 약 60ms
  10. 401 INVALID_CREDENTIALS
  11. 갈래 C: 비밀번호가 맞다
  12. userId, passwordHash
  13. verifyPassword → true 약 60ms
  14. userId

세 갈래 모두 scrypt를 정확히 한 번 계산한다. 그리고 A와 B는 같은 예외를 던진다. 이 두 가지가 다음 두 절의 주제다.

없는 이메일에도 해시를 계산하는 이유

갈래 A에서 hashPassword(password)의 결과는 어디에도 쓰지 않는다. 시간을 쓰는 것 자체가 목적이다. 이 줄을 지우면 어떻게 되는지 시간 막대로 비교해 보자. 맨 앞의 짧은 회색 막대가 DB 조회(수 ms로 잡았다)이고, scrypt는 위에서 잰 약 60ms다.

B. 틀린 비밀번호
DB verifyPassword (scrypt) 401
A. 없는 이메일지금 코드
DB hashPassword (버리는 scrypt) 401
A. 없는 이메일해시를 건너뛰면
DB 401 (약 15배 빠름)

해시를 건너뛰면 없는 이메일은 몇 ms 만에, 있는 이메일은 60ms쯤 뒤에 401이 온다. 응답 본문이 똑같아도 공격자는 이메일 목록을 하나씩 넣어 보며 시간만 재서 누가 가입했는지 가려낼 수 있다. 이렇게 가입 여부를 알아내는 것을 계정 열거라고 한다(01 문서의 계정 열거). 가입한 이메일 목록은 비밀번호 대입 공격이나 피싱 메일의 표적 목록이 된다.

hashPassword는 솔트를 뽑고 deriveKey를 한 번 부른다. verifyPassword도 deriveKey를 한 번 부른다. 무거운 부분이 같으므로 두 갈래의 응답 시간이 거의 같아진다.

Better Auth와 같다. Better Auth도 이메일로 사용자를 찾지 못하면 입력한 비밀번호를 한 번 해시한 뒤 같은 오류를 던진다.

선택 읽기: 이 동작을 지키는 테스트

응답 시간을 직접 재는 테스트는 기계 상태에 따라 흔들린다. 그래서 테스트는 "없는 이메일에서도 해시 함수가 한 번 불렸다"를 확인한다. apps/api/test/auth.int.spec.ts의 '없는 이메일도 같은 401이고, 비밀번호 해시를 한 번 계산해 응답 시간으로 구분되지 않게 한다'가 그 테스트다. 누군가 더미 해시 줄을 "쓸모없는 코드"로 보고 지우면 이 테스트가 실패한다.

같은 401 응답

import { HttpStatus } from '@nestjs/common';
import { ProblemException } from '../problem-details/problem.exception.js';

// 없는 이메일과 틀린 비밀번호에 같은 응답을 보내, 어느 쪽이 틀렸는지로 가입 여부를 알 수 없게 한다.
export function createInvalidCredentialsException(): ProblemException {
  return new ProblemException({
    status: HttpStatus.UNAUTHORIZED,
    code: 'INVALID_CREDENTIALS',
    detail: '이메일 또는 비밀번호가 올바르지 않습니다.',
  });
}

갈래 A와 B는 이 함수가 만든 같은 예외를 던진다. 응답은 상태 코드, code, 문구까지 똑같다. 

{
  "type": "about:blank",
  "title": "Unauthorized",
  "status": 401,
  "detail": "이메일 또는 비밀번호가 올바르지 않습니다.",
  "code": "INVALID_CREDENTIALS"

"가입하지 않은 이메일입니다"와 "비밀번호가 틀렸습니다"로 나눠 알려 주면 사용자에게는 친절하지만, 공격자에게는 시간을 잴 필요도 없이 가입 여부를 알려 주는 셈이다. 그래서 응답 내용과 응답 시간을 모두 같게 맞춘다. 실제 예매 서비스의 로그인 화면도 대부분 "아이디 또는 비밀번호를 확인해 주세요"처럼 어느 쪽이 틀렸는지 말하지 않는다. 응답 형식(Problem Details)과 code를 고른 이유는 09 문서에 있다.

이메일 정규화와 형식 검사를 하지 않는 이유

verifyCredentials에 들어오는 이메일은 이미 요청 본문 스키마를 지나 정리된 값이다. 

import { z } from 'zod';

const EMAIL_MESSAGE = '이메일을 입력해야 합니다.';
const PASSWORD_MESSAGE = '비밀번호를 입력해야 합니다.';

// POST /auth/sign-in의 본문. 이 스키마 하나에서 검증, OpenAPI 요청 본문, 타입이 모두 나온다.
// 이메일은 가입할 때처럼 앞뒤 공백을 지우고 소문자로 바꿔 비교한다.
// 형식 검사는 하지 않는다. 형식이 틀린 이메일도 없는 이메일과 같은 401로 응답하면 된다.
export const signInBodySchema = z.object({
  email: z
    .string(EMAIL_MESSAGE)
    .trim()
    .toLowerCase()
    .min(1, EMAIL_MESSAGE)
    .meta({ description: '이메일', example: 'user@example.com' }),
  password: z
    .string(PASSWORD_MESSAGE)
    .min(1, PASSWORD_MESSAGE)
    .meta({ description: '비밀번호' }),
  rememberMe: z.boolean('true나 false여야 합니다.').meta({
    description:
      '로그인 상태 유지. 켜면 세션이 7일 동안 유지되고 쓰는 동안 연장된다. 끄면 1일 뒤 끝나고 브라우저를 닫으면 쿠키가 사라진다.',
  }),
});

export type SignInBody = z.infer<typeof signInBodySchema>;

trim과 toLowerCase

users.email에는 가입할 때 소문자로 바꾼 값이 들어간다(03 문서). 로그인할 때도 같은 규칙으로 바꿔야 ' User@Example.com '처럼 앞뒤에 공백을 붙이거나 대문자를 섞어 쳐도 같은 계정을 찾는다. 스키마가 값을 바꿔서 넘기므로(zod의 trim, toLowerCase는 검사가 아니라 변환이다) 서비스 코드는 정리된 값만 받는다.

형식 검사를 하지 않는 이유

z.email() 같은 형식 검사를 넣지 않았다. 넣으면 abc는 400 VALIDATION_FAILED, abc@x.com은 401 INVALID_CREDENTIALS로 응답이 갈린다. 형식이 틀린 이메일은 어차피 가입되어 있을 수 없으므로, 없는 이메일과 같은 401로 끝내면 결과가 같고 규칙도 하나 줄어든다. 형식 검사는 새 값을 받아 저장하는 회원가입(#74)에서 한다. 빈 값만은 min(1)로 400을 낸다. 빈 칸을 보낸 것은 공격이 아니라 화면의 실수라서, 어느 칸이 비었는지 알려 주는 편이 낫다.

아직 없는 것

  • 비밀번호 규칙과 가입할 때의 해시: 최소 길이 같은 규칙과, 가입 요청에서 hashPassword를 불러 accounts에 넣는 흐름은 회원가입 API(#74)에서 더한다. 그때 이 문서에 절을 더한다.
  • 로그인 시도 횟수 제한: scrypt가 한 번의 시도를 느리게 만들어도, 많은 서버에서 많이 시도하면 막지 못한다.

Better Auth와 다르다. Better Auth는 운영 환경에서 로그인·가입 요청 속도 제한을 기본으로 켠다. 이 저장소는 속도 제한을 Redis를 처음 들이는 10단계에서 함께 넣는다(ADR 0009). 그 전까지 로그인 API는 횟수 제한이 없다.

4. macOS에서 복사해 붙여 넣은 비밀번호 한글1234가 조합형이었다. 가입은 휴대폰(완성형)으로 했다. 로그인되는가?

NFKC 정규화 절의 코드 포인트 표를 본다.

답 보기

된다. deriveKey가 저장할 때와 확인할 때 모두 normalize('NFKC')를 거치므로, 조합형 U+1112 U+1161 U+11AB도 완성형 U+D55C로 바뀐 뒤 scrypt에 들어간다. 정규화가 없었다면 바이트가 달라 다른 키가 나오고 로그인에 실패한다.

5. maxmem을 128 * 16384 * 16 * 2에서 128 * 16384 * 16 * 10으로 올리면 로그인 한 번에 쓰는 메모리가 늘어나는가?

scrypt 파라미터와 메모리 절을 본다.

답 보기

늘지 않는다. 실제로 쓰는 메모리는 N과 r이 정한다(약 128 × N × r = 32MiB). maxmem은 그보다 많이 쓰려 하면 거부하는 상한일 뿐이다. 메모리를 더 쓰게 하려면 N이나 r을 올려야 하고, 그러면 이미 저장된 해시는 확인되지 않는다.
