02 로그인 요청 한 번 따라가기

사용자가 이메일과 비밀번호로 로그인하고(POST /auth/sign-in), 받은 쿠키로 내 정보를 조회하기(GET /me)까지 요청 두 번이 API 서버 안에서 어떤 순서로 지나가는지 따라간다. 단계마다 무엇이 일어나는지만 보고, 각 단계를 자세히 푸는 일은 04~09 문서에 맡긴다. 큰 그림에서 이 흐름이 어디에 있는지는 00 문서에 있다.

한눈에 보기

로그인은 "이 사람이 누구인지 확인하고, 다음 요청부터는 다시 묻지 않도록 표를 하나 쥐여 주는 일"이다. 표가 세션 쿠키이고, 표의 원본 기록이 DB의 세션 행이다. 아래 순서도의 1~9가 로그인 요청, 10~16이 다음 요청이다.

  1. 브라우저
  2. API 서버
  3. DB
  1. 로그인 요청
  2. POST /auth/sign-in email, password, rememberMe
  3. zod로 본문 검증 이메일은 trim + 소문자
  4. 이메일로 credential 계정 찾기
  5. user_id, password_hash
  6. scrypt로 비밀번호 확인
  7. 토큰 만들기 32자 난수
  8. 세션 행 INSERT 토큰의 SHA-256 해시만
  9. 쿠키 값 = 토큰.HMAC 서명
  10. 200 + Set-Cookie 본문: { user }
  11. 다음 요청
  12. GET /me Cookie: 토큰.서명
  13. 가드: 서명 확인
  14. 토큰 해시로 세션 찾기
  15. 세션 행
  16. 만료 확인 연장할 때면 만료 다시 쓰기
  17. 200 + 내 정보

핵심 하나: 서버는 로그인할 때 비밀번호를 한 번 확인하고, 그다음부터는 비밀번호를 다시 보지 않는다. 대신 요청마다 쿠키에 든 토큰이 DB의 세션 행과 맞는지만 본다. 그래서 세션 행을 지우면(로그아웃, 탈퇴) 쿠키가 남아 있어도 바로 로그인이 풀린다. 이것이 JWT 대신 DB 세션을 고른 이유다(세션과 JWT).

등장하는 파일

로그인 흐름은 두 폴더에 나뉘어 있다. auth/는 사용자와 운영자가 함께 쓰는 세션·비밀번호 로직이고, users/는 사용자 쪽 API와 세션 테이블 연결이다. 이렇게 나눈 이유는 08 문서에서 본다.

요청 보내기

로그인 화면(스토어, #73에서 만든다)이 보내는 요청은 이런 모양이다. 본문은 JSON이고 세 값이 모두 필수다. 

POST /auth/sign-in HTTP/1.1
Host: localhost:3000
Content-Type: application/json

{"email": " Kim@Example.com", "password": "password1!", "rememberMe": true}
값뜻
email가입한 이메일. 대소문자나 앞뒤 공백이 달라도 같은 이메일로 본다
password비밀번호 원문. HTTPS로 보내고 서버는 저장하지 않는다
rememberMe로그인 상태 유지. 세션을 7일 유지할지 1일로 끝낼지 정한다(06 문서)

본문 검증

요청이 컨트롤러 메서드에 닿기 전에 검증 파이프가 본문을 signInBodySchema로 검사하고 다듬는다. 파이프가 무엇이고 언제 실행되는지는 nest 05 문서에 있다. 

// apps/api/src/users/sign-in-body.ts
export const signInBodySchema = z.object({
  email: z
    .string(EMAIL_MESSAGE)
    .trim()
    .toLowerCase()
    .min(1, EMAIL_MESSAGE)
    .meta({ description: '이메일', example: 'user@example.com' }),
  password: z
    .string(PASSWORD_MESSAGE)
    .min(1, PASSWORD_MESSAGE)
    .meta({ description: '비밀번호' }),
  rememberMe: z.boolean('true나 false여야 합니다.').meta({
    description:
      '로그인 상태 유지. 켜면 세션이 7일 동안 유지되고 쓰는 동안 연장된다. 끄면 1일 뒤 끝나고 브라우저를 닫으면 쿠키가 사라진다.',
  }),
});
  1. 이메일을 다듬는다 " Kim@Example.com"은 trim()과 toLowerCase()를 지나 "kim@example.com"이 된다. 가입할 때도 같은 방식으로 저장하므로, 이렇게 다듬어야 DB의 값과 글자 그대로 비교할 수 있다.
  2. 형식은 검사하지 않는다 "abc"처럼 이메일 모양이 아니어도 통과시킨다. 그런 이메일은 어차피 DB에 없으니, 뒤에서 "없는 이메일"과 같은 401로 응답하면 된다. 로그인에서 형식 오류를 따로 알려 줄 이득이 없다.
  3. 빠진 값은 400 rememberMe를 빠뜨리면 400 VALIDATION_FAILED가 나가고 컨트롤러는 불리지 않는다. 기본값을 두지 않은 이유는 09 문서에 있다.

컨트롤러가 하는 일

검증을 통과하면 AuthController.signIn이 불린다. 하는 일은 세 줄이다.

// apps/api/src/users/auth.controller.ts
  @Post('sign-in')
  @HttpCode(HttpStatus.OK)
  @ApiOkResponse({ type: SessionDto, description: '로그인한 세션' })
  async signIn(
    @Body({ schema: signInBodySchema }) body: SignInBody,
    @Req() request: Request,
    @Res({ passthrough: true }) response: Response,
  ): Promise<SessionDto> {
    const userId = await this.usersService.verifyCredentials(body);
    await this.sessionManager.issue({
      request,
      response,
      subjectId: userId,
      rememberMe: body.rememberMe,
    });
    return { user: await this.usersService.findSessionUser(userId) };
  }
signIn의 세 단계
  1. verifyCredentials: 누구인가
  2. issue: 표(세션) 발급
  3. findSessionUser: 응답 본문

@Res({ passthrough: true })는 응답 객체를 받아 쿠키만 얹고, 본문은 평소처럼 return한 값으로 Nest가 보내게 하는 설정이다. passthrough가 없으면 응답을 직접 끝내야 한다. @HttpCode(HttpStatus.OK)는 Nest가 POST에 붙이는 기본값 201(Created)을 200으로 바꾼다. 로그인은 새 자원을 만든다기보다 "로그인한 세션"을 돌려주는 일이라 200으로 둔다.

비밀번호 확인

verifyCredentials는 이메일로 계정을 찾고 비밀번호가 맞는지 본다. 비밀번호 해시는 사용자 테이블이 아니라 계정 테이블에 있으므로 둘을 JOIN한다. 테이블을 이렇게 나눈 이유는 03 문서에 있다. 

// apps/api/src/users/users.service.ts
    const [account] = await this.db
      .select({ userId: accounts.userId, passwordHash: accounts.passwordHash })
      .from(accounts)
      .innerJoin(users, eq(users.id, accounts.userId))
      .where(and(eq(users.email, email), eq(accounts.provider, 'credential')));

    if (!account?.passwordHash) {
      // 비밀번호 해시는 수십 ms가 걸린다. 없는 이메일에서도 한 번 계산해 응답 시간으로 가입 여부를 알 수 없게 한다(Better Auth와 같음).
      await hashPassword(password);
      throw createInvalidCredentialsException();
    }
    const matches = await verifyPassword({
      password,
      hash: account.passwordHash,
    });
    if (!matches) {
      throw createInvalidCredentialsException();
    }
    return account.userId;

DB로 가는 SQL은 대략 이렇다.

select "accounts"."user_id", "accounts"."password_hash"
from "accounts"
inner join "users" on "users"."id" = "accounts"."user_id"
where ("users"."email" = $1 and "accounts"."provider" = $2)
-- $1 = 'kim@example.com', $2 = 'credential'

틀린 두 경우의 응답이 상태, 본문, 걸리는 시간까지 같다. 다르면 남의 이메일이 가입돼 있는지 알아낼 수 있기 때문이다 (계정 존재 여부 노출, 타이밍 공격). scrypt, 솔트, 상수 시간 비교는 04 문서에서 자세히 본다.

세션 발급

누구인지 확인했으면 SessionManager.issue가 세션을 만든다. 각 단계의 이유는 05 문서(토큰)와 06 문서(발급)에 있다.

  1. 브라우저
  2. SessionManager
  3. DB
  1. 비밀번호 확인이 끝났다. 이제 issue({ request, response, subjectId, rememberMe })
  2. 이전 쿠키가 있나 readToken(request)
  3. 이전 세션 행 삭제 deleteByTokenHash(이전 토큰의 해시) · 이전 쿠키가 있을 때만
  4. 새 토큰을 만든다 createSessionToken() → aB3xK9pQuNYD…
  5. 토큰을 해시한다 hashSessionToken(token) → cfba0e82…
  6. sessions 행 저장 token_hash, user_id, expires_at, remember_me, IP, User-Agent
  7. 토큰에 서명한다 signSessionToken({ token, secret }) → aB3xK9pQ….gvaibV…
  8. Set-Cookie openrun.session_token=토큰.서명

새 토큰 하나가 두 갈래로 나뉜다는 것이 핵심이다. DB에는 해시를, 브라우저에는 서명을 붙인 원문을 보낸다. 아래 값은 실제로 계산한 것이다(서명은 예시 비밀키로 만들었다).

DB로 가는 갈래 aB3xK9pQuNYDrgTdxQwiH5Ect3qKdnvlcreateSessionToken() SHA-256 cfba0e82d48e53b7681546b8376dec3dd98b77c57ca07d136c74f582bb2e9522sessions.token_hash (hex 64자)
브라우저로 가는 갈래 aB3xK9pQuNYDrgTdxQwiH5Ect3qKdnvl같은 토큰 HMAC-SHA256 + AUTH_SECRET aB3xK9pQuNYDrgTdxQwiH5Ect3qKdnvl.gvaibVCtyOHsrg54mOTHnOlmlcBeCOECWmgPMwZhPVk=쿠키 값 = 토큰 + "." + 서명(base64 44자)
  1. 이전 세션이 있으면 지운다 로그인한 채로 다시 로그인하면 요청에 이전 쿠키가 실려 온다. 그 세션 행을 먼저 지워, 쓰이지 않는 세션 행이 주인 없이 남지 않게 한다. 남이 미리 심어 둔 세션을 이어 쓰는 공격(세션 고정)은 이 삭제가 아니라 다음 단계에서 토큰을 늘 새로 만드는 것으로 막힌다.
  2. 토큰을 새로 만든다 영문 대소문자와 숫자(a-z, A-Z, 0-9의 62종) 중에서 32자를 무작위로 뽑는다. 추측할 수 없을 만큼 경우의 수가 많다(약 190비트).
  3. DB에는 토큰의 해시만 넣는다 sessions에 token_hash(SHA-256), user_id, expires_at(지금 + 7일 또는 1일), remember_me, IP, User-Agent를 넣는다. DB가 유출돼도 해시로는 쿠키를 만들 수 없다.
  4. 쿠키에는 토큰과 서명을 넣는다 쿠키 값은 토큰.서명이다. 서명은 서버만 아는 AUTH_SECRET으로 만든 HMAC이라, 서명이 틀린 쿠키는 DB를 보기 전에 거를 수 있다.

실제 코드다. 주석의 번호가 위 단계 번호다.

// apps/api/src/auth/session-manager.ts
async issue({ request, response, subjectId, rememberMe }) {
  const { store, secret, clock, getPolicy } = this.options;

  // 1. 이전 세션이 있으면 지운다
  const previousToken = this.readToken(request);
  if (previousToken) {
    await store.deleteByTokenHash(hashSessionToken(previousToken));
  }

  // 2. 토큰을 새로 만든다
  const token = createSessionToken();

  // 3. DB에는 토큰의 해시만 넣는다
  const policy = getPolicy({ rememberMe }); // 7일 또는 1일
  await store.create({
    tokenHash: hashSessionToken(token),
    subjectId,
    expiresAt: new Date(clock.now().getTime() + policy.expiresInMs),
    rememberMe,
    ipAddress: request.ip ?? null,
    userAgent: request.get('user-agent') ?? null,
  });

  // 4. 쿠키에는 토큰과 서명을 넣는다
  this.setCookie({
    response,
    value: signSessionToken({ token, secret }),
    policy,
  });
}

안에서 부르는 세 함수는 각각 한 줄짜리다.

// apps/api/src/auth/session-token.ts
const TOKEN_ALPHABET = 'ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789';

// 62종 중 하나를 32번 뽑아 잇는다
export function createSessionToken() {
  return Array.from({ length: 32 }, () => TOKEN_ALPHABET[randomInt(62)]).join('');
}

// SHA-256 해시(hex 64자). DB에 넣고 찾을 때 쓴다
export function hashSessionToken(token) {
  return createHash('sha256').update(token).digest('hex');
}

// "토큰.서명". 서명은 AUTH_SECRET으로 만든 HMAC-SHA256의 base64다
export function signSessionToken({ token, secret }) {
  const signature = createHmac('sha256', secret).update(token).digest('base64');
  return `${token}.${signature}`;
}

읽기 쉽게 타입과 상수 이름을 줄였다. signSessionToken은 실제로는 서명 계산을 getSignature로 나눠 두었다.

발급이 끝나면 남는 것

issue()가 끝나면 서버 메모리에는 토큰이 남지 않는다. 토큰의 흔적은 두 곳에만 있고, 둘은 무게가 다르다. 누가 그 값을 훔쳤을 때 무슨 일이 생기는지로 비교하면 차이가 분명하다.

어디에무엇이예훔치면
브라우저 쿠키토큰 원문 + 서명aB3xK9pQ….gvaibV…= 그대로 쿠키에 넣으면 그 사용자로 로그인된다. 그래서 HttpOnly와 Secure로 쿠키가 새어 나가지 않게 지킨다
DB sessions.token_hash토큰의 SHA-256(hex)cfba0e82… (64자) 로그인할 수 없다. 해시에서 토큰 원문을 되살릴 수 없고, 서명을 만들 AUTH_SECRET도 DB에 없다

로그인에 쓸 수 있는 값은 브라우저 쿠키 하나뿐이다. DB가 통째로 유출돼도 세션을 가로챌 수 없게 하려고 원문 대신 해시를 저장한다.

응답

로그인 응답은 헤더의 Set-Cookie와 JSON 본문 두 부분이다. 둘은 서로 다른 코드에서 만들어져 하나의 응답으로 합쳐진다. 로컬 개발 환경(http://localhost)에서 실제로 받는 응답은 이렇다. 

HTTP/1.1 200 OK
Set-Cookie: openrun.session_token=aB3xK9pQ….gvaibV…%3D; Max-Age=604800; Path=/; Expires=Sun, 22 Nov 2026 03:00:00 GMT; HttpOnly; SameSite=Lax
Content-Type: application/json; charset=utf-8

{"user": {"id": 1, "email": "kim@example.com", "name": "김오픈", "emailVerified": true}}

두 부분은 어디서 오나

  1. AuthController.signIn
  2. SessionManager
  3. UsersService
  4. Nest와 Express
  1. issue({ request, response, … })
  2. response.cookie(이름, 값, 옵션) 응답 객체에 Set-Cookie를 얹어 두기만 한다
  3. 끝
  4. findSessionUser(userId)
  5. users 행을 읽어 본문 모양으로 바꾼다
  6. { id, email, name, emailVerified }
  7. return { user } @Res({ passthrough: true })라 반환값이 본문이 된다
  8. 얹어 둔 헤더 + JSON 본문을 함께 보낸다 200 OK

issue()는 쿠키를 응답 객체에 얹어 둘 뿐 응답을 보내지 않는다. 응답은 컨트롤러가 return한 뒤 Nest가 한 번에 보낸다. 그래서 쿠키를 얹는 코드와 본문을 만드는 코드가 따로 있어도 하나의 응답이 된다.

Set-Cookie 한 줄 뜯어 보기

헤더의 조각마다 그 값을 정한 코드를 아래에 적었다.

openrun.session_token=aB3xK9pQ….gvaibV…%3D; Max-Age=604800; Path=/; Expires=Sun, 22 Nov 2026 …; HttpOnly; SameSite=Lax 초록은 쿠키 자체(이름과 값), 파랑은 브라우저에게 주는 보관 규칙이다.

이 조각들을 만드는 코드는 SessionManager의 두 메서드다.

// apps/api/src/auth/session-manager.ts
private setCookie({ response, value, policy }) {
  response.cookie(this.options.cookie.name, value, {
    ...this.buildCookieOptions(),
    // rememberMe를 켰을 때만 maxAge를 준다(밀리초). Express가 Max-Age(초)와 Expires로 바꿔 적는다
    ...(policy.persistentCookie && { maxAge: policy.expiresInMs }),
  });
}

private buildCookieOptions() {
  const { domain, secure } = this.options.cookie;
  return {
    httpOnly: true,
    sameSite: 'lax',
    path: '/',
    secure, // 운영에서만 true
    ...(domain && { domain }), // 운영에서만 COOKIE_DOMAIN
  };
}
  • Max-Age=604800은 7일을 초로 적은 것이다(7 × 24 × 60 × 60). rememberMe: false면 maxAge를 주지 않아 Max-Age와 Expires가 빠지고, 브라우저를 닫을 때 사라지는 쿠키가 된다.
  • 운영 환경에서는 이름이 __Secure-openrun.session_token이 되고 Secure와 Domain이 붙는다. 속성 하나하나는 07 문서에서 본다.
  • 서명은 base64라 +, /, =가 섞이는데, Express가 쿠키 값을 URL 인코딩해(%2B, %2F, %3D) 내려보낸다. 위 값 끝의 %3D가 =다. 다음 요청에서 서버가 쿠키를 읽을 때 다시 디코딩하므로 신경 쓸 일은 없다.

본문 만들기

본문은 findSessionUser가 users 행을 읽어 만든다. DB 칸을 그대로 내보내지 않고, 화면에 필요한 모양으로 바꾼다.

DB 행에서 응답 본문으로 email_verified_at: 2026-11-10 09:12users 행 (이메일 가입은 가입할 때 채움) !== null emailVerified: true응답 본문 
// apps/api/src/users/users.service.ts
async findSessionUser(userId: number): Promise<SessionUserDto> {
  const [user] = await this.db
    .select({ id: users.id, email: users.email, name: users.name, emailVerifiedAt: users.emailVerifiedAt })
    .from(users)
    .where(eq(users.id, userId));
  if (!user?.email) {
    throw new Error(`세션의 사용자를 찾지 못했습니다: ${userId}`);
  }
  return {
    id: user.id,
    email: user.email,
    name: user.name,
    emailVerified: user.emailVerifiedAt !== null,
  };
}

쿠키는 HttpOnly라 페이지의 자바스크립트가 읽을 수 없다. 그래서 로그인 화면은 쿠키가 아니라 이 본문의 user로 누가 로그인했는지 안다. 본문 모양과 emailVerified가 들어간 이유는 09 문서에 있다.

쿠키를 싣고 GET /me

브라우저는 받은 쿠키를 저장해 두었다가, 같은 API 서버로 가는 다음 요청에 Cookie 헤더로 자동으로 싣는다. 서버가 "저장해 둬"라고 한 값(Set-Cookie)을 그대로 돌려줄 뿐, 브라우저는 그 뜻을 모른다. 

GET /me HTTP/1.1
Host: localhost:3000
Cookie: openrun.session_token=<토큰 32자>.<서명>

스토어(localhost:3001)의 브라우저 코드가 API(localhost:3000)를 부를 때는 출처가 달라 쿠키가 저절로 실리지 않는다. fetch에 credentials: 'include'를 주고, API는 그 출처를 허용하는 CORS 응답을 보내야 한다. 이 설정은 #72와 #73에서 다룬다. 이 문서는 쿠키를 그대로 싣는 클라이언트(테스트의 supertest 에이전트, curl)를 기준으로 본다.

가드가 세션을 확인한다

MeController에는 @UseGuards(UserSessionGuard)가 붙어 있다. 가드는 핸들러보다 먼저 실행되어 "들여보낼지"를 정한다. 가드가 무엇인지는 nest 06 문서, 이 가드를 만드는 방식은 08 문서에 있다. 

// apps/api/src/users/me.controller.ts
@Controller('me')
@UseGuards(UserSessionGuard)
export class MeController {

가드는 SessionManager.authenticate를 부른다. 이 함수가 쿠키 하나로 세션을 찾아가는 순서는 이렇다.

  1. 쿠키를 꺼낸다 Cookie 헤더에서 세션 쿠키 이름의 값을 꺼낸다. 없으면 로그인하지 않은 것이다.
  2. 서명을 확인한다 토큰.서명을 마지막 .에서 나누고, 토큰으로 서명을 다시 계산해 비교한다. 다르면 DB를 보지 않고 로그인하지 않은 것으로 다룬다.
  3. 해시로 세션 행을 찾는다 토큰을 SHA-256으로 해시해 token_hash가 같은 행을 찾는다. 없으면(로그아웃했거나 지워졌으면) 쿠키를 지우라고 응답한다.
  4. 만료를 본다 expires_at이 지났으면 행을 지우고 쿠키도 지운다. 연장할 때가 됐으면 만료를 다시 쓰고 쿠키를 다시 내린다.
  5. 통과 { sessionId, subjectId }를 요청 객체에 붙여 두고 핸들러로 보낸다. 
// apps/api/src/auth/session-guard.ts
    async canActivate(context: ExecutionContext): Promise<boolean> {
      const http = context.switchToHttp();
      const request = http.getRequest<RequestWithSession>();
      const session = await this.sessionManager.authenticate({
        request,
        response: http.getResponse<Response>(),
      });
      if (!session) {
        throw createAuthenticationRequiredException();
      }
      request[AUTHENTICATED_SESSION] = session;
      return true;
    }

핸들러가 세션을 받는다

가드가 붙여 둔 세션을 핸들러는 @CurrentSession()으로 꺼낸다. subjectId가 사용자 id이므로, 그 id로 사용자를 읽어 돌려준다. 

// apps/api/src/users/me.controller.ts
  @Get()
  @ApiOkResponse({ type: SessionUserDto })
  findMe(
    @CurrentSession() session: AuthenticatedSession,
  ): Promise<SessionUserDto> {
    return this.usersService.findSessionUser(session.subjectId);
  }

연장되는 갈래

로그인 상태 유지를 켰으면 세션은 7일짜리지만, 쓰는 동안에는 끝나지 않는다. 마지막으로 만료를 정한 뒤 1일이 지난 첫 요청에서 만료를 "지금부터 7일"로 다시 쓰고 쿠키도 다시 내린다. 아래는 월요일에 로그인하고 수요일에 다시 들어온 경우다.

로그인 때 정한 만료
0일 + 7일 로그인
2일째 요청 뒤 만료
2일 + 7일로 연장 요청(1일 지남 → 연장)

1일이 지나지 않은 요청은 DB에 쓰지 않는다. 요청마다 만료를 고쳐 쓰면 DB 쓰기가 너무 많아지기 때문이다. 계산 방법과 경계는 06 문서에서 본다.
