07 세션 쿠키 설정

로그인하면 API가 내려 주는 Set-Cookie 한 줄에 어떤 속성이 왜 붙는지 정리한다. SessionManager의 쿠키 메서드 세 개와 user-session.ts의 이름·정책, 환경 변수를 읽는 env.ts를 따라간다. 헤더 모양은 이 저장소의 Express(5.x)로 직접 내려 받아 확인했다.

한눈에 보기

세션 쿠키는 05 문서의 토큰.서명을 담는 그릇이다. 쿠키를 빼앗기면 서명도 해시도 소용없으므로, 속성들은 모두 이 값이 새어 나가지 않게 하거나 필요한 곳에만 실려 가게 하는 데 쓰인다.

속성 값 한 줄 이유
이름 openrun.session_token, 운영은 앞에 __Secure- 접두사가 있으면 브라우저가 HTTPS로 받은 Secure 쿠키만 허용한다
HttpOnly 늘 켬 페이지의 자바스크립트가 읽지 못한다. XSS가 토큰을 훔쳐 가지 못한다
Secure 운영만 켬 HTTPS 요청에만 실린다
SameSite Lax 다른 사이트가 보내는 요청에는 싣지 않되, 링크로 들어오는 이동에는 싣는다
Path / API의 모든 경로에 실린다
Domain 운영은 상위 도메인, 로컬은 없음 스토어 서버도 쿠키를 받아 로그인 상태로 화면을 그린다
Max-Age 로그인 상태 유지를 켜면 7일, 끄면 없음 없으면 브라우저를 닫을 때 사라지는 쿠키가 된다

각 속성이 브라우저에서 어떻게 동작하는지(일반 규칙)는 01 문서의 쿠키 절과 그 아래 속성별 절에 있다. 이 문서는 이 저장소가 값을 어떻게 골랐는지만 다룬다.

로컬과 운영의 Set-Cookie

로그인 상태 유지를 켜고 로그인했을 때 응답 헤더다. 쿠키 값은 줄였다.

로컬 (http://localhost, NODE_ENV는 production이 아님, COOKIE_DOMAIN 비움)

Set-Cookie: openrun.session_token=Xk3p…Q9aZ.5%2Fy8…C9U%3D; Max-Age=604800; Path=/; Expires=Sun, 22 Nov 2026 08:10:58 GMT; HttpOnly; SameSite=Lax

운영 (https, NODE_ENV=production, COOKIE_DOMAIN=openrun.example.com)

Set-Cookie: __Secure-openrun.session_token=Xk3p…Q9aZ.5%2Fy8…C9U%3D; Max-Age=604800; Domain=openrun.example.com; Path=/; Expires=Sun, 22 Nov 2026 08:10:58 GMT; HttpOnly; Secure; SameSite=Lax
차이 로컬 운영 정하는 것
이름 openrun.session_token __Secure-openrun.session_token shouldUseSecureCookies() (NODE_ENV)
Secure 없음 있음
Domain 없음 openrun.example.com readCookieDomain() (COOKIE_DOMAIN)

헤더를 읽을 때 알아 둘 것 세 가지가 있다.

  • 코드는 maxAge를 밀리초(7 * DAY_MS)로 넘기지만, Express가 헤더에는 초(604800)로 바꿔 쓴다. 같은 시점을 가리키는 Expires도 함께 붙인다. 둘 다 있으면 브라우저는 Max-Age를 따른다(01 문서의 Max-Age).
  • 서명의 base64 글자 /, =, +는 Express가 %2F, %3D, %2B로 인코딩해 내린다. 읽을 때 다시 풀린다.
  • 로그인 상태 유지를 끄면 Max-Age와 Expires가 둘 다 빠진다(아래).

쿠키를 만드는 코드

쿠키를 다루는 곳은 SessionManager의 private 메서드 세 개뿐이다. 세션을 발급하거나 연장할 때 setCookie를, 세션이 없거나 만료됐거나 로그아웃할 때 clearCookie를 부른다. 

private setCookie({
  response,
  value,
  policy,
}: {
  response: Response;
  value: string;
  policy: SessionPolicy;
}): void {
  response.cookie(this.options.cookie.name, value, {
    ...this.buildCookieOptions(),
    // 1. 로그인 상태 유지를 켠 정책일 때만 maxAge를 넣는다
    ...(policy.persistentCookie && { maxAge: policy.expiresInMs }),
  });
}

private clearCookie(response: Response): void {
  response.clearCookie(this.options.cookie.name, this.buildCookieOptions());
}

// 2. 내릴 때와 지울 때 같은 옵션을 쓰도록 한 곳에서 만든다
private buildCookieOptions(): CookieOptions {
  const { domain, secure } = this.options.cookie;
  return {
    httpOnly: true,
    sameSite: 'lax',
    path: '/',
    secure,
    // 3. domain은 값이 있을 때만 넣는다
    ...(domain && { domain }),
  };
}
  1. maxAge는 정책이 정한다 policy.persistentCookie가 true일 때만 maxAge를 넣는다. ...(false && …)는 ...false가 되어 아무것도 펼치지 않는다.
  2. 공통 옵션은 buildCookieOptions 한 곳에서 httpOnly, sameSite, path, secure, domain은 내릴 때와 지울 때 똑같아야 한다. 한 메서드가 만들어 두 곳에서 쓴다.
  3. domain은 있을 때만 넣는다 ...(domain && { domain })는 domain이 undefined면 ...undefined가 되어 역시 아무것도 펼치지 않는다. 그래서 로컬에서는 키 자체가 없고 헤더에도 Domain이 나오지 않는다.

이름, Domain, Secure, 정책은 사용자 세션 쪽 설정 파일이 정해 SessionManager에 넘긴다.

const DAY_MS = 24 * 60 * 60 * 1000;

// 로그인 상태 유지를 켜면 7일 동안 유지하고, 마지막 연장 뒤 1일이 지난 첫 요청에서 다시 7일로 연장한다(Better Auth와 같음).
const REMEMBERED_POLICY: SessionPolicy = {
  kind: 'sliding',
  expiresInMs: 7 * DAY_MS,
  updateAgeMs: DAY_MS,
  persistentCookie: true,
};
// 끄면 1일 뒤 끝나고 연장하지 않는다. 쿠키에 Max-Age가 없어 브라우저를 닫으면 사라진다.
const NOT_REMEMBERED_POLICY: SessionPolicy = {
  kind: 'fixed',
  expiresInMs: DAY_MS,
  persistentCookie: false,
};

const COOKIE_NAME = 'openrun.session_token';
// __Secure- 접두사를 붙이면 브라우저가 Secure 쿠키로만 받는다.
const SECURE_COOKIE_PREFIX = '__Secure-';

/** 사용자 세션의 SessionManager 주입 토큰. */
export const USER_SESSION_MANAGER = Symbol('USER_SESSION_MANAGER');

/** 사용자 로그인이 필요한 핸들러에 붙이는 가드. */
export const UserSessionGuard = createSessionGuard(USER_SESSION_MANAGER);

export const userSessionManagerProvider: FactoryProvider<SessionManager> = {
  provide: USER_SESSION_MANAGER,
  inject: [UserSessionStore, Clock],
  useFactory: (store: UserSessionStore, clock: Clock) => {
    const useSecureCookies = shouldUseSecureCookies();
    return new SessionManager({
      store,
      clock,
      secret: readAuthSecret(),
      cookie: {
        name: useSecureCookies ? `${SECURE_COOKIE_PREFIX}${COOKIE_NAME}` : COOKIE_NAME,
        domain: readCookieDomain(),
        secure: useSecureCookies,
      },
      getPolicy: ({ rememberMe }) =>
        rememberMe ? REMEMBERED_POLICY : NOT_REMEMBERED_POLICY,
    });
  },
};
/** 사용자 세션 쿠키의 Domain 속성. 스토어와 API가 서브도메인으로 나뉘는 배포에서 상위 도메인을 적는다. 없으면 API 호스트에만 전송된다. */
export function readCookieDomain(
  source: NodeJS.ProcessEnv = process.env,
): string | undefined {
  return source.COOKIE_DOMAIN || undefined;
}

/** 쿠키에 Secure 속성과 `__Secure-` 접두사를 붙일지. 운영 환경(NODE_ENV=production)은 HTTPS로만 서비스하고, 로컬은 http://localhost라 Secure 쿠키를 쓸 수 없다. */
export function shouldUseSecureCookies(
  source: NodeJS.ProcessEnv = process.env,
): boolean {
  return source.NODE_ENV === 'production';
}

SessionManager는 쿠키 이름이나 도메인을 직접 알지 않는다. 덕분에 운영자 세션(#82)은 이름과 Domain만 다른 설정으로 같은 클래스를 하나 더 만들면 된다(08 문서).

이름과 __Secure- 접두사

이름은 openrun.session_token이다. 앱 이름을 앞에 붙여, 같은 도메인 아래 다른 쿠키(분석 도구, 운영자 쿠키)와 헷갈리지 않게 한다. 운영에서는 앞에 __Secure-가 더 붙는다.

__Secure-openrun.session_token 로컬에서는 접두사 없이 openrun.session_token이다. 
// apps/api/src/users/user-session.ts
const COOKIE_NAME = 'openrun.session_token';
// __Secure- 접두사를 붙이면 브라우저가 Secure 쿠키로만 받는다.
const SECURE_COOKIE_PREFIX = '__Secure-';

const useSecureCookies = shouldUseSecureCookies(); // 운영에서만 true
// ...
cookie: {
  name: useSecureCookies ? `${SECURE_COOKIE_PREFIX}${COOKIE_NAME}` : COOKIE_NAME,
  domain: readCookieDomain(),
  secure: useSecureCookies,
},

이름이 __Secure-로 시작하는 쿠키는 브라우저가 Secure 속성이 있고 HTTPS 응답에서 온 것만 받아 준다(01 문서의 쿠키 접두사). 같은 이름의 쿠키가 세 경로로 들어올 때 브라우저가 하는 일은 이렇다.

우리 API의 정상 응답 (HTTPS, Secure 있음) __Secure-openrun.session_token=…; Secure 접두사 검사 저장한다
Secure를 빼먹은 설정 (HTTPS, Secure 없음) __Secure-openrun.session_token=… 접두사 검사 버린다 로그인이 안 되는 것으로 바로 드러난다
누가 http 페이지에서 심으려 할 때 __Secure-openrun.session_token=가짜; Secure 접두사 검사 버린다 HTTPS 응답이 아니다

Better Auth와 같다. Better Auth도 이름이 better-auth.session_token이고, Secure일 때 __Secure-를 붙인다(운영 이름 __Secure-better-auth.session_token).

HttpOnly

HttpOnly 쿠키는 브라우저 쿠키 저장소에 있지만 document.cookie에는 보이지 않는다. 같은 쿠키를 페이지 자바스크립트가 읽을 때와 브라우저가 요청에 실을 때 결과가 다르다.

페이지 자바스크립트가 읽으면 쿠키 저장소openrun.session_token=aB3x… document.cookie ""HttpOnly 쿠키는 빠진다
브라우저가 요청을 보내면 쿠키 저장소openrun.session_token=aB3x… 요청에 싣기 Cookie: openrun.session_token=aB3x…

그래서 스토어나 어드민 페이지에 XSS(공격자의 스크립트가 페이지에서 실행되는 취약점)가 생겨도 스크립트가 토큰을 읽어 공격자 서버로 보낼 수 없다(01 문서의 HttpOnly). 서버 코드는 옵션 한 줄이다. 

// apps/api/src/auth/session-manager.ts
private buildCookieOptions() {
  return {
    httpOnly: true,
    sameSite: 'lax',
    path: '/',
    // ...
  };
}

프론트엔드는 토큰 없이 어떻게 로그인 상태를 아나

프론트엔드 코드는 토큰을 읽을 필요가 없다. 브라우저가 요청마다 알아서 쿠키를 싣고, 로그인 상태와 사용자 정보는 GET /auth/session 응답 본문으로 받는다(09 문서).

  1. 스토어 페이지 JS
  2. 브라우저
  3. API
  1. fetch('/auth/session', { credentials: 'include' }) 토큰을 모른 채 부른다
  2. GET /auth/session Cookie: openrun.session_token=aB3x… (브라우저가 싣는다)
  3. 200 { "id": 1, "name": "김오픈", … }
  4. 본문만 건넨다 누가 로그인했는지 안다. 토큰은 끝까지 모른다

스토어에는 아직 이 호출이 없다. 화면을 붙일 때 이 모양이 된다. 토큰을 localStorage에 두고 Authorization 헤더로 보내는 방식과 비교하면, 자바스크립트가 토큰에 손댈 수 있는 길이 아예 없다는 점이 다르다.

HttpOnly는 토큰을 훔쳐 가는 것을 막을 뿐이다. XSS 스크립트는 그 페이지 안에서 쿠키가 실린 요청을 보낼 수 있으므로, 사용자가 페이지에 머무는 동안에는 사용자 행세를 할 수 있다. XSS 자체를 막는 일은 따로 필요하다.

Secure

Secure 쿠키는 HTTPS 요청에만 실린다(01 문서의 Secure). 카페 와이파이처럼 누군가 통신을 엿볼 수 있는 곳에서 http 주소로 한 번만 요청해도 쿠키가 평문으로 새어 나가는 일을 막는다.

① 운영: https 주소로 요청
https://store.openrun.example.com
내 예매 내역을 연다
GET /me (암호화됨)
api.openrun.example.com쿠키 주인
HTTPS → 쿠키가 실린다
  • Secure 쿠키
② 누가 http 주소로 유도했을 때
http://openrun.example.com
카페 와이파이에서 http 링크를 눌렀다
GET / (평문)
openrun.example.com엿보는 사람에게도 보인다
HTTP → 쿠키를 싣지 않는다
  • Secure 쿠키

로컬은 http://localhost라서 Secure를 켜면 쿠키를 쓸 수 없다. 그래서 환경에 따라 한 값으로 켜고 끈다.

운영 NODE_ENV=production shouldUseSecureCookies() trueSecure 켬 + 이름에 __Secure-
로컬 NODE_ENV=development shouldUseSecureCookies() falseSecure 끔 + 접두사 없음 
// apps/api/src/config/env.ts
export function shouldUseSecureCookies(source = process.env): boolean {
  return source.NODE_ENV === 'production';
}

// apps/api/src/users/user-session.ts
const useSecureCookies = shouldUseSecureCookies();
cookie: {
  name: useSecureCookies ? `${SECURE_COOKIE_PREFIX}${COOKIE_NAME}` : COOKIE_NAME, // 접두사
  secure: useSecureCookies, // Secure 속성
  // ...
},

Secure 속성과 접두사가 같은 secure 값 하나에서 나온다. 그래서 "접두사는 있는데 Secure가 없는" 조합은 생길 수 없다. 브라우저에 따라 localhost를 예외로 받아 주기도 하지만 모두 그렇지는 않으므로, 로컬에서는 끄는 쪽으로 정했다.

SameSite=Lax

SameSite는 다른 사이트에서 시작된 요청에 쿠키를 실을지 정한다(01 문서의 SameSite). 여기서 사이트는 등록 가능한 도메인 단위라, openrun.example.com(스토어), api.openrun.example.com, admin.openrun.example.com은 모두 같은 사이트다. 로컬의 localhost:3000과 localhost:3001도 같은 사이트다.

우리 사이트에 로그인해 둔(브라우저에 우리 쿠키가 있는) 사용자가 여러 페이지에서 우리 서버로 요청을 보내는 경우다.

① 스토어 화면이 API를 부른다
https://openrun.example.com/shows
페이지가 내 정보를 불러온다
fetch GET /me
api.openrun.example.com쿠키 주인
같은 사이트
  • Strict
  • Lax
  • None
② 카카오톡 링크를 눌러 들어온다
https://kakao.com
친구가 보낸 공연 링크를 누른다
링크 이동 GET /shows/1
openrun.example.com쿠키 주인
다른 사이트, 사용자가 직접 이동
  • Strict
  • Lax
  • None
③ 악성 페이지가 몰래 요청한다
https://evil.com
숨은 폼, fetch, <img>가 저절로 요청한다
폼 POST /me/…
api.openrun.example.com쿠키 주인
다른 사이트, 사용자 몰래
  • Strict
  • Lax
  • None
  • Strict가 아닌 이유: 공연 링크를 친구에게 받아 눌렀는데 첫 화면이 로그아웃 상태로 그려지면 이상하다. 스토어 서버가 그 첫 요청에서 쿠키를 받아야 로그인 상태로 화면을 그릴 수 있다. 실제 예매 서비스들도 링크로 들어왔을 때 로그인이 유지된다.
  • None이 아닌 이유: 다른 사이트가 보내는 요청에 쿠키를 실어 줄 이유가 없다. None이면 CSRF(사용자 모르게 다른 사이트가 요청을 보내게 하는 공격) 방어를 SameSite에서 전혀 얻지 못한다.

Lax가 막지 못하는 것

Lax는 CSRF의 큰 부분을 막지만 전부는 아니다.

  • 같은 사이트 안에서 오는 요청. SameSite는 사이트 단위라, 같은 상위 도메인의 다른 서브도메인(예: admin.)이나 그 아래 어떤 페이지에서 보낸 요청은 다른 곳으로 보지 않는다.
  • 최상위 GET 이동. 링크를 누르는 이동에는 쿠키가 실리므로, 상태를 바꾸는 GET API가 있으면 링크 하나로 실행된다. 그래서 상태를 바꾸는 API는 GET으로 만들지 않는다.
  • SameSite를 지원하지 않는 오래된 브라우저.

이 빈틈은 요청의 Origin 헤더를 검사해 막는다. 이 검사와 CORS 설정은 아직 없고 #72에서 더한다(아래).

Path=/

Path는 쿠키를 실을 요청 경로의 시작 부분이다. 브라우저는 요청 경로가 Path로 시작할 때만 쿠키를 싣는다. API의 모든 경로에 쿠키가 실려야 하므로 /다.

요청 경로 Path=/ (지금) Path=/auth였다면
/auth/session✓ 실린다✓ 실린다
/me✓ 실린다✕ 안 실린다 → 401
/orders/1 (앞으로)✓ 실린다✕ 안 실린다 → 401

Express의 기본값도 /지만 굳이 적었다. 쿠키를 지울 때 Path가 같아야 하는데(아래), 기본값에 기대지 않고 한 함수에 드러내 두면 내릴 때와 지울 때 같은 값이 쓰인다는 것이 코드에서 보인다. 

// apps/api/src/auth/session-manager.ts
private setCookie({ response, value, policy }) {
  response.cookie(this.options.cookie.name, value, { ...this.buildCookieOptions(), /* maxAge */ });
}
private clearCookie(response) {
  response.clearCookie(this.options.cookie.name, this.buildCookieOptions());
}
private buildCookieOptions() {
  return { httpOnly: true, sameSite: 'lax', path: '/', /* secure, domain */ };
}

내릴 때(setCookie)와 지울 때(clearCookie) 모두 buildCookieOptions()에서 path: '/'를 가져간다.

Domain: 스토어 서버 렌더링을 위해

Domain이 없는 쿠키는 쿠키를 내린 호스트(api.openrun.example.com)에만 실린다. Domain=openrun.example.com을 주면 그 도메인과 모든 서브도메인에 실린다(01 문서의 Domain).

  1. 브라우저
  2. 스토어 서버 (Next.js)
  3. API 서버
  1. Domain=openrun.example.com 이라서
  2. GET openrun.example.com/shows/12 Cookie: __Secure-openrun.session_token=…
  3. GET /auth/session 받은 쿠키를 그대로 실어 보낸다
  4. { name: '김오픈', … }
  5. 로그인한 헤더가 그려진 HTML
  6. Domain이 없었다면
  7. GET openrun.example.com/shows/12 쿠키 없음. api. 호스트 전용이라 실리지 않는다
  8. 로그아웃 상태로 HTML을 그림 브라우저에서 다시 조회해 헤더가 바뀌며 깜빡인다

스토어는 Next.js 서버 렌더링이라, 브라우저가 스토어 서버에 페이지를 요청할 때 쿠키가 함께 와야 서버가 API에 세션을 물어보고 로그인한 화면을 바로 그릴 수 있다. 그래서 사용자 세션 쿠키는 상위 도메인에 굽는다(ADR 0009의 결과 절). 스토어 서버가 쿠키를 API로 넘기는 코드는 스토어 로그인 화면과 헤더(#73)에서 더한다.

로컬에서는 스토어(localhost:3001)와 API(localhost:3000)가 포트만 다르다. 쿠키는 포트를 가리지 않으므로 Domain 없이도 둘 다에 실린다. 그래서 apps/api/.env.example의 COOKIE_DOMAIN은 비어 있고, readCookieDomain은 빈 문자열을 undefined로 바꿔 Domain 속성을 아예 빼게 한다.

상위 도메인에 구운 쿠키는 그 아래 모든 서브도메인에 간다. admin.도 사용자 세션 쿠키를 받는다. 어드민이 사용자 쿠키를 읽지 않게 하는 것은 API가 맡는다. /admin/* 경로에서는 운영자 쿠키만 읽는다(ADR 0010).

로그인 상태 유지와 Max-Age

로그인 요청의 rememberMe에 따라 세션 정책이 갈리고, 정책의 persistentCookie가 쿠키의 Max-Age를 정한다.

rememberMe 서버 세션 만료 (expiresInMs) 연장 (kind, updateAgeMs) 쿠키
true 7일 'sliding'. 마지막 연장 뒤 1일이 지난 첫 요청에서 다시 7일 Max-Age=604800. 연장할 때 다시 내려 7일로 늘린다
false 1일 'fixed'. 하지 않음 Max-Age 없음. 브라우저를 닫으면 사라진다

쿠키에도 수명이 있고 서버 세션에도 만료가 있다. 둘을 시간 막대에 함께 놓아 보자. 켠 경우는 1.5일째에 요청이 한 번 있었다고 가정한다.

켬: 서버 세션sessions.expires_at
처음 만료 7일 연장한 만료 요청: 연장
켬: 쿠키Max-Age
Max-Age 7일 다시 내린 쿠키 7일 Set-Cookie
끔: 서버 세션
1일 만료
끔: 쿠키Max-Age 없음
사용 중 탭 복원 시 남기도 브라우저 닫음
  • 켠 경우에는 쿠키 수명과 서버 만료를 같은 7일로 맞추고, 연장할 때 둘을 함께 늘린다. 쿠키만 먼저 사라지거나 쿠키는 남았는데 서버 세션만 끝나는 엇갈림이 줄어든다. 연장 계산은 06 문서에 있다.
  • 끈 경우 쿠키에 Max-Age가 없으면 "세션 쿠키"가 되어 브라우저를 닫을 때 지워진다. 공용 PC에서 로그인 상태 유지를 끄는 이유가 이것이다. 그런데 요즘 브라우저는 "닫기 전 탭 다시 열기"를 켜 두면 세션 쿠키까지 되살리기도 한다. 쿠키 수명만 믿을 수 없으므로 서버 세션에도 1일 만료를 둬, 쿠키가 살아 있어도 1일이 지나면 세션이 끝나게 한다.

Better Auth와 다르다. Better Auth는 로그인 상태 유지를 끈 사실을 별도의 서명 쿠키 dont_remember로 들고 다닌다. 이 저장소는 세션 행의 remember_me 칸에 둔다. 쿠키가 하나로 줄고, 정책을 고를 때 DB에서 읽은 세션 행만 보면 된다(ADR 0009).

clearCookie에 같은 옵션을 넘기는 이유

HTTP에는 "쿠키 지우기" 명령이 따로 없다. 같은 쿠키를 이미 지난 만료로 다시 내려 브라우저가 지우게 한다. Express의 clearCookie가 내리는 헤더는 이렇다(로컬). 

Set-Cookie: openrun.session_token=; Path=/; Expires=Thu, 01 Jan 1970 00:00:00 GMT; HttpOnly; SameSite=Lax

브라우저는 쿠키를 이름, Domain, Path의 조합으로 구분한다. 지우는 헤더의 Domain이나 Path가 다르면 브라우저는 그것을 "다른 쿠키"로 보고, 원래 쿠키는 그대로 남는다.

지우는 헤더 결과 (운영)
buildCookieOptions()를 그대로 넘김 (지금 코드) Domain, Path가 같아 원래 쿠키가 지워진다
옵션 없이 clearCookie(name) Domain이 없어 api. 호스트 전용 쿠키를 지우려는 헤더가 된다. 상위 도메인의 원래 쿠키는 남는다. 게다가 __Secure- 이름인데 Secure가 없어 브라우저가 헤더 자체를 무시한다

로그아웃했는데 쿠키가 남아 있으면 서버의 세션 행은 지워졌어도 브라우저는 계속 그 쿠키를 보낸다. 세션을 못 찾아 로그인되지는 않지만, 요청마다 DB를 조회하고 쿠키를 지우려는 헛수고가 반복된다. 그래서 setCookie와 clearCookie가 같은 buildCookieOptions를 쓰게 했다.

아직 없는 것: CSRF 방어와 운영자 쿠키

CSRF 방어와 CORS (#72)

CSRF 토큰은 쓰지 않는다. 변경 요청은 SameSite=Lax, Origin 헤더 검사, JSON 본문만 받기의 세 겹으로 막는다(ADR 0009). 이 문서의 SameSite가 첫 겹이고, Lax가 막지 못하는 것을 나머지 두 겹이 막는다. 스토어가 API를 쿠키와 함께 부를 수 있게 하는 credentials 허용 CORS도 그때 더한다. 개념은 01 문서의 CSRF, CORS, Origin 절에 있다.

운영자 쿠키 (#82)

운영자 세션은 사용자 세션과 같은 SessionManager를 쓰되 쿠키 설정이 다르다(ADR 0010).

사용자 세션 (지금) 운영자 세션 (#82 예정)
쿠키 이름 openrun.session_token 다른 이름
Domain 상위 도메인 (스토어 서버 렌더링) 없음. api. 호스트에만 실린다. 어드민은 SPA라 서버에서 쿠키를 읽을 일이 없다
만료 7일(연장) 또는 1일 30분 동안 요청이 없으면 만료. 로그인 상태 유지 없음
읽는 경로 /admin/* 밖 /admin/*만

스토어와 admin.은 같은 사이트라 SameSite가 둘 사이의 요청을 막아 주지 못한다. 어드민 API의 CSRF 방어는 Origin 검사가 맡는다(ADR 0010).
