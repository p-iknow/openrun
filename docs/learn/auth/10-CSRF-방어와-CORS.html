10 CSRF 방어와 CORS

쿠키로 인증하는 API를 다른 사이트가 몰래 부르지 못하게 막고, 스토어와 어드민은 쿠키를 실어 부를 수 있게 하는 apps/api/src/cross-origin/을 케이스별로 정리한다. 케이스마다 어떤 공격이나 요구가 있고, 어느 미들웨어가 어떤 헤더를 보고 무슨 응답을 내는지 적는다. CSRF, CORS, 출처와 사이트, SameSite 개념은 01 문서에 있고, 이 문서는 이 저장소의 규칙과 코드만 다룬다.

한눈에 보기

CSRF 토큰은 쓰지 않는다(ADR 0009). 대신 세 가지 방어로 막는다. 쿠키의 SameSite=Lax는 07 문서에서 이미 붙였고, 이 문서의 미들웨어가 나머지 두 방어와 CORS를 더한다.

방어 어디서 막는 것
SameSite=Lax 브라우저(쿠키 속성) 다른 사이트에서 시작된 POST에 쿠키를 싣지 않는다
Origin 검사 OriginCheckMiddleware 요청을 보낸 출처가 그 경로의 허용 출처가 아니면 403 ORIGIN_NOT_ALLOWED
JSON 본문만 받기 JsonBodyMiddleware 폼처럼 preflight 없이 보낼 수 있는 본문 형식을 415로 거절한다

CORS(CorsMiddleware)는 방어가 아니다. 허용한 두 출처가 쿠키를 실은 요청의 응답을 읽게 해 준다.

환경 변수 로컬 값 쓰이는 곳
STORE_ORIGIN http://localhost:3001 CORS 허용, /admin/* 밖 경로의 변경 요청 허용 출처
ADMIN_ORIGIN http://localhost:3002 CORS 허용, /admin/* 변경 요청 허용 출처

둘 다 AllowedOrigins 프로바이더가 부팅 때 읽는다. 없거나 http://localhost:3001/처럼 경로나 끝의 /가 붙으면 부팅하지 않는다. 브라우저가 보내는 Origin과 글자 그대로 비교하기 때문이다.

미들웨어 세 개와 순서

// cross-origin.module.ts
consumer
  .apply(CorsMiddleware, OriginCheckMiddleware, JsonBodyMiddleware)
  .forRoutes('{*splat}');
  1. CorsMiddleware허용 출처면 CORS 헤더를 붙인다. preflight(OPTIONS)는 여기서 204로 끝낸다
    막지 않는다허용하지 않은 출처는 헤더만 빼고 다음으로 넘긴다
  2. OriginCheckMiddlewareGET, HEAD, OPTIONS 밖의 요청만 본다
    403 ORIGIN_NOT_ALLOWED출처가 허용 출처가 아니다
  3. JsonBodyMiddleware본문이 있는 변경 요청만 본다
    415 UNSUPPORTED_MEDIA_TYPE본문이 application/json이 아니다
  4. 컨트롤러
  • CORS가 먼저: preflight에는 쿠키도 본문도 없다. 뒤의 검사보다 먼저 응답해야 브라우저가 본 요청을 보낼 수 있다.
  • Origin이 JSON보다 먼저: 다른 출처의 폼 제출은 "출처가 틀렸다"(403)가 원인이다. 415보다 먼저 알려 주는 게 맞다.
  • main.ts의 enableCors가 아닌 이유: 통합 테스트는 main.ts를 거치지 않고 AppModule로 앱을 만든다. 모듈의 미들웨어여야 테스트 앱에도 같은 규칙이 붙어 HTTP 경계에서 검증할 수 있다.
  • '{*splat}': 루트(/)까지 포함한 모든 경로다. 다만 Nest 미들웨어는 컨트롤러에 없는 경로에는 붙지 않아, 없는 경로는 검사 없이 404가 된다. 실행될 핸들러가 없으니 문제없다.

① 다른 사이트의 폼 제출

문제: 로그인한 사용자가 evil.com을 열면, 숨은 폼이 API로 POST를 보낸다. 브라우저가 세션 쿠키를 실어 주면 서버는 사용자가 보낸 요청으로 착각한다.

evil.com의 숨은 폼
https://evil.com
<form method="post" action="https://api.openrun.com/auth/sign-out"> 자동 제출
POST /auth/sign-out
api.openrun.comOrigin: https://evil.com
다른 사이트 → 쿠키 없음, 출처 불일치
  • SameSite=Lax
  • Origin 검사

해결:

  • evil.com과 openrun.com은 다른 사이트라 SameSite=Lax가 쿠키를 뺀다. 쿠키가 없으니 피해자 권한으로 실행되지 않는다.
  • 쿠키가 실리는 환경(SameSite를 모르는 오래된 브라우저 등)이어도 Origin: https://evil.com이 허용 출처가 아니라 403이다.

테스트: 허용 목록에 없는 Origin은 403 ORIGIN_NOT_ALLOWED다

② 같은 사이트의 서브도메인

문제: SameSite는 출처가 아니라 사이트(등록 가능한 도메인)로 판단한다. 사용자 콘텐츠를 올리는 서브도메인이나 탈취된 서브도메인은 스토어와 같은 사이트다. 게다가 사용자 세션 쿠키는 스토어 서버 렌더링을 위해 상위 도메인에 굽는다(07 문서).

호스트 사이트 출처
store.openrun.com 모두 openrun.com → SameSite=Lax 쿠키가 실린다 허용 출처(STORE_ORIGIN)
api.openrun.com API
evil.openrun.com 허용 출처 아님

해결: Origin 검사가 출처를 글자 그대로 비교한다. https://evil.openrun.com은 STORE_ORIGIN과 같지 않으니 403이다. SameSite가 막지 못하는 이 경우가 Origin 검사가 있는 가장 큰 이유다. 

const hasCookie = Boolean(request.get('cookie'));
if (hasCookie && getRequestOrigin(request) !== allowed) {
  throw createOriginNotAllowedException();
}

쿠키가 유효한 세션인지는 보지 않는다. 쿠키가 실렸는지만 본다. 세션을 DB에서 읽기 전에, 싸게 막을 수 있는 것을 먼저 막는다.

③ 스토어 출처로 어드민 API

문제: 스토어와 어드민은 같은 사이트라 SameSite가 둘 사이를 막지 못한다. 스토어에 XSS가 생기면 스토어 페이지의 스크립트가 어드민 API를 부를 수 있다.

해결: 허용 출처를 경로마다 하나로 정한다.

// allowed-origins.ts
getOriginFor(pathname: string): string {
  return isAdminPath(pathname) ? this.admin : this.store;
}
경로 STORE_ORIGIN에서 ADMIN_ORIGIN에서
/admin/* 403 통과
나머지 통과 403

CORS는 두 출처 모두에 연다. 경로별 제한은 CORS가 아니라 Origin 검사가 맡는다. CORS는 응답을 읽게 할지만 정할 뿐, 폼처럼 preflight 없는 요청이 서버에 닿는 것은 막지 못하기 때문이다(⑥).

경로 판단은 request.path가 아니라 원래 URL의 경로(getPathname)로 한다. Nest가 미들웨어를 경로에 마운트하면 request.path에는 마운트 뒤의 나머지만 남아 /admin이 사라진다.

④ Origin이 없는 쿠키 요청

문제: 오래된 브라우저나 일부 같은 출처 요청은 Origin을 보내지 않는다. 그렇다고 Origin이 없는 요청을 통과시키면, Origin을 빼는 방법을 찾은 공격이 그대로 지나간다.

해결: Origin이 없으면 Referer의 출처를 쓰고, 둘 다 없으면 막는다.

function getRequestOrigin(request: Request): string | null {
  const origin = request.get('origin');
  if (origin) {
    return origin;
  }
  const referer = request.get('referer');
  return referer ? (URL.parse(referer)?.origin ?? null) : null;
}
쿠키 요청의 헤더 판단에 쓰는 출처 결과
Origin: http://store… Origin 통과
Referer: http://store…/login만 Referer의 출처 통과
Origin: null "null"(허용 출처와 다름) 403
둘 다 없음 null 403

Origin: null은 sandbox iframe이나 일부 리다이렉트에서 브라우저가 보내는 값이다. 어디서 왔는지 알 수 없다는 뜻이니 허용하지 않는다.

⑤ 로그인 CSRF

문제: 공격자가 피해자의 브라우저를 공격자 계정으로 로그인시킨다. 피해자는 자기 계정인 줄 알고 결제 정보나 개인정보를 입력하고, 그 정보가 공격자 계정에 쌓인다. 로그인 요청에는 쿠키가 없어서 ②의 쿠키 검사에 걸리지 않는다.

공격 시나리오

  1. 공격자가 준비한다 openrun에 자기 계정(attacker@evil.com)을 만들고, 자기 사이트에 숨은 로그인 폼을 둔다. 
<!-- evil.com/이벤트 페이지 -->
<form method="post" action="https://api.openrun.com/auth/sign-in">
  <input name="email" value="attacker@evil.com" />
  <input name="password" value="공격자 비밀번호" />
</form>
<script>document.forms[0].submit()</script>
  1. 피해자를 끌어들인다 "뮤지컬 티켓 추첨 이벤트" 같은 링크를 메신저나 커뮤니티에 뿌린다. 피해자가 열면 폼이 자동으로 제출된다. 피해자가 로그아웃 상태든 다른 계정으로 로그인한 상태든 상관없다.
  2. 피해자 브라우저가 공격자 계정으로 로그인된다 API가 로그인에 성공해 Set-Cookie로 공격자 계정의 세션 쿠키를 피해자 브라우저에 굽는다. 공격자가 페이지를 openrun으로 다시 넘기면 피해자는 평소처럼 쓴다. 헤더에 이름이 작게 보일 뿐이라 대부분 알아채지 못한다.
  3. 피해자가 정보를 남긴다 예매하며 이름, 휴대폰 번호, 티켓 배송 주소, 생년월일을 입력한다. 결제 수단을 등록하거나 본 공연, 좌석, 관심 공연 기록이 쌓인다.
  4. 공격자가 가져간다 공격자는 자기 계정으로 정상 로그인해 마이페이지에서 이 정보를 본다. 결제 수단이 계정에 남아 있으면 그것으로 결제를 시도할 수도 있다.
일반 CSRF 로그인 CSRF
쓰는 세션 피해자의 세션 공격자의 세션
요청에 쿠키 있음 없음(로그인 요청이라)
피해 피해자 권한으로 무언가를 실행한다 피해자가 입력한 정보가 공격자에게 넘어간다

2008년 스탠퍼드의 CSRF 방어 연구(Barth, Jackson, Mitchell, "Robust Defenses for Cross-Site Request Forgery")가 이 공격으로 Google 검색 기록과 PayPal 결제 정보를 빼낼 수 있다고 보였다. 그 뒤로 로그인 폼에도 CSRF 방어를 거는 것이 보통이 되었다.

막는 방법

해결: 쿠키 없는 로그인·가입 요청(/auth/sign-in, /auth/sign-up와 그 /admin 경로)만 따로 검사한다. Better Auth의 formCsrfMiddleware와 같은 규칙이다. 

if (
  !hasCookie &&
  isAuthEntryPath(pathname) &&
  isForgedAuthEntryRequest({ request, allowed })
) {
  throw createOriginNotAllowedException();
}

function isForgedAuthEntryRequest({ request, allowed }): boolean {
  const isCrossSiteNavigation =
    request.get('sec-fetch-site') === 'cross-site' &&
    request.get('sec-fetch-mode') === 'navigate';
  const origin = request.get('origin');
  return isCrossSiteNavigation || (!!origin && origin !== allowed);
}
조건 뜻
Sec-Fetch-Site: cross-site + Sec-Fetch-Mode: navigate 다른 사이트의 페이지가 폼 제출이나 이동으로 보냈다
Origin이 있는데 허용 출처와 다름 다른 출처의 페이지가 보냈다(fetch든 폼이든)

두 헤더 모두 브라우저만 붙이는 헤더(forbidden header)라 페이지의 스크립트가 바꿀 수 없다. 실제 브라우저의 폼 제출은 둘을 함께 보내지만, 테스트는 분기마다 따로 검증하려고 하나씩만 넣는다.

쿠키 요청과 다른 점: Origin이 없으면 통과시키고, Referer로 대신 판단하지 않는다. 쿠키가 없으면 빼앗을 세션이 없고, curl이나 서버 간 호출처럼 Origin 없는 정상 요청도 받아야 하기 때문이다. 그래서 "다른 사이트에서 왔다"는 증거가 있을 때만 막는다.

Better Auth는 신뢰 출처 전체와 맞춰 보지만, 여기서는 경로별 허용 출처와 맞춰 본다. 어드민 로그인은 어드민 출처에서만, 사용자 로그인과 가입은 스토어 출처에서만 받는다(ADR 0009의 "Better Auth와 다르게 정한 것").

Origin도 Sec-Fetch도 보내지 않는 아주 오래된 브라우저는 이 검사를 지나간다. 그래도 폼으로는 JSON을 보낼 수 없어 415가 되므로(⑥) 남는 틈은 좁다.

⑥ text/plain 본문의 fetch

문제: 공격 페이지가 fetch(url, { method: 'POST', body: '...', credentials: 'include' })로 text/plain 본문을 보낸다. text/plain, application/x-www-form-urlencoded, multipart/form-data는 단순 요청이라 preflight 없이 서버에 바로 닿는다. CORS는 응답을 못 읽게 할 뿐 실행은 막지 못한다.

해결: 미들웨어를 차례로 지나며 이렇게 막힌다.

  • CorsMiddleware 허용하지 않은 출처 → CORS 헤더 없이 다음으로
  • OriginCheckMiddleware
    • 쿠키가 실림 403 출처 불일치
    • 쿠키 없음, 로그인·가입 403 출처 불일치
    • 쿠키 없음, 그 밖의 경로 통과
  • JsonBodyMiddleware 415 application/json이 아님 
// json-body.middleware.ts
if (!isSafeMethod(request) && hasBody(request) && !request.is('application/json')) {
  throw new ProblemException({ status: 415, code: 'UNSUPPORTED_MEDIA_TYPE', ... });
}

아래 두 처리는 모두 정상 요청을 415로 잘못 막지 않으려고 있다.

charset=utf-8이 붙은 JSON

스토어의 로그인 요청은 이렇게 보낸다.

fetch('https://api.openrun.com/auth/sign-in', {
  method: 'POST',
  credentials: 'include',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ email, password, rememberMe }),
});

HTTP 클라이언트 라이브러리나 도구에 따라 Content-Type: application/json; charset=utf-8처럼 문자 인코딩을 덧붙이기도 한다(테스트에 쓰는 supertest도 그렇다). ; 뒤는 매개변수라 같은 JSON이다. 문자열을 그대로 비교하면 이 요청이 415가 된다. 

request.get('content-type') === 'application/json' // 'application/json; charset=utf-8' → false → 415 (잘못 막힘)
request.is('application/json')                      // 매개변수를 떼고 비교 → 맞음 → 통과

본문 없는 POST(로그아웃)

로그아웃은 보낼 데이터가 없다.

fetch('https://api.openrun.com/auth/sign-out', { method: 'POST', credentials: 'include' });

브라우저는 본문 없는 POST에 Content-Length: 0을 붙이고, 형식이 없으니 Content-Type은 보내지 않는다.

POST /auth/sign-out
Content-Length: 0
(Content-Type 없음)

본문이 없으니 막을 이유가 없다. 그런데 request.is()는 Content-Length 헤더가 있으면 값이 0이어도 본문이 있다고 보고, Content-Type이 없으니 JSON이 아니라고 판단한다. 그래서 hasBody로 Content-Length: 0을 먼저 "본문 없음"으로 걸러 낸다.

요청 request.is()만 볼 때 hasBody를 먼저 볼 때
로그아웃(Content-Length: 0, Content-Type 없음) JSON 아님 → 415(잘못 막힘) 본문 없음 → 통과
로그인(JSON 본문) 통과 통과
공격 폼(text/plain 본문) 415 본문 있음, JSON 아님 → 415 
function hasBody(request: Request): boolean {
  const contentLength = request.get('content-length');
  return (
    request.get('transfer-encoding') !== undefined ||      // 길이를 미리 알리지 않고 조각으로 보내는 본문
    (contentLength !== undefined && contentLength !== '0') // 길이가 0보다 큰 본문
  );
}

처음에는 이 확인 없이 구현했는데, 로그아웃 테스트가 415로 실패해서 넣었다.

⑦ JSON 본문의 fetch

문제: 공격 페이지가 Content-Type: application/json으로 보내면 415는 피한다.

해결: application/json은 단순 요청이 아니라서 브라우저가 먼저 preflight(OPTIONS)를 보낸다. CorsMiddleware가 허용하지 않은 출처의 preflight에 CORS 헤더를 주지 않으니, 브라우저는 본 요청을 아예 보내지 않는다. JSON만 받는 규칙이 CORS를 방어로 바꿔 주는 셈이다.

⑧ 허용한 출처가 응답을 읽기

요구: 스토어(store.)와 API(api.)는 출처가 다르다. 스토어 브라우저 코드가 credentials: 'include'로 API를 부르고 응답을 읽으려면, 서버가 그 출처와 credentials를 허락해야 한다.

해결: 허용한 출처에만 CORS 헤더를 붙인다.

// cors.middleware.ts
this.handler = cors((request, callback) => {
  const origin = request.headers.origin;
  callback(
    null, // 오류 자리. 실패할 일이 없어 늘 null이다
    origin && origins.has(origin)
      ? { origin, credentials: true }
      : { origin: false },
  );
});

요청은 다음 미들웨어로 가고, 브라우저는 응답을 막는다

  • 옵션을 요청마다 고르는 이유: cors({ origin: [...], credentials: true })처럼 고정하면 cors는 허용하지 않은 출처에도 Access-Control-Allow-Credentials를 붙인다.
  • *를 쓰지 않는 이유: credentials를 허용하는 응답에는 브라우저가 Access-Control-Allow-Origin: *를 받아 주지 않는다. 출처를 하나 골라 돌려줘야 한다.
  • Vary: Origin: 출처마다 다른 Access-Control-Allow-Origin을 돌려주므로, 캐시가 출처별로 응답을 나눠 저장하라는 표시다. 없으면 CDN이 스토어용 응답을 어드민에 줘서 어드민이 응답을 읽지 못할 수 있다. cors 패키지가 origin에 문자열을 넘기면 붙여 준다.
  • 허용하지 않은 출처를 오류로 넘기지 않는 이유: callback(new Error())는 500이 된다. 응답을 막는 건 브라우저의 일이니 서버는 헤더만 뺀다.

⑨ GET 요청

규칙: GET, HEAD, OPTIONS는 Origin 검사도 JSON 검사도 하지 않는다(isSafeMethod). 다른 사이트의 <img src>나 링크 이동도 GET을 보내고, SameSite=Lax는 최상위 GET 이동에 쿠키를 싣는다. 이 요청들을 막으면 스토어로 들어오는 링크까지 깨진다.

그래서 GET으로 상태를 바꾸지 않는다는 것이 이 방어 전체의 전제다. GET 이동은 쿠키가 실리고, Origin을 보내지 않고, 본문도 없어 세 방어를 모두 비켜 간다(01 문서의 CSRF). 다른 출처가 GET 응답을 읽는 것은 CORS가 막는다.

⑩ curl과 서버 간 호출

curl은 Origin이든 Sec-Fetch-Site든 마음대로 넣고 뺄 수 있다. 그래도 괜찮다. CSRF는 브라우저가 피해자의 쿠키를 자동으로 실어 줄 때만 성립하는 공격이다. curl을 쓰는 사람은 자기 쿠키로 자기 계정을 다룰 뿐이다. Origin 검사는 브라우저가 정직하게 붙이는 헤더로 다른 사이트를 걸러 내는 장치이지, 모든 클라이언트를 막는 장치가 아니다.

  • 남은 위험: curl로 비밀번호를 대량으로 추측하는 무차별 대입은 CSRF 방어로 막을 수 없다. 로그인·가입 요청 속도 제한이 맡고, 10단계에서 Redis와 함께 넣는다.

스스로 확인하기

1. SameSite=Lax 쿠키가 있는데도 Origin 검사가 필요한 경우는?

같은 사이트의 다른 서브도메인에서 온 요청이다. SameSite는 사이트로 판단해 쿠키를 싣지만, Origin 검사는 출처를 글자 그대로 비교해 막는다(②, ③).

2. CORS 헤더를 안 보내도 다른 출처의 요청은 서버에 닿는다. 그러면 CORS가 막는 것은?

다른 출처의 스크립트가 응답을 읽는 것, 그리고 preflight가 필요한 요청(JSON 본문 등)의 본 요청 전송이다. 단순 요청의 실행은 막지 못해서 Origin 검사와 JSON 본문 제한이 필요하다(⑥, ⑦).

3. 쿠키가 실린 요청은 Origin이 없으면 막는데, 쿠키 없는 로그인 요청은 왜 통과시키는가?

쿠키가 없으면 빼앗을 세션이 없고, Origin 없는 정상 요청(curl, 서버 간 호출)도 받아야 한다. 그래서 다른 사이트에서 왔다는 증거(Sec-Fetch, 틀린 Origin)가 있을 때만 막는다(⑤).

4. 이 줄을 지우면 어떤 요청이 깨지는가?

json-body.middleware.ts에서 hasBody 확인을 뺀다.
