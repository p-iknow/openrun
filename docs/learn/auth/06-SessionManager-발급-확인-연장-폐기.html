06 SessionManager: 발급, 확인, 연장, 폐기

인증 코드의 한가운데인 apps/api/src/auth/session-manager.ts를 한 줄씩 읽는다. 로그인하면 세션을 만들고(발급), 요청마다 쿠키로 세션을 찾고(확인), 쓰는 동안 만료를 늦추고(연장), 로그아웃하면 지운다(폐기). 판단 순서는 표와 트리로, 만료와 연장은 시간 막대로, 요청 두 개가 겹치는 상황은 순서도로 본다.

SessionManager가 하는 네 가지 일

SessionManager는 "세션의 규칙"만 아는 클래스다. 어느 테이블에 저장하는지, 만료가 며칠인지, 쿠키 이름이 무엇인지는 모르고 생성자로 받는다. 그래서 사용자 세션과 (앞으로 만들) 운영자 세션이 같은 클래스를 쓴다. 공개 메서드는 issue, authenticate, revoke 셋이고, 연장은 authenticate 안에서 일어난다.

로그인: POST /auth/sign-in
  1. 비밀번호 확인(UsersService)
  2. issue: 행 저장 + 쿠키 굽기
로그인이 필요한 요청: GET /me, GET /auth/session
  1. authenticate: 쿠키 → 행 찾기
  2. 만료면 지우기
  3. 연장할 때면 연장
  4. 세션 또는 null
로그아웃: POST /auth/sign-out
  1. revoke: 행 삭제 + 쿠키 지우기
메서드 누가 부르나 DB에 하는 일 응답에 하는 일
issue AuthController.signIn 이전 세션 행 삭제(있으면), 새 행 INSERT 세션 쿠키 굽기
authenticate 로그인 가드, AuthController.getSession SELECT, 만료면 DELETE, 연장할 때면 UPDATE 만료·없음이면 쿠키 지우기, 연장하면 쿠키 다시 굽기
revoke AuthController.signOut 행 DELETE(있으면) 쿠키 지우기

토큰을 만들고 서명하고 해시하는 함수(createSessionToken, signSessionToken, hashSessionToken, readSignedSessionToken)는 05 문서에서, 쿠키 속성은 07 문서에서 다룬다. 이 문서는 그 함수들을 언제, 어떤 순서로 부르는지에 집중한다.

세션 정책 두 가지

로그인할 때 사용자가 고른 "로그인 상태 유지(rememberMe)"에 따라 세션의 수명 규칙이 달라진다. 이 규칙 묶음을 정책(SessionPolicy)이라고 부르고, 사용자 쪽 파일 users/user-session.ts에 둔다. 

// apps/api/src/auth/session-manager.ts
/** 세션 하나의 만료와 연장 규칙. */
export interface SessionPolicy {
  expiresInMs: number;
  /** 마지막 연장 뒤 이만큼 지난 첫 요청에서 만료를 지금부터 expiresInMs로 다시 쓴다. null이면 연장하지 않는다. */
  updateAgeMs: number | null;
  /** true면 쿠키에 Max-Age(expiresInMs)를 둔다. false면 브라우저를 닫을 때 사라지는 쿠키다. */
  persistentCookie: boolean;
}
// apps/api/src/users/user-session.ts
const DAY_MS = 24 * 60 * 60 * 1000;

// 로그인 상태 유지를 켜면 7일 동안 유지하고, 마지막 연장 뒤 1일이 지난 첫 요청에서 다시 7일로 연장한다(Better Auth와 같음).
const REMEMBERED_POLICY: SessionPolicy = {
  expiresInMs: 7 * DAY_MS,
  updateAgeMs: DAY_MS,
  persistentCookie: true,
};
// 끄면 1일 뒤 끝나고 연장하지 않는다. 쿠키에 Max-Age가 없어 브라우저를 닫으면 사라진다.
const NOT_REMEMBERED_POLICY: SessionPolicy = {
  expiresInMs: DAY_MS,
  updateAgeMs: null,
  persistentCookie: false,
};
로그인 상태 유지 켬 로그인 상태 유지 끔
expiresInMs (유지 기간) 7일 1일
updateAgeMs (연장 간격) 1일: 마지막 연장 뒤 1일이 지난 첫 요청에서 다시 7일로 null: 연장하지 않음
persistentCookie true: 쿠키에 Max-Age 7일 false: 브라우저를 닫으면 사라지는 쿠키
결과 7일 안에 한 번이라도 쓰면 계속 로그인돼 있다 길어야 1일, 브라우저를 닫으면 그 전에 끝난다

세션마다 정책이 다르므로 SessionManager는 정책 하나를 받지 않고 세션을 보고 정책을 고르는 함수 getPolicy를 받는다. 발급할 때는 요청 본문의 rememberMe로, 확인할 때는 DB 행에 저장해 둔 rememberMe로 같은 함수를 부른다. 

// apps/api/src/users/user-session.ts
      getPolicy: ({ rememberMe }) =>
        rememberMe ? REMEMBERED_POLICY : NOT_REMEMBERED_POLICY,

issue: 발급

AuthController.signIn이 비밀번호를 확인해 사용자 id를 얻은 뒤 부른다. 여기서 subjectId는 "이 세션의 주인"이다. 사용자 세션이면 사용자 id, 운영자 세션이면 운영자 id가 된다. 

// apps/api/src/auth/session-manager.ts
  /** 새 세션을 만들고 쿠키를 내린다. 요청에 이전 세션 쿠키가 있으면 그 세션은 지운다. */
  async issue({
    request,
    response,
    subjectId,
    rememberMe,
  }: {
    request: Request;
    response: Response;
    subjectId: number;
    rememberMe: boolean;
  }): Promise<void> {
    const { store, secret, clock, getPolicy } = this.options;
    const previousToken = this.readToken(request);
    if (previousToken) {
      await store.deleteByTokenHash(hashSessionToken(previousToken));
    }

    const token = createSessionToken();
    const policy = getPolicy({ rememberMe });
    await store.create({
      tokenHash: hashSessionToken(token),
      subjectId,
      expiresAt: new Date(clock.now().getTime() + policy.expiresInMs),
      rememberMe,
      ipAddress: request.ip ?? null,
      userAgent: request.get('user-agent') ?? null,
    });
    this.setCookie({
      response,
      value: signSessionToken({ token, secret }),
      policy,
    });
  }
  1. 이전 세션 쿠키가 있으면 그 행을 지운다 (92-95행) 로그인한 채로 다시 로그인하면 브라우저에는 이전 쿠키가 실려 온다. 새 쿠키가 이전 쿠키를 덮어쓰므로, 이전 행을 그대로 두면 아무도 쓰지 않는 세션이 만료될 때까지 남는다. 그 토큰이 혹시 어딘가로 새어 나갔다면 그것도 계속 유효하다. 그래서 새 세션을 만들기 전에 지운다. readToken이 서명을 확인하므로 위조한 쿠키로 남의 행을 지울 수는 없다.
  2. 새 토큰을 만든다 (97행) 이전 쿠키가 있든 없든 항상 새 토큰이다. 이것이 세션 고정 공격을 막는 핵심이다. 공격자가 미리 심어 둔 토큰이 로그인 뒤에도 쓰이는 일이 없다.
  3. 정책으로 만료 일시를 정한다 (98, 102행) 지금 + expiresInMs다. 지금 시각은 Date.now()가 아니라 주입받은 clock.now()로 구한다(아래).
  4. 행을 저장한다 (99-106행) 토큰 원문이 아니라 SHA-256 해시를 저장한다. IP와 User-Agent는 나중에 "로그인한 기기 목록" 같은 화면에 쓸 수 있도록 함께 남긴다.
  5. 서명한 토큰을 쿠키로 굽는다 (107-111행) 쿠키 값은 토큰.서명이다. 정책의 persistentCookie에 따라 Max-Age가 붙거나 빠진다.

"이전 행 지우기"와 "세션 고정 방지"는 다른 일이다. 고정 공격은 2번(늘 새 토큰)으로 이미 막힌다. 1번은 덮어써져 주인 없는 행이 남지 않게 하는 정리다. 둘 다 스펙 #70의 "다시 로그인하면 새 세션을 발급하고 이전 쿠키의 세션은 지운다"에서 나왔다.

선택 읽기: 이 동작을 지키는 테스트

첫 로그인 쿠키를 실은 채 다시 로그인하면, 첫 쿠키로는 세션이 null이고 두 번째 쿠키는 값이 다르다.

authenticate: 확인의 판단 순서

authenticate는 결과를 요청에 묶어 두는 껍데기이고(아래), 실제 판단은 findSession이 한다. 판단은 위에서 아래로 한 번만 흐르고, 걸리는 곳에서 바로 끝난다.

  • 요청의 Cookie 헤더 쿠키 이름으로 값을 꺼낸다
    • ① 쿠키 없음 / 서명 틀림 null DB를 보지 않는다. 쿠키도 건드리지 않는다
    • 토큰 해시로 행 찾기 SELECT 한 번
      • ② 행 없음 null 쿠키 지우기 (로그아웃·탈퇴 뒤 남은 쿠키)
      • ③ 만료 일시 ≤ 지금 null 행 DELETE + 쿠키 지우기
      • ④ 연장할 때가 됐다 UPDATE로 만료를 지금 + 유지 기간으로
        • ⑤ UPDATE된 행 0개 null 그새 로그아웃됐다. 쿠키 지우기
        • ⑥ UPDATE 성공 세션 같은 토큰으로 쿠키 다시 굽기
      • ⑦ 아직 연장할 때가 아니다 세션 쿠키를 건드리지 않는다

경우마다 DB와 응답에 무슨 일이 일어나는지 모으면 이렇다.

경우 DB 조회 DB 쓰기 Set-Cookie 결과
① 쿠키 없음 / 서명 틀림 0 0 없음 null
② 행 없음 1 0 지우기 null
③ 만료 1 DELETE 지우기 null
⑤ 연장하려는데 행이 사라짐 1 UPDATE(0행) 지우기 null
⑥ 연장 성공 1 UPDATE 다시 굽기 세션
⑦ 그냥 통과 (가장 흔함) 1 0 없음 세션

로그인한 사용자의 요청 대부분은 ⑦이다. SELECT 한 번으로 끝나고 아무것도 쓰지 않는다. 이제 코드를 단계별로 본다.

① 쿠키에서 토큰 꺼내기

// apps/api/src/auth/session-manager.ts
  private async findSession({
    request,
    response,
  }: {
    request: Request;
    response: Response;
  }): Promise<AuthenticatedSession | null> {
    const { store, secret, clock, getPolicy } = this.options;
    const token = this.readToken(request);
    if (!token) {
      return null;
    }
    const tokenHash = hashSessionToken(token);
    const session = await store.findByTokenHash(tokenHash);
    if (!session) {
      this.clearCookie(response);
      return null;
    }

    const now = clock.now().getTime();
    if (session.expiresAt.getTime() <= now) {
      await store.deleteByTokenHash(tokenHash);
      this.clearCookie(response);
      return null;
    }

    const policy = getPolicy(session);
    // 만료 일시에서 유지 기간을 빼면 마지막으로 만료를 정한(발급하거나 연장한) 시각이다(Better Auth와 같음).
    const lastRefreshedAt = session.expiresAt.getTime() - policy.expiresInMs;
    if (
      policy.updateAgeMs !== null &&
      lastRefreshedAt + policy.updateAgeMs <= now
    ) {
      const extended = await store.extend({
        id: session.id,
        expiresAt: new Date(now + policy.expiresInMs),
      });
      // 확인한 뒤 연장하기 전에 다른 요청(로그아웃)이 행을 지웠다.
      if (!extended) {
        this.clearCookie(response);
        return null;
      }
      this.setCookie({
        response,
        value: signSessionToken({ token, secret }),
        policy,
      });
    }

    return { sessionId: session.id, subjectId: session.subjectId };
  }

readToken은 쿠키가 없거나 서명이 틀리면 null을 준다. 이때는 쿠키를 지우지 않는다. 서명이 틀린 쿠키는 우리가 구운 것이 아닐 수 있고, 그냥 무시하면 충분하다.

② 행이 없으면 쿠키를 지운다

    const tokenHash = hashSessionToken(token);
    const session = await store.findByTokenHash(tokenHash);
    if (!session) {
      this.clearCookie(response);
      return null;
    }

서명이 맞으니 우리가 구운 쿠키인데 행이 없다. 다른 탭에서 로그아웃했거나, 다시 로그인해 이전 행이 지워졌거나, 탈퇴한 경우다. 쓸모없어진 쿠키를 브라우저가 계속 보내지 않도록 지운다.

③ 만료됐으면 행과 쿠키를 지운다

    const now = clock.now().getTime();
    if (session.expiresAt.getTime() <= now) {
      await store.deleteByTokenHash(tokenHash);
      this.clearCookie(response);
      return null;
    }

비교가 <=라는 점을 보자. 만료 일시와 지금이 정확히 같으면 이미 만료다. 7일짜리 세션은 발급 뒤 7일 - 1ms까지 통하고 정확히 7일에 끝난다. 쿠키의 Max-Age도 7일이라 보통은 브라우저가 먼저 쿠키를 버리지만, 서버는 쿠키 수명을 믿지 않고 행의 expires_at으로 판단한다.

④~⑦ 연장

연장 조건의 계산은 그림이 있어야 이해하기 쉬우므로 다음 절에서 따로 본다.

연장: 언제, 얼마나

로그인 상태 유지를 켠 세션은 "7일 동안 쓰지 않으면 끝나는" 세션이다. 이런 방식을 슬라이딩 만료라고 부른다. 요청이 올 때마다 만료를 뒤로 미는 것이다. 문제는 "요청마다" 미루면 요청마다 DB에 UPDATE를 하게 된다는 점이다. 그래서 마지막으로 미룬 뒤 1일(updateAgeMs)이 지난 첫 요청에서만 미룬다. DB 쓰기가 세션당 하루 한 번 이하로 줄어든다.

"마지막으로 미룬 시각"을 저장하지 않고 구한다

마지막 연장 시각을 따로 칸에 두지 않는다. 만료 일시는 늘 마지막으로 정한 시각 + expiresInMs로 정해지므로, 거꾸로 빼면 된다. 

lastRefreshedAt = expiresAt - expiresInMs      // 발급했거나 마지막으로 연장한 시각
연장할 때인가    = lastRefreshedAt + updateAgeMs <= now
요청 시각 expiresAt lastRefreshedAt (= expiresAt - 7일) + 1일 ≤ 지금? 결과
0일 (로그인) 7일 - - 발급
0.5일 7일 0일 1일 ≤ 0.5일? 아니다 ⑦ 그냥 통과
1.5일 7일 0일 1일 ≤ 1.5일? 그렇다 ⑥ 연장: expiresAt = 1.5 + 7 = 8.5일
2일 8.5일 1.5일 2.5일 ≤ 2일? 아니다 ⑦ 그냥 통과
8.5일 (그 사이 요청 없음) 8.5일 - - ③ 만료

같은 이야기를 시간축에 그리면 이렇다. 빨간 선이 요청, 막대가 그 시점의 유효 기간이다.

요청
로그인 요청 요청 → 연장 요청 만료
처음 유효 기간로그인 때 정한 만료
0일 ~ 7일 (1.5일에 대체됨)
연장한 유효 기간1.5일 요청이 다시 정함
1.5일 ~ 8.5일
연장하지 않는 구간마지막 연장 뒤 1일

0.5일 요청은 초록 구간 안이라 연장하지 않는다. 1.5일 요청은 초록 구간을 벗어났으므로 연장한다. 2일 요청은 새 초록 구간(1.5~2.5일) 안이라 다시 그냥 통과한다. 2일 뒤로 요청이 없으면 8.5일에 만료된다.

로그인 상태 유지를 끈 세션은 훨씬 단순하다. updateAgeMs가 null이라 연장 조건을 아예 보지 않는다.

요청
로그인 요청 (연장 없음) 요청 → 401
유효 기간브라우저를 닫으면 쿠키도 사라짐
0일 ~ 1일

상한이 없다. 로그인 상태 유지를 켜고 7일 안에 한 번씩만 쓰면 세션은 끝없이 이어진다. "로그인한 지 30일이 지나면 무조건 다시 로그인" 같은 절대 만료는 지금 없다. Better Auth도 기본 세션에는 절대 만료를 두지 않고, 민감한 작업에만 "로그인한 지 얼마나 됐나(freshAge)"를 따로 본다.

선택 읽기: 1일 경계를 확인하는 테스트

moveClock으로 앱의 시각을 옮긴다(Clock 절). 정확히 1일 뒤 요청에서 쿠키를 다시 받고, 처음 만료(7일)를 넘겨도 연장한 만료(8일) 전이면 /me가 통한다.

로그아웃과 연장이 겹칠 때

탭 두 개를 열어 두었다고 하자. 탭 A가 GET /me를 보냈고 마침 연장할 때가 됐다. 그런데 A가 행을 읽은 직후, 탭 B가 로그아웃해 행을 지운다. A는 이미 "유효한 세션"이라고 판단한 뒤라 UPDATE를 시도한다.

  1. 탭 A
  2. API 서버
  3. DB
  4. 탭 B
  1. GET /me 세션 쿠키
  2. SELECT ... WHERE token_hash = ?
  3. 행 만료 전, 연장할 때가 됨
  4. A가 판단을 마치고 UPDATE하기 전에 B가 끼어든다
  5. POST /auth/sign-out
  6. DELETE ... WHERE token_hash = ?
  7. 204 쿠키 지우기
  8. UPDATE ... WHERE id = ? RETURNING id A의 연장
  9. 0행
  10. 401 쿠키 지우기

저장소의 extend는 UPDATE에 RETURNING id를 붙여, 실제로 바뀐 행이 있었는지를 불리언으로 돌려준다. 

// apps/api/src/users/user-session-store.ts
  async extend({
    id,
    expiresAt,
  }: {
    id: number;
    expiresAt: Date;
  }): Promise<boolean> {
    const updated = await this.db
      .update(sessions)
      .set({ expiresAt, updatedAt: this.clock.now() })
      .where(eq(sessions.id, id))
      .returning({ id: sessions.id });
    return updated.length > 0;
  }
      const extended = await store.extend({
        id: session.id,
        expiresAt: new Date(now + policy.expiresInMs),
      });
      // 확인한 뒤 연장하기 전에 다른 요청(로그아웃)이 행을 지웠다.
      if (!extended) {
        this.clearCookie(response);
        return null;
      }

이 확인이 없다면 어떻게 될까?

  • UPDATE는 0행을 바꾸고도 오류 없이 끝난다. SQL에서 "조건에 맞는 행이 없음"은 실패가 아니다.
  • A는 세션을 돌려받아 로그아웃된 뒤인데도 로그인한 사용자로 처리된다.
  • A의 응답이 B의 응답보다 늦게 도착하면, A가 다시 구운 쿠키가 B가 지운 쿠키를 되살린다. 행은 없으니 다음 요청에서 ②로 걸리긴 하지만, 사용자는 "로그아웃했는데 쿠키가 남아 있는" 이상한 상태를 본다.

모든 겹침을 막지는 않는다. ⑦(연장 없이 통과)인 요청이 B의 DELETE 직전에 행을 읽었다면, 그 요청 하나는 로그인한 채로 끝난다. 이미 판단을 마친 요청을 되돌릴 방법은 없고, 그다음 요청부터 막히면 충분하다고 본다. 연장 경로만 확인하는 이유는 그 경로가 쿠키를 새로 굽는 유일한 확인 경로이기 때문이다.

WeakMap: 요청당 한 번만 확인

// apps/api/src/auth/session-manager.ts
export class SessionManager {
  // 한 요청에서 가드와 컨트롤러가 함께 불러도 DB 조회와 연장을 한 번만 하도록 결과를 요청에 묶어 둔다.
  private readonly authenticated = new WeakMap<
    Request,
    Promise<AuthenticatedSession | null>
  >();
  // ...
  authenticate({
    request,
    response,
  }: {
    request: Request;
    response: Response;
  }): Promise<AuthenticatedSession | null> {
    let result = this.authenticated.get(request);
    if (!result) {
      result = this.findSession({ request, response });
      this.authenticated.set(request, result);
    }
    return result;
  }

authenticate는 같은 요청 객체로 두 번 불려도 findSession을 한 번만 실행한다. 왜 필요할까?

  1. 한 요청에서 여러 곳이 세션을 확인할 수 있다 로그인 가드가 확인한 뒤, 같은 요청에서 다른 가드나 컨트롤러가 또 확인할 수 있다. 지금 코드에는 한 요청에서 두 번 부르는 곳이 아직 없다(/me는 가드가 확인한 결과를 @CurrentSession()으로 받는다). 하지만 세션을 보는 곳이 늘어날 때를 대비해 두었다.
  2. 두 번 실행하면 비용과 부작용이 두 번이다 SELECT가 두 번 나간다. 연장할 때라면 UPDATE와 Set-Cookie도 두 번이다. 응답 헤더에 같은 쿠키가 두 줄 들어가는 것은 오류는 아니어도 깔끔하지 않다.
  3. 결과가 아니라 Promise를 저장한다 첫 호출이 아직 DB를 기다리는 중에 두 번째 호출이 오면, 결과를 저장하는 방식으로는 아직 저장된 값이 없어 또 조회한다. Promise를 바로 저장해 두면 두 번째 호출은 같은 Promise를 받아 같은 결과를 기다린다.
  4. Map이 아니라 WeakMap이다 키가 요청 객체다. 일반 Map은 키를 꽉 붙잡고 있어서, 요청이 끝나도 요청 객체와 결과가 메모리에서 사라지지 않는다. 요청이 쌓일수록 메모리가 샌다. WeakMap은 키를 약하게 붙잡아서, 요청 객체를 아무도 쓰지 않으면 항목도 함께 사라진다. 
// 프론트엔드에 비유하면 "같은 요청 안에서만 유효한 캐시"다. React의 cache()가 렌더 한 번 안에서만 결과를 나누는 것과 비슷하다.
const authenticated = new WeakMap<Request, Promise<Session | null>>();

const a = authenticate(req); // findSession 실행, Promise를 저장
const b = authenticate(req); // 저장된 같은 Promise를 돌려줌
a === b;                     // true

// 요청이 끝나 req를 아무도 참조하지 않으면 WeakMap의 항목도 가비지 컬렉션 대상이 된다.

결과를 요청 객체의 속성(request.session = ...)에 붙이지 않은 것도 이유가 있다. SessionManager는 사용자용과 운영자용이 따로 만들어지고, 각자 자기 WeakMap을 가진다. 한 요청에서 두 매니저가 확인해도 결과가 섞이지 않는다.

revoke: 폐기

// apps/api/src/auth/session-manager.ts
  /** 세션 행과 쿠키를 지운다. 세션이 이미 없어도 그대로 끝난다. */
  async revoke({
    request,
    response,
  }: {
    request: Request;
    response: Response;
  }): Promise<void> {
    const token = this.readToken(request);
    if (token) {
      await this.options.store.deleteByTokenHash(hashSessionToken(token));
    }
    this.clearCookie(response);
  }

토큰이 있으면 그 해시로 행을 지우고, 쿠키는 무조건 지운다. 행이 이미 없거나, 쿠키가 없거나, 서명이 틀려도 오류를 내지 않는다. 로그아웃의 목적은 "이 브라우저가 로그인돼 있지 않은 상태"이고, 이미 그 상태라면 성공으로 보면 된다. 이런 성질을 멱등성(몇 번 해도 결과가 같음)이라고 한다. 그래서 POST /auth/sign-out은 두 번 불러도, 쿠키 없이 불러도 204다(09 문서).

세션은 "행 삭제"로 끝난다. revoked_at 같은 칸을 두고 표시만 하지 않는다. 행이 없으면 ②로 걸리므로, 지우는 것만으로 그 토큰은 다시 쓰일 수 없다. 이것이 JWT 대신 DB 세션을 고른 이유다. JWT는 서명만 맞으면 통하므로 만료 전에 끊으려면 차단 목록이 따로 필요하다.

readToken: 서명부터 본다

// apps/api/src/auth/session-manager.ts
  // 서명이 맞는 쿠키의 토큰만 돌려준다. 서명이 틀리면 DB를 조회하지 않고 없는 것으로 다룬다.
  private readToken(request: Request): string | null {
    const value = parseCookie(request.get('cookie') ?? '')[
      this.options.cookie.name
    ];
    if (!value) {
      return null;
    }
    return readSignedSessionToken({ value, secret: this.options.secret });
  }

issue, authenticate, revoke 셋 다 쿠키를 이 함수로만 읽는다. 쿠키 값 토큰.서명의 서명을 AUTH_SECRET으로 다시 계산해 맞을 때만 토큰을 돌려준다.

  • DB를 보호한다. 아무 문자열이나 쿠키에 넣어 보내는 요청은 서명에서 걸러져 DB까지 가지 않는다. HMAC 계산은 메모리 안에서 끝나므로 DB 조회보다 훨씬 싸다.
  • 한 번 더 막는다. 토큰 자체가 약 190비트 난수라 추측은 사실상 불가능하지만, 서명이 있으면 DB가 유출돼도 비밀키 없이는 쓸 수 있는 쿠키를 만들 수 없다.

서명을 비교할 때 === 대신 timingSafeEqual을 쓰는 이유와 해시·서명의 차이는 05 문서와 HMAC, 타이밍 공격 절에 있다.

쿠키를 굽고 지우는 setCookie, clearCookie, buildCookieOptions는 07 문서에서 다룬다. 여기서 기억할 것은 하나다. 지울 때도 구울 때와 같은 속성(경로, 도메인)을 준다. 브라우저는 이름, 경로, 도메인이 모두 같아야 같은 쿠키로 보고 지운다.

테이블과 정책을 바깥에서 받는다

SessionManager는 Nest의 @Injectable() 클래스가 아니다. 생성자로 옵션 객체 하나를 받는 평범한 클래스이고, 바뀌는 부분은 모두 그 옵션에 들어 있다. 

// apps/api/src/auth/session-manager.ts
/** 저장소에서 읽은 세션. 주체(subject)는 사용자 세션이면 사용자, 운영자 세션이면 운영자다. */
export interface StoredSession {
  id: number;
  subjectId: number;
  expiresAt: Date;
  rememberMe: boolean;
}

/**
 * 세션 행을 읽고 쓰는 곳. 세션 테이블을 소유한 모듈이 구현해 넘긴다.
 * 사용자 세션과 운영자 세션은 테이블만 다르고 같은 SessionManager 로직을 쓴다.
 */
export interface SessionStore {
  create(input: {
    tokenHash: string;
    subjectId: number;
    expiresAt: Date;
    rememberMe: boolean;
    ipAddress: string | null;
    userAgent: string | null;
  }): Promise<void>;
  findByTokenHash(tokenHash: string): Promise<StoredSession | null>;
  /** 만료 일시를 다시 쓴다. 그새 행이 지워졌으면 false다. */
  extend(input: { id: number; expiresAt: Date }): Promise<boolean>;
  deleteByTokenHash(tokenHash: string): Promise<void>;
}
// ...
export interface SessionManagerOptions {
  store: SessionStore;
  cookie: SessionCookieSettings;
  /** 쿠키 서명 키(AUTH_SECRET). */
  secret: string;
  clock: Clock;
  getPolicy: (session: { rememberMe: boolean }) => SessionPolicy;
}
  • SessionManagerOptions 세션 종류마다 다른 것만 모았다
    • store: SessionStore 어느 테이블에 읽고 쓰나. 테이블을 소유한 모듈이 구현한다
    • getPolicy 세션마다 유지 기간, 연장 간격, 쿠키 수명
    • cookie 쿠키 이름, Domain, Secure
    • secret 서명 키 AUTH_SECRET
    • clock 지금 시각. 테스트에서 바꿔 끼운다

SessionStore는 메서드 네 개짜리 인터페이스다. SessionManager는 Drizzle도, sessions 테이블도 모른다. 사용자 세션은 users/user-session-store.ts의 UserSessionStore가 구현하고, users/user-session.ts가 모든 옵션을 채워 매니저를 만든다(08 문서).

운영자 세션(#82)은 옵션만 다르다

운영자 로그인 티켓(#82)은 아직 구현 전이다. 티켓에 적힌 규칙을 옵션에 대 보면, 바뀌는 곳이 옵션뿐이라는 것을 알 수 있다.

옵션 사용자 세션 구현됨 운영자 세션 #82 예정
store UserSessionStore (sessions 테이블) 운영자 세션 테이블을 읽고 쓰는 저장소
getPolicy 켬: 7일 / 1일마다 연장 / Max-Age 있음
끔: 1일 / 연장 없음 / Max-Age 없음		 30분 / 5분마다 연장 / Max-Age 없음 (로그인 상태 유지 없음)
cookie openrun.session_token, 상위 도메인 다른 이름, Domain 없이 API 호스트 전용

30분 동안 요청이 없으면 끝나는 "유휴 만료"도 새 코드가 아니다. 위의 슬라이딩 만료에 숫자만 30분과 5분으로 넣으면 된다.

소셜 로그인(1.4b)도 issue를 그대로 쓴다

구글·카카오 로그인은 "비밀번호 확인" 대신 "제공자가 확인해 준 계정으로 사용자 찾기"를 한다. 사용자 id를 얻은 다음부터는 이메일 로그인과 같다. 콜백에서 issue({ request, response, subjectId: userId, rememberMe })를 부르면 같은 세션, 같은 쿠키가 나온다. 세션은 "어떻게 로그인했나"를 몰라도 된다. 로그인 수단은 03 문서의 accounts 테이블이 맡는다.

Clock: 시간을 테스트에서 움직이기

만료와 연장은 모두 "지금"에 달려 있다. Date.now()를 바로 부르면, 7일 만료를 테스트하려고 정말 7일을 기다리거나 전역 타이머를 가짜로 바꿔야 한다. 그래서 지금 시각을 주는 객체 Clock을 주입받는다. 

// apps/api/src/clock/clock.module.ts
// 현재 시각을 돌려준다. 판매 상태처럼 시각에 따라 달라지는 값은 DB의 now() 대신 이 값을 SQL 파라미터로 넘겨 계산한다.
// 추상 클래스를 주입 토큰으로 써서, 테스트는 overrideProvider(Clock)로 고정 시각을 끼운다.
export abstract class Clock {
  abstract now(): Date;
}

@Injectable()
export class SystemClock extends Clock {
  now(): Date {
    return new Date();
  }
}

아직 없는 것: 만료된 행 정리

만료된 행은 그 쿠키가 다시 왔을 때만 ③에서 지워진다. 사용자가 쿠키를 지웠거나 브라우저를 닫아 쿠키가 사라진 세션(로그인 상태 유지를 끈 세션)은 다시 오지 않으므로, 그 행은 만료된 채 sessions 테이블에 남는다.

지금은 이런 행을 주기적으로 지우는 작업이 없다. 남은 행은 expires_at이 지나 있어 쓰일 수 없으므로 보안 문제는 아니고, 테이블이 조금씩 커질 뿐이다.

Better Auth와 같은 점, 다른 점

이 클래스는 Better Auth의 세션 처리를 본떴다(ADR 0009).

항목 Better Auth openrun
연장 조건 expiresAt - expiresIn + updateAge <= now 같다
연장할 때 행이 사라졌으면 쿠키를 지우고 로그인 안 됨으로 같다
찾은 세션이 만료됐으면 행과 쿠키를 지움 같다
DB에 저장하는 토큰 원문 SHA-256 해시
로그인 상태 유지를 끈 표시 서명한 별도 쿠키 dont_remember 세션 행의 remember_me
쿠키 캐시(DB 조회를 잠시 건너뜀) 설정으로 켬 없음. 요청마다 DB 조회

Better Auth와 다르게 정한 것: 토큰은 해시로 저장한다. DB와 비밀키가 함께 유출돼도 저장된 값으로 쿠키를 만들 수 없게 하기 위해서다. 로그인 상태 유지 여부는 쿠키가 아니라 세션 행에 둔다. 쿠키 캐시는 세션 조회가 느리다는 측정 근거가 생기는 9단계에서 전후를 측정하며 도입한다(ADR 0009).

1. 로그인 상태 유지를 켜고 로그인했다. 언제 만료될까?

시각 한 일
0일 로그인
0.9일 GET /me
1.2일 GET /me
2.1일 GET /me
그 뒤 요청 없음

8.2일. 0.9일은 마지막 연장(0일) 뒤 1일이 안 됐으므로 그냥 통과한다. 1.2일은 1일이 지났으므로 연장해 만료가 1.2 + 7 = 8.2일이 된다. 2.1일은 마지막 연장(1.2일) 뒤 0.9일이라 연장하지 않는다. 그 뒤 요청이 없으니 8.2일에 끝난다. 2.1일의 요청이 만료를 늘려 주지 않았다는 점이 핵심이다.

2. 로그인 상태 유지를 끈 정책에도 연장을 켜면 어떻게 될까?

users/user-session.ts의 정책을 아래처럼 바꾼다. 유지 기간과 연장 간격이 둘 다 1일이다.

 const NOT_REMEMBERED_POLICY: SessionPolicy = {
   expiresInMs: DAY_MS,
-  updateAgeMs: null,
+  updateAgeMs: DAY_MS,
   persistentCookie: false,
 };
답 보기

한 번도 연장되지 않는다. 연장 조건은 lastRefreshedAt + 1일 <= now인데, lastRefreshedAt + 1일은 바로 expiresAt이다. 즉 "만료 시각이 지났으면 연장"이라는 뜻이 된다. 그런데 그 전에 ③이 expiresAt <= now를 먼저 보고 행을 지운다. 연장 간격은 유지 기간보다 짧아야 의미가 있다.
