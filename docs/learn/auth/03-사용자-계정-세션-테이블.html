03 사용자·계정·세션 테이블

로그인에 쓰는 세 테이블 users(사람), accounts(로그인 수단), sessions(로그인 세션)의 칸과 제약을 하나씩 보고, 왜 이렇게 나눴는지 따라간다. 특히 비밀번호를 사용자 테이블이 아니라 계정 테이블에 둔 결정이 1.4b의 구글·카카오 로그인을 어떻게 받아 내는지 본다. 스키마는 apps/api/src/db/schema/users.ts, 마이그레이션은 apps/api/drizzle/0008_create_users_accounts_sessions.sql이다. 기본 키, 외래 키, 유니크 같은 DB 개념은 db-and-drizzle 01 문서, Drizzle 문법은 db-and-drizzle 02 문서에 있다.

회색 선은 외래 키다. 세 갈래 까마귀 발(N) 쪽이 "여러 개", 막대(1) 쪽이 "하나"다. 사용자 한 명에게 계정 여러 개, 세션 여러 개가 붙는다. 빨간 표시는 이 문서에서 자세히 보는 칸과 제약이다.

테이블한 행이 뜻하는 것비유
users스토어에 가입한 사람 한 명회원 명부의 한 줄
accounts그 사람이 로그인하는 방법 하나(이메일+비밀번호, 구글, 카카오)한 사람이 가진 열쇠 하나
sessions어느 브라우저에서 로그인해 있는 상태 하나입장할 때 받은 손목 띠 하나

사용자가 노트북과 휴대폰에서 로그인해 있으면 세션 행이 둘이다. 이메일로도, 나중에 카카오로도 로그인할 수 있게 연결하면 계정 행이 둘이다. 사람은 여전히 한 명이라 users 행은 하나다.

운영자는 이 세 테이블에 없다. 운영자는 따로 operators 테이블과 운영자 세션 테이블을 두기로 했다(ADR 0010, #82에서 만든다).

users: 사람

// apps/api/src/db/schema/users.ts
export const users = pgTable('users', {
  id: integer().primaryKey().generatedAlwaysAsIdentity(),
  // 소문자로 정규화해 넣는다. 탈퇴(1.8)하면 지우므로 NULL을 허용한다.
  // PostgreSQL의 UNIQUE는 NULL끼리 겹치는 것으로 보지 않으므로, 유니크는 이메일이 있는 행에만 걸린다.
  email: text().unique(),
  name: text().notNull(),
  // 이메일 인증을 마친 일시다. NULL이면 인증하지 않았다.
  emailVerifiedAt: timestamp('email_verified_at', { withTimezone: true }),
  createdAt: timestamp('created_at', { withTimezone: true })
    .notNull()
    .defaultNow(),
  updatedAt: timestamp('updated_at', { withTimezone: true })
    .notNull()
    .defaultNow(),
});

email: 소문자, 유니크, 그런데 NULL 허용

  • 소문자로 넣는다. Kim@Example.com과 kim@example.com이 다른 사람으로 가입되면 안 된다. 가입할 때와 로그인할 때 모두 소문자로 바꾸므로, DB에서는 글자 그대로 비교하면 된다(02 문서).
  • 유니크다. 한 이메일로 두 사람이 가입할 수 없다. 앱에서 먼저 확인하더라도, 동시에 들어온 가입 요청 둘을 끝까지 막는 것은 DB의 유니크 제약이다(왜 DB가 막아야 하나).
  • 그런데 NOT NULL이 아니다. 탈퇴(1.8)하면 개인정보인 이메일을 지우고 행은 남긴다. 주문 같은 기록이 이 행을 가리키고 있어서다. 탈퇴한 사람이 여럿이면 email이 NULL인 행이 여럿 생기는데, PostgreSQL의 유니크 제약은 NULL끼리 같다고 보지 않으므로 막히지 않는다(유니크와 NULL). 그래서 "이메일이 있는 행끼리만 유니크"가 따로 조건을 쓰지 않고도 이루어진다.

2NULL(탈퇴)

4kim@example.com유니크 위반으로 들어가지 않는다

email_verified_at: 참/거짓 대신 일시

"이메일 인증을 마쳤는가"는 참/거짓이지만 boolean 대신 일시를 둔다. NULL이면 아직, 값이 있으면 그때 마쳤다. 칸 하나로 "했는지"와 "언제 했는지"를 함께 남긴다. API 응답에서는 emailVerified: user.emailVerifiedAt !== null로 참/거짓만 내보낸다(09 문서).

이메일 가입은 가입 화면 안에서 인증번호로 이메일을 인증해야 끝나므로(#76, #74), 가입할 때 이 칸을 채운다. 이메일 가입자에게는 NULL이 없다. 그래도 NULL을 허용하는 것은 1.4b 소셜 가입에서 제공자가 인증해 주지 않은 이메일을 받을 수 있어서다. 가입 전의 인증 시도는 사용자가 아직 없으므로 이 테이블이 아니라 email_verifications 테이블(#76)에 두고, 가입하면 그 행을 지운다.

users에는 비밀번호가 없다. 이 문서에서 가장 중요한 결정이라 다음 절에서 따로 본다.

비밀번호를 users에 두지 않는 이유

가장 단순한 설계는 사용자 테이블에 비밀번호 해시 칸을 두는 것이다. 이메일 로그인만 있다면 그것으로 충분하다.

설계 A: users에 password_hash
  1. users(id, email, password_hash, …)
설계 B(이 저장소): 로그인 수단을 accounts로
  1. users(id, email, …)
  2. accounts(user_id, provider, provider_account_id, password_hash)

1단계에는 구글·카카오 로그인(1.4b)이 들어온다. 그때 설계 A에서 생기는 일을 보자.

  1. 카카오로만 가입한 사람 비밀번호가 없다. password_hash를 NULL로 두면 "비밀번호가 없는 사용자"와 "데이터가 잘못된 사용자"를 구분할 수 없다.
  2. 카카오 사용자를 다시 알아보기 카카오가 주는 사용자 식별자를 저장할 칸이 필요하다. users.kakao_id를 더한다.
  3. 구글도 붙인다 users.google_id를 또 더한다. 제공자가 늘 때마다 사용자 테이블에 칸이 늘고, 대부분의 행에서 그 칸은 비어 있다.
  4. 한 사람이 이메일과 카카오를 함께 쓰기(1.8의 소셜 연결) 칸이 다 한 행에 있어 되긴 하지만, "연결 해제"나 "마지막 로그인 수단은 끊을 수 없다" 같은 규칙을 칸마다 따로 짜야 한다.

설계 B는 "로그인 수단"을 행으로 둔다. 이메일+비밀번호도, 구글도, 카카오도 accounts의 행 하나이고 모양이 같다. 제공자가 늘어도 테이블 모양은 그대로이고, 한 사람이 수단을 여럿 가지면 행이 여럿일 뿐이다. 이 모양은 Better Auth의 account 테이블을 따른 것이다. Auth.js 같은 다른 인증 라이브러리도 사용자와 로그인 수단을 나누는 같은 모양을 쓴다.

사용자(users)는 "누구인가", 계정(accounts)은 "어떻게 들어오는가"다. 로그인 방식이 늘거나 바뀌어도 "누구인가"는 그대로여야 주문, 찜, 리뷰가 같은 사람에게 붙어 있다.

1.4b와 1.8을 마친 뒤의 모습을 예시 데이터로 그려 보면 이렇다. 구글·카카오 행은 아직 들어갈 수 없는, 앞으로의 모습이다.

accounts: 로그인 수단

// apps/api/src/db/schema/users.ts
// 로그인 수단의 제공자다. 1.4b에서 google, kakao를 더한다.
export const ACCOUNT_PROVIDERS = ['credential'] as const;
export type AccountProvider = (typeof ACCOUNT_PROVIDERS)[number];

export const accountProvider = pgEnum('account_provider', ACCOUNT_PROVIDERS);

// 사용자의 로그인 수단 하나다(Better Auth의 account 테이블). 이메일 로그인 계정(credential)이 비밀번호 해시를 갖는다.
// 사용자 테이블에 비밀번호를 두지 않아, 소셜 로그인만 쓰는 사용자도 같은 모양이 된다.
export const accounts = pgTable(
  'accounts',
  {
    id: integer().primaryKey().generatedAlwaysAsIdentity(),
    userId: integer('user_id')
      .notNull()
      .references(() => users.id, { onDelete: 'cascade' }),
    provider: accountProvider().notNull(),
    // 제공자 안에서 이 계정을 가리키는 값이다. 이메일 로그인 계정은 Better Auth처럼 사용자 id를 넣는다.
    providerAccountId: text('provider_account_id').notNull(),
    // scrypt 해시(`솔트:키`, hex)다. 이메일 로그인 계정에만 있다.
    passwordHash: text('password_hash'),
    createdAt: timestamp('created_at', { withTimezone: true })
      .notNull()
      .defaultNow(),
    updatedAt: timestamp('updated_at', { withTimezone: true })
      .notNull()
      .defaultNow(),
  },
  (table) => [
    // 같은 제공자의 같은 계정이 두 사용자에게 연결되지 않게 막는다.
    unique().on(table.provider, table.providerAccountId),
    index().on(table.userId),
  ],
);
칸뜻
user_id이 수단으로 들어오면 누가 되는가
provider어느 제공자인가. 지금은 credential(이메일+비밀번호) 하나다. 정해진 값만 들어가도록 pgEnum으로 둔다
provider_account_id그 제공자 안에서 이 계정을 가리키는 값. 카카오라면 카카오가 주는 회원 번호다
password_hashcredential 계정에만 있는 scrypt 해시. 만드는 법은 04 문서

UNIQUE (provider, provider_account_id)

"카카오 회원 3141592653"은 세상에 하나다. 이 계정이 우리 사용자 두 명에게 동시에 연결되면, 카카오로 로그인했을 때 누구로 들여보낼지 정할 수 없다. 그래서 두 칸의 조합을 유니크로 묶는다. 조합 유니크가 어떻게 동작하는지는 여러 컬럼 유니크에 있다.

providerprovider_account_id결과
kakao3141592653들어간다
google3141592653들어간다. 제공자가 다르면 같은 번호라도 다른 계정이다
kakao3141592653막힌다. 이미 누군가에게 연결된 카카오 계정이다

이 유니크 제약에는 인덱스가 따라 생긴다(유니크와 인덱스). 1.4b에서 "카카오가 알려 준 회원 번호로 우리 사용자 찾기"가 바로 이 두 칸으로 찾는 조회라, 그 조회도 이 인덱스로 빠르다.

index (user_id)

PostgreSQL은 외래 키 칸에 인덱스를 자동으로 만들지 않는다. "이 사용자의 계정 전부"를 찾을 일(로그인 수단 목록, 사용자 행이 지워질 때 딸린 행 찾기)이 있어 user_id에 인덱스를 따로 둔다. 지금 로그인 조회는 이메일로 사용자를 찾아 JOIN하므로 이 인덱스를 쓸 수 있다(02 문서의 SQL).

credential 계정의 provider_account_id

카카오 계정이라면 provider_account_id에 카카오 회원 번호를 넣으면 된다. 그런데 이메일+비밀번호 계정은 "제공자 안의 식별자"가 따로 없다. 우리가 제공자이기 때문이다. 이 저장소는 Better Auth처럼 사용자 id를 넣는다.

넣을 수 있는 값생기는 일
사용자 id (선택)사용자마다 값이 하나로 정해져, UNIQUE (provider, provider_account_id)가 "사용자 한 명에게 credential 계정은 하나"까지 막아 준다. 바뀔 일도 없다
이메일이메일을 바꾸면(1.8) 두 테이블을 함께 고쳐야 한다. 탈퇴로 이메일을 지우면 NOT NULL인 이 칸에 넣을 값이 없다
비워 두기(NULL)칸이 NOT NULL이 아니어야 하고, NULL끼리는 유니크로 막히지 않아 한 사람에게 credential 계정이 둘 생길 수 있다

사용자 id를 넣으면 테이블의 모든 행이 "제공자 + 그 안의 식별자"라는 같은 규칙을 지키고, 덤으로 credential 계정이 사용자당 하나라는 규칙도 DB가 지킨다. 다만 사용자 id는 사용자 행을 넣은 뒤에야 알 수 있으므로, 가입(#74)은 사용자 행을 먼저 넣고 돌려받은 id로 계정 행을 넣는다.

로그인 조회는 이 칸을 쓰지 않는다. 이메일은 users에 있으므로 이메일로 사용자를 찾고, 그 사용자의 credential 계정을 JOIN한다.

sessions: 로그인 세션

// apps/api/src/db/schema/users.ts
export const sessions = pgTable(
  'sessions',
  {
    id: integer().primaryKey().generatedAlwaysAsIdentity(),
    tokenHash: text('token_hash').notNull().unique(),
    userId: integer('user_id')
      .notNull()
      .references(() => users.id, { onDelete: 'cascade' }),
    expiresAt: timestamp('expires_at', { withTimezone: true }).notNull(),
    // 로그인 상태 유지를 골랐는지다. 켜면 7일 동안 유지하며 연장하고, 끄면 1일 뒤 끝나며 연장하지 않는다.
    rememberMe: boolean('remember_me').notNull(),
    ipAddress: text('ip_address'),
    userAgent: text('user_agent'),
    createdAt: timestamp('created_at', { withTimezone: true })
      .notNull()
      .defaultNow(),
    updatedAt: timestamp('updated_at', { withTimezone: true })
      .notNull()
      .defaultNow(),
  },
  (table) => [index().on(table.userId)],
);
칸뜻누가 쓰나
token_hash쿠키에 든 토큰의 SHA-256 해시(hex 64자). 원문은 저장하지 않는다요청마다 이 값으로 세션을 찾는다
user_id이 세션의 주인가드가 핸들러에 넘기는 subjectId
expires_at이 시각이 지나면 끝난 세션만료 판단, 연장 시점 계산
remember_me로그인 상태 유지를 골랐는지만료·연장 정책 고르기
ip_address, user_agent로그인한 곳과 브라우저기록용. 판단에는 쓰지 않는다

token_hash: 유니크이자 찾는 열쇠

세션을 찾는 유일한 방법이 "쿠키의 토큰을 해시해 같은 행 찾기"다. 유니크 제약이 같은 해시가 두 번 들어가지 않게 막고, 함께 생기는 인덱스가 이 조회를 빠르게 한다. 토큰을 해시해서 저장하는 이유와 해시가 겹칠 걱정이 없는 이유는 05 문서에 있다.

Better Auth와 다른 점: Better Auth는 세션 테이블에 토큰 원문을 저장한다. 이 저장소는 SHA-256 해시를 저장해, DB가 유출돼도 그 값으로 쿠키를 만들 수 없게 했다(ADR 0009).

remember_me: 세션 행에 둔다

로그인 상태 유지를 켰는지에 따라 세션의 규칙이 달라진다. 켰으면 7일 유지와 연장, 껐으면 1일 뒤 끝이다. 요청이 올 때마다 이 세션이 어느 규칙을 따르는지 알아야 하므로, 고른 값을 세션 행에 저장한다. 규칙의 내용은 06 문서에 있다.

Better Auth와 다른 점: Better Auth는 "유지하지 않음"을 별도 쿠키(dont_remember)로 들고 다닌다. 이 저장소는 세션 행에 둔다. 세션의 규칙을 정하는 값이 세션과 같은 곳에 있어 쿠키 하나만 다루면 되고, 서버가 판단에 쓰는 값을 브라우저에 맡기지 않는다(ADR 0009).

ip_address, user_agent

세션을 만들 때 요청의 IP와 User-Agent 헤더를 적어 둔다. Better Auth도 같은 칸을 둔다. 지금은 어디서도 읽지 않는 기록이고, 로그인 판단에도 쓰지 않는다. IP는 휴대폰이 와이파이와 LTE를 오가기만 해도 바뀌어서 판단에 쓰면 멀쩡한 사용자가 로그아웃된다. 둘 다 값이 없을 수 있어 NULL을 허용한다.

index (user_id)

"이 사용자의 세션 전부"를 지울 일이 있다. 탈퇴(1.8)하면 세션을 모두 끊어야 하고, 사용자 행이 지워질 때 딸린 세션을 찾는 것도 이 칸이다. 그래서 accounts처럼 user_id에 인덱스를 둔다. expires_at에는 인덱스가 없다. 만료된 행은 그 세션으로 요청이 올 때 지운다(06 문서). 아무도 다시 오지 않는 만료 세션을 한꺼번에 지우는 일은 아직 하지 않는다.

사용자 행이 지워지면

accounts.user_id와 sessions.user_id는 모두 onDelete: 'cascade'다. 사용자 행을 지우면 그 사람의 계정과 세션도 DB가 함께 지운다. 값별 동작은 onDelete에 있다.

DELETE FROM users WHERE id = 1
  1. users 1 삭제
  2. accounts의 user_id = 1 삭제
  3. sessions의 user_id = 1 삭제

계정과 세션은 사용자 없이는 뜻이 없다. 주인 없는 비밀번호 해시나, 아무도 아닌 사람으로 로그인되는 세션이 남지 않게 한다. 기본값 (no action)이었다면 딸린 행을 먼저 지우지 않는 한 사용자 행을 지울 수 없다.

탈퇴는 사용자 행을 지우는 일이 아니다. 1.8의 탈퇴는 이메일 같은 개인정보를 지우고 행은 남기는 방식을 전제로 하고 있어서(email 절), 그때는 cascade가 동작하지 않는다. 탈퇴할 때 세션을 끊는 일은 앱이 직접 해야 한다. cascade는 테스트 데이터 정리처럼 행을 실제로 지울 때 딸린 행이 남지 않게 하는 안전장치다.

마이그레이션 SQL

세 테이블은 마이그레이션 하나(0008)로 만들었다. drizzle-kit이 스키마에서 만든 SQL 중 이 문서에서 본 제약만 추렸다. 마이그레이션을 만드는 순서는 db-and-drizzle 08 문서에 있다. 

CREATE TYPE "public"."account_provider" AS ENUM('credential');
CREATE TABLE "accounts" (
	"id" integer PRIMARY KEY GENERATED ALWAYS AS IDENTITY (...),
	"user_id" integer NOT NULL,
	"provider" "account_provider" NOT NULL,
	"provider_account_id" text NOT NULL,
	"password_hash" text,
	...
	CONSTRAINT "accounts_provider_provider_account_id_unique" UNIQUE("provider","provider_account_id")
);
CREATE TABLE "sessions" (
	"id" integer PRIMARY KEY GENERATED ALWAYS AS IDENTITY (...),
	"token_hash" text NOT NULL,
	"user_id" integer NOT NULL,
	"expires_at" timestamp with time zone NOT NULL,
	"remember_me" boolean NOT NULL,
	"ip_address" text,
	"user_agent" text,
	...
	CONSTRAINT "sessions_token_hash_unique" UNIQUE("token_hash")
);
CREATE TABLE "users" (
	"id" integer PRIMARY KEY GENERATED ALWAYS AS IDENTITY (...),
	"email" text,
	"name" text NOT NULL,
	"email_verified_at" timestamp with time zone,
	...
	CONSTRAINT "users_email_unique" UNIQUE("email")
);
ALTER TABLE "accounts" ADD CONSTRAINT "accounts_user_id_users_id_fk" FOREIGN KEY ("user_id") REFERENCES "public"."users"("id") ON DELETE cascade ON UPDATE no action;
ALTER TABLE "sessions" ADD CONSTRAINT "sessions_user_id_users_id_fk" FOREIGN KEY ("user_id") REFERENCES "public"."users"("id") ON DELETE cascade ON UPDATE no action;
CREATE INDEX "accounts_user_id_index" ON "accounts" USING btree ("user_id");
CREATE INDEX "sessions_user_id_index" ON "sessions" USING btree ("user_id");

users를 나중에 만드는데도 문제가 없는 이유는 외래 키를 테이블을 다 만든 뒤 ALTER TABLE로 따로 걸기 때문이다. password_hash에는 NOT NULL이 없다. 소셜 계정 행에는 비밀번호가 없어서다.

소셜 로그인을 붙이면

이 절은 1.4b에서 할 일을 지금 스키마에 비춰 본 것이다. 실제로 무엇을 바꿀지는 1.4b 설계에서 정하고, 그때 이 문서를 고친다.

  1. 제공자 값 더하기 ACCOUNT_PROVIDERS에 'google', 'kakao'를 더하고 마이그레이션을 만든다. PostgreSQL enum에 값을 더하는 SQL은 ALTER TYPE "account_provider" ADD VALUE 'google'이다. 테이블 모양은 그대로다.
  2. 카카오로 들어온 사람 알아보기 카카오가 알려 준 회원 번호로 provider = 'kakao' AND provider_account_id = '…'인 행을 찾는다. 있으면 그 user_id로 세션을 발급한다. 세션 발급부터는 이메일 로그인과 똑같이 SessionManager.issue를 쓴다.
  3. 처음 온 사람 가입시키기 없으면 users 행과 kakao 계정 행을 함께 만든다. 비밀번호 칸은 비어 있다.
  4. 이미 같은 이메일로 가입한 사람 카카오 계정의 이메일이 기존 사용자와 같을 때 어떻게 할지는 1.4b에서 정한다. 조사 메모 (docs/research/social-signup-email.md)는 제공자가 인증한 이메일이면 자동으로 연결하고, 이메일이 없거나 인증되지 않았으면 가입 화면에서 받아 #76의 인증번호로 인증하는 쪽을 권한다. 구글은 gmail과 Workspace 주소만 인증을 보장한다. 어느 쪽이든 결과는 accounts에 행을 더하거나 더하지 않는 일이라 스키마는 바뀌지 않는다.

Better Auth의 account 테이블에는 제공자가 준 액세스 토큰, 리프레시 토큰 같은 칸도 있다. 로그인만 하고 제공자 API를 따로 부르지 않는다면 필요 없으므로, 그 칸을 더할지도 1.4b에서 정한다.
