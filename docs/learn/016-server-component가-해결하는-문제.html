Server Component가 해결하는 문제

기존 SSR도 서버에서 HTML을 만들어 줬다. 그런데 왜 Server Component가 따로 나왔을까? 기존 SSR이 하이드레이션 때문에 모든 컴포넌트를 브라우저로 보내 다시 실행해야 했던 문제를 짚고, 같은 화면을 기존 방식(pages 폴더)과 Server Component 방식(app 폴더)으로 만들어 브라우저로 가는 코드와 데이터를 직접 비교한다.

한 줄 답

기존 SSR은 HTML을 미리 만들어 줄 뿐, 모든 컴포넌트의 코드를 브라우저로 보내 다시 실행(하이드레이션)해야 했다. Server Component는 서버에서만 실행하고 결과만 보내는 컴포넌트를 만들어, 클릭할 것이 없는 부분은 브라우저로 보내지도, 다시 실행하지도 않게 했다.

이 문서는 015 Server Component 단계와 SSR 단계를 읽었다고 보고 쓴다. "1단계(설계도 만들기)", "2단계(HTML 만들기)", "RSC payload" 같은 말은 015에서 설명했다.

기존 SSR은 어떻게 동작했나

App Router(app 폴더)가 나오기 전 Next는 pages 폴더를 썼다. 서버에서 데이터가 필요한 페이지는 이렇게 만들었다. 

// pages/shows.tsx (기존 방식)
export async function getServerSideProps() {
  const shows = await fetchShows(); // 데이터는 페이지 맨 위 이 함수에서만 읽는다
  return { props: { shows } };
}

export default function ShowsPage({ shows }) {
  return (
    <main>
      <Badge tone="primary">테스트 서비스</Badge>
      <ShowList shows={shows} /> {/* 아래 컴포넌트에는 props로 내려보낸다 */}
    </main>
  );
}
서버
  1. getServerSideProps로 데이터 읽기
  2. 모든 컴포넌트를 실행해 HTML 만들기
  3. HTML + 데이터(JSON) 보내기
브라우저
  1. HTML 그리기
  2. 모든 컴포넌트의 JS 받기
  3. 모든 컴포넌트를 다시 실행해 하이드레이션

서버가 HTML을 만들어 주니 첫 화면은 빨리 뜬다. 문제는 브라우저 쪽이다. HTML이 있는데도 모든 컴포넌트를 다시 실행해야 했다. 왜 그런지부터 본다.

HTML이 있는데 왜 다시 실행하나

서버가 만든 HTML은 이런 글자다.

<button class="group relative inline-flex h-[52px] …">클라이언트 버튼</button>

여기에는 모양만 있고, 다음 세 가지가 없다.

HTML에 없는 것 왜 없나 없으면
onClick 같은 함수 함수는 글자로 적을 수 없다 버튼이 보이지만 눌러도 아무 일도 없다
상태 (useState) 열림/닫힘 같은 값은 JS 메모리에만 있다 상태에 따라 화면을 바꿀 수 없다
어느 컴포넌트의 결과인지 브라우저에게는 그냥 <button> 태그다 함수와 상태를 어디에 붙일지 모른다

그래서 React는 브라우저에서 컴포넌트를 한 번 더 실행한다. 이것이 하이드레이션이다.

  1. 다시 실행 Button 함수를 실행하면 "<button>을 이 클래스로, onClick은 이 함수로"라는 결과가 나온다.
  2. 맞춰 보기 그 결과를 이미 그려진 HTML과 하나씩 맞춰 본다. "이 <button>이 아까 실행한 Button의 결과구나."
  3. 붙이기 맞으면 HTML을 새로 그리지 않고, 그 <button>에 함수와 상태만 붙인다.

다시 실행하는 목적은 화면을 다시 그리는 것이 아니라 이미 그려진 HTML에 함수와 상태를 연결하는 것이다. 다만 연결하려면 컴포넌트를 실행해 봐야 하므로, 그 컴포넌트의 JS 코드가 브라우저에 있어야 한다.

기존 SSR은 왜 "모든" 컴포넌트를 다시 실행했나

기존 방식에서 페이지는 통째로 하나의 클라이언트 앱이다. React는 어떤 컴포넌트가 연결할 함수나 상태가 없는지 미리 알 수 없다. 그래서 클릭할 것이 없는 배지, 제목, 목록까지 모든 컴포넌트를 실행해 맞춰 봐야 했고, 그러려면 모든 컴포넌트의 JS가 브라우저로 가야 했다.

기존 SSR의 네 가지 문제

문제 기존 SSR Server Component
1. 브라우저로 가는 코드 클릭할 것이 없는 컴포넌트도 하이드레이션 때문에 코드가 전부 브라우저로 간다 Server Component 코드는 브라우저로 가지 않는다. 결과만 RSC payload에 실린다
2. 같은 일을 두 번 서버가 실행해 HTML을 만들고, 브라우저가 같은 컴포넌트를 또 실행한다 Server Component는 서버에서 한 번만 실행한다. 브라우저는 Client Component만 다시 실행한다
3. 데이터를 읽는 곳과 보내는 양 페이지 맨 위 getServerSideProps에서만 읽고 props로 내려보낸다. 하이드레이션에 필요해서 props 데이터 전체가 HTML과 별도로 JSON으로 한 번 더 간다 필요한 컴포넌트가 async로 직접 읽는다. 브라우저로는 그린 결과만 간다
4. 무거운 라이브러리와 서버 자원 컴포넌트 코드가 브라우저로 가니, 안에서 쓴 라이브러리도 같이 간다. DB나 비밀값은 컴포넌트 안에서 못 쓴다 서버에서만 실행되니 마크다운 변환기 같은 라이브러리나 DB 접근을 컴포넌트 안에서 써도 브라우저로 가지 않는다

1번과 3번은 아래 실험에서 직접 확인했다. 2번과 4번은 React와 Next 공식 문서의 설명이고, 이번에 따로 측정하지는 않았다.

같은 화면을 두 방식으로

스토어 앱에 같은 화면을 두 방식으로 만들었다(실험 뒤 지웠다). 서버용 Badge, 클라이언트용 Button, 데이터 목록이 있다. 데이터에는 화면에 쓰지 않는 필드 internalMemo를 일부러 넣었다. 

// 기존 방식: pages/probe-pages.tsx
export async function getServerSideProps() {
  const items = [{ title: '공연 A', internalMemo: '화면에-안-쓰는-값-PAGES' }];
  return { props: { items } };
}

export default function ProbePages({ items }) {
  return (
    <main>
      <Badge tone="primary">서버용 배지</Badge>
      <Button variant="secondary">클라이언트 버튼</Button>
      <ul>
        {items.map((item) => (
          <li key={item.title}>{item.title}</li>
        ))}
      </ul>
    </main>
  );
}
// Server Component 방식: app/probe-app/page.tsx
async function readItems() {
  return [{ title: '공연 A', internalMemo: '화면에-안-쓰는-값-APP' }];
}

export default async function ProbeApp() {
  await connection();
  const items = await readItems(); // 컴포넌트 안에서 직접 읽는다
  return (
    <main>
      <Badge tone="primary">서버용 배지</Badge>
      <Button variant="secondary">클라이언트 버튼</Button>
      <ul>
        {items.map((item) => (
          <li key={item.title}>{item.title}</li>
        ))}
      </ul>
    </main>
  );
}

next build 뒤 next start로 띄우고, 각 페이지의 HTML과 HTML이 불러오는 브라우저 JS 파일을 모두 받아 살펴봤다.

결과 1: 브라우저로 가는 코드

브라우저 JS 안에 기존 방식 (pages) Server Component 방식 (app)
Badge 코드 (rounded-badge 클래스) 있음 없음
Button 코드 (h-[52px] 클래스) 있음 있음

Badge는 클릭할 것이 없는데도, 기존 방식에서는 하이드레이션 때문에 브라우저로 갔다. Server Component 방식에서는 Badge가 서버에서 실행돼 결과만 payload에 실리므로 코드가 가지 않았다. Button은 두 방식 모두 브라우저에서 실행해야 하므로 간다.

결과 2: 브라우저로 가는 데이터 (처음 열 때)

기존 방식의 HTML에는 그린 화면과 별도로 이런 태그가 있었다.

<script id="__NEXT_DATA__" type="application/json">
  {
    "props": {
      "pageProps": {
        "items": [
          { "title": "공연 A", "internalMemo": "화면에-안-쓰는-값-PAGES" }
        ]
      }
    },
    …
  }
</script>
기존 방식 Server Component 방식
HTML 안의 internalMemo 값 있음 __NEXT_DATA__에 props 전체 없음
데이터가 실리는 모습 그린 HTML(<li>공연 A</li>) + 원본 데이터 JSON, 두 번 그린 결과만

기존 방식은 브라우저에서 ProbePages를 다시 실행해야 하니, 그때 넘길 props 데이터를 통째로 보내야 한다. 화면에 쓰지 않는 필드까지 따라간다.

결과 3: 링크로 이동할 때 받는 것

기존 방식 Server Component 방식
요청 주소 /_next/data/<빌드 ID>/probe-pages.json /probe-app?_rsc=…
Content-Type application/json text/x-component (RSC payload)
받은 내용 {"pageProps":{"items":[{"title":"공연 A","internalMemo":"…"}]}}
원본 데이터. 브라우저가 모든 컴포넌트를 실행해 그린다 		["$","li","공연 A",{"children":"공연 A"}]
그린 결과. internalMemo는 0번 나온다

그런데 JS 전체 크기는 오히려 컸다

기존 방식 Server Component 방식
브라우저 JS 합계 (압축 전) 517,455바이트 617,159바이트
HTML 크기 2,301바이트 8,134바이트 (RSC payload가 함께 실림)

이 작은 페이지에서는 Server Component 방식이 JS가 약 100KB 더 컸다. App Router 자체의 기본 코드(라우터, RSC payload를 읽는 코드 등)가 Pages Router보다 크기 때문이다. Server Component로 줄어드는 것은 서버에서만 쓰는 컴포넌트와 그 라이브러리의 코드라서, 이 실험처럼 Badge 하나뿐이면 줄어드는 양보다 기본 코드 차이가 더 크다. 화면에 서버용 컴포넌트와 무거운 라이브러리가 많을수록 차이가 반대로 벌어진다. "Server Component를 쓰면 무조건 JS가 작아진다"가 아니라 "서버에서만 쓰는 부분의 코드를 보내지 않게 된다"로 이해해야 한다.

Server Component가 바꾼 것

기존 SSR Server Component + SSR
HTML 서버가 만든다 서버가 만든다 (015의 2단계)
하이드레이션 때 다시 실행하는 것 모든 컴포넌트 Client Component만
브라우저로 가는 컴포넌트 코드 모든 컴포넌트 Client Component만
함께 가는 데이터 props 데이터 전체 (__NEXT_DATA__) 그린 결과와 Client Component에 넘긴 props만 (RSC payload)
데이터를 읽는 곳 페이지 맨 위 getServerSideProps 필요한 컴포넌트 안 (async)
링크로 이동할 때 받는 것 원본 데이터 JSON 그린 결과 (RSC payload)

핵심은 "모든 컴포넌트"가 "Client Component만"으로 바뀐 것이다. 하이드레이션 범위가 줄어드니, 브라우저로 가는 코드와 데이터, 브라우저가 다시 하는 일이 함께 줄어든다.

SSR을 없앤 것은 아니다

Server Component는 SSR을 대신하지 않는다. 015에서 본 2단계(HTML 만들기)가 그대로 SSR이다. Server Component는 SSR 앞에 1단계(설계도 만들기)를 하나 더 둔 것이다.

  • 처음 열 때 HTML을 빨리 보여 주는 일은 여전히 SSR이 한다.
  • Server Component는 그 HTML에 이벤트를 붙이는 하이드레이션의 범위를 줄인다.
  • 링크로 이동할 때는 SSR 없이 RSC payload만 받는다(015).

대가: 서버와 클라이언트의 경계

Server Component를 쓰면 한 페이지 안에 서버에서만 도는 코드와 브라우저에서도 도는 코드가 섞인다. 그 사이의 경계를 개발자가 신경 써야 한다. 이 PR에서 겪은 일들이 모두 여기서 나왔다.

경계에서 생기는 일 이 PR에서
어느 파일에 'use client'를 붙일지 정해야 한다 store-ui 컴포넌트마다 서버용·클라이언트용을 나누고 문서에 적었다
'use client' 파일은 서버에서 이름표로만 보인다 Drawer.Root가 undefined가 됐다(014). 동적 페이지였다면 빌드를 통과하고 요청 때 터졌다
Server Component가 Client Component에 넘기는 props는 글자로 적을 수 있어야 한다 함수 props(onClick, onOpenChange)는 앱의 클라이언트 컴포넌트에서만 넘긴다
Client Component에 넘긴 props는 payload에 그대로 보인다 화면에 필요한 값만 골라 넘겨야 한다(015 "RSC payload 자세히")

우리 프로젝트에서는

  • 스토어 홈(apps/store/app/page.tsx)은 Server Component다. 컴포넌트 안에서 await fetchShows(…)로 공연 목록을 직접 읽는다. 기존 방식이었다면 getServerSideProps에 있어야 했다.
  • store-ui의 Badge, Skeleton, Pagination은 지시어 없는 컴포넌트라 Server Component에서 쓰면 코드가 브라우저로 가지 않는다. Button, TextField, Select, ToggleGroup, Drawer만 브라우저로 간다.
  • 공연 목록 화면(1.3)에서도 목록과 카드는 Server Component로 두고, 필터처럼 이벤트가 필요한 부분만 앱의 클라이언트 컴포넌트로 분리하면 브라우저로 가는 코드가 줄어든다.

스스로 확인하기

1. 기존 SSR은 HTML을 미리 만들어 주는데, 브라우저에서 컴포넌트를 다시 실행하는 이유는?

HTML에는 모양만 있고 onClick 같은 함수, 상태, 어느 컴포넌트의 결과인지가 없다. React가 컴포넌트를 다시 실행해 결과를 HTML과 맞춰 보고, 그 자리에 함수와 상태를 붙인다. 이것이 하이드레이션이다.

2. 기존 SSR은 왜 클릭할 것이 없는 컴포넌트까지 다시 실행했나?

페이지가 통째로 하나의 클라이언트 앱이라, React가 어떤 컴포넌트에 붙일 함수나 상태가 없는지 미리 알 수 없다. 그래서 모든 컴포넌트를 실행해 맞춰 봐야 했고, 모든 컴포넌트의 JS가 브라우저로 가야 했다.

3. 실험에서 기존 방식과 Server Component 방식의 브라우저 JS는 무엇이 달랐나?

기존 방식에는 Badge 코드가 있었고 Server Component 방식에는 없었다. Button 코드는 둘 다 있었다. 다만 JS 전체 크기는 App Router의 기본 코드 때문에 Server Component 방식이 약 100KB 더 컸다.

4. 화면에 쓰지 않는 데이터 필드는 두 방식에서 각각 어떻게 됐나?

기존 방식은 props 전체가 HTML 안의 __NEXT_DATA__와 이동 때의 JSON에 실려 브라우저로 갔다. Server Component 방식은 그린 결과만 RSC payload에 실려서 그 필드가 0번 나왔다.

5. Server Component가 나오면서 SSR은 없어졌나?

아니다. 처음 열 때 HTML을 만드는 2단계가 그대로 SSR이다. Server Component는 그 앞에 설계도를 만드는 1단계를 두고, 하이드레이션 범위를 Client Component로 줄였다.

6. Server Component를 쓰는 대가는 무엇인가?

서버와 클라이언트의 경계를 개발자가 관리해야 한다. 'use client'를 어디에 붙일지 정하고, 'use client' 파일은 서버에서 이름표로만 보인다는 점(Drawer.Root 문제), 함수 props를 넘길 수 없다는 점, Client Component props가 payload에 그대로 보인다는 점을 지켜야 한다.
