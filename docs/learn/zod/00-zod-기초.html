00 zod 기초: 실행 중에도 남는 타입

zod가 무엇이고 왜 쓰는지, 그리고 apps/api/src/shows/show-list-query.ts에 나오는 문법 (z.object, z.coerce, .int(), .min(), .default(), .meta(), z.infer)을 예제로 하나씩 설명한다. 모든 예제의 결과는 저장소가 쓰는 zod 4.6.7로 직접 실행해 확인했다.

한눈에 보기

zod는 "값이 이런 모양이어야 한다"는 규칙(스키마)을 자바스크립트 객체로 만들고, 실행 중에 들어온 값을 그 규칙으로 검사하는 라이브러리다. 같은 스키마에서 TypeScript 타입과 JSON Schema(OpenAPI 문서)도 뽑아낼 수 있어서, 규칙을 한 번만 적으면 된다.

스키마 하나에서 나오는 것
  1. showListQuerySchema
  2. 실행 중 검사: parse, safeParse
  3. 타입: z.infer
  4. 문서: z.toJSONSchema

이 저장소에서는 API가 GET /shows의 쿼리(page, size)를 zod로 검사한다. Nest가 zod를 어떻게 부르는지는 nest 05 문서에 있고, 이 문서는 zod 자체에 집중한다.

TypeScript 타입은 실행 중에 없다

TypeScript 타입은 컴파일할 때 검사하고 나면 지워진다. 아래 코드는 타입 검사를 통과하지만 실행하면 틀린 값을 그대로 쓴다.

interface ShowListQuery {
  page: number;
}

// 쿼리 문자열은 서버가 받는 순간에는 그냥 글자 덩어리다.
const query = req.query as ShowListQuery; // "믿어 줘"라고 적었을 뿐, 검사는 없다

query.page;         // 실제 값은 'abc' (글자)
query.page - 1;     // NaN
(query.page + 1);   // 'abc1' (글자 이어 붙이기)

컴파일된 자바스크립트에는 interface가 한 줄도 남지 않는다. 그래서 바깥에서 들어오는 값(HTTP 요청, 파일, 환경 변수, 외부 API 응답)은 타입만으로 지킬 수 없다. 직접 검사하면 이렇게 된다. 

function parseQuery(raw: Record<string, unknown>): ShowListQuery {
  const page = raw.page === undefined ? 1 : Number(raw.page);
  if (!Number.isSafeInteger(page) || page < 1) {
    throw new Error('page는 1 이상의 정수여야 합니다.');
  }
  return { page };
}

동작은 하지만 규칙이 두 군데에 있다. interface ShowListQuery(타입)와 parseQuery(검사)다. 한쪽에 size를 더하고 다른 쪽을 잊으면 둘이 어긋난다. zod는 검사 규칙을 먼저 적고, 타입은 거기서 뽑는다. 그러면 둘이 어긋날 수 없다. 

import { z } from 'zod';

const showListQuerySchema = z.object({
  page: z.coerce.number().int().min(1).default(1),
});
type ShowListQuery = z.infer<typeof showListQuerySchema>; // { page: number }

const query = showListQuerySchema.parse(req.query); // 실제로 검사하고, 통과한 값만 돌려준다

스키마 만들고 parse하기

스키마는 z.로 시작하는 함수로 만든다. 만든 스키마로 값을 검사하는 방법은 두 가지다.

const User = z.object({
  name: z.string(),
  age: z.number(),
});

// 1. parse: 통과하면 값을 돌려주고, 실패하면 ZodError를 던진다.
User.parse({ name: '영창', age: 30 });
// → { name: '영창', age: 30 }

User.parse({ name: 1 });
// → ZodError를 던진다. issues가 2개(name은 글자가 아님, age가 없음)

// 2. safeParse: 던지지 않고 결과 객체를 돌려준다.
const result = User.safeParse({ name: '영창', age: '30' });
if (result.success) {
  result.data; // 통과한 값
} else {
  result.error.issues;
  // [{ code: 'invalid_type', path: ['age'], message: 'Invalid input: expected number, received string' }]
}
parse safeParse
성공 값을 돌려줌 { success: true, data }
실패 ZodError를 던짐 { success: false, error }
언제 쓰나 실패하면 그냥 멈춰도 될 때(예: 앱이 뜰 때 환경 변수 검사) 실패를 직접 다룰 때(예: 오류를 응답으로 바꾸기)

'30'(글자)은 z.number()를 통과하지 못한다. zod는 기본으로 값을 바꾸지 않고 검사만 한다. 글자를 숫자로 바꾸려면 coerce를 쓴다.

"스키마"는 검사기다

스키마는 원래 "데이터가 어떤 모양이어야 하는지 적은 설명"이다(DB 스키마, JSON Schema처럼). zod는 이 설명을 직접 검사까지 하는 객체로 만들고, 그 객체를 스키마라고 부른다. 그래서 zod 문서에서 "스키마"는 검사기로 바꿔 읽으면 된다.

  • 스키마를 만든다 = 검사기를 조립한다. z.object(...), .int(), .default()가 하는 일이다. 서버가 켜질 때 한 번 한다.
  • 스키마로 검사한다 = 조립한 검사기에 값을 넣는다. parse, safeParse가 하는 일이다. 요청이 올 때마다 한다.
// 조립: User라는 검사기를 만든다. 아직 아무 값도 검사하지 않았다.
const User = z.object({ name: z.string(), age: z.number() });

// 검사: 값을 넣는다.
User.safeParse({ name: '영창', age: 30 }); // { success: true, data: ... }

스키마 객체 안에는 검사 함수(_zod.parse)가 들어 있고, parse와 safeParse가 그 함수를 실행한다. 큰 검사기는 작은 검사기를 품는다. User는 name을 맡은 z.string()과 age를 맡은 z.number()를 품고 있고, 이 저장소의 showListQuerySchema도 page, size 같은 필드마다 작은 검사기를 품은 큰 검사기다. 검사기를 함수로 흉내 내 보는 방법은 zod 02 문서에 있다.

체이닝: 규칙을 이어 붙이기

.int().min(1)처럼 메서드를 이어 붙일 때마다 새 스키마가 만들어진다. 원래 스키마는 바뀌지 않는다. 배열의 map이 원래 배열을 두고 새 배열을 돌려주는 것과 같다. 

const base = z.number();
const positive = base.min(1);

base.safeParse(-5).success;     // true  (base는 그대로다)
positive.safeParse(-5).success; // false

그래서 공통 규칙을 변수로 두고 필드마다 이어 붙여 써도 서로 영향을 주지 않는다.

이어 붙인 메서드가 늘 쓴 순서대로 실행되지는 않는다. .default(), .optional()은 맨 뒤에 써도 가장 먼저 값을 본다. 메서드별 실행 순서는 zod 02 문서에 있다.

숫자 규칙: number, int, min, max

문법 뜻 실패 예 오류 코드
z.number() 자바스크립트 숫자인가. NaN은 실패 '2', NaN invalid_type
.int() 정수인가. zod 4는 Number.MAX_SAFE_INTEGER(253−1)까지만 받는다 1.5, 2 ** 53 invalid_type, too_big
.min(1) 1 이상인가 0 too_small
.max(100) 100 이하인가 101 too_big

.int()가 안전한 정수까지만 받는 이유: 253을 넘으면 자바스크립트가 정수를 정확히 나타내지 못한다 (2 ** 53 === 2 ** 53 + 1이 true다). 이 저장소에서는 page가 이 범위를 넘으면 offset 계산도 믿을 수 없으므로, .max()를 따로 적지 않고 .int()에 맡겼다.

한 값이 여러 규칙에 걸리면

z.number().int().min(1).safeParse(-1.5);
// issues: [{ code: 'invalid_type', message: 'Invalid input: expected int, received number' }]
// -1.5는 1 미만이기도 하지만 오류는 하나다.

.int() 실패는 "타입이 틀렸다"(invalid_type)로 보고 거기서 멈춘다. 그래서 숫자 필드는 보통 오류가 하나다. 반면 문자열 규칙은 걸린 것을 모두 낸다. 

z.string().max(3).regex(/^[a-z]*$/).safeParse('ABCDE');
// issues: [{ code: 'too_big', ... }, { code: 'invalid_format', ... }]

coerce: 글자를 숫자로

z.coerce.number()는 검사하기 전에 값을 자바스크립트의 Number(value)로 바꾼다. 쿼리 문자열은 늘 글자로 오므로 이것이 없으면 '2'도 실패한다.

들어온 값 Number(값) z.coerce.number() 결과
'2'2통과 2
' 2'2 (앞뒤 공백 무시)통과 2
'1e1'10 (지수 표기)통과 10
'0x10'16 (16진수)통과 16
''0통과 0
true1통과 1
null0통과 0
['3']3통과 3
'abc'NaN실패 invalid_type
undefinedNaN실패 invalid_type
['1', '2']NaN실패 invalid_type

coerce는 Number()의 규칙을 그대로 따른다. 빈 글자 ''와 null이 0이 되고, '1e1'이 10이 된다. 그래서 coerce 뒤에 .int(), .min(1) 같은 규칙을 함께 걸어야 한다. ?page=(빈 값)가 400이 되는 것은 0이 .min(1)에서 걸리기 때문이다.

선택 읽기: z.coerce.boolean()의 함정

Boolean(value)를 쓰므로 글자가 비어 있지 않으면 모두 true다.

z.coerce.boolean().parse('false'); // true (!)

쿼리의 ?soldOut=false 같은 값을 다룰 때는 z.enum(['true', 'false'])로 받은 뒤 바꾸거나 zod 4의 z.stringbool()을 쓴다.

default와 optional

const page = z.coerce.number().int().min(1).default(1);

page.parse(undefined); // 1   (값이 없으면 기본값. 앞의 coerce와 검사는 거치지 않는다)
page.parse('3');       // 3
page.parse('');        // 실패: too_small (빈 글자는 "없음"이 아니다. Number('')는 0)
page.parse(null);      // 실패: too_small (null도 "없음"이 아니다. Number(null)은 0)
  • 기본값은 undefined일 때만 쓴다. 쿼리에서 ?page를 아예 빼면 undefined지만, ?page=는 빈 글자 ''다.
  • 위치는 맨 뒤여도 판단은 가장 먼저 한다. .default(1)은 앞의 스키마 전체를 감싸는 껍질이라, 값이 undefined면 안쪽(coerce, int, min)을 부르지 않고 바로 1을 돌려준다. Number(undefined)는 NaN이니, 이 순서가 아니었다면 쿼리를 생략한 요청이 실패했을 것이다. 왜 그렇게 되는지는 zod 02 문서에 있다.

값이 없어도 되지만 기본값을 넣고 싶지 않으면 .optional()을 쓴다.

z.object({ q: z.string().optional() }).parse({});  // {}      (q가 없는 채로 통과)
z.object({ q: z.string().default('') }).parse({}); // { q: '' }
z.object({ q: z.string() }).safeParse({});         // 실패: path ['q'], expected string, received undefined

object: 모르는 키는 어떻게 되나

z.object는 속성마다 스키마를 받는다. 스키마에 없는 키를 다루는 방식에 따라 세 가지가 있다.

z.object({ a: z.number() }).parse({ a: 1, b: 2 });       // { a: 1 }        버린다 (기본)
z.strictObject({ a: z.number() }).parse({ a: 1, b: 2 }); // 실패: unrecognized_keys "b"
z.looseObject({ a: z.number() }).parse({ a: 1, b: 2 });  // { a: 1, b: 2 }  그대로 둔다

이 저장소는 기본 z.object를 쓴다. 공유된 주소에 광고 추적용 ?utm_source=... 같은 값이 붙어 와도 오류를 내지 않고, 결과에는 아는 값만 남아 서비스 코드가 모르는 값을 실수로 쓰지 않는다.

여러 필드가 틀리면 필드마다 오류가 나온다. path가 어느 필드인지 알려 준다. 배열 안이면 몇 번째인지도 들어간다. 

z.object({ a: z.number(), b: z.string() }).safeParse({ a: 'x', b: 1 });
// issues: [{ path: ['a'], ... }, { path: ['b'], ... }]

z.object({ genre: z.array(z.enum(['musical', 'play'])) }).safeParse({ genre: ['musical', 'x'] });
// issues: [{ code: 'invalid_value', path: ['genre', 1], ... }]

오류와 메시지

실패하면 issues 배열이 나온다. 항목 하나는 이렇게 생겼다.

속성 뜻 예
code 어떤 종류의 실패인가 invalid_type, too_small, too_big, invalid_format
path 어디가 틀렸나 (속성 이름과 배열 위치) ['page'], ['genre', 1]
message 사람이 읽는 설명 'Too small: expected number to be >=1'

기본 문구는 영어다. 메시지는 규칙마다 바꿀 수 있고, 방법이 세 가지다.

// 1. 글자 하나 (가장 짧다. 이 저장소가 쓰는 방식)
z.number('숫자여야 합니다').safeParse('x');
// message: '숫자여야 합니다'

// 2. { error: 글자 }
z.number().min(1, { error: '1 이상' }).safeParse(0);
// message: '1 이상'

// 3. { error: 함수 } (실패 정보를 문구에 넣을 때)
z.number().min(1, { error: (issue) => `${issue.minimum} 이상이어야 함 (받은 값 ${issue.input})` }).safeParse(0);
// message: '1 이상이어야 함 (받은 값 0)'

z.number('...')처럼 타입 함수에 준 문구는 "숫자가 아니다"(invalid_type) 실패에 쓰인다. z.coerce.number(PAGE_MESSAGE)는 Number() 결과가 NaN일 때의 문구다.

z.infer, z.input, z.output

스키마에서 타입을 뽑는다. typeof showListQuerySchema는 "스키마 값의 타입"이고, z.infer가 그 안에서 "검사를 통과한 값의 타입"을 꺼낸다. 

const S = z.object({
  page: z.coerce.number().int().min(1).default(1),
  q: z.string().optional(),
  name: z.string().default('x'),
});

type In = z.input<typeof S>;
// { page?: unknown; q?: string | undefined; name?: string | undefined }

type Out = z.output<typeof S>; // z.infer와 같다
// { page: number; name: string; q?: string | undefined }
z.input (들어오는 값) z.output = z.infer (나가는 값)
.default()가 있는 속성 생략 가능 (?) 항상 있음
z.coerce.number() unknown (무엇이든 받아 바꿔 보므로) number
.optional() 생략 가능 생략 가능

핸들러와 서비스는 검사를 통과한 값을 다루므로 z.infer(= 출력)를 쓴다. 이 저장소의 ShowListQuery가 그것이다. 요청을 보내는 쪽(클라이언트)이 무엇을 생략할 수 있는지는 z.input이 말해 준다. OpenAPI 문서가 page를 필수가 아닌 것으로 보여 주는 것도 입력 쪽을 문서로 만들기 때문이다(다음 절).

meta와 JSON Schema

.meta({ description })은 검사에는 아무 영향이 없고, 스키마에 설명을 붙인다. 이 설명은 스키마를 JSON Schema로 바꿀 때 함께 나간다. 

const S = z.object({
  page: z.coerce.number().int().min(1).default(1).meta({ description: '페이지' }),
});

z.toJSONSchema(S, { io: 'input' });
// {
//   type: 'object',
//   properties: {
//     page: { default: 1, description: '페이지', type: 'integer', minimum: 1, maximum: 9007199254740991 }
//   }
// }

z.toJSONSchema(S); // io 기본값은 'output'
// { ..., required: ['page'], additionalProperties: false }

규칙이 문서로 바뀌는 대응은 이렇다.

zod JSON Schema
.int()type: 'integer', maximum: 9007199254740991
.min(1)minimum: 1
.max(100)maximum: 100
.default(1)default: 1, 입력 쪽이면 required에서 빠짐
.meta({ description })description

입력 쪽(io: 'input')에는 required가 없다. 기본값이 있어 생략해도 되기 때문이다. 출력 쪽에는 required: ['page']와 additionalProperties: false가 붙는다. 통과한 값에는 page가 반드시 있고, 모르는 키는 버려졌기 때문이다. 요청 문서에는 입력 쪽이 맞다.

~standard: 다른 도구가 zod를 읽는 문

zod 스키마에는 ~standard라는 속성이 있다. Standard Schema라는 공통 규격으로, zod·Valibot·ArkType 같은 검증 라이브러리가 같은 모양의 문을 열어 두는 약속이다. 도구는 라이브러리 이름을 몰라도 이 문만 두드리면 된다. 

Object.keys(S['~standard']);
// ['validate', 'vendor', 'version', 'jsonSchema']

await S['~standard'].validate({ page: 'x' });
// { issues: [{ code: 'invalid_type', path: ['page'], message: 'Invalid input: expected number, received NaN', ... }] }

S['~standard'].jsonSchema.input({ target: 'openapi-3.0' });
// page의 JSON Schema (위 절과 같은 내용을 OpenAPI 3.0 문법으로)
  • Nest 12의 StandardSchemaValidationPipe는 validate를 불러 요청을 검사한다(nest 05 문서).
  • @nestjs/swagger 12는 jsonSchema.input을 불러 apps/api/openapi.json의 쿼리 파라미터를 만든다.

그래서 Nest용 zod 연결 라이브러리(nestjs-zod 등) 없이 zod만 설치해도 된다. 앞에 붙은 ~는 자동 완성 목록 맨 뒤로 보내 평소 코드에서 눈에 띄지 않게 하려는 이름 규칙이다.

show-list-query.ts 한 줄씩

import { z } from 'zod';

const DEFAULT_PAGE_SIZE = 20;
// 한 번에 너무 많은 행을 읽지 않게 막는다. 스토어는 20으로 고정해 쓴다.
const MAX_PAGE_SIZE = 100;

const PAGE_MESSAGE = '1 이상의 정수여야 합니다.';
const SIZE_MESSAGE = `1 이상 ${MAX_PAGE_SIZE} 이하의 정수여야 합니다.`;

export const showListQuerySchema = z.object({
  page: z.coerce
    .number(PAGE_MESSAGE)
    .int(PAGE_MESSAGE)
    .min(1, PAGE_MESSAGE)
    .default(1)
    .meta({ description: '페이지 번호(1부터). 마지막 페이지를 넘으면 오류가 아니라 빈 items로 응답한다.' }),
  size: z.coerce
    .number(SIZE_MESSAGE)
    .int(SIZE_MESSAGE)
    .min(1, SIZE_MESSAGE)
    .max(MAX_PAGE_SIZE, SIZE_MESSAGE)
    .default(DEFAULT_PAGE_SIZE)
    .meta({ description: '페이지 크기' }),
});

export type ShowListQuery = z.infer<typeof showListQuerySchema>;
코드 하는 일 설명한 절
PAGE_MESSAGE, SIZE_MESSAGE 필드마다 문구 하나. 어느 규칙에 걸려도 같은 문구가 나온다 오류와 메시지
z.object({ ... }) 쿼리 객체 전체의 모양. 모르는 쿼리는 버린다 object
z.coerce.number(PAGE_MESSAGE) 글자를 Number()로 바꾼다. NaN이면 이 문구로 실패 coerce
.int(PAGE_MESSAGE) 안전한 정수인가. 큰 수 상한도 여기서 막는다 숫자 규칙
.min(1, ...), .max(MAX_PAGE_SIZE, ...) 범위 숫자 규칙
.default(1), .default(DEFAULT_PAGE_SIZE) 쿼리를 생략하면 쓸 값. 생략한 요청은 coerce를 거치지 않는다 default
.meta({ description }) OpenAPI 쿼리 파라미터 설명 meta
z.infer<typeof showListQuerySchema> 통과한 값의 타입 { page: number; size: number }. 컨트롤러와 서비스가 쓴다 z.infer

규칙의 순서도 뜻이 있다. coerce로 숫자가 된 다음에야 .int()와 .min()이 의미가 있고, .default()는 맨 뒤에서 전체를 감싸야 "값이 없으면 바로 기본값"이 된다. .meta()는 검사와 무관해 어디에 둬도 되지만 마지막에 두어 규칙과 설명을 나눠 읽게 했다.

값 하나가 지나가는 길

page 필드에 값이 들어왔을 때 스키마 안에서 일어나는 일이다.

  • .default(1) undefined면 바로 1을 돌려주고 끝. 아니면 안쪽으로
    • z.coerce Number(값). 'abc' → NaN
      • .number() NaN이면 실패(invalid_type, PAGE_MESSAGE)
        • .int() 정수가 아니거나 너무 크면 실패하고 여기서 멈춤
          • .min(1) 1 미만이면 실패(too_small)
들어온 page 지나간 길 결과
없음default1
'3'coerce → 3 → number ✓ → int ✓ → min ✓3
'abc'coerce → NaN → number ✗실패 invalid_type
'1.5'coerce → 1.5 → number ✓ → int ✗실패 invalid_type
''coerce → 0 → number ✓ → int ✓ → min ✗실패 too_small

세 실패 모두 메시지는 '1 이상의 정수여야 합니다.'로 같다. 이 결과가 Nest에서 어떻게 400 응답이 되는지는 nest 05 문서에 있다.

헷갈리기 쉬운 점

zod는 기본으로 값을 바꾸지 않는다. z.number()는 '2'를 거절한다. 바꾸고 싶으면 z.coerce를 명시해야 한다.

coerce는 너그럽다. '', null은 0, '1e1'은 10, 'false'는 z.coerce.boolean()에서 true다. 뒤에 범위 규칙을 꼭 함께 건다.

기본값은 undefined에만 적용된다. 빈 글자 ''와 null은 "값이 있다"로 본다.

타입 주석은 검사가 아니다. const q: ShowListQuery = req.query는 검사를 하지 않는다. 값이 그 모양인 것은 parse(또는 그것을 부르는 Nest 파이프)를 거쳤을 때뿐이다.

스스로 확인하기

1. 스키마를 이렇게 바꾸면 ?page=2는 어떻게 되는가?

parse와 coerce 절을 묻는다.

-  page: z.coerce
-    .number(PAGE_MESSAGE)
+  page: z
+    .number(PAGE_MESSAGE)
답 보기

400이 온다. 쿼리 값은 글자 '2'이고, coerce가 없으면 zod는 글자를 숫자로 바꾸지 않는다. z.number()가 invalid_type으로 실패해 올바른 요청까지 모두 막힌다. 쿼리를 생략한 요청은 .default(1) 덕분에 통과한다.

2. .default(1)을 맨 앞으로 옮길 수 있는가? 옮기면 무엇이 달라지는가?

default와 체이닝 절을 묻는다.

-  page: z.coerce.number(PAGE_MESSAGE).int(PAGE_MESSAGE).min(1, PAGE_MESSAGE).default(1)
+  page: z.coerce.number(PAGE_MESSAGE).default(1).int(PAGE_MESSAGE).min(1, PAGE_MESSAGE)
답 보기

쓸 수 없다. .default()는 스키마를 감싼 ZodDefault를 돌려주고, 여기에는 숫자 규칙 메서드(.int(), .min())가 없어 타입 오류가 난다. 체이닝은 "앞의 결과에 메서드를 부르는 것"이라, 각 메서드가 무엇을 돌려주는지에 따라 이어 붙일 수 있는 것이 정해진다. 규칙을 다 건 뒤 마지막에 기본값으로 감싸는 이유다.

3. 아래 두 줄의 결과는 각각 무엇인가?

coerce 표와 default 절을 묻는다. 스키마는 이 저장소의 page와 같다.

const page = z.coerce.number().int().min(1).default(1);
page.safeParse('0x10');
page.safeParse(null);
답 보기

'0x10'은 Number('0x10')이 16이라 통과해 16이 된다. null은 undefined가 아니라 기본값이 쓰이지 않고, Number(null)이 0이라 .min(1)에서 too_small로 실패한다. 스토어가 API를 부르기 전에 ^[1-9]\d*$로 주소를 정리하는 이유 중 하나가 이런 너그러움이다.

4. 서비스 함수의 매개변수 타입을 z.input으로 바꾸면 무엇이 문제인가?

z.infer, z.input, z.output 절을 묻는다.

-async findPage({ page, size }: ShowListQuery): Promise<ShowPageDto> {
+async findPage({ page, size }: z.input<typeof showListQuerySchema>): Promise<ShowPageDto> {
답 보기

입력 타입에서 page와 size는 unknown이고 생략 가능하다. 그래서 .limit(size)와 (page - 1) * size가 타입 오류가 난다. 서비스는 검사를 통과한 값을 받으므로 출력 타입(z.infer)이 맞다. 입력 타입은 "보내는 쪽이 무엇을 보낼 수 있나"를 나타낸다.
