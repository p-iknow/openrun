hydration 자세히

hydration은 서버가 만든 HTML에 브라우저에서 함수와 상태를 붙이는 일이다. 스토어 앱에 임시 페이지를 만들어 HTML만 있을 때와 hydration 뒤의 차이, hydration이 끝나는 시점, 서버 결과와 브라우저 결과가 다를 때(hydration 불일치) React가 하는 일을 개발 모드와 배포 빌드에서 직접 확인했다. 그리고 실무에서 마주칠 불일치 다섯 가지를 재현하고 고친 방법을 정리한다.

hydration이 하는 일

016 문서에서 본 대로, 서버가 만든 HTML에는 모양만 있다. onClick 같은 함수, useState 상태, "이 태그가 어느 컴포넌트의 결과인지"가 없다.

서버
  1. 컴포넌트를 실행해 HTML 만들기
브라우저
  1. HTML 그리기 (보이지만 안 눌림)
  2. JS 받기
  3. 컴포넌트를 다시 실행해 HTML과 맞춰 보기
  4. 함수와 상태 붙이기 (이제 눌림)

hydration은 화면을 다시 그리는 일이 아니다. 이미 그려진 HTML을 그대로 쓰고, 거기에 함수와 상태만 붙인다. 그러려면 브라우저 결과가 서버 HTML과 같아야 한다. 이 "같아야 한다"가 이 문서의 대부분을 차지한다.

Server Component를 쓰는 앱에서는 Client Component만 hydration한다. Server Component의 결과는 RSC payload에 이미 적혀 있어 다시 실행하지 않는다(016).

HTML만 있을 때와 hydration 뒤

확인에 쓴 임시 Client Component다(실험 뒤 지웠다). 누르면 숫자가 올라가는 버튼과, hydration이 끝나면 글자가 바뀌는 문단이 있다. 

'use client';

export function Basic() {
  const [count, setCount] = useState(0);
  const [done, setDone] = useState(false);
  useEffect(() => {
    // useEffect는 hydration이 끝난 뒤에만 실행된다
    window.__hydratedAt = performance.now();
    setDone(true);
  }, []);
  return (
    <>
      <button id="counter" onClick={() => setCount(count + 1)}>
        눌린 횟수 {count}
      </button>
      <p id="hydrated">{done ? 'hydration 끝' : '아직 hydration 전'}</p>
    </>
  );
}

서버가 보낸 HTML은 이렇다.

<button id="counter" type="button">눌린 횟수 <!-- -->0</button>
<p id="hydrated">아직 hydration 전</p>
  • onClick에 해당하는 것이 HTML 어디에도 없다. onclick 속성도 없다.
  • <!-- -->는 React가 넣은 표시다. "눌린 횟수 "와 {count}가 따로 된 글자 조각이라는 것을 hydration 때 구분하려고 둔다.

이 HTML을 JS 실행을 막은 iframe(sandbox)에 넣으면 "JS가 아직 오지 않은 상태"를 만들 수 있다. 같은 버튼을 두 상태에서 눌러 비교했다.

HTML만 (JS 실행 막음) hydration 뒤
버튼을 누르면 0 → 0 두 번 눌러도 그대로 0 → 1
문단 글자 아직 hydration 전 hydration 끝
버튼 요소의 React 연결 표시 (__reactFiber$… 속성) 없음 있음
버튼의 onclick 속성 없음 여전히 없음

hydration 뒤에도 onclick 속성이 없는 것이 흥미롭다. React는 버튼마다 이벤트를 붙이지 않고, 앱의 맨 바깥 요소 한 곳에서 모든 클릭을 받아 해당 컴포넌트의 onClick을 불러 준다(React 공식 설명의 이벤트 위임). 버튼 요소에 붙는 것은 "이 요소는 이 컴포넌트의 것"이라는 연결 표시(__reactFiber$…)다.

언제 끝나나

첫 화면이 그려진 시각(First Contentful Paint)과, hydration이 끝나야 실행되는 useEffect가 기록한 시각을 비교했다. 내 컴퓨터, 로컬 서버 기준이다.

첫 화면 hydration 끝
개발 모드 (next dev) 40ms 67ms
배포 빌드 (next start) 40ms 37ms
  • 개발 모드에서는 첫 화면이 보이고 약 27ms 동안 "보이지만 안 눌리는" 구간이 있었다. 배포 빌드는 JS가 작고 빨라서 이 컴퓨터에서는 첫 화면과 거의 같은 때 끝났다.
  • 이 구간은 JS를 받고 실행하는 시간만큼 생긴다. 느린 휴대폰이나 느린 네트워크, Client Component가 많은 페이지에서는 길어진다. 이번에는 그런 환경을 측정하지 않았다.
  • Client Component를 줄이면 받고 실행할 JS가 줄어 이 구간도 짧아진다. Server Component가 hydration 범위를 줄인 이유가 이것이다.

어떻게 맞춰 보나

  1. 컴포넌트를 실행한다 브라우저에서 Client Component를 실행해 "이런 태그, 이런 글자, 이런 속성이어야 한다"는 결과를 얻는다.
  2. 이미 있는 DOM과 하나씩 비교한다 위에서부터 차례로 태그 이름, 글자, 속성이 서버 HTML로 만들어진 DOM과 같은지 본다.
  3. 같으면 그 DOM을 그대로 쓴다 새로 만들지 않고 연결 표시와 이벤트만 붙인다. 화면이 깜빡이지 않는 이유다.

그래서 서버와 브라우저에서 같은 입력이면 같은 결과가 나와야 한다. 서버에는 없고 브라우저에만 있는 값(localStorage, window 크기 등)으로 결과를 바꾸면 비교가 실패한다.

useId는 이 비교를 통과하도록 만든 id다. 같은 실험 페이지에서 서버 HTML의 id와 hydration 뒤 브라우저의 id가 둘 다 _R_2atpesnelb_로 같았다. 무작위 값이 아니라 트리 안 위치로 만들기 때문이다.

맞지 않으면 React는 무엇을 하나

불일치는 두 종류로 나뉘고, React가 하는 일이 다르다. 아래 "실무에서 마주치는 불일치"의 실험에서 확인한 결과다.

종류 개발 모드 콘솔 배포 빌드 콘솔 화면은
글자, 태그가 다름 "Hydration failed … this tree will be regenerated on the client" + 차이 표시 "Minified React error #418" 복구됨 서버 HTML을 버리고 브라우저에서 새로 그린다. 브라우저 값이 보인다
속성이 다름 "some attributes … didn't match … This won't be patched up" 아무것도 안 나옴 안 고쳐짐 DOM에는 서버 값이 남고, React는 브라우저 값을 알고 있다. 둘이 어긋난 채로 남는다

개발 모드의 차이 표시 읽는 법

개발 모드 오류에는 어느 컴포넌트의 어디가 다른지가 나온다. localStorage 사례의 실제 메시지 끝부분이다.

<ProbeHyd>
  <main>
    <StorageBad>
      <p id="out">
+       3
-       0
  • +는 브라우저(클라이언트)에서 나온 값, -는 서버 HTML에 있던 값이다.
  • 위의 컴포넌트 이름(StorageBad)을 따라가면 어느 코드에서 생겼는지 찾을 수 있다.

"복구됨"도 공짜가 아니다. 서버가 만든 HTML을 버리고 그 트리를 브라우저에서 처음부터 다시 그리므로, SSR로 얻은 이점이 그 부분에서 사라지고 화면이 한 번 바뀐다. 그리고 속성 불일치는 배포 빌드에서 소리 없이 남는다. 그래서 불일치는 개발 모드 콘솔에서 보일 때 바로 고쳐야 한다.

실무에서 마주치는 불일치

Math.random(), Date.now() 같은 교과서 예제 말고, 공연 예매 서비스에서 실제로 나올 만한 경우를 재현했다. 경우마다 문제 버전과 고친 버전을 따로 띄워 개발 모드 콘솔과 화면을 확인했다.

경우 원인 분류 고친 방법
1. 최근 본 공연 수 (localStorage) 브라우저에만 있는 값 서버 값으로 먼저 그리고, hydration 뒤 바꾸기
2. 모바일 필터와 데스크톱 칩 (화면 폭) 브라우저에만 있는 값 둘 다 그리고 CSS로 하나만 보이기
3. 공연 카드 안의 예매 링크 잘못된 HTML 구조 링크를 겹치지 않기
4. 라벨과 입력 칸 id 실행할 때마다 다른 값 useId
5. 브라우저 확장 바깥에서 DOM을 바꿈 막을 수 없는 부분과 할 수 있는 부분 나누기

1. 최근 본 공연 수 (localStorage)

상황: 사용자가 본 공연 목록을 localStorage에 저장해 두고, 헤더에 "최근 본 공연 3개"를 보여 준다. 

// ❌ 문제 버전
export function RecentCount() {
  // 서버에는 localStorage가 없어서 0, 브라우저에서는 저장된 개수
  const count = typeof window === 'undefined' ? 0 : readRecentCount();
  return <p>최근 본 공연 {count}개</p>;
}

증상: 서버 HTML은 "0개", 브라우저 결과는 "3개"라서 "Hydration failed"가 나고 차이 표시는 + 3 / - 0이었다. 트리를 다시 그려 화면은 "3개"가 됐다. 배포 빌드에서는 #418 오류였다.

typeof window로 서버와 브라우저를 나누는 것 자체가 불일치를 만든다. hydration은 브라우저에서 실행되지만, 결과는 서버와 같아야 하기 때문이다. 

// ✅ 고친 버전
function subscribe(callback: () => void) {
  window.addEventListener('storage', callback);
  return () => window.removeEventListener('storage', callback);
}

export function RecentCount() {
  const count = useSyncExternalStore(
    subscribe,
    readRecentCount, // 브라우저 값
    () => null, // 서버와 hydration 때 쓰는 값
  );
  return (
    <p>{count === null ? '불러오는 중' : `최근 본 공연 ${count}개`}</p>
  );
}
  • useSyncExternalStore의 세 번째 인자(서버용 값)는 서버에서 그릴 때와 hydration 때 둘 다 쓰인다. 그래서 두 결과가 "불러오는 중"으로 같아 통과하고, hydration이 끝난 뒤 브라우저 값(3개)으로 다시 그린다. 확인해 보니 오류 없이 "최근 본 공연 3개"가 보였다.
  • useEffect에서 읽어 useState에 넣어도 같은 효과다. useSyncExternalStore는 다른 탭에서 값이 바뀔 때(storage 이벤트)도 따라간다는 점이 낫다.
  • 값이 화면 구조를 크게 바꾼다면(로그인 여부, 테마 등) "불러오는 중"이 거슬린다. 그때는 값을 쿠키에 두고 서버가 요청에서 읽어 처음부터 맞게 그리는 편이 낫다.

2. 모바일 필터와 데스크톱 칩 (화면 폭)

상황: 1.3의 목록 화면에서 모바일은 "필터 열기" 버튼(바텀 시트), 데스크톱은 필터 칩 줄을 보여 준다. 

// ❌ 문제 버전
export function Filters() {
  // 서버는 화면 폭을 모르니 모바일로 가정한다
  const isMobile =
    typeof window === 'undefined' ? true : window.innerWidth < 768;
  return isMobile ? <MobileFilterButton /> : <FilterChips />;
}

증상: 데스크톱(폭 1920px) 브라우저에서 "Hydration failed", 차이 표시는 + <p>(칩 줄) / - <button>(시트 버튼)이었다. 화면 폭을 읽는 useMediaQuery 같은 훅을 첫 그리기에 바로 쓰면 똑같은 문제가 생긴다. 

// ✅ 고친 버전: 둘 다 그리고 CSS로 하나만 보인다
export function Filters() {
  return (
    <>
      <div className="md:hidden">
        <MobileFilterButton />
      </div>
      <div className="hidden md:block">
        <FilterChips />
      </div>
    </>
  );
}
  • 서버와 브라우저의 HTML이 같다. 어느 쪽을 보일지는 브라우저의 CSS가 정한다. 확인해 보니 오류 없이 데스크톱 폭에서 칩 줄만 보였다.
  • 첫 화면부터 맞는 쪽이 보여서 깜빡임도 없다. 반응형은 가능하면 JS가 아니라 CSS로 나눈다.
  • 둘 다 그리기에 너무 무겁다면, 서버용 값으로 먼저 그리고 hydration 뒤 바꾸는 방식(1번)을 쓴다. 대신 첫 화면이 한 번 바뀐다.

3. 공연 카드 안의 예매 링크

상황: 공연 카드 전체를 상세 페이지 링크로 감싸고, 카드 안에 "예매하기" 링크를 또 넣었다.

// ❌ 문제 버전 (Server Component여도 생긴다)
<a href="/shows/1">
  <span>공연 A</span>
  <a href="/shows/1/book">예매하기</a>
</a>

증상: React 코드는 같은데도 불일치가 난다. 원인은 브라우저의 HTML 해석이다.

모습
서버가 보낸 글자 <a …><span>공연 A</span><a …>예매하기</a></a> (겹침)
브라우저가 해석한 DOM <a …><span>공연 A</span></a><a …>예매하기</a> (나란히 떼어 놓음)

HTML 규칙상 링크 안에 링크를 둘 수 없어서 브라우저가 HTML을 읽으며 구조를 고쳐 버린다. React가 기대한 구조와 달라 "Hydration failed"가 났다. 오류 메시지의 원인 목록에도 "Invalid HTML tag nesting"이 있다. 

// ✅ 고친 버전: 링크를 겹치지 않는다
<div>
  <Link href="/shows/1">공연 A</Link>
  <Link href="/shows/1/book">예매하기</Link>
</div>
  • 확인해 보니 오류가 없었다.
  • 카드 전체를 눌러도 상세로 가게 하고 싶으면, 상세 링크에 after:absolute after:inset-0처럼 카드 전체를 덮는 영역을 주고 예매 링크를 그 위(relative z-…)에 둔다. 링크는 겹치지 않으면서 카드 전체가 눌린다.
  • 같은 원리로 HTML 규칙을 어기는 중첩은 모두 위험하다. 예를 들어 <p> 안에 <div>(Skeleton처럼 div로 된 컴포넌트를 문단 안에 넣는 경우)도 HTML 규칙 위반이다. 이번에 따로 실험하지는 않았다.

4. 라벨과 입력 칸 id

상황: 라벨과 입력 칸을 잇거나 aria-describedby를 걸려고 id가 필요해서 crypto.randomUUID()로 만들었다. 

// ❌ 문제 버전
const [id] = useState(() => crypto.randomUUID()); // 서버와 브라우저가 따로 만든다
return (
  <>
    <label htmlFor={id}>공연 제목</label>
    <input id={id} />
  </>
);

증상: 앞의 경우들보다 위험하다. 속성 불일치라서 React가 고치지 않는다.

개발 모드 배포 빌드
콘솔 "attributes … didn't match … won't be patched up" 아무것도 안 나옴
DOM의 input id 서버가 만든 값 (예: cf9cad65-…)
React가 알고 있는 id 브라우저가 만든 다른 값 (예: 25c854fe-…)

지금은 label과 input이 둘 다 서버 값이라 우연히 서로 맞는다. 하지만 hydration 뒤에 새로 그려지는 요소(예: 입력 오류가 나면 나타나는 안내 문구의 aria-describedby)는 React가 아는 id를 쓰므로 가리킬 대상이 없다. 스크린 리더 사용자만 겪는 문제라 눈으로는 찾기 어렵고, 배포 빌드에서는 경고도 없다. 

// ✅ 고친 버전
const id = useId(); // 트리 안 위치로 만들어 서버와 브라우저가 같다

확인해 보니 label의 for와 input의 id가 서버와 브라우저 모두 _R_2atpesnelb_로 같았다.

5. 브라우저 확장

상황: 실험하다가 실제로 겪었다. 사전 확장 프로그램을 켠 Chrome에서 아무 문제 없는 페이지를 열었는데 "Hydration failed"가 났다. 차이 표시에 React가 만든 적 없는 것이 있었다. 

<div
+ hidden={true}
- hidden={null}
- data-wxt-integrated=""
>
+ <Suspense name="Next.Metadata">
- <div id="__endic_crx__">
  • 확장이 React보다 먼저 페이지의 <body> 안에 속성과 요소를 넣어서, 서버 HTML과 브라우저 결과가 달라졌다.
  • React가 트리를 브라우저에서 다시 그리면서 부작용도 생겼다. useId 값이 서버의 _R_95esnelb_에서 브라우저 형식의 _r_0_로 바뀌었다.
  • 확장을 끄자 같은 페이지에서 오류가 사라졌다.

할 수 있는 것과 없는 것:

  • 사용자가 어떤 확장을 쓰는지는 막을 수 없다. 그래서 복구되는(트리를 다시 그리는) 불일치는 앱이 견딜 수 있어야 한다.
  • 개발할 때는 확장을 끈 Chrome 프로필이나 시크릿 창으로 확인한다. 그래야 내 코드의 불일치와 확장의 불일치가 섞이지 않는다.
  • <html>, <body>의 속성만 바꾸는 확장(다크 모드 확장 등) 때문이라면 그 요소에 suppressHydrationWarning을 붙여 경고를 끌 수 있다. React 문서에 따르면 이 속성은 그 요소 한 단계의 속성과 글자에만 듣고, 이번처럼 요소를 끼워 넣는 경우는 막지 못한다.

불일치를 고치는 순서

  1. 개발 모드 콘솔의 차이 표시를 읽는다 +(브라우저)와 -(서버) 값, 위의 컴포넌트 이름으로 어느 코드인지 찾는다. 배포 빌드의 #418만으로는 어디인지 알 수 없다.
  2. 확장 때문인지부터 가린다 차이 표시에 내가 만든 적 없는 속성이나 요소가 있으면 확장을 끈 창에서 다시 연다.
  3. 원인을 분류한다 브라우저에만 있는 값인가(localStorage, 화면 폭, 브라우저 시간대), 실행할 때마다 다른 값인가(랜덤 id), HTML 구조 문제인가(링크 겹침).
  4. 분류에 맞는 방법을 고른다 아래 표에서 위쪽 방법일수록 깜빡임이 없다.
  5. 속성 불일치는 특히 꼼꼼히 본다 배포 빌드에서는 경고 없이 남는다. 개발 모드에서 "won't be patched up" 경고가 한 번이라도 보이면 넘기지 않는다.
방법 쓰는 때 예
서버와 브라우저가 같은 결과를 내게 한다 CSS로 나눌 수 있거나, 같은 값을 만들 수 있을 때 화면 폭 → CSS, 랜덤 id → useId, 링크 겹침 → 구조 바꾸기
서버도 그 값을 알게 한다 값이 첫 화면 구조를 크게 바꿀 때 로그인 여부, 테마를 쿠키에 두고 서버가 요청에서 읽기
서버 값으로 먼저 그리고 hydration 뒤 바꾼다 브라우저에만 있는 값이고, 첫 화면이 한 번 바뀌어도 될 때 최근 본 공연 → useSyncExternalStore(서버용 값)나 useEffect
suppressHydrationWarning 다른 방법이 없고, 그 요소 한 단계의 글자나 속성만 다를 때 <html>, <body>를 바꾸는 확장

suppressHydrationWarning은 경고만 끈다. 속성 불일치라면 DOM과 React가 어긋난 채 남는 것은 그대로다. 내 코드가 원인이라면 위의 세 방법으로 고친다.

우리 프로젝트에서는

  • store-ui의 ToggleGroup(packages/store-ui/src/toggle-group.tsx)은 라벨과 칩 묶음을 이을 때 useId를 쓴다. 4번 경우를 이미 피하고 있다. Base UI 컴포넌트(Select, Drawer 등)도 안에서 같은 방식으로 id를 만든다.
  • 1.3의 목록 화면에서 모바일 필터 시트(Drawer)와 데스크톱 필터 칩 줄은 2번처럼 CSS로 나눈다. 화면 폭을 JS로 읽어 하나만 그리지 않는다.
  • 1.3의 공연 카드는 3번처럼 링크를 겹치지 않는다. 카드 전체를 누르게 하려면 덮는 영역 방식을 쓴다.
  • "최근 본 공연"처럼 브라우저에만 있는 값을 보여 줄 일이 생기면 1번 방식(useSyncExternalStore의 서버용 값)을 쓴다.
  • 개발할 때 hydration 경고를 확인하려면 확장을 끈 Chrome 프로필을 쓴다.

스스로 확인하기

1. hydration 전에는 버튼이 왜 눌리지 않나? hydration 뒤 버튼 요소에는 무엇이 생기나?

HTML에는 onClick 함수가 없다. hydration이 끝나야 React가 그 요소를 컴포넌트와 연결한다. 실험에서 hydration 뒤 버튼에는 __reactFiber$… 연결 표시가 생겼지만 onclick 속성은 여전히 없었다. React는 앱 바깥 요소 한 곳에서 클릭을 받아 전달한다.

2. 글자가 다른 불일치와 속성이 다른 불일치는 React가 어떻게 다르게 처리하나?

글자나 태그가 다르면 서버 HTML을 버리고 브라우저에서 다시 그려 복구한다(개발: Hydration failed, 배포: #418). 속성이 다르면 고치지 않는다. DOM에는 서버 값이 남고 React는 브라우저 값을 알고 있어 어긋난 채 남는다. 배포 빌드에서는 경고도 없다.

3. typeof window로 서버와 브라우저를 나눠 값을 고르면 왜 불일치가 나나?

hydration은 브라우저에서 실행되므로 브라우저 쪽 값이 나온다. 그런데 hydration의 결과는 서버 HTML과 같아야 한다. 서버 쪽 값으로 만든 HTML과 브라우저 쪽 값으로 만든 결과가 다르니 비교가 실패한다.

4. useSyncExternalStore의 세 번째 인자는 언제 쓰이고, 왜 불일치를 막나?

서버에서 그릴 때와 hydration 때 둘 다 쓰인다. 두 번 모두 같은 값(예: null)이니 결과가 같아 통과하고, hydration이 끝난 뒤 브라우저 값으로 다시 그린다.

5. 공연 카드 전체를 링크로 감싸고 안에 예매 링크를 넣으면, Server Component여도 불일치가 나는 이유는?

브라우저가 HTML을 해석할 때 링크 안의 링크를 허용하지 않아 둘을 나란히 떼어 놓는다. React가 기대한 겹친 구조와 실제 DOM이 달라진다. 링크를 겹치지 않게 구조를 바꾼다.

6. 확장 때문에 생긴 불일치에 suppressHydrationWarning을 붙이면 해결되나?

html, body의 속성만 바꾸는 확장이면 그 요소에 붙여 경고를 끌 수 있다. 하지만 그 요소 한 단계에만 들어서, 이번처럼 body 안에 요소를 끼워 넣는 확장은 막지 못한다. 사용자 환경은 막을 수 없으니 복구되는 불일치를 견디게 하고, 개발할 때는 확장을 끈 창으로 확인한다.
