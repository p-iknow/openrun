Storybook 설정과 스토리 문법

packages/store-ui의 Storybook이 어떤 설정 파일로 돌아가는지 보고, badge.stories.tsx를 위에서 아래로 읽으며 meta, argTypes, args, render와 satisfies 같은 TypeScript 문법을 정리한다. 이어서 Skeleton과 토큰 화면에만 있는 문법, 루트 빌드와의 연결을 본다.

한눈에 보기

.storybook/ 폴더는 Storybook 앱 자체를 설정하고, *.stories.tsx는 화면에 보여 줄 예시를 적는다. 스토리 파일은 export default로 파일 정보(meta)를, 이름 있는 export로 스토리 하나하나를 내보낸다.

  2. main.ts 읽기
  3. *.stories.tsx 수집
  4. Vite + Tailwind로 번들

  1. preview.ts 실행
  2. storybook.css 적용

main.ts: 본체 설정

// packages/store-ui/.storybook/main.ts
import type { StorybookConfig } from '@storybook/react-vite';
import tailwindcss from '@tailwindcss/vite';

const config: StorybookConfig = {
  framework: '@storybook/react-vite',
  stories: ['../src/**/*.stories.tsx'],
  addons: ['@storybook/addon-docs', '@storybook/addon-a11y'],
  core: {
    disableTelemetry: true,
  },
  viteFinal(viteConfig) {
    viteConfig.plugins = [...(viteConfig.plugins ?? []), tailwindcss()];
    return viteConfig;
  },
};

export default config;
항목 뜻
framework "React 컴포넌트를 Vite로 번들해서 보여 줘"라는 뜻이다. Storybook은 React, Vue, Svelte 등을 모두 지원하므로 무엇을 쓰는지 알려 줘야 한다. Next.js 앱이 아니라 순수 React 라이브러리라 react-vite를 골랐다.
stories 스토리 파일을 찾을 glob 패턴이다. 경로는 .storybook/ 폴더 기준이라 ../src로 시작한다. **는 모든 하위 폴더라서 src/docs/tokens.stories.tsx도 잡힌다.
addons 기능 확장. 다음 절에서 본다.
core.disableTelemetry Storybook은 기본으로 익명 사용 통계를 보낸다. 이 설정으로 끈다.
viteFinal Storybook이 내부에서 만든 Vite 설정을 마지막에 한 번 손볼 기회다. 여기서 Tailwind v4의 Vite 플러그인을 끼워 넣어, CSS의 @import 'tailwindcss'가 실제 유틸리티 클래스로 바뀌게 한다.

viteFinal 안의 한 줄을 풀면 이렇다.

  1. viteConfig.plugins ?? [] 기존 플러그인 목록이 없으면(undefined) 빈 배열로 대신한다. ??는 왼쪽이 null이나 undefined일 때만 오른쪽을 쓴다.
  2. [...기존, tailwindcss()] 기존 플러그인을 펼쳐 놓고 맨 뒤에 Tailwind를 붙인 새 배열을 만든다. 기존 플러그인을 덮어쓰지 않는 것이 핵심이다.

애드온 두 개

애드온 하는 일
@storybook/addon-docs 스토리에서 Docs 페이지를 만든다. 컴포넌트 설명, props 표, 모든 스토리 미리보기가 한 페이지에 모인다.
@storybook/addon-a11y 스토리마다 Accessibility 탭을 붙인다. 안에서 axe-core 검사기를 돌려 색 대비 부족, 라벨 없는 버튼 같은 접근성 위반을 보여 준다. 위반이 있어도 빌드는 실패하지 않는다.

Storybook 9부터 Docs는 core에서 분리돼 따로 설치한다. 반대로 Controls, Actions, Viewport처럼 예전 "essentials" 묶음에 있던 기능은 core에 들어가서 addons에 적지 않는다.

preview.ts: 공통 적용

// packages/store-ui/.storybook/preview.ts
import type { Preview } from '@storybook/react-vite';
import './storybook.css';

const preview: Preview = {};

export default preview;

main.ts가 Storybook 서버(Node) 쪽 설정이라면, preview.ts는 스토리가 그려지는 브라우저(iframe) 쪽 설정이다. 핵심은 import './storybook.css' 한 줄이다. 이 줄 덕분에 모든 스토리에 Tailwind, 토큰, 폰트가 적용된다.

preview 객체는 지금 비어 있다. 나중에 모든 스토리 공통 parameters나 decorators(스토리를 감싸는 래퍼, 예: 테마 Provider)를 여기에 넣는다.

storybook.css: 스타일 연결

/* packages/store-ui/.storybook/storybook.css */
@import 'tailwindcss';
@import '../src/tokens.css';

/* 스토리와 컴포넌트가 쓰는 클래스를 소스에서 찾는다. */
@source '../src';
  • @import 'tailwindcss': Tailwind v4를 불러온다. v4는 tailwind.config.js 대신 CSS 안에서 설정한다.
  • @import '../src/tokens.css': 디자인 토큰(@theme 블록)을 불러온다. 이 덕분에 bg-primary, gap-sm, rounded-card 같은 의미 토큰 클래스가 생긴다.
  • @source '../src': Tailwind에게 이 폴더 파일을 훑어 실제로 쓰인 클래스만 CSS로 만들라고 알린다. 경로는 이 CSS 파일 기준이다. 
@font-face {
  font-family: 'Pretendard Variable';
  src: url('../node_modules/pretendard/dist/web/variable/woff2/PretendardVariable.woff2')
    format('woff2');
  font-weight: 45 920;
  font-display: swap;
}

:root {
  --font-pretendard: 'Pretendard Variable';
}

body {
  font-family: var(--font-sans);
  color: var(--color-text);
}
  • 스토어 앱은 next/font/local로 폰트를 불러오지만 Storybook에는 Next.js가 없다. 그래서 같은 폰트 파일을 표준 CSS @font-face로 직접 불러온다.
  • font-weight: 45 920: 가변(Variable) 폰트라 굵기 범위를 적는다. 범위 안의 어떤 굵기든 쓸 수 있다.
  • font-display: swap: 로딩 중에는 기본 폰트로 먼저 보여 주고, 로드되면 바꾼다.
  • 토큰의 --font-sans는 --font-pretendard를 읽는다. 스토어에서는 next/font가 이 변수를 만들고 Storybook에서는 :root가 만든다. 그래서 토큰 파일을 고치지 않고 양쪽에서 같은 폰트가 나온다.
  • url('../node_modules/...')는 Vite가 빌드할 때 파일을 찾아 결과물에 복사한다.

CSF의 두 규칙

스토리 파일은 CSF(Component Story Format)라는 규칙을 따른다. 규칙은 두 가지뿐이다.

  1. export default → meta 이 파일 전체에 대한 정보다. 사이드바 위치, 다루는 컴포넌트, 기본 props를 적는다.
  2. 이름 있는 export → 스토리 하나 export 하나가 사이드바 항목 하나가 된다. export 이름이 곧 스토리 이름이다.

아래에서는 badge.stories.tsx를 파일 위에서 아래 순서로 읽는다. import → 톤 목록 → meta → 스토리 순이다.

import type과 .js 확장자

import type { Meta, StoryObj } from '@storybook/react-vite';
import { Badge, type BadgeTone } from './badge.js';
  • 타입만 가져올 때는 type을 붙인다. tsconfig의 verbatimModuleSyntax: true 때문에 필수다. 컴파일된 JS에서 지워질 import임을 분명히 한다. Meta, StoryObj는 타입이라 줄 전체에, BadgeTone은 값인 Badge와 같은 줄이라 이름 앞에 붙였다.
  • .tsx 파일을 ./badge.js로 import하는 것은 moduleResolution: "nodenext" 규칙이다. 빌드 후 실제 파일 이름에 맞춰 적는다.

tones: 톤 목록 만들기

// Record로 적어 Badge에 톤이 추가되면 여기서 타입 오류가 난다.
const toneSet = {
  neutral: true,
  primary: true,
  success: true,
  warning: true,
  danger: true,
} satisfies Record<BadgeTone, true>;
const tones = Object.keys(toneSet) as BadgeTone[];

tones는 톤 5개 배열이다. 뒤에서 Controls 선택지(argTypes)와 AllTones 스토리가 함께 쓴다.

  • Record<K, V>는 "키는 K 전부, 값은 V"인 객체 타입이다. Record<BadgeTone, true>는 모든 톤이 키로 있어야 한다.
  • satisfies는 "이 타입에 맞는지 검사만 한다"는 뜻이다. meta에서 한 번 더 나오고, satisfies 절에서 자세히 본다.
  • Badge에 info 톤을 추가하면 여기서 "info가 없다"는 오류가 난다. 배열 ['neutral', ...]로 적으면 빠뜨려도 오류가 나지 않는다.
  • Object.keys()는 TypeScript에서 항상 string[]을 돌려줘서 as BadgeTone[]로 좁힌다. 바로 위에서 키를 검사했으니 안전한 단언이다.

meta: 파일 정보

const meta = {
  title: 'Components/Badge',
  component: Badge,
  tags: ['autodocs'],
  parameters: {
    docs: {
      description: { component: '**서버용** 컴포넌트다. ...' },
    },
  },
  argTypes: {
    tone: { control: 'inline-radio', options: tones },
  },
  args: {
    children: '배지',
  },
} satisfies Meta<typeof Badge>;

export default meta;
항목 뜻
title 사이드바 위치. /가 폴더 구분이라 Components 폴더 안의 Badge가 된다. 토큰 화면은 Foundations/Tokens라 다른 폴더로 간다.
component 이 스토리들이 다루는 컴포넌트. Storybook이 TypeScript props 타입을 분석해 Docs 페이지의 props 표와 Controls를 만든다. SkeletonProps의 /** */ 주석도 props 설명으로 나온다.
tags: ['autodocs'] Docs 페이지를 자동 생성한다. 사이드바에 Docs 항목이 생기고 모든 스토리가 한 페이지에 모인다. 토큰 화면에는 이 태그가 없어 Docs 항목 없이 스토리만 보인다.
parameters 스토리의 표시 방식 설정. docs.description.component는 Docs 페이지 맨 위의 설명이고 마크다운이라 **굵게**, `코드`가 먹힌다.
argTypes prop을 Controls 패널에서 어떻게 조작할지 정한다. 다음 절에서 자세히 본다.
args 컴포넌트에 넘길 props 기본값. 이 파일의 모든 스토리에 children: '배지'가 들어간다.
satisfies Meta<...> meta 형식이 맞는지 검사한다. 왜 : Meta가 아닌지는 뒤에서 본다.

argTypes: Controls 정하기

argTypes: {
  tone: { control: 'inline-radio', options: tones },
},

args와 argTypes의 차이

args argTypes
무엇 prop에 넣을 값 그 prop을 어떻게 보여 주고 조작할지
예 children: '배지' tone은 라디오 버튼, 선택지는 5개
비유 입력칸에 든 내용 입력칸의 종류(텍스트칸, 라디오, 드롭다운)

argTypes는 값을 정하지 않는다. Controls 패널 UI만 정한다.

한 줄씩 보기

  • tone: Badge의 tone prop에 대한 설정이다.
  • control: 'inline-radio': 라디오 버튼을 가로 한 줄로 보여 준다. 'radio'(세로), 'select'(드롭다운), 'check'(여러 개 선택), 'text', 'boolean', 'number', 'color' 등도 있다. 선택지가 적으면 한눈에 보이는 inline-radio, 많으면 select가 낫다.
  • options: tones: 선택지다. 앞에서 만든 톤 5개 배열이다.

왜 직접 적나

Storybook은 component의 TypeScript 타입을 분석해 Controls를 자동으로 만든다. tone?: 'neutral' | 'primary'처럼 글자 그대로 적힌 유니언이면 선택지를 알아낸다. 그런데 Badge의 톤 타입은 cva 설정에서 계산해 뽑는다. 

export type BadgeTone = NonNullable<VariantProps<typeof badgeVariants>['tone']>;

타입 분석기(react-docgen)는 코드를 실행하거나 이런 타입을 계산하지 않고 글자만 읽는다. 그래서 보통 다섯 값을 알아내지 못해, 쓸모없는 텍스트칸이 나오거나 control이 나오지 않는다. argTypes로 "이 prop은 이 다섯 중 하나"라고 직접 알려 준다.

options: tones로 재사용하는 이유

  1. Badge에 info 톤을 추가한다 cva 설정에 한 줄 넣는다.
  2. toneSet에서 타입 오류가 난다 satisfies Record<BadgeTone, true>가 info가 없다고 알린다.
  3. 고치면 tones에 info가 들어간다
  4. Controls와 AllTones에 자동으로 생긴다 선택지를 여기 다시 적지 않았으므로 한 곳만 고치면 된다.

스토리와 args 합치기

type Story = StoryObj<typeof meta>;

export const Neutral: Story = { args: { tone: 'neutral' } };
export const Primary: Story = { args: { tone: 'primary' } };
  • export 이름이 스토리 이름이다. Neutral은 "Neutral", AllTones는 낱말을 띄어 "All Tones"로 나온다.
  • args는 합쳐진다. meta의 { children: '배지' }와 스토리의 { tone: 'neutral' }가 합쳐져 <Badge tone="neutral">배지</Badge>가 된다. 같은 키가 있으면 스토리 쪽이 이긴다.
  • render가 없으면 Storybook이 알아서 <meta.component {...args} />로 그린다.
  • type Story는 StoryObj<typeof meta>를 짧게 부르는 별칭이다. 스토리가 6개라 매번 길게 적지 않으려고 만들었다.

satisfies Meta와 StoryObj

children은 Badge의 필수 prop인데, 스토리는 tone만 적었다. 그래도 타입 오류가 없는 것은 meta가 children을 줬다는 사실을 TypeScript가 알기 때문이다. 이걸 가능하게 하는 것이 satisfies다. 

const meta = { ... } satisfies Meta<typeof Badge>;
type Story = StoryObj<typeof meta>;
쓰는 법 meta의 타입 스토리의 props 검사
const meta: Meta<typeof Badge> = {...} 넓은 Meta<...>로 덮어써진다. 어떤 args를 줬는지 잊는다. 허술 모든 prop을 선택으로 본다. meta와 스토리 어디에도 children이 없어도 오류가 나지 않는다.
const meta = {...} satisfies Meta<typeof Badge> 형식만 검사하고 적은 내용을 기억한다 선택 meta에서 준 children만 선택이 되고, 나머지 필수 prop은 계속 필수다. 빠뜨리면 오류가 난다.

meta의 args에서 children을 지우면 satisfies에서는 Neutral 등에서 "children이 없다"는 오류가 난다. : Meta였다면 오류 없이 글자 없는 빈 배지를 그린다. satisfies는 필수 prop을 빠뜨린 실수를 잡아 준다. Storybook 공식 문서도 이 패턴을 권한다.

  • typeof Badge: Badge 값(함수)에서 타입을 뽑는다. Storybook이 거기서 props 타입을 읽는다.
  • typeof meta: meta 객체의 타입을 뽑는다. meta가 준 args 정보가 여기 담겨 있다.

render: 직접 그리기

/** 톤 5개를 나란히 본다. 직접 그리므로 Controls는 끈다. 톤 하나를 골라 보려면 톤별 스토리를 쓴다. */
export const AllTones: Story = {
  parameters: { controls: { disable: true } },
  render: () => (
    <div className="flex flex-wrap gap-sm">
      {tones.map((tone) => (
        <Badge key={tone} tone={tone}>
          {tone}
        </Badge>
      ))}
    </div>
  ),
};

컴포넌트 하나가 아니라 여러 개를 조합하거나 감싸야 할 때 render를 쓴다.

  • render는 (args) => ...로 args를 받을 수 있는데, 여기서는 받지 않아 ()다. 그래서 Controls를 바꿔도 화면이 바뀌지 않는다.
  • 바꿔도 소용없는 패널은 헷갈리므로 parameters: { controls: { disable: true } }로 이 스토리만 Controls를 끈다. 스토리의 parameters는 meta의 parameters 위에 덮인다.

skeleton.stories.tsx의 PosterCard도 같은 방식이다. Skeleton 세 개를 aria-busy="true" 영역으로 감싸 "실제로는 이렇게 조합해 쓴다"를 보여 주고, Controls를 끈다.

JSDoc 주석: 스토리 설명

// packages/store-ui/src/skeleton.stories.tsx
/** 포스터가 로드되기 전 같은 크기를 차지하는 3:4 자리 표시자. */
export const Poster: Story = {
  args: { className: 'aspect-[3/4] w-[180px]' },
};

스토리 export 바로 위의 /** */ 주석은 Docs 페이지에서 그 스토리의 설명으로 나온다. 일반 // 주석은 나오지 않는다. 그래서 독자에게 보일 설명은 /** */로, 코드 읽는 사람만 볼 메모는 //로 적는다. PosterCard의 "Controls는 끈다" 메모가 //인 이유다.

layout: 캔버스 배치

// packages/store-ui/src/docs/tokens.stories.tsx
parameters: {
  layout: 'fullscreen',
  // ...
},
값 모양
'padded' 기본 가장자리에 여백을 둔다. Badge, Skeleton 스토리가 이 모양이다.
'centered' 가운데 정렬한다.
'fullscreen' 토큰 화면 여백 없이 꽉 채운다. 페이지 전체를 쓰는 문서 화면에 맞는다.

스토리가 하나뿐인 경우

export const Tokens: StoryObj<typeof meta> = {};

이 한 줄은 "사이드바에 Tokens 항목을 하나 만들고, 추가 설정 없이 <TokensPage />를 그려라"라는 뜻이다.

왜 이 줄이 있어야 하나

export default meta만으로는 화면에 아무것도 나오지 않는다. meta는 "이 파일이 무엇에 관한 것인지"를 적은 정보일 뿐이다. 사이드바에 클릭할 항목이 생기려면 이름 있는 export가 하나 이상 있어야 한다. 보여 줄 화면이 하나뿐이어도 export는 하나 필요하다.

빈 객체 {}의 뜻

스토리 객체에는 args, render, parameters를 넣을 수 있다. {}는 "따로 바꿀 설정이 없으니 기본대로 그려라"라는 뜻이다. 기본 동작은 <meta.component {...args} />다.

스토리 component 합쳐진 args 그려지는 것
Badge의 Neutral Badge { children: '배지', tone: 'neutral' } <Badge tone="neutral">배지</Badge>
토큰의 Tokens TokensPage {} <TokensPage />

TokensPage는 props를 받지 않고 혼자 tokens.css를 읽어 그린다. 넘길 args가 없으니 빈 객체면 충분하다. TokensPage는 라이브러리 컴포넌트가 아니라 이 파일 안의 문서 화면이지만, component에 넣으면 평소처럼 그려진다. 스토리가 꼭 실제 컴포넌트일 필요는 없다.

왜 type Story 별칭을 안 만들었나

Badge는 스토리가 6개라 type Story 별칭을 만들었다(앞 절). 토큰 화면은 1개라 별칭을 만들면 오히려 한 줄이 는다. 그래서 바로 적었고, 동작은 같다. 

// 지금 코드
export const Tokens: StoryObj<typeof meta> = {};

// 이렇게 써도 완전히 같다
type Story = StoryObj<typeof meta>;
export const Tokens: Story = {};

타입을 붙이는 이유는 오타 방지다. { arg: {...} }처럼 잘못 적거나 TokensPage에 없는 prop을 넣으면 TypeScript가 바로 알려 준다.

tokens.css를 읽어 그리기

import tokensCss from '../tokens.css?raw';
const tokens = readTokens(tokensCss);
  • ?raw는 파일 내용을 문자열 그대로 가져오는 Vite 기능이다. 그 문자열을 readTokens()로 파싱한다. 자세한 원리는 008 문서에 있다.
  • 예시는 var(--spacing-md) 대신 읽은 값을 style={{ width: s.value }}처럼 인라인 스타일로 넣는다. Tailwind v4는 클래스로 쓰인 테마 변수만 CSS에 내보내서, 아무 데서도 쓰지 않은 토큰은 변수가 없기 때문이다(008 문서).

docs 폴더와 Foundations/Components

이슈(#21) 스펙은 이 이름들을 정하지 않았다. 아래는 이 브랜치에서 고른 관례다.

src/docs: dist에 안 들어가는 문서용 코드

src/docs/에는 tokens.stories.tsx와 read-tokens.ts가 있다. 둘 다 Storybook 토큰 화면에서만 쓰고 스토어 앱은 쓰지 않는다. 이 구분은 tsconfig.build.json에서 쓰인다. 

"exclude": ["src/**/*.stories.tsx", "src/**/*.spec.ts", "src/docs"]
  1. 스토리 파일은 이름으로 빠진다 *.stories.tsx 패턴에 걸린다.
  2. read-tokens.ts는 이름으로 못 뺀다 평범한 이름이라 그대로 두면 dist에 들어가, 스토어가 쓸 수 있는 코드처럼 보인다.
  3. 폴더째 뺀다 그래서 "src/docs 안 = 문서 전용, dist에 안 들어감"이라는 규칙이 된다.

src/docs는 사이드바 위치와 상관없다. 사이드바 위치는 meta의 title이 정하고, title을 생략할 때만 Storybook이 파일 경로로 이름을 붙인다. tags: ['autodocs']로 생기는 Docs 페이지와도 관계없다. Docs 페이지는 애드온 기능이고 src/docs는 우리가 정한 폴더 이름일 뿐이다.

Foundations와 Components

디자인 시스템에서 흔히 쓰는 사이드바 분류다.

Foundations Components
무엇 모든 화면이 공유하는 기본 규칙: 색, 글자 크기, 간격, 모서리 규칙으로 만든 재사용 UI 조각: Badge, Skeleton
앱에서 쓰는 법 bg-primary, p-lg 같은 클래스 import { Badge } from '@openrun/store-ui'
코드 위치 src/tokens.css src/badge.tsx, src/skeleton.tsx
Storybook 화면 값을 보여 주는 문서 한 장. 조작할 props가 없다. 컴포넌트마다 스토리 여러 개, Controls, Docs 페이지

Foundations는 재료, Components는 그 재료로 만든 결과물이다. Badge의 tone="primary"는 결국 Foundations의 primary 색을 쓴다. 타이포그래피 예시나 아이콘 목록처럼 값과 규칙을 보여 주는 문서는 Foundations/에, Button이나 Card 같은 컴포넌트는 Components/에 둔다.

스스로 확인하기

1. main.ts의 stories 경로가 'src/**'가 아니라 '../src/**'인 이유는?

경로가 .storybook/ 폴더 기준이기 때문이다. .storybook/에서 한 단계 올라가야 src가 있다.

2. preview.ts에서 import './storybook.css'를 지우면 스토리 화면은 어떻게 되나?

Tailwind 클래스, 토큰, 폰트가 모두 빠진다. bg-primary, gap-sm 같은 클래스가 CSS로 만들어지지 않아 컴포넌트가 스타일 없이 그려진다.

3. meta의 args에서 children을 지우면 어떻게 되나? meta를 : Meta로 적었다면?

지금처럼 satisfies면 Neutral 등 tone만 적은 스토리에서 "children이 없다"는 타입 오류가 난다. : Meta로 적었다면 모든 prop을 선택으로 보므로 오류 없이 글자 없는 빈 배지가 그려진다.

4. AllTones 스토리에는 왜 Controls 패널이 없나?

render: () => ...가 args를 받지 않고 tones 배열로 직접 그려서, Controls를 바꿔도 화면이 바뀌지 않는다. 그래서 parameters: { controls: { disable: true } }로 껐다. args를 쓰려면 render: (args) => ...로 받아 넘겨야 한다.

5. tokens.stories.tsx에서 export const Tokens 줄을 지우면?

이름 있는 export가 없어 사이드바에 클릭할 스토리가 생기지 않는다. meta는 파일 정보일 뿐 스스로 화면을 만들지 않는다.

6. Badge에 info 톤을 추가하고 스토리를 고치지 않으면 어디서 알 수 있나?

toneSet의 satisfies Record<BadgeTone, true>에서 info가 없다는 타입 오류가 난다. pnpm typecheck에서 걸린다. 고치면 Controls 선택지와 AllTones에 info가 함께 생긴다.
