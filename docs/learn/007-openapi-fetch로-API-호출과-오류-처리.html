openapi-fetch로 API 호출과 오류 처리: 서버 컴포넌트, React Query

스토어 첫 페이지의 fetchShows에서 출발해, 생성된 API 클라이언트가 fetch를 어떻게 감싸는지, HTTP 오류를 왜 예외가 아니라 값으로 돌려주는지, React Query와는 어떻게 이어 쓰는지 정리한다. 기준 버전은 openapi-fetch 0.17이고, 오류 처리 동작은 설치된 패키지 소스로 확인했다.

한눈에 보기

openapi-fetch는 응답을 받으면 값으로, 응답을 못 받으면 예외로 돌려준다. 500이 와도 예외가 나지 않는다. 그래서 "실패하면 던진다"는 정책은 부르는 쪽이 정한다. 우리 fetchShows가 data가 없으면 직접 던지는 이유다.

질문 짧은 답
fetch는 어디 있나 client.GET('/shows') 안에서 openapi-fetch가 부른다.
오류 처리는 이렇게 하면 되나 된다. data === undefined로 확인하고 던지면 오류 화면으로 간다.
왜 오류를 값으로 주나 fetch와 같은 규칙, 오류 타입 유지, 예상된 4xx 분기, 정책을 앱에 맡기기.
React Query에 쓸 수 있나 쓸 수 있다. fetchShows를 queryFn에 넣거나 openapi-react-query를 쓴다.

fetch는 어디에 숨어 있나

apps/store/app/page.tsx는 fetch를 직접 부르지 않는다. 실제 호출은 세 단계 아래에 있다.

  • HomePage 서버 컴포넌트. async 함수라 바로 await한다.
    • connection() 빌드 때 그리지 않고 요청마다 렌더링한다. 006 문서 참고.
    • createServerApiClient() API_INTERNAL_URL을 읽어 클라이언트를 만든다.
    • fetchShows(client) 응답을 확인하고, 실패하면 던진다.
      • client.GET('/shows') openapi-fetch가 URL을 만들고 응답을 읽는다.
        • fetch(request) 실제 HTTP 요청. 결과는 { data, error, response }로 돌아온다. 
// apps/store/src/shows/fetch-shows.ts
export async function fetchShows(client: ApiClient): Promise<Show[]> {
  const { data, response } = await client.GET('/shows');
  if (data === undefined) {
    throw new Error(`공연 목록을 불러오지 못했습니다 (HTTP ${response.status})`);
  }
  return data;
}

서버 컴포넌트에서는 이렇게 데이터를 가져오는 함수를 따로 두고, 컴포넌트에서 await로 부르는 형태가 흔하다. 컴포넌트는 받은 데이터를 그리는 일만 한다.

왜 fetch를 직접 쓰지 않나

  1. 타입이 계약에서 나온다 '/shows' 경로와 응답 타입 Show[]는 apps/api/openapi.json에서 생성된다. API의 DTO가 바뀌면 store의 typecheck가 실패한다. fetch를 직접 쓰면 await res.json()의 결과가 any라 이런 확인이 없다.
  2. 클라이언트를 바꿔 끼울 수 있다 fetchShows는 클라이언트를 인자로 받는다. 테스트에서는 가짜 fetch를 넣은 클라이언트를 주고 API 없이 검증한다(apps/store/src/shows/fetch-shows.spec.ts). 환경 변수를 읽는 일은 createServerApiClient만 한다. 
// 테스트: 진짜 API 대신 정해진 응답을 돌려주는 fetch를 넣는다
const client = createApiClient({
  baseUrl: 'http://api.internal:3000',
  fetch: async (request: Request) => Response.json([{ id: 1, title: '레미제라블' }]),
});
await fetchShows(client); // [{ id: 1, title: '레미제라블' }]

fetch의 규칙: 응답을 받으면 성공

브라우저와 Node의 fetch는 404나 500이 와도 예외를 던지지 않는다. 서버가 어쨌든 응답했으니 요청은 성공이고, 상태는 response.ok와 response.status로 알려 준다. 예외(reject)는 네트워크가 끊기거나 주소를 찾지 못해 응답 자체를 못 받았을 때만 난다.

상황 fetch openapi-fetch axios
200 값 response 값 { data, response } 값 { data }
404, 500 값 response.ok === false 값 { error, response } 예외 AxiosError
네트워크 오류 예외 TypeError 예외 그대로 다시 던짐 예외 AxiosError

openapi-fetch는 fetch를 얇게 감싼 라이브러리라 이 규칙을 바꾸지 않았다. axios에 익숙하면 낯설게 느껴지는 부분이다.

왜 값으로 돌려주나

1. 오류에도 타입을 붙이려고

가장 큰 이유다. OpenAPI 문서에는 상태 코드마다 응답 모양이 적혀 있다. openapi-fetch는 이것으로 error의 타입까지 만든다. 예외로 던지면 이 타입이 사라진다. TypeScript에서 catch (e)의 e는 항상 unknown이기 때문이다. 

const { data, error } = await client.GET('/shows/{id}', { params: { path: { id: 1 } } });
if (error) {
  error.message; // 404 응답 스키마의 타입으로 추론된다
  return;
}
data.title; // 여기서는 data가 있다고 좁혀진다

결과는 data와 error 중 하나만 있는 유니온 타입이다. 한쪽을 확인하면 다른 쪽 타입이 저절로 좁혀진다.

2. 4xx는 고장이 아니라 예상된 결과인 경우가 많아서

예매 서비스에서는 이런 응답이 정상 흐름의 일부다.

  • 이미 팔린 좌석을 고르면 409
  • 없는 공연을 열면 404
  • 입력값이 틀리면 400

화면에서 갈라서 보여 줘야 하는 경우다. 값으로 받으면 if로 나누면 된다. 예외로 받으면 try/catch 안에서 상태 코드를 다시 꺼내 나눠야 한다.

3. 오류 정책을 앱에 맡기려고

예외를 던질지, 어떤 오류 클래스로 바꿀지는 앱마다 다르다. 라이브러리는 정책을 정하지 않고 값만 돌려준다. 던지고 싶으면 두 가지 방법이 있다.

방법 적용 범위 어울리는 경우
함수에서 직접 던지기 (fetchShows처럼) 그 함수만 API마다 실패의 의미가 다를 때
미들웨어 onResponse에서 던지기 그 클라이언트의 모든 요청 모든 실패를 같은 방식으로 다룰 때 
client.use({
  onResponse({ response }) {
    if (!response.ok) {
      throw new Error(`${response.url}: ${response.status}`);
    }
  },
});

data로 확인하는 이유

if (error)로 확인하는 게 더 자연스러워 보이지만 fetchShows는 data === undefined를 본다. openapi-fetch 소스를 보면 오류 응답의 본문이 비었을 때 error가 거짓 값이 되기 때문이다.

응답 data error if (error) data === undefined
200 + 목록 목록 없음 통과 통과
500 + JSON 본문 없음 본문 객체 잡음 잡음
500 + Content-Length: 0 없음 undefined 놓침 잡음
500 + 빈 본문 (길이 헤더 없음) 없음 "" 놓침 잡음
선택 읽기: openapi-fetch 0.17의 응답 처리 부분

node_modules/.pnpm/openapi-fetch@0.17.0/.../dist/index.mjs에서 응답을 읽는 부분을 줄였다. 본문이 없으면 error: undefined, 본문이 JSON이 아니면 문자열이 그대로 error가 된다. 

if (response.status === 204 || contentLength === '0') {
  return response.ok ? { data: undefined, response } : { error: undefined, response };
}
if (response.ok) {
  return { data: await response.json(), response };
}
let error = await response.text(); // 빈 본문이면 ""
try {
  error = JSON.parse(error);
} catch {}
return { error, response };

주의할 점도 있다. 성공 응답이 204처럼 본문 없이 오면 data도 undefined다. 본문 없는 성공 응답이 정상인 API라면 data 대신 response.ok로 확인해야 한다. GET /shows는 항상 배열을 돌려주므로 해당하지 않는다.

던진 오류는 어디로 가나

  1. 가장 가까운 error.tsx가 받는다 서버 컴포넌트에서 던진 오류는 같은 경로나 상위 경로의 error.tsx가 그린다. 지금 store에는 error.tsx가 없어서 Next의 기본 오류 화면이 나온다.
  2. 프로덕션에서는 메시지가 브라우저로 가지 않는다 오류 메시지는 서버 로그에만 남고, 브라우저에는 로그와 짝을 맞추는 digest 값만 간다. "HTTP 500" 같은 내부 정보가 사용자에게 보이지 않는다.
  3. 사용자에게 보일 화면은 error.tsx로 만든다 error.tsx는 클라이언트 컴포넌트여야 한다. reset()을 부르면 그 구간을 다시 렌더링한다. 
// app/error.tsx (아직 만들지 않았다)
'use client';

export default function Error({ reset }: { error: Error; reset: () => void }) {
  return (
    <main>
      <p>공연 목록을 불러오지 못했습니다.</p>
      <button onClick={() => reset()}>다시 시도</button>
    </main>
  );
}

queryFn은 reject해야 한다

React Query는 queryFn이 reject될 때만 오류 상태(isError)가 되고 다시 시도한다. fetchShows는 HTTP 오류에서 직접 던지므로 그대로 넣으면 된다. 

'use client';

const { data, isError } = useQuery({
  queryKey: ['shows'],
  queryFn: () => fetchShows(browserApiClient),
});

client.GET을 queryFn에 바로 넣으면 안 된다. 500이 와도 정상으로 끝나므로 React Query는 성공으로 여기고, data가 없는 채로 넘어간다. 다시 시도도 하지 않는다.

openapi-react-query

openapi-fetch를 만든 팀의 공식 래퍼다. 경로만 적으면 queryKey를 [method, path, params]로 만들고, 오류가 나면 던져서 isError로 보낸다. 

import createQueryClient from 'openapi-react-query';

const $api = createQueryClient(createApiClient({ baseUrl }));

const { data, error } = $api.useQuery('get', '/shows');
// useQuery($api.queryOptions('get', '/shows'))처럼 옵션만 만들어 쓸 수도 있다
fetchShows + useQuery openapi-react-query
타입 계약에서 생성 계약에서 생성
queryKey 직접 정한다 자동
오류 값 우리가 던진 Error 응답 본문 (스키마 타입)
응답 가공, 테스트 함수 안에서, 함수 단위로 hook을 쓰는 쪽으로 옮겨 간다
서버 컴포넌트에서 재사용 같은 함수를 그대로 queryOptions로 가능

엔드포인트가 몇 개 없으면 왼쪽, 많아지면 오른쪽이 편하다.

브라우저에서 부를 때 필요한 것

React Query는 클라이언트 컴포넌트에서 돈다. 지금 store의 클라이언트는 서버 전용이라 바로 쓸 수 없다.

문제 이유 해결
주소 API_INTERNAL_URL은 서버에서만 읽히는 환경 변수다. 브라우저용 NEXT_PUBLIC_API_URL을 따로 두거나, Next가 /api/*를 프록시한다.
CORS store(3001)와 API(3000)는 출처가 다르다. NestJS에서 CORS를 연다. 프록시를 쓰면 같은 출처라 필요 없다.
첫 화면 클라이언트에서만 부르면 빈 화면 뒤에 목록이 나온다. 서버에서 미리 받아 넘긴다. 아래 순서 참고.
  1. 서버 컴포넌트에서 미리 받는다 queryClient.prefetchQuery({ queryKey: ['shows'], queryFn: () => fetchShows(serverClient) })
  2. 캐시를 클라이언트로 넘긴다 <HydrationBoundary state={dehydrate(queryClient)}>로 감싼다.
  3. 클라이언트는 다시 요청하지 않고 이어 쓴다 같은 queryKey로 useQuery를 부르면 넘겨받은 캐시를 쓴다.

1단계는 서버용 클라이언트, 3단계는 브라우저용 클라이언트를 쓰지만 fetchShows는 같은 함수다. 클라이언트를 인자로 받게 만든 덕분이다.

우리 프로젝트에서는

  • 공연 목록은 실패하면 화면을 그릴 수 없다. 그래서 fetchShows에서 던져 오류 화면으로 보낸다.
  • 오류 응답 규격(코드, 메시지)은 1.3에서 정한다. 그때 error 본문을 읽어 오류 클래스로 바꾼다. 지금 미리 만들면 아직 없는 규격을 추측하게 된다.
  • 좌석 선점처럼 409가 정상 흐름인 API가 생기면 그쪽은 던지지 않고 error를 보고 나눈다. 그래서 미들웨어로 모든 요청을 한꺼번에 던지게 하지 않고, 함수마다 정한다.
  • React Query는 아직 필요 없다. 공연 목록은 서버에서 한 번 그리면 끝이다. 클라이언트에서 다시 불러오거나, 화면을 옮겨도 캐시를 유지하거나, 사용자 조작에 따라 데이터가 바뀌는 화면이 생기면 들인다.

스스로 확인하기

1. API 서버를 끈 채 공연 페이지를 열면 fetchShows의 어느 줄에서 실패하나?

if (data === undefined)까지 가지 않는다. 응답을 못 받았으므로 client.GET 안의 fetch가 reject되고, openapi-fetch가 그 예외를 다시 던져 await client.GET(...) 줄에서 바로 실패한다.

2. useQuery의 queryFn에 client.GET을 그대로 넣으면 500일 때 화면은 어떻게 되나?

queryFn이 정상으로 끝나므로 React Query는 성공으로 본다. isError는 거짓이고 다시 시도도 하지 않는다. 결과 객체의 data가 없어서 화면에서 목록을 그리다 실패하거나 빈 화면이 된다.

3. 모든 요청에 onResponse 미들웨어로 예외를 던지게 하면 무엇을 잃나?

두 가지를 잃는다. 하나는 상태 코드별 error 타입이다. 예외로 바뀌면 catch에서 unknown이 된다. 다른 하나는 409 같은 예상된 실패를 if로 나누는 흐름이다. 그런 API도 try/catch로 받아야 한다.

4. 프로덕션에서 fetchShows가 던진 "HTTP 500" 메시지는 사용자에게 보이나?

보이지 않는다. 서버 컴포넌트의 오류 메시지는 서버 로그에만 남고, 브라우저에는 digest만 간다. 사용자에게 보일 문구는 error.tsx에 따로 적는다.
