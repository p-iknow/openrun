07 redirect와 notFound: 흐름을 끊는 함수

next/navigation의 redirect, permanentRedirect, notFound, forbidden, unauthorized는 모두 값을 돌려주지 않고 예외를 던져 렌더링을 멈춘다. 그래서 뒤에 return을 쓰지 않아도 흐름이 끝난다. 이 문서는 각 함수가 무엇을 던지고, Next가 그 예외를 받아 어떤 응답을 만드는지, 그리고 예외라서 생기는 함정을 본다. 내용은 Next 16.4.5의 소스 코드와 문서, 그리고 이 저장소의 스토어를 띄워 실제로 받은 응답을 기준으로 했다.

한눈에 보기

함수 언제 쓰나 던지는 예외의 digest 결과
redirect(url) 다른 주소로 보낼 때 NEXT_REDIRECT;replace;/;307; 307 리다이렉트
permanentRedirect(url) 주소가 영영 바뀌었을 때 NEXT_REDIRECT;replace;/;308; 308 리다이렉트
notFound() 찾는 자원이 없을 때 NEXT_HTTP_ERROR_FALLBACK;404 404와 not-found.tsx 화면
forbidden() 실험 로그인했지만 권한이 없을 때 NEXT_HTTP_ERROR_FALLBACK;403 403과 forbidden.tsx 화면
unauthorized() 실험 로그인하지 않았을 때 NEXT_HTTP_ERROR_FALLBACK;401 401과 unauthorized.tsx 화면

다섯 함수 모두 서버 컴포넌트, Route Handler, Server Action에서 쓸 수 있다. 상태 코드는 응답을 보내기 시작하기 전에 부른 경우다. 이미 보내기 시작했으면 달라진다(스트리밍 절).

이 함수들은 "여기서 이 요청은 끝났다"를 예외로 Next에게 알린다. 함수를 부른 줄 아래는 실행되지 않고, Next가 예외를 받아 리다이렉트나 404 같은 응답으로 바꾼다.

return이 없어도 되는 이유

스토어의 공연 목록 페이지(apps/store/app/page.tsx)는 이렇게 쓴다.

const { query, redirectTo } = normalizeShowListQuery(await searchParams);
if (redirectTo !== null) {
  redirect(redirectTo); // return이 없다
}

const showPage = await fetchShows({ client: createServerApiClient(), query });

redirect 뒤에 return이 없으니, 리다이렉트할 때도 fetchShows가 불릴 것처럼 보인다. 하지만 설치된 Next의 redirect는 이렇게 생겼다. 

// next/dist/client/components/redirect.js
function redirect(url, type) {
  type ??= actionAsyncStorage?.getStore()?.isAction ? 'push' : 'replace';
  throw getRedirectError(url, type, RedirectStatusCode.TemporaryRedirect);
}

본문이 throw 한 줄이다. 값을 돌려주는 길이 없으니 부른 곳으로 돌아오지 않는다. 예외는 함수를 차례로 빠져나가 HomePage도 그 줄에서 끝나고, fetchShows는 실행되지 않는다. notFound도 같다. 

// next/dist/client/components/not-found.js
const DIGEST = 'NEXT_HTTP_ERROR_FALLBACK;404';
function notFound() {
  const error = new Error(DIGEST);
  error.digest = DIGEST;
  throw error;
}

타입도 알고 있다: never

타입 선언에서 반환 타입은 never, 곧 "절대 돌아오지 않는다"다.

export declare function redirect(url: string, type?: RedirectType): never;
export declare function notFound(): never;

그래서 TypeScript도 if 안에서 흐름이 끝난다는 것을 안다. if를 지나온 아래쪽에서는 조건이 거짓이었던 경우만 남으므로, 값의 타입이 좁혀진다. 

const show = await fetchShow(id); // Show | undefined
if (!show) {
  notFound();
}
show.title; // 여기서 show는 Show. undefined일 수 없다

notFound()가 never가 아니라 void였다면 TypeScript는 아래에서도 show를 Show | undefined로 보고 show.title에 오류를 낸다. 공식 문서도 return redirect()나 return notFound()로 쓸 필요가 없다고 적는다.

Next가 예외를 알아보는 법

던져진 것은 평범한 Error지만 digest라는 글자 속성이 붙어 있다. Next는 렌더링 중에 잡은 예외의 digest를 ;로 잘라 읽고, 정해진 모양이면 오류가 아니라 지시로 다룬다.

digest 잘라 읽은 칸 알아보는 함수
NEXT_REDIRECT;replace;/;307; 종류, 기록 방식(replace/push), 주소, 상태 코드 isRedirectError
NEXT_HTTP_ERROR_FALLBACK;404 종류, 상태 코드(401, 403, 404 중 하나) isHTTPAccessFallbackError

두 함수를 합친 것이 isNextRouterError다. 앱의 error.tsx를 그리는 오류 경계도 이 함수로 먼저 거른다. 

// next/dist/client/components/error-boundary.js
static getDerivedStateFromError(thrownValue) {
  if (isNextRouterError(thrownValue)) {
    // 다른 경계(예: 부모 구간의 NotFound 경계)가 처리해야 하므로 다시 던진다
    throw thrownValue;
  }
  ...
}

그래서 redirect()나 notFound()를 불러도 error.tsx의 "문제가 생겼어요" 화면이 뜨지 않는다. error.tsx는 진짜 오류만 받는다.

redirect와 permanentRedirect

redirect permanentRedirect
상태 코드 307 Temporary Redirect 308 Permanent Redirect
뜻 이번 요청만 다른 곳으로 이 주소는 앞으로도 저기다. 브라우저와 검색 엔진이 기억할 수 있다
예 로그인이 필요해 /login으로, 잘못 쓴 쿼리를 정리한 주소로 공연 주소 형식을 바꿔 옛 주소를 새 주소로

307과 308은 302, 301과 달리 브라우저가 요청 방식(POST 등)과 본문을 바꾸지 않고 그대로 다시 보낸다.

두 번째 인자 type: replace와 push

브라우저 방문 기록에 새 칸을 쌓을지(push), 지금 칸을 바꿀지(replace)다. 기본은 Server Action 안에서는 push, 그 밖에서는 replace다. 위 소스의 isAction ? 'push' : 'replace'가 그것이다. 서버 컴포넌트에서는 효과가 없다.

어디서 부를 수 있나

  • 서버 컴포넌트: 렌더링 중 어디서든. 이 저장소의 쓰임새다.
  • Server Action: 자바스크립트가 있으면 클라이언트 이동으로, 자바스크립트 없이 폼을 제출했으면 303 See Other로 응답한다(action-handler.js가 상태 코드를 303으로 바꾼다).
  • Route Handler: 307/308 응답.
  • 클라이언트 컴포넌트: 렌더링 중에는 되지만 onClick 같은 이벤트 핸들러에서는 안 된다. 이벤트에서는 useRouter().push()를 쓴다.

요청이 렌더링에 닿기도 전에 보내고 싶으면(예: 옛 주소 전체를 새 주소로) next.config.ts의 redirects나 Proxy를 쓴다.

notFound와 not-found.tsx

notFound()를 부르면 그 구간에서 가장 가까운 not-found.tsx를 그린다. 공연 상세처럼 주소의 ID에 해당하는 공연이 없을 때 쓴다. 

// app/shows/[id]/page.tsx (예시)
export default async function ShowPage({ params }: PageProps<'/shows/[id]'>) {
  const { id } = await params;
  const show = await fetchShow(id);
  if (!show) {
    notFound();
  }
  return <ShowDetail show={show} />;
}
  • not-found.tsx가 없으면 Next의 기본 404 화면("This page could not be found.")이 나온다. 이 저장소에는 아직 not-found.tsx가 없어서, 없는 주소 /nope을 열면 이 기본 화면과 404를 받는다.
  • Next가 <meta name="robots" content="noindex" />를 넣어 검색 엔진이 이 페이지를 색인하지 않게 한다.
  • redirect와 달리 주소는 바뀌지 않는다. 사용자는 자기가 친 주소를 그대로 보면서 "없음" 화면을 본다.

redirect와 notFound 중 무엇을 쓸지는 "고쳐 줄 수 있는 주소인가"로 나눈다. ?page=abc는 뜻이 분명한 주소(/)로 고쳐 줄 수 있어 redirect, 없는 공연 ID는 고칠 곳이 없어 notFound다.

forbidden과 unauthorized

같은 방식으로 401, 403 화면을 그리는 함수다. 아직 실험 기능이라 next.config.ts에서 켜야 한다. 켜지 않고 부르면 예외가 바뀌어 `forbidden()` is experimental ...라는 진짜 오류가 난다. 

// next.config.ts
const nextConfig: NextConfig = {
  experimental: { authInterrupts: true },
};
함수 상태 그리는 파일 예
unauthorized() 401 unauthorized.tsx 로그인하지 않고 예매 내역을 열었다
forbidden() 403 forbidden.tsx 로그인했지만 남의 예매 내역을 열었다

이 저장소는 아직 로그인이 없어 쓰지 않는다. 로그인이 생기면 로그인 페이지로 redirect할지, 401 화면을 보여 줄지 정해야 한다.

스트리밍이 시작된 뒤의 응답

HTTP 응답은 상태 줄(200 OK 등)을 맨 앞에 보낸다. 그래서 Next가 응답을 보내기 시작한 뒤에는 상태 코드를 바꿀 수 없다. 이 저장소의 app/loading.tsx처럼 로딩 화면이 있으면 Next는 로딩 화면부터 먼저 보내므로(스트리밍), page.tsx가 redirect를 부를 때는 이미 200을 보낸 뒤다.

그때 Next는 상태 코드 대신 HTML 안에 지시를 넣는다. 스토어를 띄워 실제로 받은 응답이다.

$ curl -i "http://localhost:3001/?page=abc"
HTTP/1.1 200 OK
...
<meta id="__next-page-redirect" http-equiv="refresh" content="1;url=/"/>
함수 응답을 보내기 전 스트리밍이 시작된 뒤
redirect 307과 Location 헤더 200과 <meta http-equiv="refresh" content="1;url=...">
permanentRedirect 308과 Location 헤더 200과 content="0;url=..."
notFound 404 200과 noindex meta, not-found 화면

자바스크립트가 켜진 브라우저에서는 Next 클라이언트가 바로 주소를 바꾸므로 사용자는 차이를 거의 느끼지 못한다. meta 태그는 자바스크립트가 없을 때를 위한 대비다. 다만 상태 코드를 보고 판단하는 검색 엔진, 모니터링, curl 같은 도구는 200을 본다. 정확한 상태 코드가 중요하면 로딩 화면보다 먼저, 곧 스트리밍이 시작되기 전에 판단이 끝나도록 구조를 잡는다.

try/catch에 삼켜지는 문제

예외라서 생기는 함정이다. try 안에서 부르면 catch가 Next보다 먼저 받아 버린다.

export default function Page() {
  try {
    redirect('/');
  } catch (error) {
    return <p>{error.digest}</p>;
  }
}

임시 페이지로 띄워 보면 리다이렉트되지 않고 200과 함께 NEXT_REDIRECT;replace;/;307;라는 글자가 화면에 나온다. 예외를 Next가 받지 못했으니 리다이렉트도 일어나지 않는다. 실제로는 주로 이렇게 숨어 있다. 

try {
  const show = await fetchShow(id); // 이 안에서 404면 notFound()를 부른다
  ...
} catch (error) {
  console.error(error);
  return <ErrorMessage />; // notFound()까지 여기로 와서 404 대신 오류 화면이 된다
}

피하는 법

  1. try 밖에서 부른다 try에서는 결과만 받아 오고, 판단과 redirect/notFound는 try가 끝난 뒤에 한다. 공식 문서가 권하는 방법이다.
  2. catch 첫 줄에서 unstable_rethrow try 안에서 불릴 수밖에 없으면 catch 맨 앞에서 unstable_rethrow(error)를 부른다. Next의 예외면 다시 던지고, 아니면 아무것도 하지 않는다. 
import { notFound, unstable_rethrow } from 'next/navigation';

try {
  notFound();
} catch (error) {
  unstable_rethrow(error); // Next의 예외면 여기서 다시 던진다
  return <p>삼킴</p>;   // 진짜 오류만 여기까지 온다
}

임시 페이지로 띄워 보면 "삼킴" 대신 not-found 화면("This page could not be found.")과 noindex meta가 나온다. unstable_rethrow의 몸통은 아래와 같다. isNextRouterError(리다이렉트와 401/403/404) 말고도 Next가 렌더링을 바꾸려고 던지는 다른 예외들도 다시 던지고, error.cause도 따라 들어가 본다. 

// next/dist/client/components/unstable-rethrow.js
function unstable_rethrow(error) {
  if (isNextRouterError(error) || isBailoutToCSRError(error) || isDynamicServerError(error) || ...) {
    throw error;
  }
  if (error instanceof Error && 'cause' in error) {
    unstable_rethrow(error.cause);
  }
}

이름의 unstable_은 API가 아직 바뀔 수 있다는 뜻이다. 1번 방법으로 풀 수 있으면 그쪽이 낫다. 같은 이유로 await하지 않은 Promise 안에서 notFound()를 부르면 아무도 받지 못해 not-found 화면이 나오지 않는다. 렌더링 경로, 곧 컴포넌트나 컴포넌트가 await하는 함수 안에서 불러야 한다.

우리 프로젝트에서는

apps/store/app/page.tsx가 redirect를 두 번 쓴다. 둘 다 try 밖이다.

시점 조건 예
API를 부르기 전 쿼리를 정리한 주소가 지금 주소와 다르다 /?page=abc → /, /?page=1&foo=bar → /
API 응답을 받은 뒤 요청한 페이지가 마지막 페이지를 넘는다 /?page=99 → /?page=4

첫 번째를 API 호출 앞에 둔 이유는 잘못된 쿼리를 그대로 보내 API에서 400을 받지 않기 위해서다. 두 번째는 전체 페이지 수를 알아야 하므로 응답 뒤에만 할 수 있다. app/loading.tsx가 있어서 둘 다 200과 meta refresh로 나간다.

스스로 확인하기

1. 아래에서 if 뒤의 show.title에 타입 오류가 나지 않는 이유는?

return이 없어도 되는 이유 절의 never를 묻는다.

const show = await fetchShow(id); // Show | undefined
if (!show) {
  notFound();
}
show.title;
답 보기

notFound()의 반환 타입이 never라서, TypeScript는 if 안으로 들어간 흐름이 아래로 내려오지 않는다고 본다. 아래에는 show가 참이었던 경우만 남아 Show로 좁혀진다. 실행할 때도 notFound()가 예외를 던지므로 실제로 내려오지 않는다.

2. 이 페이지에서 공연이 없으면 사용자는 무엇을 보나?

try/catch 절. fetchShow는 API가 404면 notFound()를 부른다.

try {
  const show = await fetchShow(id);
  return <ShowDetail show={show} />;
} catch {
  return <p>공연을 불러오지 못했어요.</p>;
}
답 보기

not-found 화면이 아니라 "공연을 불러오지 못했어요."를 본다. notFound()가 던진 예외를 catch가 먼저 받아 Next까지 가지 않는다. catch 첫 줄에 unstable_rethrow(error)를 넣거나, try에서는 응답만 받고 notFound()는 try 밖에서 부르도록 고친다.

3. curl -i "localhost:3001/?page=abc"가 307이 아니라 200을 받는 이유는?

스트리밍 절과 app/loading.tsx를 묻는다.

답 보기

app/loading.tsx가 있어 Next가 로딩 화면부터 보내기 시작하고, 그 순간 상태 줄 200 OK가 이미 나간다. page.tsx의 redirect는 그 뒤에 불리므로 상태 코드를 바꿀 수 없고, Next는 대신 <meta http-equiv="refresh" content="1;url=/">를 넣는다. 브라우저에서는 Next 클라이언트가 곧바로 /로 옮긴다.
