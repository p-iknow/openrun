11 useOptimistic이 해결하는 문제와 원리

React 19의 useOptimistic이 어떤 문제를 풀고, 어떤 규칙으로 임시 값을 보여 주고 거두는지 정리한다. 2부의 기록은 스토어 앱의 개발 서버에 실험용 페이지를 잠깐 만들어 React 19.3.1로 직접 잰 값이다. 이 저장소에서 쓰는 곳은 필터 칩이고, 그 사례는 store-logic 01 문서에 따로 있다.

한눈에 보기

useOptimistic은 진짜 값 위에 잠깐 덮는 임시 값이다. 서버의 답을 기다리는 동안 "아마 이렇게 될 것"이라는 값을 먼저 보여 주고, 작업(transition)이 끝나면 덮개를 걷어 진짜 값을 보여 준다. 성공하면 진짜 값이 이미 같아져 있어 화면이 그대로이고, 실패하면 저절로 원래 값으로 돌아간다. 

const [shown, setOptimistic] = useOptimistic(realValue);
//     ↑ 화면에 보여 줄 값        ↑ 진짜 값(props, 서버에서 온 값, useState 값 등)

startTransition(async () => {
  setOptimistic(guess);      // 덮개를 씌운다: 바로 화면에 보인다
  await saveToServer(guess); // 기다리는 동안 덮개가 유지된다
  // 함수가 끝나면 덮개를 걷는다. 그때 보이는 것은 realValue
});
질문 답
무엇을 푸나서버를 기다리는 동안 화면이 반응하지 않는 공백
임시 값은 언제 보이나setOptimistic을 부른 즉시
언제 사라지나그 값을 넣은 transition(action)이 끝날 때. 시간이 정해진 것이 아니다
사라진 뒤 무엇이 보이나그 순간의 진짜 값(인자)
실패하면되돌리는 코드 없이 진짜 값으로 돌아간다
어디서 불러야 하나startTransition 안이나 <form action> 같은 action 안

서버를 기다리는 동안의 공백

좋아요 버튼을 생각해 보자. 누르면 서버에 저장하고, 서버가 답하면 새 좋아요 수를 보여 준다. 화면에 보이는 값이 서버에서 온 값이라면, 누른 뒤 답이 올 때까지 화면은 그대로다. 

  0ms  ♡ 12   누름 → 서버로 요청
500ms  ♡ 12   아직 답 없음      ← 눌렀는지 알 수 없다
900ms  ♥ 13   답이 와서 바뀜

이 공백에서 문제가 세 가지 생긴다.

  1. 반응이 없다 사용자는 눌린 줄 모르고 한 번 더 누른다. 그러면 좋아요가 취소된다.
  2. 다음 조작이 옛 값에서 계산된다 할 일 두 개를 빠르게 추가하면, 두 번째를 추가할 때 화면의 목록에는 첫 번째가 아직 없다. 화면에 보이는 값을 바탕으로 다음 값을 만드는 코드라면 첫 번째가 빠진다.
  3. 느린 앱처럼 느껴진다 결과가 거의 확실한 작업(좋아요, 체크, 메시지 전송)까지 매번 기다리게 하면 앱 전체가 굼떠 보인다.

useOptimistic은 이 공백에 "결과를 짐작한 값"을 보여 준다. 좋아요는 거의 항상 성공하므로 ♥ 13을 먼저 보여 줘도 틀릴 일이 드물다. 이렇게 성공을 먼저 가정하는 방식을 낙관적 업데이트(optimistic update)라고 한다.

다른 방법으로 메우면

로딩 표시만 한다

useTransition의 isPending으로 버튼에 스피너를 띄우면 "누른 것"은 알 수 있다. 하지만 결과는 여전히 기다려야 한다. 결과가 거의 확실한 작업에서는 스피너도 기다림이다. 결제처럼 결과를 짐작하면 안 되는 작업에는 이쪽이 맞다(쓰지 않는 편이 나은 때).

useState로 화면용 복사본을 둔다

const [liked, setLiked] = useState(post.liked); // 처음 한 번만 복사한다

async function onClick() {
  const previous = liked;
  setLiked(!liked);                 // 먼저 바꾸고
  try {
    await likePost(post.id);
  } catch {
    setLiked(previous);             // 실패하면 직접 되돌린다
  }
}

useEffect(() => setLiked(post.liked), [post.liked]); // 서버 값이 바뀌면 직접 맞춘다

동작은 하지만 직접 챙길 것이 많다.

  • 되돌리기: 실패할 때마다 이전 값을 기억해 두고 되돌리는 코드를 써야 한다.
  • 맞추기: 진짜 값(post.liked)이 다른 이유로 바뀌면 useEffect로 복사본을 맞춰야 한다. 바뀐 값이 한 번 늦게 그려지고, 값이 두 곳에 있어 어긋날 틈이 생긴다.
  • 순서: 요청 두 개가 겹쳐 늦게 보낸 것이 먼저 돌아오면 무엇을 기준으로 되돌릴지 정해야 한다.

useOptimistic은 이 세 가지를 React에 맡긴다. 복사본을 두지 않고, 진짜 값 위에 덮개만 씌우기 때문이다.

두 가지 쓰는 법

값을 바로 넣기

const [liked, setOptimisticLiked] = useOptimistic(post.liked);

setOptimisticLiked(true); // 임시 값으로 true를 보여 준다

임시 값이 무엇인지 그 자리에서 알 때 쓴다. 좋아요, 스위치, 필터 칩처럼 "새 값 하나"로 끝나는 경우다.

계산 함수 주기

const [shownMessages, addOptimisticMessage] = useOptimistic(
  messages,                                         // 진짜 값
  (current, newText: string) => [                   // (지금 값, 넘긴 것) => 보여 줄 값
    ...current,
    { text: newText, sending: true },
  ],
);

addOptimisticMessage('안녕'); // current 뒤에 '안녕(보내는 중)'을 붙인 목록을 보여 준다

"지금 값에 무엇을 더하거나 빼는" 경우에 쓴다. 두 번째 인자는 useReducer의 reducer와 모양이 같다. 이 함수는 한 번만 실행되고 끝나는 것이 아니라, 진짜 값이 바뀌면 새 진짜 값 위에서 다시 실행된다(특징 5번). 그래서 목록처럼 여러 곳에서 바뀌는 값에 안전하다.

덮개 모델

useOptimistic이 렌더링마다 하는 일을 의사 코드로 쓰면 이렇다.

function useOptimistic(realValue, update = (current, next) => next) {
  // 아직 끝나지 않은 transition에서 넣은 임시 값들
  const pending = 진행_중인_임시_값_목록();

  // 진짜 값에서 시작해 임시 값을 차례로 덮는다
  let shown = realValue;
  for (const p of pending) shown = update(shown, p);

  return [shown, 임시_값을_넣는_함수];
}
  • 저장하지 않는다: shown은 매번 realValue에서 새로 계산한다. useState(초기값)은 처음 한 번만 읽지만, useOptimistic(realValue)는 렌더링마다 읽는다. 임시 값이 없으면 const shown = realValue와 같다.
  • 덮개는 쌓인다: 임시 값이 여러 개면 들어온 순서대로 덮는다.
  • 걷히면 진짜 값: transition이 끝난 임시 값은 목록에서 빠진다. 다 빠지면 realValue만 남는다.
  • 화면에 보이는 값= 진짜 값 + 덮개들
    • 덮개 2두 번째 transition이 끝나면 걷힌다
    • 덮개 1첫 번째 transition이 끝나면 걷힌다
    • 진짜 값props나 상태. 서버 답이 오면 부모가 바꾼다

덮개는 언제 걷히나

덮개는 그것을 넣은 transition이 끝날 때 걷힌다. startTransition에 비동기 함수를 넘기면 그 함수가 끝날 때(await가 모두 풀릴 때)가 끝이다. <form action={fn}>은 React가 fn을 transition으로 실행하므로 fn이 끝날 때가 끝이다.

그래서 "진짜 값을 바꾸는 일"은 덮개가 걷히기 전에, 같은 transition 안에서 끝내야 한다. 실험 기록이다.

startTransition(async () => {
  setShown(1);
  await sleep(1000);
  startTransition(() => setBase(1)); // 진짜 값도 1로 바꾼다
});
   2ms  진짜 0  보이는 값 1   ← 덮개
1003ms  진짜 1  보이는 값 1   ← 덮개가 걷히는 순간 진짜 값도 1이라 화면 변화 없음

진짜 값을 바꾸지 않고 끝내면 덮개만 걷혀 원래 값으로 돌아간다.

startTransition(async () => {
  setShown(5);
  await sleep(1000);       // 진짜 값은 그대로
});
   1ms  진짜 1  보이는 값 5
1002ms  진짜 1  보이는 값 1   ← 원래 값으로 돌아간다

await 뒤에서 상태를 바꿀 때 다시 startTransition으로 감싼 것은 React 문서가 권하는 방법이다. await 뒤의 상태 변경은 transition으로 표시되지 않는 한계가 있기 때문이다.

특징 일곱 가지

1. 즉시 그려진다

transition 안의 다른 갱신은 급하지 않은 일로 미뤄지지만, 임시 값은 바로 그리는 차선에 들어간다. 위 실험에서 모두 0~2ms 만에 화면에 나왔다. 그래서 transition 안에서 불러도 "느린 갱신"이 되지 않는다.

2. transition 밖에서 부르면 오류가 찍힌다

An optimistic state update occurred outside a transition or action. To fix, move the update to an action, or wrap with startTransition.

덮개를 언제 걷을지 정할 transition이 없기 때문이다. 이 오류가 나도 화면은 그려질 수 있지만, 언제 걷힐지는 React 내부 사정에 맡기게 된다.

3. 실패하면 저절로 돌아간다

startTransition(async () => {
  setShown(99);
  await sleep(1000);
  try { throw new Error('저장 실패'); } catch { /* 알림만 띄운다 */ }
});
   1ms  진짜 1  보이는 값 99
1002ms  진짜 1  보이는 값 1    ← 되돌리는 코드 없이 돌아간다

오류를 잡지 않고 던져도 덮개는 걷힌다. 실험에서는 500ms 뒤 원래 값으로 돌아갔고, 오류는 처리되지 않은 전역 오류(Uncaught Error)로 콘솔에 찍혔다. 사용자에게 알리려면 직접 잡아서 알림을 띄우는 편이 낫다.

4. 값을 바로 넣는 형태는 진행 중에 진짜 값이 바뀌어도 임시 값을 유지한다

startTransition(async () => { setShown(100); await sleep(1500); });
setTimeout(() => setBase(7), 500); // 진행 중에 진짜 값이 다른 이유로 바뀐다
   0ms  진짜 0  보이는 값 100
 502ms  진짜 7  보이는 값 100   ← 덮개가 그대로 덮고 있다
1503ms  진짜 7  보이는 값 7     ← 걷히면 새 진짜 값

5. 계산 함수 형태는 새 진짜 값 위에서 다시 계산한다

const [shown, add] = useOptimistic(list, (current, m) => [...current, m + '(임시)']);

startTransition(async () => { add('x'); await sleep(1500); });
setTimeout(() => setList(['a', 'z']), 500); // 진행 중에 다른 항목이 들어온다
   0ms  진짜 [a]     보이는 값 [a, x(임시)]
 501ms  진짜 [a, z]  보이는 값 [a, z, x(임시)]   ← 새 진짜 값 위에 다시 붙였다
1503ms  진짜 [a, z]  보이는 값 [a, z]

채팅방에 다른 사람의 메시지가 들어와도 내가 보내는 중인 메시지가 사라지지 않고 맨 뒤에 붙어 있는 것이 이 덕분이다. 목록을 다룰 때는 이 형태를 쓰는 편이 안전하다.

6. 겹친 작업은 모두 끝난 뒤 한꺼번에 반영된다

메시지 b를 보내고(1초 걸림), 0.2초 뒤에 c를 보냈다(1.5초 걸림).

   1ms  진짜 [a]        보이는 값 [a, b(보내는 중)]
 202ms  진짜 [a]        보이는 값 [a, b(보내는 중), c(보내는 중)]
1704ms  진짜 [a, b, c]  보이는 값 [a, b, c]

b는 1초에 끝났지만 진짜 값에 b가 들어간 화면은 c가 끝난 1.7초에 함께 나왔다. 진행 중인 action이 있을 때 시작한 action은 React가 하나로 묶어(entangle) 모두 끝나야 결과를 커밋하기 때문이다. 그동안에도 덮개가 b와 c를 보여 주므로 사용자에게는 문제가 없다. 다만 "b가 끝나자마자 무언가 보인다"를 기대하면 안 된다.

7. 렌더링마다 진짜 값을 새로 읽는다

덮개가 없을 때 useOptimistic(value)는 value 그대로다. 그래서 진짜 값이 다른 이유로 바뀌어도(다른 탭에서 수정, 주소 변경, 새로고침된 데이터) 맞추는 코드 없이 화면이 따라간다. useState로 복사본을 둘 때 필요하던 useEffect가 없어도 되는 이유다.

좋아요 버튼

결과가 거의 확실하고, 틀려도 되돌리면 그만인 가장 흔한 사례다. 상태 두 개(눌렀는지, 몇 개인지)를 객체 하나로 덮는다.

'use client';

function LikeButton({ post }: { post: { id: string; liked: boolean; likeCount: number } }) {
  const router = useRouter();
  const [shown, setOptimistic] = useOptimistic({ liked: post.liked, count: post.likeCount });

  return (
    <button
      aria-pressed={shown.liked}
      onClick={() => {
        const next = !shown.liked;
        startTransition(async () => {
          setOptimistic({ liked: next, count: shown.count + (next ? 1 : -1) });
          await setLike(post.id, next); // 서버에 저장
          router.refresh();             // 서버가 새 post를 내려 주게 한다(진짜 값 바꾸기)
        });
      }}
    >
      {shown.liked ? '♥' : '♡'} {shown.count}
    </button>
  );
}
  • 다음 값을 post.liked가 아니라 shown.liked에서 계산한다. 빠르게 두 번 눌러도 화면에 보이는 값을 기준으로 뒤집힌다.
  • router.refresh()도 transition 안에서 불렀으므로, 새 post가 그려질 때까지 덮개가 유지된다.

채팅 메시지 보내기

보내는 중인 메시지를 흐리게 보여 주는 사례다. React 공식 문서의 예와 같은 모양이다. 목록에 더하므로 계산 함수 형태를 쓰고, <form action>으로 보낸다.

'use client';

type Message = { id: string; text: string; sending?: boolean };

function Chat({ messages, send }: { messages: Message[]; send: (text: string) => Promise<void> }) {
  const [shown, addOptimistic] = useOptimistic(messages, (current, text: string) => [
    ...current,
    { id: `temp-${current.length}`, text, sending: true },
  ]);

  return (
    <>
      <ul>
        {shown.map((m) => (
          <li key={m.id} className={m.sending ? 'opacity-50' : ''}>
            {m.text} {m.sending && '(보내는 중)'}
          </li>
        ))}
      </ul>
      <form
        action={async (formData) => {
          const text = String(formData.get('text'));
          addOptimistic(text); // form action은 이미 transition이라 startTransition이 필요 없다
          await send(text);    // 부모가 messages를 바꾼다
        }}
      >
        <input name="text" />
        <button>보내기</button>
      </form>
    </>
  );
}
  • 임시 id: 진짜 id는 서버가 만든다. 임시 항목에는 임시 id를 주고, 덮개가 걷히면 진짜 항목(진짜 id)으로 바뀐다. 서버가 만드는 값은 짐작하지 않고 자리만 채운다.
  • 상태 표시: sending 같은 표시를 넣어 "아직 확정이 아니다"를 보여 줄 수 있다.
  • 다른 사람의 메시지: 보내는 중에 messages가 바뀌어도 새 목록 위에 다시 붙는다(특징 5).

목록에서 지우기

지우는 것도 덮개로 표현한다. 지울 id를 넘기면 목록에서 뺀 값을 보여 준다.

const [shownTodos, removeOptimistic] = useOptimistic(todos, (current, id: string) =>
  current.filter((todo) => todo.id !== id),
);

function onDelete(id: string) {
  startTransition(async () => {
    removeOptimistic(id);
    const ok = await deleteTodo(id);
    if (!ok) toast('지우지 못했습니다'); // 덮개가 걷히면 항목이 다시 나타난다
    else startTransition(() => setTodos((prev) => prev.filter((t) => t.id !== id)));
  });
}

실패하면 항목이 다시 나타난다. 사라졌던 것이 돌아오면 사용자가 놀라므로 알림을 함께 띄운다.

설정 스위치와 서버 함수

Next의 서버 함수(Server Function, 'use server')와 함께 쓰는 사례다. 서버 함수가 데이터를 바꾸고 revalidatePath로 페이지를 다시 그리게 하면, 새 props가 진짜 값이 된다. 

// actions.ts
'use server';
export async function setNotification(on: boolean) {
  await db.update(settings).set({ notification: on });
  revalidatePath('/settings'); // 서버가 새 settings로 페이지를 다시 그린다
}

// notification-switch.tsx
'use client';
export function NotificationSwitch({ on }: { on: boolean }) {
  const [shownOn, setOptimisticOn] = useOptimistic(on);
  return (
    <Switch
      checked={shownOn}
      onCheckedChange={(next) => {
        startTransition(async () => {
          setOptimisticOn(next);
          await setNotification(next); // 새 페이지까지 받아 온 뒤에 끝난다
        });
      }}
    />
  );
}

서버 함수 호출이 끝날 때 새로 그린 페이지도 함께 도착하므로, 덮개가 걷히는 순간 on은 이미 새 값이다.

주소를 바꾸는 필터 칩

이 저장소의 사례다. 칩은 주소의 값(query.genre)을 그대로 보여 주는 제어 컴포넌트라서, 주소가 바뀌기 전(서버가 새 페이지를 그리기 전)에는 눌러도 켜지지 않는다. 덮개로 그 사이를 메운다. 

const [shownQuery, setShownQuery] = useOptimistic(query);

// 장르 칩을 누르면
const next = getGenreChangeQuery({ query: shownQuery, value }); // 화면의 쿼리에서 다음 쿼리를 만든다
startTransition(() => {
  setShownQuery(next);
  router.replace(getShowListHref(next)); // 화면 이동도 transition이라 새 페이지가 그려질 때 함께 끝난다
});

임시 값을 장르와 판매 상태로 나누지 않고 쿼리 전체 하나로 둔 것이 요점이다. 다음 값은 진짜 값(query)이 아니라 보이는 값(shownQuery)에서 만든다는 규칙(헷갈리기 쉬운 점)을 칩 줄 두 개에 걸쳐 지키려면, 두 칩 줄이 같은 보이는 값을 봐야 한다.

다른 사례와 달리 비동기 함수가 아니다. router.replace가 안에서 transition을 열고, 새 페이지가 서버에서 올 때까지 그 transition이 끝나지 않기 때문에 덮개가 유지된다. 왜 제어 컴포넌트로 뒀는지, 실험 결과는 store-logic 01 문서에 있다.

쓰지 않는 편이 나은 때

낙관적 업데이트는 "거의 성공한다"는 가정 위에 있다. 가정이 깨지기 쉽거나, 깨졌을 때 되돌리는 것이 혼란스러우면 쓰지 않는다.

상황 이유 대신
좌석 선점, 결제, 예매 확정 다른 사람과 경쟁해 실패가 흔하다. "예매됨"을 보였다가 되돌리면 사용자가 믿고 떠날 수 있다 isPending으로 처리 중을 보이고 서버의 답을 기다린다
서버가 값을 정한다(가격 계산, 재고 수량) 짐작한 값이 틀리기 쉽다 자리만 비워 두고 답을 기다린다
되돌릴 수 없는 일(메일 발송, 삭제 후 복구 불가) 보여 준 결과를 되돌려도 실제로 일어난 일은 안 돌아온다 확인을 받고, 처리 중을 보인다

헷갈리기 쉬운 점

  • 임시 값은 상태가 아니다. setOptimistic으로 넣은 값은 저장되지 않는다. transition이 끝나면 사라지므로, 남기고 싶은 결과는 반드시 진짜 값(상태, props, 서버 데이터)에 넣어야 한다.
  • "일정 시간"이 아니라 "작업이 끝날 때까지"다. 서버가 0.1초 만에 답하면 0.1초, 5초 걸리면 5초 동안 보인다.
  • 진짜 값을 바꾸는 일까지 transition 안에 넣어야 한다. 진짜 값을 다시 받아 오는 일(router.refresh, 상태 갱신)이 transition이 끝난 뒤에 일어나면, 덮개가 먼저 걷혀 원래 값이 잠깐 보인다. 비동기 함수를 startTransition에 넘겨, 저장과 새로 받기를 모두 그 안에서 await한다.
  • 다음 값은 보이는 값에서 계산한다. 좋아요 토글처럼 이전 값으로 다음 값을 만들 때 진짜 값(post.liked)을 쓰면, 연속으로 눌렀을 때 옛 값을 기준으로 계산한다.
  • useTransition의 isPending과 함께 쓸 수 있다. 덮개로 결과를 먼저 보이고, isPending으로 "저장 중" 같은 작은 표시를 더할 수 있다.

확인 문제

1. 좋아요를 누르면 ♥ 13이 잠깐 보였다가 ♡ 12로 돌아가고, 조금 뒤 ♥ 13이 된다. 무엇이 문제인가?

덮개는 언제 걷히나 절. 코드는 아래와 같다.

async function onClick() {
  startTransition(() => {
    setOptimistic({ liked: true, count: 13 });
  });
  await setLike(post.id, true);
  router.refresh();
}
답 보기

transition에 든 것이 setOptimistic 한 줄뿐이라, transition이 곧바로 끝나 덮개가 걷힌다. 그 순간 진짜 값 post는 아직 옛 값(♡ 12)이다. 서버 저장과 router.refresh()는 transition이 끝난 뒤에 일어나므로, 새 페이지가 와서야 ♥ 13이 된다. 저장과 새로 받기를 비동기 transition 안으로 옮긴다: startTransition(async () => { setOptimistic(...); await setLike(...); router.refresh(); }).

2. 채팅에서 내 메시지를 보내는 중에 다른 사람의 메시지가 도착했다. 아래 두 코드 중 다른 사람의 메시지가 바로 보이지 않는 쪽은?

특징 4번과 5번.

// (가)
const [shown, setShown] = useOptimistic(messages);
setShown([...messages, mine]);

// (나)
const [shown, add] = useOptimistic(messages, (current, m) => [...current, m]);
add(mine);
답 보기

(가)다. 내 메시지는 보이지만 다른 사람의 메시지는 덮개가 걷힐 때까지 보이지 않는다. 넣은 순간의 messages로 만든 배열을 그대로 덮어 두기 때문에, 진행 중에 messages가 바뀌어도 덮개가 옛 목록을 보여 준다. (나)는 새 messages 위에서 함수를 다시 실행하므로 다른 사람의 메시지와 내 메시지가 모두 보인다. 목록에는 (나)를 쓴다.

3. 공연 좌석 선택 화면에서 "선점하기"를 누르면 바로 "선점 완료"를 보여 주자는 제안이 나왔다. 어떻게 답하겠는가?

쓰지 않는 편이 나은 때 절.

답 보기

쓰지 않는 편이 낫다. 인기 공연의 좌석은 여러 사람이 동시에 노리므로 실패가 흔하다. "선점 완료"를 보였다가 되돌리면 사용자는 이미 잡았다고 믿고 결제로 넘어가거나 화면을 떠날 수 있다. 버튼을 처리 중 상태(isPending)로 바꾸고 서버의 답을 기다린 뒤 결과를 보인다.
