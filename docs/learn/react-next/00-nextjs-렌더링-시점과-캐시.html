Next.js 렌더링 시점과 캐시: connection, 정적 쉘, use cache, io

스토어 첫 페이지의 await connection() 한 줄에서 출발해, Next.js가 코드를 언제 실행하고 결과를 어떻게 캐시하는지 정리한다. 기준 버전은 Next.js 16.4이다. 공식 문서는 canary 기준이라, 설치된 16.4.5에 io, cacheLife, cacheTag, cacheComponents가 있는 것을 따로 확인했다.

한눈에 보기

Next.js의 렌더링 질문은 결국 하나다. 이 코드를 빌드 때 실행해 결과를 굳혀 둘까, 요청이 올 때마다 실행할까? 이 문서의 도구는 모두 이 질문에 답하는 방법이다.

도구 한 줄 설명 우리 코드에서
connection() 여기부터는 실제 요청이 올 때 실행하라 사용 중
unstable_noStore() 이 컴포넌트는 캐시하지 마라. v15에서 connection()으로 대체됨 안 씀
Cache Components 한 페이지 안에서 미리 그릴 부분과 요청 때 그릴 부분을 나누는 모드 꺼져 있음
정적 쉘 빌드 때 미리 만들어 바로 보내는 페이지 뼈대 HTML Cache Components를 켜야 생김
'use cache' 이 함수나 컴포넌트의 결과를 캐시하라 안 씀
cacheLife / cacheTag 캐시의 수명 / 무효화용 이름표 안 씀
io() 이 뒤에 실행할 때마다 값이 달라지는 작업이 있다 안 씀

빌드 때 페이지를 미리 그린다

우리 스토어 페이지는 이렇게 생겼다.

// apps/store/apps-src/_index/index-page.tsx
import { connection } from 'next/server';
import { createServerApiClient } from '@shared/api/client';
import { fetchShows } from '@shared/api/shows';

export default async function HomePage() {
  // 이 페이지는 빌드 때 미리 그리지 않고 요청마다 렌더링한다. 그래서 빌드에 API와 DB가 필요 없다.
  await connection();
  const shows = await fetchShows(createServerApiClient());

  return (
    <main>
      <h1>공연</h1>
      <ul>
        {shows.map((show) => (
          <li key={show.id}>{show.title}</li>
        ))}
      </ul>
    </main>
  );
}

next build는 라우트마다 컴포넌트를 실제로 실행해 보고, HTML을 미리 만들어 둘 수 있는지 시험한다. 이것을 사전 렌더링(prerendering)이라 한다. 요청마다 달라질 이유가 보이지 않으면 그 결과를 정적 페이지로 굳힌다.

Next가 "요청마다 달라진다"고 알아채는 단서는 cookies(), headers() 같은 요청 시점 API다. 우리 페이지는 이런 API를 쓰지 않는다. fetchShows는 openapi-fetch를 거쳐 평범한 fetch를 부를 뿐이다. 그래서 connection()이 없으면 Next는 이 페이지를 정적으로 만들 수 있다고 보고, 빌드 중에 API를 실제로 호출한다.

connection()이 없으면 빌드 결과가 둘 중 하나가 된다.

  • API가 꺼져 있으면 연결이 거부되어 빌드가 실패한다.
  • API가 켜져 있으면 빌드 시점의 공연 목록이 HTML에 굳는다. 이후 DB가 바뀌어도 화면은 그대로다.

connection()이 하는 일

공식 문서의 정의: 렌더링을 이어가기 전에 실제 사용자 요청이 들어올 때까지 기다리라고 Next에 알린다. 

function connection(): Promise<void>
  • 인자가 없다.
  • void Promise를 돌려주고, 반환값은 쓰라고 만든 것이 아니다. await해서 "여기부터"라는 시점을 표시하는 용도로만 쓴다.
  • 문서는 요청 시점 API를 쓰지 않는데도 요청마다 결과가 달라야 할 때 쓰라고 한다. 문서의 예는 Math.random()과 new Date()다. 우리는 "DB 값을 요청마다 새로 읽어야 한다"가 그 이유다.

멈추는 것은 빌드가 아니라 이 페이지의 사전 렌더링이다

같은 함수가 빌드 때와 요청 때 다르게 실행된다.

next build (사전 렌더링 시도)
  1. HomePage() 실행
  2. await connection() → 이 페이지의 사전 렌더링을 그만둠
  3. fetchShows는 실행되지 않음 → API, DB 필요 없음
  4. 라우트를 Dynamic(ƒ)으로 표시하고 다음 라우트로
실제 요청 GET /
  1. HomePage() 실행
  2. await connection() → 바로 통과
  3. fetchShows 실행 → 항상 최신 DB 값
  4. HTML 응답

빌드 출력에서 결과를 확인할 수 있다. API와 DB를 모두 끈 상태에서도 빌드가 통과한다.

Route (app)
┌ ƒ /
└ ○ /_not-found
○  (Static)   prerendered as static content
ƒ  (Dynamic)  server-rendered on demand

noStore, force-dynamic과의 관계

같은 목적을 이루는 방법이 시기별로 세 가지 있었다.

방법 범위 상태
export const dynamic = 'force-dynamic' 라우트 전체 동작은 같지만 문서는 connection()을 권장
unstable_noStore() 부른 컴포넌트 v14 도입, v15에서 deprecated
connection() 부른 지점 이후 v15 안정화, 현재 권장

noStore는 왜 생겼고 왜 바뀌었나

Next 14의 App Router는 기본적으로 많은 것을 캐시했다. fetch 결과도 기본으로 캐시됐다. 그래서 동적으로 만들려면 "캐시하지 마"라고 꺼야 했다.

  • fetch를 쓰면 cache: 'no-store' 옵션으로 끌 수 있었다.
  • DB 드라이버나 ORM처럼 fetch가 아닌 방식으로 읽으면 옵션을 줄 곳이 없었다. noStore()가 그 빈자리를 채웠다. 공식 문서 예시도 db.query(...)다. 
import { unstable_noStore as noStore } from 'next/cache';

export default async function ServerComponent() {
  noStore(); // fetch의 cache: 'no-store'와 같은 효과
  const result = await db.query(...);
}

문서에 적힌 교체 이유는 "Next.js의 앞으로의 방향에 맞추기 위해서"뿐이다. 아래는 문서 내용을 바탕으로 한 해석이다.

  • 기본값이 바뀌었다. Next 15부터 fetch는 기본으로 캐시되지 않는다. Cache Components에서는 'use cache'를 붙이지 않는 한 아무것도 캐시되지 않는다. 끌 캐시가 없으니 "no store"라는 이름이 의미를 잃었다.
  • 질문이 바뀌었다. 핵심이 "캐시할까 말까"에서 "빌드 때 실행할까, 요청 때 실행할까"로 옮겨 갔다. connection()은 이 질문에 맞는 이름이다.

Cache Components: 페이지 안에서 부분마다 나누기

지금 우리 설정에서는 라우트 전체가 정적(○)이거나 동적(ƒ)이거나 둘 중 하나다. connection() 한 줄 때문에 <h1>공연</h1>처럼 절대 바뀌지 않는 부분까지 요청마다 서버에서 새로 만든다.

Cache Components는 next.config.ts에서 켜는 모드다. 켜면 컴포넌트 단위로 나눈다. 이 렌더링 방식을 문서는 Partial Prerendering(PPR)이라 부르고, Cache Components의 기본 동작이다. 

// next.config.ts (우리는 아직 켜지 않았다)
const nextConfig: NextConfig = {
  cacheComponents: true,
};

켜면 빌드 때 컴포넌트마다 처리 방식이 정해진다.

컴포넌트가 하는 일 빌드 때 처리
고정 마크업, import, 순수 계산 미리 렌더링
'use cache'가 붙음 실행해서 결과를 캐시하고 미리 렌더링
<Suspense> 안에서 요청에 의존하는 작업 (cookies(), connection(), io() 등) fallback만 미리 렌더링, 내용은 요청 때 스트리밍

Cache Components를 켜면 connection()을 부르는 컴포넌트를 <Suspense>나 loading.js 안에 둬야 한다. 경계가 없으면 그 라우트로의 이동이 즉시 일어나지 않고 막힌다.

정적 쉘

정적 쉘(static shell)은 빌드 때 미리 만들어 두고 요청이 오면 바로 보내는 페이지의 뼈대 HTML이다. 미리 렌더링할 수 있는 모든 내용과, 나중에 채울 동적 부분의 Suspense fallback으로 이루어진다.

공식 문서의 블로그 예시를 쉘 관점에서 나누면 이렇다.

  • BlogPage
    • <header> 정적 쉘 고정 마크업
    • <BlogPosts> 정적 쉘 'use cache' 결과
    • <Suspense> 정적 쉘 fallback("불러오는 중…")만 들어감
      • <UserPreferences> 요청 시점 cookies()를 읽어 스트리밍

정적 쉘이 붙은 세 부분이 빌드 때 만들어져 즉시 응답된다. 요청 시점인 마지막 부분만 요청이 온 뒤 서버가 계산해 fallback 자리에 채워 넣는다. 

export default function BlogPage() {
  return (
    <>
      <header>...</header>              {/* 정적: 자동으로 미리 렌더링 */}
      <BlogPosts />                     {/* 'use cache': 쉘에 포함 */}
      <Suspense fallback={<p>불러오는 중...</p>}>
        <UserPreferences />             {/* cookies(): 요청 때 스트리밍 */}
      </Suspense>
    </>
  );
}
  • 쉘은 CDN에서 바로 보낼 수 있다. 서버까지 가지 않으니 첫 화면이 즉시 뜬다.
  • 쉘에는 첫 접속용 HTML과, 다른 페이지에서 넘어올 때 쓰는 RSC Payload가 함께 들어 있다.
  • 빈칸으로 남은 부분만 서버가 요청 때 계산해 이어서 보낸다.

'use cache'

'use client'처럼 문자열로 적는 지시어다. 자기를 감싸고 있는 async 함수나 컴포넌트의 반환값을 캐시한다.

붙이는 자리: 함수 본문의 첫 줄

호출하는 곳에 붙이는 것이 아니다. 캐시하려는 함수 안, 본문의 첫 줄에 적는다. 'use strict'를 함수 첫 줄에 쓰는 것과 같은 문법이다. 실행 문장이 아니라 "이 함수는 이렇게 다뤄라"는 표시라서 맨 앞에 와야 한다. 

async function getTask(id: string) {   // ← 캐시되는 함수
  'use cache'                          // ← getTask 본문의 첫 줄
  cacheLife('hours')
  cacheTag('tasks', `task-${id}`)
  return getTaskById(id)               // ← 안에서 DB를 읽는 실제 호출 (지시어와 무관)
}

호출하는 쪽은 평범하게 부른다. 캐시를 쓸지는 함수 쪽에서 이미 정했다.

await getTask('42') // 수명 안이면 캐시 결과를 돌려주고, getTaskById는 실행하지 않는다
await getTask('42') // 같은 인자 → 같은 캐시 항목
await getTask('7')  // 다른 인자 → 별도 캐시 항목, 이때는 getTaskById가 실행된다

붙일 수 있는 자리 세 가지

자리 캐시되는 것
데이터 함수 본문의 첫 줄 그 함수의 반환값 (예: getProducts())
컴포넌트 본문의 첫 줄 그 컴포넌트의 렌더링 결과 (예: BlogPosts)
파일의 첫 줄 ('use client'와 같은 자리) 그 파일에서 export한 async 함수 전부

알아 둘 성질

  • 캐시 키: 인자와 바깥에서 가져다 쓴 값이 자동으로 키가 된다. 입력이 다르면 캐시 항목도 다르다.
  • 쉘에 들어간다: 수명이 너무 짧지 않으면 결과가 정적 쉘에 포함된다.

캐시 결과는 모든 사용자가 공유한다. 로그인한 사용자의 정보처럼 사람마다 달라야 하는 데이터에 붙이면 다른 사람의 데이터가 보일 수 있다.

cacheLife: 시간 기준 수명

'use cache' 함수 안에서 부른다. 캐시 하나에 세 개의 시간을 붙인다. 'hours' 같은 이름은 세 값을 묶어 둔 프로필이다.

값 뜻 'hours'
stale 브라우저가 서버에 묻지 않고 가진 값을 그대로 쓰는 시간 5분
revalidate 이 시간이 지나면 다음 요청에는 일단 옛 값을 주고, 뒤에서 새로 계산한다 1시간
expire 이 시간이 지나면 옛 값을 주지 않고, 요청이 새 계산을 기다린다 1일

getTask('42')를 처음 부른 뒤를 시간 순서로 보면 이렇다.

캐시를 만든 뒤 요청이 오면
0 ~ 1시간 캐시를 그대로 돌려준다
1시간 ~ 1일 옛 값을 바로 돌려주고, 뒤에서 새로 계산해 캐시를 바꾼다
1일 이후 옛 값을 주지 않는다. 새로 계산할 때까지 요청이 기다린다

"옛 값을 주면서 뒤에서 갱신한다"는 방식을 stale-while-revalidate라 한다. 사용자는 기다리지 않고, 다음 사람은 새 값을 받는다.

선택 읽기: 기본 제공 프로필 전체
프로필 stale revalidate expire
default5분15분만료 없음
seconds30초1초1분
minutes5분1분1시간
hours5분1시간1일
days5분1일1주
weeks5분1주30일
max5분30일1년

프로필 이름 대신 객체로 세 값을 직접 정할 수도 있다.

cacheLife를 빼면 default가 적용된다. revalidate 15분에 시간으로는 만료되지 않는다. 문서는 수명이 코드에서 보이도록 'use cache'마다 cacheLife를 함께 쓰라고 권한다.

cacheTag: 이벤트 기준 무효화

시간만으로는 부족한 경우가 있다. 운영자가 공연 제목을 고쳤다면 1시간을 기다리지 않고 바로 반영돼야 한다. 이때 캐시에 이름표를 붙여 두고, 데이터가 바뀌면 그 이름표로 캐시를 찾아 무효화한다. 

cacheTag('tasks', `task-${id}`)
// 'tasks'   → 목록 전체를 버릴 때 쓰는 넓은 이름표
// 'task-42' → 이 항목 하나만 버릴 때 쓰는 좁은 이름표

무효화하는 쪽에서는 아래 둘 중 하나를 부른다.

함수 동작 쓸 수 있는 곳
updateTag('task-42') 즉시 만료한다. 다음 요청은 새 값을 기다린다. 방금 고친 사람이 자기 수정 결과를 바로 봐야 할 때 쓴다. Server Action만
revalidateTag('tasks', 'max') 옛 값이라고 표시만 한다. 다음 요청은 옛 값을 받고, 뒤에서 갱신된다. 두 번째 인자로 옛 값을 줘도 되는 기간을 정한다. Server Action, Route Handler

무효화는 함수를 부른 순간이 아니라 그 데이터를 다음에 요청할 때 일어난다. 태그가 붙은 페이지가 한꺼번에 다시 계산되지 않고, 방문되는 대로 하나씩 갱신된다.

cacheLife와 cacheTag는 함께 쓴다. 평소에는 시간 기준으로 갱신하고, 데이터가 바뀌는 사건이 있으면 이름표로 바로 무효화한다.

io(): connection()과 무엇이 다른가

왜 "멈출 지점"이 필요한가

Cache Components에서 Next는 빌드 때 컴포넌트를 실행해 보고 결과를 쉘에 넣을지 정한다. 그런데 new Date()나 Math.random()은 동기 함수라 Next가 중간에 가로챌 수 없다. 그대로 두면 빌드 시각이나 빌드 때 뽑은 난수가 쉘에 굳어 버린다. 그래서 그 앞에 await 지점을 하나 두게 해, Next가 거기서 멈출 기회를 얻는다. connection()과 io()는 둘 다 이 멈출 지점이다.

connection()으로는 안 되는 경우

현재 시각으로 인사말을 만드는 함수를 두 곳에서 쓰고 싶다고 하자.

async function greeting() {
  await connection() // 사전 렌더링 때 시각이 굳지 않게
  const hour = new Date().getHours()
  return hour < 12 ? '좋은 아침' : '좋은 오후'
}

// ① 캐시 없는 곳: 요청마다 계산하면 된다
<Suspense><Header text={await greeting()} /></Suspense>

// ② 캐시하는 컴포넌트: 한 번 계산해서 캐시하고 싶다
async function Banner() {
  'use cache'
  const text = await greeting() // 💥 connection()이 캐시 범위 안에서 오류를 던진다
}

connection()은 "실제 요청을 기다려라"는 뜻인데, 캐시 범위 안에는 기다릴 요청이 없다. 캐시는 여러 요청이 공유하는 결과이기 때문이다. 그래서 오류를 던지고, greeting()을 캐시용과 비캐시용 두 벌로 만들어야 한다.

io()는 상황에 따라 알아서 동작한다

import { io } from 'next/cache'

async function greeting() {
  await io()
  const hour = new Date().getHours()
  return hour < 12 ? '좋은 아침' : '좋은 오후'
}
어디서 불렸나 connection() io()
캐시 밖, 사전 렌더링 중 사전 렌더링을 멈춤 사전 렌더링을 멈춤 (같음)
'use cache' 안 오류 즉시 통과 → 캐시를 채울 때 한 번 계산해 저장
Cache Components 꺼짐 라우트를 동적으로 만듦 우리 경우 즉시 통과 (효과 없음)
실제 요청, 브라우저 통과 즉시 통과

io()는 "기다려라"가 아니라 "이 뒤에 실행할 때마다 값이 달라지는 작업이 있다"는 표시다. 그 표시를 어떻게 다룰지는 Next가 정한다. 캐시 밖이면 쉘에서 빼고, 캐시 안이면 캐시가 값을 고정하게 둔다.

문서는 쉘에서 빼는 용도라면 io()를 쓰고, 정말 실제 요청을 기다려야 할 때만 connection()을 쓰라고 한다. 이름으로 보면 connection()은 요청에 대한 말이고, io()는 작업의 성격에 대한 말이다. 현재 시각을 읽는 데 요청이 필요한 것은 아니니, new Date() 앞에는 io()가 의미상 더 맞다. 이 마지막 부분은 문서를 바탕으로 한 해석이다.

Client Component에서는 await 대신 use(io())로 쓴다.

우리 프로젝트에서는

  1. 지금은 connection()이 맞다 Cache Components를 켜지 않았다. 이 상태에서 io()는 즉시 통과해 아무 효과가 없다. 페이지를 동적으로 만들어 빌드에서 API를 부르지 않게 하려면 connection()이 필요하다.
  2. 켠다면 페이지를 나눌 수 있다 <h1>공연</h1>은 정적 쉘로 미리 나가고, 공연 목록은 <Suspense> 안에서 스트리밍하거나 'use cache'로 캐시할 수 있다.
  3. 캐시하면 무효화 경로가 필요하다 공연을 수정하는 코드는 Next의 Server Action이 아니라 NestJS API에 있다 (CODING_STANDARDS.md: 비즈니스 로직은 API에 둔다). updateTag는 Server Action에서만 쓸 수 있으니, Next에 Route Handler를 만들고 API가 그것을 호출해 revalidateTag를 부르는 식이 될 것이다.
  4. 결정은 나중에 한다 스펙 #1은 "캐시 전략은 실제 조회 화면이 생길 때 정한다"고 미뤄 두었다. 1.3 이후 조회 화면을 만들 때 Cache Components 도입과 무효화 경로를 함께 검토한다.

스스로 확인하기

질문에 먼저 답해 본 뒤, 눌러서 답을 확인한다.

1. page.tsx에서 connection()을 fetchShows 호출 아래로 옮기면 어떻게 되는가?

사전 렌더링은 await connection()에 도달해야 멈춘다. 그 위에 있는 fetchShows는 빌드 때 실행되므로, API가 꺼져 있으면 빌드가 실패한다. 멈출 지점은 요청에 의존하는 작업보다 앞에 있어야 한다.

2. 로그인한 관객의 예매 내역을 읽는 함수에 'use cache'를 붙이면 무엇이 문제인가?

캐시 결과는 모든 사용자가 공유한다. 캐시 키가 사용자를 구분하지 않으면 다른 관객의 예매 내역이 보일 수 있다. 사람마다 다른 데이터는 캐시하지 않고 <Suspense> 안에서 요청 때 렌더링한다.

3. cacheLife('hours')를 붙인 공연 목록이 있다. 운영자가 공연을 추가한 지 30분 뒤에 관객이 접속하면 새 공연이 보이는가? 바로 보이게 하려면?

보이지 않는다. revalidate가 1시간이라 30분 뒤에는 캐시가 그대로 쓰인다. 바로 보이게 하려면 목록에 cacheTag('shows')를 붙이고, 공연이 추가될 때 revalidateTag('shows', 'max')를 불러야 한다. 우리 구조에서는 이 호출을 NestJS API가 Next의 Route Handler를 통해 일으켜야 한다.

4. io()가 있는데 connection()은 왜 남아 있는가?

문서는 "실제 요청을 기다려야 할 때"는 connection()을 쓰라고 한다. 둘은 캐시 범위 안에서 다르게 동작한다. 아래는 그 차이에 대한 해석이다. 실제 요청이 있어야만 의미가 있는 작업이 캐시 범위 안에서 조용히 통과하면, 한 요청의 결과가 모두에게 공유될 수 있다. connection()은 그 경우 오류를 던지므로 실수가 드러난다.
