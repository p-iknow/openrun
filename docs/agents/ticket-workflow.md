# 티켓 작업 규칙

`/implement #<번호>`로 티켓을 구현할 때 처음부터 끝까지 따른다. 학습이 목적인 프로젝트이므로, 사용자가 코드를 설명할 수 있게 되어야 티켓이 끝난다.

## 단계

1. **브랜치:** 최신 `main`에서 티켓 브랜치를 만든다. 이름은 `<번호>-<짧은-설명>`으로 한다. 현재 브랜치가 이미 이 티켓의 브랜치이면 그대로 쓴다. 완료 기준: 티켓 브랜치에 있다.
2. **구현과 점검:** `/implement`의 절차대로 구현하고 커밋한다. `/code-review`의 지적을 아래 "지적 처리"대로 나눈다. 완료 기준: 명백한 문제를 모두 고쳤고, 판단이 필요한 지적은 사용자가 모두 결정해 반영했으며, 테스트와 타입 검사, 통합 테스트(`test:integration`), 빌드(`pnpm build`)가 통과한다. 통합 테스트와 빌드(Storybook 빌드 포함)는 pre-commit에서 돌지 않으므로 PR을 열기 전에 직접 실행한다.
3. **PR:** 브랜치를 push하고 `pr` 스킬 양식으로 PR을 연다. 아래 "PR 추가 내용"을 넣고 `Closes #<번호>`로 티켓을 연결한다. 완료 기준: PR 주소를 사용자에게 알렸다.
4. **리뷰:** 사용자의 질문에 현재 코드를 근거로 답하고, 요청받은 수정을 같은 브랜치에 커밋한다. 완료 기준: 사용자가 리뷰를 마쳤다고 말했다.

병합은 사용자가 직접 한다.

## 지적 처리

- **명백한 문제:** 버그, 스펙 누락, 표준 위반처럼 답이 하나인 지적은 PR을 열기 전에 고친다.
- **판단이 필요한 지적:** 설계 선택처럼 답이 여러 개인 지적은 PR을 열기 전에 세션에서 선택지와 추천을 보여 주고 사용자에게 결정을 받는다. 결정대로 고쳐 커밋하고, 결정과 이유를 PR의 "리뷰에서 정한 것"에 적는다.

## PR 추가 내용

`pr` 스킬 양식 뒤에 아래 섹션을 붙인다.

```markdown
## 왜 이렇게 했나

<핵심 결정과 이유>

## 쓰지 않은 대안

<고려한 대안과 고르지 않은 이유>

## 리뷰에서 정한 것

<판단이 필요했던 지적마다 사용자의 결정과 이유>

## 이해 확인 질문

<꼭 필요한 면접식 질문>
```

판단이 필요한 지적이 없었으면 "리뷰에서 정한 것" 섹션을 생략한다.

## 이해 확인 질문

- 백엔드나 인프라를 바꾼 PR에 넣는다. 화면 UI만 바꾼 PR에는 "이해 확인 질문" 섹션을 생략한다.
- 이 PR의 코드에서 나온 판단과 실패 상황을 묻는다. 예: "여기서 트랜잭션이 끝나기 전에 서버가 죽으면 주문은 어떻게 되는가?"
- 개수는 정하지 않는다. 사용자가 답하지 못하면 이 PR을 설명할 수 없는 것만 고르고, 그런 것이 없으면 섹션을 생략한다.
- 질문에 대한 답을 PR에 적지 않는다.
- 사용자는 세션에서 말로 답한다. 빈틈을 구체적으로 짚고 함께 파고든다. 면접에 쓸 만한 내용은 사용자에게 확인한 뒤 해당 단계의 `docs/stage-notes/` 문서에 남긴다.
