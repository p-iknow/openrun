# 이력서 문장과 측정값

`[ ]`는 구현과 측정 후 실제 값으로 채운다. 하지 않은 내용은 쓰지 않으며, 수치는 부하 테스트 결과임을 밝힌다.

이력서에는 가장 깊게 다룬 3~5개만 고른다. 추천 우선순위는 동시성, 결제 정합성, 트래픽 제어, 쿼리 성능, 장애 대응 순이다.

## 항목

### 동시성과 트랜잭션 (6단계)
동시 [N]건 예매 부하 테스트로 중복 예매 [N]건을 재현하고, [락 방식]을 비교·적용해 중복 예매 0건과 처리량 [N] TPS를 달성

### 좌석 선점 (6단계)
결제 전 좌석을 [N]분간 선점하고 만료 시 자동 해제하는 구조를 [구현 방식]으로 설계해 미결제 좌석의 장기 점유 방지

### 비동기 처리 (7단계)
트랜잭셔널 아웃박스와 [큐 기술]로 티켓 발급을 비동기화해, 워커 강제 종료 테스트에서 작업 유실 [N]건과 API p95 [N]ms → [N]ms 확인

### 결제 정합성 (8단계)
멱등 키와 주문 상태 머신으로 중복 승인·웹훅 중복 수신을 처리하고, [N]개 장애 시나리오 테스트에서 결제와 주문 상태 불일치 [N]건 확인

### 쿼리와 캐시 성능 (9단계)
- [N]건 데이터에서 실행 계획을 분석해 [인덱스·쿼리 개선]을 적용하고, 조회 p95를 [N]ms → [N]ms로 단축
- [캐시 대상]에 [캐시 전략]을 적용해 DB 부하를 [N]% 줄이고 캐시 적중률 [N]% 달성

### 트래픽 제어 (10단계)
[자료구조] 기반 입장 대기열로 동시 진입량을 제어해, 동시 접속 [N]명 테스트에서 오류율 [N]% → [N]%로 개선

### 실시간 통신 (11단계)
[전송 방식]과 [메시지 브로커]로 다중 서버 환경의 좌석 상태 전달을 구현하고, 동시 연결 [N]개에서 전달 지연 p95 [N]ms 측정

### 인증과 보안 (1단계)
[인증 방식]과 역할 기반 접근 제어를 구현하고, 타인 예매 조회·결제 금액 조작을 차단하는 서버 검증과 보안 테스트 [N]건 작성

### API 설계와 테스트 (1~2단계)
OpenAPI로 API [N]개를 문서화하고, Testcontainers 기반 통합 테스트 [N]건을 CI에 연동해 핵심 예매 흐름을 자동 검증

### 운영과 장애 대응 (5, 13단계)
- 메트릭·로그·트레이스를 구축해 [실제 병목]을 찾아 [해결 방법]으로 개선하고, p95 [N]ms → [N]ms 달성
- [DB·Redis·서버] 장애 훈련을 [N]회 수행해 복구 절차를 문서화하고, 복구 시간 [N]분 측정

### 부하 테스트 (5, 6, 10단계)
k6로 예매 오픈 트래픽을 시뮬레이션해 [N] TPS 지점의 [병목]을 찾고, 개선 후 처리량을 [N] → [N] TPS로 향상

## 면접 대비 질문
- 결제 성공 후 좌석 확정 전에 서버가 죽으면?
- 선점 만료 순간에 결제 요청이 들어오면?
- Redis가 죽으면 대기열과 예매는?
- 부하 테스트가 실제 트래픽을 얼마나 대변하는가?
- 트래픽이 10배 늘면 어디가 먼저 무너지는가?
- 사용자가 좌석 상태를 늦게 봐도 괜찮은 이유는?
